# 第 16 章 · 成本归因与预算控制：谁花了这 2.83 亿

> 读完你能回答：
> ① 五维归因是哪五维，各自服务谁？
> ② 哪些成本能直接算到人头上，哪些只能分摊？
> ③ 共享资源（缓存池、冗余卡）按什么摊才公平？
> ④ 硬限额和软预警分别设在多少，超了怎么办？
> ⑤ 配额为什么要预扣，定时汇总行不行？

---

## 1. 问题：月底一张总账单

财务把 2.83 亿的账单发过来，只有一行：推理服务，全年 2.83 亿。

三个业务线立刻吵起来：

- 售后说："我们只占三成流量，凭什么摊三分之一？"
- 物流说："我们的请求都很短，凭什么按请求数摊？"
- 营销说："我们只在活动期间用，平时不用，凭什么按年摊？"

三种说法都有道理，因为它们争的不是"总量"，是"分摊口径"。而口径不定义清楚，这件事永远吵不完。

成本归因要解决的就是这个：把总额拆到能认领的粒度，并且让被拆的人接受拆法。

## 2. 五维归因

一笔成本可以从五个角度看，每个角度服务不同的人。

| 维度 | 粒度 | 例子 | 谁在看 |
|---|---|---|---|
| 租户 | 谁付钱 | tenant-a | 商务、财务 |
| 业务线 | 哪个产品 | 售后 / 物流 / 营销 | 业务负责人 |
| 模型 | 用哪个模型 | 200B MoE / lite-8B / 外部 API | 算法、平台 |
| 请求类型 | 干什么 | 意图分类 / 多步退款 / 政策问答 | 产品 |
| 时间 | 什么时候 | 小时 / 日 / 月 | 容量规划 |

五个维度不是五张报表，是同一份明细的五种切法。所以底下要有一张"请求级明细表"，五维都从它聚合出来——不能各建一套，否则五个数对不上。

明细表的最小字段就是第 15 章那条计量记录：租户、模型、token 四类、结束状态、时间戳。加上业务线和请求类型两个标签，就有了五维。

标签怎么打？两个来源：

- 业务线：按租户配置（一个租户通常属于一个业务线），少数跨线的按 API key 区分
- 请求类型：按意图分类的结果（第 6 章路由器的输出），这个标签是免费的

## 3. 能直接算的 64%，要分摊的 36%

不是所有成本都能追到具体请求。先看结构：

| 成本类型 | 金额 | 占比 | 能不能直接归因 |
|---|---|---|---|
| prefill 与 decode 的算力 | 1.81 亿 | 64% | 能，token × 单价 |
| 冗余与弹性 | 1.02 亿 | 36% | 不能，只能分摊 |

前一行是"真的被某个请求用掉的"，后一行是"为了扛峰值和故障而常备的"。

**36% 靠分摊，不靠计量。** 这个比例决定了归因的精度上限——再怎么精确计量，也只能把 64% 算准，剩下 36% 的方法选择会带来 10 个点以上的差异。

这一条要先跟财务说清楚，否则他们会以为"上了计量系统，账就能算到分"。

### 3.1 勾稽：五个维度必须能加回总账

五维归因最容易出的错不是算错，是**对不上**：租户维度加起来 2.80 亿，业务线维度加起来 2.86 亿，总账 2.83 亿。

所以每天要跑一次勾稽，四条规则：

| 检查 | 期望 | 不等说明什么 |
|---|---|---|
| Σ 租户 = 总账 | 差 <0.1% | 有请求没打租户标签 |
| Σ 业务线 = 总账 | 差 <0.3% | 跨线租户没拆分 |
| Σ 模型 = 总账 | 差 <0.1% | 有调用绕过了计量 |
| Σ 小时 = 日总额 | 差 <0.5% | 跨小时的请求被算重或漏算 |

第三行最值得盯。**有调用绕过计量**通常意味着有人直连了模型服务，没走网关——这既是账的问题，也是安全问题（没走网关就没有鉴权和限流）。

模型维度天然不均衡，可以顺手看出成本结构：

| 模型 | 流量占比 | 成本占比 |
|---|---|---|
| 200B MoE | 55% | 约三分之二 |
| lite-8B | 40% | 约一成 |
| 外部 API | 5% | 约三分之一 |

最后一行是反差最大的：**5% 的流量吃掉三分之一的成本**，因为外部 API 单价 3.5 分/轮，是自建的 12 倍。这一行会直接推动"兜底能不能再少一点"的讨论。

### 3.2 那把全部成本摊进单价行不行

到这里会有一个自然的想法：既然单价里已经含了冗余（第 15 章的 ×1.56），那全部成本都在 token 价里了，按 token 算不就完了？何必再谈分摊？

这个想法对了一半。

**对的一半：收钱确实可以只按 token。** 第 15 章那张价目表就是全成本单价——10.24 里面含了算力、冗余、运营。对外报价按它算，不会亏。

**没解决的一半：内部管账不能只看 token。** 因为"谁用了多少 token"和"谁导致了多少钱"不是一回事。

看一个具体的例子。两条业务线的用量曲线完全不同：

| 业务线 | 月度 token 占比 | 峰值容量占比 | 差 |
|---|---|---|---|
| 售后（平稳） | 80% | 70% | −10 个点 |
| 营销（突发） | 20% | 30% | +10 个点 |

营销只在活动期间用，一个月用 20 天，但活动那几天要占三成容量。售后全天均匀，用得多但不拉高峰值。

按统一 token 单价收钱：

```
营销付 20%
但它导致了 30% 的容量
差额 10 个点 = 2,830 万/年
```

这 2,830 万是售后替营销付的。这就是**交叉补贴**：用量平稳的租户，补贴用量突发的租户。

电信业几十年前遇到过同样的问题：按流量计费、忙时闲时同价，结果闲时用户补贴忙时用户。解法是峰谷差价，本质就是回到分摊。

所以统一 token 单价在技术上完全可行，它是一个**商务选择**：选择让平稳用户补贴突发用户。如果所有租户都接受这个约定，那没问题；只要有一方不接受，就必须回到"用量 + 容量"的双轨。

### 3.3 那缓存池的问题消失了吗

没有消失，只是从"看得见"变成"看不见"。

统一单价下，缓存被挤占导致的命中率下降，不影响账单——因为 cached 和 uncached 同价。用户感觉不到，但成本真实发生了：B 租户命中率从 90% 掉到 70%，它要多算 20% 的 prefill token，只是账单上看不出来。

结果是平台在补贴被挤占的租户。如果挤占长期存在，这笔钱会一直流出去，而且无人认领——直到某天发现"整体成本涨了 15%，但所有租户的用量都没变"。

所以只要缓存是共享的，计量就必须区分 cached 与 uncached。这不是为了收钱，是为了让挤占这件事可见。

### 3.4 一句话的判据

| 场景 | 统一 token 单价够不够 |
|---|---|
| 对外报价、账单 | 够 |
| 业务线考核、预算 | 不够 |
| 容量规划、谁该扩容 | 不够 |
| 缓存/预留等共享资源 | 不够 |

判据是：**你需要"总量"还是需要"归因"。** 收钱只需要总量，管账需要归因。

## 4. 分摊的三种口径

同一个 36%，三种摊法，结果差 20 个百分点。

| 摊法 | 怎么算 | 对谁有利 | 后果 |
|---|---|---|---|
| 按用量 | 按 token 数占比 | 平稳型租户 | 高峰期租户白占容量 |
| 按峰值 | 按峰值并发占比 | 平稳型租户 | 高峰型被重罚 |
| 按预留 | 按预购容量 | 谁预留谁付 | 预留了不用就浪费 |

举个具体的例子。三个租户的用量和峰值不一样：

| 租户 | 日均用量 | 峰值占比 | 按用量摊 | 按峰值摊 |
|---|---|---|---|---|
| A（高峰型） | 30% | 50% | 30% | 50% |
| B（平稳型） | 50% | 30% | 50% | 30% |
| C（长尾） | 20% | 20% | 20% | 20% |

A 是白天集中用，B 是全天均匀用。按用量摊，A 付 30%；按峰值摊，A 付 50%——差 20 个百分点，一年就是 2,000 万。

这个差异不能靠技术解决，是商务决策。业界常见的做法是组合：

```
应付 = 用量费（按 token）+ 容量预留费（按峰值）
     = 64% 按用量 + 36% 按峰值
```

这样 A 付 0.64×30% + 0.36×50% = 37.2%，B 付 0.64×50% + 0.36×30% = 42.8%，C 付 20%。比单纯的任一摊法都更容易接受。

## 5. 缓存池怎么摊

还有一个更麻烦的共享资源：前缀缓存。

A 租户的热门前缀占了缓存池的 40%，把 B 租户的挤出去了。B 的命中率因此从 90% 掉到 70%，成本上升。这笔账算谁的？

三种处理：

| 做法 | 效果 | 代价 |
|---|---|---|
| 不隔离，谁抢到算谁的 | 利用率最高 | 大租户挤小租户，不公平 |
| 按租户配额分池 | 公平 | 小租户分到的池子太小，命中率低 |
| 共享 + 计费时按实际命中率算 | 折中 | 需要精确记录每个租户的命中率 |

我们选第三种：缓存池共享，但计量时用各租户自己的 cached 比例。B 被挤掉了，它的 cached 少，付的钱就少——成本自动转给了占得多的人。

这一条能成立，前提是第 15 章的计量记录里 cached 与 uncached 是分开的。

## 6. 预算控制：三档阈值

归因解决"花了多少"，预算控制解决"能不能继续花"。

三个阈值，动作不同：

| 用量 | 动作 | 谁收到通知 | 用户感知 |
|---|---|---|---|
| 80% | 软预警 | 租户管理员 + 平台 | 无 |
| 95% | 降级 | 租户 + 平台 | 慢一点 / 短一点 |
| 100% | 阻断新请求 | 租户 + 平台 | 429 |

关键设计是 95% 那一档：**不是直接拒绝，是先降级**。

降级的顺序按第 6 章和第 15 章的组合来：

1. 关深度思考（省 3.5 倍成本）
2. 长回答截断到 200 token
3. 非关键请求走 lite-8B
4. 才轮到拒绝

这样做的好处是：预算用完的租户还能用，只是慢一点、笨一点。比直接 429 友好，也比"不设限"可控。

## 7. 配额怎么落地

配额要有三个属性：能实时扣、能预扣、能退。

```
请求进来
  → 查配额（Redis，O(1)）
  → 预扣估算额度（第 15 章的 5.16 分）
  → 检查剩余额度够不够
  → 不够就走降级或拒绝
  → 结束后结算，退回多扣的
```

为什么不能定时汇总？因为一次批量调用就能把月度预算打穿。假设某租户月预算 100 万，定时汇总每 5 分钟一次，这 5 分钟里他可以跑 200 万的量——下个周期才发现，已经晚了。

所以配额必须是**实时强一致**的读，至少在预扣这一步。

Redis 存什么：

```
quota:{tenant}:{month}      已用额度（分）
quota:{tenant}:{month}:hold 冻结中（进行中的请求）
```

两个 key 分开，是为了让"已用"和"进行中"能分别统计。冻结部分超时 5 分钟自动释放（第 15 章）。

### 7.1 配额的三级继承

预算不是一个平铺的数字，是三层结构：

```
公司年度预算 2.83 亿
  ├─ 业务线 A 1.2 亿
  │    ├─ 租户 a1 6,000 万
  │    └─ 租户 a2 6,000 万
  └─ 业务线 B 1.6 亿
```

扣减顺序自下而上检查，自上而下扣：

- 请求进来，先看租户配额够不够
- 租户够了，再看业务线剩余够不够（防止某条线被单个租户吃穿）
- 都够才放行

两级都扣，意味着同一笔消费在两个层级各记一次。这不是浪费存储，是为了让"哪个业务线超了"和"哪个租户超了"能分别回答。

继承规则要定清楚：租户配额是业务线配额的子集，还是独立额度？前者简单（子集用完就停），后者灵活（业务线内部可调剂）。多数公司选后者——给业务线一个池子，线内自己分。

## 8. 超额之后的四种处理

100% 之后不是只有"拒绝"一个选项：

| 处理 | 适用 | 实现 |
|---|---|---|
| 拒绝新请求 | 默认 | 429 + Retry-After |
| 允许透支到 120% | 重要租户 | 白名单 + 事后补签 |
| 降级到共享池 | 有弹性 | 走慢速队列 |
| 转人工审批 | 突发大额 | 工单 |

透支的设计要小心：给谁透支、透支多少、谁批，都要写进合同。技术侧只负责执行——按租户配置一个 `overdraft_ratio`，0 表示不许透支。

## 8.1 一个月的预算是怎么跑的

配额不是设一次就完事，它按月滚动。一个典型流程：

| 时间 | 动作 | 谁做 |
|---|---|---|
| 上月 20 日 | 出下月预测（按近 3 月趋势 + 已知活动） | 财务 + 平台 |
| 上月 25 日 | 分到业务线，业务线分到租户 | 业务负责人 |
| 当月 1 日 | 配额生效 | 平台 |
| 每周一 | 用量周报，超 60% 的提前预警 | 平台 |
| 当月 20 日 | 中期检查，预测超支的申请追加 | 业务 + 财务 |
| 次月 3 日 | 结算，差异分析 | 财务 |

第二步最关键，也最容易糊弄：业务线拿到总额后，往往按上月的比例一分了事。结果用量涨了的租户月初就撞线，用量降了的租户预算闲置。

正确做法是按"用量趋势"分，不是按"上月占比"分。趋势看两点：近四周的斜率，以及有没有已知的活动（大促、新品上线）。

## 9. 失败模式

| 现象 | 根因 | 怎么发现 | 怎么修 |
|---|---|---|---|
| 五个维度的数对不上 | 各建一套报表 | 交叉验证总和 | 统一从明细表聚合 |
| 归因误差超过 10% | 共享成本按单一维度摊 | 对比两种摊法 | 改成用量 + 峰值组合 |
| 租户投诉被多收 | 缓存被挤占但仍按命中计 | 查 cached 比例 | 按实际命中率计量 |
| 预算打穿才发现 | 定时汇总而非实时扣 | 对比日终与实时 | 改预扣 |
| 降级没生效，直接拒绝 | 阈值配置写成同一档 | 查配置 | 80/95/100 三档分开 |
| 透支无人审批 | 白名单太长 | 月度审计 | 收紧白名单 |

第四行最典型。多数系统把配额做成"每日对一次账"，看着能用，实际上防不住批量调用——一个大客户的一次导入就能超支两个月。

## 9.1 归因结果怎么用

归因不是为了让财务好看，是为了改行为。四个典型用法，按见效速度排：

| 用法 | 从归因里看什么 | 见效 |
|---|---|---|
| 砍兜底 | 外部 API 占三分之一成本 | 一周 |
| 缩短长回答 | 输出 token 集中在少数租户 | 两周 |
| 提缓存命中 | 某租户 cached 比例只有 40% | 一月 |
| 调峰谷定价 | 峰时成本是谷时的 4 倍 | 一季度 |

第一条最快。外部 API 只占 5% 流量、三分之一成本，说明兜底策略太宽——其中 60% 的请求本可以自建模型答。把它从 5% 压到 2%，一年省 2,000 万（第 14 章的第 10 条降本措施就是这个）。

第三条最容易被忽略。cached 比例 40% 意味着这个租户的系统提示里混了变量，前缀每次都不同（第 7 章）。改法不是加卡，是让他把变量挪到用户消息里——一行代码，成本降一半。

这也是归因的真正价值：**它把"成本高"这个模糊感受，变成了"这个租户的 cached 比例只有 40%"这种可执行的动作。**

## 10. 什么情况下这些结论不成立

| 结论 | 推翻条件 |
|---|---|
| 36% 必须分摊 | 租户数少于 3 个时，直接按合同谈固定费更简单 |
| 按用量 + 峰值组合摊 | 租户的用量曲线高度一致时，单一口径就够 |
| 95% 降级 | 租户明确要求"超了就直接停"时，跳过降级 |
| 实时预扣 | 内部系统、无计费诉求时，可以只做监控 |

## 11. 验收

1. 能说出你的系统里五维各是什么，明细表能不能支撑五维聚合。
2. 能算出可直算成本与需分摊成本的比例。
3. 能对两个用量曲线不同的租户，分别算出按用量摊和按峰值摊的金额差异。
4. 能设计三档阈值，并说清每档的动作。

## 12. 复盘卡

```
我原来以为…实际…差在：
```

我原来以为成本归因是"把账算准"，实际差在 36% 的共享成本根本没有"准"可言——它只能"摊"，而摊法是个商务决策，不是技术决策。

## 13. 延伸

- 第 14 章：总成本怎么来的，本章是把它拆开
- 第 15 章：计量记录是归因的原料
- 第 17 章：归因结果怎么变成对外报价
- 第 25 章：配额与限流在网关上的实现

结论是：成本归因的上限不在计量精度，在共享成本的分摊口径。64% 可以直接算，36% 只能谈——而这 36% 恰好是决定租户公不公平的那部分，所以它必须是商务和技术的共同决策，技术单方面定一个摊法，一定会在下一次续约时被推翻。
