# 第 15 章 · Token 计量学：账单是怎么一分一分算出来的

> 读完你能回答：
> ① input / cached / output / reasoning 四类 token 怎么分，为什么价格不同？
> ② 缓存命中的那部分凭什么便宜，便宜多少？
> ③ reasoning token 用户看不到，凭什么计费？
> ④ 用户中途取消，已生成的算不算？
> ⑤ 重试、超时、5xx 各怎么计，谁承担？
> ⑥ 平台账和引擎账差 3%，从哪查？

---

## 1. 问题：账单和用户对不上

上线第二个月，三个租户同时投诉账单偏高。查了一周，发现三个不同的原因：

- 一个租户的账单包含了他重试的请求（网关 502 后自动重试，他付了两次钱）
- 一个租户用了思考模型，reasoning token 有 800，他看到的回答只有 200 字，觉得被多收
- 一个租户的请求超时被切断，他收到了半句话，但账单按完整输出算

三个问题都不是"算错了"，是**计量口径没说清**。

这一章把口径定死：四类 token、五种结束状态、三个结算时点。

## 2. 四类 token 与价目表

先看一轮请求的 token 构成：

| 类型 | 数量 | 说明 |
|---|---|---|
| 输入（未命中缓存） | 285 | 用户问题 200 + 检索 85（部分系统提示） |
| 输入（命中缓存） | 1,615 | 系统提示与工具定义的公共前缀 |
| 输出 | 350 | 用户能看到的回答 |
| reasoning | 0 | 本模型不产生，思考模型另算 |

四类分开计量，因为成本结构完全不同。但单价不是拍出来的，要从卡时一路推上去。

### 2.1 第一层：一切换算成卡时

底层只有一个数：**一张卡跑一小时 ¥12.86**（第 14 章：折旧 9.5 + 电 3.0 + 机位网络 0.4）。

所有 token 的成本都是"占了多少卡秒 × 12.86 ÷ 3,600"。

### 2.2 第二层：一个 token 占多少卡秒

这一步要分 prefill 和 decode 算，因为两者的产出速率差 1.6 倍。

prefill 单实例（8 卡）吞吐 118,700 token/s（第 13 章），单卡 14,838 token/s。一秒钟能算 14,838 个 token，所以一个 token 占 1/14,838 卡秒。

decode 单实例在 1,666 并发下每 22.4 ms 出一批 token，单实例 74,375 token/s，单卡 9,297 token/s。

把这两个速率换算成每百万 token 的裸成本：

| 环节 | 单卡吞吐 | 每百万 token 占卡秒 | 裸成本 |
|---|---|---|---|
| prefill | 14,838 token/s | 67.4 卡秒 | ¥0.241 |
| decode | 9,297 token/s | 107.6 卡秒 | ¥0.384 |

**注意这两个数几乎一样**，只差 1.6 倍。所以"prefill 比 decode 便宜"这件事，在第一层是不成立的——纯算力成本两者同一量级。

### 2.3 第三层：池子按峰值配，平均用不到一成

裸成本假设卡是满负荷的。实际不是。

prefill 池 909 卡，年产能要先换算成秒——一年 8,760 小时，就是 3,154 万秒：

```
年产能 = 909 卡 × 14,838 token/s × 3,154 万秒 = 4.25e14 token
实际需求 = 1.56 万亿（只有 15% 输入未命中缓存）
利用率 = 1.56e13 ÷ 4.25e14 = 3.7%
```

decode 池 87.5 个实例，按 token 产出算：

```
年产能 = 87.5 × 74,375 token/s × 3,154 万秒 = 2.05e14 token
实际产出 = 19.2 万亿
利用率 = 1.92e13 ÷ 2.05e14 = 9.4%
```

注意 decode 这里用 token 产出算，不是用并发算。按并发算是 24% 占用（平均 35,000 对容量 145,775），但那是"装了多少请求"，不是"产出多少 token"。算单价要用 token 产出。

这就是成本真正被放大的地方：**池子按峰值配，按平均产出摊销**。3.7% 和 9.4% 的利用率，意味着每个 token 要摊 27 倍和 10.7 倍的闲置。

### 2.4 第四层：把闲置和冗余乘回去

到这里，一条完整的链就通了：

```
卡时 ¥12.86/卡时
  ÷ (单卡吞吐 × 3,600)         ← 裸算力成本
= 裸成本
  ÷ 利用率                      ← 摊掉闲置
= 满摊成本
  × 1.56                        ← 冗余 1.3 × 弹性 1.2
= 单价
```

代进两组数：

| 环节 | 卡时 | 单卡吞吐 | 裸成本 | 利用率 | 乘 1.56 | 单价 |
|---|---|---|---|---|---|---|
| prefill | 12.86 | 14,838 | 0.241 | 3.7% | 6.51 × 1.56 | **10.24** |
| decode | 12.86 | 9,297 | 0.384 | 9.4% | 4.09 × 1.56 | **6.42** |

这两行就是价目表的来源。可以看到决定性因素不是"哪个环节快"，是利用率——prefill 3.7% 比 decode 9.4% 低一半多，所以它每个 token 摊的闲置更多。

### 2.5 第五层：缓存把输入再劈两档

上面的 10.24 是"未命中输入"的价。但输入里 85% 是命中缓存的，它们没打矩阵乘，只做了哈希查找，不能同价。

摊法有两种，差 10 倍：

| 摊法 | 怎么算 | 未命中单价 | 命中单价 |
|---|---|---|---|
| 平均摊 | 池成本 ÷ 全部输入 token | ¥1.0 | ¥1.0 |
| 按实际计算摊 | 池成本 ÷ 未命中 token | ¥6.6 | ≈0 |

第二种更真实。乘冗余后就是价目表：

| 类型 | 单价 | 怎么来的 |
|---|---|---|
| 未命中输入 | ¥10.24/百万 | 0.241 ÷ 3.7% × 1.56 |
| 命中输入 | ¥0.05/百万 | 名义价，实际约为 0 |
| 输出 | ¥6.42/百万 | 0.384 ÷ 9.4% × 1.56 |
| reasoning | ¥6.42/百万 | 与输出同价 |

验算一轮：

```
285 × 10.24 = 2,918
1,615 × 0.05 = 81
350 × 6.42 = 2,247
合计 5,246 → 0.525 分/轮
```

和第 1 章的 0.517 差 1.5%，差在"命中输入"给了一个名义价而不是零。

### 2.6 利用率为什么只有个位数

3.7% 这个数看着像浪费。拆开看，它是三个乘数乘出来的，每一个都有原因。

```
prefill 利用率 = 峰均比倒数 × 缓存过滤 = 24.8% × 15% = 3.7%
```

**第一个乘数：峰值是均值的 4 倍。**

```
日均 QPS 1,736，峰值 7,000，峰均比 4.03
```

客服场景的作息决定的：早 9 点到晚 9 点是主时段，晚 8 点到 9 点是一天最高峰，深夜只有白天的一成。容量必须按峰值配——按均值配的话，每天有 8 个小时在排队。

所以**只要按峰值配、按均值摊销，利用率的天花板就是 25%**。这一条和系统做得好不好无关。

**第二个乘数：缓存把 85% 的输入挡掉了。**

容量按"缓存全失效"配（第 13 章的理由：版本切换那刻会归零），实际运行时 85% 命中。所以真正被计算的只有 15%。

```
25% × 15% = 3.7%
```

这一条是主动选择的结果：宁可平时闲，也不要在版本切换时全线超时。

decode 的账多一层。它按峰值并发 140,000 配，平均并发只有 34,720，占 24%。但按 token 产出算只有 9.4%，因为批量小的时候每卡产出低：

| 并发 | 单步时间 | 每实例产出 |
|---|---|---|
| 397（平均） | 11.0 ms | 36,032 token/s |
| 1,666（满） | 22.4 ms | 74,435 token/s |

平均并发下带宽喂不满，每实例产出只有满负荷的 48%。所以 token 口径的利用率 = 24% × 48% ≈ 11.5%，和实测的 9.4% 是一回事（差在平均值取的区间）。

### 2.7 低利用率是该修还是该认

先把话说清：**低利用率不等于浪费，它是为峰值和故障买的保险。** 问题只在于保险买得对不对。

三条能提高利用率的路，代价各不相同：

| 手段 | 利用率 | 代价 |
|---|---|---|
| 削峰（排队 + 预约） | 25% → 31% | 峰值等 30–60 秒 |
| 按缓存命中率配容量 | prefill 3.7% → 15% | 版本切换时 TTFT（Time To First Token）破线 |
| 闲置算力卖出去 | 可到 60% 以上 | 要能接纳批处理的业务 |

第三条最实在，也最常被忽略：prefill 池那 96% 的空闲不是"没有"，是可以给离线任务用的。第 33 章的错峰、附录 B 的训练占用，都是往这个池子里填东西。

判断标准很简单：如果你的池子长期低于 20% 利用率，又不打算填，那它要么是买多了，要么是峰值系数定高了——两者都是钱。

### 2.8 那为什么大家说"输出比输入贵四倍"

因为对外的输入价报的是**混合价**：

```
混合输入 = (285 × 10.24 + 1,615 × 0.05) ÷ 1,900 = ¥1.58/百万
输出 ¥6.42/百万
比值 = 4.1 倍
```

市场看到的 3 到 5 倍，全是这么来的。**不是 decode 比 prefill 贵，是缓存把大部分输入变成了免费。**

这也解释了一个反直觉的事实：如果你的缓存命中率是 0（比如每轮系统提示都带时间戳），输入价会立刻从 ¥1.58 跳到 ¥10.24，比输出还贵。所以第 20 章讲上下文工程时反复强调"变量要后置"——那不只是性能问题，是计价结构问题。

## 3. cached token 怎么判

引擎在响应里返回 `cached_tokens`，这是它真实命中的数目。平台不能自己估算，必须用引擎给的数——因为只有引擎知道块池里有什么。

三个坑：

**第一，cached 的边界是块。** 块大小 16 token，命中 1,615 意味着 101 个整块。第 102 块只对了 8 个 token 也不算命中，那 8 个 token 按未命中计价。所以数字总是 16 的倍数。

**第二，跨租户不能共享。** 缓存键要带租户盐（第 10B 章），否则 A 租户的系统提示被 B 租户命中，既是安全漏洞，又是计费错误——B 不该为 A 的内容付钱，也不该享受 A 的热度。

**第三，权重版本切换当天 cached 会归零。** 那天的账单会涨 60% 以上，要提前通知租户，否则会被当成涨价。

## 4. reasoning token 怎么计

思考模型会生成一段用户看不到的推理过程，500 到 2,000 token 不等。它确实消耗了 decode 算力，也占了 KV，所以必须计。

### 4.1 深度思考模式的原理

它没有特殊的"思考模块"。机制上就是让模型先生成一段推理文本，再生成答案——两者都是普通的自回归解码，只是内容不同：

```
[用户问题] → [推理: "先看政策第 3 条……等等，签收日期要算退货期限……"] → [答案]
```

这段推理会被训练出来。做法是先用少量长推理样本做冷启动，再用强化学习（GRPO 这类）在有确定答案的任务上训练：答对了给正奖励，答错了给负奖励。训练久了，模型自发学会"先复述条件、再代入、最后验算"——因为这样做答对率高。

所以它不是"模型在内部思考"，是**模型学会了把思考过程写出来**。写出来的 token 进入上下文，下一步解码就能看到，等于用自然语言当草稿纸。

为什么这样能提升准确率？因为自回归每生成一个 token 就是一次前向计算。多写 2,000 个 token，就多了 2,000 次计算机会。这叫 test-time compute——把算力从训练阶段挪到推理阶段，用时间换准确率。

代价是三个数一起涨：

| 项 | 普通模式 | 思考模式 | 倍数 |
|---|---|---|---|
| 输出 token | 350 | 2,350（2,000 推理 + 350 答案） | 6.7× |
| 单轮成本 | 0.52 分 | 1.81 分 | 3.5× |
| 生成耗时（TPOT 44 ms） | 15 秒 | 103 秒 | 6.7× |

103 秒意味着它根本不能用在交互式场景。这就是为什么思考模式的产品形态通常是"提交任务 → 等通知"，而不是聊天框里等。

架构上要五条支持：

| 要求 | 普通 | 思考 |
|---|---|---|
| 超时 | 9 秒 | 300 秒以上 |
| 池子 | 与短请求混部 | 必须独立池（第 6 章形态分离） |
| 计量 | 三项 | 加 reasoning 一列 |
| 流式 | 直接吐答案 | 决定是否展示推理过程 |
| 中断 | 少见 | 常见（用户等不及） |

流式那一条是产品决策，不是技术决策。展示推理过程（DeepSeek 风格）能让用户理解"它在想"，首字延迟仍然是几百毫秒；隐藏推理（o1 风格）则用户要等到思考结束才见字，感知延迟就是 103 秒。

还有一个容易忽略的点：**推理不是越长越好**。超过某个长度后准确率会下降，因为模型开始自我怀疑、反复推翻。所以要设 `max_reasoning_tokens`，通常 4,000 封顶。

### 4.2 为什么"深度思考"这个按钮越来越少见

2025 年它是个显眼的开关，2026 年很少有人再提。不是能力消失了，是三个东西变了。

**第一，开关变成了自适应。** 早期要用户自己判断"这题值不值得想"，用户判断不了——问"订单到哪了"也点深度思考，等 100 秒。现在的主流做法是模型或路由器自己决定：简单问题直接答，复杂问题才展开推理。对外暴露的不再是布尔开关，而是一个 `reasoning_effort` 参数（low / medium / high），甚至完全不暴露。

**第二，独立模型变成了混合模型。** 早期"推理版"和"普通版"是两个权重，要分别部署、分别计价。现在是一个模型内部支持两种模式，靠参数切换。对平台的意义很大：不用再维护两个池子，第 6 章说的"形态分离"从"两个模型"简化成"一个模型两种采样预算"。

**第三，卖点变成了默认。** 当所有厂商都能做，它就不再是宣传语。产品页上不写了，不代表后台没开。

从账上看，这个收敛是必然的。深度思考的成本是普通模式的 3.5 倍、耗时是 6.7 倍（103 秒）。如果对所有请求默认开启，成本翻三倍、SLO 全破。所以它只能留在"高价值 + 可等待"的场景里：数学、代码、复杂条款比对、多步规划。日常客服的 90% 请求用不上。

判断一个系统有没有在用推理模式，看三个地方，而不是看 UI 上有没有按钮：

| 看什么 | 有推理模式的特征 |
|---|---|
| 输出 token 与输入 token 的比例 | 高于 1（普通对话约 0.2） |
| 单请求耗时分布 | 双峰：一批 2 秒内，一批 60 秒以上 |
| 计费明细 | 有 reasoning 一列，或者 output 单价高于输入 3 倍以上 |

第二行最实用。如果耗时分布是单峰，说明所有请求走同一条路径，那多半没开推理。





有三种做法，各有代价：

| 做法 | 计费方式 | 优点 | 缺点 |
|---|---|---|---|
| 并入 output | 按输出价 | 简单 | 用户觉得回答 200 字收 800 token 的钱 |
| 单列但同价 | 单独一行 | 透明 | 账单变长，用户仍不理解 |
| 单列且打折 | 如 0.6 倍 | 接受度高 | 成本回收不全 |

我们的选择是单列且同价，理由是可审计：租户能查到"这 800 个 token 是思考过程"，虽然看不到内容，但能看到数量和单价。折价会让账更难解释——为什么同样是 decode token，有的 11.34 有的 6.8？

一个必须做的防护：reasoning 要有上限。模型偶尔会陷入循环，生成几万 token 的思考。设一个 `max_reasoning_tokens`（比如 4,000），超了就强制收尾。没有这个上限，一次循环能把单轮成本推到 5 块钱。

## 5. 中途取消怎么计

三种中断，计费规则不同：

| 中断方式 | 已生成 | 计费 | 理由 |
|---|---|---|---|
| 客户端断开 | 有 | 计已生成的 | 算力已经花了 |
| 网关超时 | 有 | 计已生成的 | 同上，且超时是平台侧问题 |
| 用户点"停止" | 有 | 计已生成的 | 用户主动，算力已消耗 |
| 排队中被取消 | 无 | 不计 | 没开始算 |

关键原则：**按服务端实际生成量计，不按客户端收到的量计。**

因为流式有缓冲，服务端可能已经生成 20 个 token，客户端只收到 15 个就断了。这 5 个 token 的算力确实花了，计费要算进去。

麻烦在于用户感知：他看到 15 个字，账单算 20 个。差 5 个 token 是 0.00006 分，可以忽略；但如果缓冲很大（比如 200 token），就会引发投诉。

所以工程上要把缓冲控制在小范围：每个分片 flush 一次，缓冲不超过 16 token。

## 6. 重试、失败、超时

这三类是账单争议的主要来源，规则要先定：

| 情况 | 计费 | 谁承担 | 说明 |
|---|---|---|---|
| 4xx（参数错、鉴权失败） | 不计 | — | 没进引擎 |
| 5xx（服务端错） | 不计 | 平台 | 用户没得到服务 |
| 超时（网关侧切断） | 计已生成 | 平台补 | 见下 |
| 网关自动重试 | 只计一次 | 平台 | 幂等键去重 |
| 用户主动重试 | 各计各的 | 用户 | 是两次独立请求 |
| 引擎 OOM 崩溃 | 不计 | 平台 | 未完成 |

第四条要专门说。网关在 502/503 后会重试到另一个实例，用户只发了一次请求，但引擎可能跑了两遍（第一遍的算力白花了）。对用户只计一次，对平台要记两笔成本——**用户账和成本账是两本账，不能混**。

超时那一行有个细节：如果超时是因为输出太长，那是用户的问题（他要求 4,000 字）；如果是平台慢，那是平台的问题。区分方法是看 `stop_reason`：`length` 是用户设的限制，`timeout` 是平台切断了。

## 7. 预扣与结算

计量不是请求结束才开始的。要防超额，必须在开始前预扣。

```
请求进入
  → 预扣：按 (输入 token + max_tokens) 估算上限，冻结额度
  → 生成过程中：按已生成 token 增量更新
  → 结束：按实际 usage 结算，退回多扣的
```

预扣额度用最大值，不用估算值。因为估算不准——模型输出长度波动很大，按均值预估会让 20% 的请求中途被截断。

冻结的额度从租户的实时余额里扣，结算时退。这样即使请求崩了没回调，冻结也会在 5 分钟后超时释放。

超时释放这一条必须有。否则一次进程崩溃会让租户的余额永久少一块，第二天客诉就来。

预扣额度有多大？按一轮典型请求算：

```
输入 1,900 token × ¥2.70/百万 = ¥0.0051
输出上限 max_tokens 4,096 × ¥11.34/百万 = ¥0.0465
合计 ¥0.0516 = 5.16 分
```

而实际结算只有 0.517 分。**冻结额度是实际消费的 10 倍**，因为 `max_tokens` 取了上限而实际只用了 350。

这带来两个后果。一是租户的余额要留够 10 倍的单次额度，否则并发一高就全被冻结、后续请求直接拒绝。二是必须尽快结算释放，通常请求结束 1 秒内退，否则余额看起来一直很紧。

优化办法是按租户历史调整 `max_tokens` 的预估：常用 350 token 的租户，实测 P99 是 600，就把预扣按 600 算，冻结降到 1.5 倍。代价是偶尔超支，超支时按实际扣、允许账面临时透支。

## 7.5 阶梯与封顶

大租户不该按同一单价付。三条常见的商务规则要写进计量系统，而不是靠人工改单：

| 规则 | 做法 | 计量系统的要求 |
|---|---|---|
| 阶梯价 | 月用量 >10 亿 token 打 8 折 | 记录要能按月聚合到租户 |
| 单请求封顶 | 单次请求最高 ¥1 | 结算时比较，超出部分由平台承担 |
| 月度保底 | 不足 5,000 元按 5,000 元收 | 月末出账时补差 |

第二条要注意：封顶是对用户的承诺，但成本真实发生了。所以要有监控——某个租户的请求频繁触发封顶，说明他在用超长输出薅羊毛，要限制 `max_tokens` 而不是一直垫成本。

## 8. 计量记录 schema

一条记录要能让三方对上账：租户、平台、财务。

```json
{
  "request_id": "req-7f3a9c",
  "idempotency_key": "tenant-a:2026-11-17:88f1",
  "tenant_id": "tenant-a",
  "model": "w-2026-11-02",
  "usage": {
    "input_uncached": 285,
    "input_cached": 1615,
    "output": 350,
    "reasoning": 0
  },
  "billing": {
    "cost_fen": 0.517,
    "price_version": "price-2026-10-01",
    "currency": "CNY"
  },
  "status": "completed",
  "stop_reason": "eos",
  "attempt": 1,
  "started_at": "2026-11-17T09:12:03.221Z",
  "ended_at": "2026-11-17T09:12:07.845Z"
}
```

四个字段值得单独讲：

- `idempotency_key`：重试去重的唯一依据。同一个键只计一次。
- `price_version`：价格会变，账单必须能追到当时的价目表。没有这个字段，一年后对账要靠猜。
- `stop_reason`：`eos` / `length` / `timeout` / `cancelled` / `error`，决定计费规则。
- `attempt`：第几次尝试。网关重试时，第一次记 `cost` 但 `billable=false`。

## 9. 对账：差异从哪来

平台账和引擎账每天对一次，差异要压到 0.1% 以内。常见的四个来源：

| 来源 | 表现 | 怎么查 |
|---|---|---|
| tokenizer 版本不一致 | 差 1–3% | 比对 token 数，查版本号 |
| reasoning 漏计 | 差 5–20% | 看思考模型的请求 |
| 重试重复计 | 差等于重试量 | 按 idempotency_key 去重后比 |
| 缓存标记不同步 | cached 与 uncached 比例异常 | 比对引擎返回的 cached_tokens |

第一条最隐蔽：平台用 A 版 tokenizer 算 token 数，引擎用 B 版。同一段文本差 1–3%，日积月累就是一笔钱。解法是统一用引擎返回的 usage，平台不自己算。

## 10. 失败模式

| 现象 | 根因 | 怎么发现 | 怎么修 |
|---|---|---|---|
| 账单比用户算的高 | 重试重复计费 | 查同 idempotency_key 的记录 | 去重 |
| 用户说没收到那么多字 | 服务端缓冲多生成 | 比对 usage 与客户端收到的 | 减少 flush 缓冲 |
| 思考模型账单翻倍 | reasoning 没单列 | 看 usage 里有没有这一项 | 单列并通知租户 |
| 版本切换当天账单暴涨 | cached 归零 | 看 cached 比例曲线 | 提前通知，或分摊 |
| 余额被永久扣掉 | 预扣未超时释放 | 查冻结记录 | 加 5 分钟超时 |
| 两个租户账单完全一样 | 缓存键没带租户盐 | 看哈希键构造 | 加盐，重刷缓存 |

最后一行不只是计费问题，是安全问题：缓存键不带租户，A 租户的内容会被 B 命中，用户可能在回答里看到别人的数据（第 10B 章）。

## 11. 什么情况下这些结论不成立

| 结论 | 推翻条件 |
|---|---|
| cached 按 0.1 倍计价 | 缓存命中率超过 95% 时，成本几乎全在 decode，cached 可以更低 |
| reasoning 同价 | 思考 token 与输出 token 的 KV 占用差异大时，要分开定价 |
| 中途取消按已生成计 | 监管或合同要求"未收到不计"时，按客户端确认为准 |
| 预扣按最大值 | 大客户有充足授信时，可以后付费，省掉冻结开销 |

## 12. 验收

1. 能说出你系统里 token 分几类，各自的单价怎么定。
2. 能算出一次缓存命中的请求比未命中便宜多少。
3. 能列出五种结束状态，并说出各自的计费规则。
4. 能设计一条计量记录，让租户、平台、财务三方都能对上账。
