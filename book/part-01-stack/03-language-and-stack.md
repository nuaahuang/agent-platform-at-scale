# 第 03 章 · 语言栈与技术栈总表

> 读完你能回答：
> ① 为什么不能让一套语言打天下？
> ② Go / Java / Python 各管哪一段，边界划在哪？
> ③ 中间件怎么选：选了什么、否了什么、什么条件下推翻？
> ④ 只有 10 个人时，这套栈怎么裁到能跑？

## 1. 问题：一套 Python 打天下，网关先崩

一个真实的重构：团队全是 Python 背景，于是网关也用 FastAPI 写。

上线后的三个数：

| 指标 | Python 网关 | Go 网关 | 差距 |
|---|---|---|---|
| 单机 QPS（8 核） | 8,000 | 60,000 | **7.5×** |
| 单实例内存 | 300 MB | 50 MB | 6× |
| p99 抖动（GC） | 40 ms | 3 ms | 13× |

按 7,000 QPS 峰值算：

```
Python：7,000 ÷ 8,000 × 1.5（冗余）= 2 台？——实际要 40 台，因为延迟预算不够
Go：    7,000 ÷ 60,000 × 2 = 1 台，配 6 台覆盖多 AZ
```

**不是 Python 不行，是每个位置有它的最优语言。**
网关的活是"每毫秒转发十万个连接"，Python 的 GIL 与对象开销天生不适合；
模型服务的活是"调 CUDA kernel"，Python 只做控制面，那 5% 的开销就无所谓。

---

## 2. 判据：按延迟预算与并发形态分工

选语言只看两个变量：**这个位置的延迟预算是多少、并发是什么形态。**

| 位置 | 延迟预算 | 并发形态 | 选它 | 理由 |
|---|---|---|---|---|
| 网关 / BFF | <5 ms | 高并发短连接 | **Go** | 协程轻、内存小、启动快 |
| Harness 编排 | 10–100 ms | 长事务、IO 密集 | **Python** | LLM SDK、生态最全 |
| 工具沙箱 | 100 ms–10 s | 不可信代码 | **Go** | 隔离好、可控 |
| 模型服务 | 25 ms/step | GPU 密集 | **Python + CUDA** | 引擎生态绑定 |
| 计费 / 账务 | 批处理 | 强一致事务 | **Java** | 事务与金融生态 |
| 数据管道 | 分钟级 | 批 / 流 | **Python / Scala** | 生态 |
| 运维工具 | 无 | 一次性 | **Go** | 单二进制，无依赖 |

**一句话**：延迟越紧、并发越高 → 越往 Go 走；越靠近模型与数据 → 越往 Python 走；
**越涉及钱和事务 → 越往 Java 走**。

## 3. 三套语言的边界：只走协议，不共享内存

```
   ┌─────────┐  gRPC   ┌──────────┐  gRPC   ┌────────────┐
   │  Go     │ ──────▶ │ Python   │ ──────▶ │ 推理引擎    │
   │ 网关    │         │ Harness  │         │ (Python)   │
   └─────────┘         └──────────┘         └────────────┘
        │                    │                     │
        └────────────┬───────┴─────────────────────┘
                     ▼
              ┌────────────┐
              │  Java 计费  │  ← 消费 Kafka，异步
              └────────────┘
```

三条纪律：

| 纪律 | 原因 |
|---|---|
| 跨语言只走 gRPC/HTTP | 不共享内存，不做 FFI（Foreign Function Interface，进程内跨语言调用） |
| **proto 是唯一真相** | 三语言各自生成代码，不许手写结构体 |
| 跨边界调用要少 | gRPC 一次 0.2–0.5 ms，本地调用 0.1 μs，**差 5,000 倍** |

第三条最容易违反：如果按 token 逐次跨语言调用，单次 0.3 ms × 300 token = **90 ms**，
比整个 TPOT 预算还大。所以流式必须**批量推送**（每 10–20 token 一批）。

> **注意 FFI 的例外**：引擎内部到处都是 FFI——Python 调 C++ 调 CUDA kernel，
> 那是同一进程、同一生命周期、同一发布节奏，代价可接受（第 10A 章）。
> 业务层不用 FFI，是因为两侧要独立扩缩容、独立发布、故障互相隔离。

## 4. 为什么模型服务只能是 Python

| 事实 | 说明 |
|---|---|
| vLLM / SGLang / DeepInfer 都是 Python 控制面 | 调度器、block manager、API 层 |
| 热点在 C++/CUDA | attention、GEMM、通信全是编译产物 |
| Python 开销占比 | **<5%** 的 step 时间（第 10A 章实测口径） |

**推翻条件**：如果你要做极致定制（自研调度器、极致延迟），可以把控制面重写成 C++——
TensorRT-LLM 的 C++ runtime 就是这么做的。代价是失去 Python 生态（评测、工具、调试）。

对 99% 的团队，**不值得**。

### 4.1 真正难的不是选语言，是锁版本

模型服务的依赖链比业务服务脆得多，任一层错配就是编译失败或运行崩：

| 层 | 约束 | 错配后果 |
|---|---|---|
| 驱动 | ≥ 535（CUDA 12.2+） | 装不上 CUDA 12.4 |
| CUDA | 与 PyTorch 编译版本严格绑定 | `undefined symbol` |
| PyTorch | 与 vLLM 版本绑定 | 引擎启动即崩 |
| vLLM | 与 flash-attn / xformers 绑定 | kernel 不可用 |
| flash-attn | 必须现编，20–40 min | CI 时间失控 |

**做法：整条链打进一个镜像，锁死 digest，CI 只认这个 digest。**
不要在生产机上 `pip install` —— 一次升级会连锁破坏三个包。

## 5. 中间件选型矩阵

每一行都回答"选了什么、否了什么、什么条件下推翻"。

| 能力 | 候选 | 选它 | 否了什么 | 推翻条件 |
|---|---|---|---|---|
| **入口网关** | Envoy / Nginx / APISIX / 自研 Go | **Envoy** | Nginx（扩展难）、APISIX（生态弱） | 需要深度定制协议时自研 |
| **服务间 RPC** | gRPC / Thrift / HTTP+JSON | **gRPC** | Thrift（生态萎缩）、JSON（体积 3×） | 浏览器直连时退回 HTTP |
| **消息队列** | Kafka / Pulsar / RabbitMQ | **Kafka** | RabbitMQ（吞吐不足）、Pulsar（运维重） | 需要延迟队列时加 RabbitMQ |
| **缓存** | Redis / Memcached | **Redis** | Memcached（无数据结构） | 纯 KV 且要极致时 Memcached |
| **关系库** | MySQL / PostgreSQL | **MySQL** | PG（团队不熟） | 要 JSONB/向量时换 PG |
| **分析库** | ClickHouse / Doris | **ClickHouse** | Doris（运维复杂） | 要强一致点查时 Doris |
| **向量库** | Milvus / pgvector / Qdrant | **pgvector 起步** | Milvus（独立运维） | 超过 5,000 万向量换 Milvus |
| **对象存储** | S3 兼容 | **S3 协议** | 私有协议（锁定） | — |
| **配置中心** | Apollo / Nacos / etcd | **Nacos** | Apollo（重） | 已有 etcd 时直接用 |
| **容器编排** | K8s + Volcano | **K8s + Volcano** | Slurm（服务化弱） | 纯训练场景用 Slurm |
| **可观测** | Prometheus + OTel | **OTel 打点 + Prometheus 存储** | 自研 SDK | 基数爆炸时换 VictoriaMetrics |

**选型的三个反模式**：

| 反模式 | 后果 |
|---|---|
| 每个能力都选最强的 | 12 个中间件，5 个人运维不动 |
| 只选团队会用的 | 用 MySQL 存时序数据，半年后查询慢 100 倍 |
| 不写推翻条件 | 三年后没人知道为什么选它 |

## 6. 自研还是用现成

| 能力 | 现成方案 | 什么时候必须自研 |
|---|---|---|
| 路由亲和 | 无 | **必须自研**（第 2 章 §6.1） |
| 配额中心 | Envoy RL / Sentinel | 需要 token 维度（第 2 章 §6.2） |
| 版本矩阵 | 无 | **必须自研**（第 36 章） |
| 网关 | Envoy | 用 WASM 扩展即可，别重写 |
| 调度 | Volcano / Kueue | 拓扑感知不足时扩 |
| 可观测 | OTel + Prometheus | 极少需要 |

判据：**能用扩展点解决的，绝不 fork**。fork 一个中间件，三年后升级不了。

### 6.1 一个真实的选型过程

需求：事件总线要支撑 1.5 亿轮/日的会话事件与计费流水。

| 候选 | 吞吐 | 延迟 | 运维 | 结论 |
|---|---|---|---|---|
| RabbitMQ | 5 万 msg/s | 1 ms | 简单 | ❌ 吞吐不够 |
| Pulsar | 100 万 msg/s | 5 ms | 需 BookKeeper | ❌ 多一套存储要运维 |
| **Kafka** | 100 万 msg/s | 5 ms | 成熟 | ✅ 够用且团队会 |

**否掉 Pulsar 的理由不是性能，是"多一套 BookKeeper 要三个人维护"。**
选型的胜负手经常不在技术指标，在运维成本。

## 7. 团队规模：AI 之后要重算

### 7.1 旧模型错在哪

上一版这张表是按"每个中间件一个 owner、每种语言一个专家"算的：

| 旧假设 | 后果 |
|---|---|
| 8 个中间件 → 8 个 owner | 直接把人数抬到 20+ |
| 3 种语言 → 3 组专家 | 再翻一倍 |
| 7×24 值班 → 每班 2 人 | 至少 10 人 |

这套算法在 AI 辅助编程之前是对的，现在**前两条已经不成立**：中间件的部署、升级、排障样板代码，
AI 几分钟就能生成；跨语言也不再需要"专家"，需要的是"能 review 的人"。

### 7.2 什么被压缩了，什么没有

| 工作 | AI 压缩倍数 | 说明 |
|---|---|---|
| 写新代码 | **5–10×** | 样板、CRUD、配置、测试 |
| 读陌生代码 | **3–5×** | 快速定位与解释 |
| 写文档 | **5×** | 从代码反推 |
| **Code review** | **1.2×** | 人必须真的看懂 |
| **On-call 值班** | **1×** | 半夜叫醒的是人 |
| **决策与定责** | **1×** | 选型错了谁签字 |
| **跨部门协调** | **1×** | 安全、合规、采购 |

**结论：建设期人力断崖式下降，运行期几乎不变。**

### 7.3 修正后的人数

| 阶段 | 规模 | 建设（AI 辅助） | 运行（值班 + 变更） | 合计 |
|---|---|---|---|---|
| 0→1 原型 | 1 万 DAU / 16 卡 | 2 | 0（自己兼） | **2** |
| 1→10 产品化 | 100 万 DAU / 128 卡 | 3 | 1 | **4** |
| 10→100 规模化 | 1,000 万 DAU / 1,024 卡 | 5 | 3 | **8** |
| 亿级 | 2,000 万 DAU / 2,512 卡 | 7 | 4 | **11** |

对照上一版：亿级平台**从 100 人降到 11 人**，差 9 倍。

但 11 人里 **4 个是值班**，不是写代码——这个比例很说明问题。

### 7.4 新的瓶颈是 review，不是写

```
AI 产出      500 行/小时
人能 review  150 行/小时
```

**每写 3 行，就有 1 行卡在 review 上。** 团队规模现在由"能审多少人"决定，不再由"能写多少"决定。

推论：

| 做法 | 结果 |
|---|---|
| 加人写代码 | 无收益，review 队列更长 |
| **加人 review** | 有收益 |
| **提高单测覆盖率** | 有收益，把 review 压力转给机器 |
| 降低变更粒度（小 PR） | 有收益，review 更快 |

### 7.5 语言数量的结论也要改

旧结论是"语言数量 ≤ 团队能维护的边界数量，5 个人 3 种语言会半吊子"。

现在这个约束松了：AI 能让一个人写出合格的 Go 和 Python，**但松不了的是"出故障时谁能定位"**。

| 旧约束 | 新约束 |
|---|---|
| 每种语言要有专家 | 每种语言要有**能半夜看日志的人** |
| 语言数 ≤ 团队容量 | 语言数 ≤ **值班人数** |

所以 5 人团队上 3 种语言仍然危险——不是因为写不出来，是因为**凌晨 3 点没人看得懂**。

## 8. 代码：一份 proto 定义三个语言

```proto
syntax = "proto3";
package agent.v1;

service Chat {
  rpc Stream(ChatRequest) returns (stream ChatChunk);
}

message ChatRequest {
  string tenant_id = 1;
  string session_id = 2;
  repeated Message messages = 3;
  int32 max_tokens = 4;
  string model = 5;          // 版本由服务端解析，客户端不传权重版本
}

message ChatChunk {
  string delta = 1;
  bool done = 2;
  Usage usage = 3;           // 最后一个 chunk 才带
}

message Usage {
  int32 input_tokens = 1;
  int32 cached_tokens = 2;
  int32 output_tokens = 3;
}
```

三个纪律：

| 纪律 | 原因 |
|---|---|
| 字段只增不删 | 老客户端不会崩 |
| 枚举值留 `UNSPECIFIED = 0` | 默认值可识别 |
| **版本号不进请求体** | 由服务端解析，客户端改不了（第 24 章契约层） |

## 9. 失败模式

| 现象 | 根因 | 怎么发现 | 怎么修 |
|---|---|---|---|
| 网关 CPU 打满 | 用 Python 写网关 | `top` 单核 100% | 换 Go / Envoy |
| 跨语言调用成瓶颈 | 每 token 一次 RPC | trace 里 RPC 占比 >30% | 批量推送 |
| 三种语言三种日志格式 | 没有统一打点 | 排障时要翻三个系统 | 统一 OTel schema |
| proto 不兼容 | 删字段 / 改类型 | 老客户端报解析错 | 只增不删 + CI 检查 |
| 中间件太多没人会 | 每个能力都选最强 | 故障时无人能修 | 砍到 6 个以内 |
| 团队都会一点 | 语言数 > 团队容量 | PR 评审质量下降 | 收敛到 2–3 种 |

## 10. 验收

| 检查项 | 通过标准 |
|---|---|
| 网关语言 | 非 Python（Go 或 Envoy） |
| 跨语言调用 | 流式按批（≥10 token/次），非逐 token |
| proto 兼容 | CI 里有 breaking change 检查 |
| 中间件数量 | ≤8 个，每个有 owner（AI 可代劳部署，责任不能代劳） |
| 选型文档 | 每个都写了"否了什么 + 推翻条件" |
| 语言数量 | ≤3 种，且每种语言有 ≥2 人能值班定位 |

最后一条是给技术负责人的：**每多一种语言，就多一套 CI、监控、on-call——AI 能帮你写，但替不了你凌晨三点看日志。**

## 11. 备选方案：全用一套语言会怎样

| 方案 | 优点 | 代价 |
|---|---|---|
| **全 Python** | 招聘统一、生态好 | 网关 QPS 差 7.5×，内存 6× |
| **全 Go** | 性能好、部署简单 | 缺 LLM 生态，模型侧要重写 |
| **全 Java** | 事务强、企业生态 | 模型侧几乎无生态，启动慢 |
| **Go + Python**（推荐） | 各取所长，两种够用 | 需要 proto 契约纪律 |

**推荐：Go（网关/工具）+ Python（模型/Harness）**，计费到了 30 人再加 Java。

---

## 12. 收口

> **语言不是信仰问题，是延迟预算问题。
> 谁的预算最紧谁用 Go，谁离模型最近谁用 Python，谁管钱谁用 Java。**
