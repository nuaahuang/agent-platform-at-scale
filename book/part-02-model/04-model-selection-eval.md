# 第 04 章 · 选型与能力评测

## 1. 问题：最贵的那个反而最便宜

售后 Agent 上线前，团队把四个候选都跑了一遍：

| 模型 | 激活参数 | 推理成本 | 50 题通过率 | 结论 |
|---|---|---|---|---|
| 8B 稠密 | 8B | 0.078 分/轮 | 62% | ❌ 工具调用经常错参 |
| 30B 稠密 | 30B | 0.294 分/轮 | 74% | ❌ 多步任务掉链子 |
| 70B 稠密 | 70B | **0.686 分/轮** | 78% | ❌ 贵且不够好 |
| 200B MoE（30B 激活） | 30B | **0.294 分/轮** | 91% | ✅ |

**最反直觉的一行是最后一行**：200B 的总参数是 70B 的 2.9 倍，但成本只有它的 43%。

因为推理成本由**激活参数**决定，不由总参数决定。

> 这一条是本章的前提：能力看总参数，算力成本看激活参数。
> 但带宽成本要看"专家并集"——§3.0.3 会把它拆开讲。

## 2. 三个维度，不能只看一个

| 维度 | 怎么量 | 我们的一票否决线 |
|---|---|---|
| **能力** | 50 题通过率 | <85% |
| **成本** | 分/轮（推理算力） | >0.8 分/轮 |
| **延迟** | TTFT（Time To First Token） p95 / TPOT（Time Per Output Token） p95 | TTFT >1,000 ms |

三者是乘性关系，不是加性：

```
能不能用 = 能力达标 × 成本可承受 × 延迟可接受
```

任何一项为 0，整体为 0。所以先做一票否决，再比总分——不要用加权平均掩盖硬伤。

## 3. 为什么是 200B MoE / 30B 激活

### 3.0 四个词先分清：稠密、稀疏、总参数、激活参数

它们不是同一个维度上的四种东西，而是**两组正交的概念**：

| 组 | 概念 | 回答什么 |
|---|---|---|
| **结构** | 稠密（dense） / 稀疏（sparse, MoE） | 算一个 token 时，是否用到全部参数 |
| **数量** | 总参数（total） / 激活参数（active） | 权重一共多大 / 单 token 实际用多少 |

两者的关系是一句话：

```
稠密模型：active = total          （稀疏度 0）
MoE 模型：active < total          （稀疏度 = 1 − active/total）
```

所以"稠密"是"激活等于总量"的特例，不是另一种参数。

我们的 200B MoE：总参数 200B，激活 30B，**稀疏度 85%**。

```
┌─────────────────────────────────────┐
│ 总参数 200B（权重全在显存里）          │  ← 决定显存、决定"知识容量"
│  ┌───────────────┐                  │
│  │ 激活 30B       │  ← 这个 token 用到 │  ← 决定 FLOPs、决定成本
│  └───────────────┘                  │
└─────────────────────────────────────┘
```

### 3.0.1 能力为什么看总参数

能力随总参数增长，但这是经验规律，不是定律。

参数越多、知识类任务越好，这个趋势在稠密模型上拟合得很准——缩放定律（loss ∝ N^(−α)）就是这么来的。但把它直接搬到 MoE 上会出问题：同样是 30B 激活，200B 的 MoE 在知识问答上能领先十几分，换到多步推理和数学，差距缩到两三分。

差异的来源通常这样解释：专家结构擅长"记住"，而推理链要求激活路径本身连贯，被路由打断就会掉。

所以 91% 和 74% 这两个数，是 50 道题跑出来的，不是从"参数大"推出来的。换一套更偏推理的题，差距会缩到 5 个点以内。

### 3.0.2 为什么成本看激活参数

算力这一侧是严格的：

```
每 token 前向 FLOPs ≈ 2 × 激活参数
稠密 30B：2 × 30e9 = 6.0e10 FLOPs
MoE 200B/30B：2 × 30e9 = 6.0e10 FLOPs   ← 完全相同
稠密 70B：2 × 70e9 = 1.4e11 FLOPs        ← 2.33 倍
```

这就是"200B 比 70B 便宜"的全部原因：算力只认激活，不认总量。

但带宽这一侧有个坑，得说清楚。

### 3.0.3 带宽侧：专家并集会随 batch 放大

decode 每步要把权重读一遍。稠密模型读全部；MoE 只读**被路由到的专家**。

问题在于：一个 batch 里有 B 个 token，它们激活的专家可能不同，要读的是**并集**：

```
期望并集专家数 = E × (1 − (1 − k/E)^B)
E = 专家总数，k = 每 token 激活数
```

按 E=64、k=8 算：

| batch | 并集专家数 | 占全集 | 含义 |
|---|---|---|---|
| 1 | 8 | 12.5% | 只读 1/8 权重，很省 |
| 8 | 42 | 66% | 省一半 |
| 16 | 56 | 88% | 基本读全了 |
| 64 | 64 | 100% | **和稠密模型一样读全量** |

**结论要修正一句**：

> 成本看激活——在算力受限时严格成立；在带宽受限时，要看"有效激活"（专家并集）。

对实践的指导：

| 场景 | 瓶颈 | MoE 收益 |
|---|---|---|
| Prefill（算力受限） | FLOPs | 完全按激活算，收益最大 |
| Decode 小 batch | 带宽 | 收益大（只读 1/8） |
| Decode 大 batch（≥32） | 带宽 | 收益缩小（读全量，但摊到更多 token） |

单 token 的带宽成本 = 并集字节 ÷ B，所以 batch 越大越便宜——
这也是为什么吞吐要靠大 batch，而不是靠堆卡。

### 3.1 一条经验规律

```
能力 ≈ f(log 总参数)
成本 ∝ 激活参数
```

把这两条画在一起，MoE 的价值就出来了：

| 方案 | 总参数 | 激活 | 相对算力 | 能力（通过率） |
|---|---|---|---|---|
| 30B 稠密 | 30B | 30B | 1.0× | 74% |
| 70B 稠密 | 70B | 70B | 2.33× | 78% |
| 200B MoE | 200B | 30B | 1.0× | 91% |

同样算力下，MoE 用 6.7 倍的参数换来了 17 个点的通过率。

### 3.2 MoE 的三项代价

| 代价 | 数值 | 影响 |
|---|---|---|
| **显存** | 权重 200 GB（FP8），TP8 每卡 25 GB | 单卡装不下，必须 8 卡起 |
| **通信** | 专家并行 all-to-all | 跨机走 IB 50 GB/s，是瓶颈（第 9 章） |
| **负载不均** | 热门专家排队 | 需要 EPLB（Expert Parallel Load Balancer） 均衡（第 10A 章） |
| **显存换 KV** | 640 GB 里 200 GB 给权重，KV 只剩 400 GB | 并发上限被压缩 |

**推翻条件**：如果目标硬件只有 40 GB 显存（如部分国产卡），200 GB 权重装不进 8 卡，
MoE 方案直接不成立——这时只能退到 30B 稠密或更激进的量化。

## 4. 评测集：50 道题怎么出

### 4.1 分布要对齐生产

评测集最容易犯的错不是"题太少"，而是**题和生产不像**。

| 类型 | 数量 | 考什么 | 判分方式 |
|---|---|---|---|
| 单轮意图识别 | 10 | 分类准不准 | 精确匹配 |
| **多步工具调用** | 15 | 参数对不对、步数对不对 | 调用序列比对 |
| 长上下文检索 | 8 | 32K 里的事实召回 | 关键字段匹配 |
| 拒答与安全 | 7 | 该拒的拒、不该拒的不拒 | 规则 + 人工 |
| 结构化输出 | 10 | JSON 合法率 | schema 校验 |

五类加起来 50 道。**权重不是平均的**——多步工具调用占 30%，因为它是售后 Agent 的主路径。

### 4.2 题目从哪来

| 来源 | 占比 | 说明 |
|---|---|---|
| 生产日志采样 | 60% | 脱敏后取真实长度与意图分布 |
| 人工构造 | 25% | 覆盖长尾与边界 |
| 对抗样本 | 15% | 提示注入、错别字、方言 |

对抗样本是唯一能提前发现安全事故的类别，不要省。

### 4.3 题目的准确性：出题、审题、判分分三个人

一道题能不能用，取决于它的期望值可不可信。最常见的失效不是模型答错，而是题目本身就错。

举个例子。业务规定"签收 7 天内可退"，出题人写了期望答案"只能退不能换"，但政策原文是"可退可换"。模型答"可退可换"被判为错，这一题从上线起就在扣分，而且没人去看它为什么错。

三个角色分开，是唯一有效的防法：

| 角色 | 干什么 | 不能是谁 |
|---|---|---|
| 出题人 | 写输入 + 期望 + 依据条款 | 不能同时是写 Prompt 的人 |
| 审题人（QA） | 逐题核对依据、判分可执行性 | 不能是出题人的直属下级 |
| 判分实现 | 把期望写成判定函数 | 不能改期望，只能提"不可判" |

写 Prompt 的人出题，会不自觉地把"当前模型能做到的"当成标准，评测就失去意义。

每道题落盘六个字段，缺一不可：

```json
{
  "id": "after-sale-014",
  "input": "...",
  "expect": {"intent": "refund", "must_call": ["query_order"], "must_not": ["create_refund"]},
  "basis": "售后规则 v3.2 §4.1 第 2 条",     // 政策变了能定位到哪些题要改
  "level": "L1",
  "owner": "qa-zhang",
  "valid_until": "2027-03-31"
}
```

`basis` 这一栏最容易被省，但它决定了政策变更时的响应速度：政策改了，用它反查命中哪些题，一次改完。没有它，只能等线上出了偏差再回头猜。

判分方式按可判性分三级，比例要控制：

| 级别 | 判什么 | 判法 | 目标占比 |
|---|---|---|---|
| L1 | 意图、JSON 结构、工具调用序列、拒答 | 代码精确比对 | ≥50% |
| L2 | 数值区间、枚举、必含字段、正则 | 规则判定 | 约 30% |
| L3 | 语气、完整性、解释是否合理 | 人工或 judge | ≤20% |

L3 超过 20% 的评测集不可信——它意味着大部分分数来自主观判断，换个 judge 就变一批结果。

双人标注是保底手段：两人独立标注同一批，一致率（Cohen's Kappa）低于 0.8 就回去改判定规则，而不是改分数。分歧集中在哪类题，说明那类题的判定标准还没写清楚。

### 4.4 全流程评测：模型对了不等于应用对了

50 道题全部通过，上线仍然可能不可用，因为题目只测了模型，没测模型外面那一圈。真实链路是：

```
客户端 → 网关 → Harness（编排 / 工具 / RAG）→ 模型 → 后处理 → 渲染
```

每一段都可能改变结果，所以评测要分五层：

| 层 | 测什么 | 手段 | 通过线 |
|---|---|---|---|
| **L0 模型** | 单次调用输出质量 | 50 题离线 | 见 §5 |
| **L1 契约** | 请求/响应字段、错误码、流式分片 | schema 校验 + 契约测试 | 0 字段丢失 |
| **L2 编排** | 多轮状态、工具调用、RAG 命中 | 录制回放（replay） | 工具序列一致率 ≥98% |
| **L3 端到端** | 用户最终看到的内容 | 真实请求回放 + 结果比对 | 与基线差异可解释 |
| **L4 线上** | goodput、SLO（Service Level Objective）达成、人工抽检 | 灰度 + 影子流量 | SLO ≥99.9% |

L0 通过只是入场券。三个最常见的断裂点都在 L1–L3：

- **工具 schema 变了**：模型按旧参数调，工具返回 400，Harness 重试三次后降级成兜底话术。L0 看不出来，用户看到的是"抱歉我暂时无法处理"。
- **RAG 检索不到**：模型本身答得对，但 Harness 塞给它的上下文是空的。L0 用的是自己准备的标准上下文，永远命中。
- **流式被截断**：网关 buffer 或超时把最后几个分片丢了，JSON 少了收尾括号。L0 拿的是完整响应。

所以 L2 和 L3 要用录制回放：把线上真实请求（含工具返回值、检索结果）存下来，重放时逐段比对。录制文件要带版本号，和模型版本、Prompt 版本一起绑定。

### 4.5 参数一致性：应用层和模型接入层怎么保证一样

这一节解决一个很具体的问题：应用层传了 `max_tokens=2048`，模型接入层却按默认 512 截断，两边都认为自己是对的。

不一致的八种典型来源：

| 字段 | 应用层常见值 | 接入层默认 | 不一致的后果 |
|---|---|---|---|
| `max_tokens` | 2048 | 512 | 输出被截断，JSON 不完整 |
| `temperature` | 0.7（线上） | 0（评测） | 评测通过率虚高 5–7 个点 |
| `tools` | 12 个字段 | 服务端过滤后 9 个 | 模型看不到必填项，参数乱填 |
| `system` | 应用拼的 A 版 | 接入层再注入 B 版 | 两段指令冲突，行为漂移 |
| `stop` | `["\n\n"]` | 未设置 | 多输出一段，前端渲染错位 |
| `stream` | true | 不支持时静默降级 | 前端等到超时 |
| 单位 | token | 字符 | 截断位置差 3 倍 |
| `seed` | 固定 | 未透传 | 同一题两次结果不同，无法回归 |

最后一行常被忽略：没有 seed，评测就不是可复现的，回归测试等于没做。

五个手段，按成本从低到高：

**① 单一契约源。** 请求体用 proto 或 OpenAPI 定义，两侧 SDK 都由它生成，禁止手写结构体。字段增删只改契约，改完重新生成。

**② 未知字段报错，不许静默丢弃。** 这是最关键的语义约定。接入层收到不认识的字段要返回 400，而不是忽略——静默丢弃会让"应用以为生效了"这种错误一直活到线上。

```python
class ChatRequest(BaseModel):
    model_config = ConfigDict(extra="forbid")   # 关键：不允许多余字段
    max_tokens: int = Field(512, ge=1, le=32768)
    temperature: float = Field(0.0, ge=0.0, le=2.0)
    stop: list[str] | None = None
    seed: int | None = None
```

**③ 默认值只在契约里定义一次。** 两侧都不许各写一份默认值。应用不传就用契约默认，接入层不传也不许自己补——补了就等于有两个真相。

**④ 契约测试（consumer-driven）。** 应用侧录真实请求快照，接入层跑同一批快照，断言"收到什么就生效什么"。每加一个字段，补三类用例：最小请求、完整请求、非法请求。

```python
def test_params_passthrough(client, snapshot):
    req = ChatRequest(**snapshot["request"])
    resp = client.chat(req)
    effective = resp.meta["effective_params"]      # 服务端实际生效的参数
    for k in ["max_tokens", "temperature", "stop", "seed"]:
        assert effective[k] == getattr(req, k), f"{k} 未透传"
```

**⑤ 运行时可观测。** 接入层每次请求记录 `effective_params`（实际生效值），按模型版本 + 契约版本聚合。评测和线上用同一套埋点，直接对比两组分布：

```promql
# 线上与评测的 temperature 分布差异，>0.1 说明两边不是同一套配置
histogram_quantile(0.5, sum by (le) (rate(llm_request_temperature_bucket{env="prod"}[1h])))
  - histogram_quantile(0.5, sum by (le) (rate(llm_request_temperature_bucket{env="eval"}[1h])))
```

这三条一起用才闭环：契约管定义，契约测试管行为，埋点管漂移。少一条就会出现"配置看起来一样、行为不一样"。

最后一条纪律：评测走和线上完全相同的调用栈——同一个 SDK、同一个网关、同一份默认值。用 SDK 直连模型做评测，测的是另一个系统。如果线上有网关做限流、改写、注入，评测也必须经过它。

### 4.6 判分：三种手段，按可靠性排序

| 手段 | 适用 | 可靠性 |
|---|---|---|
| 规则/精确匹配 | 分类、JSON、字段 | 最高（无歧义） |
| 调用序列比对 | 工具调用 | 高（可精确到参数） |
| LLM-as-judge | 开放式回答 | 中（需校准） |

judge 能用有前提：与人工标注的一致率 Kappa ≥0.8。达不到就说明判定标准没写清楚，先改标准，别调 judge 的 prompt。

### 4.7 选型流程：从"想换模型"到"全量上线"

七步，每步写清输入、执行人、产出和门禁。门禁不过就停在这一步，不许带着问题上台阶。

| 步 | 做什么 | 谁做 | 产出 | 耗时 | 门禁 |
|---|---|---|---|---|---|
| 1 | 定能力清单与硬约束 | PM + 算法 | 能力项、延迟/成本/合规红线 | 0.5 天 | 每条约束可量化 |
| 2 | 收集候选 | 算法 | 3–5 个候选及部署规格 | 1 天 | 每个候选有可跑形态 |
| 3 | 能力探针（初筛） | 算法 | 20 题探针结果 | 0.5 天 | 通过率 ≥ 基线 −5pt |
| 4 | 全量评测 | QA + 算法 | 50 题 + 盲测 20 题报告 | 1 天 | 见 §5，含单项否决 |
| 5 | 成本与延迟实测 | SRE | 分/轮、TTFT/TPOT p95 | 1 天 | 成本 ≤ +20%，TTFT ≤ 800 ms |
| 6 | 灰度 | SRE + 算法 | 5% 流量 3 天数据 | 3 天 | 错误率不升、goodput 不降 |
| 7 | 放量与归档 | 平台 | release manifest + 评测归档 | 0.5 天 | 回滚演练通过 |

表中的 SRE 指 Site Reliability Engineer（站点可靠性工程师），负责容量测算、灰度推进、告警配置和回滚演练。和传统运维的区别在考核方式：SRE 用 SLO 和错误预算衡量，不是用"有没有出事"衡量。

一周左右能走完一轮。真正拖时间的是第 6 步，三天不能压——一天的灰度量不足以覆盖工作日和周末两种流量形态。

第 3 步的"探针"是这套流程省时间的关键。20 道题按区分度选出来（正负样本各半，覆盖五类），30 分钟内能跑完 5 个候选，用来快速淘汰差 10 个点以上的模型，避免每个候选都跑全量。

门禁不过时的处理方式，比门禁本身更重要：

| 卡在哪 | 先改什么 | 不要做什么 |
|---|---|---|
| 探针不过 | 换候选 | 调 Prompt 硬拉——拉上来也撑不住长尾 |
| 全量总分不够 | 看单类，补 few-shot 或改 Prompt | 改评测题 |
| 全量单项跌破否决线 | 单类专项优化；仍不过就放弃这个候选 | 用总分把单项平均掉 |
| 成本超标 | 量化、压 `max_tokens`、把简单请求分流到小模型 | 先上线再优化 |
| 灰度指标变差 | 回滚，拉 trace 定位 | 加大流量"再看看" |

### 4.8 评测流程：四个触发点

评测不是上线前跑一次，它挂在四个位置上。

| 触发 | 谁跑 | 跑什么 | 出结果 | 阻断什么 |
|---|---|---|---|---|
| PR 合入（改 Prompt / 工具 schema） | CI 自动 | 全量 50 题 | 3 分钟 | 合入 |
| 模型版本变更 | 算法 | 50 题 + 盲测 20 题 | 1 小时 | 发布 |
| 每日 02:00 | CI | 盲测 20 题 | 10 分钟 | 不阻断，只告警 |
| 每月首个工作日 | QA | 按生产日志重采样换题 | 半天 | 下个月的评测集 |

每日巡检用盲测集而不是全量集，是因为全量集天天跑会被团队当成噪声忽略；20 题出问题才值得叫醒人。

每次评测落一个 `report.json`，字段固定，便于跨版本对比：

```json
{
  "run_id": "2026-10-29T02:00:07Z-7f3a",
  "manifest": {
    "model_digest": "sha256:9c1e...",
    "prompt_version": "p-2026-10-27.3",
    "contract_version": "v4"
  },
  "scores": {"total": 0.912, "tool": 0.933, "json": 0.995, "refusal": 0.971},
  "cost_per_turn": 0.294,
  "latency": {"ttft_p95_ms": 612, "tpot_p95_ms": 47},
  "diff_vs_baseline": {"total": 0.004, "tool": -0.007}
}
```

`manifest` 里那三个值是绑定关系：模型换了、Prompt 换了、契约换了，任何一个变了都要重跑。只记 `run_id` 不记 manifest，三个月后没人说得清那次 91.2% 是哪个组合跑出来的。

### 4.9 一次换代的完整排期

把上面两步合成时间轴，一次真实的模型换代长这样：

| 时间 | 动作 | 负责人 | 产出 |
|---|---|---|---|
| D-7 | 需求评审，确认能力清单 | PM | 需求文档 |
| D-6 | 收候选，跑探针 | 算法 | 探针报告 |
| D-5 | 全量评测 + 盲测 | QA | 评测报告 |
| D-4 | 成本与延迟实测 | SRE | 容量测算 |
| D-3 | 灰度 5% 开启 | SRE | 灰度看板 |
| D-1 | 灰度复盘 | PM + SRE | 放量决议 |
| D0 | 放量 100%，归档 | 平台 | release manifest |
| D+3 | 回滚演练 | SRE | 演练记录 |

D-3 到 D0 之间如果指标变差，走回滚而不是延期——已灰度的流量留着，问题会一直存在。

## 5. 通过标准：不是"准确率 90%"

绝对阈值没有意义——模型会升级，题目会变难。正确做法是**对标现网基线**：

| 指标 | 现网基线 | 通过线 | 一票否决 |
|---|---|---|---|
| 总通过率 | 91% | ≥89%（−2 pt） | <85% |
| 工具调用参数正确率 | 94% | ≥92% | <88% |
| 安全拒答率 | 97% | ≥95% | <90% |
| JSON 合法率 | 99.5% | ≥99% | <97% |
| TTFT p95 | 610 ms | ≤800 ms | >1,000 ms |

三条规则：

1. **总分允许 −2 pt**，因为新版本常在边缘题上波动；
2. 任何单项跌破一票否决线，整体不通过——85% 总分里工具调用 0 分也是废的；
3. **安全项只许升不许降**，没有"−2 pt"的余地。

---

## 6. 三个陷阱

| 陷阱 | 表现 | 防法 |
|---|---|---|
| **过拟合评测集** | 每次调 Prompt 都涨分，上线不涨 | 留出 20% 从不参与调优的"盲测集"，每月换题 |
| **Judge 偏见** | 偏爱长回答、偏爱第一个选项 | 交换 A/B 顺序、双 judge 交叉 |
| **分布漂移** | 评测集是三个月前的，生产已经变了 | 每月按生产日志重采样 |

第一条最隐蔽：团队反复在 50 题上调 Prompt，分数从 78% 刷到 93%，
上线后真实通过率只有 79%——刷的是题，不是能力。

### 6.1 多久跑一次

| 触发 | 跑什么 | 耗时 |
|---|---|---|
| 模型版本上线 | 全量 50 题 + 盲测 20 题 | 25 s |
| Prompt 变更 | 全量 50 题 | 20 s |
| 工具 schema 变更 | 工具类 15 题 | 8 s |
| 每日巡检 | 盲测 20 题 | 10 s |
| 每月 | 按生产日志重采样换题 | 半天 |

每次变更都跑，但只在"晋级"时跑盲测集——盲测集见得多就失效了。

## 7. 代码：一个能跑的评测脚本

```python
import asyncio, json, statistics
from collections import Counter

async def run_case(client, case):
    resp = await client.chat(case["messages"], max_tokens=case.get("max_tokens", 512),
                             tools=case.get("tools"), temperature=0)
    return judge(case, resp)          # 返回 (passed: bool, detail: dict)

def judge(case, resp):
    t = case["type"]
    if t == "intent":
        return resp.intent == case["expect"], {"got": resp.intent}
    if t == "tool":
        got = [(c.name, c.args) for c in resp.tool_calls]
        return got == case["expect_calls"], {"got": got}
    if t == "json":
        try: json.loads(resp.text); return True, {}
        except Exception: return False, {"raw": resp.text[:80]}
    if t == "refusal":
        return case["should_refuse"] == resp.refused, {}
    if t == "recall":
        return case["needle"] in resp.text, {}
    raise ValueError(t)

async def main():
    cases = json.load(open("eval/cases_50.json"))
    client = make_client(model="200b-moe")
    results = await asyncio.gather(*[run_case(client, c) for c in cases])
    by_type = Counter()
    for c, (ok, _) in zip(cases, results):
        by_type[(c["type"], ok)] += 1
    total = sum(ok for ok, _ in results) / len(results)
    print(f"总通过率 {total:.1%}")
    for t in {c["type"] for c in cases}:
        n = by_type[(t, True)] + by_type[(t, False)]
        print(f"  {t:8s} {by_type[(t, True)]}/{n}")
```

三个要点：

| 要点 | 原因 |
|---|---|
| `temperature=0` | 否则同一题两次结果不同，无法回归 |
| 按类型分组报 | 总分掩盖单类崩 |
| 并发跑 | 50 题串行要 5 分钟，并发 20 秒 |

## 8. 最终选型矩阵

| 候选 | 通过率 | 成本 | TTFT p95 | 结论 |
|---|---|---|---|---|
| 8B | 62% | 0.078 分 | 300 ms | 只做意图分类的子任务 |
| 30B 稠密 | 74% | 0.294 分 | 450 ms | ❌ 主路径不够 |
| 70B 稠密 | 78% | 0.686 分 | 700 ms | ❌ 贵且不够 |
| 200B MoE | 91% | **0.294 分** | 610 ms | ✅ **主路径** |
| 外部 API | 93% | 3.5 分 | 900 ms | 只做兜底与冷启动 |

**混合部署**才是最终答案：

```
8B   → 意图分类、简单问答（占流量 40%，成本 1/4）
200B → 复杂售后（占流量 55%）
API  → 兜底与疑难（占流量 5%）
```

按这个比例，加权成本 ≈ 0.4×0.078 + 0.55×0.294 + 0.05×3.5 = **0.37 分/轮**，
比全用 200B（0.294）贵一点，但比全用 API 便宜 9 倍。

## 9. 失败模式

| 现象 | 根因 | 怎么发现 | 怎么修 |
|---|---|---|---|
| 评测 93%，上线 79% | 刷题过拟合 | 盲测集分数低 | 换题 + 盲测 |
| 总分 89% 但工具调用 0 分 | 平均掩盖单类 | 分组报告 | 一票否决 |
| 上线后"感觉变笨" | 分布漂移 | 生产抽样通过率 | 每月重采样 |
| Judge 分数虚高 | 长度偏好 | A/B 交换后不一致 | 双 judge |
| 换模型后成本翻倍 | 只看通过率不看 token | 统计 output_tokens | 加成本维度 |
| 安全测试全过但线上被绕过 | 缺对抗样本 | — | 补注入类用例 |

## 10. 验收

| 检查项 | 通过标准 |
|---|---|
| 题量与覆盖 | ≥50 题，5 类齐全，工具调用占比 ≥25% |
| 分布一致 | 与生产分布 KL 散度 <0.1 |
| 盲测集 | 存在且从不参与调优，20 题以上 |
| Judge 校准 | 与人工 Kappa ≥0.8 |
| 一票否决 | 安全/JSON/延迟三项独立判定 |
| 分组报告 | 每类单独出分，不只有总分 |
| 可复现 | 固定 temperature=0、固定评测集版本 |

## 11. 备选方案

| 方案 | 何时选 | 代价 |
|---|---|---|
| 全用外部 API | 日调用 <10 万 | 成本 12×，数据出境 |
| 只用 8B + 规则 | 任务高度确定 | 复杂售后走不通 |
| 蒸馏 200B → 30B | 已有 6 个月以上真实轨迹 | 需要 3–6 个月，效果天花板低于教师 |
| 微调 30B | 领域非常窄 | 泛化差，版本管理复杂（第 5 章） |

**顺序建议**：先用 MoE 大模型跑通业务，收集 6 个月真实轨迹，再考虑蒸馏小模型降本。

## 12. 收口

> **选型不是选最强，是选"在成本与延迟约束下，能力刚好够用"的那个。
> MoE 之所以成为默认答案，是因为它把"更大"和"更便宜"从对立变成了同向。**
