# 第 04 章 · 选型与能力评测

> 读完你能回答：
> ① 为什么是 200B MoE / 30B 激活，而不是 30B 稠密或 70B？
> ② 50 道评测题怎么出、怎么判、判到什么程度算通过？
> ③ 评测集会不会过拟合？三个陷阱怎么防？
> ④ 上线后发现能力不够，先改哪里？

## 1. 问题：最贵的那个反而最便宜

售后 Agent 上线前，团队把四个候选都跑了一遍：

| 模型 | 激活参数 | 推理成本 | 50 题通过率 | 结论 |
|---|---|---|---|---|
| 8B 稠密 | 8B | 0.078 分/轮 | 62% | ❌ 工具调用经常错参 |
| 30B 稠密 | 30B | 0.294 分/轮 | 74% | ❌ 多步任务掉链子 |
| 70B 稠密 | 70B | **0.686 分/轮** | 78% | ❌ 贵且不够好 |
| 200B MoE（30B 激活） | 30B | **0.294 分/轮** | 91% | ✅ |

**最反直觉的一行是最后一行**：200B 的总参数是 70B 的 2.9 倍，但成本只有它的 43%。

因为推理成本由**激活参数**决定，不由总参数决定。

> 这一条是本章的前提：能力看总参数，算力成本看激活参数。
> 但带宽成本要看"专家并集"——§3.0.3 会把它拆开讲。

---

## 2. 三个维度，不能只看一个

| 维度 | 怎么量 | 我们的一票否决线 |
|---|---|---|
| **能力** | 50 题通过率 | <85% |
| **成本** | 分/轮（推理算力） | >0.8 分/轮 |
| **延迟** | TTFT（Time To First Token） p95 / TPOT（Time Per Output Token） p95 | TTFT >1,000 ms |

三者是乘性关系，不是加性：

```
能不能用 = 能力达标 × 成本可承受 × 延迟可接受
```

任何一项为 0，整体为 0。所以先做一票否决，再比总分——不要用加权平均掩盖硬伤。

## 3. 为什么是 200B MoE / 30B 激活

### 3.0 四个词先分清：稠密、稀疏、总参数、激活参数

它们不是同一个维度上的四种东西，而是**两组正交的概念**：

| 组 | 概念 | 回答什么 |
|---|---|---|
| **结构** | 稠密（dense） / 稀疏（sparse, MoE） | 算一个 token 时，是否用到全部参数 |
| **数量** | 总参数（total） / 激活参数（active） | 权重一共多大 / 单 token 实际用多少 |

两者的关系是一句话：

```
稠密模型：active = total          （稀疏度 0）
MoE 模型：active < total          （稀疏度 = 1 − active/total）
```

所以"稠密"是"激活等于总量"的特例，不是另一种参数。

我们的 200B MoE：总参数 200B，激活 30B，**稀疏度 85%**。

```
┌─────────────────────────────────────┐
│ 总参数 200B（权重全在显存里）          │  ← 决定显存、决定"知识容量"
│  ┌───────────────┐                  │
│  │ 激活 30B       │  ← 这个 token 用到 │  ← 决定 FLOPs、决定成本
│  └───────────────┘                  │
└─────────────────────────────────────┘
```

### 3.0.1 能力为什么看总参数

能力随总参数增长，但这是经验规律，不是定律。

参数越多、知识类任务越好，这个趋势在稠密模型上拟合得很准——缩放定律（loss ∝ N^(−α)）就是这么来的。但把它直接搬到 MoE 上会出问题：同样是 30B 激活，200B 的 MoE 在知识问答上能领先十几分，换到多步推理和数学，差距缩到两三分。

差异的来源通常这样解释：专家结构擅长"记住"，而推理链要求激活路径本身连贯，被路由打断就会掉。

所以 91% 和 74% 这两个数，是 50 道题跑出来的，不是从"参数大"推出来的。换一套更偏推理的题，差距会缩到 5 个点以内。

### 3.0.2 为什么成本看激活参数

算力这一侧是严格的：

```
每 token 前向 FLOPs ≈ 2 × 激活参数
稠密 30B：2 × 30e9 = 6.0e10 FLOPs
MoE 200B/30B：2 × 30e9 = 6.0e10 FLOPs   ← 完全相同
稠密 70B：2 × 70e9 = 1.4e11 FLOPs        ← 2.33 倍
```

这就是"200B 比 70B 便宜"的全部原因：算力只认激活，不认总量。

但带宽这一侧有个坑，必须讲清。

### 3.0.3 带宽侧：专家并集会随 batch 放大

decode 每步要把权重读一遍。稠密模型读全部；MoE 只读**被路由到的专家**。

问题在于：一个 batch 里有 B 个 token，它们激活的专家可能不同，要读的是**并集**：

```
期望并集专家数 = E × (1 − (1 − k/E)^B)
E = 专家总数，k = 每 token 激活数
```

按 E=64、k=8 算：

| batch | 并集专家数 | 占全集 | 含义 |
|---|---|---|---|
| 1 | 8 | 12.5% | 只读 1/8 权重，很省 |
| 8 | 42 | 66% | 省一半 |
| 16 | 56 | 88% | 基本读全了 |
| 64 | 64 | 100% | **和稠密模型一样读全量** |

**结论要修正一句**：

> 成本看激活——在算力受限时严格成立；在带宽受限时，要看"有效激活"（专家并集）。

对实践的指导：

| 场景 | 瓶颈 | MoE 收益 |
|---|---|---|
| Prefill（算力受限） | FLOPs | 完全按激活算，收益最大 |
| Decode 小 batch | 带宽 | 收益大（只读 1/8） |
| Decode 大 batch（≥32） | 带宽 | 收益缩小（读全量，但摊到更多 token） |

单 token 的带宽成本 = 并集字节 ÷ B，所以 batch 越大越便宜——
这也是为什么吞吐要靠大 batch，而不是靠堆卡。

### 3.1 一条经验规律

```
能力 ≈ f(log 总参数)
成本 ∝ 激活参数
```

把这两条画在一起，MoE 的价值就出来了：

| 方案 | 总参数 | 激活 | 相对算力 | 能力（通过率） |
|---|---|---|---|---|
| 30B 稠密 | 30B | 30B | 1.0× | 74% |
| 70B 稠密 | 70B | 70B | 2.33× | 78% |
| 200B MoE | 200B | 30B | 1.0× | 91% |

同样算力下，MoE 用 6.7 倍的参数换来了 17 个点的通过率。

### 3.2 MoE 的代价必须说清

| 代价 | 数值 | 影响 |
|---|---|---|
| **显存** | 权重 200 GB（FP8），TP8 每卡 25 GB | 单卡装不下，必须 8 卡起 |
| **通信** | 专家并行 all-to-all | 跨机走 IB 50 GB/s，是瓶颈（第 9 章） |
| **负载不均** | 热门专家排队 | 需要 EPLB（Expert Parallel Load Balancer） 均衡（第 10A 章） |
| **显存换 KV** | 640 GB 里 200 GB 给权重，KV 只剩 400 GB | 并发上限被压缩 |

**推翻条件**：如果目标硬件只有 40 GB 显存（如部分国产卡），200 GB 权重装不进 8 卡，
MoE 方案直接不成立——这时只能退到 30B 稠密或更激进的量化。

## 4. 评测集：50 道题怎么出

### 4.1 分布必须等于生产分布

评测集最容易犯的错不是"题太少"，而是**题和生产不像**。

| 类型 | 数量 | 考什么 | 判分方式 |
|---|---|---|---|
| 单轮意图识别 | 10 | 分类准不准 | 精确匹配 |
| **多步工具调用** | 15 | 参数对不对、步数对不对 | 调用序列比对 |
| 长上下文检索 | 8 | 32K 里的事实召回 | 关键字段匹配 |
| 拒答与安全 | 7 | 该拒的拒、不该拒的不拒 | 规则 + 人工 |
| 结构化输出 | 10 | JSON 合法率 | schema 校验 |

五类加起来 50 道。**权重不是平均的**——多步工具调用占 30%，因为它是售后 Agent 的主路径。

### 4.2 题目从哪来

| 来源 | 占比 | 说明 |
|---|---|---|
| 生产日志采样 | 60% | 脱敏后取真实分布 |
| 人工构造 | 25% | 覆盖长尾与边界 |
| 对抗样本 | 15% | 提示注入、错别字、方言 |

对抗样本是唯一能提前发现安全事故的类别，不要省。

### 4.3 判分：三种手段，按可靠性排序

| 手段 | 适用 | 可靠性 |
|---|---|---|
| **规则/精确匹配** | 分类、JSON、字段 | 最高（无歧义） |
| **调用序列比对** | 工具调用 | 高（可精确到参数） |
| LLM-as-judge | 开放式回答 | 中（需校准） |

用 judge 有前提：与人工标注的一致率 Kappa ≥0.8 才能用，否则就是自欺欺人。

## 5. 通过标准：不是"准确率 90%"

绝对阈值没有意义——模型会升级，题目会变难。正确做法是**对标现网基线**：

| 指标 | 现网基线 | 通过线 | 一票否决 |
|---|---|---|---|
| 总通过率 | 91% | ≥89%（−2 pt） | <85% |
| 工具调用参数正确率 | 94% | ≥92% | <88% |
| 安全拒答率 | 97% | ≥95% | <90% |
| JSON 合法率 | 99.5% | ≥99% | <97% |
| TTFT p95 | 610 ms | ≤800 ms | >1,000 ms |

三条规则：

1. **总分允许 −2 pt**，因为新版本常在边缘题上波动；
2. 任何单项跌破一票否决线，整体不通过——85% 总分里工具调用 0 分也是废的；
3. **安全项只许升不许降**，没有"−2 pt"的余地。

---

## 6. 三个陷阱

| 陷阱 | 表现 | 防法 |
|---|---|---|
| **过拟合评测集** | 每次调 Prompt 都涨分，上线不涨 | 留出 20% 从不参与调优的"盲测集"，每月换题 |
| **Judge 偏见** | 偏爱长回答、偏爱第一个选项 | 交换 A/B 顺序、双 judge 交叉 |
| **分布漂移** | 评测集是三个月前的，生产已经变了 | 每月按生产日志重采样 |

第一条最隐蔽：团队反复在 50 题上调 Prompt，分数从 78% 刷到 93%，
上线后真实通过率只有 79%——刷的是题，不是能力。

### 6.1 多久跑一次

| 触发 | 跑什么 | 耗时 |
|---|---|---|
| 模型版本上线 | 全量 50 题 + 盲测 20 题 | 25 s |
| Prompt 变更 | 全量 50 题 | 20 s |
| 工具 schema 变更 | 工具类 15 题 | 8 s |
| 每日巡检 | 盲测 20 题 | 10 s |
| 每月 | 按生产日志重采样换题 | 半天 |

每次变更都跑，但只在"晋级"时跑盲测集——盲测集见得多就失效了。

## 7. 代码：一个能跑的评测脚本

```python
import asyncio, json, statistics
from collections import Counter

async def run_case(client, case):
    resp = await client.chat(case["messages"], max_tokens=case.get("max_tokens", 512),
                             tools=case.get("tools"), temperature=0)
    return judge(case, resp)          # 返回 (passed: bool, detail: dict)

def judge(case, resp):
    t = case["type"]
    if t == "intent":
        return resp.intent == case["expect"], {"got": resp.intent}
    if t == "tool":
        got = [(c.name, c.args) for c in resp.tool_calls]
        return got == case["expect_calls"], {"got": got}
    if t == "json":
        try: json.loads(resp.text); return True, {}
        except Exception: return False, {"raw": resp.text[:80]}
    if t == "refusal":
        return case["should_refuse"] == resp.refused, {}
    if t == "recall":
        return case["needle"] in resp.text, {}
    raise ValueError(t)

async def main():
    cases = json.load(open("eval/cases_50.json"))
    client = make_client(model="200b-moe")
    results = await asyncio.gather(*[run_case(client, c) for c in cases])
    by_type = Counter()
    for c, (ok, _) in zip(cases, results):
        by_type[(c["type"], ok)] += 1
    total = sum(ok for ok, _ in results) / len(results)
    print(f"总通过率 {total:.1%}")
    for t in {c["type"] for c in cases}:
        n = by_type[(t, True)] + by_type[(t, False)]
        print(f"  {t:8s} {by_type[(t, True)]}/{n}")
```

三个要点：

| 要点 | 原因 |
|---|---|
| `temperature=0` | 否则同一题两次结果不同，无法回归 |
| 按类型分组报 | 总分掩盖单类崩 |
| 并发跑 | 50 题串行要 5 分钟，并发 20 秒 |

## 8. 最终选型矩阵

| 候选 | 通过率 | 成本 | TTFT p95 | 结论 |
|---|---|---|---|---|
| 8B | 62% | 0.078 分 | 300 ms | 只做意图分类的子任务 |
| 30B 稠密 | 74% | 0.294 分 | 450 ms | ❌ 主路径不够 |
| 70B 稠密 | 78% | 0.686 分 | 700 ms | ❌ 贵且不够 |
| 200B MoE | 91% | **0.294 分** | 610 ms | ✅ **主路径** |
| 外部 API | 93% | 3.5 分 | 900 ms | 只做兜底与冷启动 |

**混合部署**才是最终答案：

```
8B   → 意图分类、简单问答（占流量 40%，成本 1/4）
200B → 复杂售后（占流量 55%）
API  → 兜底与疑难（占流量 5%）
```

按这个比例，加权成本 ≈ 0.4×0.078 + 0.55×0.294 + 0.05×3.5 = **0.37 分/轮**，
比全用 200B（0.294）贵一点，但比全用 API 便宜 9 倍。

## 9. 失败模式

| 现象 | 根因 | 怎么发现 | 怎么修 |
|---|---|---|---|
| 评测 93%，上线 79% | 刷题过拟合 | 盲测集分数低 | 换题 + 盲测 |
| 总分 89% 但工具调用 0 分 | 平均掩盖单类 | 分组报告 | 一票否决 |
| 上线后"感觉变笨" | 分布漂移 | 生产抽样通过率 | 每月重采样 |
| Judge 分数虚高 | 长度偏好 | A/B 交换后不一致 | 双 judge |
| 换模型后成本翻倍 | 只看通过率不看 token | 统计 output_tokens | 加成本维度 |
| 安全测试全过但线上被绕过 | 缺对抗样本 | — | 补注入类用例 |

## 10. 验收

| 检查项 | 通过标准 |
|---|---|
| 题量与覆盖 | ≥50 题，5 类齐全，工具调用占比 ≥25% |
| 分布一致 | 与生产分布 KL 散度 <0.1 |
| 盲测集 | 存在且从不参与调优，20 题以上 |
| Judge 校准 | 与人工 Kappa ≥0.8 |
| 一票否决 | 安全/JSON/延迟三项独立判定 |
| 分组报告 | 每类单独出分，不只有总分 |
| 可复现 | 固定 temperature=0、固定评测集版本 |

## 11. 备选方案

| 方案 | 何时选 | 代价 |
|---|---|---|
| 全用外部 API | 日调用 <10 万 | 成本 12×，数据出境 |
| 只用 8B + 规则 | 任务高度确定 | 复杂售后走不通 |
| 蒸馏 200B → 30B | 已有 6 个月以上真实轨迹 | 需要 3–6 个月，效果天花板低于教师 |
| 微调 30B | 领域非常窄 | 泛化差，版本管理复杂（第 5 章） |

**顺序建议**：先用 MoE 大模型跑通业务，收集 6 个月真实轨迹，再考虑蒸馏小模型降本。

## 12. 收口

> **选型不是选最强，是选"在成本与延迟约束下，能力刚好够用"的那个。
> MoE 之所以成为默认答案，是因为它把"更大"和"更便宜"从对立变成了同向。**

## 13. 复盘卡

```
一句话：能力看总参数、成本看激活参数；200B MoE 用 30B 的算力拿到 91% 通过率。
我算的：70B 稠密 0.686 分/轮 vs 200B MoE 0.294 分/轮，后者便宜 57% 还强 13 个点。
我原来以为…实际…差在：以为参数大就贵，实际贵不贵取决于激活多少。
还没懂：混合部署里 8B 与 200B 的路由准确率怎么保证——分错一次就白省。
```
