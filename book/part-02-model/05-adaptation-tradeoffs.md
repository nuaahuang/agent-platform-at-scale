# 第 05 章 · 适配取舍：Prompt / RAG / 微调 / 蒸馏

> 读完你能回答：
> ① 客诉说"它不懂我们的业务"，这句话背后可能是三种病，怎么分？.
> ② 四种手段改的分别是什么，改一个要多久、能不能回滚？
> ③ RAG 的三个天花板在哪，什么时候它反而不如把文档塞进 Prompt？
> ④ 微调的三个门槛缺一个就不该做，分别是哪三个？
> ⑤ 蒸馏什么时候值得，什么时候只是把老师的错抄一遍？

---

## 1. 同一句抱怨，三种病

运营那边反馈："它不懂我们售后业务。"

这句话本身没有信息量。把它拆开，至少是三种完全不同的病，对应四条不同的修复路径：

| 用户实际遇到的现象 | 病在哪 | 该走哪条路 | 修复周期 |
|---|---|---|---|
| 问"我的订单到哪了"，模型答"请提供订单号"但不查 | 不知道有这个工具 | Prompt 补工具说明 | 半天 |
| 问"签收 9 天能退吗"，模型答"可以退" | 不知道政策是 7 天 | RAG 检索政策 | 两周 |
| 每次回复都带"亲~"，不符合客诉场景 | 行为不符合要求 | Prompt 改语气约束 | 半天 |
| 输出的 JSON 少了 `refund_amount` 字段 | 格式不稳定 | Prompt few-shot 或微调 | 3 天到 2 个月 |
| 多步退款流程走到第三步就乱 | 能力不足（不是知识） | 换更大模型，或拆步骤 | 换模型 |

这张表是本章的地基。四件事修的从来不是同一个东西：

- Prompt 改的是**指令**，模型权重和知识都没动
- RAG 改的是**这次请求的输入上下文**，知识在系统外
- 微调改的是**权重**，知识进模型了，但会忘
- 蒸馏改的是**模型规模**，用一个小的去模仿大的

选错路径的代价不是白花钱，是花两个月得出"这条路不行"的结论，然后再花两个月。

## 2. 这些手段在训练的哪个位置

预训练、后训练、微调、蒸馏不是四个并列的选项。前两个是模型厂商造模型的阶段，后两个是你拿到模型之后的动作：

```
预训练 ──────┼────── 后训练 ──────┼────── 微调 ──────┼────── 蒸馏
学语言与世界知识      学"怎么对话"        学"你的业务"        换个小的重学
10T+ token          百万条              5 千条             5 万条
厂商做               厂商做              你做               你做
亿元级               百万元              万元               万元
```

先把这个位置关系记住，后面四条路的取舍才说得清。

### 2.1 预训练：把世界压进权重

预训练做的事只有一个：给一段文本，预测下一个 token。用 10 到 20 万亿 token 反复练这一件事。

产出叫基座模型（base model）。它的特点是会续写，不会对话。你问它"你好"，它可能续写"你好，请问有什么可以帮您"——不是因为它理解指令，是因为客服语料里这句话出现得太多次。

成本量级：200B 参数、30T token，按 2 万卡天算，¥10/卡时大约 2 亿元。这是模型厂商的生意，不是你的。

你在这个阶段唯一要关心的事是供应商的发版节奏，因为它决定你什么时候需要重做微调和评测。

### 2.2 后训练：让基座学会"听话"

后训练把"续写器"变成"助手"，分两段：

第一段是 SFT（Supervised Fine-Tuning，监督微调），用百万级的（指令，回答）对训练，教它三件事：看懂指令、按格式输出、知道什么时候拒绝。

第二段是偏好对齐，让它学会"哪种回答更好"。两条技术路线：

| 路线 | 做法 | 成本 | 稳定性 |
|---|---|---|---|
| RLHF | 训奖励模型 + PPO 强化学习 | 高（要训三个模型） | 难调，容易训崩 |
| DPO | 直接用偏好对做对比学习 | 低（一个模型） | 稳定，工程上更常用 |

这里有个必须记住的认知：知识在预训练就定了，后训练改的是表达方式。所以"模型不知道我们公司政策"这件事，后训练同样救不了——它只是让模型更会把自己知道的东西说得像那么回事。

### 2.3 微调：你和厂商做的是同一件事

技术上，后训练里的 SFT 就是微调。区别不在方法，在谁做、用什么数据、为了什么：

| | 厂商的后训练 SFT | 你的微调 |
|---|---|---|
| 数据来源 | 通用指令集（公开采集 + 众包） | 你的业务日志与标注 |
| 规模 | 百万条 | 5 千到 5 万条 |
| 目标 | 通用助手能力 | 特定任务的格式、话术、分类 |
| 评测 | 通用榜单 | 你的 50 题 |

所以不要把"后训练"和"微调"当成两种技术。它们是同一个动作在不同阶段的两次使用。

工程上你几乎不会做全参微调。200B 全参训练要几百张卡，而 LoRA 只训一小部分参数：

```python
LoraConfig(
    r=16,               # 秩，决定可训练参数量
    lora_alpha=32,      # 缩放，通常取 2×r
    target_modules=["q_proj", "k_proj", "v_proj", "o_proj"],
    lora_dropout=0.05,
)
```

r=16 时，可训练参数约占全量的 0.1%，8 张 H100 六小时能跑完 5 千条样本。

### 2.4 蒸馏：不是阶段，是手段

蒸馏和前三个不在一个维度上。它不是"训练的某个阶段"，而是一种知识迁移的方式，可以发生在任何阶段：

- 预训练阶段蒸馏：学生学老师的 logits 分布（软标签），用 KL 散度对齐
- 后训练阶段蒸馏：学生学老师的回答文本（硬标签），本质是用老师的数据做 SFT

| 形式 | 学生学到什么 | 需要老师开放什么 | 效果 |
|---|---|---|---|
| 硬蒸馏 | 老师的输出文本 | 只要 API | 一般，损失了概率信息 |
| 软蒸馏 | 老师的完整概率分布 | logits 接口 | 更好，小模型可提升 8–12 个点 |

现实里大多数是硬蒸馏，因为外部 API 只给文本。这也是为什么蒸馏出来的模型上限就是老师的水平，且会把老师的错抄得更自信。

### 2.5 一张表分清四件事

| | 预训练 | 后训练 | 微调 | 蒸馏 |
|---|---|---|---|---|
| 在哪个阶段 | 最前 | 预训练之后 | 后训练之后 | 任意阶段，是手段不是阶段 |
| 谁做 | 模型厂商 | 模型厂商 | 你 | 你 |
| 数据量 | 10T+ token | 百万条 | 5 千到 5 万条 | 5 万条 |
| 改哪些参数 | 全部 | 全部 | 0.1%（LoRA）到全部 | 学生全部 |
| 能加新知识吗 | 能 | 少量 | 基本不能 | 继承老师的 |
| 能改行为吗 | — | 能 | 能 | 能 |
| 成本量级 | 亿元 | 百万元 | 万元 | 万元 |
| 周期 | 数月 | 数周 | 数天 | 数周 |

### 2.6 为什么微调加不进新知识

这是最反直觉的一条，机制值得说清楚。

知识存在 FFN 的权重里。要让一个新事实被"记住"，它需要在训练中反复出现几百次，梯度才会把这块权重推到能稳定召回的位置。你的政策文档每条只出现一次，5 千条样本摊下来，每个事实平均曝光一次。

再加上 LoRA 只动 0.1% 的参数，模型能调的余地本来就小。结果就是它学会了"回答政策类问题的语气和句式"，没学会"政策的具体内容"。

这个现象在评测里一眼能看出：问训练集里出现过的条款，它答得很像；问一个训练集里没有的具体订单能不能退，它照样编，而且编得比微调前更流利。

所以分工是固定的：

| 内容类型 | 走哪条路 | 原因 |
|---|---|---|
| 政策条款、价格、库存、订单状态 | RAG | 每天在变，且每条只有一份 |
| 输出格式、话术、分类标准 | 微调 | 稳定、重复、样本量够 |
| 流程约束、拒绝边界 | Prompt | 一两句话能写清 |

### 2.7 对你的三个决策意味着什么

第一，你只做后两个。预训练和后训练是厂商的活，你能控制的是微调和蒸馏，加上 Prompt 和 RAG。

第二，基座升级会废掉你的微调。厂商发新版本时，LoRA 权重和新的基座不兼容，必须重训——而 Prompt 和 RAG 可以直接迁过去。这是"先 Prompt 再 RAG 再微调"的第二个理由（第一个是成本递增）：越靠前的手段，迁移成本越低。

第三，看厂商宣传时留个心眼。说"后训练让模型更懂行业"多半是话术，模型的知识边界在预训练结束时就定了；真要让模型知道你的业务，还得靠 RAG。

## 3. 四种手段的账

先把账摆开，再谈怎么选。

| | 改什么 | 不改什么 | 生效周期 | 回滚成本 | 单轮成本增量 |
|---|---|---|---|---|---|
| Prompt | 指令与约束 | 权重、知识 | 分钟级 | 回滚到旧版本 | +50 到 +300 token 输入 |
| RAG | 输入上下文 | 权重 | 天到周 | 关掉检索开关 | +1,500 到 +3,000 输入 token |
| 微调 | 权重 | 系统架构 | 周到月 | 切回基础模型 | 0（权重变，推理结构不变) |
| 蒸馏 | 模型规模 | 教师模型 | 月 | 切回大模型 | 降 3.8 倍（8B 替 200B） |

回滚成本这一列最容易被忽略。微调把能力写进权重之后，"改回去"意味着重新拿基础模型再训一遍，中间那两周的评测和灰度要重走。Prompt 改坏了，一分钟就能退。

所以原则是按成本递增试：先 Prompt，不行再 RAG，都不够才微调，蒸馏是最后一步且只对高频窄任务做。

## 4. Prompt：最便宜，也最容易高估

Prompt 能解决的都是"模型本来就会，只是没被要求"的事：

- 输出格式（JSON schema、字段顺序、必填项）
- 语气与话术边界（不说"亲"、不承诺具体到账时间）
- 流程约束（先查订单再给方案、退款金额必须复述）
- 拒绝条件（超出权限时转人工）

它解决不了"模型根本不知道"的事。政策条款、这个用户的会员等级、昨天的系统故障——这些不在权重里。硬要用 Prompt 补，得到的不是正确答案，是更自信的编造。

一个具体的边界例子：给模型加一句"退款必须在签收 7 天内"，模型会照做，但它不知道"7 天"从哪天算。这个不知道会以两种方式暴露：一种是答错（用户说"我 8 天前签收的"它还说能退），一种是过度保守（把所有退款都转人工）。两种都比不加这句更糟。

Prompt 的成本要算进去。系统提示从 300 token 涨到 1,200 token，按 prefill 0.09 ms/token 算，TTFT（Time To First Token，首 token 延迟）多 81 ms。基线 610 ms 变成 691 ms，离 800 ms 的红线只剩 109 ms。这就是为什么系统提示不能无限加——它和 TTFT 抢的是同一份 SLO（Service Level Objective）预算。

Prompt 必须有版本号，而且要和评测报告绑定。用 `p-2026-10-27.3` 这种格式，改一次加一次，评测报告的 manifest 里记这个值（第 4 章 §4.8）。没有版本号的 Prompt，出了问题连"什么时候开始坏的"都查不出来。

## 5. RAG：解决"不知道"，但有三个天花板

RAG（Retrieval-Augmented Generation，检索增强生成）的做法很直接：用户提问 → 检索相关文档 → 把文档片段拼进上下文 → 模型基于上下文回答。

它把知识从权重里挪到了系统外，好处是政策改了只改文档，不用重训。但它有天花板，而且三个都在工程侧，不在模型侧。

### 5.1 第一个天花板：检索不到

用户问"我买的东西晚到了三天，能赔吗"，知识库里的条款写的是"配送超时补偿标准"。字面几乎没有重叠，向量检索能不能命中，取决于 embedding 的质量和分块方式。

分块是最常出错的地方。把一份 8,000 字的售后规则按 512 token 切，很可能把"7 天无理由"和它的例外条款切到两块里去。检索命中前半块，模型就按"可以退"回答，而例外条款说的是"拆封的电子产品除外"。

工程上的做法是三件事一起上：

| 手段 | 配置 | 解决什么 |
|---|---|---|
| 分块 | 512 token，重叠 64 | 避免条款被切断 |
| 混合检索 | 向量 + BM25，各取 20 条 | 字面不重叠时靠语义，术语精确时靠关键词 |
| 重排 | 交叉编码器，取前 3 | 20 条里挑真正相关的 3 条 |

三件都做，召回率能从 60% 出头到 85% 左右。只做向量检索就上线，是第一大坑。

### 5.2 第二个天花板：检索到了，但模型没用上

这是更隐蔽的一种。检索结果正确，拼进上下文了，模型回答却绕开了它。

原因有两个。一是上下文太长，关键信息落在中间，模型对首尾更敏感——把最重要的那条放最前面，效果比排序优化更直接。二是上下文里有互相矛盾的条款（新旧政策同时被检索出来），模型会挑一个,挑哪个不确定。

解法是给检索结果加元数据：政策生效日期、适用范围、优先级。拼上下文时按生效日期过滤，冲突时明确告诉模型"以 2026-09 版为准"。这比调 Prompt 有效得多。

### 5.3 第三个天花板：上下文预算和 TTFT 抢资源

这是最硬的一个，也是容量规划里最容易被忽略的。

检索 2,000 token 上下文，prefill 多 180 ms（0.09 ms/token）。基线 TTFT 610 ms 变成 790 ms，而 SLO 是 800 ms——只剩 10 ms 余量，任何抖动都会破线。

所以 RAG 的上下文长度不是一个"效果越好越长"的参数，它有硬上限：

```
可用上下文预算 = (TTFT 目标 − 当前 TTFT) / 0.09 ms per token
```

按 800 ms 目标和 610 ms 基线算，预算是 2,111 token。这决定了 top-k 取 3 还是 5，也决定了要不要做重排压缩。

如果业务确实需要更长的上下文，只有两条路：把 TTFT 目标放宽（用户感知会变差），或者把检索结果做摘要后再拼（多一次模型调用，但省上下文）。

### 5.4 什么时候不该用 RAG

两个判断：

知识总量很小，比如整个售后规则不到 50 页，约 3 万 token。这种情况下把它全塞进系统提示，比搭一套检索系统简单得多，也没有召回失败的风险。代价是每轮多付 3 万 token 的 prefill，按 0.09 ms/token 算 TTFT 要 2.7 秒——超过 SLO，所以只在低峰或离线场景可用。

另一个判断是任务性质：RAG 适合"查了就能答"，不适合"查了还要推"。用户问"我的情况和条款里第三条对不对得上"，这是推理任务，检索解决不了，得靠模型能力和 Prompt 引导。

## 6. 微调：三个门槛，缺一个就别做

微调的诱惑在于它看起来最"彻底"——直接改模型。但它是四条路里唯一会留下长期负债的一条。

### 6.1 门槛一：数据量

高质量样本 5,000 条起，且必须包含错例。

所谓错例，是"模型现在会答错、但正确答案明确"的样本。只用正确样本训，模型学到的是"这种问法该怎么答"，学不到"这种问法容易错在哪"。

数据的另一个要求是一致性。5,000 条样本如果由三个人标，标准不统一，训出来的模型会比基座更不稳定——它把三种标准都学了。

### 6.2 门槛二：任务窄且稳定

微调适合"同一个动作重复一万次"：把非结构化地址解析成省市区、把客诉文本分类到 12 个工单类型、把退款理由映射到标准码。

它不适合"什么都能答"——那是通用能力，微调只会让它在这件事上变差（灾难性遗忘）。判断方法很简单：能不能用一句话写清"这个模型只做这件事"。写不清就别微调。

### 6.3 门槛三：能承担版本管理成本

微调之后，你的发布单元从"Prompt 版本"变成了三件套：模型权重 + 训练数据 + 评测基线。

任何一件变了，都要重跑全量评测。这不是流程洁癖——只跑任务集会漏掉通用能力退化。常见做法是混合数据：80% 任务样本 + 20% 通用样本，训完两边都测。

一个 LoRA 微调的实测量级：8×H100，5,000 条样本，r=16、alpha=32、学习率 1e-4、3 个 epoch，约 6 小时，按 ¥30/卡时算约 ¥1,440。钱不多，贵的是后面的评测和灰度。

### 6.4 灾难性遗忘有多严重

按上面的混合比例训，通用能力通常掉 2 到 5 个百分点。掉在哪很关键：知识问答掉得多，指令遵循掉得少。

如果掉超过 5 个点，说明任务数据和通用数据的比例失衡，或者学习率太高。这两个参数是最常调的两个。

## 7. 蒸馏：只在高频窄任务上划算

蒸馏是让一个小模型学大模型的输出分布。它划算的条件有三个，同时满足才行：

| 条件 | 判据 | 不满足的后果 |
|---|---|---|
| 流量足够大 | 该任务占比 ≥20% | 省下的钱不够训练和评测成本 |
| 任务足够窄 | 一句话能说清 | 学生学不全，掉点严重 |
| 老师足够强 | 老师在该任务上 ≥90% | 学生只能学到老师的水平 |

售后场景里符合条件的是意图分类：占流量 40%，任务窄（12 个类），200B 老师在 50 题上 91%。

做法是拿 200B 标注 5 万条，其中 10% 人工校验，然后用它训 8B。结果通常是 8B 从 62% 提到 85% 到 88%，成本从 0.294 分/轮降到 0.078 分/轮，3.8 倍。

有一个风险要说清：老师答错的样本，学生会学得更自信。因为学生学的不是"正确答案"，是"老师的输出分布"。所以 10% 人工校验那一步不能省，尤其是边界样本。

另一个风险是分布漂移。意图分类的类别会变，加一个新类别就要重蒸一次，否则新类会被硬分到旧类里。

## 8. 决策树

把上面五节压成一棵树，遇到"它不懂业务"这类反馈时从上往下走：

```
用户抱怨"不懂业务"
│
├─ 问：是"不知道事实"还是"行为不对"？
│
├─ 不知道事实（政策、订单、库存）
│   ├─ 知识总量 < 50 页 → 全量塞进 Prompt（注意 TTFT 预算）
│   ├─ 知识会变 → RAG（混合检索 + 重排）
│   └─ 需要跨文档推理 → RAG + 更强的模型，别指望检索本身
│
├─ 行为不对（格式、语气、流程）
│   ├─ 能用一两句话写清规则 → 改 Prompt（半天，先试这个）
│   ├─ 写不清但能举例 → Prompt few-shot（三天）
│   └─ 例子要几千条、且任务极窄 → 微调（两个月）
│
└─ 能力不足（多步推理、长链路）
    ├─ 换更大的模型 → 成本上升，先算账
    └─ 拆步骤 + 每步用小模型 → 工程活，但成本可控
```

这棵树里唯一需要"判断力"的节点是第一个。判断方法不是问产品经理，是拿 20 条 badcase 逐条看：每条错在哪一步，错的原因是"没这条信息"还是"有信息但没用对"。

## 9. 组合起来长什么样

真实的系统不会只用一种。售后 Agent 的分层是这样：

| 层 | 占比 | 手段 | 模型 | 单轮成本 |
|---|---|---|---|---|
| 意图分类 | 40% | 蒸馏到 8B + Prompt | 8B | 0.078 分 |
| 简单问答 | 25% | Prompt + 小 RAG | 8B | 0.11 分 |
| 复杂售后 | 30% | RAG + Prompt | 200B MoE | 0.35 分 |
| 疑难与兜底 | 5% | 大模型 API | 外部 | 3.5 分 |

加权下来约 0.30 分/轮，比全走 200B 的 0.294 分差不多，但复杂场景的成功率高 6 个百分点——这才是分层的目的，不是为了省钱，是为了把预算花在需要的地方。

## 10. 失败模式

| 现象 | 根因 | 怎么发现 | 怎么修 |
|---|---|---|---|
| 加了 RAG，回答反而更差 | 检索到矛盾条款，模型挑错的 | 抽样看上下文里有没有新旧两版 | 按生效日期过滤元数据 |
| Prompt 越写越长，效果没变好 | 指令互相冲突，模型挑一条执行 | 逐条删，看哪条有用 | 砍到 800 token 以内 |
| 微调后通用能力崩了 | 任务数据占比过高 | 训完跑通用评测集 | 混合 80/20 重训 |
| 蒸馏模型在边界样本上特别自信 | 学了老师的错误分布 | 看错误样本的置信度分布 | 10% 人工校验，加拒答样本 |
| RAG 上线后 TTFT 破线 | 上下文预算没算 | 对比上线前后 TTFT p95 | top-k 从 5 降到 3，或加重排压缩 |
| 换了模型，Prompt 全废 | 指令格式不通用 | 新模型上跑全量评测 | Prompt 与模型一起评测，别分开 |

第一条最反直觉：RAG 不是"有总比没有好"。检索系统引入了一个新的失败点，而这个失败点用户看得见——模型会引用一条过时条款，说得头头是道。

## 11. 什么情况下这些结论不成立

| 结论 | 推翻条件 |
|---|---|
| 先 Prompt 再 RAG 再微调 | 知识每天变（如库存、价格）时，微调从一开始就错 |
| RAG 上下文控制在 2,000 token | 模型支持长上下文且 prefill 更快时，可以放宽 |
| 微调需要 5,000 条 | 任务极窄（二分类）时，1,000 条够 |
| 蒸馏只在 ≥20% 流量做 | 成本敏感且延迟要求极严时，10% 也可能值得 |

## 12. 验收：四个问题答得出来才算懂

1. 给定一条 badcase，能判断它属于"不知道"还是"不会"，并说出依据。
2. 能算出加 2,000 token 上下文对 TTFT 的影响，并判断是否破线。
3. 能说出微调之后发布单元变成了哪三件，为什么必须一起绑。
4. 能判断一个任务该不该蒸馏，用哪三个条件。
