# 第 07 章 · 模型版本管理：四层版本，只有一层能请求级灰度

> 读完你能回答：
> ① 代码、Prompt、模型权重、精度格式四层版本，谁能独立发布，谁必须绑在一起？
> ② 版本矩阵里哪些组合是合法的，哪些一上线就出事？
> ③ 为什么模型灰度只能按实例切，不能按请求切？
> ④ 权重一变为什么要作废全部 KV，不作废会怎样？
> ⑤ 30 分钟回滚的前提有三个，缺一个就回不去？

---

## 1. 问题：两个变更撞在同一天

10 月 27 日，两件事排进了同一周：

- 算法组要把模型从 FP8 换成 FP8 加 KV 量化，说能再省 12% 成本
- 产品组要上线新版 Prompt，改退款话术，说客诉能降 8%

两个变更单独看都没问题。一起上，出了问题就分不清是谁的。

更麻烦的是它们互相影响：新 Prompt 更长，prefill 变慢，KV 量化又在长上下文掉点更多。上线后 TTFT（Time To First Token，首 token 延迟）涨了 90 ms、长文通过率掉 2 个点，两个指标都在报警，但没人能说清哪个变更导致的。

这一章解决的就是这件事：把版本拆成可独立发布的层，定清楚谁和谁必须绑、谁变了要重跑什么、谁变了要让什么失效。

## 2. 四层版本

一个 Agent 平台同时存在四种版本，变更频率差两个数量级：

| 层 | 命名示例 | 变更频率 | 影响面 | 谁改 |
|---|---|---|---|---|
| 代码 | `gw-v3.2.1` | 每天 | 全链路 | 工程 |
| Prompt | `p-2026-10-27.3` | 每周 | 行为与格式 | 产品 + 算法 |
| 模型权重 | `w-2026-11-02` | 每月 | 能力与知识 | 算法 |
| 精度格式 | `fp8-e4m3` | 季度 | 性能与精度 | 算法 + 平台 |

这四层的差别不只是频率。前两层可以回滚得很快，后两层回滚要动权重和显存。

关键区别在于：代码和 Prompt 是"可以按请求生效"的，模型权重和精度格式是"按实例生效"的。因为一个推理实例只装得下一份权重，不可能同一个实例对 A 用户跑旧模型、对 B 用户跑新模型。

这个物理约束决定了本章的核心结论：灰度方式被版本类型限制，不是你想怎么切就怎么切。

## 3. 版本矩阵：什么组合是合法的

四层任意组合有 16 种，但只有一部分能跑。下面是实际会遇到的组合：

| 变更 | 必须重跑 | 必须失效 | 能独立发布吗 |
|---|---|---|---|
| 代码（业务层） | 契约测试 | 无 | 能 |
| 代码（引擎 / kernel 层） | 回放 + 压测 | 无 | 能，但要重测性能 |
| Prompt | 50 题 + 盲测 | 前缀缓存（Prompt 是前缀时） | 能 |
| 模型权重 | 50 题 + 回放 + 通用集 | 全部 KV | 能，但要按实例 |
| 精度格式 | 50 题 + 逐题 diff + KL | 全部 KV + 量化校准 | 能，但要按实例 |
| Tokenizer | 全部重测 | 全部 KV + 重新校准 + 重算成本 | 不能，要整体换 |

最后一行是特例。Tokenizer 换了，token id 的映射全变，历史 KV 的哈希、量化的 scale、成本核算的 token 计数全部失效。这种变更不该"灰度"，只能整体切换，而且要提前一周通知所有下游。

三种组合最容易出事：

第一种，新权重配旧 KV。权重变了但缓存没清，新模型读到旧模型算出来的 KV，注意力结果错乱。症状是输出不通顺、答非所问，但不会报错，很难定位。第 10B 章讲过，权重版本是 KV 唯一的真实失效条件，这种事得由发布流程强制保证，不能靠人记得。

第二种，新 tokenizer 配旧量化 scale。Tokenizer 换了之后，激活的数值分布变了，原来的 per-tensor scale 就压不住了，要么溢出被 clamp，要么精度骤降。表现是准确率掉 5 个点以上，但量化配置看起来没变。

第三种，新 Prompt 配旧评测基线。Prompt 改了，通过率从 91% 掉到 89%，团队以为是模型退化，实际是新 Prompt 让模型更保守。基线要和版本绑定，不绑就没法归因。

## 4. 一个串标识完整组合

版本散落在四个地方，发布时必然对不上。解决办法是打成一个 manifest：

```json
{
  "release": "r-2026-11-05.1",
  "code": "gw-v3.2.1",
  "prompt": "p-2026-10-27.3",
  "weights": "w-2026-11-02",
  "precision": "fp8-e4m3",
  "tokenizer": "tok-v4",
  "eval_baseline": "e-2026-10-20",
  "created_at": "2026-11-05T09:12:00Z"
}
```

六个字段缺一个，出问题就查不清。第 4 章的评测报告用同一套 manifest，评测结果和线上运行的是同一个组合——这一点是排查的前提。

manifest 要落到两个地方：镜像的 label（运行时能查到），和发布记录表（历史能查）。只放镜像 label，回滚时找不到旧版本是什么组合；只放记录表，容器里查不到自己跑的是哪个版本。

## 5. 评测门禁：哪几项不过就不许发

门禁不是"跑一遍评测"，是"不过就拦住"。四项硬门禁，来自第 4 章的通过线：

| 门禁 | 通过线 | 一票否决 | 谁看 |
|---|---|---|---|
| 总通过率 | ≥89%（基线 −2pt） | <85% | 自动 |
| 工具调用参数正确率 | ≥92% | <88% | 自动 |
| 安全拒答率 | ≥95% | <90% | 自动 |
| JSON 合法率 | ≥99% | <97% | 自动 |

四项之外还有三条软门禁，需要人签核：

- 通用能力退化不超过 5 个点（防止微调把模型训窄）
- 长上下文（>16K）通过率不低于基线 2 个点
- 成本变化在 ±20% 以内，超出要说明原因

软门禁的意义在于拦住"任务指标变好、整体变差"的发布。这种情况在微调和量化里都常见。

门禁的判定要绑定 manifest。同一份 Prompt、同一个权重、同一套评测集，跑出来的结果才有可比性。换了评测集再比，比的是两件事。

## 6. 灰度：模型层只能按实例切

这是本章最容易做错的地方。

业务代码的灰度是按请求切的：给 5% 的请求打标，走新版本，其余走旧版本。同一个实例可以同时服务两个版本。

模型不行。一个实例的显存里只装得下一份 200 GB 权重，要同时跑两个版本就得两份显存，等于两倍的卡。所以模型灰度只有一种做法：换实例。

具体做法是双池：

```
旧池：2,384 卡，跑 w-2026-10-20
新池：128 卡，跑 w-2026-11-02
路由：按租户哈希，5% 的租户进新池
```

比例从 5% 开始，按租户切而不是按请求切——同一个用户在一次会话里不能一会儿新模型一会儿旧模型，否则上下文对不上。

| 阶段 | 卡数占比 | 观察时长 | 放量条件 |
|---|---|---|---|
| 金丝雀 | 5%（128 卡） | 1 天 | 错误率不升，客诉不升 |
| 小流量 | 20%（512 卡） | 2 天 | goodput 不降，成本符合预期 |
| 半量 | 50% | 2 天 | 以上全部满足 |
| 全量 | 100% | — | 回滚演练通过 |

每个阶段都要跨一个完整的流量周期。只在工作日灰度，周末的流量形态（占比 30%，但客诉集中）根本没覆盖到。

双池期间的成本要额外算：新池 128 卡没有前缀缓存，命中率从 85% 掉到 0，TTFT 会短暂破线。所以所以切流前要先预热（下一节）。

## 7. KV 作废与预热

### 7.1 缓存里存的到底是什么

先把这件事说清楚，后面才谈得上预热。

前缀缓存存的不是请求，也不是回答文本，是 KV 块——每个块 16 个 token 的 K 和 V 张量，1.92 MB，躺在显存里（第 10B 章）。

索引也不是请求 id，是 token 序列的哈希。而且是**链式**的：

```
h0 = hash(块0 的 16 个 token)
h1 = hash(h0 + 块1 的 16 个 token)
h2 = hash(h1 + 块2 的 16 个 token)
```

链式的作用是：要命中第 3 块，必须前 3 块完全相同。这就是为什么只有"从第 0 个 token 开始的前缀"能复用——RoPE 的位置编码使得中间截一段的 KV 不能直接拼。

一个新请求进来，引擎做的事是：

| 步 | 动作 | 结果 |
|---|---|---|
| 1 | tokenize 成 ids | 拿到 3,200 个整数 id |
| 2 | 每 16 个切一块，逐块算链式哈希 | 200 个哈希 |
| 3 | 拿哈希去块池查 | 前 187 块命中，后 13 块未命中 |
| 4 | 只对未命中的 13 块做 prefill | 算 208 个 token，不是 3,200 |
| 5 | 新算出的块写回池子，登记哈希 | 池子变大 |

表里第 1 步的 id 是什么，值得停一下。Tokenizer 把文本切成 token——不是词，是子词片段——每个 token 在词表里有一个下标，这个下标就是 id。现代模型的词表在 12 万到 15 万之间，所以 id 是一个 0 到 15 万之间的整数。

| 文本 | 切分 | id（示意） |
|---|---|---|
| 退货 | 退 / 货 | 45,102 / 8,733 |
| 我的订单 | 我 / 的 / 订单 | 1,024 / 13 / 88,301 |

中文大约 1 个 token 对 1.5 个汉字，所以 3,200 个 id 约等于 2,100 个汉字——正是"系统提示 + 工具定义"的量级。

用 id 而不是文本，是因为模型只认 id。同一句话用不同 tokenizer 切，id 完全不同，算出来的 KV 也不同。这是第 3 节那条规则的根源：换 tokenizer 等于换了一套坐标系，历史 KV 的哈希、量化的 scale、计费的 token 数全部对不上，只能整体切换。

所以"缓存"是引擎在**第一次**处理某个前缀时顺手写下的，不需要任何配置。命中率 85% 这个数，就是长期运行后自然形成的。

### 7.2 那预热是在做什么

预热看清楚了：它是**主动把还没人用过的那段前缀，提前算一遍写进池子**。

不是"把旧请求搬回来"，也不是"重放"——旧 KV 已经随权重版本作废了，搬不回来。是拿同样的文本，用新权重重新算一遍 prefill，得到新 KV，写进池子。

一个具体的例子。售后 Agent 的系统提示加工具定义是 3,000 token，每天出现 50 万次：

| 状态 | 每个请求要 prefill | 单请求耗时 | 一天的总计算量 |
|---|---|---|---|
| 预热前 | 3,000 token | 270 ms | 41,667 小时 |
| 预热后 | 200 token（用户问题） | 18 ms | 2,778 小时 |

差 15 倍。这就是为什么值得花 3 分钟做预热。

那"Top 100"是怎么来的？这里最容易误解成"挑 100 条代表性请求"。不是。

一个请求的结构是这样的：

```
[ system 提示 ][ tools 定义 ][ 历史对话 ][ 用户问题 ]
└────────────── 前缀，全平台只有几百种 ──────────────┘  └ 每次都不同 ┘
```

用户问题各不一样，但前面的 system 和 tools 是模板，全平台只有几百种组合（业务线 × Prompt 版本 × 工具集）。所以统计的对象是**前缀**，不是请求：

| 环节 | 数量级 |
|---|---|
| 一天的请求 | 1.5 亿条 |
| 去掉用户问题、只留 system + tools | 150 万条 |
| 按前缀哈希去重 | 约 200 种 |
| 按出现次数排序取前 100 | 100 种（覆盖 78%） |

真实分布通常更集中：前 5 种前缀就可能覆盖 70%，前 100 种覆盖 78%，后面是长尾。如果业务简单，可能总共只有 8 种前缀，那"Top 100"实际就是 8 条。

反过来说，如果统计出来有几万种前缀，通常不是业务复杂，是有人在系统提示里拼了时间戳、用户名或订单号——变量前置了。这种写法会让缓存命中率长期为零，是设计问题，不是预热能救的（第 20 章讲上下文工程时会再提）。

拿到这 100 个前缀的**文本**之后，才轮到渲染和重算。完整流程七步：

| 步 | 动作 | 产出 |
|---|---|---|
| 1 | 日志取最近 7 天，抽 1% | 150 万条记录 |
| 2 | 每条取 system + tools，canonical JSON 算 SHA1 | 前缀指纹 |
| 3 | 按指纹计数，降序取前 100 | 100 种前缀的文本 |
| 4 | 用线上同款 tokenizer + 模板渲染成 token ids | 每条的真实 id 序列 |
| 5 | 按 id 长度累加，估算 KV 占用，超预算就截断 | 实际预热的条数与总 token |
| 6 | 逐条 `engine.generate(max_tokens=1)` | 引擎切块、算哈希、prefill、写回池子 |
| 7 | 读 `num_cached_tokens` 断言 | 确认写入成功 |

第 5 步最容易被跳过，但它是唯一能防止"预热把显存吃满"的环节。做法不是"100 条乘平均长度"，而是先渲染、按实际长度累加——前缀长度分布很偏，一条 8,000 token 的长前缀顶三条 2,600 的。

算例：

| 前缀档位 | 条数 | 单条 token | 小计 token | KV 占用 |
|---|---|---|---|---|
| 短（<1K） | 55 | 800 | 44,000 | 5.3 GB |
| 中（1–3K） | 30 | 2,000 | 60,000 | 7.2 GB |
| 长（3–8K） | 15 | 5,000 | 75,000 | 9.0 GB |
| 合计 | 100 | — | 179,000 | 21.5 GB |

179,000 token 乘 120 KB 约 21.5 GB，占 400 GB 池子的 5.4%，安全。

如果统计出来是 60 万 token（比如长前缀占比高），就是 72 GB、18%，仍然能跑但接近警戒线。这时候按"每 GB 省多少毫秒"排序，砍掉短前缀——短前缀 prefill 本来就快，预热收益低。

预算公式和警戒水位在 §8.4.2，这里只强调顺序：**先估再算，不是算完再看显存**。

第 6 步是关键：它不是"把文本存进去"，是让引擎**真的算一遍**。算出来的块进了池子，后面真实请求才可能命中。

然后对这 100 条文本，各发一次只跑 prefill 的请求，让引擎按正常路径算出 KV 写进池子。之后真实请求带着同样的 token ids 进来，链式哈希一致，直接命中。

为什么不用"把 KV 存到磁盘再读回来"？因为重算更快也更简单：300K token 的 prefill 只要 27 秒计算，而 36 GB 的 KV 落盘再加载要处理序列化、块布局对齐、版本校验，出一次错就是脏缓存。

### 7.3 权重一变，为什么全废

权重版本变了，KV 就全部作废。这不是缓存策略的问题，是数学上的必然：KV 是旧权重的中间结果，新权重的注意力分布不同，旧 KV 拿来用就是错的。

失效的代价：

| 时点 | 命中率 | TTFT p95 | 现象 |
|---|---|---|---|
| 切换前 | 85% | 610 ms | 正常 |
| 刚切换 | 0% | 1,900 ms | 超时告警集中爆发 |
| 预热 5 分钟后 | 40% | 1,100 ms | 仍破线 |
| 预热 20 分钟后 | 85% | 620 ms | 恢复 |

预热不是等自然流量填满，那要几个小时。做法是主动重算：取线上 Top 100 的前缀（覆盖 78% 的请求），在新实例上各跑一遍 prefill，把新 KV 写进池子。

重算不是简单发一百个请求，中间有三个坑会让命中率停在 20% 上不去。具体做法见 §8.4。

100 条提示的 prefill 计算量是 300K token × 0.09 ms ≈ 27 秒，加上模板渲染、调度和并发度限制，实际 1–3 分钟。之后靠自然流量把长尾补到 85%。

预热要在切流之前做。切完再预热，前 20 分钟的请求全部承受 1.9 秒的 TTFT。

## 8. 滚动替换：把一批卡换掉的完整时序

上一节说模型灰度按实例切，这里补最关键的一段：一个实例从"跑旧模型"变成"跑新模型"，中间到底发生什么。

先纠正一个常见误解。版本切换不做原地换权重，做销毁重建。原因是显存碎片——不重启进程、只卸载权重再加载新权重，第二次加载大概率 OOM。vLLM 的 sleep/wake 是给"同版本内腾显存"用的，不是给换版本用的。

所以一次替换是六步，不是"下载新权重然后热加载"：

| 步 | 动作 | 耗时 | 判据 |
|---|---|---|---|
| 1 | 摘流（从服务发现移除） | 0 秒 | 新请求不再进来 |
| 2 | 等待在途请求跑完 | ≤30 秒 | `active_requests == 0` |
| 3 | 进程退出，KV 随显存释放 | 5 秒 | 显存回落 |
| 4 | 拉新镜像与新权重 | 2–3 分钟 | 权重 checksum 匹配 |
| 5 | 模型 warmup | 2 分钟 | 首 token 延迟回到基线 |
| 6 | KV 预热 | 3 分钟 | 命中率回到 60% 以上 |

单批约 14 分钟，其中 7 分钟是纯等待。下面拆开说每一步的细节。

### 8.1 摘流量：软摘，不是硬断

摘流的意思是把实例从服务发现里移除，让它不再接新请求，但它身上还有正在跑的请求，不能立刻杀。

做法是在 readiness 探针上做文章：

```yaml
lifecycle:
  preStop:
    exec:
      command: ["/bin/sh", "-c", "curl -s -X POST localhost:8000/drain; sleep 30"]
terminationGracePeriodSeconds: 60
readinessProbe:
  httpGet: {path: /healthz/ready, port: 8000}
  periodSeconds: 2
```

`/drain` 做三件事：把 `draining` 置真、对新请求返回 503 加 `Retry-After`、等 `active_requests` 归零。探针失败后 k8s 把它从 Endpoints 摘掉，网关不再路由过来。

30 秒这个数不是拍的。端到端 p99.9 是 15 秒（第 1 章），等两倍覆盖长尾。超过 30 秒还没跑完的，是流式长输出，需要特殊处理：在下一个 token 边界发 `[DONE]` 收尾，前端显示"回答已停止"，而不是报错——用户看到半句话，比看到"网络错误"好得多。

摘流期间的三类请求要分别处理：

| 请求类型 | 处理 | 用户感知 |
|---|---|---|
| 未开始的 | 503 + Retry-After，网关重试到别的实例 | 延迟 +200 ms，无感 |
| 正在跑的非流式 | 等它跑完，最多 30 秒 | 正常 |
| 正在跑的流式 | 到下一个 token 边界收尾 | "回答已停止" |

网关那边要配合：摘流瞬间会有几十个 in-flight 请求同时 503，重试预算要够，否则会把重试风暴变成故障。

### 8.2 清 KV：靠进程退出，不靠"记得清"

KV 在显存里，进程一死操作系统就回收了，不需要单独清。这也是为什么用销毁重建而不是热加载——它把"清 KV"这个容易忘的步骤，变成了物理必然。

如果非要在进程内换（比如只想换 LoRA adapter），必须显式清理，而且要检查两个数：

```python
engine.sleep(level=2)          # 释放 KV 与权重回 CPU
assert torch.cuda.memory_reserved() < 2 * 1024**3   # 低于 2 GB 才算真释放
torch.cuda.empty_cache()       # 归还给驱动，减少碎片
```

只看 `memory_allocated` 降下来不够，`memory_reserved` 才是真正占着卡的量。reserved 没降就加载新权重，会 OOM——而且报的错是"显存不足"，看起来像权重太大，实际是碎片。

### 8.3 加载权重：先落盘，再并行进显存

200 GB 权重不是从对象存储直接进显存的。路径是三段：

```
对象存储 → 节点本地 NVMe（67 秒，3 GB/s） → 各 GPU 显存（约 60 秒）
```

TP8 的 8 个 rank 读同一份文件，走操作系统的页缓存，只有第一遍是真读盘。所以同节点上第二个实例起，加载能快一倍。

加载完必须校验，不能只看文件大小：抽样 16 层算哈希，和 manifest 里的值比对。校验失败就拒绝启动——用错权重比用旧权重危险得多，因为它的表现是"看起来能跑，但结果不对"。

### 8.4 预热分三层，顺序不能反

大多数人只做第一层，结果前几分钟的请求全在踩坑。

| 层 | 做什么 | 耗时 | 不做的后果 |
|---|---|---|---|
| 权重 warmup | 跑 dummy 请求触发 kernel autotune | 2 分钟 | 首个真实请求慢 3–5 秒 |
| KV 预热 | Top 100 提示回填前缀缓存 | 3 分钟 | 命中率 0，TTFT 1.9 秒 |
| 调度预热 | 低流量跑 5 分钟看队列与 TPOT（Time Per Output Token） | 5 分钟 | 配置错误要等放量才发现 |

第一层最容易被跳过。GPU 的 kernel 首次调用要编译和选优，vLLM 在启动时可以用 profile run 提前触发。不做的话，第一个真实请求会吃到 3–5 秒的额外延迟，而灰度阶段偏偏最容易把这个当成"新模型更慢"。

第三层是观察，不是技术动作：新实例接 1% 流量跑 5 分钟，看队列长度、TPOT 分布、显存水位是否和旧实例一致。不一致就停下来查，别急着放量。

#### 8.4.1 Top 100 怎么重算

重算的难点不在"发请求"，在"让引擎算出来的前缀和线上那条逐 token 相同"。

三个坑，每一个都能让命中率停在 20%：

第一个坑是模板。用 messages 数组发送，引擎会用**服务端自己的** chat template 渲染；预热脚本如果你自己拼字符串，两边的 token 序列差一个空格，block hash 就不同，命中不了。正确做法是预热脚本加载**同一个** tokenizer 和模板，直接渲染成 token ids 再发。

第二个坑是工具定义的序列化。tools 里的 key 顺序、空格、是否转义，只要变一处，前缀就变了。必须固定成 canonical JSON（`sort_keys=True`），而且这个序列化函数要和线上网关用同一份代码，不能各写一遍。

第三个坑是只预热了一半。前缀是"系统提示 + 工具定义"这段公共部分，如果预热时漏了 tools，实际请求的前缀比预热的长，照样不命中。

脚本里要包含"先估再算"这一步：渲染完拿到 id 长度，累加超过预算就截断，然后再进循环。

```python
BUDGET_TOKENS = int(400 * 1024**3 * 0.15 / (120 * 1024))   # 15% 池子 ≈ 52 万 token
plan, used = [], 0
for key in top:                       # top 已按出现次数降序
    ids = render(seen[key]["system"], seen[key]["tools"])
    if used + len(ids) > BUDGET_TOKENS:
        break                         # 超预算就停，宁少不炸
    plan.append((key, ids)); used += len(ids)
print(f"预热 {len(plan)} 条，共 {used} token，约 {used*120/1024**2:.1f} GB")
```

完整的回填脚本长这样：

```python
import json, hashlib
from transformers import AutoTokenizer
from vllm import SamplingParams

tok = AutoTokenizer.from_pretrained("/models/w-2026-11-02")

def canonical(obj):
    return json.dumps(obj, sort_keys=True, ensure_ascii=False, separators=(",", ":"))

def render(system, tools):
    msgs = [{"role": "system", "content": system}]
    text = tok.apply_chat_template(
        msgs, tools=tools, tokenize=False, add_generation_prompt=False
    )
    return tok(text, add_special_tokens=False)["input_ids"]

# 1) 从访问日志聚合 Top 100 前缀（按次数排序、按哈希去重）
seen, counter = {}, {}
for line in open("access.jsonl"):
    r = json.loads(line)
    key = hashlib.sha1((r["system"] + canonical(r["tools"])).encode()).hexdigest()
    if key not in seen:
        seen[key] = r
    counter[key] = counter.get(key, 0) + 1

top = sorted(counter, key=counter.get, reverse=True)[:100]

# 2) 逐条走真正的 prefill，只生成 1 个 token
params = SamplingParams(max_tokens=1, temperature=0, ignore_eos=True)
for i, key in enumerate(top):
    ids = render(seen[key]["system"], seen[key]["tools"])
    out = engine.generate(prompt_token_ids=ids, sampling_params=params,
                          request_id=f"prewarm-{i}")
    cached = out.outputs[0].num_cached_tokens
    assert cached >= len(ids) - 16, f"第 {i} 条未命中：缓存 {cached}/{len(ids)}"
```

最后那个 assert 是校验，不是装饰。`num_cached_tokens` 是引擎真实写入的 token 数，减去一个 block（16 token）的边界误差，剩下的必须全部命中。断言挂了说明模板或序列化对不上，这时候继续跑完一百条也没意义。

并发度要控制。预热请求会占用调度器，如果在**存量实例**上做（扩容预热），并发不要超过 4，否则抢走真实请求的 batch。在新实例上做没有这个问题，因为新实例还没接流量——这也是为什么 §8 的时序把预热放在接流之前。

显存代价要提前算：100 条 × 3,000 token = 300K token，按每 token 121 KB 算约 36 GB，占 400 GB KV 池的 9%。如果显存本来就紧张，预热会触发淘汰，把刚写进去的又挤出来，命中率卡在 40% 上不去。这种情况要么降数量到 50 条，要么等扩容。

#### 8.4.2 预热会不会把显存占满

会，而且这是预热最现实的失败方式。

先算账。每个 token 的 KV 约 120 KB（1.92 MB ÷ 16），所以：

| 场景 | 前缀数 | 每前缀 token | 总 KV | 占 400 GB 池 |
|---|---|---|---|---|
| 售后主流程 | 100 | 3,000 | 36 GB | 9% |
| 长文档问答 | 20 | 32,000 | 77 GB | 19% |
| 极端（全量长前缀） | 100 | 32,000 | 384 GB | 96% |

前两行安全，第三行会爆。爆的表现不是报错，是新请求拿不到块，触发淘汰，把刚预热的又挤出去——命中率从 60% 掉回 30%，而且越预热越低。

三个机制让这件事可控。

**第一，预热块不带引用，随时会被淘汰。**

块池是共享的，空闲块按 LRU 排队。预热写进去的块引用计数是 0，一旦有新请求要块，它们就是第一批候选。所以预热是"尽力而为"，不是"钉住"。

这也解释了一个反直觉现象：预热完立刻测命中率是 60%，跑 5 分钟掉到 40%。不是预热没生效，是被真实流量挤掉了。

要让高频前缀留住，得靠"周期性重算"而不是"一次性预热"——每 10 分钟补一次 Top 20，让它们在 LRU 队列里保持新鲜。

**第二，预热前先算预算。**

```
可预热前缀数 = 池子 × (1 − 安全水位) ÷ (前缀长度 × 每 token KV)

安全水位取 15%，留给在途请求

400 GB × 0.85 = 340 GB
3,000 token 前缀：340 GB ÷ 360 MB ≈ 966 条 → 100 条毫无压力
32,000 token 前缀：340 GB ÷ 3.84 GB ≈ 88 条 → 必须减量
```

脚本里加一个累计判断，超预算就截断，只预热前 N 条。宁少不炸。

**第三，健康标准是预热后剩余空闲块不低于 20%。**

预热完立刻查两个数：

```python
free_ratio = engine.num_free_blocks() / engine.num_total_blocks()
assert free_ratio > 0.20, f"预热过量，空闲块只剩 {free_ratio:.0%}"
```

低于 20% 就把预热条数砍半重来。这个阈值不是拍的：真实流量的并发峰值需要足够块才能接住，池子被预热吃到 80% 以上时，一次流量突增就会触发大面积淘汰。

还有一个取巧办法：只预热长前缀。原因不是"短前缀不值得算"，是**单位显存的收益随长度上升**：

| 前缀长度 | prefill 耗时 | KV 占用 | 每 GB 省 |
|---|---|---|---|
| 800 token | 60 ms | 0.09 GB | 655 ms/GB |
| 2,000 token | 159 ms | 0.23 GB | 693 ms/GB |
| 5,000 token | 450 ms | 0.57 GB | 786 ms/GB |
| 8,000 token | 806 ms | 0.92 GB | 880 ms/GB |

如果 prefill 严格按 0.09 ms/token 线性，这一列会是常数（786 ms/GB）——因为时间和显存都正比于长度，比值自然不变。实际上它随长度上升，因为 prefill 里有两部分：

```
T(N) = a·N + b·N²     a ≈ 0.072 ms/token，b ≈ 3.6e-6 ms/token²
       └ 线性层 ┘    └ 注意力，O(N²) ┘
```

线性层（QKV、MLP、专家）按 token 走，注意力按 token 的平方走。5,000 token 时注意力只占 20%，32,000 token 时占到 62%。所以长前缀的每 token 成本更高，它省下的时间也就更多。

这也提醒一件事：0.09 ms/token 是 5,000 token 这个点的平均值，不是常数。用它估算 800 token 会多算 20%，估算 32K 会少算一倍。

不过截断的时候，频次仍然是第一位的。一条出现 50 万次的前缀和一条出现 100 次的，单条收益相同，总收益差 5,000 倍；而长短带来的单位差异只有 34%。排序按"频次 × 单条节省时间"，长度只作为同频次时的次序。

### 8.5 分批的粒度由冗余决定

一批换多少卡，不是拍脑袋，是算出来的：

```
在线容量冗余 = 10%
峰值需求 = 2,512 卡
可承受同时下线 = 2,512 × 10% = 251 卡
每批 ≤ 251 卡，取 128（TP8 的整数倍，也是单节点池的常见粒度）
```

20 批，每批 14 分钟，总计约 4.7 小时。

如果想快，可以并行两批，但容量会掉 10%，正好吃光冗余——这时候任何一次突发流量都会破 SLO（Service Level Objective）。所以并行度不是越快越好，是"冗余除以单批影响"。

一个可以复用的公式：

```
最大并行批次 = floor(容量冗余 / 单批卡数占比)
并行 2 批 = 10% 冗余
并行 3 批 = 15% 冗余
```

没有额外冗余就串行。这也解释了为什么大版本发布要挑低峰期——低峰期的实际负载只有峰值的 45%，等效冗余翻倍。

## 9. 回滚：30 分钟的前提是三个

回滚的目标是 30 分钟内恢复到旧版本。这个数字能不能达到，取决于三件事在发布前有没有准备好。

| 前提 | 不满足会怎样 | 怎么准备 |
|---|---|---|
| 旧权重文件还在 | 要重新导出和校准，2 小时起 | 保留最近 3 个版本，冷存储 |
| 旧版 KV 能重建 | 缓存无法恢复，TTFT 长期破线 | 预热脚本支持指定版本 |
| 数据库 schema 兼容 | 降级后读不了新写入的字段 | 变更前后各保留一个兼容版本 |

第三条最容易忽略。模型版本回滚通常不涉及 schema，但如果同一批发布里带了新字段（比如工具调用记录新增了 `refund_reason_code`），回滚后旧代码读到这个字段会报错，或者直接忽略导致数据丢失。

30 分钟的构成：

```
权重传输 200 GB / 2–3 分钟
分批加载 20 批 × 1 分钟 = 20 分钟（与传输重叠）
切流 2 分钟
预热 3 分钟
合计约 25 分钟，留 5 分钟余量
```

这个账要提前算，不能出事时才算。而且每季度要真做一次回滚演练——演练不做，第一次真回滚一定会超时。

## 10. 版本保留策略：留多了占地方，留少了回不去

权重文件很大，200 GB 一个，攒一年就是 2.4 TB。保留策略要在"回得去"和"存得起"之间定。

| 版本 | 保留时长 | 存哪 | 一个月成本 |
|---|---|---|---|
| 当前线上 | 常驻，每实例一份 | GPU 显存 | 已含在推理成本里 |
| 前一个版本 | 30 天 | 对象存储 + 预热好的实例池 | ¥120 |
| 再往前一个 | 90 天 | 对象存储冷层 | ¥30 |
| 更早 | 删除 | — | 0 |

存得起，是因为对象存储便宜：200 GB 乘 ¥0.15/GB/月，一个版本一个月三十块。真正贵的是"保留可随时切换的实例池"——要真做到 30 分钟回滚，前几天得留一批空卡或者能快速腾出的池子。

所以策略分两档：有明确上线日期的发布，前 7 天留一个 128 卡的空池；日常小版本只保留冷存储里的权重，回滚需要 25 分钟重建。

## 11. 失败模式

| 现象 | 根因 | 怎么发现 | 怎么修 |
|---|---|---|---|
| 输出不通顺、答非所问 | 新权重读到旧 KV | 检查 KV 的权重版本标签 | 强制作废，发布流程加校验 |
| 准确率掉 5 点以上，配置没变 | tokenizer 换了但没重校准 | 对比 token 数与历史 | 重跑量化校准 |
| 灰度没发现问题，全量后崩 | 灰度量不足，没跨周末 | 看灰度时长与流量分布 | 灰度拉长到 5 天，含周末 |
| 回滚超时 | 旧权重文件被清了 | 检查版本保留策略 | 保留最近 3 个版本 |
| 成本突然上涨 | 新 Prompt 变长，prefill 增加 | 对比平均输入 token | 压缩系统提示 |
| 两个变更同时上，无法归因 | 没按层独立发布 | 查 manifest 变更记录 | 一次只改一层 |

第六行是这一章存在的理由。所有规则都可以简化成一句：一次只改一层。

## 12. 什么情况下这些结论不成立

| 结论 | 推翻条件 |
|---|---|
| 模型灰度按实例切 | 用多 LoRA 时，不同 adapter 可在同实例共存，能按请求切 |
| 权重变更必须作废全部 KV | 模型只换了 LoRA adapter 时，基座 KV 仍可用 |
| 灰度至少 5 天 | 安全补丁或严重 bug 修复时，走紧急通道，2 小时内全量 |
| 一次只改一层 | 相邻层强耦合时（如 tokenizer 与量化），必须整体切换 |
