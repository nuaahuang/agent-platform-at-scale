# 第 13 章 · 容量模型：2,512 卡是怎么算出来的

> 读完你能回答：
> ① 从 1.5 亿轮/日 到 2,512 卡，中间要过几步？
> ② 为什么 prefill 按算力算、decode 按并发算？
> ③ 1,609 到 2,512 多出来的 56% 是什么？
> ④ 四个假设里哪个最危险，错 20% 会多花多少钱？
> ⑤ 如果 10% 的请求变成 32K 上下文，卡数会变成多少？

---

## 1. 问题：这个数字被引用了三十次，但从没推过

前面十二章反复出现 2,512 卡：第 1 章算成本用它，第 6 章算量化收益用它，第 7 章算滚动替换用它，附录 B 算训练冲突用它。

但它是怎么来的？如果只会背这个数，换个业务量就废了。

这一章把它拆成六步，每一步都能单独验算。算完之后你会看到，容量方案不是拍一个总数，是六个假设加两个系数的乘积。改任何一个输入，后面的数跟着变——这就是容量模型和容量数字的区别。

先把结论摆出来：

| 步 | 算什么 | 结果 |
|---|---|---|
| 1 | 日 token 量 | 4.8 千亿输入 / 525 亿输出 |
| 2 | 峰值 token 率 | 1.33 千万 token/s（prefill） |
| 3 | prefill 卡数 | 909 |
| 4 | decode 卡数 | 700 |
| 5 | 两个系数 | ×1.3 ×1.2 |
| 6 | 合计 | 2,512 |

下面逐步来。

## 2. 从轮次到 token

业务输入是 1.5 亿轮/日。第一件事是换成 token。

| 参数 | 取值 | 依据 |
|---|---|---|
| 日轮次 | 1.5 亿 | 业务规划 |
| 平均输入 | 1,900 token | 系统提示 1,500 + 用户问题 200 + 检索 200 |
| 平均输出 | 350 token | 售后回答的中位数偏长 |
| 日输入 | 2,850 亿 token | 1.5 亿 × 1,900 |
| 日输出 | 525 亿 token | 1.5 亿 × 350 |

这两个数决定了后面所有推导。它们也是最容易错的——平均输入 1,900 是**全平台均值**，不是某个租户的值。第 7 章里那个 3,200 的售后主流程，只占 1.5 亿轮里的 0.3%，不能拿它当平均值。

再换到峰值：

```
日均 QPS = 1.5 亿 ÷ 86,400 = 1,736
峰值 QPS = 7,000
峰值系数 = 7,000 ÷ 1,736 = 4.0
```

4 倍峰值系数，来自客服场景的作息：早 9 点到晚 9 点是白天均值，晚 8 点到 9 点的一小时是全天峰值，深夜只有白天的一成。

## 3. 为什么 prefill 和 decode 要分开算

这是容量模型最核心的一步，也是最容易混的一步。

同样处理一个 token，prefill 和 decode 的"受限资源"完全不同：

| | prefill | decode |
|---|---|---|
| 算什么 | 一次性算完所有输入 | 逐 token 生成 |
| 算术强度 | 高（M=几百到几千） | 低（M=batch） |
| 受限资源 | **算力**（FLOPS） | **显存容量**（KV 并发） |
| 单位 | token/s | 并发请求数 |
| 卡数由什么决定 | 峰值 token 率 ÷ 单卡吞吐 | 峰值并发 ÷ 单实例并发上限 |

第 2 章的 roofline 已经解释了原因：decode 的算术强度约等于 batch/2，远低于 H100 的平衡点 590，所以它卡在带宽上；而带宽又与 KV 容量绑定——装不下更多并发，就摊不薄权重。

所以两个池子分开建，不用同一个公式。

## 4. prefill 卡数：算力除以吞吐

先算单实例能跑多少 token/s。

200B MoE，30B 激活。每 token 需要 2 × 30e9 = 6e10 FLOPs。TP8 一台 H100 服务器，FP8 峰值 8 × 1,979 TFLOPS = 15.8 PFLOPS，按 MFU 45% 算有效算力：

```
有效算力 = 8 × 1,979 × 0.45 = 7,124 TFLOPS = 7.12e15 FLOPs/s
单实例吞吐 = 7.12e15 ÷ 6e10 = 118,700 token/s
```

峰值需要的 prefill 吞吐：

```
7,000 QPS × 1,900 token = 1.33e7 token/s
```

卡数：

```
1.33e7 ÷ 118,700 = 112 个实例
112 × 8 = 896 卡，向上取整到 909（预留 1.5% 应对长度分布波动）
```

909 卡，113.6 个实例。

这里有个关键选择：**没有扣除前缀缓存的收益**。

线上稳态的命中去重率是 85%，也就是说大部分输入 token 不用重算。如果扣掉，prefill 只需要 200 卡左右。

但这 85% 会在权重版本切换的那一刻归零（第 7 章），届时所有输入都要重算。容量按"缓存全失效"配，才能扛住版本切换和冷启动；命中的时候，那部分就是余量。

所以这里的原则是：**缓存是余量，不是预算。** 按最坏情况配卡，按平均情况花钱。

## 5. decode 卡数：并发除以容量

decode 不能用算力推。它卡在两个地方：KV 容量决定能装多少并发，带宽决定每个 token 多快。

先看单实例能装多少并发。KV 池 400 GB，每 token 的 KV 约 120 KB：

| 平均上下文 | 单请求 KV | 单实例并发 |
|---|---|---|
| 2K | 0.24 GB | 1,666 |
| 8K | 0.94 GB | 425 |
| 32K | 3.84 GB | 104 |

全平台平均上下文按 2K 算，单实例 1,666 并发。

再算峰值并发。总并发 = 峰值 QPS × 平均驻留时间：

```
平均驻留 = TTFT（Time To First Token，首 token 延迟）+ 输出长度 × TPOT（Time Per Output Token，每 token 间隔）
         = 0.6 s + 350 × 0.05 s
         = 18.1 s，取 20 s（含工具调用与重试）
峰值并发 = 7,000 × 20 = 140,000
```

卡数：

```
140,000 ÷ 1,666 = 84 个实例
84 × 8 = 672 卡，取整到 700
```

700 卡，87.5 个实例。

再验一下带宽够不够，别出现"装得下但跑不快"：

```
单步时间 = (权重 200 GB + KV 400 GB) ÷ (8 × 3.35 TB/s)
         = 600 ÷ 26,800 = 22.4 ms
```

22.4 ms 小于 TPOT 目标 50 ms，合格。有意思的是，带宽在这里反而有余量：单实例能跑 1,666 ÷ 0.0224 = 74,000 token/s，而实际只需 7,000 × 350 ÷ 87.5 = 28,000 token/s。

这说明 decode 的卡数是被**并发**压着走的，不是被吞吐。配多了不提升 SLO（Service Level Objective，服务等级目标），配少了直接拒绝请求。

## 6. 两个系数：从 1,609 到 2,512

909 + 700 = 1,609。离 2,512 还差 56%。

这 56% 不是浪费，是两个必须留的余量：

| 系数 | 含义 | 不含它的后果 |
|---|---|---|
| ×1.3 | N+1 冗余与故障域 | 挂一个可用区，容量掉 33%，直接破 SLO |
| ×1.2 | 弹性与碎片 | 灰度双池、权重加载、显存碎片、突发流量，全都没地方放 |

1.3 的来历：三个可用区各承 1/3 流量，任意一个整体不可用时，另外两个要接住全部。这意味着每个 AZ 必须能跑到 1.5 倍负载，平均下来就是多留 50%——但不需要 1.5，因为故障时可以先降级（第 35 章）再扩容，取 1.3 是"能撑住降级后的负载"。

1.2 的来历：第 7 章的双池灰度要同时存在两套实例，占 5%；权重加载和显存碎片占 5%；突发流量的 10 分钟窗口内扩不出来（第 33 章），要预留 10%。加起来 20%。

```
1,609 × 1.3 = 2,092
2,092 × 1.2 = 2,510 → 取整 2,512
```

2,512 这个数就是这么来的。它不是"拍脑袋多买点"，是六步推导加两个系数。

## 7. 回算：成本和单价

容量模型的另一端是钱，两个数必须自洽。

单卡全生命周期成本（3 年折旧 + 电费 + 机位 + 网络）：

```
H100 采购 ¥250,000
3 年折旧：250,000 ÷ (3 × 8,760) = ¥9.5/卡时
电费与制冷：¥3.0/卡时
机位与网络：¥0.4/卡时
合计：¥12.9/卡时
```

年成本：

```
2,512 × 8,760 × 12.9 = ¥2.84 亿
```

单轮成本：

```
¥2.84 亿 ÷ (1.5 亿 × 365) = ¥0.00518 = 0.518 分/轮
```

和第 1 章的 0.517 分/轮对上了（差异来自取整）。这条路走得通，说明容量模型和成本模型是同一套假设，没有各算各的。

反过来也能验：如果只买了 1,609 卡，年成本是 ¥1.82 亿，单轮 0.33 分——看起来便宜，但故障时会全线崩，省下的钱不够赔一次事故。

## 8. 敏感性：哪个假设最危险

六个假设，各错 20%，对卡数的影响不一样：

| 假设 | 基准 | 错 20% 后 | 卡数变化 | 年成本变化 |
|---|---|---|---|---|
| 峰值系数 | 4.0 | 4.8 | +502 卡 | +¥5,680 万 |
| 冗余系数 | 1.56 | 1.87 | +497 卡 | +¥5,620 万 |
| MFU | 45% | 36% | +353 卡 | +¥3,980 万 |
| 平均输入 | 1,900 | 2,280 | +282 卡 | +¥3,180 万 |
| 平均上下文 | 2K | 2.4K | +164 卡 | +¥1,850 万 |
| 平均输出 | 350 | 420 | +39 卡 | +¥440 万 |

把这张表和上面的六步推导对照着看，会发现一个规律：越靠下游的假设，放大效应越强。

前两行加起来接近 1,000 卡，比后面四项的总和还多。

原因是它们位置不同：峰值系数和冗余系数作用在乘法链的末端，前面的数错了只影响自己那一项，后面的系数错了会放大全部。

第三行 MFU 值得单独说。它只影响 prefill 那一半，所以 20% 的偏差只带来 352 卡，而不是 500 卡。大多数人以为"模型跑得快不快"决定容量，其实它只决定容量的一半。

最后一行反直觉：平均输出从 350 涨到 420（+20%），卡数只多 39 张。因为 decode 是按并发配的，而并发 = QPS × 驻留时间，驻留从 20 秒涨到 21.6 秒，只多了 8%，而 700 卡本来就有 4% 的余量。

这说明一件事：**decode 池的余量是把"输出变长"吃掉的**。余量用完之前，输出长度不影响容量；用完那一刻，卡数会跳变。所以真正要盯的不是输出长度的均值，是它冲过余量的时间点。

容量评审时，最该被追问的是"峰值系数凭什么取 4"，而不是"MFU 为什么是 45%"。

## 9. 32K 场景：换一种算法

如果业务从"短问答"变成"长文档"，上面整套推导都要重来，因为瓶颈换了。

假设 10% 的请求是 32K 上下文：

```
平均上下文 = 0.9 × 2K + 0.1 × 32K = 5.0K
单请求 KV = 5.0K × 120 KB = 0.6 GB
单实例并发 = 400 ÷ 0.6 = 667
decode 卡数 = 140,000 ÷ 667 × 8 = 1,679 卡
```

从 700 涨到 1,679，翻 2.4 倍。而 prefill 卡数几乎不变——32K 的 prefill 只是算得久一点，token 总量没变多少。

这个不对称是 32K 场景最难的地方：**它几乎只吃 decode 的并发，不吃 prefill 的算力**。所以不能靠"加 prefill 池"解决，只能加 decode 池，或者用 KV 量化把每 token 的 KV 压一半（第 6 章）。

如果 10% 长上下文就要多买 979 卡，一年 ¥1.1 亿。这时候该问的是：这 10% 的请求值不值得单独建一个池？第 6 章的"形态分离"就是答案——长请求走独立池，不和短请求挤在一起。

## 10. 失败模式

| 现象 | 根因 | 怎么发现 | 怎么修 |
|---|---|---|---|
| 按模型配了卡，上线就不够 | 没留两个系数 | 压测峰值直接破 SLO | 补 1.56，或确认降级路径 |
| 卡够但 TTFT 破线 | prefill 与 decode 混在一个池 | 看两个池子的队列长度 | 拆池，按第 11 章 PD 分离 |
| 成本对不上账 | 容量模型与成本模型用了不同假设 | 反算单轮成本 | 两边共用一张参数表 |
| 版本切换时大面积超时 | 容量按"缓存命中"配的 | 切换瞬间命中率归零 | 按缓存全失效配容量 |
| 长上下文上线后拒绝率飙升 | 并发被 KV 吃掉 | 看单实例并发数 | 长请求独立池，或 KV 量化 |
| 实际只用了一半卡 | 峰值系数取太高 | 看 7 天的实际峰值曲线 | 按 P99 而非理论峰值重算 |

最后一行是反向错误：容量配多了也是错，一年白花几千万。判断依据是连续 30 天的峰值曲线，不是某一天的尖峰。

## 11. 什么情况下这些结论不成立

| 结论 | 推翻条件 |
|---|---|
| 缓存不算进容量 | 缓存命中率长期稳定在 90% 以上且版本切换可预约时，可以扣一部分 |
| 峰值系数 4.0 | 业务有削峰手段（预约、排队）时，可以降到 2.5 |
| decode 按并发算 | 输出极长（>4K token）时，带宽会成为先绑的那一项 |
| 1.3 的冗余 | 单 AZ 部署（放弃多活）时，这 30% 可以省，但要接受整体故障 |

## 12. 验收

1. 能用自己的业务参数（轮次、输入、输出、峰值系数）算出四个数：日 token、峰值 token 率、prefill 卡、decode 卡。
2. 能解释为什么 decode 按并发算而 prefill 按算力算。
3. 能说出 1.3 和 1.2 各覆盖什么，去掉会怎样。
4. 能算出长上下文占比 10% 时 decode 卡数的变化。

## 13. 复盘卡

```
我原来以为…实际…差在：
```

我原来以为卡数 = 总 token ÷ 单卡吞吐，实际差在 decode 那一半根本不能用吞吐算——它被并发和 KV 容量卡着，算力再多也装不下更多请求。

## 14. 延伸

- 第 2 章：roofline，解释为什么 decode 卡在带宽
- 第 6 章：KV 量化如何把单请求 KV 减半，直接改 decode 卡数
- 第 11 章：PD 分离，把两个池子真正拆开
- 第 33 章：弹性，回答"1.2 的弹性预留为什么不能更小"
- 附录 B：训练占用卡时，本章的容量模型要再加一个变量

结论是：2,512 不是一个数，是一条链——业务量乘峰值系数，分成 prefill 与 decode 两条路各自算，最后乘两个冗余系数。链上任何一个环节改写，末端都会变，所以容量评审要问的是假设，不是结果。
