## 1. 先看一个具体的麻烦

最常见的 agent 循环长这样：

```python
def loop(user_msg):
    resp = call_gpt(user_msg)          # 写死了一个模型
    while resp.tool_calls:
        result = run_tool(resp.tool_calls)
        resp = call_gpt(user_msg + result)
    return resp.text
```

现在要支持第二个模型（DeepSeek），得改成：

```python
def loop(user_msg):
    resp = call_gpt(user_msg) if model == "gpt" else call_deepseek(user_msg)
    while resp.tool_calls:
        result = run_tool(resp.tool_calls)
        resp = call_gpt(...) if model == "gpt" else call_deepseek(...)
    return resp.text
```

第三个模型（Qwen）再加一个分支。到第五个模型，这个循环里有五个 if，而且**每加一个模型，你都要重新测整个循环**——哪怕逻辑一点没变。

这是"写死"的代价：**变化的东西被写进了不变的地方。**

dsh 的答案是：

```python
def loop(user_msg):
    resp = ctx.llm.chat(user_msg)      # 只认"能聊天"这件事，不认具体模型
    while resp.tool_calls:
        result = ctx.tools.execute(resp.tool_calls)
        resp = ctx.llm.chat(user_msg + result)
    return resp.text
```

换模型时，循环**一个字不改**，改的是启动配置：让 `ctx.llm` 指向另一个实现。

"旁边挂一个"落到的位置，就是启动配置里那一行，循环的代码不动。

## 2. dsh 的架构，其实只回答三个问题

把上面的例子放大到整个系统，dsh 只是在回答三个问题：

| 问题 | 答案 | 对应的东西 |
|---|---|---|
| 发生的事记在哪？ | 一本只能往后写的账本 | 会话日志 |
| 模型这次该看到什么？ | 从账本里算出来 | 提示词组装 |
| 想加新能力，改哪？ | 加一个插件，不改主干 | Cordis |

三个问题答完，架构就清楚了。剩下的名词都是这三件事的零件。

**关键在第二个答案："算出来"。**

多数系统把"模型该看到什么"存在内存里（一个 `history` 数组），边跑边改。dsh 不存这个数组——它每次**从账本重新算一遍**。

这一个选择改了下面四件事：

| 如果存 history | 如果从账本算 |
|---|---|
| 进程挂了 history 就没了 | 账本在磁盘，重启接着算 |
| 想回放三个月前的请求 | 做不到，history 早被覆盖 | 账本还在，能重放 |
| 想 fork 一条分支 | 要深拷贝数组 | 复制账本前缀即可 |
| 内存和磁盘两份状态 | 可能不一致 | 只有一份真相 |

## 3. 一次请求的流水账

用户说："我要退第 3 件商品。"

dsh 依次做下面这八件事，每一步结束后都会往账本追加至少一条记录，下面是完整顺序：

| # | 谁做 | 做什么 | 写进账本 |
|---|---|---|---|
| 1 | 循环 | 领到这句话，开一个"轮次" | `turn/start` |
| 2 | 循环 | 问插件：这一步该用哪个模型 | （快照保存，不写）|
| 3 | 提示词组装 | 拼出"系统规则 + 最近对话 + 工具说明" | 无（拼出来的） |
| 4 | 循环 | 把拼好的东西发给模型 | `request/header` |
| 5 | 模型 | 回："先查订单，参数是 order_123" | `assistant/message` |
| 6 | 工具层 | 执行 `query_order`，拿到"已签收" | `tool/call` + `tool/result` |
| 7 | 循环 | 还有工具调用欠着，进下一步 | `step/end`，然后回到第 3 步 |
| 8 | 循环 | 模型这次回了最终答案，没有工具调用 | `turn/end` |

一个 5 步的请求，这样的记录大约 47 条，占 47 KB 左右。

**注意第 3 步**：模型看到的内容不是存着的，是**现拼的**。拼的原料是账本里的记录（第 4、5、6 步写进去的那些）。

"唯一真源"落到操作层，就是账本是原料、其他都是成品，成品可以随时重做。

### 3.1 账本真的长这样

上面那张表是抽象说法。真实的记录是这样一行行追加的：

```json
{"seq":118,"turn":7,"step":3,"type":"tool/call","ts":1732435218447,
 "call_id":"call_9f2","name":"query_order","args":{"order_id":"order_123"},"bytes":86}
{"seq":119,"turn":7,"step":3,"type":"tool/result","ts":1732435218552,
 "call_id":"call_9f2","status":"ok","bytes":1240,"tokens":412}
{"seq":120,"turn":7,"step":3,"type":"step/end","ts":1732435218560,
 "usage":{"input":3184,"cached":2902,"output":96},"ms":1153}
{"seq":121,"turn":7,"step":4,"type":"step/start","ts":1732435218561}
```

四个字段值得注意：

| 字段 | 作用 |
|---|---|
| `seq` | 严格递增的序号，并发写入时靠它定序 |
| `turn` / `step` | 定位这条记录属于哪一轮哪一步 |
| `ts` | 毫秒时间戳，用于算耗时和超时 |
| `bytes` / `tokens` | 这条记录占多大，用于算成本和截断 |

`seq` 连续且递增，意味着**任何两条记录之间不会插进第三条**。这是"日志即真相"能成立的基础——如果顺序会乱，重放出来的历史就是错的。

一次 5 步的请求，`seq` 大约从 100 走到 147，共 47 条。第 120 行那条 `step/end` 里的 `usage` 告诉我们：这一步输入 3,184 token，其中 2,902 命中缓存（91%），输出 96 token，耗时 1,153 ms。

这三个数直接对应成本：命中部分按 ¥0.05/百万算，未命中的 282 token 按 ¥10.24/百万算，输出 96 token 按 ¥6.42/百万算。加起来约 0.0012 元。

**日志不只是审计，它就是计费的数据源。** 这是"只记一份"的另一个好处。

## 4. 那些名词，一句话一个

| 名词 | 一句话 | 为什么需要它 |
|---|---|---|
| **Cordis** | 让"挂插件"这件事成立的框架 | 提供"注册/撤销"的机制 |
| **ctx** | 插件之间互相找人的通讯录 | `ctx.llm` 就是"谁能聊天" |
| **事件** | 广播：谁想听谁听，发的人不需要知道谁在听 | 加功能不用改发的人 |
| **插件树** | 谁依附于谁的层级 | 卸载一个，下面的一起卸 |
| **profile** | 一套插件清单 | `web` / `headless` / `sdk` 就是三份清单 |
| **seam** | 一个"岗位说明书"：接口 + 实现 + 使用方 | 换实现不影响使用方 |
| **patch** | 按 id 改某个插件配置 | 不改源码就能定制 |

七个名词里，只有 **ctx** 和 **事件** 是真正需要理解的，其余五个都是它们的衍生物。下面这张表说明每个名词分别由谁衍生出来。

- 有 ctx，才有"换零件不改循环"
- 有事件，才有"加功能不改主干"
- seam 是 ctx 的用法规范（接口要单独立出来）
- profile / patch 是启动时怎么组装这棵树的配置格式
- Cordis 是上面这些机制的总称

## 5. 这样设计换来了四件"换掉不改主干"

| 换什么 | 改哪 | 主干代码 |
|---|---|---|
| 换模型 | 启动配置里换一个适配器插件 | 不动 |
| 加工具 | 写一个工具插件注册到 `ctx.tools` | 不动 |
| 换沙箱 | 换文件系统/进程的 provider | 不动，Bash/PTY/LSP 一起搬走 |
| 加行为（比如"危险操作先确认"）| 监听 `tools/pre-execute` 事件 | 不动 |

第四行最能说明价值。"危险操作先确认"这个需求，在写死的循环里要加 if；在 dsh 里是挂一个监听器——**需求变了加监听器，不是改循环**。

上面四行都是"换东西"。还有一种更常见的需求是"加东西"，下一节用加一个工具走一遍。

### 5.1 加一个工具，具体改哪

"加工具"这句话太抽象。具体到文件层面是这样：

| 步骤 | 做什么 | 代码量 |
|---|---|---|
| 1 | 写一个文件，声明名称、参数 schema、执行函数 | 约 60 行 |
| 2 | 在插件里注册到 `ctx.tools` | 1 行 |
| 3 | 在启动配置里加上这个插件 | 1 行 |
| 4 | 重启，模型看到新工具 | 0 行 |

第 1 步的 60 行里，真正有逻辑的约 20 行，其余是参数声明和错误处理。第 4 步是 0 行——提示词里列哪些工具，是**从注册表算出来的**，不是手写的清单。

这一点经常被忽略：如果工具清单是手写的，加工具就要同时改注册代码和提示词字符串，两处容易不一致——模型被告知有一个叫 `query_order` 的工具，实际注册的是 `queryOrder`，于是永远调不对。

**清单从注册表算出来，"不一致"这个 bug 类别就消失了。**

## 6. 它是 ReAct 吗

形态上是。默认的循环实现里，一个类就叫 `ReactLoopInbox`，干的正是 ReAct 那件事：请求 → 调工具 → 看结果 → 再请求。

但两点要说清：

**第一，循环是可替换的。** `agent-loop` 只是一个默认实现，插件依赖的是 `agent` 接口。换一个循环不用改其他任何东西。

**第二，ReAct 里的"Thought"不在循环里。** 论文里的 Thought 是提示词结构（让模型输出"思考：… 行动：…"）；在 dsh 里，思考发生在模型内部，循环拿到的只有结构化的工具调用。

所以准确定位是：**默认实现是 ReAct 形态，架构本身是"轮次 + 步骤"的状态机。**

## 7. 代价

不能只讲好处。这套设计有四笔账：

| 代价 | 表现 |
|---|---|
| 概念多 | 要理解 ctx、事件、scope、realm 才能改代码 |
| 调试绕 | 一个行为跨 3–5 个插件，看调用栈看不出全貌 |
| 启动慢 | 插件初始化 200–500 ms，比单体慢 3–5 倍 |
| 需要文档 | 改之前得先查"这个行为归谁"，不能靠读代码猜 |

它适合**要被外部扩展、生命周期以年计**的平台。自己团队做一个固定流程的 agent，200 行循环更好维护。

判断标准：**你的 harness 会不会被第三方扩展？**

## 8. 我们能借的四条

不做插件架构，也能借这四条：

| 原则 | 怎么用 |
|---|---|
| 只记事实，不记成品 | 存事件，不存拼好的上下文，重启能重算 |
| 接口单独立出来 | 模型、工具、沙箱都先定义接口再实现 |
| 用事件代替 if | 加需求时先想"能不能挂个钩子" |
| 配置分层可 dump | base → 应用 → 用户 patch，能打印出最终配置 |

第一条最实用：把 `messages` 数组换成"事件 + 启动时重放"，进程崩溃后能从最后一条 `seq` 接着算，不用回滚到请求起点。

## 9. 失败模式

| 现象 | 根因 | 怎么发现 | 怎么修 |
|---|---|---|---|
| 循环里 if 越来越多 | 把变化写进了不变的地方 | 数循环里的分支数 | 抽接口，改由配置决定 |
| 重启后行为不一致 | 内存里存了第二份状态 | 重启前后对比 | 只留日志为真源 |
| 换模型要改五处 | 没定义接口 | 搜模型名出现次数 | 抽适配器 |
| 插件卸了还留副作用 | 注册没返回撤销函数 | 卸载后看指标 | 注册即返回 disposer |
| 配置改了不生效 | patch 层优先级搞错 | dump 配置对比 | 按层排查 |

## 10. 验收

1. 能用代码说清"加一个模型"在写死循环和插件架构下各要改什么。
2. 能说出"只记事实不记成品"带来的三个好处。
3. 能判断你的系统该不该做插件化。

## 11. 复盘卡

```
我原来以为…实际…差在：
```

我原来以为 harness 就是一个循环加几个工具，实际差在"循环里该写什么"——写死的部分越少，这个系统活得越久。

复盘卡里那句"写死的部分越少，这个系统活得越久"，落到工程上就是四件可执行的事：日志只追加、接口先定、需求先想钩子、配置能 dump。
