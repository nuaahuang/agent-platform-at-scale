# 第 08 章 · 一次请求的完整旅程

> 迁移自 v1 `ch01-request-journey.md`。文中引用"第 N 章"为 **v1 旧编号**，与 v3 的对应关系见 [../../MIGRATION.md](../../MIGRATION.md)。


> **一句话结论**：架构不是一张框图，是**一条请求的时间线**。
> 你能把这条线上一共几跳、每跳多少毫秒、钱花在哪一跳说清楚，架构就入门了。

---

## 1. 问题：为什么先看"一条请求"

大多数架构图死在两个地方：

- 画了 30 个方框，但说不清一条请求按什么顺序穿过它们；
- 能说出"用了 K8s、Kafka、Redis"，但说不出哪一跳最慢、哪一跳最贵。

所以第一章不画大图，只跟一条请求走一遍。

**场景**（虚构示例）：用户说"我上周买的耳机想退货，但已经拆封了，能退吗"。这是一次典型的多轮售后咨询。

---

## 2. 机制：12 跳

| # | 跳 | 做什么 | 典型耗时 | p95 |
|---|---|---|---|---|
| 1 | CDN / GSLB | 就近接入、TLS 握手 | 10ms | 30ms |
| 2 | 接入网关 | 路由、限流、鉴权 | 3ms | 10ms |
| 3 | 配额 / 风控 | 查额度、黑名单 | 2ms | 8ms |
| 4 | Agent Runtime | 选 Agent、加载会话状态 | 15ms | 40ms |
| 5 | 上下文组装 | L0–L7 拼 prompt，查缓存 | 20ms | 60ms |
| 6 | 模型网关 | 选模型、限流、路由 | 2ms | 8ms |
| 7 | **排队** | 等 GPU 槽位 | 10ms | 300ms |
| 8 | Prefill | 读 5,000 token 前缀 | 300ms | 600ms |
| 9 | Decode | 生成 350 token × 25ms | 8,750ms | — |
| 10 | 工具调用（平均 2 次） | 检索 / 计算 / 写库 | 300ms | 1,200ms |
| 11 | 输出护栏 | 红线、免责声明 | 20ms | 50ms |
| 12 | 首包回传 | SSE 推给客户端 | 5ms | 20ms |

**读这张表的三个要点**：

1. 第 9 跳占了 90% 的时间。所以"优化端到端"≈"优化 decode"，而 decode 由显存带宽决定（第 02 章）。
2. **第 7 跳是唯一会"失控"的**：负载一高，它从 10ms 跳到 300ms 甚至 2s，把 p95 拉爆。
3. 第 10 跳是唯一"不归你管"的：下游工具的延迟你只能熔断、降级、换供应商。

### 2.1 两个不同的"延迟"

| 指标 | 全称 | 定义 | 目标 | 用户体验 |
|---|---|---|---|---|
| TTFT | Time To First Token | 请求发出到第 1 个 token（排队+prefill） | < 800ms | "它开始回答了" |
| TPOT | Time Per Output Token | decode 每多生成一个 token 的间隔（一个 step） | ≤ 50ms | "字在流畅地冒" |
| **端到端** | — | TTFT + TPOT×输出长度 + 工具 | 3–9s | "它答完了" |

```
发出请求 ──TTFT──▶ 字₁ ─TPOT─▶ 字₂ ─TPOT─▶ … ─▶ 字₃₅₀
端到端 = TTFT + 349 × TPOT（+工具时间）
```
TPOT = 一个 step 的时长 ≈ (30GB + B×0.96GB) ÷ 3.35TB/s；B 越大它越长。

> 这个加和**只对"同一个请求"成立**（一次真实的端到端就是这几段相加）。
> 跨请求谈 p95 时不能这么加——p95 不可加，见第 1 章 §2.3。
TTFT 归 prefill 池管（看排队数），TPOT 归 decode 池管（看 TPOT p95 与 KV 水位）。

**新手最常犯的错**：把 TTFT 当成总延迟，然后奇怪"为什么用户还是嫌慢"。

## 3. 数量级：并发到底是多少

这是架构评审最爱问的问题，也是最容易答错的地方。三个口径，三个数：

| 口径 | 定义 | 高峰 | 极端 |
|---|---|---|---|
| **在线会话** | 打开着页面的 SSE 连接 | **62 万** | 94 万 |
| **在飞请求** | 正在生成中的请求 | 2.5 万 – 6 万 | — |
| QPS | 每秒新发起的请求 | 7,000 | — |

### 3.0 先搞清楚量纲：为什么"次数 × 时间 ÷ 时间"得到"个"

把单位写出来，一目了然：

```
DAU             [人]
× 人均会话数     [次/人]      →  [次/天]        日会话数
× 单次时长       [秒/次]      →  [秒/天]        一天总共"占用"了多少会话·秒
÷ 86400         [秒/天]      →  [个]            平均同时有多少个会话在挂着
```

最后一步的量纲是 秒/天 ÷ 秒/天 = 无量纲，物理含义就是"**平均占用数量**"。

直觉一：总占用 ÷ 总时间

```
3000 万次 × 600 秒 = 180 亿"会话·秒"
180 亿 ÷ 86400 秒 = 20.8 万个会话同时在挂
```

就像"10 个人各住 1 小时，酒店一天 24 小时，平均住了几个人？"
→ 10 人·小时 ÷ 24 小时 = 0.42 人。人·小时除以小时，剩下的是"人"。

直觉二：Little's Law

```
L = λ × W
λ = 日会话数 / 86400 = 347 次/秒     （到达率）
W = 600 秒                            （每次停留）
L = 347 × 600 = 20.8 万               （同时在场数）
```

单位：`次/秒 × 秒 = 次`。这里的"次"不是"第几次"，而是"**此刻正在进行的次数**"。

为什么是"连接数"而不是"请求数"：

| | 生命周期 | 峰值数量 |
|---|---|---|
| 连接 | 整个会话（10 分钟） | 62 万 |
| 请求 | 一次生成（3.5–9 秒） | 2.5–6 万 |

差的那 10 倍，就是用户看结果、思考、打字的时间——连接挂着，但没在生成。

**三条边界条件**（评审时会问）：

1. **窗口要一致**：用"日"算出来的是**日均**并发；要峰值，就用峰值那一小时的 λ 重算。
2. Little's Law 只管平均：它不预测峰值。峰值要靠到达分布或线上曲线。
3. **稳态假设**：忽略跨零点的会话，日初日末的边界效应在千万级下可忽略。

**自己验证**：`cd lab && python3 littles_law.py`
它会造 100 万个按早晚高峰到达的会话，逐分钟统计并发，你会看到
实测平均 6,933 vs 公式预测 6,944（误差 0.16%），而**峰均比 3.18**——
平均是算出来的，峰值是估出来的。

### 3.1 62 万是怎么算出来的

它不是拍的，是会话级的 Little's Law：

```
日会话数      = DAU × 人均会话数 = 2000 万 × 1.5 = 3000 万
会话总时长    = 3000 万 × 10 分钟 = 3 亿分钟 = 180 亿秒
平均同时在线  = 180 亿秒 / 86400 秒 ≈ 20.8 万
高峰同时在线  = 20.8 万 × 3（早晚高峰突发）≈ 62 万
极端峰值      = 62 万 × 1.5 ≈ 94 万
```

三个假设，每个都能被质疑：

| 假设 | 取值 | 依据 | 怎么校准 |
|---|---|---|---|
| 人均会话数 | 1.5 次/天 | 客服/助手类产品的常见值 | 看埋点：日会话数 / DAU |
| 单次会话时长 | 10 分钟 | 多轮沟通 + 看结果 | 看会话时长分布的中位数 |
| 突发系数 | 3× | 早晚高峰集中 | 用线上同时在线曲线的 P95 / 均值 |

**敏感性**（假设变了，数字怎么动）：

| 变化 | 结果 |
|---|---|
| 会话时长 5 分钟 | 31 万 |
| 会话时长 20 分钟 | 125 万 |
| 突发系数 2× | 42 万 |
| 突发系数 4× | 83 万 |
| 人均 1.2 次 | 50 万 |
| 人均 2.0 次 | 83 万 |

**所以正确说法是**："在'人均 1.5 次、每次 10 分钟、峰值 3 倍'的假设下，高峰约 62 万连接。"
评审时把假设一起说出来，比只报一个数可信得多。

### 3.2 这个数字决定了什么

| 资源 | 推算 | 结论 |
|---|---|---|
| 网关实例 | 62 万 ÷ 单实例 5 万连接 | 至少 13 个，按 N+1 与单元化 → 每单元 30 副本 |
| 网关内存 | 62 万 × 20KB/连接 | ≈ 12 GB（连接缓冲区） |
| 文件描述符 | 每连接 1 个 fd | 必须调 `ulimit`，否则先于 CPU 崩 |
| 负载均衡 | 长连接不能用轮询 | 用 least_conn / 一致性哈希 |
| 重连风暴 | 网关重启时 62 万同时重连 | 必须加退避 + 抖动 |

**交叉验证**：62 万连接里约 10% 正在生成 → 6.2 万在飞请求，
与"7,000 QPS × 9 秒长回答 ≈ 6.3 万"吻合。两条独立路径算出同一个数，这个数才可信。

### 3.3 "2.5 万 – 6 万在飞请求"怎么来的：两级 Little's Law

第一级：先从日轮次推出峰值 QPS

```
日轮次 = DAU × 人均会话 × 每会话轮次
       = 2000 万 × 1.5 × 5 = 1.5 亿

峰值 QPS = 日轮次 × 高峰小时占比 / 3600 × 小时内突发系数
         = 1.5 亿 × 12% / 3600 × 1.4
         = 5,000 × 1.4 = 7,000
```

两个假设：高峰 1 小时承载全天 12% 的轮次（均匀分布应是 1/24≈4.2%，高峰约 2.9 倍）；
**高峰小时内瞬时再 ×1.4**。

第二级：QPS × 单轮生成时长

```
在飞请求 = QPS × W
  W = 3.5s（短回答 ~100–140 token + TTFT 0.8s）→ 7,000 × 3.5 = 2.45 万
  W = 9.0s（350 token × 25ms TPOT = 8.75s + TTFT）→ 7,000 × 9 = 6.3 万
```

**为什么是一个区间而不是一个数**：单轮时长取决于回答长度分布——
短卡片回答 3 秒，长流程回答 9 秒。容量按 6 万备，调度按实时 W 看。

> 注意：这里的"在飞请求"= 正在 prefill 或 decode 的请求（占 GPU 槽位）；
> SSE 连接里那些"等用户打字"的不算——所以它只有连接数的 1/10。

**三个口径收口**：

- 62 万 SSE 连接 = 会话级 Little's Law（停留 10 分钟）；
- 2.5–6 万在飞请求 = 请求级 Little's Law（生成 3.5–9 秒）；
- 7,000 QPS = 入口到达率，是后两级的输入。

所以"2.5 万并发"和"6 万并发"都对——取决于你问的是平均还是长尾。
评审时先反问一句"你说的是哪个口径"，立刻显得专业。

## 4. 钱花在哪一跳

| 成本项 | 占比 | 说明 |
|---|---|---|
| GPU | ~70% | 主要由 decode 的 token 数决定 |
| 网络 / 带宽 | ~10% | 图片上传、SSE 长连接 |
| 存储 | ~8% | 事件、媒体、向量 |
| 中间件 | ~7% | MySQL / Redis / Kafka |
| 其他 | ~5% | 可观测、CDN |

**推论**：想降本，先动 token（分级路由、缩短输出、提高缓存命中），而不是先动中间件。
中间件全砍了也只省 7%。

## 5. 设计含义：链路图怎么变成架构决策

链路图不是画着好看，它决定了三件事。

**（1）延迟预算怎么切**

| 段 | 预算 | 谁负责 | 超了怎么办 |
|---|---|---|---|
| 接入（DNS/TLS/网关） | 50 ms | 网关 | 长连接、连接复用 |
| 鉴权 + 配额 | 20 ms | 网关 | token 本地缓存 |
| 排队 | ≤200 ms | 调度器 | 拒绝，或降级到小模型 |
| Prefill | ≤450 ms | 引擎 | 前缀缓存、chunked |
| 首 token 传输 | ≤80 ms | 网络 | 就近接入、cell 下沉 |
| **TTFT 合计** | 800 ms | — | — |
| Decode 350 token × 25 ms | 8.75 s | 引擎 | TPOT、投机解码 |

（2）哪一跳能买，哪一跳只能优化

第 10 跳（工具）不归你管 → 只能熔断、降级、换供应商；
第 5–6 跳（decode）归你管 → 只能靠 TPOT 和 batch。
归你管的做优化，不归你管的做隔离——把这两类混在一起讨论，永远得不出结论。

**（3）容量按什么定**

按 QPS 定算力（prefill），按在飞请求定显存（KV），按并发定连接数。
三个口径对应三种资源，混着算就会像 §3 那样差出 10 倍。

## 5.5 失败模式：旅程断在哪一段

| 现象 | 根因 | 怎么发现 | 怎么修 |
|---|---|---|---|
| TTFT 比各段之和多出几百 ms | 漏了引擎的等待队列 | trace 里网关与引擎之间有一段空白 | 在 `add_request` 处打点（第 10B 章 §3.1） |
| 同一会话两次走了不同实例 | 路由亲和没生效 | 比对两次的 `instance_id` | 检查会话哈希的 key 是否含 tenant |
| 端到端 9 s，各段加起来只有 5 s | 客户端渲染与网络没计入 | 客户端埋点与服务端时钟对齐 | 加客户端首帧打点 |
| 首 token 很快、整体很慢 | 输出被网关缓冲或下游限流 | 看 TPOT 分布是否被拉长 | 查网关 flush 策略 |
| 偶发 3–5 s 尖峰 | 连接池耗尽或 TCP 重传 | 连接数曲线 + 抓包 | 调 keepalive、扩连接池 |

第二条最难查：它不报错，只是让前缀缓存命中率悄悄掉 20 个点，然后 TTFT 整体上移。


## 6. 验收：五个数字必须能被复算

| 数字 | 复算方式 | 误差容忍 |
|---|---|---|
| 峰值 QPS | `labs/calc.py` | ±10% |
| 在飞请求 | `labs/littles_law.py`：W = L / λ | ±15% |
| TTFT p95 | 压测 | 与各跳之和差 <15% |
| TPOT p95 | 压测 | ±5 ms |
| 端到端 p50 | TTFT + 349×TPOT + 工具 | ±10% |

**判据**：链路图每一跳耗时加起来，应落在端到端 p50 的 ±15% 内。
差得远时，不是图错了，就是有一跳没测到——通常是**排队**。

## 7. 三个误区

误区 1：TTFT 达标 = 体验达标。
错。TTFT 800ms 但 decode 慢，用户看到字一个个蹦，照样骂。

误区 2：QPS 就是并发。
错。7,000 QPS 可能对应 2.5 万在飞请求，也可能对应 6 万。容量按在飞请求算，不按 QPS 算。

误区 3：SSE 连接数 = 请求数。
错。62 万连接里大部分在"看历史"，不占 GPU。
