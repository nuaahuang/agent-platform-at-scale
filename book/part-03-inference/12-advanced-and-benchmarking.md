## 1. 问题：压测过的配置，上线三小时就崩

三种最常见的翻车：

| 现场 | 压测时看到的 | 上线后 |
|---|---|---|
| A | 并发 1，TTFT 120 ms | 7000 QPS 时 TTFT 4.2 s，超时雪崩 |
| B | 固定 512 token 输入，吞吐 3200 tok/s/GPU | 真实输入 p95 4800 token，吞吐掉到 1100 |
| C | 闭环 200 并发，QPS 稳定 6500 | 开环到达率 7000 时排队爆炸，p99 到 30 s |

根因只有一个：**压测测的是"系统最快能跑多快"，而生产要的是"在 SLO 下最多能接多少"。**

这两个数字能差 2–3 倍。本章讲的就是怎么测后面那个。

## 2. 特性矩阵：先分清"白拿"和"要付代价"

| 特性 | 收益 | 代价 | 什么时候开 | 什么时候必须关 |
|---|---|---|---|---|
| **前缀缓存** | 命中 85% → 卡数 2512→1808（−28%） | 常驻显存 + 租户隔离风险 | 系统提示/工具 Schema 稳定 | 多租户且提示含敏感数据 |
| **Chunked prefill** | TPOT 尖刺消失 | TTFT 略增（多几个 step） | 长短请求混跑 | 纯短请求（无收益） |
| **投机解码** | 低并发下单用户 +60%–85% | 高并发下挤占 batch | 交互型产品、并发 <128 | 批处理型、GPU 已饱和 |
| **结构化输出** | 解析失败率 3.2%→0.1% | 每步多一次 mask 计算 | 工具调用、JSON 输出 | 自由文本创作 |
| **多 LoRA** | 一个基座服务 N 个租户 | batch 内多 adapter 掉吞吐 | 租户多、单租户量小 | 单租户占满集群 |
| **KV 量化 FP8** | 显存减半，并发 ×1.8 | 长上下文精度 −1.3 pt | 显存瓶颈 | 长文档精确检索 |
| **长上下文扩展** | 32K → 128K | 卡数 ×4（2k→16k 是 1664→5632） | 真有长文档需求 | 只是"怕不够" |

> 这张表的用法：**每一项都要能在评审会上回答"开了它，SLO 和成本各变多少"**。
> 答不上来的，就是没测过。

## 3. 投机解码：什么时候是赚的

### 3.1 三个符号，先定义清楚

投机解码的做法是：小模型先"猜"几个 token，大模型**一次前向**把它们全验一遍。

| 符号 | 含义 | 怎么得到 | 典型值 |
|---|---|---|---|
| **k** | 每步草稿模型猜几个 token | 你配的参数（如 `USE_NEXTN_DECODE=5`） | 2–8 |
| **α** | **单个**草稿 token 被接受的概率 | 实测：接受数 ÷ 草稿总数 | 0.4–0.9 |
| **c** | 每多验一个草稿，耗时涨多少（**无量纲**，相对一次普通 step） | 实测：step 耗时增量 ÷ 基准 step 耗时 | 0.05–1.0 |

> **c 的单位是"没有单位"**——它是两个时间的比：
>
> ```
> c = 每多一个草稿 token 增加的耗时（ms/token） ÷ 基准 step 耗时（ms）
>   = 1.25 ms/token ÷ 25 ms = 0.05 /token
> ```
>
> 所以 `1 + k·c` 算出来的是**耗时倍数**（1.2 倍），**不是钱**。
> 要换成钱，还得乘一步的成本——那是第 14、17 章的事。

**α 是最关键的未知数**，它取决于草稿模型和主模型有多像。
同一个草稿模型，在"续写代码"上 α 可能 0.85，在"复杂推理"上只有 0.35。

### 3.2 一条时间轴看懂在干什么

```
不带投机：每个 step 出 1 个 token
  step1   step2   step3   step4   step5
   [T]     [T]     [T]     [T]     [T]      → 5 个 token，花 5 个 step

带投机（k=4）：每个 step 赌一把
  step1:  草稿 d1 d2 d3 d4
          目标模型一次验证 5 个位置（d1..d4 + 1 个修正位）
          结果：d1 ✓  d2 ✓  d3 ✗  → 输出 3 个 token（接受 2 个 + 修正 1 个）
  step2:  从新位置再来一轮 …
```

所以问题变成两句话：

1. **一个 step 平均能出几个 token？** → 记为 E
2. **一个 step 变贵了多少？** → 记为 1 + k·c

加速比就是这两个数的比。

### 3.3 E 怎么来的：把"平均"拆成"每个位置的概率"

第 i 个草稿要被接受，必须**前面 i 个全对**（第 3 个被接受，意味着第 1、2 个也对）。
假设每个位置独立、接受率都是 α：

| 位置 | 被接受的条件 | 概率 | 对期望的贡献 |
|---|---|---|---|
| 第 1 个草稿 | d1 对 | α | α |
| 第 2 个草稿 | d1、d2 都对 | α² | α² |
| 第 3 个草稿 | 前 3 个都对 | α³ | α³ |
| 第 4 个草稿 | 前 4 个都对 | α⁴ | α⁴ |
| **修正位** | 目标模型**必出** 1 个 | 1 | 1 |
| | | | **E = 1 + α + α² + α³ + α⁴** |

这就是那个等比数列的来历——**它不是凑出来的，是"第 i 个位置要求前 i 个都对"的直接结果**。

α = 0.8 时：

```
E = 1 + 0.8 + 0.64 + 0.512 + 0.4096 = 3.36
```

意思是：**每一步平均产出 3.36 个 token**，而不是 1 个。

### 3.4 c 为什么是 0.05 而不是 1

直觉上"验 5 个位置应该贵 5 倍"，但 decode 阶段不是这样算的：

```
一步的耗时 ≈ 读一遍权重（固定） + 读 KV（随 batch） + 算（随 token 数）
```

- **低并发**：权重读取占 90% 以上，多算 4 个位置几乎不增加时间 → c ≈ 0.05
  （一步 25 ms，多一个草稿只多 1.25 ms）；
- **高并发**：batch 已经塞满，多 4 个位置就是实打实的算力 → c 会一路涨到接近 1。

**c 不是常数，它是"GPU 有多忙"的度量。** 这一点决定了下一节。

### 3.5 合起来：S = E / (1 + k·c)

α = 0.8、k = 4、c = 0.05：

```
E = 3.36（一步出 3.36 个 token）
成本 = 1 + 4×0.05 = 1.2（一步贵 20%）
S = 3.36 / 1.2 = 2.80×
```

对照一下：如果不做投机，一步出 1 个 token、成本 1，S = 1。
**收益全部来自"一个 step 出多个 token"摊薄了权重读取。**

### 3.6 α 和 k 怎么配：不是越大越好

固定 c = 0.05，扫一遍 α × k：

| α ＼ k | 2 | 4 | 6 |
|---|---|---|---|
| 0.4 | 1.42× | 1.37× | **1.28×** |
| 0.6 | 1.78× | **1.92×** | 1.87× |
| 0.8 | 2.22× | 2.80× | **3.04×** |
| 0.9 | 2.46× | 3.41× | **4.01×** |

看 α = 0.4 那一行：**k 从 2 加到 6，收益反而下降**。
因为第 5、6 个草稿的接受概率只有 α⁵ ≈ 1%、α⁶ ≈ 0.4%，
但每一个都要付 c = 5% 的成本——**赚的比花的多**。

判据：**只要 α^k > c 就继续加，否则停。**

| α | α^k > 0.05 的边界 | 理论最优 k |
|---|---|---|
| 0.4 | k < 3.3 | 3 |
| 0.6 | k < 5.9 | 5 |
| 0.8 | k < 13.4 | 13 |
| 0.9 | k < 28 | 28（实际被 batch 上限压到 5–8） |

这就是 DeepInfer 默认 `k = 5` 的原因：α 在 0.6–0.7 时，5 刚好在拐点附近。

### 3.7 并发一上来，c 变了，结论就翻了

| 并发 | c | S = 3.36 / (1 + 4c) | 状态 |
|---|---|---|---|
| 1 | 0.05 | **2.80×** | GPU 空闲，验证白赚 |
| 16 | 0.07 | 2.63× | 仍有空余 |
| 128 | 0.35 | 1.40× | batch 接近饱和 |
| 512 | 0.55 | 1.05× | 只剩零头 |
| 1024 | 0.64 | **0.94×** | 挤占他人，净亏 |

**公式没变，变的是 c。** 这就是"投机解码不是提吞吐的工具"的全部数学来源。

> **以为**投机解码能提吞吐，**其实**它只在 GPU 没跑满时有效——
> 它买的是"单用户体验"，卖的是"batch 槽位"。
> DeepSeek 的 DSpark 数据正是这个形状：单用户 +60%–85%，整体吞吐只 +4%–7%（第 10 章 §9）。

### 3.8 决策

| 场景 | 开不开 | 理由 |
|---|---|---|
| C 端对话，并发 20–100 | **开** | c 小，收益最大 |
| Agent 长任务，并发 500+ | 谨慎 | 先测总吞吐，可能为负 |
| 离线批处理 | **不开** | 直接拉满 batch 更划算 |
| 已撞 SLO 上限 | 不开 | 会把 p95 推高 |

## 4. 压测方法论：五个必须钉死的变量

| 变量 | 为什么重要 | 怎么固定 |
|---|---|---|
| **输入长度分布** | 固定长度会高估吞吐 2–3 倍 | 用生产采样，或对数正态（p50 800 / p95 4800） |
| **输出长度分布** | 决定 decode 步数 | 记录真实 EOS 分布，别用 max_tokens |
| **并发模型** | 闭环会掩盖排队 | 开环 Poisson 到达 |
| **缓存状态** | 冷启动和热缓存差 30% | 冷/热各测一轮，分开报 |
| **是否含网关** | 引擎内 TTFT ≠ 用户 TTFT | 端到端压测，至少含网关与网络 |

### 4.1 闭环 vs 开环：最容易被忽略的一条

```
闭环（closed-loop）：固定 N 个客户端，一个请求完成才发下一个
   → 系统变慢时，客户端也自动变慢，排队被"吸收"了

开环（open-loop）：按固定速率 λ 发请求，不等响应
   → 系统变慢时请求继续堆积，排队与超时立刻暴露
```

这就是 **coordinated omission**：闭环压测里，系统越慢，压测工具发的越少，
于是你永远测不到真实的 p99。**生产是开环的**，所以压测也必须是开环。

### 4.2 一个 30 行的开环压测脚本

```python
import asyncio, aiohttp, random, time, statistics

async def one(session, url, in_len, out_len, rec):
    t0 = time.perf_counter()
    first = None
    async with session.post(url, json={"max_tokens": out_len,
                                       "stream": True}) as r:
        async for line in r.content:
            if line.startswith(b"data:") and first is None:
                first = time.perf_counter()
    t1 = time.perf_counter()
    rec.append(((first - t0) * 1000, (t1 - first) * 1000 / max(out_len, 1)))

async def main(rate, duration, url):
    rec = []
    conn = aiohttp.TCPConnector(limit=0)          # 不设上限，避免客户端成瓶颈
    async with aiohttp.ClientSession(connector=conn) as s:
        tasks, t0 = [], time.perf_counter()
        while time.perf_counter() - t0 < duration:
            await asyncio.sleep(random.expovariate(rate))   # Poisson 到达
            tasks.append(asyncio.create_task(one(s, url, 800, 300, rec)))
        await asyncio.gather(*tasks)
    ttft = sorted(x[0] for x in rec)
    print(f"n={len(rec)} TTFT p50={ttft[len(ttft)//2]:.0f}ms "
          f"p95={ttft[int(len(ttft)*0.95)]:.0f}ms")
```

三个坑：`limit=0` 不设连接上限、客户端要多核、时钟要 NTP 同步。

### 4.3 长度分布为什么值 3 倍

同一套硬件，只换输入分布：

| 负载 | 平均输入 | 平均输出 | 单卡吞吐 |
|---|---|---|---|
| 固定 512 / 256 | 512 | 256 | 3,200 tok/s |
| 均匀 100–2,000 | 1,050 | 256 | 1,900 tok/s |
| 生产分布（p50 800 / p95 4,800） | 1,250 | 300 | **1,100 tok/s** |

原因有两个：attention 的计算随长度平方增长；长请求的 KV 常驻，挤掉并发。
**用固定长度压测，等于给系统开了一张 3 倍的假支票。**

## 5. 三个必测场景

| 场景 | 怎么打 | 通过标准 |
|---|---|---|
| **稳态容量** | 阶梯加压 500→8000 QPS，每档 5 分钟 | 找到 TTFT p95 = 800 ms 的拐点 |
| **尖峰** | 0→3× 峰值，持续 30 s | 不雪崩；恢复时间 <60 s |
| **长稳** | 24 小时，70% 负载 | KV 碎片不涨、内存无泄漏、p95 不漂移 |

尖峰测试的关键不是"扛住"，是**"扛不住时怎么退化"**：是拒绝新请求（好），
还是所有请求一起变慢（坏）。这就是第 24 章背压要解决的问题。

长上下文还要单测一层：在 32K 上下文里埋 10 个事实（needle-in-a-haystack），看召回率。
吞吐达标但召回掉 3 个点，等于这个配置不能用——**性能达标不等于能力达标**。

## 6. 一份压测报告必须有的字段

| 字段 | 示例 | 为什么必须有 |
|---|---|---|
| **配置指纹** | 模型 v4.1-flash-1017、引擎 v0.9.2、TP8、max_num_seqs 256、block 16、KV FP8 | 没有它，结果无法复现 |
| **负载画像** | 输入 p50 800 / p95 4800，输出 p50 220 / p95 900，Poisson | 换分布结果全变 |
| **结果** | QPS 7600、TTFT p95 610 ms、TPOT p95 38 ms、错误率 0.03% | 只看均值等于没测 |

| **资源** | GPU 利用率 71%、KV 占用 78%、显存峰值 76 GB | 判断瓶颈在哪 |

## 7. 五个常见误判

| 现象 | 根因 | 正确做法 |
|---|---|---|
| 压到 5000 QPS 很稳，上线 3000 就崩 | 闭环压测掩盖排队 | 改开环 Poisson |
| 引擎 TTFT 200 ms，用户看到 1500 ms | 没算网关、排队、网络 | 端到端压测 |
| 吞吐很高，但用户投诉卡 | 只看吞吐不看 p99 | SLO 优先，看 p95/p99 |
| 首轮快，跑两小时变慢 | KV 碎片、缓存膨胀、连接泄漏 | 24h 长稳 |
| 换模型后结果不可比 | 输出长度变了 | 按 token 数对齐，不按请求数 |

第二条最普遍：**引擎内指标和用户体感之间，隔着 3–4 跳**（第 8 章的 12 跳链路里，
网关 + 排队 + 网络约占 300–800 ms）。只压引擎，等于只测了一半。

## 8. 一组可对齐的数字

以本书教学案例（2512 卡、7000 QPS 峰值）为例，一次合格压测应产出：

| 指标 | 目标 | 实测 | 余量 |
|---|---|---|---|
| QPS | 7000 | 7600 | +8.6% |
| TTFT p95 | ≤800 ms | 610 ms | 24% |
| TPOT p95 | ≤50 ms | 38 ms | 24% |
| 端到端 p95 | ≤9 s | 7.9 s | 12% |
| 错误率 | <0.1% | 0.03% | — |
| KV 占用 | <90% | 78% | 12 pt |

**余量最小的那一项，就是下一次扩容的触发点**——这里是端到端（12%），
不是 QPS。看错指标会导致"提前扩卡但体验没改善"。

## 9. 没有同规模环境怎么压

2512 卡的集群，测试环境不可能也是 2512 卡。这是所有大规模系统的共同处境。

### 9.1 换问题：不复制规模，测单位产出

把"集群能扛多少 QPS"拆成两个独立的问题：

```
集群容量 = 单卡在 SLO 下的产出（可测） × 卡数（已知） × 规模折扣（可估）
```

第一个问题 8 张卡就能回答，第二个是采购数字，第三个是经验系数。
**整条链里，只有"规模折扣"需要大规模才能测准**——而它可以靠分段验证逼近。

### 9.2 四层测试：每层只需要很少的卡

| 层 | 规模 | 测什么 | 能发现 | 发现不了 |
|---|---|---|---|---|
| **L1 单机** | 1–8 卡 | 单卡吞吐-延迟曲线、SLO 拐点 | 引擎调优、batch 上限 | 任何跨机问题 |
| **L2 小集群** | 32–64 卡 | PD 比例、路由、前缀缓存命中 | 组间干扰、负载不均 | 网络拥塞 |
| **L3 影子** | 512 卡 + 5% 真实流量 | 端到端 SLO、真实分布 | 网关、排队、长尾 | 全量故障叠加 |
| **L4 生产** | 2512 卡 | **只做混沌与故障演练，不做压测** | 重调度风暴、级联失败 | — |

关键认知：**L4 不是用来压的，是用来"打坏"的**。压测找边界，混沌找塌陷。

### 9.3 外推三步，加三个折扣

| 步骤 | 做法 | 我们的数 |
|---|---|---|
| ① 测单卡 | L1 上找 TTFT p95 = 800 ms 的拐点 | 2.8 QPS/卡（7000 ÷ 2512） |
| ② 乘卡数 | 线性放大 | 7000 QPS |
| ③ 打折扣 | 见下表 | 见下 |

| 折扣 | 典型值 | 来源 |
|---|---|---|
| 网络与调度损耗 | 8%–15% | L2 上对比"单机组"与"跨机组" |
| 故障预留 | 10% | 一台挂掉后的重调度窗口 |
| 碎片与预热 | 5% | 冷启动、KV 未命中 |
| **合计** | **约 1.25×** | 与第 1 章的 ×1.3 余量对应 |

**注意**：单卡测的是"混合口径"（prefill + decode 一起），不能拿去和 decode 单卡的
3,500 tok/s 比较——两者不是同一个指标。

### 9.4 没有真实流量，用三种替代

| 方式 | 成本 | 真实度 | 适用层 |
|---|---|---|---|
| **合成负载**（Poisson + 生产长度分布） | 极低 | 中 | L1、L2 |
| **录制回放**（生产请求脱敏后重放） | 中 | 高 | L2、L3 |
| **分流灰度**（5% 真实用户） | 低（但要有用户） | 最高 | L3 |

回放有个坑：**工具调用要 mock**，否则测试集群会真的去查订单、发短信。

### 9.5 只有真实规模才暴露的五件事

诚实地说，下面这些在小集群上永远测不出来，只能靠**分批上线**逼近：

| 问题 | 什么时候炸 | 怎么防 |
|---|---|---|
| spine 层网络拥塞 | 跨 POD 的 all-to-all 占比升高时 | 分批扩，每批不超过一个 spine |
| 调度器与元数据压力 | 节点数 > 500 后线性变差 | 压测 etcd/调度器本身 |
| 模型加载带宽 | 一次发布拉起 2512 个副本 | 限制并发拉取，用 P2P 分发 |
| 故障叠加 | 一台挂 → 重调度 → 雪崩 | 混沌演练，故意杀节点 |
| 冷缓存击穿 | 全量重启后前缀缓存全空 | 灰度重启，控制冷启动比例 |

**分批上线的节奏**：64 → 256 → 512 → 1024 → 全量，每批至少观察 24 小时。

### 9.6 仿真器：唯一能"免费"跑 2512 卡的办法

把 L1 测到的**服务时间分布**（不是均值）作为输入，用离散事件仿真跑 2512 卡的排队。

| 能回答 | 不能回答 |
|---|---|
| P:D 比例取多少最省 | 网络拥塞 |
| 路由策略 A/B 谁更好 | 硬件故障 |
| 峰值时排队多长 | 缓存命中率 |

工具不复杂：SimPy 或自己写 200 行事件循环。**仿真不能替代压测，但能把"试错成本"从 2512 卡降到 0 卡。**

### 9.7 仿真器的三个要素与一条可信判据

它跑得快的真正原因不是"算得省"，是**时间可以快进**：不执行模型，只按事件推进时钟。

| 要素 | 建模什么 | 数据从哪来 |
|---|---|---|
| 到达过程 | 请求何时来 | 生产日志（Poisson 或实测轨迹） |
| 服务时间 | prefill / 一个 decode step 多久 | L1 实测的**分布**，不是均值 |
| 调度规则 | batching、抢占、KV 上限 | 引擎源码里的真实逻辑 |

开源参考：[Vidur](https://github.com/microsoft/vidur)（MIT，微软）——LLM 推理仿真器，
支持连续批处理与多种并行策略，可作为自研的对照基线。

**可信判据**：拿 L2 小集群的一次真实实验做回放，仿真出的 p95 误差 **< 15%** 才敢用于决策。
达不到，就只是漂亮的数字。

## 10. 过载怎么测：测的不是"扛住"，是"退化曲线"

设计容量 7000 QPS，那 10,500 QPS 打进来会发生什么？这才是生产最关心的问题。

**过载测试的产出不是"最大 QPS"，是三条曲线：**

```
有效吞吐 goodput  ──┐
                     ├── 随到达率变化的形状
成功率            ──┤
TTFT p95          ──┘
```

### 10.1 好形状 vs 坏形状

| 形状 | 表现 | 含义 |
|---|---|---|
| **好**（优雅退化） | 到达率超容量后，goodput 走平，成功率缓降，p95 温和上升 | 系统在"推掉多余"，保护了在处理的 |
| **坏**（拥塞崩溃） | p95 直线上升 → 全超时 → goodput 归零 | 谁也没服务好，还占着资源 |

拥塞崩溃的典型链条：

```
过载 1.2× → 排队变长 → 请求超时 → 客户端重试 → 实际负载 2.4× → 彻底崩
```

**重试放大是最常见的放大器**：1.2 倍的过载，能被重试放大成 2.4 倍。

### 10.2 五级降级阶梯（先设计，再测）

测之前必须先有"降级去哪"的答案，否则测出来也不知道该看什么：

| 级 | 动作 | 省下什么 | 用户感知 |
|---|---|---|---|
| L0 | 全功能 | — | 正常 |
| L1 | 关投机解码 | 算力（batch 槽位） | 单用户变慢，吞吐升 |
| L2 | max_tokens 4096 → 1024 | decode 时长 | 长回答被截断 |
| L3 | 关工具调用 / 检索 | 一跳 + token | 能力降级 |
| L4 | 切 8B lite 模型 | 算力 ×3 | 质量下降 |
| L5 | 429 + Retry-After | 全部 | 排队/重试 |

**顺序不能反**：先牺牲"锦上添花"（投机、长度），最后才牺牲可用性（拒绝）。
这也呼应第 1 章的优先级：**可用性 > 体验 > 成本**。

### 10.3 怎么打：四个必测档位

| 档位 | 到达率 | 持续 | 看什么 |
|---|---|---|---|
| 稳态 | 1.0× | 10 min | 基线，SLO 应全绿 |
| 轻度过载 | 1.2× | 10 min | 是否开始排队、丢弃率 |
| 中度过载 | 1.5× | 10 min | 降级是否触发、goodput 是否走平 |
| 重度/尖峰 | 0→3× in 10 s | 5 min | 是否拥塞崩溃、恢复时间 |

**必须持续到稳态**（至少 3 倍的平均排队时间），否则测的是瞬态，不是过载行为。

### 10.4 验收清单：合格 vs 不合格

| 检查项 | 合格 | 不合格 |
|---|---|---|
| 拒绝发生的位置 | 入口快速拒绝（<50 ms） | 排队 30 s 后超时 |
| 拒绝的语义 | 429 + Retry-After + 可重试标记 | 500 或直接断连 |
| 公平性 | 按租户配额，小客户不被饿死 | 先到先得，大客户挤爆 |
| 降级是否自动 | 阈值触发、可观测 | 靠人手动切 |
| GPU 保护 | KV 水位不超 90%，不 OOM | 打满后 OOM 重启 |
| 恢复 | 撤压后 5 min 内回到 SLO | 越等越糟 |
| 级联 | 无重试风暴 | 客户端重试把负载放大 2× |

### 10.5 小集群怎么测这个

好消息：**过载行为主要由控制面决定，与集群规模弱相关。**

限流阈值、队列长度、降级触发点都是"按设计容量比例"配置的。在 64 卡的小集群上
把阈值等比缩到 1/40，压到 1.5× 设计容量，看到的退化曲线和生产是同一形状。

| 参数 | 生产（2512 卡） | 测试（64 卡） |
|---|---|---|
| 设计容量 | 7000 QPS | 175 QPS |
| 限流阈值 | 7200 QPS | 180 QPS |
| 队列上限 | 2.5 万在飞 | 625 在飞 |
| 降级触发 | 排队 > 2 s | 排队 > 2 s（不变） |

**只有"排队时间"这类时间量纲的阈值不用缩放**——这也是为什么过载测试在小集群上特别可信。

### 10.6 观测：判断"优雅"需要的六个指标

| 指标 | 看什么 |
|---|---|
| goodput（达标请求/秒） | 核心，别的都是解释它 |
| 丢弃率与丢弃位置 | 入口拒绝比队列超时好 |
| 队列深度 | 是否无界增长 |
| KV 水位 | 是否逼近 OOM |
| 降级命中计数 | 哪一级被触发 |
| 客户端重试率 | 是否在放大故障 |

## 11. 验收：怎么证明压测是可信的

| 检查项 | 通过标准 |
|---|---|
| 是否开环 | 到达过程是 Poisson，不是固定并发 |
| 客户端不是瓶颈 | 压测机 CPU <60%，无连接池上限 |
| 长度分布来自生产 | 有采样依据，不是拍脑袋 |
| 冷/热缓存分别报 | 两个数都给了 |
| 端到端覆盖 | 至少含网关与网络 |
| 配置指纹完整 | 六项齐全 |
| 长稳 ≥24h | 有 p95 漂移曲线 |

七条里缺任何一条，这份报告只能当"参考"，不能进容量模型。
