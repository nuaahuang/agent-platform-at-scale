## A.0 问题：单卡为什么不够

200B 模型 FP8 权重 = 200 GB，H800 单卡 80 GB，**装都装不下**——这是并行的第一条理由。
第二条是算力：prefill 一个 5K token 请求需要 2 × 30B × 5000 = 3.0e14 FLOP，
单卡 1.98 PFLOPS 下要 0.43 s（还没算 MFU），乘上 7000 QPS 的峰值直接不可行。

| 约束 | 单卡数字 | 后果 | 对应并行 |
|---|---|---|---|
| 显存 | 80 GB vs 200 GB 权重 | 放不下 | TP / PP / EP |
| 算力 | 1.98 PFLOPS | prefill 太慢 | TP / EP |
| 带宽 | 3.35 TB/s | decode 每步读 30 GB → 8.96 ms | **并行解决不了**，只能加卡 |

结论先行：TP 解决"放不下"和"单步太慢"，EP 解决"专家太多放不下"，PP 解决"跨机放得下但延迟高"。
并行不是越多越好——每加一级，就多一次通信，通信是这条路上最贵的税。

## A.1 稠密 vs 稀疏：一张表

| | 稠密（Dense） | 稀疏（MoE） |
|---|---|---|
| 每 token 算力 | 2 × N_total | 2 × N_active |
| 显存占用 | N_total | N_total（全部专家都要装） |
| 通信 | TP 的 all-reduce | TP + EP 的 all-to-all |
| 延迟可预测性 | 高 | 低（路由不均、专家倾斜） |
| 小 batch 表现 | 好 | 差（专家利用率低） |
| 大 batch 表现 | 线性变贵 | **摊薄后更便宜** |
| 工程复杂度 | 低 | 高（路由、均衡、通信） |
| 典型用途 | 延迟敏感、小模型 | 大模型、追求"每 FLOP 的质量" |

**一句话**：稀疏是用**显存和通信**换**算力**；稠密是用**算力**换**简单和稳定**。

**什么时候稀疏不划算**：
- batch 很小（每个专家只分到几个 token，算力省了但通信没省）；
- 网络差（all-to-all 打满，GPU 等网络）；
- 延迟敏感（路由 + 通信让 p99 抖动）。

## A.2 四种并行：DP / TP / PP / EP

| 并行 | 切什么 | 通信 | 典型范围 |
|---|---|---|---|
| DP 数据并行 | 切 batch，每卡一份完整模型 | 梯度 all-reduce（训练） | 多机 |
| TP 张量并行 | 切**一层内的矩阵**（按列/行） | 每层 all-reduce | 机内 ≤8 卡（NVLink） |
| PP 流水并行 | 切**层**（前几层在 A 卡，后几层在 B 卡） | 点对点 send/recv | 多机 |
| EP 专家并行 | 切 **MoE 专家**（e1–e8 放不同卡） | all-to-all | 多机（IB/RDMA（Remote Direct Memory Access）） |

### TP 长什么样

一个线性层 `Y = XW`，W 是 4096×4096。TP=2 时：

```
GPU0: W 的左半（4096×2048）→ 算出一半输出
GPU1: W 的右半（4096×2048）→ 算出另一半输出
两边结果相加 → all-reduce → 得到完整 Y
```

每层都要 all-reduce 一次，所以 TP 很吃互联带宽。
H800 的 NVLink 是 400GB/s，机内 TP=8 才划算；跨机 TP 基本不可用。

### EP 长什么样

8 个专家，4 张卡，每卡 2 个专家：

```
GPU0: e0 e1      GPU2: e4 e5
GPU1: e2 e3      GPU3: e6 e7
```

一个 token 在 GPU0 上，路由到 `e1`（本地）和 `e5`（GPU2）：

```
① dispatch：GPU0 把 token 的隐藏状态发给 GPU2
② 专家计算：GPU0 算 e1，GPU2 算 e5
③ combine：GPU2 把结果发回 GPU0，加权求和
```

每张卡都要和所有其他卡交换数据，这一步叫 all-to-all。

## A.3 五种集合通信（用 4 张卡举例）

设 4 张卡各自持有一个向量：

```
G0=[1,2]   G1=[3,4]   G2=[5,6]   G3=[7,8]
```

### all-reduce：所有人得到"总和"

```
结果：G0=G1=G2=G3=[16,20]
```

用途：TP 每层合并部分和；DP 同步梯度。
代价：约 `2 × (N-1)/N × 数据量`，N 越大越接近 2 倍数据量。

### all-gather：所有人拿到"全部片段"

```
G0 原本只有 A 段 → 最终 G0=[A,B,C,D]，其他卡同
```

用途：TP 的输出拼接、ZeRO 推理取权重。

### reduce-scatter：先求和，再各拿一片

```
总和 [16,20] 切成两片 → G0,G1 拿 [16]，G2,G3 拿 [20]
```

用途：ZeRO 梯度分片。all-reduce = reduce-scatter + all-gather，所以能省一半流量。

### all-to-all：每个人给每个人发"不同的东西"

```
交换前：每张卡有 4 份，分别属于 G0/G1/G2/G3
交换后：G0 收到来自 G0/G1/G2/G3 的第 0 份
```

**这是"转置"**：把 `[卡][数据块]` 变成 `[数据块][卡]`。
用途：EP 的 dispatch/combine；序列并行。

### broadcast / send-recv

- broadcast：一个人发给所有人（配置下发）；
- send/recv：点对点（PP 的层间传递）。

## A.4 为什么 EP 一定要 all-to-all：算一笔账

每层、每个 step：

```
通信量 = tokens × top_k × hidden × bytes
       = 512 × 2 × 7168 × 2 B
       ≈ 14.7 MB（单向）
```

60 层、dispatch + combine 两个方向：

```
14.7 MB × 60 × 2 ≈ 1.76 GB / step
```

如果每卡 100ms 出一个 step，光通信就要 17.6 GB/s，还没算拥塞和抖动。
所以 MoE 推理只有 RDMA 才跑得动；rail-optimized 网络是为了让一组专家落在同一台交换机下，把跨 leaf 的流量砍掉。

对比 TP 的 all-reduce：每层通信量约等于**激活值大小**（512×7168×2B≈7.3MB），
量级相近，但 TP 在机内走 NVLink（400GB/s），EP 跨机走 IB（400Gb/s=50GB/s）——
同样的数据量，跨机贵 8 倍。

## A.5 2:4 结构化稀疏：怎么剪、怎么微调

### 规则

每 **4 个连续权重**为一组，只能保留 **2 个**，另 2 个置零：

```
原始： [0.9, 0.1, 0.7, 0.2]  → 保留 [0.9, _, 0.7, _]
元数据： 2 bit 记录"留了哪两个"
```

硬件（Ampere 之后的稀疏 Tensor Core）读到元数据就跳过零，**理论算力 ×2**。

### 三步落地

1. **选保留谁**：按绝对值大小（magnitude）或 SparseGPT 之类的方法，逐组选 2 个；
2. 固定 mask 继续训练（微调）：被剪掉的权重不再更新，其余权重用较小学习率再训一段，
   把掉下去的效果拉回来——**这一步就是"并微调"**；
3. **导出稀疏格式**：cuSPARSELt / TensorRT-LLM 的 sparse 权重，推理引擎要支持。

### 为什么生产里很少用

| 问题 | 说明 |
|---|---|
| 精度损失 | LLM 权重存在离群通道（部分层 >10σ），强行 2:4 精度掉 2–5 pt，微调也只补回一半 |
| 引擎支持 | vLLM/SGLang 对 2:4 稀疏算子支持有限，主流还是 dense |
| 收益打折 | decode 是带宽受限，算力翻倍不代表速度翻倍（可能只快 1.2–1.5×） |
| 维护成本 | 每换一版模型都要重新剪枝 + 微调 + 验证 |

**结论**：2:4 稀疏适合"算力卡脖子、模型固定、愿意做精度补偿"的场景；
通用推理平台**默认用 dense**，把钱花在 KV 压缩和批处理上更划算。

## A.6 RDMA 与 rail-optimized

### A.6.1 RDMA：让网卡直接写对方内存

普通 TCP 发数据要经过：用户态 → 内核 socket → 协议栈 → 网卡 → 对方内核 → 用户态，
每一跳都有 CPU 拷贝和中断。RDMA 把这套全绕过：

```
本机 GPU 显存 ──NIC DMA──→ 网络 ──→ 对方 NIC DMA──→ 对方 GPU 显存
                （CPU 全程不参与，内核不参与）
```

| | TCP | RDMA |
|---|---|---|
| 延迟 | 20–100 µs | **2–5 µs** |
| CPU 占用 | 每包都要处理 | ≈0 |
| 拷贝次数 | 2–4 次 | 0（零拷贝） |
| 带宽 | 受 CPU 限制 | 100–400 Gb/s 轻松跑满 |

**三种实现**：

| 类型 | 说明 | 现状 |
|---|---|---|
| InfiniBand | 原生 RDMA，专用网络 | 性能最好，交换机贵 |
| RoCEv2 | 以太网上的 RDMA | 便宜，但要配无损网络（PFC/ECN） |
| iWARP | 老方案 | 少用 |

GPUDirect RDMA：网卡直接读写 GPU 显存（走 PCIe/NVLink），
不经过主机内存中转——多机推理的 all-to-all 必须开这个，否则多一次拷贝。

**代价**：RDMA 要求网络**无损**（丢包重传代价极高），要配 PFC、ECN、DCQCN，
运维门槛比普通以太网高一个档次。

### A.6.2 rail-optimized：一台机器 8 张卡，8 条独立的"车道"

普通做法：一个节点插 1–2 张网卡，8 张 GPU 共享 → all-to-all 时 8 卡抢一条车道。

rail-optimized：每张 GPU 配一张网卡，各自接到独立的 leaf 交换机（一条 rail）。

```
              Leaf0        Leaf1        ...      Leaf7
                │            │                     │
  节点 A:  GPU0─NIC0     GPU1─NIC1    ...      GPU7─NIC7
                │            │                     │
  节点 B:  GPU0─NIC0     GPU1─NIC1    ...      GPU7─NIC7
```

**关键性质**：节点 A 的 GPU3 和节点 B 的 GPU3 通信，**只经过 Leaf3 一跳**，
不经过 spine，不和其他 rail 抢带宽 → 同号 GPU 之间是"非阻塞"的。

**为什么这对 EP 特别重要**：all-to-all 里，每张 GPU 要和"其他所有卡的对应专家"交换数据。
如果拓扑是 rail 对齐的，集合通信库（NCCL）可以把通信组织成"同号 GPU 之间"，
把大部分流量关在 leaf 内，避免 spine 拥塞。

**代价**：8 张网卡 + 8 台 leaf 交换机，布线和成本都上去了；跨 rail 的流量仍要过 spine，
所以专家放置策略要尽量"同号优先"。

### A.6.3 与前面数字的对应

| 场景 | 走什么 | 带宽 |
|---|---|---|
| TP 的 all-reduce（机内） | NVLink | 400 GB/s |
| EP 的 all-to-all（跨机） | IB/RoCE + RDMA | 50 GB/s（400Gb/s） |
| PD 分离的 KV 传输 | RDMA（NIXL/Mooncake） | 50 GB/s |
| 模型权重/checkpoint 加载 | 3FS over RDMA | 50 GB/s |

同一个 14.7MB 的 all-to-all，走 NVLink 是 0.04ms，走 IB 是 0.3ms，走 TCP 可能 1ms+。
这就是为什么"跨机贵 8 倍"不是形容词，是算出来的。

### A.6.4 PFC / ECN / DCQCN：无损网络的三件套

RoCEv2 跑在以太网上，而以太网**默认会丢包**。RDMA 最怕丢包，所以要把网络改造成"无损"：

| 机制 | 全称 | 干什么 | 类比 |
|---|---|---|---|
| PFC | Priority Flow Control（802.1Qbb） | 交换机队列快满时，向上游发 PAUSE 帧，让它**暂停发送**某个优先级的流量 | 路口红灯，整条路停下 |
| ECN | Explicit Congestion Notification（RFC 3168） | 队列超过阈值时，交换机在包头打**拥塞标记**，接收方通知发送方减速 | 在车上贴"前方拥堵"标签 |
| DCQCN | Datacenter QCN | RoCE 网卡收到拥塞通知后降速，再逐步恢复的完整算法 | 看到标签后松油门的规则 |

**为什么要两个一起用**：ECN 是"提前减速"（治本），PFC 是"马上刹停"（兜底）。
只靠 PFC 会有两个严重问题：

- **拥塞传播**：一台交换机 PAUSE 上游，上游又 PAUSE 它的上游，一路传回去；
- **PFC 死锁**：缓冲区形成循环等待，整个网络卡死，要手动恢复。

所以好的无损网络是"ECN/DCQCN 把速度调平滑，PFC 尽量不触发，只在极端情况兜底"。

### A.6.5 丢包为什么对 RDMA 是灾难

TCP 是为"会丢包的网络"设计的（SACK、快重传），RDMA 不是。丢一个包会发生：

1. RDMA 可靠连接要**重传整个窗口**（go-back-N），不是只补一个包；
2. 集合通信有 barrier：all-reduce 必须等所有 GPU 都到齐——
   一张卡等重传，其余几十张卡全部空转；
3. 显存里为这次通信准备的 buffer 不能释放，后续步骤全堵住；
4. 延迟从微秒跳到毫秒，NCCL 超时（训练任务默认十几分钟无进展会直接崩溃重启）。

> 类比：32 个人抬一根长木头，一个人绊倒，全部人停住；
> 如果木头掉了（超时），整趟重来。TCP 像各自跑步，摔一个不影响别人。

0.1% 的丢包率在普通 Web 服务里毫无感觉，在 RDMA 集群里等于事故。

### A.6.6 rail 与 NCCL

**rail（轨道）**：一张物理网卡 + 它直连的那组 leaf 交换机构成一个网络平面。
一张 GPU 对应一条 rail，8 张 GPU 的节点就有 8 条互不共享的 rail。
"多 rail"就是多条并行的独立平面，同号 GPU 之间永远在同一条 rail 上一跳直达。

NCCL（NVIDIA Collective Communications Library）：GPU 集合通信库，
PyTorch 里的 `all_reduce` / `all_to_all` 最终都是调它。它做两件事：

1. **拓扑发现**：启动时探测 NVLink、PCIe、网卡怎么连，给每张 GPU 编号；
2. **选算法和路由**：ring 还是 tree、走哪张网卡、是否 rail 对齐——
   发现 GPU i 都在 rail i 上，就把通信组织成"同号通信"，流量不进 spine。

类比：NCCL 是物流调度系统，NVLink/IB 是高速公路，rail 是专用车道。
路修得再好，调度系统不按拓扑发货也会堵。

### A.6.7 采购/上云时那句话怎么理解

> "跨节点是否 IB 或无损 RoCE？"

| 网络 | 含义 | 能不能跑 EP/PD |
|---|---|---|
| InfiniBand | 原生 RDMA，信用机制天然无损 | ✅ 最佳 |
| **无损 RoCEv2** | 以太网 + RDMA + PFC/ECN/DCQCN 全套配置 | ✅ 可以 |
| **普通 VPC 以太网** | 多租户、有损、没有无损配置 | ❌ 退回 TCP，慢 8 倍 |

要追问的四件事：

1. 网卡型号与带宽（如 ConnectX-7、每 GPU 400Gb/s）；
2. 是否 **rail 对齐**（8 卡 8 网，还是 8 卡共享 2 网）；
3. 是否支持 GPUDirect RDMA（网卡直读写显存）；
4. 实例能否强制放置在同一 RoCE 子网 / 集群放置组里。

## A.8 NVLink 域：TP 的天然边界

NVLink 是 NVIDIA 的 GPU 间专有互联（不是 PCIe，也不是网络）。
H800 一机 8 卡通过板上的 NVSwitch 芯片两两全互联：任意两张卡之间都有
400 GB/s 的直连带宽（H100 是 900 GB/s，H800 出口受限版降到 400）。

**NVLink 域** = 被这张 NVSwitch 全互联网络覆盖、通信不出机的 GPU 集合：

```
              ┌────── NVSwitch（板载，全互联） ──────┐
              │                                       │
          GPU0 ─── GPU1 ─── GPU2 ─── GPU3
          GPU4 ─── GPU5 ─── GPU6 ─── GPU7
              └──────── 一个 NVLink 域 = 8 卡 ────────┘
                       │ PCIe + 网卡（IB 50GB/s）
                   ──── 跨节点，出域 ────
```

三层带宽对比：

| 路径 | 带宽 | 延迟 | 谁走这里 |
|---|---|---|---|
| GPU ↔ HBM | 3.35 TB/s | ns | 权重/KV 读取 |
| GPU ↔ GPU（**NVLink 域内**） | 400 GB/s | µs | TP 的 all-reduce |
| GPU ↔ 跨节点 GPU（IB/RDMA） | 50 GB/s | 几 µs–几十 µs | EP 的 all-to-all、PD 传 KV |

**为什么 TP 不出域**：TP 每层都要 all-reduce，一次推理 60 层 ×2（attention/FFN）= 上百次。
域内走 NVLink 总开销可接受；跨域走 IB，每层通信时间 ×8，TP 的加速比会被吃光。
域的大小 = TP 的实际上限：H800/H100 是 8；GB200 NVL72 用机柜级 NVLink Switch
把 72 张卡接成一张网，域才扩大到 72。

**怎么查自己机器的域**：

```bash
nvidia-smi topo -m
# 输出矩阵里：
#   NV#  = 第 # 条 NVLink（域内）
#   PIX  = 同 PCIe switch
#   SYS  = 跨 NUMA/跨节点（出域了）
```

NCCL 启动时做的"拓扑发现"，本质就是找到这个域，把 TP 通信排在域内、EP 通信走网卡。

**K8s 调度含义**：一个 TP=8 的 Pod 必须被调度到**同一台 8 卡机**（单 NUMA 节点），
所以资源申请写 `nvidia.com/gpu: 8`；跨机的 EP 组则要配合放置组 + rail 对齐的网络。

### A.8.1 历代服务器的 NVLink 域大小（选型速查）

域大小是 NVIDIA 基板/机柜设计决定的，不能任意选——没有 12 卡这种原生域。

| 平台 | 域大小 | GPU 间带宽（聚合） | 显存 | 典型用途 |
|---|---|---|---|---|
| PCIe 卡（L40S / H100 PCIe / 4090） | 1（无 NVLink 或仅成对桥接） | — | 24–80GB | 小模型、图形 |
| DGX Station A100 | 4 | 600 GB/s | 4×80GB | 小型工作站 |
| HGX A100/A800 SXM4 | 8 | 600 / 400（A800 出口版） GB/s | 8×80GB | 上一代机房主力 |
| HGX H100/H800 SXM5 | 8 | 900 / **400（H800）** GB/s | 8×80GB HBM3 | 当前推理主力 |
| HGX H200 | 8 | 900 GB/s | 8×141GB HBM3e | 长上下文/大 KV |
| HGX H20（出口特供） | 8 | 900 GB/s（互联没砍，算力砍） | 8×141/96GB，4TB/s | 中国区常见 |
| DGX/HGX B200 | 8 | 1.8 TB/s（NVLink 5） | 8×192GB | Blackwell 单机 |
| GB200 NVL72（整柜） | 72 | 每 GPU 1.8 TB/s | 72×192GB | 超大模型单域 |
| GB300 NVL72（2025） | 72 | 1.8 TB/s | 72×288GB HBM3e | DeepSeek 671B 可单域 |
| Rubin NVL144（路线图） | 144 | NVLink 6 | 未量产 | 2026 |

**几个关键判断**：

1. **8 是事实上的标准域**：云厂商 p5（AWS）、NDv5（Azure）、A3（GCP）、
   国内 H800/H20 实例几乎都是 8 卡；
2. 10/16 卡服务器 ≠ 16 卡域：超微等厂商的 16 卡机型通常是"两块 8 卡基板 + PCIe/IB 互联"，
   本质是**两个域**，跨基板通信立刻掉到 IB 级；
3. **72 域是机柜级域**：NVL72 把 NVSwitch 做进整柜，671B FP8（670GB）可以
   "TP 不出域"地跑——这是它相对 DeepSeek"TP=8 + EP 跨机 RDMA"路线的卖点；
4. **选型不只看域**：H20 互联满血但算力只有 H100 的 ~15%，适合推理/KV 大、prefill 不重
   的场景；H800 算力强但互联被砍到 400GB/s。

**模型怎么落**：

| 模型 | 最小域 | 最佳部署 |
|---|---|---|
| 8B FP16（16GB） | 1 卡 | 一卡多实例 |
| 70B FP16（140GB） | 2–4 卡 | 8 卡机内 TP=4，留显存给 KV |
| 200B MoE FP8（200GB） | 3 卡（下限） | 8 卡 H800/H200，TP=8 |
| 671B FP8（670GB） | 9 卡 → 必须跨域 | TP=8×EP 跨机 RDMA，或 NVL72 单域 |

### 用我们的架构语言评估国产卡

1. **权重装得下吗**：200B FP8 = 200GB；910 系列无 FP8，BF16 要 400GB——
   8×910C（128GB×8=1TB）装得下，但留给 KV 的比例下降，并发会话数变少，要重算容量；
2. **decode 看带宽**：重点对比 HBM 带宽而非算力，910B 带宽约为 H800 的一半量级，
   单 token 成本要按实测重算，不能直接套用 3,490 tok/s 的上限；
3. **引擎**：PagedAttention/连续批处理/前缀缓存不是免费的——需要厂商 kernel 适配。
   昇腾走 MindIE 或 vllm-ascend，成熟度和 SGLang 特性（RadixAttention）可能滞后；
4. **网络**：只有华为有 UB 这种机柜级域；其他家的 EP 跨机依赖无损 RoCE（§A.6 全套照样要配）；
5. **采购策略**：合规要求国产卡时，建议 H800 池与国产池双栈、网关层按模型路由，
   用同一套 SLO（TTFT（Time To First Token）/TPOT（Time Per Output Token）/单 token 成本）做 A/B，而不是假设两边等价。

## A.8.3 失败模式：并行最容易在哪坏

| 现象 | 根因 | 怎么发现 | 怎么修 |
|---|---|---|---|
| NCCL hang，无报错 | 拓扑不匹配 / MTU 不一致 | `nccl-tests` 卡在 init；`nvidia-smi topo -m` | 统一 MTU 9000，按 rail 建环 |
| all-to-all 只有理论值 1/5 | EP 跨 rail、PFC 风暴 | IB 端口 `port_xmit_discards` 告警 | 双平面 + 专家按 rail 放置 |
| TP 从 8 扩到 16 无加速 | 出了 NVLink 域 | `topo -m` 显示 `SYS` | 回到 TP≤8，跨机用 PP/EP |
| 训练与推理互相拖慢 | 共用一张 IB 网 | PFC pause 计数飙升 | 训练/推理分平面 |
| decode 吞吐只有理论 60% | all-to-all 与 KV 读抢带宽 | nsys 里 memcpy 占比过半 | 调 EP 度，换 EP8/TP8 组合 |

复算见 `labs/pd_cost_lab.py`（不同并行度下的吞吐与成本）。

## A.8.4 推翻条件：这个并行策略什么时候不成立

TP=8 是机内 NVLink 下的最优解，但它有明确边界：

| 前提 | 不成立时 | 换成什么 |
|---|---|---|
| 单机放得下 8 卡且 NVLink 全互联 | 卡间只有 PCIe | TP 降到 2，靠 PP 补 |
| 权重能切进 8 张卡 | 权重 > 8×80 GB | 加 PP，接受跨机 |
| 跨机带宽 ≥ 50 GB/s | 只有 25 Gbps 以太 | 放弃跨机 EP，改机内 TP + 跨机 PP |

下面三条就是它的推翻条件，最容易被踩到的是第三条。EP 的 all-to-all 对带宽极敏感，带宽不够时通信会把收益吃光，不如老老实实 TP+PP。账可以自己算：25 Gbps 以太传 8 MB 的 all-to-all 消息约 2.7 ms，EP 每步两次就是 5.4 ms，占 25 ms TPOT 的 21%——带宽再低一半，通信就吃掉四成 decode 时间。


## A.9 自测

1. TP=8 时，一个线性层要做几次 all-reduce？为什么 TP 一般不跨机？
2. EP 的 all-to-all 传的是什么？为什么它是 MoE 推理的瓶颈？
3. all-reduce 和 all-to-all 的区别，用一句话说清。
4. 2:4 稀疏的"2 倍"为什么在 decode 上拿不到？
5. 什么情况下 MoE 反而不如稠密模型划算？

<details><summary>参考答案</summary>

1. 每层 1 次（前向），因为要把各卡的部分和加起来；跨机 all-reduce 走 IB，带宽只有 NVLink 的 1/8，延迟高，所以 TP 限制在机内。
2. 传 token 的隐藏状态（dispatch 送去专家，combine 送回结果）；量大、突发、跨机，且专家分布不均会加剧拥塞。
3. all-reduce 是"大家求和后人人都有全量结果"；all-to-all 是"人人把不同的数据发给不同的人"，本质是转置。
4. decode 受显存带宽限制，算力闲置率本就 >80%（MFU <10%）；稀疏只省算力、不省带宽，所以加速有限。
5. batch 小、网络差、延迟敏感、专家负载严重不均时，MoE 的通信和调度开销会吃掉算力优势。
</details>
