# 第 11 章 · 调度与 PD 分离

> 迁移自 v1 `ch04-pd-disaggregation.md`。文中引用"第 N 章"为 **v1 旧编号**，与 v3 的对应关系见 [../../MIGRATION.md](../../MIGRATION.md)。


> **一句话结论**：prefill 和 decode 是两种相反的负载——一个突发吃算力，一个平稳吃带宽。
> 规模一大，唯一正确的做法是拆成两个资源池、两套调度信号、两个 SLO（Service Level Objective），
> 中间用一次 KV 传输完成交接。

---

## 1. 问题重述：为什么必须谈这件事

把前三章的结论并排放：

| | Prefill | Decode |
|---|---|---|
| 工作方式 | 几千 token 一次并行 | 1 token/步，走几百步 |
| Roofline 位置 | 平屋顶，**算力受限** | 斜屋顶，**带宽受限** |
| 负载形态 | **突发**（7000 QPS 到达） | 平稳（每个会话持续几秒） |
| 关心的 SLO | TTFT（Time To First Token） < 800ms | TPOT（Time Per Output Token） p95 ≤ 50ms |
| 扩容速度 | 秒级响应突发 | 分钟级，随在飞会话数变 |
| 容量模型里的卡数 | 909（含前缀命中折扣） | 700 |

让它们共用一张卡，就像让急诊和住院部共用同一间手术室：
住院（decode）本来按部就班，一来急诊（5000 token prefill）所有人暂停。

实验 [`pd_lab.py`](../../labs/pd_lab.py) 把这一幕量化了（40 个在跑 decode，7 QPS 到达）：

| 模式 | TPOT p50 | TPOT p95 | TPOT max | 超 50ms 占比 | TTFT p95 |
|---|---|---|---|---|---|
| 混部（prefill 独占） | 25ms | 75ms | 224ms | 10.8% | 200ms |
| Chunked prefill | 36ms | 36ms | 36ms | 0% | 667ms |
| **PD 分离** | 25ms | 25ms | 25ms | 0% | 220ms |

三种处理哲学：

1. **混部独占**：prefill 来了整卡归它，decode 全队停住 → 尖刺；
2. Chunked：prefill 切碎混跑，人人有份 → 平滑但都变慢（TTFT 3.3 倍）；
3. **PD 分离**：急诊住院物理分楼 → 两个 SLO 同时达标，代价是多一套资源 + 一次交接。

## 2. PD 分离的架构与数据流

```
              ┌────────────── Gateway / Router ──────────────┐
              │  KV-aware 路由：这个前缀在哪台 P？在哪台 D？    │
              └───────┬───────────────────────────┬──────────┘
                      ▼                           ▼
        ┌─────────────────────┐       ┌─────────────────────┐
        │  Prefill Pool (P)   │       │  Decode Pool (D)    │
        │  大算力配比          │       │  大显存带宽配比       │
        │  TTFT 调度          │       │  TPOT 调度          │
        │  基数树：命中前缀    │       │  连续批处理 + 分页   │
        └──────────┬──────────┘       └──────────▲──────────┘
                   │  算完所有 KV                 │
                   ▼                             │
        ┌─────────────────────┐    RDMA（Remote Direct Memory Access）/RoCE      │
        │  KV 传输层           │ ────────────────▶ │
        │  NIXL / Mooncake /  │  0.96GB ≈ 20ms    │
        │  vLLM KV Connector  │                   │
        └─────────────────────┘                   │
                   │  首 token 可直接流式返回 ──────┘
```

**请求生命周期**：

```
1. 请求到 Router，按前缀亲和选一个 P 实例（让基数树命中率最大化）
2. P 实例 prefill：命中部分零计算，只算后缀
3. 算完的 KV 经 RDMA 推（或 D 实例拉）到选定的 D 实例
4. Router 把请求的后续流切到 D；TTFT 几乎不增加（20ms 传输与首包重叠）
5. D 实例连续批处理跑完整个 decode，期间该请求不离开这台 D
6. 结束，D 上的分页 KV 归还；热前缀留在 D 的基数树/缓存里供下轮复用
```

## 3. KV 传输：传什么、传多少、为什么比重算便宜

只传 K/V 张量，不传权重（权重每个实例本来就有一份）。

```
8K 会话 KV = 0.96GB（FP16；FP8 KV 再减半）
传输时间   = 0.96GB ÷ 50GB/s（400Gb IB）≈ 20ms
重算时间   = 5,000 token prefill ≈ 300–430ms
           → 传输便宜 15 倍
32K 会话  = 3.84GB ÷ 50 ≈ 77ms，重算约 2.8s → 仍然划算
```

**工程细节**：

| 问题 | 做法 |
|---|---|
| 传输时机 | prefill 结束立刻异步传，与首 token 流式返回并行，隐藏延迟 |
| 传哪里 | D 实例的空闲物理页（第 03 章的分页 pool），按页表写入，不复制第二遍 |
| KV 量化 | 用 FP8 KV 传输再反量化，流量减半（精度损失要评测） |
| 拓扑要求 | GPUDirect RDMA + rail 对齐（附录 A.6），否则退回 TCP，20ms 变几百 ms |
| 对齐要求 | P 和 D 必须同模型版本、同精度、同 KV 布局（MLA 压缩维度都要一致） |
| 主流实现 | NIXL（NVIDIA）、Mooncake（Moonshot）、vLLM KV Connectors、SGLang PD disaggregation |

**什么时候传输反而不划算**（不要教条分离）：

- 集群太小：两个池各自凑不满 8 卡实例，碎片化浪费；
- 没有 RDMA：TCP 传 KV 可能慢于重算；
- 输入极短、输出极短：prefill 占大头，decode 池本身负载轻；
- 前缀命中极高且 prefill 本就很轻时，chunked 混跑更简单。

经验阈值：日请求数十万级以上、平均输出 >150 token、有 IB/RoCE，分离才开始赚钱。

## 4. 两个池各自的调度器

### 4.1 Prefill 池：围绕 TTFT

- **入队即排队**：核心指标是 `num_requests_waiting` 和队列等待时间；
- 调度策略：FCFS + 抢占式优先级（付费用户插队，被抢占请求只重算 prefill）；
- Chunked prefill 仍在用：池内部把超长 prompt 切块，防止单请求饿死队列；
- 基数树匹配是入队第一动作，决定"算多少"。

### 4.2 Decode 池：围绕 TPOT

- 连续批处理（§第 03 章），每 25ms 重组 batch；
- batch 上限由两条红线共同决定：TPOT p95 ≤ 50ms 和 **KV 水位 < 85%**；
- 撞线时的动作有梯度：拒绝新加入 → 抢占低优先级请求（换出 KV 到 CPU，可换回）→ 丢弃重算；
- **会话粘性**：一个请求的 decode 中途不迁移实例（迁移 = 再传一次 KV）。

### 4.3 Router：第三个调度器

它做两个决定：

1. **选 P**：前缀亲和（同租户/同系统提示 → 同一实例的基数树）；
2. **选 D**：看 D 实例的实时 TPOT 与 KV 水位（KV-aware routing），
   这正是 Gateway API Inference Extension 的 `InferencePool` 在标准化的接口。

## 5. 扩缩容：两套完全不同的信号

| | Prefill 池 | Decode 池 |
|---|---|---|
| 主信号 | 排队请求数、TTFT p95 | TPOT p95、KV 水位、抢占次数 |
| 响应速度 | 秒级（突发） | 分钟级（随会话数平滑变） |
| 冷启动代价 | 拉权重 200GB ≈ 数分钟 → **必须有 warm pool** | 同左 |
| 缩容方式 | 队列空了立刻缩 | drain：等现有会话跑完再下线，不能杀连接 |
| K8s 手段 | KEDA（Kubernetes Event-driven Autoscaling） + Karpenter + 预热池 | KEDA + PDB + 优雅终止宽限 |

我们部署目录里的 [`20-keda-decode.yaml`](../../deploy/k8s/20-keda-decode.yaml)
已经是这套信号（waiting 数 + cache 水位双触发）；P 池再加一个队列长度触发器即可。

**关键纪律**：**不要按 GPU 利用率扩缩容**。decode 池 GPU 算力利用率常年 <10%（带宽受限！），
按 GPU% 扩容会永远不弹。按队列和 SLO 扩。

### 5.1 分离后"闲置的另一半"怎么办

先纠正一个直觉：另一半资源本来就用不上，不是分离造成的。

P 跑 prefill T=5,000 时，AI≈10,000，远在屋顶拐点 590 之上：

```
算力：跑满（平屋顶）
带宽需求 = 算力 ÷ AI = 1.98 PFLOPS ÷ 10,000 = 198 GB/s ≈ HBM 的 6%
→ 即使和 decode 共卡，这 94% 带宽也"喂不动额外 decode"：
   多塞 decode 不会多要带宽吗？会——但 prefill 的 kernel 已经占满 Tensor Core，
   decode 的小矩阵乘只能排队（实验里的 224ms 尖刺就是这么来的）
```

D 池反过来：带宽跑满时算力只用 0.3%。这是 Roofline 的物理结论，混部也一样。

混部的真实账不是"互补填满"，而是**互相踩**：

| | 混部（或 chunked） | PD 分离 |
|---|---|---|
| prefill kernel 在跑时 | decode 被推迟，TPOT 尖刺 | D 池照常每 25ms 出字 |
| 空闲出来的"另一半" | 无法利用（kernel 独占 SM、batch 形状冲突） | 不浪费——池大小各自按瓶颈资源定 |
| 总卡数 | 按"尖刺叠加"超配 | 按 P:D=1.3:1 分别配，总量更低 |

进一步省"另一半"的三个手段：

1. **异构 SKU**：P 池用算力强卡（H800），D 池用带宽/显存强卡（H200、甚至 H20——
   互联满血、141GB 显存但算力被砍，恰好匹配 decode），每一分钱花在瓶颈资源上；
2. **池内 chunked**：P 池把长 prompt 切块提 MFU，D 池纯 decode 把带宽跑满，
   互补优化发生在**池内**而不是混在一池；
3. **独立伸缩**：P 池按秒级突发弹，D 池按会话量缓变——这是混部永远做不到的弹性粒度。

一句话：**分离不是"把浪费拆成两半"，而是承认算力和带宽在两种负载下本就不可兼得，
让每种卡只对自己的瓶颈负责。**

### 5.2 异构 SKU 的具体利用率：H800（P）vs H200（D）

> 口径：8 卡 TP=8 节点；200B MoE FP8 权重 200GB；KV 0.96GB/会话（8K，FP16）。
> 注意"利用率"必须说清是**哪种资源**——算力、带宽、容量三个数字完全不同。

| 维度（一个 8 卡节点） | **H800 池（P）** | **H200 池（D）** |
|---|---|---|
| 峰值 FP8 算力 | 15.8 PFLOPS | 15.8 PFLOPS（**一样**） |
| HBM 容量 / 带宽 | 640GB / 26.8 TB/s | 1,128GB / 38.4 TB/s |
| 权重占用 | 200GB | 200GB |
| KV 预算 | 440GB | 928GB |
| 8K 并发会话上限 | 458 | **967（2.1 倍）** |
| **算力 MFU** | 35–40% ✅ | 7–10%（decode 天然低） |
| **HBM 带宽利用率（MBU）** | 2.4%（长 prefill） | 60–70% ✅ |
| **HBM 容量利用率** | 权重 31% + 瞬态 KV 10–20% | ~80%（200 权重 + ~700 KV）✅ |
| 节点有效吞吐 | ~10.5 万 prefill tok/s | ~2.6 万 output tok/s（H800 只有 1.8 万） |
| 优化的 SLO | TTFT | TPOT |
| 单 output token 相对成本 | — | **便宜约 30–40%**（同价位时） |

推导（可以手算复核）：

```
P：15.8 PF × 40% MFU = 6.34 PFLOPS ÷ 60 GFLOP/token ≈ 10.6 万 tok/s
   带宽需求 = 6.34e15 ÷ 10,000(AI) = 634 GB/s ≈ 26.8TB/s 的 2.4%

D：26.8/38.4 TB/s × 65% MBU ÷ 0.96 GB
   H800 → 18.1k tok/s，H200 → 26.0k tok/s
   对应 decode MFU：6.9% / 9.8%
```

**看这张表的正确姿势**：

1. **不存在"一个利用率"**：P 池算力 40%、带宽 2%、容量 40%；D 池算力 8%、带宽 65%、容量 80%——
   每个池都有一项"主资源"被打满，这正是分离+异构的目的；
2. H200 算力和 H800 完全相同（都是 Hopper），贵只贵在 HBM——
   而 D 池恰好为 HBM 付费，P 池不为用不上的 HBM 多花钱；
3. 中国区替代：P 池 H800，D 池可用 H20（96GB/卡、4TB/s、互联满血、算力被砍）——
   decode 不缺算力，H20 当 D 池 SKU 是合规与成本的双优解；
4. 拿"GPU 利用率"（nvidia-smi 的 SM%）考核两个池都会误判，
   P 看 MFU、D 看 MBU 和 KV 水位。

### 5.3 异构后数据怎么搬：跨节点 KV 迁移

只搬 K/V 张量，权重不搬（权重每个节点本来就有一份 200GB）。

```
P(H800) prefill 完成
   │ ① 把 KV 注册到传输层（NIXL/Mooncake）：句柄 + 块位置清单
   │ ② Router 用 KV-aware 策略选一个 KV 水位低的 H200 D 节点
   ▼
③ GPUDirect RDMA：P 显存 ── rail 对齐的 IB ──▶ D 显存的物理分页
   不经主机内存、不做第二次拷贝
   8K：0.96GB ÷ 50GB/s ≈ 20ms（FP8 KV 约 10ms）
   32K：3.84GB ≈ 77ms
   │ ④ 首 token 与传输并行流式返回，TTFT 只多 ~20ms
   ▼
D(H200)：按收到的块建页表（第 03 章 TokenToKVPool）→ decode 立即开始
```

**能搬的前提（一致性契约）**：

| 必须一致 | 不一致会怎样 |
|---|---|
| 模型版本/修订 | KV 语义不同 → 结果错乱（必须整池作废重建，见 §6.3 树的版本绑定） |
| 权重精度与 KV 精度 | 要加反量化转换，通常直接重算 |
| 注意力结构（GQA 头数/MLA 隐维） | 张量变不出对应维度 |
| TP 切分方式 | P、D 都 TP=8 时张量分片天然对齐；TP 度数不同要 reshard（专门的重分片 kernel） |
| KV 布局/块大小 | 由传输层做块级映射（NIXL registry 干这个），引擎侧不感知 |

H800 → H200 为什么能直接搬：同一 Hopper 架构、同样的 FP8 格式和张量核，KV 就是一串数字，
换 HBM 更大的同代卡不改变 KV 内容——异构只异在"内存规格"，不在"计算语义"。

**失败回退**：D 池满、RDMA 超时 → 在目标节点重算 prefill（付 300–430ms）或换一台 D 重传，
不能让请求挂死；传输层要有超时 + 重试 + 重算三级降级。

**跨厂商（H800 → 昇腾）**：KV 布局、kernel、页表全不同，不能直接搬——
要么在目标栈重算 prefill，要么**每个技术栈内部各自闭环 PD**（呼应附录 A.8.2 的双栈策略）。

### 5.4 量化收益：四种架构的卡数、成本、SLO

同一负载（20M DAU、1.5 亿轮/日、7000 QPS、输入 5000、输出 350、命中 70%）：
实验 [`pd_cost_lab.py`](../../labs/pd_cost_lab.py)，口径与 `capacity_model.py` 一致
（冗余 1.3 × 双 AZ 1.2；H200 整机价按 +30%、H20 按 −15% 假设）。

| 架构 | P 卡 | D 卡 | 总卡 | 年推理成本 | vs A | TPOT p95 | SLO 未达 | 每 GPU 日产出 | 元/百万输出 tok |
|---|---|---|---|---|---|---|---|---|---|
| A 混部同构 H800 | 909 | 700 | 3,016 | 1.93 亿 | — | 75ms | 10.8% | 1,741 万 | 10.05 |
| B PD 同构 H800 | 909 | 700 | 2,512 | 1.61 亿 | **−16.7%** | 25ms | 0 | 2,090 万 | 8.37 |
| C PD 异构 H800+H200 | 909 | 489 | 2,184 | 1.51 亿 | **−21.7%** | 25ms | 0 | 2,404 万 | 7.87 |
| D PD 异构 H800+H20 | 909 | 586 | 2,336 | 1.42 亿 | **−26.1%** | 25ms | 0 | 2,247 万 | 7.42 |

**收益拆成三笔（不要混着说）**：

1. **PD 分离本身（A→B）**：卡数 −16.7%、成本 −16.7%，
   换来 TPOT p95 **75ms → 25ms**、SLO 未达率 **10.8% → 0**。
   省的原因不是"卡跑得更快"，而是混部要压住尖刺必须超配 20%（1.20 争用系数）。
2. **异构 SKU（B→C）**：卡数再 −13.1%，成本 −6.0%。
   D 池换成 H200 后单卡 decode 吞吐 ×1.43（带宽 4.8 vs 3.35），但整机贵 30%，所以钱只省 6%。
   盈亏平衡点：H200 整机溢价 < 55% 时，异构仍比同构便宜；超过就该留在同构。
3. **合规替代（B→D）**：H20 单卡便宜且带宽 4.0TB/s 高于 H800，卡数 −7.0%、成本 −11.3%；
   代价是算力被砍到 1/6——decode 不缺算力，所以几乎无感，但 prefill 绝不能放 H20 池。

**必说的五个前提**（否则这些百分比不成立）：

- **规模**：小集群两个池各自凑不满 8 卡实例，碎片化会把收益吃光；
- **网络**：无 RDMA/GPUDirect 时 KV 传输从 20ms 变几百 ms，PD 收益归零；
- **命中率**：前缀命中从 70% 掉到 40%，P 池要翻倍，比例失衡；
- **上下文**：32K 时 D 池变 KV 容量受限，H200（141GB）优势扩大，H20 优势缩小；
- **价格**：H200/H20 整机价必须用真实采购价替换后重跑，别抄假设值。

## 7. 落到我们的容量模型

- 基准 2,512 卡中，raw 配比约 P 909 / D 700（其余为冗余），比例约 1.3 : 1；
- 这个比例随业务漂移：输出越长、D 越重；长 prompt 越多、P 越重——所以池子要独立可调；
- 8 个 cell 各自内部 PD 分离；**cell 之间不传 KV**（0.96GB × 跨城延迟不划算）；
- 多轮对话的第二轮：前缀在 D 实例的基数树里 → Router 把请求路由回同一台 D，
  由它直接做轻量 prefill 或交回 P——路由亲和把"分离成本"降到最低。

---

## 8. 四个误区

误区 0：P 池跑 prefill 时带宽闲置，是分离制造的浪费。
不是——prefill 在平屋顶上，AI≈10,000 时只需 6% 的 HBM 带宽；同理 decode 池带宽跑满时
算力闲置 99%+。这是 Roofline 的物理事实，**混部时这些资源一样用不上**（kernel 独占
计算单元、batch 形状冲突），分离只是让每种资源"各归其主"。

误区 1：PD 分离 = 成本翻倍。
两个池都在跑满自己擅长的负载，混部时的"prefill 尖刺期 decode 空转"消失，
容量模型显示总量反而更省；翻倍的是**资源碎片**风险（小规模才疼）。

误区 2：有了 chunked prefill 就不用分离。
Chunked 是"不分离时的最优解"（TPOT 从 224ms 尖刺变 36ms 平滑）；
但它把 TTFT 拉长 3 倍，且两种负载仍互相稀释。高 QPS 生产形态两者都要：池内 chunked，池间分离。

误区 3：KV 传输就是 memcpy。
它要解决选实例、建页表、RDMA 直写显存、版本一致性、失败回退（重算）五件事，
所以才用 NIXL/Mooncake 这种专门组件，不在业务代码里手写。

## 8.5 失败模式与推翻条件

| 现象 | 根因 | 怎么发现 | 怎么修 |
|---|---|---|---|
| 上了 PD，吞吐反而降 10% | KV 传输开销大于并行收益 | 看 transfer 时间占总时长比例 | 占比 >15% 就回退 |
| prefill 实例闲着、decode 排队 | 两侧配比失衡 | 两个队列长度对比 | 加动态比例守卫（第 33 章 §8） |
| TTFT 变好，TPOT 变差 | decode 侧 batch 变大 | 分阶段看指标 | 限制 decode 的 `max_num_seqs` |
| 扩缩容时零星 500 | 实例被摘除时还有 KV 在传 | 传输出错日志 | 先 drain 再退（第 33 章 §11） |
| P99 尖峰周期性出现 | 传输队列堆积 | 传输队列深度曲线 | 限并发传输数 |

第二条最隐蔽：它表现得像"PD 没效果"，实际是配比错了。

**推翻条件**：短请求为主（平均 <500 token）时 prefill 占比太低，拆分的收益抵不过传输开销，这时不该上 PD。

## 11. 验收：怎么证明 PD 真的有效

| 指标 | 混部基线 | PD 目标 | 复算 |
|---|---|---|---|
| TPOT p95 | 75 ms | ≤ 25 ms | `labs/pd_lab.py` |
| TTFT p95 | 200 ms | ≤ 240 ms | `labs/pd_lab.py` |
| KV 传输 P99 | — | < 30 ms | trace |
| P:D 卡数周漂移 | — | <10% | `labs/pd_cost_lab.py` |
