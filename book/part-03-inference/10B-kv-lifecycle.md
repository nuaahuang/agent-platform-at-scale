# 第 10B 章 · KV 的生命周期：分配、淘汰、抢占与卸载

> 读完你能回答：
> ① 大家嘴里的"KV 淘汰"，其实是三件不同的事，分别是什么？
> ② 为什么前缀缓存的淘汰必须从叶子开始？
> ③ 抢占一个请求，recompute 和 swap 差多少，怎么选？
> ④ 为什么 KV 不需要 TTL？

## 1. 问题：每秒 58 万次块分配

一个 2,000 万 DAU 的平台，每天 1.5 亿轮对话、平均 5,350 token：

```
1.5e8 轮 × 5,350 token ÷ 16（块大小）÷ 86,400 s ≈ 58 万次/秒
```

每秒 58 万次 KV 块分配与释放。 每一次都要回答三个问题：

1. 有没有空闲块？（**分配**）
2. 没有的话，能不能挤掉部分缓存？（**淘汰**）
3. 还不能的话，牺牲哪个正在跑的请求？（**抢占**）

三个问题对应三套机制，混在一起讲必然讲糊。

---

## 2. 三种回收不是一回事

| 类型 | 触发时机 | 影响 | 负责模块 | 用户感知 |
|---|---|---|---|---|
| **① 空闲块回收** | 请求正常结束 | 无 | BlockAllocator | 无 |
| **② 前缀缓存淘汰** | 要腾空间给新请求 | 下次命中率下降 | LRU / 基数树 | 变慢一点 |
| ③ 抢占 preemption | 正在跑的请求被夺走 KV | 该请求回炉 | Scheduler | **可见卡顿（1.6 s）** |

日常说的"淘汰"是 ②，但生产事故多来自 ③——因为它直接让用户看到一个**正在输出的回答突然停住**。

```
请求到达 ─▶ 分配块 ─▶ [算 KV] ─▶ 输出 ─▶ 释放块
                │                    │
                │ 无空闲块            │ 引用计数 -1
                ▼                    ▼
           ② 淘汰缓存 ──▶ 无缓存可淘汰 ──▶ ③ 抢占
```

## 3. 分配器：free list + block table

物理上 KV 按 **16 token 一块**切分（第 10 章 §4）。一个 TP8 实例的真实账：

```
显存总量   8 × 80 GB = 640 GB
权重       200 GB（200B MoE，FP8，1 byte/参数）
激活+工作区 40 GB
KV 可用    400 GB
单块大小   16 token × 120 KB = 1.92 MB
块总数     400 GB ÷ 1.92 MB ≈ 208,000 块
```

分配器维护两个结构：

| 结构 | 内容 | 作用 |
|---|---|---|
| free list | 所有空闲块的物理编号 | O(1) 取块 |
| block table | 每请求的"逻辑第 i 块 → 物理第 j 块" | 支持不连续存放 |

```python
def allocate(seq, n_blocks):
    if len(free_list) >= n_blocks:
        blocks = [free_list.pop() for _ in range(n_blocks)]
        seq.block_table.extend(blocks)
        return True
    if evict_prefix_cache(n_blocks - len(free_list)):   # ②
        return allocate(seq, n_blocks)
    victim = scheduler.pick_victim()                     # ③
    return preempt(victim) and allocate(seq, n_blocks)
```

### 3.1 拿不到块的请求去哪了：waiting 队列

上一节那个 `allocate()` 返回 `False` 之后，请求并没有消失——它进了**引擎的等待队列**。

排队不在网关，在 KV 分配器的门口。

| 层 | 队列在哪 | 默认容量 | 满了怎么样 |
|---|---|---|---|
| 客户端 | 并发池 / 连接池 | 自定 | 本地等待 |
| 网关 | Envoy 熔断器 `max_pending_requests` | 1,024 | **直接 503** |
| **引擎** | `Scheduler.waiting`（deque） | **无上限**（vLLM 默认） | **无限排队** |

引擎里每个 step 做一遍这件事：

```
for req in waiting:            # 从队头开始
    if block_manager.can_allocate(req):
        waiting.remove(req)
        running.append(req)    # 进入本 step 的 batch
    else:
        break                  # KV 不够，队头都进不去，后面更进不去
```

于是有两个数决定了用户的等待：

```
排队时间 ≈ 队列长度 ÷ 每实例吞吐
```

按我们的账（单实例 2.8 QPS）：队列 64 个 → 平均等 **23 秒**。
这就是第 33 章把 `num_requests_waiting > 64` 当扩容阈值的原因。

最危险的默认值是"队列无上限"：流量翻倍时队列长到 5,000，
TTFT（Time To First Token） 变成 30 分钟，所有请求都在等一个永远不会释放的块——成功率 100%，体验归零。

### 3.2 队列会不会满：上限怎么定，满了怎么办

先分清三种"放不下"，它们的行为完全不同：

| 位置 | 默认上限 | 满了的表现 |
|---|---|---|
| 网关熔断器 | 1,024 | 503，**快速返回** |
| **引擎 waiting 队列** | **无上限** | 不报错，延迟无限涨 |
| KV 块池 | 208,000 块 | 请求卡在 waiting |

关键：引擎队列不会"满"，它只会一直涨。

涨到进程 OOM 被 kill，所有在飞请求一起丢——这比"满了直接拒绝"糟糕一个量级。

所以队列必须由我们自己设上限。定法是一条除法：

```
队列上限 = 目标等待时间 × 单实例吞吐
        = 30 s × 2.8 QPS ≈ 84
```

配 5,000 的队列，等于向用户承诺"最多等 30 分钟"。

### 3.3 满了之后：四种策略

| 策略 | 做法 | 评价 |
|---|---|---|
| **拒绝新请求** | 429 + `Retry-After: 5` | **默认选择**，保护已接受的 |
| **丢最老的** | 踢掉队头 | **绝对不要**——它最接近完成，丢掉最亏 |
| **降级** | 切小模型 / 缩短 max_tokens | 体验降级，但保住可用性 |
| **带超时排队** | 等 30 s 仍未开始就 503 | 推荐，与拒绝组合 |

实现位置有四种，选一种或叠加：

```python
LIMIT = 84                     # 目标等待 30 s × 2.8 QPS
inflight = {}

def admit(instance_id):
    if inflight.get(instance_id, 0) >= LIMIT:
        return False           # → 429 + Retry-After
    inflight[instance_id] = inflight.get(instance_id, 0) + 1
    return True
```

| 位置 | 手段 | 优点 |
|---|---|---|
| 应用侧 | 有界 Semaphore / 计数器 | 精确到实例，最可控 |
| 网关 | Envoy `max_pending_requests: 84` | 挡在最外层，省资源 |
| 令牌桶 | 按 QPS 与 token 双维度限速 | 防长请求偷额度 |
| 引擎 | 调小 `max_num_seqs` | 间接减少排队，不精确 |

**拒绝必须满足三个条件**，否则会把过载放大成雪崩：

1. **快**：<50 ms 返回，不要先排队再超时；
2. **可重试**：429 + `Retry-After`，明确告诉客户端多久后再来；
3. **有预算**：客户端重试要有上限——1.2 倍过载能被无脑重试放大成 2.4 倍（第 2 章 §8.2）。

### 3.4 三个必须观测的数

```text
queue_depth            队列深度（>84 说明准入没生效）
admission_rejected     拒绝率（持续 >20% 说明容量不足）
queue_wait_ms          排队时长 p95（这才是用户感知的那段）
```

**排队时长比队列深度更重要**：队列 200 但每秒消化 300，用户等 0.7 秒；
队列 50 但每秒只消化 5，用户等 10 秒。

背压与准入的完整设计见第 25 章。

关键：`block table` 是间接层，所以物理块可以不连续——这正是 PagedAttention 的全部意义（第 10 章 §4）。

## 4. 前缀缓存淘汰：叶子 LRU + 引用计数

### 4.1 为什么是树，为什么从叶子删

前缀缓存的结构天然是树（RadixAttention）：

```
        [系统提示 2.5K]          ← 根，全体共享
         /            \
   [会话 A 历史]   [会话 B 历史]
        |              |
   [A 新增]        [B 新增]      ← 叶子
```

两条硬约束：

| 约束 | 原因 |
|---|---|
| **从叶子开始删** | 父节点被子节点引用，先删父会让子悬空 |
| **`ref > 0` 不能删** | 正在被请求使用，删了就是读写已释放内存 |

```python
def evict_prefix_cache(need):
    freed = 0
    while freed < need:
        # 只在"引用计数为 0 的叶子"里挑，按最后访问时间
        cand = min(evictable_leaves, key=lambda n: n.last_access)
        freed += free_node(cand)      # 回收它独占的块
    return True
```

vLLM 是扁平版：块有内容哈希和引用计数，空闲块进 LRU 队列，分配时从队尾取。
SGLang 是树版：同上，但粒度到 token，且多一层 HiCache 下沉。

### 4.2 没有 TTL：为什么 KV 不需要时间过期

这是最容易被问住的一点：KV 缓存不设过期时间。

```
HTTP 响应缓存  →  TTL / Cache-Control / ETag
Redis key      →  TTL
JWT            →  exp
KV cache       →  token 序列的哈希
```

同一段 token、同一个权重，算出来的 KV **永远一样**。既然结果恒定，"过期"就不成立。

所以主流引擎里没有时间过期逻辑，只有两种回收：**引用归零**、**容量压力**。

| 情况 | 算过期吗 | 说明 |
|---|---|---|
| 请求结束 | ❌ | 块回 free list，但内容还在，下次能命中 |
| **权重版本变了** | ✅ **真失效** | 旧 KV 用旧权重算的，必须整批作废 |
| 显存压力 | ❌ | 被挤掉，不是过期 |
| 租户隔离 | ❌ | 逻辑隔离，与时间无关 |

**唯一的真失效是权重版本**——所以第 36 章讲灰度时，第一件事就是"KV 不跨版本共享"。

### 4.3 位置依赖：只有"从 0 开始的前缀"能复用

这条约束常被忽略。假设公共文本放中间：

```
✅ 可复用  [公共系统提示][会话 A]
✅ 可复用  [公共系统提示][会话 B]
❌ 不可复用 [A 的订单号][公共系统提示]
❌ 不可复用 [B 的订单号][公共系统提示]
```

因为 RoPE 把**位置偏移**编进了 K/V：同一段文本在第 0 位和第 12 位算出的 KV 不同。

结论：稳定内容必须放最前面。 这不是编码习惯，是数学要求。

## 5. 抢占：recompute 还是 swap

### 5.1 两种做法的代价

| 做法 | 操作 | 代价公式 |
|---|---|---|
| recompute | 丢掉 KV，稍后重跑 prefill | `L ÷ 20000`（prefill 吞吐） |
| swap | 搬到 CPU 内存，需要时搬回 | `2 × KV_bytes ÷ 64 GB/s` |

代入实际数字：

| 上下文 | KV 大小 | recompute | swap 往返 | 谁赢 |
|---|---|---|---|---|
| 2K | 240 MB | 0.10 s | 7.5 ms | swap |
| 8K | 0.96 GB | 0.40 s | 30 ms | swap |
| 32K | 3.84 GB | 1.60 s | 120 ms | swap |

纸面上 swap 快 **13 倍**，但 vLLM 默认用 recompute。三个原因：

| 原因 | 说明 |
|---|---|
| **CPU 内存贵** | 3.84 GB/请求 × 数十个被抢占请求 = 几百 GB 主机内存 |
| **PCIe 是共享资源** | 多个 swap 并发会互相拖慢，延迟从 30 ms 涨到数百 ms |
| **批处理摊薄** | 10 个被抢占请求一起重跑 prefill，单请求代价降到 1/5 以下 |

### 5.2 怎么选

| 场景 | 选择 |
|---|---|
| 单序列、短上下文（< 8K） | recompute（默认） |
| 单序列、超长上下文（> 32K）且主机内存充裕 | swap |
| beam search / 多序列组 | swap（要保住多个分支的 KV） |
| 抢占频繁（每秒 >1 次） | 先降 `max_num_seqs`，别急着改抢占策略 |

## 6. 卸载：把 KV 搬到显存之外

### 6.1 谁来做：三种组件形态

"卸载"不是一个开关，而是三种不同的部署形态，复杂度递增：

| 形态 | 组件 | 谁负责搬运 | 典型实现 | 适用 |
|---|---|---|---|---|
| **① 引擎内置** | block manager 自带两级池 | 引擎自己 | `--cpu-offload-gb`、vLLM swap space | 单机，快速试水 |
| **② 外挂连接器** | KV Connector 接口 + 外部存储客户端 | 引擎调接口，外部服务存 | LMCache connector | 希望复用已有存储 |
| **③ 独立服务** | 独立的 KV Store 集群 | 专门的传输层（RDMA（Remote Direct Memory Access）） | Mooncake Store | 跨机共享、全球复用 |

对应的角色分工：

| 角色 | 职责 |
|---|---|
| Scheduler | 决定"这个请求值不值得去远端取"（取比算快才取） |
| Block manager | 执行 evict → 发起 offload 写、发起 fetch 读 |
| Connector / Store client | 序列化、传输、重试、校验 |
| **KV Store 服务** | 存块、按哈希索引、自己再做一层 LRU |
| **平台 SRE** | 配容量、配租户配额、配保留策略 |

### 6.2 一次卸载的完整动作序列

```
① 显存告急，block manager 选中一批可淘汰块
② 判断：这批块值得下沉吗？（命中过 ≥2 次才值得）
③ 值得 → 序列化 KV 页 → 写请求发往 CPU / NVMe / 远端
      不值得 → 直接释放
④ 写成功 → 本地块回 free list，索引表记一条 "hash → 远端位置"
⑤ 新请求到达 → 查本地前缀树 miss → 查索引表
⑥ 命中 → 发起 fetch（RDMA/PCIe）→ 等数据到 → 挂进本地页表
⑦ 未命中 → 老老实实 prefill
```

第 ② 步是最容易被跳过的一步：如果不筛选就全量下沉，
等于把显存压力原封不动转移成网络压力。

### 6.3 什么时候值得：一笔除法

| 传输路径 | 带宽 | 0.96 GB（8K 请求）耗时 |
|---|---|---|
| NVLink | 900 GB/s | 1 ms |
| PCIe 4.0 x16 | 64 GB/s | 15 ms |
| RDMA 400 Gbps | 50 GB/s | 19 ms |

对比重算：8K prefill ≈ 400 ms。

```
收益 = 命中率 × (400 ms − 19 ms) − 传输与存储成本
```

只要命中率超过 10%，下沉就是赚的。 但前提是"这些前缀真的会被再次用到"——
纯随机单轮问答，命中率接近 0，下沉等于白搬。

| 场景 | 前缀复用率 | 值得吗 |
|---|---|---|
| Agent 多轮（同一会话反复带历史） | 高 | ✅ 非常值得 |
| 客服（同一套系统提示 + 工具 schema） | 很高 | ✅ 值得 |
| 一次性文档问答 | 低 | ❌ 不如重算 |
| 代码补全（同一文件反复改） | 高 | ✅ 值得 |

### 6.4 还有哪些手段：不一定要搬

卸载只是"扩容"的一种，同一目标还有四条路：

| 手段 | 做法 | 等效收益 | 代价 |
|---|---|---|---|
| **KV 量化** | FP16 → FP8/FP4 | 容量 ×2 或 ×4 | 精度掉点（第 6 章） |
| **稀疏注意力** | 只保留滑动窗口内 KV | 容量 ×N | 依赖模型结构（第 10 章 §9） |
| **只下沉高频前缀** | 按访问计数筛选 | 传输量 −80% | 需要计数与阈值 |
| **KV 预计算快照** | 离线算好公共提示的 KV，启动时分发 | 冷启动 TTFT −60% | 版本必须严格对齐 |

最后一条特别实用：把"系统提示 + 工具 schema"这 2.5K token 的 KV 离线算好，
新实例启动时直接加载，冷启动的首个请求不用再 prefill。

## 7. 多租户：朴素 LRU 会闯祸

### 7.1 不公平从哪来

前缀缓存是**全局共享**的（否则复用率为零），但 LRU 只看"最近访问"，不看"谁在用"：

```
租户 A 有 10 万活跃会话 → 持续刷新，占满缓存
租户 B 的系统提示 10 分钟没被访问 → 被挤出
→ B 每个请求都重新 prefill 2.5K token
→ B 的 TTFT 从 600 ms 变 1.4 s，A 毫发无损
```

这不是容量问题，是分配问题。 扩容治不了，只会让 A 占得更多。

### 7.2 四种解法对比

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **硬分区** | 每租户独立缓存，互不可见 | 隔离彻底、实现简单 | 碎片浪费，小租户吃不满 |
| **软配额 + 加权淘汰** | 超配额者优先被淘汰 | 利用率高 | 需要配额中心 |
| SLA（Service Level Agreement） 分级 | 金牌租户保底池 | 商业上可解释 | 配置复杂 |
| **租户哈希命名空间** | 缓存键带租户盐 | **安全**（防串号） | 减少跨租户复用 |

实践组合：命名空间（安全）+ 软配额（公平）+ 金牌保底（商业）。

```python
def weighted_evict(candidates, quota):
    # 超出配额的租户，淘汰优先级更高；同优先级下再看 LRU
    return min(candidates, key=lambda n: (quota.over(n.tenant), n.last_access))
```

### 7.3 安全性：跨租户命中 = 数据泄露

这一条比公平性更严重。如果两个租户的提示词**恰好相同**，
哈希就会碰撞到同一个缓存条目——用户在响应里可能看到别人的上下文。

**必须给缓存键加租户盐**：

```python
key = hash(tenant_id_salt + block_tokens)   # 而不是 hash(block_tokens)
```

代价是跨租户零复用。对 ToB 平台这是必须付的成本；对 ToC（单一租户）可以省掉。

### 7.4 谁负责配置，谁负责执行

| 动作 | 角色 | 频率 |
|---|---|---|
| 定配额（单租户 ≤30%） | 平台 SRE | 季度 |
| 下发配额 | 配额中心（第 2 章 §6.2） | 变更时 |
| 执行加权淘汰 | block manager | 每次淘汰 |
| 监控分租户命中率 | 可观测平台 | 实时 |

**分租户命中率是必看指标**：全局 85% 但某租户只有 20%，说明它正在被挤。

## 8. 指标与调参

### 8.1 四个必看指标

```text
vllm:gpu_cache_usage_perc      KV 水位      >90% 要扩或拒绝
vllm:num_preemptions_total     抢占次数      >0/min 说明 batch 太大
prefix_cache_hit_rate          命中率        跌 5 pt 要查
eviction_rate                  淘汰速率      高 = 缓存太小或租户太杂
```

### 8.2 `max_num_seqs` 怎么定

它决定"一个 batch 最多装几个请求"，直接影响会不会频繁抢占：

| max_num_seqs | 单实例并发 | 抢占频率 | 吞吐 | TTFT |
|---|---|---|---|---|
| 64 | 低 | 几乎为 0 | 低（-35%） | 好 |
| 128 | 中 | 低 | 中 | 好 |
| 256 | 高 | 偶发 | **高** | 一般 |
| 512 | 很高 | **频繁** | 反而下降 | 差 |

我们的账：400 GB KV ÷ 0.96 GB（8K 请求）= **416 个上限**。

配 256 时有 40% 余量，但**长请求会吃掉它**：一个 32K 请求占 3.84 GB = 4 个 8K 请求的额度。
峰值时长请求占比升高，等效并发就会突破 416，于是开始抢占。

建议配 256，并把 32K 以上请求路由到独立池（第 11 章）。

## 9. 失败模式

| 现象 | 根因 | 怎么发现 | 怎么修 |
|---|---|---|---|
| 输出到一半突然重来 | 被抢占后 recompute | `num_preemptions_total` 增长 | 降 `max_num_seqs` |
| 命中率缓慢下滑 | 前缀被挤掉 | hit_rate 曲线 | 扩 KV / 加权淘汰 |
| TTFT 偶发 4 s | 冷启动重算 32K | trace 里 prefill 时长尖峰 | 长请求走独立池 |
| 缩容后零星 500 | 全局 KV 索引没下线 | 缩容时间点错误率 | 见第 33 章 §11.4 |
| 某租户特别慢 | 被大租户挤爆缓存 | 分租户 hit_rate | 配额 |
| 显存 OOM | 块表泄漏 | 块总数只增不减 | 查未释放路径 |

第一条最伤体验：用户眼看着字一个个出来，突然停住，然后**从头开始**。

## 10. 验收：七条怎么测

### 10.1 逐条测法

| 检查项 | 怎么测 | 通过标准 |
|---|---|---|
| **抢占率** | 压测 30 min，读 `num_preemptions_total` ÷ 总请求 | <0.1% |
| **前缀命中率** | 跑生产分布流量，读 `prefix_cache_hit_rate` | ≥85% |
| **KV 水位** | 观察 `gpu_cache_usage_perc` 的 p95 与峰值 | 稳态 <85%，峰值 <95% |
| **块泄漏** | 24 h 长稳，前后对拍 `total_blocks − free_blocks` | 差值不增长 |
| **租户公平** | 造一个大租户 + 三个小租户，跑 1 h | 单租户 ≤30%，小租户命中率 ≥60% |
| **淘汰正确性** | 在 `free_node()` 加断言 `ref == 0` | 0 次触发 |
| **版本切换** | 见 10.2 | 0 次跨版本命中 |

前六条都能靠跑和看指标完成，**第七条必须专门设计测试**，而且它一旦出错是静默的。

### 10.2 版本切换：什么叫"旧 KV 被新权重复用"

#### 一个具体的坏例子

```
10:00  模型 v1 上线，前缀缓存里存了 [系统提示] 的 KV（v1 权重算的）
10:30  灰度 v2，5% 流量打到新实例
10:31  新实例收到请求，前缀哈希命中 → 从共享 KV 池取回那段 KV
10:31  新实例用它跑 decode —— 但这 KV 是 v1 的权重算出来的
```

结果：不报错、不崩溃、不超时，只是输出开始变得奇怪——
答非所问、格式错乱、偶尔胡说。而且**不可复现**（换台机器就不出现）。

> 这就是"脏命中"（dirty hit）：拿旧权重的 KV，当新权重的用。

#### 它比崩溃可怕在哪

| 维度 | 崩溃 | 脏命中 |
|---|---|---|
| 发现速度 | 秒级 | 天级（靠用户投诉） |
| 定位难度 | 有堆栈 | 无痕迹 |
| 影响面 | 全部失败，立刻回滚 | 部分答错，还在灰度里 |
| 数据后果 | 请求失败可重试 | **错误答案已经发出去了** |

#### 四种会触发混跑的场景

| 场景 | 为什么会混 |
|---|---|
| 灰度发布新旧实例并存 | 两版实例共享同一个 KV 池 |
| 滚动更新 | 旧 Pod 还没退，新 Pod 已经开始接流量 |
| 多模型共池 | 大小模型共用一套前缀缓存服务 |
| 回滚 | 回滚到 v1，但缓存里已经混进了 v2 的块 |

#### 三层防御，缺一不可

① 键层：缓存键必须带权重指纹

```python
key = sha256(
    model_weight_sha +      # 不是模型名，是权重的指纹
    tokenizer_version +     # 分词器变了 token 就变了
    tenant_salt +           # 防跨租户（见 §7.3）
    block_tokens
)
```

**用模型名不够**——`deepseek-v4.1` 这个词在打了补丁之后还是同一个名字，但权重已经变了。

② 实例层：灰度期间物理隔离

```
v1 实例 → v1 KV 池
v2 实例 → v2 KV 池
两组之间不共享，灰度结束后统一清理
```

③ 数据层：上线即失效

```python
def on_model_activate(new_version):
    kv_store.delete_prefix(f"kv:{old_version}:")   # 批量按版本前缀清
    assert kv_store.count(f"kv:{new_version}:") == 0
```

这是全书唯一该用"过期"的地方：不是时间过期，是版本过期（§4.2）。

#### 怎么验证：三个层次的测试

```python
# ① 单元测试：同一段 token，两版必须 miss
def test_no_cross_version_hit():
    pool = FakeKVPool()
    pool.put(version="v1", tokens=[1, 2, 3], kv=make_kv())
    assert pool.get(version="v2", tokens=[1, 2, 3]) is None

# ② 集成测试：灰度期间打探针
def probe_dirty_hit():
    # 用一个已知 prompt 分别打 v1 / v2，比对首 token 概率分布
    p1 = run(v1, PROMPT).logprobs[:10]
    p2 = run(v2, PROMPT).logprobs[:10]
    assert divergence(p1, p2) < 0.01 or KNOWN_DIFF

# ③ 端到端：50 条黄金用例在新版上重跑
assert golden_pass_rate(v2) >= golden_pass_rate(v1) - 0.02
```

#### 一个数字：污染窗口有多大

```
灰度 5% × 7,000 QPS × 10 分钟 = 21 万次请求
```

发现得晚 10 分钟，就是 21 万个可能答错的答案已经发出去了。

#### 运行时怎么发现"已经在脏命中"

| 信号 | 正常 | 异常 |
|---|---|---|
| 命中率 | 平稳 | **突然跳升**（新旧共享了缓存） |
| 输出长度分布 | 稳定 | 突变 |
| 困惑度 | 稳定 | 上升 |
| 拒答率 | 稳定 | 上升或归零 |

第一条最直接：灰度期间命中率莫名变高，就是跨版本共享的信号。

## 11. 备选方案：如果不这么做会怎样

| 备选做法 | 代价 | 为什么没成主流 |
|---|---|---|
| **预分配最大长度**（PagedAttention 之前） | 按 32K 预留 → 实际用 2K 时浪费 94% 显存 | 并发上不去 |
| **连续分配 + 搬移** | 每次扩容要拷贝整段 KV | 拷贝成本随长度平方增长 |
| **固定块但不共享** | 无前缀复用 | 命中率 0，等于没有缓存 |
| **全量下沉 CPU** | 每次 decode 都过 PCIe | 带宽被打爆，TPOT（Time Per Output Token） 从 25 ms 涨到 200 ms+ |
| **不分页 + 大页（2 MB）** | 内部碎片 | 短请求浪费，长请求仍不连续 |

PagedAttention 赢在"间接层"：物理可以不连续，逻辑连续由 block table 保证。
这个思路和操作系统的虚拟内存完全同构——只是页大小从 4 KB 变成了 1.92 MB。

替代路线里唯一有竞争力的是 vAttention（动态显存 + CUDA VMM API 直接映射），
它省掉了 block table 的软件开销，但要求驱动与硬件支持，可移植性差。

## 12. 收口

> **KV 的生命周期里没有"过期"，只有"不够用"。
> 淘汰是容量问题，抢占是并发问题——把两者混在一起调，永远调不对。**
