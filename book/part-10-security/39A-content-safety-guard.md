## 1. 问题：一句"全网最低价"引发的下线

售后 Agent 上线两个月，被投诉到市场监管。原因是给某个用户的回答里出现了"我们是全网最低价，保证比任何平台都便宜"——这属于绝对化用语，违反广告法。

查日志才发现，这句不是模型自己编的，是商品详情页里商家自己写了"全网最低价"，Agent 在回答"能便宜点吗"的时候把它引用了。

三个问题同时暴露：

| 问题 | 表现 |
|---|---|
| 提示词写了禁止项，但没兜住 | 安全边界里明确写了"不使用绝对化用语" |
| 没有输出侧校验 | 模型输出了违规表述，直接返回给用户 |
| 没有离线回溯 | 同类商品有 300 多个，两个月无人发现 |

这一章讲的就是怎么把这三件事补上：**在线怎么拦、离线怎么发现、守卫模型怎么设计**。

## 2. 守卫模型是什么

先说清概念。**守卫模型（Guard Model）是一个独立的小模型，专门判断"这段输入或输出该不该放行"。**

它和第 39 章的威胁模型不是一回事：

| | 威胁模型（第 39 章） | 守卫模型（本章） |
|---|---|---|
| 是什么 | 一张分析表，列出谁会怎么攻击 | 一个跑在推理链路上的分类器 |
| 产出 | 攻击面与防御点 | 放行 / 拦截 / 标记 |
| 运行方式 | 人写，季度更新 | 每请求调用，毫秒级 |
| 失败表现 | 漏掉某个攻击面 | 误杀或漏杀 |

守卫模型不是"内容审核 API"。商用审核 API 判的是通用违规（色情、暴力、政治），而你的业务违规是"绝对化用语""超出政策的承诺""虚假原价"——这些通用 API 判不出来，必须自己训。

## 3. 三层防御

| 层 | 手段 | 延迟 | 误杀率 | 漏杀率 | 覆盖 |
|---|---|---|---|---|---|
| L1 规则 | 正则、关键词、句式 | 1 ms | 3%–8% | 40%–60% | 显性违规词 |
| L2 小模型 | 0.5B 分类器 | 30 ms | 1%–3% | 15%–25% | 语义级违规 |
| L3 大模型 | 7B 生成式审核 | 200 ms | 0.5%–1% | 5%–10% | 复杂判断 |
| 人工 | 抽检 | 分钟 | — | — | 兜底 |

三层的组合方式是**并联 + 条件级联**，不是纯串联也不是纯并联：

```
L1 与 L2 同时跑同一段内容（可并行，省 1 ms）
  → 取两者里较严的结论（命中即拦，都放行才放行）
  → 只有 L2 判"可疑"的那 3%–5%，才触发 L3 复核
```

L1 和 L2 是**并联**：两个判据看同一份输入，结论取 max，谁命中都拦。
L2 到 L3 是**级联**：L3 只处理 L2 的存疑样本，不是每一条都跑。

这个结构解决的问题是：L1 快但粗（漏 40%–60%），L2 准但慢 30 倍，L3 最准但慢 200 倍。并联前两层能同时拿到"快"和"准"，级联第三层能把 200 ms 的代价摊到 5% 的请求上。

为什么要三层而不是直接上 L3：**延迟**。L3 要 200 ms，而首 token 预算只有 800 ms，占了四分之一。所以 L3 只能用在"L2 标记可疑"的少数请求上（约 3%–5%），平均延迟增加约 10 ms。

### 3.1 每层的职责边界

| 层 | 管什么 | 不管什么 |
|---|---|---|
| L1 | "最低价""第一""唯一""保证"这类词 | "比任何平台都便宜"这种变体 |
| L2 | 语义等价、意图判断、超范围 | 需要专业知识才判的（如证型是否匹配）|
| L3 | 复杂上下文、多轮累积违规 | 实时性要求高的场景 |

L1 的边界最清楚：**它只能抓显性词**。"最低价"能抓，"比任何平台都便宜"抓不到——后者要 L2。

## 4. 守卫模型怎么设计

### 4.1 先定任务形态

三种可选，成本差 10 倍：

| 形态 | 输出 | 模型 | 延迟 | 适用 |
|---|---|---|---|---|
| 二分类 | 违规/正常 | 0.5B | 30 ms | 单一违规类型 |
| 多分类 | 违规类型 | 0.5B–1B | 35 ms | 5–10 类违规 |
| 生成式 | 判定 + 理由 | 7B | 200 ms | 需要解释、需要引用条款 |

多数场景选第二种。生成式的价值在"能告诉你为什么违规、引用了哪条规则"，适合做 L3 复核和人工辅助，不适合做在线第一道。

### 4.2 训练数据从哪来

这是守卫模型最难的一步——**你没有标注数据**。

四个来源，按可用性排：

| 来源 | 量 | 质量 | 怎么拿 |
|---|---|---|---|
| 规则命中的样本 | 中 | 高（正样本）| L1 的命中记录 |
| 用户投诉/申诉 | 低 | 极高 | 客服工单 |
| 人工构造的对抗样本 | 低 | 高 | 安全团队红队 |
| 大模型标注 + 人工抽检 | 高 | 中 | 用 L3 打标，人抽 10% |

第三行最容易被忽略。**红队构造的对抗样本是唯一能提前发现新攻击面的方式**——等线上出事故再补，代价是下线。

一个可用的启动量：**每类违规 2,000 条正样本 + 10,000 条负样本**。少于这个量，0.5B 模型学不动。

第 4 行（大模型标注 + 人工抽检）是唯一能规模化拿到数据的路，但流程要说清，否则训出来的模型不能用。五步：

**第一步，用 L3 打标。** 拿 10,000 条真实样本（从线上摘要里采样），让 7B 模型逐条判"是否违规 + 违规类型 + 置信度"，输出结构化结果。

**第二步，分层抽样。** 不能随机抽——违规样本占比通常只有 3%–5%，随机抽 1,000 条里只有 30 条违规样本，不够验证。要按"违规类型 × 置信度"分层，每层抽 100–150 条。

**第三步，人工判对错。** 安全团队逐条看，标"同意 / 不同意 / 说不清"。关键是要**独立判断**，不能看着大模型的结论改——否则测的是"人是否同意"，不是"判得对不对"。

**第四步，算一致率。** 用 Cohen's Kappa，不是简单准确率（因为类别不平衡）：

| Kappa | 含义 | 能不能用 |
|---|---|---|
| ≥ 0.8 | 高度一致 | 可用，标出来的数据直接训 |
| 0.6–0.8 | 中等 | 要改提示词或补规则再标 |
| < 0.6 | 差 | 大模型的判定标准和你不一样，不能用 |

**第五步的价值在于：它同时产出了两样东西——可用的标注数据，和一份"人和模型判断分歧在哪里"的清单。后者对改规则、改提示词比数据本身更有用。

一个常见误区是跳过第二步直接随机抽。违规样本只占 3%–5%，随机抽 1,000 条只能抽到 30–50 条正样本，Kappa 的置信区间会宽到没有意义。分层抽样是让每一类都有足够样本，代价是要先知道类别分布。

第五步，不一致的回流。** Kappa 低于 0.8 的样本里，人工写清楚"为什么不同意"，这些说明就是下一版标注提示词的修改依据。

做完一轮，10,000 条里大约 9,000 条可用（900 条人工修正、100 条丢弃）。这个量刚好够训 0.5B 分类器。

成本估算：10,000 条 × 7B 审核（约 0.3 分/条）= 3,000 分 = 30 元；人工抽 1,000 条 × 30 秒 = 8.3 小时。**一轮不到 10 人时，产出 9,000 条标注数据**——比雇人从零标 10,000 条（83 小时）便宜十倍。


### 4.3 评估指标不是准确率

守卫模型的评估和普通分类器不同，因为**误杀和漏杀的代价不对称**：

| 指标 | 定义 | 目标 |
|---|---|---|
| 误杀率 | 正常内容被拦的比例 | < 2% |
| 漏杀率 | 违规内容被放行的比例 | < 5% |
| 延迟 p99 | 判定耗时 | < 50 ms |

误杀率高会赶走正常用户（"怎么什么都拦"），漏杀率高会出事。两个都重要，但**调节阈值时优先保误杀率**——因为漏杀的后果是延迟的（可能几个月后才发现），误杀的后果是立刻的（用户当天就投诉）。

这也解释了为什么第一层用规则：规则误杀率 3%–8% 偏高，但它的命中可以**只标记不拦截**，交给 L2 判断。

### 4.4 多租户：一套模型还是多套

| 方案 | 优点 | 缺点 |
|---|---|---|
| 一套通用模型 | 维护成本低 | 不同行业规则冲突 |
| 每行业一套 | 精准 | 训练数据要按行业分 |
| 一套 + 租户规则层 | 折中 | 规则层要能配 |

推荐第三种：模型通用，规则租户可配。售后的"绝对化用语"和物流的"时效承诺"是同一类问题（夸大宣传），模型能共用，只是关键词表不同。

## 5. 性能：30 ms 从哪来，怎么保住 TTFT

### 5.1 延迟分解

一条请求进网关后，防御的耗时：

| 步 | 在哪 | 耗时 |
|---|---|---|
| 字符粗估 | 网关进程内 | 0.001 ms |
| tokenize | 网关进程内（Rust） | 2 ms |
| 结构化裁剪 | 网关进程内 | 0.01 ms |
| 重复率 MinHash | 网关进程内 | 2 ms |
| **守卫模型** | **独立 GPU 服务** | **30 ms** |
| 拼接 | Harness | 0.001 ms |

34 ms，其中守卫模型占 88%。

### 5.2 首 token 延迟预算

| 环节 | 基线 | 加防御 |
|---|---|---|
| 客户端到网关 | 7 | 7 |
| 裁剪、检测、审核 | 0 | 34 |
| RAG 检索 | 180 | 180 |
| 排队 | 50 | 50 |
| prefill（缓存前缀）| 15 | 15 |
| **末尾纪律 30 token 的 prefill** | 0 | **2.7** |
| **合计** | **258** | **295** |

第四行是唯一让 prefill 变长的地方：末尾那 30 token 在变量之后，位置每次都不同，**不命中缓存**，必须现算。30 × 0.09 ms = 2.7 ms。前面 1,230 token 的静态前缀命中率不变，仍是 15 ms。

800 ms 预算用掉 37%，还剩 505 ms。

### 5.3 守卫模型不影响 TPOT（Time Per Output Token）

TPOT 是 decode 阶段每 token 的间隔，守卫模型在 prefill 之前就结束了。唯一例外是过载时的抢占，那是第 25 章的机制。

### 5.4 什么时候这套不够

换成 7B 生成式审核（200–500 ms）：

```
258 + 450 = 708 ms，只剩 92 ms
```

一次抖动就破线。三条出路：

| 出路 | 做法 | 代价 |
|---|---|---|
| 上调 SLO | TTFT 从 800 提到 1,500 ms（SLO 同步放宽） | 体验变差 |
| 异步审核 | 先返回，后台判，命中就撤回 | 医疗场景不可撤回 |
| 只审 L2 可疑的 | 5% 请求走 L3，平均只加 10 ms | 漏杀率略升 |

第三条是通用解：**用 5% 的覆盖率换 90% 的延迟节省**。

### 5.5 真正威胁 TTFT 的不是守卫

```
守卫开销：   34 ms
缓存命中与否：255 ms
```

把命中率从 0 提到 85%，比砍掉全部防御划算 7 倍。所以优先级是：

| 优先级 | 做什么 | 收益 |
|---|---|---|
| 1 | 提示词结构改对（静态前置）| 省 180 ms |
| 2 | 预热常见前缀（第 7 章）| 冷启动 270 → 15 ms |
| 3 | 削减守卫开销 | 最多省 34 ms |

**不要为了省 30 ms 去掉守卫**——那是拿 34 ms 换一次下线。

## 5.6 守卫服务怎么部署

守卫模型是独立服务，不是嵌在网关里的一个函数。三个理由：

| 理由 | 说明 |
|---|---|
| 它是 GPU 推理 | 0.5B 模型装不进网关的 CPU 进程 |
| 它要独立扩缩容 | 拦截率升高时，守卫的负载先涨 |
| 它要独立灰度 | 换模型版本不能带着主服务一起发 |

部署形态：

```
网关 ──gRPC──> 守卫服务（N 副本）──> 模型（0.5B）
                    │
                    └─ 缓存：相同输入的判定结果（LRU，60 秒）
```

**缓存很重要。** 同一段输入在 60 秒内重复送审很常见（重试、多轮），判定结果缓存能把守卫的 QPS 降 30%–50%。

四个运行参数：

| 参数 | 值 | 说明 |
|---|---|---|
| 超时 | 50 ms | 超过就走 fail-open/close |
| 并发上限 | 每副本 200 | 超过就排队 |
| 降级 | 规则兜底 | 守卫全挂时只跑 L1 |
| 采样 | 1% 全量存 | 给离线训练用 |

第三行最关键：**守卫服务挂了不能让主链路挂**。降级策略是"只用规则层"，误杀率不变、漏杀率升到 40%，但服务可用。

这和第 25 章的分层是同一个思路：**任何单点都允许失效，只要失效时是降级而不是崩。**

## 6. 持续进化：守卫模型多久重训一次

守卫模型会衰减。攻击手法在变，新的违规变体每季度都会出现。三个机制保它不旧。

### 6.1 数据闭环

```
在线拦截/标记 → 摘要进 Kafka → 离线大模型复核 → 人工抽检
            → 新的正样本 → 进训练集 → 重训 → 灰度
```

周期：**数据每日入库，模型每月重训，规则每周更新。**

为什么模型不能每周重训：训练本身几小时，但评估、灰度、回归要一周。而规则（L1）可以每周改，因为它没有训练成本。

### 6.2 漂移监控

守卫模型最危险的不是"判错"，是"悄悄失效"。三个监控指标：

| 指标 | 正常 | 异常说明 |
|---|---|---|
| 拦截率 | 3%–5% | 突然降到 1% → 模型失效或被绕过 |
| 误杀率（人工抽检）| < 2% | 升到 5% → 阈值太严 |
| 输入分布 | 稳定 | 长度/类型突变 → 业务变了，模型要重训 |

第二个靠人工抽检：每周抽 200 条被拦截的，人工判有多少是误杀。这个是唯一可信的误杀率来源。

### 6.3 红队常态化

等线上出事故再补，代价是下线。所以要有主动找问题的机制：

| 方式 | 频率 | 产出 |
|---|---|---|
| 内部红队 | 每月 | 20–50 条新对抗样本 |
| 外部众测 | 每季度 | 100+ 条 |
| 监管通报跟踪 | 持续 | 同类产品的处罚案例 |

第三行最实用：**看同行被罚什么，就补什么规则**。这是最便宜的威胁情报。

## 7. 一个完整的落地清单

| 项 | 内容 | 优先级 |
|---|---|---|
| L1 规则 | 显性违规词表 + 正则 | P0 |
| L2 模型 | 0.5B 多分类，每类 2,000 正样本 | P0 |
| 输出校验 | JSON Schema + 业务规则 | P0 |
| 离线审计 | 1% 采样 + 大模型复核 | P1 |
| L3 复核 | 7B，只审 L2 可疑的 5% | P1 |
| 红队 | 每月一轮 | P1 |
| 漂移监控 | 拦截率/误杀率/分布 | P1 |

前三项不做完，不要上线。

## 8. 失败模式

| 现象 | 根因 | 怎么发现 | 怎么修 |
|---|---|---|---|
| 违规内容上线两个月才发现 | 没有离线审计 | 事后才知道 | 补 1% 采样 |
| 正常用户被批量拦截 | 阈值太严 | 误杀率监控 | 降阈值，改由 L2 判 |
| 守卫模型拦截率从 4% 掉到 1% | 模型衰减或被绕过 | 拦截率曲线 | 重训 + 红队 |
| 加了守卫 TTFT 破线 | 用了 7B 同步审 | TTFT p95 | 改异步或只审可疑 |
| 同一内容 A 租户拦 B 租户放 | 规则没隔离 | 比对两个租户 | 规则按租户配置 |
| 提示词说一套校验做一套 | 两处维护 | 全量失败 | 从同一 schema 生成 |

第六行最常见：提示词写"缺失填 null"，校验却断言不能为 null——模型永远重试，永远失败，团队以为模型不听话。

## 9. 什么情况下这些结论不成立

| 结论 | 推翻条件 |
|---|---|
| 守卫模型必须自训 | 业务违规就是通用违规（色情/暴力）时，用商用 API 更划算 |
| 三层防御 | 单一租户、单一场景时，规则 + 输出校验就够 |
| L3 只审 5% | 监管要求全量审核时，只能同步全审并上调 SLO |
| 每月重训 | 业务规则极稳定（如只做格式转换）时，季度重训即可 |

## 10. 验收

1. 能画出你的三层防御，每层说出误杀率、漏杀率、延迟。
2. 能说出守卫模型的训练数据从哪来，每类多少条。
3. 能算出加守卫后的 TTFT，并说明是否在预算内。
4. 能设计漂移监控的三个指标。

## 11. 复盘卡

```
我原来以为…实际…差在：
```

我原来以为提示词里写了禁止项就够了，实际差在没有输出侧校验——模型会照抄输入里的违规词，而提示词管不住这个。
