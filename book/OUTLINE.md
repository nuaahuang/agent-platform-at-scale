## 前言：为什么写这本书

### 给谁

| 读者 | 能拿到什么 |
|---|---|
| 后端/架构师转 AI 平台 | 一条可复制的完整链路：从 GPU 物理到计费对账 |
| 已在做 Agent 产品的团队 | 每一层的失败模式与验收标准，少踩坑 |
| 准备自建模型服务的企业 | 选型矩阵、容量模型、成本结构，可直接改参数复用 |
| 面试/答辩 | 44 章就是 44 个可深挖的技术点 |

### 两种读法

| 读法 | 章节 | 时间 | 目标 |
|---|---|---|---|
| **主线（建立体感）** | 1、2、8、10、11、13、18、20、21、23、25、27、32、33、36、39、41、43 | 2 周 | 能画出全链路并解释每个数字 |
| **全书（参考手册）** | 44 章 + 10A | 18 周 | 能独立设计并落地 |

### 每章固定结构

```
问题（真实故障/需求） → 原理（物理/协议/算法） → 设计（选型与取舍）
→ 数字（可复算） → 代码/配置（可跑） → 失败模式（怎么坏）
→ 验收（怎么证明对了） → 复盘卡（四行）
```

### 三条承诺

1. **每个数字可复算**：配套 `labs/` 脚本，改参数重跑；
2. **每个选型有 ADR**：选了什么、否了什么、什么条件下会推翻；
3. **每个组件可替换**：接口用标准协议，不锁死厂商。

## 全书贯穿

1. **案例**：电商售后 Agent（订单/物流/退款/审批），纯教学构造，不映射任何真实产品；
2. **账本**：`labs/calc.py` 贯穿全书，每章回填参数；
3. **代码**：`platform/` walking skeleton，每部分一个可运行里程碑。

## 关键补充 1：传统互联网模式映射（第 2 章）

| 经典模式 | 在 AI 服务里 | 结论 |
|---|---|---|
| 无状态水平扩展 | GPU 有状态（KV、前缀树），必须路由亲和 | **变形** |
| 连接池 | 到引擎的 gRPC/HTTP 池仍然必要 | 复用 |
| 本地/分布式缓存 | 响应缓存 → KV/前缀缓存；语义缓存慎用（错答风险） | **变形** |
| 消息队列削峰 | GPU 排队无法"先存后算"，只能准入控制 | **失效** |
| 限流 | 从 QPS 变为 token/s + 并发会话数 | **变形** |
| 熔断降级 | 降级目标是"更小的模型/规则/人工" | **变形** |
| 多活/单元化 | cell 而非全局多活，KV 不跨区 | **变形** |
| 分库分表 | 会话按 tenant 分片，事件按时间分区 | 复用 |
| 幂等 | 工具调用有副作用，比传统写接口更关键 | 复用+ |
| 灰度发布 | 模型/Prompt/工具**三套**版本 | **扩展** |
| 压测 | 不能只按 QPS，要按 token 长度分布 | **变形** |
| 重试 | 重试放大 GPU 与 token 成本，必须预算化 | **慎用** |

## 关键补充 2：契约层五条（第 24 章）

| 契约 | 不定义会怎样 |
|---|---|
| 流式取消 | 用户关页面，引擎还在 decode，GPU 白烧 |
| 错误码语义 | 429 被当 500 重试，故障放大 3 倍 |
| 超时预算 | 应用 60s、引擎 55s，请求白算还占卡 |
| 版本矩阵 | Prompt v3 配模型 v2，指标全绿质量掉了 |
| 计量口径 | 两侧 token 数对不上，对账永远差 3% |

## 关键补充 3：扩缩容的三个数（第 33 章）

| 事实 | 数值 | 推论 |
|---|---|---|
| 扩容耗时 | 8–15 min | 反应式扩容在数学上来不及 |
| 日峰谷比 | 4×（1736 → 7000 QPS） | 必须预测式 + 预热池 |
| 缩容 drain | ≥ 9 s（最长请求） | 缩容比扩容更需要谨慎 |
