# 第 25 章 · 全链路背压与准入控制：压力怎么传，谁有权拒绝

> 读完你能回答：
> ① 从 8,000 QPS 到雪崩，中间那 90 秒发生了什么？
> ② 六跳链路里，每一跳该看什么信号、下什么动作？
> ③ 平时在线和离线怎么共池，离线任务凭什么敢用在线卡的余量？
> ④ 撞峰时从第几秒开始动作，每一步谁执行、回收多少？
> ⑤ 恢复为什么要比崩溃慢？

---

## 1. 问题：90 秒从正常到雪崩

一个普通的工作日晚上，流量从 5,000 QPS 涨到 8,000。系统容量是 7,000。

按直觉，超了 14%，应该"慢一点"。实际发生的是这样：

| 时刻 | 现象 | 关键指标 |
|---|---|---|
| T+0 | 流量 8,000 QPS | 引擎 waiting 队列 500 |
| T+10 | 队列涨到 3,000 | TTFT（Time To First Token）p95 从 800 ms 到 1.5 s |
| T+20 | 网关 9 秒超时开始触发 | 超时率 3% |
| T+30 | 客户端自动重试 | 实际到达 9,600 QPS |
| T+45 | 队列 12,000，内存告警 | TTFT p95 超过 9 s |
| T+60 | goodput 从 99% 掉到 40% | 所有请求都在超时 |
| T+90 | 人工限流到 6,000 | 队列开始下降 |
| T+10min | 恢复，但缓存全冷 | 命中率 0，TTFT 仍然 1.9 s |

超了 14%，结果不是"慢 14%"，是**完全不可用**。

三个放大器叠在一起：

第一，队列没有上限。引擎的 waiting 队列默认无界，请求进来就排，排到内存耗尽。

第二，重试放大。客户端 9 秒超时后重试，重试的请求又进队列——实际到达量比真实需求高 20%。

第三，缓存被冲垮。过载时新请求不断挤占 KV 池，把热门前缀的块淘汰掉，命中率从 85% 掉到 20%，每次请求要多算 5 倍 prefill，进一步恶化。

这一章讲的就是怎么在 T+10 秒把这件事掐住，以及平时怎么让卡不闲着。

## 2. 完整链路：六跳，每跳都有闸

先把链路摊开。一条请求从进来到出结果，经过六跳：

```
① 客户端 → ② 接入层 → ③ 网关 → ④ Harness → ⑤ LLM 网关 → ⑥ 引擎/GPU
```

每一跳都有"能不能收"的判断，但判断依据不同：

| 跳 | 责任 | 看什么信号 | 满了怎么办 |
|---|---|---|---|
| ② 接入 | TLS、连接数、地域 | 连接数、带宽 | 拒绝连接 |
| ③ 网关 | 鉴权、配额、路由 | 租户配额、全局 QPS | 429 |
| ④ Harness | 编排、工具、检索 | 工具调用耗时、上下文长度 | 缩短上下文、跳过可选步骤 |
| ⑤ LLM 网关 | 模型选择、重试、批 | 引擎 waiting、KV 水位 | 拒绝 / 降级 / 换模型 |
| ⑥ 引擎 | 调度、KV 分配 | 块池、batch 排队 | 抢占 / 拒绝 |

关键点：**每一跳只能看到自己下游那一格**。网关不知道 GPU 的 KV 水位，引擎不知道租户配额。所以压力必须逐跳往回传，不能指望某一跳"全局最优"。

这也是为什么"在网关配个 7,000 QPS 的令牌桶"没用——它看不见第五跳的队列。

## 2.5 一个能落地的部署拓扑

前面的六跳是逻辑链路。落到物理部署上，每个角色的 pod 数都不是拍的，要从账本推。

### 2.5.1 每个角色怎么算

| 角色 | 单 pod 能力 | 需求来自哪 | 算法 |
|---|---|---|---|
| GPU 推理 | 8 卡，1,666 并发（2K） | 2,512 卡（第 13 章） | 2,512 ÷ 8 = 314 |
| 网关 | 5 万长连接 | 峰值并发连接 | 140,000 ÷ 50,000 ≈ 3，加冗余 6 |
| Harness | 8 核，异步 IO | 每请求 15 ms CPU | 7,000 × 15 ms = 105 核 ÷ 8 = 13，×1.5 = 20 |
| LLM 网关 | 8 核 | 每请求 1.5 ms CPU | 7,000 × 1.5 ms = 10.5 核 → 4 |
| 检索代理 | 1,000 QPS | 每请求一次检索 | 7,000 ÷ 1,000 = 7 → 8 |
| 工具代理 | 800 QPS | 40% 请求调工具 | 2,800 ÷ 800 ≈ 4 |

网关那个数字值得解释。它不按 QPS 算，按**长连接数**算：

```
峰值并发连接 = 7,000 QPS × 20 秒平均驻留 = 140,000
单 pod 承载 5 万连接（16 GB 内存，每连接约 50 KB）
→ 3 个 pod 够用，加 N+1 和灰度并行 = 6 个
```

如果按 QPS 算，2 个 pod 就够了——会漏掉连接数这个真正的约束。

Harness 反过来，按 CPU 算：一次请求平均 15 ms 的编排 CPU（多轮循环、JSON 序列化、工具参数组装），7,000 QPS 就是 105 核。

### 2.5.2 结果：356 个 pod，不是 1,000 个

| 角色 | pod 数 | 卡 | 占比 |
|---|---|---|---|
| GPU 推理 | 314 | 2,512 | 88% |
| Harness | 20 | 0 | 6% |
| 检索代理 | 8 | 0 | 2% |
| 网关 | 6 | 0 | 2% |
| LLM 网关 | 4 | 0 | 1% |
| 工具代理 | 4 | 0 | 1% |
| 合计 | **356** | 2,512 | 100% |

**88% 的 pod 是 GPU。** CPU 侧只有 42 个 pod——这个比例很反直觉，因为传统互联网系统里 CPU pod 是绝对多数。

原因是：LLM 服务把绝大部分计算压到了 GPU 上，Harness 只剩编排逻辑。这也是为什么"加机器"在这个系统里几乎总是"加卡"，很少是"加 CPU"。

如果有人跟你说这个规模要 1,000 个 pod，多半是把 sidecar、租户隔离实例、监控组件都算进去了——那些确实存在，但不承担业务流量。

### 2.5.3 三个池怎么分

这里的分配逻辑和第 16 章的容量预留直接相关。峰值并发 140,000，其中预留租户叠加后占 105,000：

| 池 | 服务对象 | 并发 | pod | 卡 |
|---|---|---|---|---|
| 专用池 | 预留租户的保底 | 105,000 | 63 | 504 |
| 在线池 | 非预留租户 | 35,000 | 21 | 168 |
| 弹性池 | 离线任务，峰值可回收 | — | **230** | **1,840** |
| 合计 | — | 140,000 | 314 | 2,512 |

弹性池占了 73%，这是本章最重要的一个设计：**它不是一个"离线专用池"，而是"没有被预留的容量"。** 平时跑离线任务，峰值时逐级回收给在线。

这样一张卡有三种状态，按时间切换：

```
平时    ：专用池 25% 负载跑在线 + 弹性池 100% 跑离线
小高峰   ：弹性池回收 50% 给在线
大高峰   ：弹性池回收 100%，全部给在线
```

把"冗余"和"离线"合成一个池，是利用率从 25% 提到 60% 的关键——第 4 节展开。

### 2.5.4 流量按什么条件落到哪个池

网关收到请求，按四步决策，顺序不能换：

| 序 | 判据 | 目标 | 判错会怎样 |
|---|---|---|---|
| 1 | 租户在预留名单 | 专用池 | 预留租户被挤，违约 |
| 2 | `X-Offline: true` | 弹性池 | 离线抢占在线容量 |
| 3 | 上下文 > 16K | 在线池的长文子集 | 长请求挤占短请求 |
| 4 | 其余 | 在线池 | 默认 |

第一步必须在最前。如果先判"离线"再判"预留"，一个预留租户的离线任务会跑进弹性池——看起来没问题，但它占的额度是从预留里扣的，账就乱了。

### 2.5.5 池内怎么选 pod

选定池之后两件事：亲和性和负载。

**亲和性决定缓存命中率。** 同一租户尽量落到同一批 pod，前缀缓存才能复用。用一致性哈希，但要加容量上限防热点：

```
候选 = ring_hash(tenant_id) 顺时针前 3 个 pod
可用 = 候选里 KV 占用 < 80% 的
结果 = 可用里 waiting 队列最短的
```

"前 3 选 1"同时满足两件事：保留亲和性（多数时候选第一个），又能溢出（第一个满了自动到第二个）。

**会话亲和比分请求亲和更重要。** 同一会话必须落到同一 pod，否则 KV 一次都命中不了。哈希键用 `session_id`，不是 `request_id`。

### 2.5.6 网关配置

一个可用的 Envoy 片段：

```yaml
clusters:
  - name: llm_inference
    type: EDS
    lb_policy: RING_HASH
    ring_hash_lb_config:
      minimum_ring_size: 1024        # 314 pod × 约 3
    circuit_breakers:
      thresholds:
        - priority: DEFAULT
          max_connections: 30000
          max_pending_requests: 420000   # 队列上限（第 9 节）
          max_requests: 140000
    outlier_detection:
      consecutive_5xx: 5
      interval: 10s
      base_ejection_time: 30s
      max_ejection_percent: 30
    subsets:
      - name: dedicated
        filter_metadata: {pool: dedicated}
      - name: online
        filter_metadata: {pool: online}
      - name: elastic
        filter_metadata: {pool: elastic}

routes:
  - match: {prefix: "/v1/chat"}
    route:
      cluster: llm_inference
      hash_policy:
        - header: {header_name: "x-tenant-id"}
      retry_policy:
        retry_on: "5xx"
        num_retries: 1              # 只重试一次，防放大
        per_try_timeout: 9s
```

四个参数值得单独说：

| 参数 | 值 | 为什么是这个数 |
|---|---|---|
| `minimum_ring_size` | 1024 | 314 pod × 3 虚拟节点，分布够均匀 |
| `max_pending_requests` | 420,000 | 队列上限，由 SLO 反推（第 9 节）|
| `num_retries` | 1 | 重试两次会在过载时放大 3 倍 |
| `base_ejection_time` | 30 s | 够实例恢复，又不至于长期少一个 |

### 2.5.7 控制面每 10 秒下发什么

控制面不下发路由（路由是静态的），它下发**配额和降级档**：

```json
{
  "ts": "2026-11-18T15:00:10Z",
  "pools": {
    "dedicated": {"pods": 63, "max_concurrency": 105000},
    "online":    {"pods": 21, "max_concurrency": 35000},
    "elastic":   {"pods": 230, "max_concurrency": 383000}
  },
  "tenants": {
    "tenant-a": {"pool": "dedicated", "quota_qps": 2500, "reserved_conc": 46000},
    "tenant-b": {"pool": "online",    "quota_qps": 1200, "burst": 1800}
  },
  "degrade_level": 0,
  "reject_p2": false
}
```

网关拿到后自己执行：超 `quota_qps` 返 429，`degrade_level` 变了切降级策略，`reject_p2` 为真拒离线。

**控制面不在请求路径上。** 它挂了，网关照旧用上一份下发工作——这是分层的价值和代价：可用性高，实时性差（最多滞后 10 秒）。

### 2.5.8 一次请求的耗时分布

以首 token（TTFT）为目标，看每一跳花多少：

| 跳 | 耗时 | 说明 |
|---|---|---|
| 客户端 → LB | 2 ms | 就近接入 |
| LB → 网关 | 1 ms | 同机房 |
| 鉴权 + 配额 | 3 ms | Redis 查询 |
| 选池 + 选 pod | 1 ms | 内存哈希 |
| → Harness | 2 ms | — |
| RAG 检索 | 180 ms | 向量检索 + 重排 |
| → LLM 网关 | 1 ms | — |
| → 引擎 | 2 ms | — |
| 排队 | 50 ms | 当前水位 |
| prefill | 15 ms | 缓存命中（未命中 270 ms）|
| 首 token | 1 ms | — |
| **合计** | **258 ms** | SLO 是 800 ms |

两个结论：**网关总共只占 7 ms**，优化 TTFT 不该优化网关；**检索 180 ms 是大头**，缓存命中与否差 18 倍（15 ms 对 270 ms）。

### 2.5.9 一个池全挂会怎样

最后看故障：专用池 63 个 pod 全挂。

| 阶段 | 会发生什么 | 谁兜底 |
|---|---|---|
| 0–10 s | outlier detection 摘除失败 pod | Envoy |
| 10 s | 预留租户的请求无处可去 | 网关 |
| 10–20 s | 控制面把租户临时迁到在线池 | 控制面 |
| 20 s+ | 在线池被挤，goodput 下降 | 降级 + 拒绝 P2 |

关键是第三行：**预留池挂了要能把租户临时"降级"到在线池**，而不是直接拒绝。

如果租户配置里把池写死了（`pool: dedicated` 固化在租户表），专用池一挂，三个大租户全部不可用。这是故障演练里最常见的发现。

## 2.6 控制面：数据怎么流回，指令怎么下去

前面说"控制面每 10 秒下发"，但没说数据怎么上来、指令怎么下去、每个 pod 里跑的是什么。这一节补全。

### 2.6.1 五个环节，五种组件

| 环节 | 组件 | 部署在哪 | 频率 | 做什么 |
|---|---|---|---|---|
| 采集 | metrics exporter | 每个 GPU pod 内（sidecar） | 1 秒 | 暴露 waiting、KV、batch、TTFT |
| 聚合 | Prometheus / VM | 监控集群 | 10 秒拉一次 | 算分位数、速率 |
| 检测 | detector | 控制面 pod（2 副本） | 10 秒 | 判阈值，出压力等级 |
| 决策 | planner | 控制面 pod | 10 秒 | 算池配比、租户配额 |
| 下发 | config server | 控制面 pod | 10 秒 | 推 JSON 给订阅者 |
| 执行 | Envoy + LLM 网关 | 各业务 pod 内 | 每请求 | 限流、路由、降级、断连 |

关键：**采集在每个业务 pod 里，检测和决策在控制面，执行又回到业务 pod。** 控制面只是中间的"算账人"，不在请求路径上。

### 2.6.2 数据怎么流回：两条路径

只有一条路会来不及。所以设两条：

| 路径 | 周期 | 走什么 | 用来干什么 |
|---|---|---|---|
| 慢路径 | 10 秒 | exporter → Prometheus → 控制面 | 算全局配比、租户配额 |
| 快路径 | 1 秒 | 网关直连下游 `/healthz/load` | 本地背压、摘除坏实例 |

慢路径负责"该给多少"，快路径负责"现在收不收"。

只有慢路径会怎样：过载发生后最多 11 秒才动作（1 秒采集 + 10 秒周期），雪崩已经成型。

只有快路径会怎样：每个网关只看得到自己那几个上游，弹不回来也放不出去，池子配比永远调不动。

### 2.6.3 回传速率：指标全量，trace 采样

采集量要先算清楚，否则监控自己会把系统压垮。

```
指标：314 pod × 20 个 × 1 次/秒 = 6,280 samples/s
```

这个量很小。Prometheus 单实例能扛 10 万 samples/s，一个实例就够，为了 HA 配两个。

trace 完全不同：

| 方式 | 速率 | 结论 |
|---|---|---|
| 全量 trace | 7,000 QPS × 2 KB = 13.7 MB/s | 不可接受 |
| 1% 采样 | 70 spans/s × 2 KB = 0.14 MB/s | 可以 |

所以规则是：**指标全量上报，trace 按 1% 采样，错误请求 100% 采样。**

错误全采的理由：badcase 是复盘和训练的原料，不能靠运气撞上。1% 的成功采样只用来算分布。

### 2.6.4 指令怎么下去：带版本号的长轮询

下发不是推送，是订阅：

```
网关启动 → 连 config server → 拿当前版本 v42
每 10 秒 → 问"有新版吗" → 有就拉 v43，没有就继续用 v42
```

三个设计点：

**带版本号**。网关拿着 v42 工作，server 知道谁还没升到 v43。出问题时能查"这个网关用的是哪版配置"，比查日志快。

**长轮询而不是短轮询**。7,000 QPS 的系统里，73 个订阅者每 10 秒问一次是 7.3 msg/s，可以忽略。但如果换成每请求问一次，就是 7,000 QPS 的控制流量——第 3.5 节算过这笔账。

**下发失败不影响服务**。server 挂了，网关继续用 v42，只是不再更新。这是分层的价值：控制面不是单点。

### 2.6.5 通知：让 pod 体面退出

回收离线任务时，通知走两条路，一条兜底一条快速。

| 场景 | 机制 | 时机 |
|---|---|---|
| K8s 主动缩容 | SIGTERM + preStop hook | 通用 |
| 控制面主动回收 | 调 pod 的 `/drain` 端点 | 抢峰时 |
| 实例自己过载 | 主动返回 503 | 任何时候 |

`/drain` 的语义：

```
1. 置 draining=true，不再接新任务
2. 等当前任务跑完（grace 10 秒）
3. 超时的强制中断，记 checkpoint
4. 返回 200，控制面确认后回收
```

10 秒的依据：离线请求平均 3–5 秒，10 秒覆盖 95%。

### 2.6.6 抢占：靠断连，不靠协议

抢占在线请求时，LLM 网关不需要什么特殊指令——**直接关闭上游连接**。

```
LLM 网关 → 关闭到引擎的连接
引擎 → 下一个调度周期发现客户端断开
     → abort 该请求 → 释放 KV
```

延迟约一个调度周期（20–50 ms），可以接受。

为什么不用专门的 abort RPC：多一个协议就多一套要维护的一致性。HTTP/gRPC 的断连已经是引擎必须处理的情况（用户关页面就是断连），复用它成本最低。

### 2.6.7 控制的完整闭环

把上面串起来，一次过载的处理是这样的：

```
T+0    引擎 waiting 涨到 3,000
T+0    sidecar 采集到，暴露在 /metrics
T+1    Prometheus 拉到
T+10   控制面查询，detector 判定"压力 L2"
T+10   planner 算出：弹性池从 230 缩到 120，reject_p2=true
T+10   config server 推 v43 给 73 个订阅者
T+11   网关拿到 v43，开始拒离线
T+11   调度器调 110 个 pod 的 /drain
T+21   回收完成，弹性池实际 120
T+21   在线并发余量 110×1,666 = 183,000
```

从积压到回收完成是 21 秒。这就是为什么第 5 节的时序表里，T+20 秒才回收完——**控制回路的固有延迟**。

要把这个延迟压短，只能缩短慢路径的周期（10 秒 → 5 秒），代价是控制面的计算量和下发频率翻倍。

### 2.6.8 控制面自己挂了

| 组件挂了 | 影响 | 兜底 |
|---|---|---|
| Prometheus | 看不到指标，但服务正常 | 双实例 |
| detector / planner | 不再调整，用最后的配置 | 双副本 + 最后已知的良好状态 |
| config server | 网关用旧版本 v42 | 本地缓存 + 版本号 |

**没有任何一个组件挂了会导致服务不可用**——这是设计目标。代价是"出事时反应慢半拍"，而不是"出事时全挂"。

## 2.7 K8s 能覆盖多少，还要自建什么

到这里会有一个自然的想法：这些能力 K8s 是不是都有了？装个 HPA（Horizontal Pod Autoscaler）、配个 readinessProbe 不就行了吗？

答案是 K8s 覆盖了大约四成，剩下六成必须自建。分界线很清楚：

**K8s 管进程，你管请求。**

### 2.7.1 K8s 给得了的

| 能力 | 用什么 | 局限 |
|---|---|---|
| pod 放到哪台机器 | kube-scheduler | 只在启动时决策 |
| 按指标扩 pod | HPA / KEDA（Kubernetes Event-driven Autoscaling） | 周期 15 秒起，粒度是 pod |
| 摘流 | readinessProbe | 只能整 pod 摘，不能按请求 |
| 优雅退出 | preStop + gracePeriod | 够用 |
| pod 级优先级与抢占 | PriorityClass | 抢的是 pod，不是请求 |
| 故障域打散 | topologySpreadConstraints | 够用 |
| 最小可用保证 | PodDisruptionBudget | 够用 |
| 服务发现 | Service / EndpointSlice | 够用 |

这八项是扎实的，尤其 preStop + grace 和 PDB，自研的话要写不少代码。

### 2.7.2 K8s 给不了的

| 能力 | 为什么 K8s 做不了 |
|---|---|
| 请求级限流 | 它的单位是 pod，不是请求 |
| 租户配额 | ResourceQuota 按 namespace，1 万租户管不过来 |
| 请求队列与优先级 | 没有请求队列这个概念 |
| 前缀缓存亲和 | Service 的 sessionAffinity 只到 IP，到不了租户/会话 |
| 池的动态配比 | 没有"池"的概念，只有 label selector |
| 请求级抢占 | 抢占的粒度是 pod |
| goodput | 不认识业务 SLO |
| 预算与预扣 | 不认识钱 |

八个缺口的共同原因：**K8s 的抽象单位是 pod，你的业务单位是请求。**

一个 pod 里同时跑着几百个请求，K8s 看不见它们，也管不了它们。

### 2.7.3 时间尺度决定了分界

| 决策 | 周期 | 谁能做 |
|---|---|---|
| pod 放哪台机 | 分钟 | K8s |
| pod 加几个 | 15 秒–几分钟 | K8s（HPA）|
| 池配比 | 10 秒 | 自建 |
| 请求收不收 | 毫秒 | 自建（网关）|

HPA 的最小周期是 15 秒，而且它扩出来的是 pod——pod 启动要 3–5 分钟（第 33 章）。所以 HPA 永远追不上秒级的流量变化。

这不是 K8s 做得不好，是它的设计目标不同：它管的是"长期状态收敛"，你管的是"瞬时流量分配"。

### 2.7.4 那现成的能买多少

不一定要全自研，中间层有现成件：

| 需求 | 可直接用 | 还要自己做的 |
|---|---|---|
| 限流 | Envoy local ratelimit、Sentinel | 租户维度的配额存储 |
| 服务网格 | Istio | 把租户标签接进路由 |
| 扩缩容 | KEDA、Karpenter | 池配比与回收逻辑 |
| 网关 | Envoy、APISIX | subset 与优先级 |
| 指标 | Prometheus | goodput 的计算口径 |

能买的部分把"通用机制"覆盖了。自研的部分是把这些机制和**你的租户、你的 SLO、你的钱**接起来——这部分没有通用解。

### 2.7.5 一个实际的买单

一个典型团队的分工：

| 模块 | 怎么来 | 工作量 |
|---|---|---|
| K8s 编排 | 直接用 | 0 |
| 网关 | 用 Envoy + 自己写配置 | 2 人月 |
| 限流 | Envoy ratelimit + 自建配额服务 | 3 人月 |
| 控制面 | 自研（检测/决策/下发） | 6 人月 |
| 租户与计费 | 自研 | 8 人月 |
| 引擎改造 | 改 vLLM（waiting 上限、abort） | 3 人月 |

合计约 22 人月，其中 K8s 贡献 0。**差异化的部分全在自研那 22 人月里。**

所以"全部用 K8s"这个说法不成立——K8s 是地基，不是房子。

## 2.8 自研怎么自研

前面说了要自研 22 人月。这个数字要修，而且"自研"也不是从零写。

### 2.8.1 工时：压缩 2.4 倍，不是 10 倍

AI 写代码确实快，但写代码只占工作量的一部分。按五项拆：

| 环节 | 占比 | 压缩比 | 压缩后占比 |
|---|---|---|---|
| 写代码 | 40% | 6 倍 | 7% |
| 写测试 | 20% | 5 倍 | 4% |
| 调试联调 | 20% | 2 倍 | 10% |
| 设计与决策 | 10% | 1 倍 | 10% |
| 灰度与运维 | 10% | 1 倍 | 10% |

加权下来是 0.41，也就是**整体压缩 2.4 倍**。

```
22 人月 → 9 人月
```

还是按模块看一遍：

| 模块 | 传统 | 编码占比 | 现在 |
|---|---|---|---|
| 网关 | 2 | 35% | 0.9 |
| 限流 | 3 | 40% | 1.2 |
| 控制面 | 6 | 35% | 2.7 |
| 租户计费 | 8 | 40% | 3.3 |
| 引擎改造 | 3 | 50% | 1.0 |
| 合计 | 22 | — | **9.0** |

为什么不是 10 倍：`0.4 ÷ 10 = 0.04`，剩下 60% 一点没变——总时间还是原来的 64%。**写代码快了，但你还要调、要测、要灰度。**

真正被压缩的是"从想法到能跑"，没被压缩的是"从能跑到能上线"。

### 2.8.2 网关：不写网关，写配置生成器

不要从零写一个网关。Envoy 已经解决了 TLS、HTTP/2、连接池、重试、负载均衡。

自研的部分只有两块：

| 自研 | 内容 | 难度 |
|---|---|---|
| xDS 控制面 | 把池、租户、配额翻译成 Cluster/Subset/Route | 中 |
| 自定义 filter | 租户标签提取、配额检查、降级标记 | 低（WASM） |

WASM filter 的好处是热更新，不用重编 Envoy。坏处是性能比 C++ filter 差 20%–30%——在 7,000 QPS 下可以接受。

真正的难点不是写代码，是**把业务标签接进路由**：租户 ID 从哪来（header/JWT）、池标签怎么下发、subset 怎么和 EndpointSlice 对齐。

### 2.8.3 限流：三层，难点在一致性

限流分三层，各用不同机制：

| 层 | 机制 | 精度 | 延迟 |
|---|---|---|---|
| 本地令牌桶 | Envoy，进程内存 | 粗（单实例视角） | 0 |
| 全局配额 | Redis Lua 原子扣减 | 准 | 1 RTT |
| 配额分片 | 本地预分配 + 定期对账 | 中 | 0 |

**难点是多网关共享配额。** 两个方案：

| 方案 | 做法 | 代价 |
|---|---|---|
| 每请求查 Redis | 每次 RTT 扣减 | +1 ms 延迟，Redis 成热点 |
| 分片预分配 | 每个网关预领 1/N 额度，用完再领 | 误差 N 个请求，但零延迟 |

7,000 QPS 下每请求一次 Redis RTT 是不可接受的（Redis 单实例约 10 万 QPS，会打满）。所以选分片：6 个网关各预领 1,167 QPS，每 10 秒对账一次。

误差是"某网关提前用完要等对账"，最多浪费几十个请求的额度——比每请求 RTT 划算得多。

### 2.8.4 控制面：四段，难点在控制律

四段代码量都不大，难在参数整定：

| 段 | 干什么 | 代码量 | 难点 |
|---|---|---|---|
| 采集适配 | 拉 Prometheus、转成内部结构 | 300 行 | 无 |
| detector | 算压力等级 | 200 行 | 阈值怎么定 |
| planner | 算池配比与配额 | 500 行 | **控制律** |
| config server | 下发与版本管理 | 400 行 | 一致性 |

planner 是核心。最简单的写法是阈值判断（if 水位 > 80% 就缩），但它会震荡。正确的写法是带回滞的控制器：

```python
def plan(watermark, prev_pool, prev_ts, now):
    # 冷却：调整后 60 秒内不动
    if now - prev_ts < 60:
        return prev_pool
    # 滞回：扩在 60%，缩在 80%
    if watermark < 0.60 and prev_pool < MAX_POOL:
        return min(prev_pool * 1.10, MAX_POOL)   # 阻尼：每次 +10%
    if watermark > 0.80 and prev_pool > MIN_POOL:
        return max(prev_pool * 0.80, MIN_POOL)   # 阻尼：每次 -20%
    return prev_pool
```

三十行代码，但要调三个参数（0.6 / 0.8 / 1.1），每个都要用真实流量曲线试。**这部分 AI 帮不上——它不知道你的流量形状。**

### 2.8.5 租户与计费：事件溯源，不要 CRUD

计费系统的坑全在"账要能对"。用 CRUD 写（update balance set x = x - y）迟早会错，因为并发扣减、重复回调、部分失败。

正确做法是事件溯源（第 19 章）：每次消费写一条不可变事件，余额是事件的物化视图。

| 表 | 内容 | 特性 |
|---|---|---|
| `usage_event` | 每次请求一条，只插不改 | 不可变 |
| `quota_hold` | 预扣记录，可过期 | 有 TTL |
| `balance_view` | 物化视图，可重算 | 派生 |

好处是任何时候都能"重放所有事件，重建余额"，和引擎账对不上就重放一遍找差异。

这一块 AI 写代码快，但**账务规则的边界**（哪些算、哪些不算、退款怎么处理）要人来定，写错了不能靠测试发现，要靠对账。

### 2.8.6 引擎改造：最小 patch

改 vLLM 只改三处：

| 改动 | 为什么 | 风险 |
|---|---|---|
| waiting 队列上限 | 防 OOM | 低 |
| abort 接口 | 支持抢占 | 低 |
| 指标导出 | waiting/KV/batch | 低 |

不要去改调度算法和 kernel。那部分改错的代价是性能掉一半，而且很难回滚。

### 2.8.7 什么不该自研

| 别做 | 为什么 |
|---|---|
| 网关本体 | Envoy 已经十年积累，重写是负收益 |
| 服务发现 | K8s 够用 |
| 指标存储 | Prometheus/VM 够用 |
| 消息队列 | Kafka 够用 |

自研的判据只有一条：**这段代码是否承载你的业务概念（租户、SLO、钱）。** 承载就自研，不承载就用现成的。

## 2.9 开源生态：能买到多少

前面说自研要 9 人月。但 2026 年这个领域已经有成型的三层开源，实际自研量能再降一半。

### 2.9.1 三层生态

| 层 | 代表项目 | 覆盖什么 | 成熟度 |
|---|---|---|---|
| 推理平台 | AIBrix、llm-d、KServe、llmaz、OME、NVIDIA Dynamo | 部署、智能路由、扩缩容、KV 管理、PD 分离 | 中，快速演进 |
| AI 网关 | Agent Router（原 Envoy AI Gateway）、APISIX AI Gateway | 多模型统一 API、配额、failover、用量归因 | 较高 |
| 策略与调度 | OPA、KEDA、Kueue、Volcano | 策略即代码、事件驱动扩缩、批调度 | 高 |

三层的分工是：推理平台管"模型怎么跑"，AI 网关管"请求怎么进"，策略层管"规则怎么表达"。

### 2.9.2 网关层：Agent Router 的配额配置

Envoy AI Gateway 2026 年改名 Agent Router，主体是 Envoy Gateway 之上的一层 CRD 控制面。它的 token 配额能配到这个程度：

```yaml
apiVersion: aigateway.envoyproxy.io/v1alpha1
kind: BackendTrafficPolicy
spec:
  rateLimit:
    type: Global
    global:
      rules:
        - clientSelectors:
            - headers:
                - name: x-tenant-id
                  value: tenant-a
          cost:
            request:
              from: Number
              number: 1
            response:
              metadata:
                # 按 token 计费，而不是按请求数
                - metadataKey: llm_total_token
                  type: TotalToken
                # 或者用 CEL 自定义加权
                - metadataKey: llm_weighted_cost
                  type: CEL
                  cel: "input_tokens + output_tokens * 3"
```

最后那行 CEL 值得看：`input_tokens + output_tokens * 3`——**输入按 1 倍算、输出按 3 倍算**。这正是第 14 章算出来的成本结构，开源项目已经把它做成一行表达式。

这一层能覆盖的：按租户限流、按 token 计量、按权重计费、failover、多模型统一 API。基本等于我们说的"配额闸 + 限流闸"。

### 2.9.3 平台层：AIBrix 做了什么

AIBrix 是 vLLM 生态里的推理平台，2026 年 6 月到 v0.7，几个能力正好对上本书的章节：

| AIBrix 能力 | 对应本书 |
|---|---|
| LLM-aware gateway（按 KV 利用率、队列深度路由）| 第 25 章池内选点 |
| App-tailored autoscaling（按推理指标扩，不是 CPU）| 第 33 章弹性 |
| 高密度 LoRA 动态加载 | 第 6 章多 LoRA |
| 分布式 KV cache | 第 10B 章 |
| PD 分离 | 第 11 章 |
| 异构算力与 SLO 保障 | 第 13 章容量 |

我们的"ring hash 前 3 选 1"和它的 LLM-aware routing 是同一类东西——它是按 KV 占用和队列深度选 pod，我们多了一层租户亲和。

### 2.9.4 还缺什么：五块必须自己写

开源到"配额"为止，再往下是"分账"，这一段没有通用解：

| 缺口 | 为什么开源做不了 |
|---|---|
| 租户分账与计费 | 每家定价模型不同，CEL 能算钱但不能出账单 |
| 池的动态配比（在线/离线共池）| 需要知道"哪些任务可以被打断"，这是业务属性 |
| 请求级抢占 | 开源抢的是 pod，抢请求要改引擎 |
| goodput 口径 | 每家 SLO 定义不同 |
| 预扣与结算 | 涉及财务流程 |

第三条最典型：Kueue、Volcano 都能抢占 pod，但没有哪个项目会去中断一个正在生成的请求——因为它不知道那个请求是 P0 还是 P2。

合计约 8.5 人月，和纯自研的 9 人月差不多——**因为省下来的都是"通用机制"，而剩下的都是"你的业务"**。

这个结果值得记住：开源省掉的是 20 人月里的 17 人月，但最后那 8.5 人月一块都省不掉。

## 3. 压力信号：看五个数，不看 CPU

后端服务通常看 CPU 做扩缩容。LLM 服务不行：GPU 满载是正常状态，推理时本来就该跑满。

五个真正有用的信号：

| 信号 | 从哪取 | 阈值 | 说明 |
|---|---|---|---|
| waiting 队列长度 | 引擎 `Scheduler.waiting` | > 目标等待 × 吞吐 | 最直接 |
| KV 块占用率 | 已用块 ÷ 总块 | > 90% | 接近 OOM |
| TTFT p95 | 滚动 1 分钟 | > 1.5 × SLO（Service Level Objective） | 体验开始崩 |
| goodput | 达标 ÷ 总请求 | < 95% | 最终判据 |
| 拒绝率 | 429 ÷ 总请求 | > 5% | 已经在丢了 |

第三个和第四个一起看：TTFT 涨但 goodput 没掉，是慢了还能撑；goodput 掉了，是已经在丢请求。

**为什么不看 GPU 利用率**：它到 100% 是常态，没有区分度。有区分度的是"排队的人在等多久"。

这些信号要聚合成一个数往下传，否则每跳各看各的会打架。我们的做法是"最差信号主导"：

```
压力等级 = max(队列水位, KV 水位, TTFT 超线幅度, 1 − goodput)
```

取最大，不取平均。因为过载时只要有一项爆了，就必须动作——平均会把单项的爆点抹平。

## 3.5 逐跳传还是集中调度

到这里会有一个自然的疑问：既然压力信号都在，为什么不搞一个统一调度中心，收集所有信号、算一个全局最优解、再下发执行？那样不就不用"每跳自己猜"了吗？

答案是一半对。**五个时间尺度上，只有中间两层适合集中，两头必须分布。**

| 层 | 周期 | 决策什么 | 在哪做 |
|---|---|---|---|
| L1 请求准入 | 毫秒 | 收还是不收这一个请求 | 每个实例本地 |
| L2 实例背压 | 秒 | 降速多少、要不要摘除 | 网关本地 |
| L3 池调度 | 10 秒 | 弹性池扩缩多少 | **集中** |
| L4 集群弹性 | 分钟 | 加卡还是减卡 | **集中** |
| L5 容量规划 | 月 | 总共买多少卡 | 人 |

判据只有一条：**控制回路的周期必须短于被控对象的动态时间尺度。**

队列积压的速度是每秒 1,000 条——等 10 秒再决策，队列已经涨了 1 万。所以 L1 只能本地做，本地判断的延迟是微秒级。

而池子配比的变化是 10 秒级，扩卡是 7–10 分钟级，这些完全来得及集中算。

### 3.5.1 为什么不能全集中

四个理由，从硬到软：

| 问题 | 数字 |
|---|---|
| 延迟 | 中心 RPC 1 ms，每请求多 1 ms，占总延迟 1%–5% |
| 吞吐 | 7,000 QPS × 1 次决策 = 中心要扛 7,000 QPS 的控制流量 |
| 可用性 | 中心挂 = 全站失去准入能力，谁都不能拒绝谁 |
| 数据新鲜度 | 中心看到的是 1–5 秒前的聚合，用它做毫秒级决策就是基于过期状态 |

第三条最致命。准入是"必须永远在线"的能力，把它做成一个需要网络往返的中心服务，等于给全站加了一个单点。

### 3.5.2 为什么不能全分布

反过来，全分布也有三个死穴：

| 问题 | 表现 |
|---|---|
| 打架 | 池子是零和的，A 实例多占一个，B 就少一个，本地决策无法协调 |
| 震荡 | 各实例对"现在多挤"的判断不同，一会儿扩一会儿缩 |
| 说不清 | 出事时没有单一事实来源，复盘只能看一堆局部日志 |

第一条最典型：弹性池缩的时候，如果每个网关都自己判断"我这边压力小了，可以多要一点离线"，十个网关同时要，池子瞬间被抢空。

### 3.5.3 混合怎么落：策略集中，执行分布

```
自下而上：信号上报（异步、聚合、每 10 秒一次）
自上而下：策略下发（配额、阈值、优先级）
本地     ：按策略执行，不等指令
```

具体到三个决策：

| 决策 | 谁定 | 谁执行 | 怎么衔接 |
|---|---|---|---|
| 弹性池多大 | 中心每 10 秒算 | 各实例按新配额 | 下发 `P2_quota` |
| 这个请求收不收 | 本地按配额 | 网关 | 本地队列 + 下发配额 |
| 降速到多少 | 本地看下游 | 网关 | `Retry-After` |

关键在第三列：**中心只下发"允许多少"，不下发"收哪个"**。收哪个是本地的事，因为只有本地知道此刻队列里排的是什么。

### 3.5.4 分布式的老毛病：震荡

集中 + 分布混着用，最容易出的问题是控制环震荡。三个标准解法：

| 手段 | 做法 | 防什么 |
|---|---|---|
| 滞回 | 60% 扩、80% 缩 | 阈值附近抖动 |
| 阻尼 | 每次最多调 10%/20% | 一次调过头 |
| 冷却 | 调完 60 秒内不再调 | 连续调整 |

三个要一起用。只做一个，震荡会以另一种形式出现——只加滞回，会在 2 倍波动时来回切；只加阻尼，会在临界点附近慢慢摇。

### 3.5.5 一个反例

如果真把所有准入集中：

```
7,000 QPS × 1 次中心决策
中心延迟 1 ms → 每个请求多 1 ms
中心需要 7,000 QPS 的处理能力，还要 5 个 9 的可用性
```

这比推理服务本身还难做。所以业界主流的做法都是混合：Envoy 的本地令牌桶 + 全局配额服务（RLS），Kubernetes 的本地限流 + HPA。没有哪个生产系统把准入完全集中。

## 4. 平时调度：让离线任务吃掉余量

这是本章最值钱的部分。前面几章反复算过：在线利用率只有 25%，剩下的 75% 不填就是白买。

先算能填多少：

```
在线峰值需要 2,512 卡
在线平均需要 628 卡（25%）
空闲 = 1,884 卡 × 24 小时 = 45,216 卡时/日
```

如果离线任务能吃掉 80% 的空闲，就是 **36,000 卡时/日**，一年 1,320 万卡时，比现有卡数多出 33% 的算力。

### 4.1 两类任务，两种服务等级

| 类别 | 例子 | 延迟要求 | 可中断 | 计费 |
|---|---|---|---|---|
| 在线 | 客服问答、订单查询 | TTFT ≤ 800 ms | 否 | 按量/预留 |
| 离线 | 历史回刷、意图重分类、评测回放、RL rollout | 分钟到小时 | 是 | 内部结算 |

离线任务的关键属性不是"慢"，是**可以被打断并且能重来**。不能重来的任务不配进这个池子。

### 4.2 池子怎么切：三段式

```
总容量 2,512 卡
├─ 在线池 P0+P1   1,880 卡   保证 SLO，任何情况下不被挤
├─ 弹性池 P2        632 卡   离线任务用，在线压力大时逐级回收
└─（在线池的空闲部分通过"借出"临时并入弹性池）
```

为什么不全给弹性池？因为回收需要时间。如果离线占满了，在线突然涨上来，回收要 10–30 秒，这期间 SLO 已经破了。

留 25% 的在线专用，是为了让"突增"有缓冲。

### 4.3 借出：在线池的空闲怎么给离线用

在线池平均只用 25%，它那 75% 的空闲要能借出去，否则切池没意义。

借出规则三条：

| 规则 | 内容 | 为什么 |
|---|---|---|
| 借用量 ≤ 在线池空闲 × 0.8 | 留 20% 应对突发 | 突发检测有延迟 |
| 借出的实例保持"热" | 不销毁，只换任务 | 回收要在秒级 |
| 借出期间禁止改配置 | 不重启、不换模型 | 重启要 2–3 分钟 |

第三条最容易违反。运维看到离线池在跑，顺手做了个版本升级，结果在线压力一来，那批实例在重启，回收不了。

### 4.4 动态配比：每 10 秒调一次

调度器循环评估在线水位，调整弹性池大小：

```
每 10 秒：
  u = 在线池实际用量 / 在线池容量
  if u < 0.60 and 离线队列非空:
      弹性池 += 10%（从在线池空闲划出）
  if u > 0.80 and 弹性池 > 下限:
      弹性池 -= 20%（回收给在线池）
```

两个设计点：

**滞回带 60%–80%**。如果只用单一阈值（比如 70%），水位在 70% 附近抖动会来回切，每次都触发实例迁移。带宽带回，切一次要等它稳定。

**加 20% 比减 10% 快**。扩离线是缓慢的（怕占太多），收离线是激进的（怕破 SLO）。方向不对称是对的——安全优先。

### 4.5 离线任务的四级可中断性

不是所有离线任务都能随便打断。分四级：

| 级别 | 例子 | 中断代价 | 恢复方式 |
|---|---|---|---|
| L1 | 批量分类 | 丢一条记录 | 重跑这一条 |
| L2 | 评测回放 | 丢一次评测 | 重放这一条 |
| L3 | RL rollout | 丢半条轨迹 | 从 checkpoint 续 |
| L4 | 训练 step | 丢一个 step（30 秒） | 从上一步续 |

回收时按 L1→L4 的顺序，先把便宜的停掉。L4 通常不放在弹性池里——训练一个 step 30 秒，打断的代价比收益大。

### 4.6 离线任务的准入

离线任务不是"来了就放"，要有配额和排队：

| 检查 | 阈值 | 不过怎么办 |
|---|---|---|
| 离线队列长度 | < 2 小时的量 | 拒绝提交，让用户明天再来 |
| 任务截止时间 | 至少还有 2 小时 | 拒绝，或建议走专用池 |
| 单任务规模 | < 弹性池的 30% | 拆批提交 |

第三条很重要。一个占满弹性池的任务会把所有小任务饿死，而且一旦被回收，它自己也白跑。让它拆成小批，既能调度也能续跑。

## 5. 撞峰处理：带秒数的完整时序

上面是平时。现在看真撞峰了怎么办。

前提：检测到在线水位超过 80%，且持续 30 秒。所有动作由调度器自动执行，人只在告警后旁观。

| 时刻 | 触发条件 | 动作 | 执行者 | 回收/影响 |
|---|---|---|---|---|
| T+0 | 在线队列 > 60% 上限 | 告警，停止扩离线池 | 调度器 | — |
| T+5s | goodput 跌破 98% | 停止接新离线任务 | 调度器 | 离线队列冻结 |
| T+10s | 在线队列 > 80% | 开始回收：先停 L1 | 调度器 | 释放约 10% 弹性池 |
| T+20s | 队列仍涨 | 继续回收 L2、L3 | 调度器 | 弹性池归零 |
| T+30s | 排队 > 30 秒 | 降级：关深度思考、截断长回答 | 网关 | 单请求成本降 3.5 倍 |
| T+45s | goodput < 95% | 拒绝 P2 新请求 | 网关 | 只保 P0/P1 |
| T+60s | 仍恶化 | 抢占：P1 让位于 P0 | LLM 网关 | 预留租户优先 |
| T+120s | 仍恶化 | 全局限流到容量 × 0.8 | 网关 | 主动丢 20% |
| 恢复 | goodput > 99% 持续 5 分钟 | 每次放开 10%，间隔 2 分钟 | 调度器 | 渐进恢复 |

这张表有三个设计意图。

**第一，先动离线，后动在线。** 前 20 秒全部在回收离线任务，一个在线请求都还没被影响。这是"用别人的余量扛自己的峰值"。

**第二，降级在拒绝之前。** T+30 秒先降级，T+45 秒才拒绝。降级能让所有人继续被服务（只是差一点），拒绝会让一部分人拿不到服务。顺序反了就是浪费。

**第三，恢复比崩溃慢。** 崩溃用了 120 秒，恢复要 5 分钟起步——因为缓存要重新热起来（第 7 章）。恢复期的限流值要比正常容量低 20%。

### 5.1 通知：让被回收的任务体面退出

回收不是 kill -9。四步：

```
1. 调度器发 drain 信号（标记该实例不再接新任务）
2. 任务完成当前这一条（grace 10 秒）
3. 超时的强制中断，记录 checkpoint
4. 实例回到在线池，重新配权重（如果模型不同）
```

10 秒 grace 的依据：一个离线请求平均 3–5 秒，10 秒能覆盖 95%。

第 4 步容易被忽略：离线池和在线池如果模型不同（一个 8B 一个 200B），回收后要重新加载权重，2–3 分钟。所以**两个池应该用同一个模型**，或者至少让弹性池的实例预装在线模型。

### 5.2 抢占：谁让位于谁

回收是"收回空闲"，抢占是"拿走正在用的"。只有在回收完还不够时才用。

| 优先级 | 谁 | 被抢占的代价 | 抢占顺序 |
|---|---|---|---|
| P0 | 已付费预留 | 不可接受 | 最后 |
| P1 | 按量在线 | 用户等多 30 秒 | 第二 |
| P2 | 离线批处理 | 任务重跑 | 第一 |
| P3 | 内部调试 | 无 | 最先 |

P0 之间不抢占——同样付费的租户没有高低。真到了 P0 之间要抢的地步，说明容量模型错了（第 13 章），该扩卡而不是继续挤。

## 6. 恢复期：比崩溃更难

崩溃是"某个瞬间失效"，恢复是"逐渐回到正常"。恢复期有三个坑。

**坑一：缓存是冷的。** 过载时缓存被冲垮，恢复后命中率从 0 爬回 85% 要 10–20 分钟。这期间 prefill 成本是正常的 5 倍，TTFT 仍然偏高。

**坑二：重试还在来。** 客户端在崩溃期间积压的重试，会在恢复后涌入。所以恢复期的实际到达量高于真实需求。

**坑三：离线任务在抢。** 一旦 goodput 回到 99%，调度器会开始扩离线池——但此刻缓存还没热，扩太快会把在线打回去。

应对是三条：

| 措施 | 参数 | 作用 |
|---|---|---|
| 渐进放开 | 每次 +10%，间隔 2 分钟 | 防止二次冲击 |
| 推迟扩离线 | goodput 恢复后 10 分钟才允许 | 让缓存先热 |
| 恢复期限流 | 正常容量的 80% | 留出重试的余量 |

## 7. 限流按 QPS 还是 token

这是最常被问的问题，答案是**两个都要，用在不同层**。

| 层 | 按什么 | 为什么 |
|---|---|---|
| 网关入口 | QPS | 便宜、快、防突发。此时还不知道 token 数 |
| LLM 网关 | 并发请求数 | 能预估上下文长度，区分长短请求 |
| 引擎 | token/秒 + KV 水位 | 最准，但已经进来了 |

入口按 QPS 防的是"异常流量"（爬虫、攻击、配置错误），特征是请求数异常。

引擎按 token 防的是"容量打满"，而容量是被 token 消耗的。

中间层按并发最实用：

```
并发 = QPS × 停留时间
```

它同时反映请求数和时长，比单独的 QPS 准，又不需要预知 token 数。

## 8. 拒绝的四种语义

拒绝不是只有"返回 503"。语义不同，客户端行为不同。

| 语义 | 状态码 | 客户端该做什么 | 用在哪 |
|---|---|---|---|
| 重试 | 503 + Retry-After | 等 N 秒重试一次 | 临时过载 |
| 降级 | 200 + 降级标记 | 展示降级内容 | 质量可让 |
| 排队 | 202 + 位置 | 轮询或等待 | 异步任务 |
| 永久拒绝 | 429 | 不要重试，改配额 | 超配额 |

`Retry-After` 必须是真数：

```
Retry-After = 当前队列长度 ÷ 服务速率
```

队列 12,000、速率 7,000/秒，就是 1.7 秒。写死了会两头错：写 30 秒但实际 3 秒就好，客户端白等；写 3 秒但实际要 30 秒，重试还是失败，加重拥塞。

## 9. 队列为什么是雪崩放大器

排队看起来温和（不拒绝用户），过载时却在加速崩溃。

用利特尔法则：队列长度 = 到达率 × 等待时间。

```
到达 8,000 QPS，服务 7,000 QPS
净增 1,000/秒
60 秒后队列 = 60,000，等待 8.5 秒——已超过 9 秒预算，注定超时
```

系统仍在为这些注定超时的请求消耗资源。加上重试，到达变 9,600，净增 2,600/秒，翻倍时间从 60 秒缩到 23 秒。

所以队列必须有上限，且由 SLO 反推：

```
队列上限 = 目标等待 × 服务速率 = 60 秒 × 2.8 QPS/卡 × 2,512 卡 = 42 万
```

超过 42 万，新请求的等待必然超过 60 秒，**拒绝比排队好**。

这条上限的作用不是省资源，是止损：把"所有人都慢"变成"一部分人快、一部分人被拒"。

## 10. 配置

三段核心配置（Envoy 风格）：

```yaml
# ① 限流：令牌桶，防突发
rate_limits:
  - actions: [{generic_key: "llm_gateway"}]
    limit: {requests_per_unit: 7000, unit: SECOND}

# ② 排队与并发：防积压
circuit_breakers:
  thresholds:
    - priority: DEFAULT
      max_connections: 20000
      max_pending_requests: 420000   # 队列上限，由 SLO 反推
      max_requests: 140000           # 并发上限，等于峰值并发

# ③ 背压：坏实例摘除
outlier_detection:
  consecutive_5xx: 5
  base_ejection_time: 30s
  max_ejection_percent: 30
```

服务端拒绝时要带真实信息：

```python
def reject_with_retry_after(queue_len, service_rate, goodput):
    wait_s = max(1, ceil(queue_len / service_rate))
    return Response(status=503, headers={
        "Retry-After": str(wait_s),
        "X-Queue-Length": str(queue_len),
        "X-Goodput": f"{goodput:.3f}",
    })
```

后两个头是给运维的：出问题时不用翻日志，看响应头就知道系统在哪一格。

## 11. 失败模式

| 现象 | 根因 | 怎么发现 | 怎么修 |
|---|---|---|---|
| 超 20% 就全崩 | 队列无上限 | 队列无界增长 | 设上限 + 超时 |
| 限流后仍崩 | 重试放大 | 实际到达 > 真实需求 | 关自动重试或加大退避 |
| 离线任务被反复打断 | 弹性池太小 | 中断率 > 30% | 扩大弹性池，或降离线配额 |
| 回收后在线仍不够 | 两个池模型不同 | 回收耗时 2–3 分钟 | 统一模型 |
| 恢复要十几分钟 | 缓存被冲垮 | 命中率曲线 | 恢复期限流更严，先回填 |
| 长请求拖垮整池 | 无隔离 | 按长度看 TPOT（Time Per Output Token） | 长请求独立池 |
| 离线任务饿死 | 大任务占满弹性池 | 队列里小任务等待久 | 单任务上限 30% |
| 网关 429 但引擎还满 | 信号不同步 | 对比两边速率 | 统一信号源 |

## 12. 什么情况下这些结论不成立

| 结论 | 推翻条件 |
|---|---|
| 队列要设上限 | 纯离线批处理，等待无所谓，可以不设 |
| 拒绝比排队好 | 有充足余量且请求可等时，排队更友好 |
| 留 25% 在线专用 | 流量极平稳（无突发）时，可以全部混用 |
| 六跳都有闸 | 单体服务时，两道闸（限流 + 超时）就够 |
| 恢复比崩溃慢 | 缓存命中率很低（<30%）时，恢复也快 |
