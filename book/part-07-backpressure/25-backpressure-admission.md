# 第 25 章 · 全链路背压与准入控制：压力怎么传，谁有权拒绝

> ③ 压力信号该看哪五个数，为什么不是 CPU 和 GPU 利用率？
> ④ 限流按 QPS 还是按 token，两者分别防什么？
> ⑤ 拒绝、排队、降级、抢占，什么情况下该用哪个？

## 1. 问题：90 秒从正常到雪崩

一个普通的工作日晚上，流量从 5,000 QPS 涨到 8,000。系统容量是 7,000。

按直觉，超了 14%，应该"慢一点"。实际发生的是这样：

| 时刻 | 现象 | 关键指标 |
|---|---|---|
| T+0 | 流量 8,000 QPS | 引擎 waiting 队列 500 |
| T+10 | 队列涨到 3,000 | TTFT（Time To First Token）p95 从 800 ms 到 1.5 s |
| T+20 | 网关 9 秒超时开始触发 | 超时率 3% |
| T+30 | 客户端自动重试 | 实际到达 9,600 QPS |
| T+45 | 队列 12,000，内存告警 | TTFT p95 超过 9 s |
| T+60 | **goodput 从 99% 掉到 40%** | 所有请求都在超时 |
| T+90 | 人工限流到 6,000 | 队列开始下降 |
| T+10min | 恢复，但缓存全冷 | 命中率 0，TTFT 仍然 1.9 s |

超了 14%，结果不是"慢 14%"，是**完全不可用**。

三个原因叠在一起：

第一，队列没有上限。引擎的 waiting 队列默认无界，请求进来就排，排到内存耗尽。

第二，重试放大。客户端 9 秒超时后重试，重试的请求又进队列——实际到达量比真实需求高 20%，而系统的处理能力已经饱和。

第三，缓存被冲垮。过载时新请求不断挤占 KV 池，把热门前缀的块淘汰掉，命中率从 85% 掉到 20%，每次请求要多算 5 倍的 prefill，进一步恶化。

这一章讲的就是怎么在 T+10 秒的时候把这件事掐住。

## 2. 为什么单点限流救不了

最常见的做法是在网关配一个令牌桶：7,000 QPS，超过就 429。

它有两个盲区。

**盲区一：QPS 不等于负载。** 7,000 个短请求（200 token）和 7,000 个长请求（8K token）对 GPU 的压力差 40 倍。网关只看请求数，看不出来。

**盲区二：压力产生在下游，网关不知道。** 网关按 7,000 放行，但如果此刻引擎因为 KV 碎片只能跑到 5,000 的等效能力，网关仍然会放 7,000 进来——多出来的 2,000 全部堆在引擎队列里。

所以压力必须从产生的地方往回传，而不是在入口猜。

这就是背压（backpressure）和限流（rate limiting）的区别：

| | 限流 | 背压 |
|---|---|---|
| 依据 | 预设的速率 | 下游的实时状态 |
| 位置 | 入口 | 每一跳 |
| 反应 | 固定 | 随负载变化 |
| 缺点 | 猜不准 | 要协议支持 |

两者都要有，但**只有限流一定会在过载时失效**。

## 3. 压力信号：看五个数，不看 CPU

后端服务通常看 CPU 利用率做扩缩容。LLM 服务不行，因为 GPU 满载是正常状态——推理时 GPU 本来就该跑满。

五个真正有用的信号：

| 信号 | 怎么取 | 阈值 | 说明 |
|---|---|---|---|
| waiting 队列长度 | 引擎内部计数 | > 目标等待 × 吞吐 | 最直接 |
| KV 块占用率 | 已用块 ÷ 总块 | > 90% | 接近 OOM |
| TTFT p95 | 滚动 1 分钟 | > 1.5 × SLO（Service Level Objective） | 用户体验开始崩 |
| goodput | 达标请求 ÷ 总请求 | < 95% | 最终判据 |
| 拒绝率 | 429 ÷ 总请求 | > 5% | 已经在丢了 |

第三个和第四个要一起看。TTFT 涨了但 goodput 没掉，说明只是慢了，还能撑；goodput 掉了，说明已经在丢请求。

第五个是结果，不是原因——它涨起来说明前面四道闸都已经在动作了。

**为什么不看 GPU 利用率**：它到 100% 是常态，没有区分度。真正有区分度的是"排队的人在等多久"。

## 4. goodput：降载的唯一判据

一个容易被忽略的定义问题：什么叫"过载"？

不是吞吐下降——吞吐可能还在涨，但每个请求都超时了，这种吞吐是无效的。

所以判据是 goodput：**在 SLO 内完成的请求占比**。

```
goodput = (TTFT ≤ 800ms 且 TPOT ≤ 50ms 且 端到端 ≤ 9s 的请求数) ÷ 总请求数
```

SLO 是 99.9%，所以 goodput 低于 99.9% 就该动作。但实际用 95% 作为降载触发线，因为 99.9% 太灵敏，一次抖动就触发。

过载时的目标不是"保住吞吐"，是"保住 goodput"。宁可服务 5,000 个都成功的请求，也不要服务 8,000 个里 4,000 个超时的。

## 5. 逐跳背压：三种机制

压力从下往上传，有三种做法。

**机制一：队列水位信号。** 每一跳暴露自己的队列长度和容量，上游按比例降速。

```
上游允许速率 = 上游满速 × min(1, 下游剩余容量 / 下游容量)
```

缺点是滞后：水位涨起来才知道，反应过来已经晚了几秒。

**机制二：显式拒绝。** 下游满了直接返回 503 带 `Retry-After`，上游收到就降速。

优点是准确（下游最清楚自己），缺点是拒绝本身有成本，而且上游如果重试，反而放大。

**机制三：并发上限（连接数/在途请求数）。** 上游对下游维持一个在途请求上限，满了就不发新的。

这是最有效的一种——它不依赖任何信号传递，靠"发不出去"自然形成背压。HTTP/2 的流控、gRPC 的 `max_concurrent_streams` 都是这个思路。

三者组合使用：

| 层 | 用什么 | 为什么 |
|---|---|---|
| 网关 → Harness | 并发上限 | 简单可靠 |
| Harness → LLM 网关 | 并发上限 + 水位信号 | 要提前量 |
| LLM 网关 → 引擎 | 引擎队列上限 + 显式 503 | 引擎最清楚 |
| 引擎内部 | 调度器 waiting 上限 | 防 OOM |

## 6. 五道闸

把上面的机制落到请求路径上，是五道闸，每道管一件事。

| 闸 | 位置 | 判据 | 动作 | 谁受损 |
|---|---|---|---|---|
| ① 配额闸 | 网关入口 | 租户配额（第 16 章） | 429 | 超配额租户 |
| ② 限流闸 | 网关入口 | 全局限速 + 令牌桶 | 429 + Retry-After | 超出部分 |
| ③ 排队闸 | 网关 | 队列长度 vs 上限 | 等待 / 超时拒绝 | 等不及的 |
| ④ 准入闸 | LLM 网关 | 引擎 waiting 队列 | 拒绝 / 降级 | 低优先级 |
| ⑤ 执行闸 | 引擎 | KV 水位 | 抢占 / 截断 | 长请求 |

五道闸的顺序不能乱。配额在最前（商务规则优先），执行闸在最后（最后一道防线）。

每道闸都要能独立回答三个问题：

- 判据是什么数（可观测）
- 超过多少就动作（阈值）
- 动作是什么（拒绝 / 排队 / 降级 / 抢占）

答不出第三个的闸等于没有。

## 7. 限流按 QPS 还是 token

这是本章最常被问的问题，答案是**两个都要，但用在不同层**。

| 层 | 按什么 | 为什么 |
|---|---|---|
| 网关入口 | QPS | 便宜、快、防突发。此时还不知道 token 数 |
| LLM 网关 | 并发请求数 | 能预估上下文长度，能区分长短请求 |
| 引擎 | token/秒 + KV 水位 | 最准，但已经进来了 |

入口按 QPS 的合理性在于：它防的是"异常流量"（爬虫、攻击、配置错误），这些的特征是请求数异常，不是 token 数异常。

引擎按 token 的合理性在于：它防的是"容量打满"，而容量是被 token 消耗的。

中间那层按并发是最实用的折中：

```
并发 = QPS × 停留时间
```

它同时反映了请求数和请求时长，比单独的 QPS 准，又不需要预先知道 token 数。

## 8. 拒绝的四种语义

拒绝不是只有"返回 503"，语义不同，客户端的行为也不同。

| 语义 | 状态码 | 客户端该做什么 | 用在哪 |
|---|---|---|---|
| 重试 | 503 + Retry-After | 等 N 秒重试一次 | 临时过载 |
| 降级 | 200 + 降级标记 | 展示降级内容 | 质量可让 |
| 排队 | 202 + 位置 | 轮询或等待 | 异步任务 |
| 永久拒绝 | 429 | 不要重试，改配额 | 超配额 |

第一条要带 `Retry-After` 且**必须是真的**。写 `Retry-After: 30` 但实际 3 秒就好了，客户端会等 30 秒，白等；写 3 秒但实际要 30 秒，客户端重试还是失败，加重拥塞。

那个数字怎么来：

```
Retry-After = 当前队列长度 ÷ 服务速率
```

队列 12,000，速率 7,000/秒，就是 1.7 秒。这个数随队列实时变化，不能写死。

第二条容易被忽略。降级返回 200 比返回 503 对用户友好——用户看到的是"这个问题我需要确认后回复"，不是"服务不可用"。

## 9. 队列为什么是雪崩放大器

排队看起来温和（不拒绝用户），实际上在过载时是加速崩溃的。

用利特尔法则算：队列长度 = 到达率 × 等待时间。

```
到达 8,000 QPS，服务 7,000 QPS
净增 1,000/秒
60 秒后队列 = 60,000
```

队列 60,000 时，新来的请求要等 8.5 秒——已经超过 9 秒的端到端预算，意味着**它们注定超时**。但系统仍然在为它们消耗资源。

更糟的是重试：超时后客户端重试，到达率变成 9,600，净增 2,600/秒，队列翻倍速度从 60 秒变成 23 秒。

所以队列必须有上限，且上限由 SLO 反推：

```
队列上限 = 目标等待时间 × 服务速率
         = 60 秒 × 2.8 QPS/卡 × 2,512 卡
         = 42 万
```

超过 42 万，新请求的等待时间必然超过 60 秒，直接拒绝比排队好。

**这条上限的作用不是"省资源"，是"止损"**——它把系统的状态从"所有人都慢"变成"一部分人快、一部分人被拒"。后者从商业上更好看，从技术上更容易恢复。

## 10. 配置与代码

三道闸的参考配置（Envoy 风格）：

```yaml
# ① 限流：令牌桶，防突发
rate_limits:
  - actions: [{generic_key: "llm_gateway"}]
    limit: {requests_per_unit: 7000, unit: SECOND}

# ② 排队：超时 + 队列上限
circuit_breakers:
  thresholds:
    - priority: DEFAULT
      max_connections: 20000
      max_pending_requests: 420000
      max_requests: 140000

# ③ 背压：上游失败就摘除
outlier_detection:
  consecutive_5xx: 5
  base_ejection_time: 30s
  max_ejection_percent: 30
```

三段分别对应：防突发、限积压、隔离坏实例。

`max_pending_requests: 420000` 就是上面算的队列上限。`max_requests: 140000` 是并发上限（等于峰值并发）。两个数一起卡住"进来多少"和"堆多少"。

服务端返回 503 时的响应头要带真实等待时间：

```python
def reject_with_retry_after(queue_len, service_rate):
    wait_s = max(1, ceil(queue_len / service_rate))
    return Response(status=503, headers={
        "Retry-After": str(wait_s),
        "X-Queue-Length": str(queue_len),
        "X-Goodput": f"{goodput:.3f}",
    })
```

`X-Queue-Length` 和 `X-Goodput` 是给运维看的，出问题时不用翻日志就知道系统在哪一格。

## 11. 失败模式

| 现象 | 根因 | 怎么发现 | 怎么修 |
|---|---|---|---|
| 超了 20% 就全崩 | 队列无上限 | 队列长度无界增长 | 设上限 + 超时 |
| 限流后仍然崩 | 重试放大 | 实际到达 > 真实需求 | 关自动重试，或加大退避 |
| 拒绝率 5% 但 goodput 正常 | 拒绝过于保守 | 对比两者 | 放宽阈值 |
| 恢复要十几分钟 | 缓存被冲垮 | 命中率曲线 | 恢复期限流更严，先回填缓存 |
| 长请求拖垮整池 | 无隔离 | 按长度看 TPOT | 长请求独立池 |
| 网关 429 了但引擎还在满 | 信号不同步 | 对比两边速率 | 统一信号源 |

第四个最容易被忽略：过载时缓存命中率会掉，恢复不是"流量回落就恢复"，而是"缓存重新热起来才恢复"。所以要给恢复期留缓冲——限流值比正常容量低 20%，跑 10 分钟再放开。

## 12. 什么情况下这些结论不成立

| 结论 | 推翻条件 |
|---|---|
| 队列要设上限 | 离线批处理场景，等待时间无所谓，可以不设 |
| 拒绝比排队好 | 有充足容量余量且请求可等待时，排队更友好 |
| 限流按 QPS | 请求长度方差极小（如全部是分类任务）时，QPS 就够准 |
| 五道闸 | 单体服务、无多租户时，两道闸（限流 + 超时）就够 |
