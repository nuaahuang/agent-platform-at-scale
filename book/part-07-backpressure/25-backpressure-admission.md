# 第 25 章 · 全链路背压与准入控制：压力怎么传，谁有权拒绝

> 读完你能回答：
> ① 从 8,000 QPS 到雪崩，中间那 90 秒发生了什么？
> ② 六跳链路里，每一跳该看什么信号、下什么动作？
> ③ 平时在线和离线怎么共池，离线任务凭什么敢用在线卡的余量？
> ④ 撞峰时从第几秒开始动作，每一步谁执行、回收多少？
> ⑤ 恢复为什么要比崩溃慢？

---

## 1. 问题：90 秒从正常到雪崩

一个普通的工作日晚上，流量从 5,000 QPS 涨到 8,000。系统容量是 7,000。

按直觉，超了 14%，应该"慢一点"。实际发生的是这样：

| 时刻 | 现象 | 关键指标 |
|---|---|---|
| T+0 | 流量 8,000 QPS | 引擎 waiting 队列 500 |
| T+10 | 队列涨到 3,000 | TTFT（Time To First Token）p95 从 800 ms 到 1.5 s |
| T+20 | 网关 9 秒超时开始触发 | 超时率 3% |
| T+30 | 客户端自动重试 | 实际到达 9,600 QPS |
| T+45 | 队列 12,000，内存告警 | TTFT p95 超过 9 s |
| T+60 | goodput 从 99% 掉到 40% | 所有请求都在超时 |
| T+90 | 人工限流到 6,000 | 队列开始下降 |
| T+10min | 恢复，但缓存全冷 | 命中率 0，TTFT 仍然 1.9 s |

超了 14%，结果不是"慢 14%"，是**完全不可用**。

三个放大器叠在一起：

第一，队列没有上限。引擎的 waiting 队列默认无界，请求进来就排，排到内存耗尽。

第二，重试放大。客户端 9 秒超时后重试，重试的请求又进队列——实际到达量比真实需求高 20%。

第三，缓存被冲垮。过载时新请求不断挤占 KV 池，把热门前缀的块淘汰掉，命中率从 85% 掉到 20%，每次请求要多算 5 倍 prefill，进一步恶化。

这一章讲的就是怎么在 T+10 秒把这件事掐住，以及平时怎么让卡不闲着。

## 2. 完整链路：六跳，每跳都有闸

先把链路摊开。一条请求从进来到出结果，经过六跳：

```
① 客户端 → ② 接入层 → ③ 网关 → ④ Harness → ⑤ LLM 网关 → ⑥ 引擎/GPU
```

每一跳都有"能不能收"的判断，但判断依据不同：

| 跳 | 责任 | 看什么信号 | 满了怎么办 |
|---|---|---|---|
| ② 接入 | TLS、连接数、地域 | 连接数、带宽 | 拒绝连接 |
| ③ 网关 | 鉴权、配额、路由 | 租户配额、全局 QPS | 429 |
| ④ Harness | 编排、工具、检索 | 工具调用耗时、上下文长度 | 缩短上下文、跳过可选步骤 |
| ⑤ LLM 网关 | 模型选择、重试、批 | 引擎 waiting、KV 水位 | 拒绝 / 降级 / 换模型 |
| ⑥ 引擎 | 调度、KV 分配 | 块池、batch 排队 | 抢占 / 拒绝 |

关键点：**每一跳只能看到自己下游那一格**。网关不知道 GPU 的 KV 水位，引擎不知道租户配额。所以压力必须逐跳往回传，不能指望某一跳"全局最优"。

这也是为什么"在网关配个 7,000 QPS 的令牌桶"没用——它看不见第五跳的队列。

## 2.5 一个能落地的部署拓扑

前面的六跳是逻辑链路。落到物理部署上，一个 2000 万 DAU 的平台大概长这样：10 个网关、1,000 个 pod、3 个资源池。

```
                    ┌─ L4 负载均衡（ECMP / Anycast）
                    │
      ┌─────────────┼─────────────┐
      ▼             ▼             ▼
   网关-01       网关-05       网关-10       ← 10 个，各 700 QPS
      │             │             │
      └─────────────┼─────────────┘
                    │  按「租户/优先级/离线标记」选池
      ┌─────────────┼──────────────┐
      ▼             ▼              ▼
  专用池 60 pod  在线池 175 pod  弹性池 79 pod
  480 卡         1,400 卡        632 卡
  预留租户       常规在线        离线任务
      │             │              │
      └─────────────┴──────────────┘
                    │
              Harness 400 pod（编排/工具/检索）
                    │
              LLM 网关 120 pod（模型选择/重试）
                    │
              GPU 314 pod × 8 卡 = 2,512
```

1,000 个 pod 的构成：

| 角色 | pod 数 | 卡 | 说明 |
|---|---|---|---|
| 网关 | 10 | 0 | 无状态，按 QPS 扩 |
| Harness | 400 | 0 | CPU 密集，编排与工具 |
| LLM 网关 | 120 | 0 | 模型路由与重试 |
| GPU 推理 | 314 | 2,512 | 8 卡一个 pod（TP8）|
| 工具代理 / 检索 | 156 | 0 | MCP 与向量检索 |
| 合计 | 1,000 | 2,512 | — |

GPU pod 分三个池，占比和理由：

| 池 | pod | 卡 | 占比 | 装谁 | 为什么这么大 |
|---|---|---|---|---|---|
| 专用池 | 60 | 480 | 19% | 三个预留租户 | 按第 16 章的预留算 |
| 在线池 | 175 | 1,400 | 56% | 常规在线 | 要扛峰值 |
| 弹性池 | 79 | 632 | 25% | 离线任务 | 在线空闲的变现 |

### 2.5.1 流量按什么条件落到哪个池

网关收到请求，按四步决策，顺序不能换：

| 序 | 判据 | 目标 | 判错会怎样 |
|---|---|---|---|
| 1 | 租户在预留名单 | 专用池 | 预留租户被挤，违约 |
| 2 | `X-Offline: true` | 弹性池 | 离线抢占在线容量 |
| 3 | 上下文 > 16K | 在线池的长文子集 | 长请求挤占短请求 |
| 4 | 其余 | 在线池 | 默认 |

第一步必须在最前。如果先判"离线"再判"预留"，一个预留租户的离线任务会跑进弹性池——看起来没问题，但它占的额度是从预留里扣的，账就乱了。

第三步的"长文子集"不是单独的池，是在线池里的一个标签。长请求单独走一组 pod 的理由是它们占 KV 太多（32K 请求的 KV 是 2K 的 16 倍），混在一起会把短请求的并发挤掉。

### 2.5.2 池内怎么选 pod

选定池之后，两件事：亲和性和负载。

**亲和性决定缓存命中率。** 同一租户的请求尽量落到同一批 pod，这样前缀缓存能复用。做法是一致性哈希：

```
pod = ring_hash(tenant_id) 的顺时针第一个
```

但纯哈希会造成热点——大租户的流量集中到几个 pod，把这几个打满。所以要加容量上限：

```
候选 = ring 上顺时针前 3 个 pod
可用 = 候选里 KV 占用 < 80% 的
结果 = 可用里 waiting 队列最短的
```

这个"前 3 选 1"的设计很关键：它保留了亲和性（大多数时候选第一个），又能在第一个过载时溢出。

**会话亲和比分请求亲和更重要。** 同一会话的连续请求必须落到同一 pod，否则 KV 一次都命中不了。键用 `session_id`，不是 `request_id`。

### 2.5.3 网关配置

一个可用的 Envoy 片段，三个池做成了三个 subset：

```yaml
static_resources:
  clusters:
    - name: llm_inference
      type: EDS
      lb_policy: RING_HASH
      ring_hash_lb_config:
        minimum_ring_size: 1024        # 每 pod 约 3 个虚拟节点
      circuit_breakers:
        thresholds:
          - priority: DEFAULT
            max_connections: 30000
            max_pending_requests: 420000   # 队列上限（第 9 节）
            max_requests: 140000
      outlier_detection:
        consecutive_5xx: 5
        interval: 10s
        base_ejection_time: 30s
        max_ejection_percent: 30
      subsets:
        - name: dedicated
          filter_metadata: {pool: dedicated}
        - name: online
          filter_metadata: {pool: online}
        - name: elastic
          filter_metadata: {pool: elastic}

  routes:
    - match: {prefix: "/v1/chat"}
      route:
        cluster: llm_inference
        hash_policy:
          - header: {header_name: "x-tenant-id"}
        retry_policy:
          retry_on: "5xx"
          num_retries: 1          # 只重试一次，防放大
          per_try_timeout: 9s
```

四个参数值得单独说：

- `minimum_ring_size: 1024` → 314 个 pod 每个约 3 个虚拟节点，哈希分布够均匀
- `max_pending_requests: 420000` → 队列上限，由 SLO 反推（第 9 节）
- `num_retries: 1` → **只重试一次**。重试两次会在过载时把流量放大 3 倍
- `base_ejection_time: 30s` → 摘除 30 秒，够实例恢复

### 2.5.4 控制面每 10 秒下发什么

控制面不是下发路由，路由是静态的。它下发的是**配额和权重**：

```json
{
  "ts": "2026-11-18T15:00:10Z",
  "pools": {
    "dedicated": {"pods": 60, "max_concurrency": 22000},
    "online":    {"pods": 175, "max_concurrency": 64000},
    "elastic":   {"pods": 79,  "max_concurrency": 29000}
  },
  "tenants": {
    "tenant-a": {"pool": "dedicated", "quota_qps": 2500, "reserved_conc": 18000},
    "tenant-b": {"pool": "online",    "quota_qps": 1200, "burst": 1800}
  },
  "degrade_level": 0,
  "reject_p2": false
}
```

网关拿到这份数据后自己执行：超过 `quota_qps` 返回 429，`degrade_level` 变了就切换降级策略，`reject_p2` 为真就拒离线。

**控制面不在请求路径上**——网关挂了控制面照样工作，用的是上一份下发。这一点是分层的价值和代价：可用性高，实时性差（最多 10 秒滞后）。

### 2.5.5 一次请求的完整耗时

以 TTFB 为目标，看每一跳花多少：

| 跳 | 耗时 | 说明 |
|---|---|---|
| 客户端 → LB | 2 ms | 就近接入 |
| LB → 网关 | 1 ms | 同机房 |
| 鉴权 + 配额 | 3 ms | Redis 查询 |
| 选池 + 选 pod | 1 ms | 内存哈希 |
| → Harness | 2 ms | — |
| RAG 检索 | 180 ms | 向量检索 + 重排 |
| → LLM 网关 | 1 ms | — |
| → 引擎 | 2 ms | — |
| 排队 | 50 ms | 当前水位 |
| prefill | 15 ms | 缓存命中（未命中 270 ms）|
| 首 token | 1 ms | — |
| **合计 TTFT** | **258 ms** | SLO 是 800 ms |

这张表说明两件事：**网络和网关的开销可以忽略（7 ms），真正的时间花在检索（180 ms）和 prefill（15 或 270 ms）上。**

所以优化 TTFT 不该去优化网关，该去优化检索和缓存命中率。

### 2.5.6 一个池挂了会怎样

最后看故障：专用池的 60 个 pod 全挂。

| 阶段 | 会发生什么 | 谁兜底 |
|---|---|---|
| 0–10 s | outlier detection 摘除失败 pod | Envoy |
| 10 s | 预留租户的请求无处可去 | 网关 |
| 10–20 s | 按优先级压到在线池 | 控制面改 `pool` 字段 |
| 20 s+ | 在线池被挤，goodput 下降 | 降级 + 拒绝 P2 |

关键是第 3 行：**预留池挂了要能把租户临时"降级"到在线池**，而不是直接拒绝。这需要控制面支持"池迁移"，而不是把池写死在租户配置里。

如果写死了，专用池一挂，三个大租户全部不可用——这是故障演练里最常见的发现。

## 3. 压力信号：看五个数，不看 CPU

后端服务通常看 CPU 做扩缩容。LLM 服务不行：GPU 满载是正常状态，推理时本来就该跑满。

五个真正有用的信号：

| 信号 | 从哪取 | 阈值 | 说明 |
|---|---|---|---|
| waiting 队列长度 | 引擎 `Scheduler.waiting` | > 目标等待 × 吞吐 | 最直接 |
| KV 块占用率 | 已用块 ÷ 总块 | > 90% | 接近 OOM |
| TTFT p95 | 滚动 1 分钟 | > 1.5 × SLO（Service Level Objective） | 体验开始崩 |
| goodput | 达标 ÷ 总请求 | < 95% | 最终判据 |
| 拒绝率 | 429 ÷ 总请求 | > 5% | 已经在丢了 |

第三个和第四个一起看：TTFT 涨但 goodput 没掉，是慢了还能撑；goodput 掉了，是已经在丢请求。

**为什么不看 GPU 利用率**：它到 100% 是常态，没有区分度。有区分度的是"排队的人在等多久"。

这些信号要聚合成一个数往下传，否则每跳各看各的会打架。我们的做法是"最差信号主导"：

```
压力等级 = max(队列水位, KV 水位, TTFT 超线幅度, 1 − goodput)
```

取最大，不取平均。因为过载时只要有一项爆了，就必须动作——平均会把单项的爆点抹平。

## 3.5 逐跳传还是集中调度

到这里会有一个自然的疑问：既然压力信号都在，为什么不搞一个统一调度中心，收集所有信号、算一个全局最优解、再下发执行？那样不就不用"每跳自己猜"了吗？

答案是一半对。**五个时间尺度上，只有中间两层适合集中，两头必须分布。**

| 层 | 周期 | 决策什么 | 在哪做 |
|---|---|---|---|
| L1 请求准入 | 毫秒 | 收还是不收这一个请求 | 每个实例本地 |
| L2 实例背压 | 秒 | 降速多少、要不要摘除 | 网关本地 |
| L3 池调度 | 10 秒 | 弹性池扩缩多少 | **集中** |
| L4 集群弹性 | 分钟 | 加卡还是减卡 | **集中** |
| L5 容量规划 | 月 | 总共买多少卡 | 人 |

判据只有一条：**控制回路的周期必须短于被控对象的动态时间尺度。**

队列积压的速度是每秒 1,000 条——等 10 秒再决策，队列已经涨了 1 万。所以 L1 只能本地做，本地判断的延迟是微秒级。

而池子配比的变化是 10 秒级，扩卡是 7–10 分钟级，这些完全来得及集中算。

### 3.5.1 为什么不能全集中

四个理由，从硬到软：

| 问题 | 数字 |
|---|---|
| 延迟 | 中心 RPC 1 ms，每请求多 1 ms，占总延迟 1%–5% |
| 吞吐 | 7,000 QPS × 1 次决策 = 中心要扛 7,000 QPS 的控制流量 |
| 可用性 | 中心挂 = 全站失去准入能力，谁都不能拒绝谁 |
| 数据新鲜度 | 中心看到的是 1–5 秒前的聚合，用它做毫秒级决策就是基于过期状态 |

第三条最致命。准入是"必须永远在线"的能力，把它做成一个需要网络往返的中心服务，等于给全站加了一个单点。

### 3.5.2 为什么不能全分布

反过来，全分布也有三个死穴：

| 问题 | 表现 |
|---|---|
| 打架 | 池子是零和的，A 实例多占一个，B 就少一个，本地决策无法协调 |
| 震荡 | 各实例对"现在多挤"的判断不同，一会儿扩一会儿缩 |
| 说不清 | 出事时没有单一事实来源，复盘只能看一堆局部日志 |

第一条最典型：弹性池缩的时候，如果每个网关都自己判断"我这边压力小了，可以多要一点离线"，十个网关同时要，池子瞬间被抢空。

### 3.5.3 混合怎么落：策略集中，执行分布

```
自下而上：信号上报（异步、聚合、每 10 秒一次）
自上而下：策略下发（配额、阈值、优先级）
本地     ：按策略执行，不等指令
```

具体到三个决策：

| 决策 | 谁定 | 谁执行 | 怎么衔接 |
|---|---|---|---|
| 弹性池多大 | 中心每 10 秒算 | 各实例按新配额 | 下发 `P2_quota` |
| 这个请求收不收 | 本地按配额 | 网关 | 本地队列 + 下发配额 |
| 降速到多少 | 本地看下游 | 网关 | `Retry-After` |

关键在第三列：**中心只下发"允许多少"，不下发"收哪个"**。收哪个是本地的事，因为只有本地知道此刻队列里排的是什么。

### 3.5.4 分布式的老毛病：震荡

集中 + 分布混着用，最容易出的问题是控制环震荡。三个标准解法：

| 手段 | 做法 | 防什么 |
|---|---|---|
| 滞回 | 60% 扩、80% 缩 | 阈值附近抖动 |
| 阻尼 | 每次最多调 10%/20% | 一次调过头 |
| 冷却 | 调完 60 秒内不再调 | 连续调整 |

三个要一起用。只做一个，震荡会以另一种形式出现——只加滞回，会在 2 倍波动时来回切；只加阻尼，会在临界点附近慢慢摇。

### 3.5.5 一个反例

如果真把所有准入集中：

```
7,000 QPS × 1 次中心决策
中心延迟 1 ms → 每个请求多 1 ms
中心需要 7,000 QPS 的处理能力，还要 5 个 9 的可用性
```

这比推理服务本身还难做。所以业界主流的做法都是混合：Envoy 的本地令牌桶 + 全局配额服务（RLS），Kubernetes 的本地限流 + HPA。没有哪个生产系统把准入完全集中。

## 4. 平时调度：让离线任务吃掉余量

这是本章最值钱的部分。前面几章反复算过：在线利用率只有 25%，剩下的 75% 不填就是白买。

先算能填多少：

```
在线峰值需要 2,512 卡
在线平均需要 628 卡（25%）
空闲 = 1,884 卡 × 24 小时 = 45,216 卡时/日
```

如果离线任务能吃掉 80% 的空闲，就是 **36,000 卡时/日**，一年 1,320 万卡时，比现有卡数多出 33% 的算力。

### 4.1 两类任务，两种服务等级

| 类别 | 例子 | 延迟要求 | 可中断 | 计费 |
|---|---|---|---|---|
| 在线 | 客服问答、订单查询 | TTFT ≤ 800 ms | 否 | 按量/预留 |
| 离线 | 历史回刷、意图重分类、评测回放、RL rollout | 分钟到小时 | 是 | 内部结算 |

离线任务的关键属性不是"慢"，是**可以被打断并且能重来**。不能重来的任务不配进这个池子。

### 4.2 池子怎么切：三段式

```
总容量 2,512 卡
├─ 在线池 P0+P1   1,880 卡   保证 SLO，任何情况下不被挤
├─ 弹性池 P2        632 卡   离线任务用，在线压力大时逐级回收
└─（在线池的空闲部分通过"借出"临时并入弹性池）
```

为什么不全给弹性池？因为回收需要时间。如果离线占满了，在线突然涨上来，回收要 10–30 秒，这期间 SLO 已经破了。

留 25% 的在线专用，是为了让"突增"有缓冲。

### 4.3 借出：在线池的空闲怎么给离线用

在线池平均只用 25%，它那 75% 的空闲要能借出去，否则切池没意义。

借出规则三条：

| 规则 | 内容 | 为什么 |
|---|---|---|
| 借用量 ≤ 在线池空闲 × 0.8 | 留 20% 应对突发 | 突发检测有延迟 |
| 借出的实例保持"热" | 不销毁，只换任务 | 回收要在秒级 |
| 借出期间禁止改配置 | 不重启、不换模型 | 重启要 2–3 分钟 |

第三条最容易违反。运维看到离线池在跑，顺手做了个版本升级，结果在线压力一来，那批实例在重启，回收不了。

### 4.4 动态配比：每 10 秒调一次

调度器循环评估在线水位，调整弹性池大小：

```
每 10 秒：
  u = 在线池实际用量 / 在线池容量
  if u < 0.60 and 离线队列非空:
      弹性池 += 10%（从在线池空闲划出）
  if u > 0.80 and 弹性池 > 下限:
      弹性池 -= 20%（回收给在线池）
```

两个设计点：

**滞回带 60%–80%**。如果只用单一阈值（比如 70%），水位在 70% 附近抖动会来回切，每次都触发实例迁移。带宽带回，切一次要等它稳定。

**加 20% 比减 10% 快**。扩离线是缓慢的（怕占太多），收离线是激进的（怕破 SLO）。方向不对称是对的——安全优先。

### 4.5 离线任务的四级可中断性

不是所有离线任务都能随便打断。分四级：

| 级别 | 例子 | 中断代价 | 恢复方式 |
|---|---|---|---|
| L1 | 批量分类 | 丢一条记录 | 重跑这一条 |
| L2 | 评测回放 | 丢一次评测 | 重放这一条 |
| L3 | RL rollout | 丢半条轨迹 | 从 checkpoint 续 |
| L4 | 训练 step | 丢一个 step（30 秒） | 从上一步续 |

回收时按 L1→L4 的顺序，先把便宜的停掉。L4 通常不放在弹性池里——训练一个 step 30 秒，打断的代价比收益大。

### 4.6 离线任务的准入

离线任务不是"来了就放"，要有配额和排队：

| 检查 | 阈值 | 不过怎么办 |
|---|---|---|
| 离线队列长度 | < 2 小时的量 | 拒绝提交，让用户明天再来 |
| 任务截止时间 | 至少还有 2 小时 | 拒绝，或建议走专用池 |
| 单任务规模 | < 弹性池的 30% | 拆批提交 |

第三条很重要。一个占满弹性池的任务会把所有小任务饿死，而且一旦被回收，它自己也白跑。让它拆成小批，既能调度也能续跑。

## 5. 撞峰处理：带秒数的完整时序

上面是平时。现在看真撞峰了怎么办。

前提：检测到在线水位超过 80%，且持续 30 秒。所有动作由调度器自动执行，人只在告警后旁观。

| 时刻 | 触发条件 | 动作 | 执行者 | 回收/影响 |
|---|---|---|---|---|
| T+0 | 在线队列 > 60% 上限 | 告警，停止扩离线池 | 调度器 | — |
| T+5s | goodput 跌破 98% | 停止接新离线任务 | 调度器 | 离线队列冻结 |
| T+10s | 在线队列 > 80% | 开始回收：先停 L1 | 调度器 | 释放约 10% 弹性池 |
| T+20s | 队列仍涨 | 继续回收 L2、L3 | 调度器 | 弹性池归零 |
| T+30s | 排队 > 30 秒 | 降级：关深度思考、截断长回答 | 网关 | 单请求成本降 3.5 倍 |
| T+45s | goodput < 95% | 拒绝 P2 新请求 | 网关 | 只保 P0/P1 |
| T+60s | 仍恶化 | 抢占：P1 让位于 P0 | LLM 网关 | 预留租户优先 |
| T+120s | 仍恶化 | 全局限流到容量 × 0.8 | 网关 | 主动丢 20% |
| 恢复 | goodput > 99% 持续 5 分钟 | 每次放开 10%，间隔 2 分钟 | 调度器 | 渐进恢复 |

这张表有三个设计意图。

**第一，先动离线，后动在线。** 前 20 秒全部在回收离线任务，一个在线请求都还没被影响。这是"用别人的余量扛自己的峰值"。

**第二，降级在拒绝之前。** T+30 秒先降级，T+45 秒才拒绝。降级能让所有人继续被服务（只是差一点），拒绝会让一部分人拿不到服务。顺序反了就是浪费。

**第三，恢复比崩溃慢。** 崩溃用了 120 秒，恢复要 5 分钟起步——因为缓存要重新热起来（第 7 章）。恢复期的限流值要比正常容量低 20%。

### 5.1 通知：让被回收的任务体面退出

回收不是 kill -9。四步：

```
1. 调度器发 drain 信号（标记该实例不再接新任务）
2. 任务完成当前这一条（grace 10 秒）
3. 超时的强制中断，记录 checkpoint
4. 实例回到在线池，重新配权重（如果模型不同）
```

10 秒 grace 的依据：一个离线请求平均 3–5 秒，10 秒能覆盖 95%。

第 4 步容易被忽略：离线池和在线池如果模型不同（一个 8B 一个 200B），回收后要重新加载权重，2–3 分钟。所以**两个池应该用同一个模型**，或者至少让弹性池的实例预装在线模型。

### 5.2 抢占：谁让位于谁

回收是"收回空闲"，抢占是"拿走正在用的"。只有在回收完还不够时才用。

| 优先级 | 谁 | 被抢占的代价 | 抢占顺序 |
|---|---|---|---|
| P0 | 已付费预留 | 不可接受 | 最后 |
| P1 | 按量在线 | 用户等多 30 秒 | 第二 |
| P2 | 离线批处理 | 任务重跑 | 第一 |
| P3 | 内部调试 | 无 | 最先 |

P0 之间不抢占——同样付费的租户没有高低。真到了 P0 之间要抢的地步，说明容量模型错了（第 13 章），该扩卡而不是继续挤。

## 6. 恢复期：比崩溃更难

崩溃是"某个瞬间失效"，恢复是"逐渐回到正常"。恢复期有三个坑。

**坑一：缓存是冷的。** 过载时缓存被冲垮，恢复后命中率从 0 爬回 85% 要 10–20 分钟。这期间 prefill 成本是正常的 5 倍，TTFT 仍然偏高。

**坑二：重试还在来。** 客户端在崩溃期间积压的重试，会在恢复后涌入。所以恢复期的实际到达量高于真实需求。

**坑三：离线任务在抢。** 一旦 goodput 回到 99%，调度器会开始扩离线池——但此刻缓存还没热，扩太快会把在线打回去。

应对是三条：

| 措施 | 参数 | 作用 |
|---|---|---|
| 渐进放开 | 每次 +10%，间隔 2 分钟 | 防止二次冲击 |
| 推迟扩离线 | goodput 恢复后 10 分钟才允许 | 让缓存先热 |
| 恢复期限流 | 正常容量的 80% | 留出重试的余量 |

## 7. 限流按 QPS 还是 token

这是最常被问的问题，答案是**两个都要，用在不同层**。

| 层 | 按什么 | 为什么 |
|---|---|---|
| 网关入口 | QPS | 便宜、快、防突发。此时还不知道 token 数 |
| LLM 网关 | 并发请求数 | 能预估上下文长度，区分长短请求 |
| 引擎 | token/秒 + KV 水位 | 最准，但已经进来了 |

入口按 QPS 防的是"异常流量"（爬虫、攻击、配置错误），特征是请求数异常。

引擎按 token 防的是"容量打满"，而容量是被 token 消耗的。

中间层按并发最实用：

```
并发 = QPS × 停留时间
```

它同时反映请求数和时长，比单独的 QPS 准，又不需要预知 token 数。

## 8. 拒绝的四种语义

拒绝不是只有"返回 503"。语义不同，客户端行为不同。

| 语义 | 状态码 | 客户端该做什么 | 用在哪 |
|---|---|---|---|
| 重试 | 503 + Retry-After | 等 N 秒重试一次 | 临时过载 |
| 降级 | 200 + 降级标记 | 展示降级内容 | 质量可让 |
| 排队 | 202 + 位置 | 轮询或等待 | 异步任务 |
| 永久拒绝 | 429 | 不要重试，改配额 | 超配额 |

`Retry-After` 必须是真数：

```
Retry-After = 当前队列长度 ÷ 服务速率
```

队列 12,000、速率 7,000/秒，就是 1.7 秒。写死了会两头错：写 30 秒但实际 3 秒就好，客户端白等；写 3 秒但实际要 30 秒，重试还是失败，加重拥塞。

## 9. 队列为什么是雪崩放大器

排队看起来温和（不拒绝用户），过载时却在加速崩溃。

用利特尔法则：队列长度 = 到达率 × 等待时间。

```
到达 8,000 QPS，服务 7,000 QPS
净增 1,000/秒
60 秒后队列 = 60,000，等待 8.5 秒——已超过 9 秒预算，注定超时
```

系统仍在为这些注定超时的请求消耗资源。加上重试，到达变 9,600，净增 2,600/秒，翻倍时间从 60 秒缩到 23 秒。

所以队列必须有上限，且由 SLO 反推：

```
队列上限 = 目标等待 × 服务速率 = 60 秒 × 2.8 QPS/卡 × 2,512 卡 = 42 万
```

超过 42 万，新请求的等待必然超过 60 秒，**拒绝比排队好**。

这条上限的作用不是省资源，是止损：把"所有人都慢"变成"一部分人快、一部分人被拒"。

## 10. 配置

三段核心配置（Envoy 风格）：

```yaml
# ① 限流：令牌桶，防突发
rate_limits:
  - actions: [{generic_key: "llm_gateway"}]
    limit: {requests_per_unit: 7000, unit: SECOND}

# ② 排队与并发：防积压
circuit_breakers:
  thresholds:
    - priority: DEFAULT
      max_connections: 20000
      max_pending_requests: 420000   # 队列上限，由 SLO 反推
      max_requests: 140000           # 并发上限，等于峰值并发

# ③ 背压：坏实例摘除
outlier_detection:
  consecutive_5xx: 5
  base_ejection_time: 30s
  max_ejection_percent: 30
```

服务端拒绝时要带真实信息：

```python
def reject_with_retry_after(queue_len, service_rate, goodput):
    wait_s = max(1, ceil(queue_len / service_rate))
    return Response(status=503, headers={
        "Retry-After": str(wait_s),
        "X-Queue-Length": str(queue_len),
        "X-Goodput": f"{goodput:.3f}",
    })
```

后两个头是给运维的：出问题时不用翻日志，看响应头就知道系统在哪一格。

## 11. 失败模式

| 现象 | 根因 | 怎么发现 | 怎么修 |
|---|---|---|---|
| 超 20% 就全崩 | 队列无上限 | 队列无界增长 | 设上限 + 超时 |
| 限流后仍崩 | 重试放大 | 实际到达 > 真实需求 | 关自动重试或加大退避 |
| 离线任务被反复打断 | 弹性池太小 | 中断率 > 30% | 扩大弹性池，或降离线配额 |
| 回收后在线仍不够 | 两个池模型不同 | 回收耗时 2–3 分钟 | 统一模型 |
| 恢复要十几分钟 | 缓存被冲垮 | 命中率曲线 | 恢复期限流更严，先回填 |
| 长请求拖垮整池 | 无隔离 | 按长度看 TPOT（Time Per Output Token） | 长请求独立池 |
| 离线任务饿死 | 大任务占满弹性池 | 队列里小任务等待久 | 单任务上限 30% |
| 网关 429 但引擎还满 | 信号不同步 | 对比两边速率 | 统一信号源 |

## 12. 什么情况下这些结论不成立

| 结论 | 推翻条件 |
|---|---|
| 队列要设上限 | 纯离线批处理，等待无所谓，可以不设 |
| 拒绝比排队好 | 有充足余量且请求可等时，排队更友好 |
| 留 25% 在线专用 | 流量极平稳（无突发）时，可以全部混用 |
| 六跳都有闸 | 单体服务时，两道闸（限流 + 超时）就够 |
| 恢复比崩溃慢 | 缓存命中率很低（<30%）时，恢复也快 |
