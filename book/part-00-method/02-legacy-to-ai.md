# 第 02 章 · 传统互联网架构在 AI 服务中的复用、变形与失效

> 读完你能回答：
> ① 哪些经典模式可以原样搬过来，哪些必须改，哪些照抄就会死？
> ② 为什么"加机器"在 GPU 上是阶梯而不是滑杆？
> ③ 为什么限流放在网关会失效？
> ④ 一次重试到底有多贵？

---

## 1. 问题：按电商那套设计，三个月后被推翻

一个典型的重构事故，几乎每个团队都会走一遍：

> 团队按成熟电商架构设计了 Agent 平台：无状态服务 + 水平扩展 + Redis 缓存 + MQ 削峰 + 网关限流。
> 上线两周后，五个问题同时爆发。

| 设计 | 预期 | 实际 | 根因 |
|---|---|---|---|
| 无状态 + 水平扩展 | 加机器就扩容 | 扩 10% 要 10 分钟，期间流量已经涨完 | GPU 扩容有加载成本 |
| Redis 缓存回答 | 命中率 60%+ | 命中率 8% | 用户问题几乎不重复 |
| MQ 削峰 | 峰值排队，谷时消化 | 堆了 10 万条，GPU 还是 7000 QPS | 算力不能"存起来" |
| 网关限流 | 保护后端 | 短请求占满额度，长请求全排队 | 瓶颈是 token 不是 QPS |
| 失败重试 3 次 | 提高成功率 | 一次抖动变成雪崩 | 重试成本是 prefill 全量 |

**五个问题指向同一件事**：AI 服务不是"另一种 Web 服务"，它是
**有状态的、按 token 计费的、排队不可缓冲的计算服务**。

这一章不给结论，给**判据**——让你拿到任何一个经典模式，能自己判断它属于哪一档。

---

## 2. 一条判据：三问定性

拿到一个传统模式，先问三个问题：

| 问题 | 如果答案是… | 结论 |
|---|---|---|
| ① 瓶颈是"并发连接"还是"计算/带宽"？ | 计算/带宽 | 传统扩容逻辑失效 |
| ② 状态能不能外置？ | 不能（KV 在显存里） | 无状态假设失效 |
| ③ 计费单位是"请求"还是"token"？ | token | 限流/配额/成本模型全要改 |

```
拿到一个传统模式
  ├─ ① 瓶颈是计算/带宽？ ──是──▶ 传统扩容逻辑失效
  ├─ ② 状态能外置？     ──否──▶ 无状态假设失效
  └─ ③ 计费按 token？   ──是──▶ 限流/配额/成本模型全改
```

三问全过，才能原样复用；中一个，就要变形；中两个以上，基本失效。

## 3. 判定表：13 个经典模式

| 经典模式 | 判定 | 为什么 | 怎么改 |
|---|---|---|---|
| **无状态水平扩展** | **变形** | GPU 有状态：KV、前缀树都在显存 | 路由亲和 + 会话粘性 |
| **连接池** | 复用 | 到引擎的 gRPC 池仍然必要 | 容量按 KV 显存算，不按连接数 |
| **多级缓存** | **变形** | 缓存的是 KV 不是响应 | 前缀缓存，命中率 85% vs 8% |
| **MQ 削峰** | **失效** | 算力不能"先存后算" | 只能准入控制 + 拒绝 |
| **限流** | **变形** | 瓶颈是 token/s，不是 QPS | 双维度：QPS + token/s |
| **熔断** | 复用 | 语义没变 | 阈值按 token 与在飞数设 |
| **降级** | **变形** | 降级目标是"更小的模型/规则" | L0–L5 阶梯（第 35 章） |
| **多活 / 单元化** | **变形** | KV 不跨区传输 | 多 cell，会话内闭环 |
| **分库分表** | 复用 | 数据模型没变 | 按 tenant 分片 + 时间分区 |
| **幂等** | 复用+ | 工具调用有副作用，比写接口更关键 | 幂等键 + 副作用日志 |
| **灰度发布** | **扩展** | 变成三套版本：模型 / Prompt / 工具 | 版本矩阵（第 36 章） |
| **压测** | **变形** | 必须按长度分布打 | 开环 + 生产分布（第 12 章） |
| **重试** | **慎用** | 重试要重跑 prefill | 重试预算 + 只重试可重试错误 |

**判定为"复用"的只有 4 个**（连接池、熔断、分库分表、幂等）。
剩下 9 个全部要改——这个比例本身就是结论：**传统经验能直接用的部分不到三分之一**。

## 4. 逐项改法：怎么做、做到什么标准、还要新建什么

表里每一行都回答四个问题：**怎么改 / 改到多少算合格 / 要新建什么 / 新件自己有什么标准**。

| 模式 | 改法（怎么做） | 达标线 | 新增件 | 新增件达标线 |
|---|---|---|---|---|
| **无状态** | 按 `(tenant, session)` 一致性哈希；路由表存 Redis，实例 5 s 心跳；实例故障时回退冷实例 + 事件重放 | 亲和命中 ≥95%；路由收敛 ≤5 s；迁移后 TTFT（Time To First Token） ≤2 s | 路由表、会话迁移协议、预热副本 | 路由表 99.99%；迁移成功率 99.9%；预热副本 ≤5% 成本 |
| **连接池** | 池大小按"在飞请求数"定，不按连接数；每实例独立池 | 等待队列 ≤5%；连接复用率 ≥90% | 池水位指标 | 排队等待 p95 ≤5 ms |
| **多级缓存** | 缓存对象换成 **KV block**；稳定前缀（系统提示 + 工具 schema）固定放最前；租户哈希加盐 | 前缀命中 ≥85%；缓存 ≤30% 显存；跨租户 **0** 共享 | 前缀模板管理、驱逐策略、命中率看板 | 命中率跌 5 pt 告警；驱逐后 TTFT 回退 ≤200 ms |
| **MQ 削峰** | 不再"先存后算"，改**入口准入**：有界队列（≤2× 在飞）+ 快速拒绝 | 拒绝 ≤50 ms；队列 ≤2× 在飞；goodput 走平 | 拒绝语义（429 + Retry-After）、队列深度指标 | 1.5× 过载时 goodput ≥90% |
| **限流** | 三维：QPS + token/s + inflight；租户配额可借调 | 长请求消耗 token 配额；p99/p50 ≤3 | token 滑动窗口计数、配额中心 | 计数误差 <0.1%；配额变更 ≤10 s 生效 |
| **熔断** | 语义不变，阈值换成 token 速率与在飞数 | 熔断判定 ≤1 s；误熔断 <0.01% | 熔断器状态机 | 半开探测成功率 ≥95% 才恢复 |
| **降级** | L0–L5 阶梯，阈值自动触发（见第 35 章） | 触发 ≤10 s；恢复 ≤60 s | 降级开关、触发阈值、自动恢复 | 误降级率 <0.1% |
| **多活** | 改**多 cell**，按用户哈希分；cell 内闭环，跨 cell 只异步同步 | 单 cell 99.9%；cell 故障不扩散 | cell 路由、异步同步管道 | 同步延迟 ≤5 s；cell 水位 ≤70% |
| **分库分表** | 按 tenant 分片 + 时间分区，与业务库同构 | 单分片 ≤5,000 万行；0 跨分片查询 | 分片路由 | 扩容不停机；双写校验 100% 一致 |
| **幂等** | 幂等键 + 副作用台账；工具调用强制幂等 | 重复调用 **0** 副作用 | 去重表、副作用台账 | 键 TTL 24 h；去重判定 ≤5 ms |
| **灰度** | 模型 / Prompt / 工具 schema 三套版本组成一个 **release set** | 每个组合都有评测覆盖 | 版本矩阵、契约测试、影子对比 | 黄金用例 50 条 100% 通过；影子差异 <2% |
| **压测** | 开环 Poisson + 生产长度分布（见第 12 章） | 客户端不瓶颈；报告六字段齐 | 流量回放、压测平台 | 与生产分布 KL 散度 <0.1 |
| **重试** | 只重试白名单错误；每租户预算 1%；指数退避 | 重试率 <1%；放大系数 <1.1× | 重试预算计数、错误码分类表 | 预算耗尽后 100% 快速失败 |
| **扩容** | 预测式定时扩 + 预热池（见第 33 章） | 用户无感；预热成本 ≤10% | 预测模型、P2P 权重分发 | 预测误差 <15%；加载 ≤3 min |

**怎么用这张表**：先看"达标线"这一列——如果某项现在达不到，它就是你接下来一个季度的技术债清单。

其中三个"新增件"必须自建，市面上没有现成的。

## 5. 从指标到自动动作：五层控制环

§4 的达标线不是拿来"看看"的——**每一条都应该能被系统自己感知并处置**。
但"感知"和"自动处置"之间隔着四道关，任何一道没做对，自动化都会变成灾难。

### 5.1 一个指标要走完四道关

```
采集 ──▶ 聚合 ──▶ 判定 ──▶ 执行
  ▲                          │
  └────────── 反馈 ───────────┘
```

| 关卡 | 要解决什么 | 常见错误 | 达标线 |
|---|---|---|---|
| **采集** | 在哪打点、带什么标签 | 只在网关打，引擎内部是黑盒 | 每请求 ≥6 个标签；采集开销 <1% |
| **聚合** | 用什么窗口、什么分位 | 只用平均值 | 1 s / 10 s / 1 m / 5 m 四档；p50/p95/p99 |
| **判定** | 阈值、趋势还是预算 | 单点越线就动作 | 连续 3 个窗口；滞回带 20% |
| **执行** | 选对动作 + 限速 | 一律扩容 | 动作预算：每小时 ≤6 次 |

**采集这一关最重要**：如果"亲和命中"这个数在路由层没有打点，
它就只是一句口号，永远无法自动化。

### 5.2 关键：指标要分类，动作要匹配

这是整套自动化的核心洞察——**不是所有指标都该用"扩容"来响应**。

| 指标类型 | 例子 | 正确动作 | 错误的动作 | 为什么错 |
|---|---|---|---|---|
| **容量型** | 队列深度、TTFT p95、KV 水位 | 扩容 / 缩容 | 降级 | 降级只是掩盖，容量还是不够 |
| **正确性型** | 亲和命中率、跨租户共享、对账差 | 修配置 / 切流 / 回滚 | 扩容 | **命中率与卡数无关** |
| **成本型** | 每轮 token、每秒成本 | 降级 / 调参 | 扩容 | 越扩越贵 |
| **依赖型** | 下游工具错误率、DB 延迟 | 熔断 / 降级 | 扩容 | 问题不在你这边 |

**举例**：亲和命中率从 95% 掉到 60%，正确动作是检查路由表是否被重启清空、
哈希键是否变了；此时扩容 100 张卡，命中率一点不会涨。

> 判断方法：问一句"这个指标变差，是因为资源不够吗？"
> 不是，就别用扩容解决。

### 5.3 五层架构

| 层 | 职责 | 组件 | 达标线 |
|---|---|---|---|
| **L0 采集** | 打点、统一 schema | SDK / sidecar / eBPF | 标签 ≤20 个防基数爆炸 |
| **L1 汇聚** | 多分辨率聚合、原始事件留存 | 流式聚合 + 列存 | 1 s 粒度延迟 ≤3 s |
| **L2 判定** | SLO（Service Level Objective） burn rate、规则、异常检测 | 规则引擎 | 误报率 <5% |
| **L3 决策** | 选动作、算预算、定优先级 | 决策引擎 | 决策延迟 ≤5 s |
| **L4 执行** | 调 K8s / 网关 / 配置 | Controller | 动作可回滚率 100% |
| **L5 审计** | 每次自动动作留痕 | 事件日志 | 可复原"当时为什么这么做" |

**L3 和 L4 必须分开**：决策是"该怎么办"，执行是"怎么安全地办"。
合并在一起，就会出现"决策说扩 50 台，执行一口气拉起 50 台把存储打爆"。

### 5.4 一个完整例子：TTFT p95 从 600 ms 涨到 1200 ms

| 时间 | 层 | 发生了什么 |
|---|---|---|
| T+0 | L0 | 网关与引擎同时上报 TTFT，标签含 `tenant / model / cell` |
| T+30 s | L1 | 1 m 窗口 p95 = 1180 ms，越过 800 ms |
| T+90 s | L2 | 连续 3 个窗口越线，且错误预算燃烧率 3.2×（>2× 告警线） |
| T+95 s | L3 | 决策：**先判别类型**——查 token/s 是否超配额。发现长请求占比从 5%→22%，判定为"配额型过载" |
| T+100 s | L4 | 动作 1：对超配额租户限流（不动容量）；动作 2：预热池 +2 实例（3 min 后可用） |
| T+160 s | L1 | 复测 p95 = 820 ms，仍在临界 |
| T+165 s | L3 | 动作 3：触发 L1 降级（关投机解码），单用户变慢但吞吐 +12% |
| T+220 s | L2 | p95 = 640 ms，恢复；燃烧率回落到 0.4× |
| T+10 min | L3 | 稳定后**自动撤销降级**（这是最容易漏的一步） |
| 全程 | L5 | 记一条：`原因=长请求激增 动作=限流+扩容+降级 结果=恢复@220s` |

**这个例子里扩容只是三个动作之一**。只会上扩的系统，遇到长请求激增会越扩越糟。

### 5.5 自动化的三条纪律

| 纪律 | 内容 | 违反的后果 |
|---|---|---|
| **先观察两周** | 人工盯两周，确认规则不误报，再开自动执行 | 规则一上线就震荡 |
| **每个动作可回滚** | 扩容可缩、降级可撤、切流可切回 | 出了错只能重启 |
| **动作预算** | 每小时 ≤6 次，防震荡 | 扩了缩、缩了扩，抖动放大 |

**震荡是最常见的失败**：扩容阈值 80%、缩容阈值 79%，系统会整夜开开关关。
解法是滞回——扩容 80%、缩容 40%，中间 40 个点不动。

### 5.6 每层用什么组件，什么时候必须自研

| 层 | 现成能力 | 开源/商业组件 | 什么时候必须自研 |
|---|---|---|---|
| L0 采集 | 指标 SDK、抓取 | OpenTelemetry、vLLM/SGLang 的 `/metrics`、eBPF（Pixie） | 需要引擎内部细粒度（每层 KV、每 block 命中） |
| L1 汇聚 | 时序库、规则聚合 | Prometheus + Thanos/Mimir、VictoriaMetrics、ClickHouse | 高基数（按 session 维度）或跨年留存 |
| L2 判定 | SLO 规则生成 | Sloth、Pyrra、Alertmanager | 多租户差异化 SLO、复合条件 |
| L3 决策 | 简单伸缩 | HPA（custom metrics）、KEDA（Kubernetes Event-driven Autoscaling）、Karpenter | 需要"先判类型再选动作"——**必须自研** |
| L4 执行 | 扩容/灰度/切流 | K8s Operator、Argo Rollouts、Flagger、Envoy xDS | 预热池、权重分发 |
| L5 审计 | 日志 | ClickHouse / Loki | 与变更系统联动 |

**结论**：L0–L2 能买就买，L3 必须自研，L4 半自研。原因在下面三段代码里。

### 5.7 L0/L1：采集什么、怎么打点

引擎侧现成的（vLLM 为例，Prometheus 格式）：

```text
vllm:num_requests_running            正在跑的请求数
vllm:num_requests_waiting            排队数          ← 扩容的第一前导指标
vllm:gpu_cache_usage_perc            KV 水位          ← 拒绝的第一前导指标
vllm:time_to_first_token_seconds_bucket
vllm:prefix_cache_hits_total / queries_total
```

网关侧自己打（OpenTelemetry，Python）：

```python
from opentelemetry import metrics
meter = metrics.get_meter("gateway")

ttft = meter.create_histogram("llm_ttft_ms", unit="ms")
affinity = meter.create_counter("llm_affinity_total")

def on_first_token(req, elapsed_ms, hit_route):
    # 标签只放低基数维度：tenant / model / cell / route_result
    labels = {"tenant": req.tenant, "model": req.model, "cell": req.cell}
    ttft.record(elapsed_ms, labels)
    affinity.add(1, {**labels, "result": "hit" if hit_route else "miss",
                     "reason": req.fallback_reason or "none"})
```

**标签规范**（这一条决定系统能不能扩展）：

| 允许 | 禁止 |
|---|---|
| tenant_id、model、cell、version、status | session_id、request_id、user_id（基数爆炸） |
| 枚举值 ≤50 个 | 自由文本、URL 路径 |

基数失控的典型症状：Prometheus 内存一路涨到 OOM。**一条规则：标签值的集合必须能枚举完。**

### 5.8 L2/L3：判定与决策

**判定**用多窗口燃烧率（Google SRE Workbook 的标准做法）：

```yaml
# 日均 SLO 99.9% → 错误预算 0.1%
- record: slo:ttft_p95_pass:1h
  expr: sum(rate(llm_ttft_ms_bucket{le="800"}[1h])) / sum(rate(llm_ttft_ms_count[1h]))

- alert: TTFT_FastBurn
  expr: (1 - slo:ttft_p95_pass:1h) / 0.001 > 14.4   # 1 小时烧掉 2% 月预算
  for: 2m

- alert: TTFT_SlowBurn
  expr: (1 - slo:ttft_p95_pass:6h) / 0.001 > 6      # 6 小时烧掉 5%
  for: 15m
```

**决策**必须自研，因为它是"先分类、再选动作"：

```go
func (r *Reconciler) Reconcile(ctx context.Context, key string) error {
    m := r.observe(key)                       // 拉指标快照
    class := classify(m)                      // 容量 / 正确性 / 成本 / 依赖
    act, ok := decide(class, m)               // 返回动作；不满足预算则 ok=false
    if !ok { return nil }                     // 不动，也是决策
    if err := r.actuate(act); err != nil {    // 执行
        r.audit(key, act, err); return err
    }
    r.audit(key, act, nil)
    r.verifyAfter(60*time.Second, key)        // 60 秒后复测，未恢复则升级动作
    return nil
}

func classify(m Snapshot) Class {
    if m.TokensPerSec > m.Quota*1.2 { return ClassQuota }   // 配额型
    if m.KVUsage > 0.85 && m.Waiting > 0 { return ClassCapacity }
    if m.AffinityHit < 0.9 { return ClassCorrectness }      // 命中率掉 → 不扩容
    return ClassHealthy
}
```

**动作预算**用令牌桶实现（每小时 6 次）：

```go
if !r.actionBucket.Allow() {           // 超预算就不动，等人
    r.log("action budget exhausted, escalate to human")
    return nil
}
```

### 5.9 L4：执行层怎么落地

| 动作 | 现成组件 | 配置要点 |
|---|---|---|
| **扩缩容** | KEDA `ScaledObject` 拉 Prometheus 指标；Karpenter 补节点 | 冷却期 ≥5 min，防抖 |
| **限流** | Envoy global rate limit / Redis 令牌桶 Lua | 三维配额，见 §6.2 |
| **降级** | 配置中心（Apollo/Nacos）+ 热加载 | 开关可回滚，带 TTL |
| **灰度** | Argo Rollouts / Flagger | 按 release set 整体切，不单切一项 |
| **回滚** | Argo Rollouts `undo` / 蓝绿 | 一键，≤1 min |

KEDA 的关键配置（把"排队数"而不是 CPU 当指标）：

```yaml
triggers:
- type: prometheus
  metadata:
    query: sum(vllm:num_requests_waiting{pool="decode"})
    threshold: "64"          # 排队超过 64 就扩
    activationThreshold: "8"
```

**为什么不是 CPU**：GPU 利用率到 100% 时已经晚了；排队数在饱和前 30 秒就会抬头。

## 6. 三个必须自建的组件

### 6.1 路由层（Affinity Router）

| 项 | 内容 |
|---|---|
| **为什么必须自建** | 传统负载均衡按"连接数最少"分发，会打散会话，KV 全废 |
| **怎么做** | ① 路由键 = `hash(tenant_id + session_id)`；② 路由表放 Redis，实例每 5 s 心跳续租；③ 目标实例不可达时回退到"冷实例"，同时触发事件重放重建上下文 |
| **达标线** | 亲和命中 ≥95%；路由收敛 ≤5 s；单实例故障时迁移 ≤10 s；回退请求 TTFT ≤2 s |
| **常见错误** | 用随机或轮询 → 命中率趋近 0，等于每次都冷启动 |

### 6.2 配额中心（Quota Center）

| 项 | 内容 |
|---|---|
| **为什么必须自建** | 传统限流按 QPS，AI 的稀缺资源是 GPU 秒 |
| **怎么做** | ① 三维配额：QPS / token-per-second / inflight；② 滑动窗口计数，本地预扣 + 中心校正（误差 <0.1%）；③ 支持租户间借调（空闲租户的额度可被借用，10 s 内生效） |
| **达标线** | 计数误差 <0.1%；配额变更 ≤10 s 全局生效；单点故障不影响放行 |
| **推翻条件** | 当租户数 <10 时可退化为静态配置，不必上中心 |

### 6.3 版本矩阵（Release Matrix）

| 项 | 内容 |
|---|---|
| **为什么必须自建** | 传统发布只有"代码版本"，AI 有模型、Prompt、工具 schema 三套，且会互相不兼容 |
| **怎么做** | ① 三套版本组成一个不可拆的 release set（如 `m4.1-p7-t3`）；② 每个 set 必须过 50 条黄金用例；③ 灰度时整个 set 一起切，不允许单独切其中一项 |
| **达标线** | 每个 set 有用例覆盖率 100%；回滚 ≤1 min；非法组合在 CI 阶段就拒绝 |
| **反例** | 只灰度模型不灰度 Prompt → 指标全绿，质量掉了（见 §6 第七条） |

## 7. 传统架构里完全没有的六件事

上面三个是"改造出来的"，下面六个是"凭空长出来的"——传统互联网没有对应物。

| 新增件 | 传统架构为什么没有 | 怎么做 | 达标线 | 章节 |
|---|---|---|---|---|
| **token 计量** | Web 按请求计费，一次请求一个价 | 每一跳打点，input / cached / output 分开计 | 两侧对账差 <0.5% | 15 |
| **模型网关** | 后端只有一个版本 | 按版本 / 租户 / 降级状态路由 | 路由决策 ≤2 ms | 24 |
| **KV 生命周期** | 没有显存这种"带状态的缓存" | 块分配、驱逐、跨实例迁移 | 碎片率 <5% | 10、10B |
| **评测门禁** | 代码测试通过就能发 | 黄金集 + 回归 + 人工抽检 | 回归通过率 100% | 7 |
| **成本归因** | 一台机器跑一个服务，成本天然可分 | 五维打标：租户/会话/功能/模型/Prompt | 归因覆盖率 ≥99% | 16 |
| **提示词版本** | 无 | 与代码同仓管理，可 diff、可回滚 | 回滚 ≤1 min | 36 |

**判断标准**：如果你的架构图里这六个位置是空的，那说明还在用 Web 服务的形状套 AI 服务。

## 8. 四个案例：为什么失效

### 8.1 案例一：加机器为什么是阶梯不是滑杆

传统服务扩容：多起一个 Pod，容量 +1/N，秒级生效。

GPU 扩容的真实路径：

```
申请机器 → 开机 → 拉镜像 → 加载 200 GB 权重 → 预热 → 可服务
  30 s      3-5 min   1 min      2-3 min      30 s    ≈ 7-10 min
```

而且扩的不是"1 张卡"，是 **TP8 = 8 卡一个实例**——因为 200B 模型的权重切不开到单卡。

| 步骤 | 耗时 | 能优化吗 |
|---|---|---|
| 节点开机（云上） | 3–5 min | 用预留池 |
| 镜像拉取 | 30–60 s | 预置镜像 |
| **权重加载 200 GB**（200B FP8） | 2–3 min | P2P 分发、本地 NVMe 缓存 |
| 预热（跑几个请求） | 30 s | 冷启动预热脚本 |
| **合计** | **7–10 min** | 最优可压到 3–4 min |

推论：**容量是阶梯，不是滑杆**。2512 卡扩 10% 是 251 卡 ≈ 31 个 TP8 实例，
一次性要加载 31 × 200 GB = 6.2 TB——存储带宽会先成为瓶颈。

> 这就是第 33 章要讲"预热池"的原因：**你不可能等它扩，只能提前准备好。**

**慢的物理原因不在这里，在下一层**：为什么必须整卡 8 张、为什么镜像 8–15 GB、
为什么驱动不能进容器——这些是 K8s 与 GPU 运行时决定的，展开见 **第 32 章**。
本章只记结论：**容量是阶梯**。

### 8.2 案例二：一次重试有多贵

传统服务重试：CPU 空闲时成本接近 0。

LLM 重试：**要把整段上下文重新 prefill 一遍**。

```
一次 8000 token 的 prefill ≈ 0.4 GPU·秒（按 20,000 tok/s/GPU）
```

现在算一笔账：

| 场景 | 重试请求占比 | 额外 GPU | 后果 |
|---|---|---|---|
| 健康 | 0.1% | 2.8 张 | 无感 |
| 轻微抖动 | 1% | **28 张** | 吃掉一个机柜 |
| 故障中（重试 3 次） | 全部重试 3 次 | **+200%** | 雪崩 |

**1% 的重试 = 28 张卡。** 这就是为什么第 24 章要把"重试预算"写进契约：
重试不是免费的，它按 prefill 全价收费。

更进一步：**重试会和降级打架**。过载时你降级到小模型，客户端超时重试，
重试打到已经降级的池子，池子更慢，超时更多——正反馈直到崩溃。

### 8.3 案例三：为什么限流放在网关会失效

网关看到的是 QPS，GPU 的瓶颈是 **token/s**。

假设 7000 QPS 里有 5% 是长文档：

| 请求类型 | 占比 | 每请求 token | 贡献 token/s |
|---|---|---|---|
| 普通对话 | 95% | 800 | 5,320,000 |
| 长文档分析 | 5% | 32,000 | 11,200,000 |

**5% 的请求贡献了 68% 的算力消耗。** 但按 QPS 限流，它们只占 5% 的额度。

后果：

1. 长请求"合法地"占用了 40 倍的算力；
2. 短请求把额度吃满后，长请求开始排队，TTFT 从 800 ms 涨到 12 s；
3. 你以为是"容量不够"，其实是"额度分配错了"。

正确做法是**双维度限流**：

```python
def should_admit(tenant, req):
    # 维度一：QPS（防止请求数打爆调度器）
    if tenant.qps_used >= tenant.qps_quota:
        return False, "qps"
    # 维度二：token/s（防止算力被合法地偷走）
    cost = req.input_tokens + req.max_output * 0.5   # 输出按一半预估
    if tenant.tokens_used + cost > tenant.token_quota:
        return False, "token"
    # 维度三：在飞请求（防止 KV 打满）
    if tenant.inflight >= tenant.inflight_limit:
        return False, "inflight"
    return True, None
```

三个维度缺一不可：QPS 管调度器，token 管 GPU，在飞数管显存。

### 8.4 案例四：多活为什么必须变成多 cell

传统多活：两个机房各接 50% 流量，挂一个切另一个，用户无感。

LLM 的会话是有状态的，KV 就在显存里：

```
一个 32K 上下文的会话，KV ≈ 32K × 120 KB = 3.84 GB
跨区专线 10 Gbps ≈ 1.25 GB/s → 光传输就要 3.1 秒
```

而且不只是"慢"：会话一旦迁到另一个实例，**前缀缓存全部失效**，
下一个请求要重新 prefill 32K token，TTFT 从 600 ms 变成 4 s。

| 方案 | 代价 |
|---|---|
| 全局多活 | 每次迁移 3.84 GB，p99 +3 s，缓存全废 |
| **多 cell** | 每个 cell 独立闭环，会话不迁移；故障时该 cell 用户受影响 |

结论：**放弃"全局多活"，改"多 cell + 单 cell 高可用"**。
可用性的说法也要改：不是"整体 99.9%"，而是"单 cell 99.9%，cell 间故障不扩散"。

## 9. 照抄会死的七件事

| 照抄的做法 | 什么时候死 | 死法 |
|---|---|---|
| Redis 缓存回答 | 上线第一天 | 命中率 8%，白占内存 |
| MQ 削峰 | 第一次大促 | 堆 10 万条，内存爆，GPU 空转 |
| 只按 QPS 限流 | 长文档功能上线 | 5% 请求吃掉 68% 算力 |
| 无状态扩容 | 流量突增 | 新实例冷 KV，TTFT 4 s |
| 全局多活 | 跨区部署 | KV 跨区传输，p99 爆炸 |
| 失败重试 3 次 | 一次抖动 | 放大 3.6 倍，雪崩 |
| 灰度按 5% 用户切 | 三套版本错配 | 指标全绿，质量掉了 |

**第七条最隐蔽**：模型灰度了，Prompt 没灰度，评测集又没覆盖这个组合——
监控上看不出任何异常，只有用户投诉"最近变笨了"。

### 9.1 改造顺序：先动哪个

| 顺序 | 改什么 | 为什么先改它 | 不先改的后果 |
|---|---|---|---|
| 1 | 限流加 token 维度 | 成本最低，收益立刻可见 | 后面所有优化都在给长请求打工 |
| 2 | 缓存对象换成 KV/前缀 | 命中率从 8% 到 85% | 加多少卡都不够 |
| 3 | 重试加预算 | 一次抖动就会暴露 | 故障时放大 3 倍 |
| 4 | 扩容改预热池 | 周期最长，要提前排期 | 每次大促都靠人肉扛 |
| 5 | 多活改多 cell | 架构级，动一次管三年 | 晚改要还技术债 |

## 10. 失败模式

| 现象 | 根因 | 怎么发现 | 怎么修 |
|---|---|---|---|
| 扩容永远慢一步 | 把 GPU 当无状态服务 | 扩容耗时 vs 流量爬坡时间 | 预热池 + 预测式（33 章） |
| 缓存不命中还占内存 | 缓存对象选错 | 命中率 <20% | 缓存 KV 不缓存响应 |
| 削峰削不动 | 算力不可存储 | MQ 堆积且 GPU 饱和 | 准入控制替代排队（25 章） |
| 长请求饿死短请求 | 单一维度限流 | p99 与 p50 差距拉大 | token 维度限流 |
| 抖动变雪崩 | 重试放大 | 重试率突增 | 重试预算 + 熔断 |
| 灰度后质量下降 | 版本矩阵没维护 | 只有主观反馈 | 三套版本强绑定（36 章） |
| 越重试越崩 | 重试与降级互相激化 | 重试率随错误率同步上升 | 重试预算 + 降级期间禁重试 |

最后一条是个正反馈环：过载 → 降级 → 更慢 → 超时 → 重试 → 更过载。
**打破它只有一个办法：让重试本身也有预算，用完了就不再试。**
