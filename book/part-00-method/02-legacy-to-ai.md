# 第 02 章 · 传统互联网架构在 AI 服务中的复用、变形与失效

> 读完你能回答：
> ① 哪些经典模式可以原样搬过来，哪些必须改，哪些照抄就会死？
> ② 为什么"加机器"在 GPU 上是阶梯而不是滑杆？
> ③ 为什么限流放在网关会失效？
> ④ 一次重试到底有多贵？

---

## 1. 问题：按电商那套设计，三个月后被推翻

一个典型的重构事故，几乎每个团队都会走一遍：

> 团队按成熟电商架构设计了 Agent 平台：无状态服务 + 水平扩展 + Redis 缓存 + MQ 削峰 + 网关限流。
> 上线两周后，五个问题同时爆发。

| 设计 | 预期 | 实际 | 根因 |
|---|---|---|---|
| 无状态 + 水平扩展 | 加机器就扩容 | 扩 10% 要 10 分钟，期间流量已经涨完 | GPU 扩容有加载成本 |
| Redis 缓存回答 | 命中率 60%+ | 命中率 8% | 用户问题几乎不重复 |
| MQ 削峰 | 峰值排队，谷时消化 | 堆了 10 万条，GPU 还是 7000 QPS | 算力不能"存起来" |
| 网关限流 | 保护后端 | 短请求占满额度，长请求全排队 | 瓶颈是 token 不是 QPS |
| 失败重试 3 次 | 提高成功率 | 一次抖动变成雪崩 | 重试成本是 prefill 全量 |

**五个问题指向同一件事**：AI 服务不是"另一种 Web 服务"，它是
**有状态的、按 token 计费的、排队不可缓冲的计算服务**。

这一章不给结论，给**判据**——让你拿到任何一个经典模式，能自己判断它属于哪一档。

---

## 2. 一条判据：三问定性

拿到一个传统模式，先问三个问题：

| 问题 | 如果答案是… | 结论 |
|---|---|---|
| ① 瓶颈是"并发连接"还是"计算/带宽"？ | 计算/带宽 | 传统扩容逻辑失效 |
| ② 状态能不能外置？ | 不能（KV 在显存里） | 无状态假设失效 |
| ③ 计费单位是"请求"还是"token"？ | token | 限流/配额/成本模型全要改 |

```
拿到一个传统模式
  ├─ ① 瓶颈是计算/带宽？ ──是──▶ 传统扩容逻辑失效
  ├─ ② 状态能外置？     ──否──▶ 无状态假设失效
  └─ ③ 计费按 token？   ──是──▶ 限流/配额/成本模型全改
```

三问全过，才能原样复用；中一个，就要变形；中两个以上，基本失效。

## 3. 判定表：13 个经典模式

| 经典模式 | 判定 | 为什么 | 怎么改 |
|---|---|---|---|
| **无状态水平扩展** | **变形** | GPU 有状态：KV、前缀树都在显存 | 路由亲和 + 会话粘性 |
| **连接池** | 复用 | 到引擎的 gRPC 池仍然必要 | 容量按 KV 显存算，不按连接数 |
| **多级缓存** | **变形** | 缓存的是 KV 不是响应 | 前缀缓存，命中率 85% vs 8% |
| **MQ 削峰** | **失效** | 算力不能"先存后算" | 只能准入控制 + 拒绝 |
| **限流** | **变形** | 瓶颈是 token/s，不是 QPS | 双维度：QPS + token/s |
| **熔断** | 复用 | 语义没变 | 阈值按 token 与在飞数设 |
| **降级** | **变形** | 降级目标是"更小的模型/规则" | L0–L5 阶梯（第 35 章） |
| **多活 / 单元化** | **变形** | KV 不跨区传输 | 多 cell，会话内闭环 |
| **分库分表** | 复用 | 数据模型没变 | 按 tenant 分片 + 时间分区 |
| **幂等** | 复用+ | 工具调用有副作用，比写接口更关键 | 幂等键 + 副作用日志 |
| **灰度发布** | **扩展** | 变成三套版本：模型 / Prompt / 工具 | 版本矩阵（第 36 章） |
| **压测** | **变形** | 必须按长度分布打 | 开环 + 生产分布（第 12 章） |
| **重试** | **慎用** | 重试要重跑 prefill | 重试预算 + 只重试可重试错误 |

**判定为"复用"的只有 4 个**（连接池、熔断、分库分表、幂等）。
剩下 9 个全部要改——这个比例本身就是结论：**传统经验能直接用的部分不到三分之一**。

## 4. 三个深挖：为什么失效

### 4.1 案例一：加机器为什么是阶梯不是滑杆

传统服务扩容：多起一个 Pod，容量 +1/N，秒级生效。

GPU 扩容的真实路径：

```
申请机器 → 开机 → 拉镜像 → 加载 400 GB 权重 → 预热 → 可服务
  30 s      3-5 min   1 min      3-5 min      30 s    ≈ 8-10 min
```

而且扩的不是"1 张卡"，是 **TP8 = 8 卡一个实例**——因为 200B 模型的权重切不开到单卡。

| 步骤 | 耗时 | 能优化吗 |
|---|---|---|
| 节点开机（云上） | 3–5 min | 用预留池 |
| 镜像拉取 | 30–60 s | 预置镜像 |
| **权重加载 400 GB** | 3–5 min | P2P 分发、本地 NVMe 缓存 |
| 预热（跑几个请求） | 30 s | 冷启动预热脚本 |
| **合计** | **8–10 min** | 最优可压到 3–4 min |

推论：**容量是阶梯，不是滑杆**。2512 卡扩 10% 是 251 卡 ≈ 31 个 TP8 实例，
一次性要加载 31 × 400 GB = 12.4 TB——存储带宽会先成为瓶颈。

> 这就是第 33 章要讲"预热池"的原因：**你不可能等它扩，只能提前准备好。**

### 4.2 案例二：一次重试有多贵

传统服务重试：CPU 空闲时成本接近 0。

LLM 重试：**要把整段上下文重新 prefill 一遍**。

```
一次 8000 token 的 prefill ≈ 0.4 GPU·秒（按 20,000 tok/s/GPU）
```

现在算一笔账：

| 场景 | 重试请求占比 | 额外 GPU | 后果 |
|---|---|---|---|
| 健康 | 0.1% | 2.8 张 | 无感 |
| 轻微抖动 | 1% | **28 张** | 吃掉一个机柜 |
| 故障中（重试 3 次） | 全部重试 3 次 | **+200%** | 雪崩 |

**1% 的重试 = 28 张卡。** 这就是为什么第 24 章要把"重试预算"写进契约：
重试不是免费的，它按 prefill 全价收费。

更进一步：**重试会和降级打架**。过载时你降级到小模型，客户端超时重试，
重试打到已经降级的池子，池子更慢，超时更多——正反馈直到崩溃。

### 4.3 案例三：为什么限流放在网关会失效

网关看到的是 QPS，GPU 的瓶颈是 **token/s**。

假设 7000 QPS 里有 5% 是长文档：

| 请求类型 | 占比 | 每请求 token | 贡献 token/s |
|---|---|---|---|
| 普通对话 | 95% | 800 | 5,320,000 |
| 长文档分析 | 5% | 32,000 | 11,200,000 |

**5% 的请求贡献了 68% 的算力消耗。** 但按 QPS 限流，它们只占 5% 的额度。

后果：

1. 长请求"合法地"占用了 40 倍的算力；
2. 短请求把额度吃满后，长请求开始排队，TTFT 从 800 ms 涨到 12 s；
3. 你以为是"容量不够"，其实是"额度分配错了"。

正确做法是**双维度限流**：

```python
def should_admit(tenant, req):
    # 维度一：QPS（防止请求数打爆调度器）
    if tenant.qps_used >= tenant.qps_quota:
        return False, "qps"
    # 维度二：token/s（防止算力被合法地偷走）
    cost = req.input_tokens + req.max_output * 0.5   # 输出按一半预估
    if tenant.tokens_used + cost > tenant.token_quota:
        return False, "token"
    # 维度三：在飞请求（防止 KV 打满）
    if tenant.inflight >= tenant.inflight_limit:
        return False, "inflight"
    return True, None
```

三个维度缺一不可：QPS 管调度器，token 管 GPU，在飞数管显存。

### 4.4 案例四：多活为什么必须变成多 cell

传统多活：两个机房各接 50% 流量，挂一个切另一个，用户无感。

LLM 的会话是有状态的，KV 就在显存里：

```
一个 32K 上下文的会话，KV ≈ 32K × 120 KB = 3.84 GB
跨区专线 10 Gbps ≈ 1.25 GB/s → 光传输就要 3.1 秒
```

而且不只是"慢"：会话一旦迁到另一个实例，**前缀缓存全部失效**，
下一个请求要重新 prefill 32K token，TTFT 从 600 ms 变成 4 s。

| 方案 | 代价 |
|---|---|
| 全局多活 | 每次迁移 3.84 GB，p99 +3 s，缓存全废 |
| **多 cell** | 每个 cell 独立闭环，会话不迁移；故障时该 cell 用户受影响 |

结论：**放弃"全局多活"，改"多 cell + 单 cell 高可用"**。
可用性的说法也要改：不是"整体 99.9%"，而是"单 cell 99.9%，cell 间故障不扩散"。

## 5. 照抄会死的七件事

| 照抄的做法 | 什么时候死 | 死法 |
|---|---|---|
| Redis 缓存回答 | 上线第一天 | 命中率 8%，白占内存 |
| MQ 削峰 | 第一次大促 | 堆 10 万条，内存爆，GPU 空转 |
| 只按 QPS 限流 | 长文档功能上线 | 5% 请求吃掉 68% 算力 |
| 无状态扩容 | 流量突增 | 新实例冷 KV，TTFT 4 s |
| 全局多活 | 跨区部署 | KV 跨区传输，p99 爆炸 |
| 失败重试 3 次 | 一次抖动 | 放大 3.6 倍，雪崩 |
| 灰度按 5% 用户切 | 三套版本错配 | 指标全绿，质量掉了 |

**第七条最隐蔽**：模型灰度了，Prompt 没灰度，评测集又没覆盖这个组合——
监控上看不出任何异常，只有用户投诉"最近变笨了"。

### 5.1 改造顺序：先动哪个

| 顺序 | 改什么 | 为什么先改它 | 不先改的后果 |
|---|---|---|---|
| 1 | 限流加 token 维度 | 成本最低，收益立刻可见 | 后面所有优化都在给长请求打工 |
| 2 | 缓存对象换成 KV/前缀 | 命中率从 8% 到 85% | 加多少卡都不够 |
| 3 | 重试加预算 | 一次抖动就会暴露 | 故障时放大 3 倍 |
| 4 | 扩容改预热池 | 周期最长，要提前排期 | 每次大促都靠人肉扛 |
| 5 | 多活改多 cell | 架构级，动一次管三年 | 晚改要还技术债 |

## 6. 失败模式

| 现象 | 根因 | 怎么发现 | 怎么修 |
|---|---|---|---|
| 扩容永远慢一步 | 把 GPU 当无状态服务 | 扩容耗时 vs 流量爬坡时间 | 预热池 + 预测式（33 章） |
| 缓存不命中还占内存 | 缓存对象选错 | 命中率 <20% | 缓存 KV 不缓存响应 |
| 削峰削不动 | 算力不可存储 | MQ 堆积且 GPU 饱和 | 准入控制替代排队（25 章） |
| 长请求饿死短请求 | 单一维度限流 | p99 与 p50 差距拉大 | token 维度限流 |
| 抖动变雪崩 | 重试放大 | 重试率突增 | 重试预算 + 熔断 |
| 灰度后质量下降 | 版本矩阵没维护 | 只有主观反馈 | 三套版本强绑定（36 章） |
| 越重试越崩 | 重试与降级互相激化 | 重试率随错误率同步上升 | 重试预算 + 降级期间禁重试 |

最后一条是个正反馈环：过载 → 降级 → 更慢 → 超时 → 重试 → 更过载。
**打破它只有一个办法：让重试本身也有预算，用完了就不再试。**

## 7. 验收：怎么证明这张判定表用对了

| 检查项 | 通过标准 |
|---|---|
| 每个传统组件都有判定 | 13 个模式逐个标注了复用/变形/失效 |
| 变形项写了"怎么改" | 不是只写"要改" |
| 失效项有替代方案 | 例如"MQ 削峰 → 准入控制" |
| 重试有预算 | 有 max_retries + 预算上限 + 可重试错误白名单 |
| 限流有 token 维度 | 不只是 QPS |
| 缓存对象正确 | 明确缓存 KV / 前缀，不是完整响应 |

## 9. 收口

> **传统互联网的每一件工具都还在，但它们的假设变了：
> 从"无状态、可按请求计费、排队可以缓冲"，
> 变成"有状态、按 token 计费、排队等于烧钱"。**
