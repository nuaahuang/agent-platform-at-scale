# 第 01 章 · 规模、SLO（Service Level Objective） 与经济红线

> 读完你能回答：
> ① 2000 万 DAU 到底要多少卡？
> ② 三层 SLO 分别由谁负责、违约长什么样？
> ③ 每轮 0.52 分是怎么算出来的，什么情况下会变成 1 分？

---

## 1. 问题：三个数字决定这个系统能不能做

任何"亿级 Agent 平台"的方案评审，本质上只问三件事：

| 问题 | 答错的后果 | 本章给什么 |
|---|---|---|
| 要多少卡 | 买多了烧钱，买少了上线即熔断 | 2512 卡的完整推导 |
| 能不能扛住 | SLO 崩了，用户流失 | 三层 SLO 与违约形态 |
| 赚不赚钱 | 规模越大亏得越多 | 0.52 分/轮的成本结构 |

**先算账，再画架构图。** 反过来做的方案，90% 会在第一次大促时被推翻——
因为它不知道自己离悬崖有多远。

三个常见死法，本章逐一拆掉：

1. 拿"平均 QPS"买卡 → 峰值直接熔断；
2. 拿"连接数"买卡 → 多买 88 倍；
3. 只算 GPU 不算存储带宽 → 预算超支 30%。

## 2. 三层 SLO：体验、系统、成本

SLO 不是一句话，是三层。每层有独立的负责人和违约形态。

| 层 | 指标 | 目标 | 谁负责 | 违约表现 |
|---|---|---|---|---|
| **体验** | TTFT（Time To First Token） p95 | ≤ 800 ms | 推理 + 网关 | 用户觉得"卡住了" |
| | TPOT（Time Per Output Token） p95 | ≤ 50 ms | 引擎调度 | 字一个一个蹦 |
| | 端到端 p95 | ≤ 9 s | 全链路 | 用户中途退出 |
| | 首屏错误率 | < 0.5% | 网关 | 直接看到报错 |
| **系统** | 可用性 | 99.9%（月 43.2 min） | 平台 | 大面积不可用 |
| | 队列等待 p95 | ≤ 200 ms | 调度器 | 慢但没报错 |
| | 降级率 | < 5% | 路由 | 答得差但能答 |
| **成本** | 单轮成本 | ≤ 0.60 分 | 架构 | 越卖越亏 |
| | 毛利率 | ≥ 45% | 业务 | 融资故事破裂 |
| | 缓存命中 | ≥ 65% | 引擎 | 成本悄悄上升 |

**三层会互相打架**，这是设计时最容易被忽略的：

- 想降成本 → 提高 batch → TPOT 变差 → 体验层违约；
- 想保体验 → 扩容 → 成本层违约；
- 想保可用 → 降级到小模型 → 体验层"达标"但质量崩。

所以 SLO 必须**同时写清"谁让步"**：默认顺序是 **成本 < 体验 < 可用性**，
即宁可多花钱也不能不可用，但宁可慢一点也不能超预算。这个顺序要写进 ADR，
否则每次故障复盘都会变成扯皮。

### 2.1 先把四个词定死：SLI（Service Level Indicator） / SLO / SLA（Service Level Agreement） / 错误预算

这四行业最常混用的词，本书用法如下——后面 39 章不再重复解释。

| 词 | 是什么 | 本书的例子 | 常见误用 |
|---|---|---|---|
| **SLI**<br>*Service Level Indicator*（指标） | 实际测出来的数 | TTFT p95 = 780 ms | 把"目标"当指标 |
| **SLO**<br>*Service Level Objective*（目标） | 对 SLI 的内部目标值 | TTFT p95 ≤ 800 ms | 写成"尽量快" |
| **SLA**<br>*Service Level Agreement*（承诺） | 对外合同，违约要赔 | 月可用性 ≥ 99.9%，否则赔 10% 月费 | 拿 SLO 当 SLA 对外承诺 |
| **错误预算**<br>*Error Budget* | 允许失败的额度 = 1 − SLO | 99.9% → 每月 43.2 分钟 / 1,810 万次失败 | 当成"可以随便用" |

错误预算的算法（以本系统为例）：

```
月总请求 = 7000 QPS × 2,592,000 s = 1.81e10 次
允许失败 = 1.81e10 × 0.1%            = 1,810 万次
允许不可用 = 30 天 × 24 h × 0.1%     = 43.2 分钟
```

**错误预算的用法是"刹车"，不是"额度"**：本月烧掉 60%，就该冻结非必要发布，
而不是"还剩 40% 可以继续激进"。这一点决定了第 36 章灰度发布的节奏。

常用可用性换算，背下来比查表快：

| SLO | 每月不可用 | 每年不可用 |
|---|---|---|
| 99% | 7.2 小时 | 3.65 天 |
| 99.9% | 43.2 分钟 | 8.76 小时 |
| 99.95% | 21.6 分钟 | 4.38 小时 |
| 99.99% | 4.32 分钟 | 52.6 分钟 |

### 2.2 为什么是 800ms / 50ms / 9s

**先把一件事说清楚：这是三条独立约束，不是一条公式。**

| 指标 | 目标 | 独立依据 | 破了会怎样 |
|---|---|---|---|
| TTFT | ≤ 800 ms | 人类感知"即时响应"上限约 1 s | 用户以为没反应，重复点击 |
| TPOT | ≤ 50 ms | 中文阅读速度约 20 字/秒，每字 50 ms | 流式输出一顿一顿，像卡住 |
| 端到端 | ≤ 9 s | 单轮任务的耐心上限（含思考与工具调用） | 用户中途退出 |

三个数管三件不同的事：**"多久开始"、"流不流畅"、"什么时候结束"**。
它们各自独立，任一条破了都是事故，不能拿"另外两条还不错"来抵。

### 2.3 为什么端到端不能由前两项乘出来

一个直觉的写法是：

```
端到端 = TTFT + 输出长度 × TPOT
      = 800 ms + 350 × 50 ms = 18.3 s   ← 错
```

错在**分位数不可加**：

```
p95(端到端) ≠ p95(TTFT) + p95(decode)
```

TTFT 最慢的那 5% 请求，和 TPOT 最慢的那 5% 请求，**大概率不是同一批**。
真要把两个分布合成端到端分布，得做卷积；工程上没人这么算，直接实测。

正确用法是把这个式子当**量级校验**，而不是推导：

| 组合 | TTFT | 输出 token | TPOT | 端到端 |
|---|---|---|---|---|
| 典型一轮（p50） | 500 ms | 150 | 20 ms | 3.5 s |
| 长回答（p95 组合） | 800 ms | 300 | 27 ms | **8.9 s** |
| 若两项 p95 同时发生 | 800 ms | 350 | 50 ms | 18.3 s（真实中不存在） |

表格第二行说明：**9 秒对应的组合是"TTFT 打满 + 300 token + 每 token 27 ms"**。
50 ms 的 TPOT 约束比 27 ms 更严——它是用来防单步卡顿的**独立护栏**，
不是端到端公式里的那个系数。

> **常见错误**：为了"验证"9 秒，拿 350 × 50 ms 去算，算出 18.3 秒，然后怀疑数据错了。
> 两个 p95 不能相乘。要么用同一分位的实测值，要么只做量级判断。

## 3. 三个口径：62 万、2.5 万、7000

同一套业务，能算出三个差 89 倍的"并发"。混用是架构评审最常见的翻车点。

| 口径 | 公式 | 数值 | 用来定什么 |
|---|---|---|---|
| **同时在线** | DAU × 1.5 会话 × 600 s ÷ 86400 × 3 | **62 万** | 连接数、网关容量、内存 |
| **在飞请求** | QPS × 端到端时长 | **2.5 万**（3.5 s）/ 6.3 万（9 s） | KV 显存、并发会话 |
| **峰值 QPS** | 日轮次 × 12% ÷ 3600 × 1.4 | **7000** | 算力、GPU 卡数 |

### 3.1 三个数为什么差这么多

```
62 万在线  ──(只有 4% 在真正发请求)──▶  2.5 万在飞
2.5 万在飞 ──(每个请求活 3.5 秒)──────▶  7000 QPS
```

- **在线 ≠ 请求**：大部分人挂着不说话；
- **请求 ≠ QPS**：一个请求持续 3.5 秒，所以 QPS = 在飞 ÷ 3.5；
- **QPS ≠ 峰值**：12% 的日轮次挤在 1 小时里，还要再乘 1.4 的突发系数。

**拿 62 万去买 GPU，会多买 89 倍。** 这个错误在真实项目里出现过不止一次——
因为它看起来"最保守"。

### 3.2 12% 和 1.4 是哪来的

| 系数 | 含义 | 典型值 | 怎么校准 |
|---|---|---|---|
| 12% | 峰值 1 小时占日轮次比例 | 10%–15% | 看埋点：峰值小时轮次 ÷ 日轮次 |
| 1.4 | 峰值小时内的突发系数 | 1.3–1.6 | 峰值分钟 QPS ÷ 峰值小时均值 |
| 3 | 在线人数 ÷ DAU | 2–4 | 会话时长 ÷ 86400 × 日活系数 |

三个系数都**必须用自家埋点校准**，抄别人的会差 30% 以上。

## 4. 从 DAU 到 2512 张卡

推导链五步，每步都做单位消去。

### 4.1 第一步：日轮次

```
1.5 亿轮/日 = 2000 万 DAU × 1.5 会话/人 × 5 轮/会话
```

### 4.2 第二步：峰值 QPS

```
峰值小时轮次 = 1.5e8 × 12%        = 1.8e7 轮
平均峰值 QPS = 1.8e7 ÷ 3600 s     = 5000 轮/s
峰值 QPS     = 5000 × 1.4         = 7000 轮/s
```

注意这里除以 **3600**（一小时），不是 86400——因为 12% 是"集中在一小时"的比例。

### 4.3 第三步：Prefill 算力

只有**未命中缓存**的输入才需要真算：

```
峰值 prefill token/s = 7000 × 5000 × (1 − 70%) = 10.5e6 tok/s

每 token 需要的算力 = 2 × 激活参数 = 2 × 30e9 = 6e10 FLOP

所需 FLOPS = 10.5e6 × 6e10 = 6.3e17 FLOP/s
单卡可用   = 1.98e15 × 35% (MFU) = 6.93e14 FLOP/s

Prefill 卡 = 6.3e17 ÷ 6.93e14 = 909 张
```

### 4.4 第四步：Decode 算力

Decode 不是算力受限，是**带宽受限**，所以用实测吞吐而不是 FLOPs：

```
Decode 卡 = 7000 QPS × 350 token ÷ 3500 tok/s/卡 = 700 张
```

3500 这个数从哪来？H800 3.35 TB/s ÷ 每 token 要读的 30 GB 权重 ≈ 111 tok/s，
乘上 batch 的效率因子才到 3500。推导见第 8 章与 §5.2。

### 4.5 第五步：冗余与取整

```
原始需求 = 909 + 700 = 1609 张
业务冗余 × 1.3（应对突发与故障）
双 AZ    × 1.2（跨可用区不能满打满算）

理论卡数 = 1609 × 1.3 × 1.2 = 2510
按 8 卡一节点取整 = 2512 张 = 314 个节点
```

### 4.6 全链条速查

| 步骤 | 公式 | 结果 |
|---|---|---|
| 日轮次 | 20e6 × 1.5 × 5 | 1.5e8 |
| 峰值 QPS | 1.5e8 × 0.12 ÷ 3600 × 1.4 | 7000 |
| Prefill tok/s | 7000 × 5000 × 0.3 | 10.5e6 |
| Prefill 卡 | tok/s × 6e10 ÷ 6.93e14 | 909 |
| Decode 卡 | 7000 × 350 ÷ 3500 | 700 |
| 含冗余 | (909+700) × 1.3 × 1.2 | 2512 |

### 4.7 备选估法：自上而下（从预算反推规模）

上面是自下而上。反过来问同样重要：**给我 3 个亿，能撑多大？**

从上表能提炼两个常数：

- **固定成本 ≈ 1.23 亿/年**（训练 0.33 + 存储带宽 0.90），与 DAU 无关；
- **边际成本 ≈ 0.08 亿/年 每百万 DAU**（5m→30m 区间实测斜率 0.08–0.081）。

| 年预算 | 可支撑 DAU | 单轮成本 |
|---|---|---|
| 1.55 亿 | 400 万 | 1.42 分 |
| 2.03 亿 | 1,000 万 | 0.74 分 |
| 2.83 亿 | 2,000 万 | 0.52 分 |
| 3.6 亿 | 3,000 万 | 0.44 分 |
| 5.2 亿 | 5,000 万 | 0.38 分 |

这张表解释了一个残酷的事实：**预算低于 1.23 亿时，连固定成本都盖不住**，
做多大都是亏。所以"先做小规模验证"在重资产平台上是伪命题——
要么一次做到千万级，要么别自建（用 API）。

用 `labs/calc.py` 可一键复算；改任意参数立刻看到卡数变化。

```bash
python3 labs/calc.py
python3 labs/calc.py --ctx 8000        # 上下文翻倍会怎样
python3 labs/calc.py --hit 0.5         # 命中率掉到 50%
```

## 5. 钱：0.52 分/轮的构成

### 5.1 一个节点的年成本

| 项 | 计算 | 年成本 |
|---|---|---|
| 服务器折旧 | ¥120 万 ÷ 3 年 | ¥400,000 |
| 电费 | 6 kW × 8760 h × ¥0.6 × 1.25(PUE) | ¥39,420 |
| 机位 | ¥6,000/月 × 12 | ¥72,000 |
| **合计** | | **¥511,420 / 节点** |

注意：**电费只占 7.7%**。常见的误解是 AI 集群是"电老虎"，其实在当前电价下，
折旧才是大头（78%）。这直接决定了降本优先级：**先提利用率，再谈省电**。

### 5.2 年成本拆解

| 项 | 卡/量 | 年成本 | 占比 |
|---|---|---|---|
| 推理 GPU | 2512 卡 = 314 节点 | 1.61 亿 | 56.7% |
| 训练 GPU | 512 卡 = 64 节点 | 0.33 亿 | 11.6% |
| 存储 + CDN + DB | — | 0.90 亿 | 31.7% |
| **合计** | | **2.83 亿** | 100% |

**存储带宽占 31.7%**，这是"只算 GPU"的方案最容易漏掉的一块。

### 5.3 三个单位成本，分母不同差 15 倍

| 口径 | 公式 | 数值 |
|---|---|---|
| 每轮 | 2.83e8 ÷ (1.5e8 × 365) | **0.517 分** |
| 每 DAU 每天 | 2.83e8 ÷ 365 ÷ 2e7 | **3.88 分** |
| 每百万**总** token | 2.83e8 ÷ 365 ÷ 8.0e5 M | **0.97 元** |
| 每百万**输出** token（全成本） | 2.83e8 ÷ 1.92e7 M | **14.8 元** |
| 每百万**输出** token（仅推理） | 1.61e8 ÷ 1.92e7 M | **8.37 元** |

**同一个系统，"每百万 token"能算出 0.97 和 14.8 两个数，差 15 倍**——
因为前者分母是输入+输出（5350 token），后者只有输出（350 token）。

对外报价用输出口径，对内核算用总口径。**混用会导致定价直接亏 15 倍**，
这是 Token 经济章的起点（第 15–17 章）。

### 5.4 毛利：定价 1 分/轮时

```
年收入 = 1.5e8 × 365 × 0.01 元 = 5.475 亿
年成本 = 2.83 亿
毛利   = 2.645 亿 → 毛利率 48.3%
```

毛利率 48% 看起来健康，但这是 **2000 万 DAU 的规模效应**撑起来的，
下一节会看到小规模时它会变成负数。

## 6. 敏感性：哪个假设最危险

### 6.1 缓存命中率（最危险的杠杆）

| 命中率 | 总卡 | 年成本 | 单轮成本 |
|---|---|---|---|
| 30% | 4,408 | 4.05 亿 | 0.74 分 |
| 50% | 3,456 | 3.44 亿 | 0.63 分 |
| **70%** | **2,512** | **2.83 亿** | **0.52 分** |
| 85% | 1,808 | 2.38 亿 | 0.44 分 |
| 95% | 1,336 | 2.08 亿 | 0.38 分 |

命中率从 70% 掉到 30%，**卡数涨 75%，成本涨 43%**。
而命中率是最容易被产品改动悄悄打掉的东西——换一个 Prompt 模板、
在系统提示里加个时间戳，前缀就全废了。

**这就是为什么前缀缓存必须当成 SLO 来监控，而不是当成优化项。**

### 6.2 上下文长度

| 平均输入 | 总卡 | 年成本 | 单轮成本 |
|---|---|---|---|
| 2,000 | 1,664 | 2.29 亿 | 0.42 分 |
| 5,000 | 2,512 | 2.83 亿 | 0.52 分 |
| 8,000 | 3,368 | 3.38 亿 | 0.62 分 |
| 16,000 | 5,632 | 4.83 亿 | 0.88 分 |

上下文从 5K 翻到 16K，**卡数涨 124%**。这是"支持 32K 上下文"这个需求
在报价单上的真实价格——产品提需求时通常不知道。

### 6.3 规模效应：为什么 2000 万 DAU 是个坎

| DAU | 总卡 | 年成本 | 单轮成本 |
|---|---|---|---|
| 500 万 | 632 | 1.63 亿 | **1.19 分** |
| 1,000 万 | 1,256 | 2.03 亿 | 0.74 分 |
| **2,000 万** | **2,512** | **2.83 亿** | **0.52 分** |
| 3,000 万 | 3,768 | 3.64 亿 | 0.44 分 |
| 5,000 万 | 6,280 | 5.24 亿 | 0.38 分 |

原因：**固定成本被摊薄**。训练 512 卡（0.33 亿）+ 存储带宽（0.90 亿）
合计 1.23 亿，与 DAU 无关。

| DAU | 固定成本占比 | 单轮成本 |
|---|---|---|
| 500 万 | 75% | 1.19 分 |
| 2,000 万 | 43% | 0.52 分 |
| 5,000 万 | 23% | 0.38 分 |

**500 万 DAU 时，按 1 分/轮定价是亏的**（成本 1.19 分）。
这就是为什么这类平台必须做大规模——不是野心，是算术。

## 7. 失败模式：这些数字会怎么骗你

| 现象 | 根因 | 怎么发现 | 怎么修 |
|---|---|---|---|
| 上线即熔断 | 用平均 QPS（292）买了卡 | 峰值队列长度飙升 | 改用峰值 7000 重算 |
| 卡利用率 8% | 用连接数（62 万）买卡 | GPU 空转、成本翻 89 倍 | 按在飞请求与 QPS 算 |
| 预算超支 30% | 只算了 GPU | 存储/CDN 账单 | 把 31.7% 的存储项纳入模型 |
| 命中率悄悄掉 | Prompt 模板变更 | 命中率指标从 70% 掉到 40% | 前缀缓存进 SLO 看板 |
| 毛利为负 | 用总 token 口径定价 | 财务对账差异 15 倍 | 明确报价口径为输出 token |
| 扩到 32K 后成本翻 4 倍 | 产品需求没做成本换算 | 卡数从 2512 涨到 10,176 | 按上下文分档定价 |

最后一行值得单独说：32K 上下文下，KV 与 prefill 同时膨胀，
卡数从 2512 涨到 **10,176 张**、年成本 7.73 亿。
"支持 32K"不是一个功能开关，是一次容量重建。

## 8. 验收：三个数字必须能自己复算

| 数字 | 复算方式 | 允许误差 |
|---|---|---|
| 峰值 QPS = 7000 | `labs/calc.py` 与手算一致 | ±5% |
| 总卡 = 2512 | 五步推导逐步对得上 | ±5% |
| 单轮 = 0.52 分 | 年成本 ÷ 年轮次 | ±3% |

再给三个自测题，答不上说明这章还没吃透：

1. 如果峰值占比从 12% 变成 20%，总卡变成多少？（提示：QPS 线性放大）
2. 如果电价从 0.6 涨到 1.2 元，单轮成本涨多少？（提示：电费只占 7.7%）
3. 如果训练集群从 512 卡砍到 0，单轮成本变多少？（提示：固定成本摊薄）

## 9. 收口

**这三个数字不是估算，是这个系统的物理边界**：

- 2512 张卡由 7000 QPS、5000 上下文、70% 命中率唯一决定；
- 0.52 分/轮由 314 个节点的折旧、电费、机位唯一决定；
- 毛利 48% 只在 2000 万 DAU 成立，规模一缩就变负。

后面 39 章的所有设计，都是在守这三个数——或者，在解释为什么必须改它们。
