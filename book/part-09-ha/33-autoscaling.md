# 第 33 章 · 扩缩容与弹性

> 读完你能回答：
> ① 为什么 HPA（Horizontal Pod Autoscaler，水平 Pod 伸缩器）在 GPU 平台上必然失效？
> ② 预热池该备多少张卡，一年花多少钱？
> ③ 缩容为什么比扩容更危险？
> ④ PD 分离后两个池怎么分别扩，比例漂了怎么办？

---

## 1. 问题：扩容要 10 分钟，流量爬坡只要 20 分钟

电商售后 Agent 的早高峰：

```
9:00   1,736 QPS  →  620 卡
9:05   指标越线，HPA 触发扩容
9:15   第一批实例可用（8–10 分钟）
9:20   流量到顶 7,000 QPS，需要 2,512 卡
       此刻只有约 1,400 卡 → 排队、TTFT 从 600 ms 涨到 4.2 s
9:35   终于补齐，但峰值已经过去 15 分钟
```

这一轮下来，SLO 错误预算烧掉 **30%**（全月只有 43.2 分钟）。

**根因不是扩容慢，是"扩容速度 < 流量变化速度"。**
弹性的目标从来不是"扩得快"，而是**"在需要之前就位"**。

---

## 2. 三个物理约束：为什么快不了

| 环节 | 耗时 | 能否优化 | 优化后 |
|---|---|---|---|
| 节点开机（云上） | 3–5 min | 预留节点池，常备空机 | 0 |
| 镜像拉取 | 8–15 GB，1–3 min | 本地缓存 + P2P 分发 | 20–30 s |
| **权重加载 400 GB** | 3–5 min | 本地 NVMe + P2P 分发 | 2–3 min |
| 预热（跑几个请求） | 30 s | 健康检查通过即可 | 10 s |
| **合计** | **8–15 min** | | **3–4 min** |

即使用尽所有优化手段，天花板也是 **3–4 分钟**。

对比：流量从 1,736 涨到 7,000 只要 **20 分钟**，翻倍只要 **5 分钟**。

> **物理约束决定：反应式扩容永远追不上快变流量。**
> 这不是工程能力问题，是加载 400 GB 权重所需时间的问题。

### 2.1 为什么"干脆多买 30% 卡"不是答案

一个直觉方案：峰值不是 7000 吗？按 1.3 倍备足，不就永远不用扩了？

| 方案 | 卡数 | 年成本 | 结果 |
|---|---|---|---|
| 多买 30% 常备 | +754 卡 | **+¥8,494 万** | 永远够用，但 20 小时在闲置 |
| 短时预热池 | +377 卡 × 6 h | **+¥1,062 万** | 峰值前就位 |

差 **8 倍**。原因很简单：**峰值每天只占 4 小时，但买卡是 24 小时付费。**

弹性要解决的不是"容量够不够"，是"容量在不在正确的时间点"。

---

## 3. 为什么 HPA 必然失效

HPA 的模型是"观察 → 决策 → 执行"，三段都有延迟：

| 延迟段 | 时长 | 来源 |
|---|---|---|
| **指标滞后** | 15–60 s | scrape 间隔 + 聚合窗口 |
| **决策滞后** | 60–300 s | 冷却期、连续 N 个窗口确认 |
| **执行滞后** | 480–900 s | 开机 + 拉镜像 + 加载权重 |
| **总滞后** | **9–20 min** | |

而流量翻倍只要 5 分钟——**总滞后 > 流量变化时间，闭环在数学上就不成立**。

### 3.1 第二个错误：指标选错了

| 指标 | 性质 | 提前量 | 说明 |
|---|---|---|---|
| GPU 利用率 | **滞后** | 0 | 饱和才到 100%，此时已经排队 |
| KV 水位 | 前导 | 60–120 s | 逼近上限说明要拒绝 |
| **排队数**（`num_requests_waiting`） | **前导** | 30–60 s | 饱和前先抬头 |
| TTFT p95 | 前导 | 30–60 s | 用户已经感受到 |

HPA 默认看 CPU，改配自定义指标又走同一套滞后链路。
**用 GPU 利用率做伸缩信号，等于看着后视镜开车。**

## 4. 三种预测信号：在需要之前动手

| 信号 | 提前量 | 准确度 | 实现 | 适用场景 |
|---|---|---|---|---|
| **日周期（cron）** | 30–60 min | 高（±10%） | KEDA cron scaler / 定时任务 | 早高峰、晚高峰 |
| **斜率检测** | 5–10 min | 中 | 网关 QPS 斜率 > 2σ | 突发爬坡 |
| **业务日历** | 小时–天 | 最高 | 大促预案 + 人工确认 | 已知事件 |

三者是**叠加**关系，不是三选一：

```yaml
# 1) 日周期：每天 8:20 提前拉起
triggers:
- type: cron
  metadata:
    timezone: Asia/Shanghai
    start: "20 8 * * *"
    end: "30 23 * * *"
    desiredReplicas: "251"

# 2) 斜率/排队：兜底真实突发
- type: prometheus
  metadata:
    query: sum(vllm:num_requests_waiting{pool="decode"})
    threshold: "64"
```

**cron 负责"可预测的 80%"，prometheus 负责"不可预测的 20%"。**

## 5. 预热池：备多少，花多少钱

### 5.1 定义与公式

**预热池 = 已经加载好权重、随时可接流量的空实例。** 它不是"多买的卡"，
而是"把要用的卡提前推进到就绪态"。

```
预热池容量 = 峰值容量 × 预测误差 × 安全系数
```

| 参数 | 取值 | 依据 |
|---|---|---|
| 峰值容量 | 2,512 卡 | 第 13 章账本 |
| 预测误差 | ±15% | 历史 cron 预测的实际偏差 |
| 安全系数 | 1.0 | 已有 ×1.3 的容量余量 |
| **预热池** | **377 卡 ≈ 47 个 TP8 实例** | |

### 5.2 三档策略与成本

单卡年成本 = 2.83 亿 ÷ 2,512 = **¥112,660/卡·年**。

| 策略 | 池大小 | 存在时长 | 年成本 | 峰值表现 |
|---|---|---|---|---|
| **纯反应式** | 0 | — | 0 | 每次峰值烧 30% 预算 |
| **短时预热池** | 377 卡 | 6 h/天 | **¥1,062 万** | 峰值前就位 |
| **常驻预热池** | 377 卡 | 24 h | ¥4,247 万 | 全天就位 |

**选短时池**：6 小时覆盖早、晚两个高峰，成本是常驻的 1/4。

> 一个容易被忽略的点：如果这些卡本来就是为了峰值买的、夜里也要付折旧，
> 那么"常驻预热"的**边际成本只有电费**（约 ¥4,240/卡·年），不是 ¥112,660。
> 先算清楚你的卡是"自有"还是"弹性租用"，结论完全不同。

### 5.3 三级预热：热、温、冷

预热不是一个二元状态，而是三级，占用不同资源、对应不同提前量：

| 级别 | 状态 | 占用什么 | 就位时间 | 成本 |
|---|---|---|---|---|
| **热** | 进程跑着、KV 为空、健康检查通过 | GPU | 10–30 s | 全额 |
| **温** | 节点就绪、镜像与权重已在本地 NVMe、进程未起 | 磁盘 + 节点 | 2–3 min | 卡的折旧 |
| **冷** | 只有节点，什么都没拉 | 节点 | 8–10 min | 节点费 |

用法是分层覆盖时间轴：

```
峰值前 2 小时  → 温池就位（377 卡）
峰值前 30 分钟 → 温转热（30 s）
峰值中        → 冷池兜底（10 min，接受排队）
```

**热池只覆盖"最后一分钟"，温池覆盖"最后十分钟"。**
只做热池，成本最高；只做冷池，等于没做。

### 5.4 预热池也要管水位

| 水位 | 含义 | 动作 |
|---|---|---|
| < 30% 被占用 | 池子太大 | 缩减池子 |
| 30%–70% | 健康 | — |
| > 70% | 快用完 | 扩容池子或触发 cron 提前 |
| = 100% | 已击穿 | 只能靠 K8s 现开（10 min） |

## 6. 缩容：比扩容更危险

扩容失败只是慢，缩容失败是**直接掉服务**。

### 6.1 正确的缩容流程

```
摘流量（xDS 摘除端点）
   ↓  等待 ≥ 30 s（覆盖最长在飞请求 9 s + 排空余量）
等在飞请求清零
   ↓
丢弃 KV（或写入 swap）
   ↓
释放实例
```

### 6.2 四个坑

| 坑 | 后果 | 解法 |
|---|---|---|
| 立刻 kill | 在飞请求 500，用户看到失败 | drain ≥30 s |
| 缩完立刻又扩 | 整夜抖动 | **滞回**：扩容 80%、缩容 40% |
| 缩到 0 | 8 分钟后才能回来 | `minReplicaCount` = 预热池 |
| 一次缩太多 | 容量瞬间腰斩 | 每分钟最多缩 5% |

**一次误缩 10% = 251 卡 = 瞬间少 700 QPS 的处理能力**，而它要 8 分钟才能回来。

### 6.3 滞回参数

```
扩容阈值：排队 > 64  → 扩
缩容阈值：排队 < 16  → 缩（且持续 10 分钟）
冷却期：扩容后 5 min 内不缩，缩容后 10 min 内不扩
```

中间 48 个点的缓冲带，就是防震荡的全部秘密。

## 7. PD 分离后怎么分别扩

第 11 章把集群拆成 prefill 池（909 卡）与 decode 池（700 卡）。两池的瓶颈完全不同：

| 池 | 卡数 | 扩缩指标 | 谁在推高它 |
|---|---|---|---|
| **Prefill** | 909 | 排队数、输入 token/s | 输入长度变长 |
| **Decode** | 700 | KV 水位、TPOT p95 | 并发会话变多、输出变长 |

**风险：两池比例会漂移。**

```
输入长度 800 → 2,400 token（长文档功能上线）
prefill 工作量 ×3，decode 不变
P:D 从 1.3:1 漂到 3.9:1
→ prefill 排队，TTFT 从 600 ms 涨到 4,000 ms，decode 池却闲着
```

解法是**比例守卫**：每 5 分钟检查一次 P:D，偏离基线 ±20% 就触发重平衡。

```python
def guard_pd_ratio(current_pd, baseline=1.3, tol=0.2):
    drift = current_pd / baseline - 1
    if abs(drift) <= tol:
        return None
    if drift > 0:                       # prefill 不够
        return {"scale": "prefill", "delta": +int(909 * drift)}
    return {"scale": "decode", "delta": +int(700 * -drift)}
```

## 8. 实现：三层配置

### 8.1 第一层：KEDA 管副本数

```yaml
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: decode-pool
spec:
  scaleTargetRef:
    name: decode-deployment
  minReplicaCount: 12          # = 预热池，绝不为 0
  maxReplicaCount: 120
  pollingInterval: 30
  cooldownPeriod: 600
  advanced:
    horizontalPodAutoscalerConfig:
      behavior:
        scaleUp:
          stabilizationWindowSeconds: 0
        scaleDown:
          stabilizationWindowSeconds: 600   # 缩容慢，扩容快
  triggers:
  - type: prometheus
    metadata:
      query: sum(vllm:num_requests_waiting{pool="decode"})
      threshold: "64"
```

### 8.2 第二层：Karpenter 管节点

KEDA 只扩 Pod，不扩节点。节点不够时 Pod 会停在 `Pending`。

```yaml
apiVersion: karpenter.sh/v1
kind: NodePool
spec:
  limits:
    nvidia.com/gpu: "3000"
  template:
    spec:
      requirements:
      - key: node.kubernetes.io/instance-type
        operator: In
        values: ["p5.48xlarge"]        # 8×H800
```

### 8.3 第三层：预热池控制器

```go
func (r *WarmPoolReconciler) Reconcile(ctx context.Context, _ ctrl.Request) error {
    pool := r.currentWarmInstances()
    demand := r.predictedDemand(30 * time.Minute)   // cron + 斜率
    target := int(float64(demand) * 0.15)           // 15% 预热
    switch {
    case pool < target-2:
        return r.warmUp(target - pool)              // 提前加载
    case pool > target+5:
        return r.coolDown(pool - target)            // 缩容也走 drain
    }
    return nil
}
```

### 8.4 完整时序：8:20 到 9:20 谁在做什么

| 时间 | 触发 | 谁 | 动作 | 累计容量 |
|---|---|---|---|---|
| 8:20 | 日周期预测 | cron（KEDA） | 目标 251 副本 = 2,008 卡开始拉起 | 620 |
| 8:20–8:35 | 冷启动 | Karpenter + 节点池 | 补节点、拉镜像、加载权重 | 1,200 |
| 8:50 | — | — | 权重全部就位，进程转热 | 2,008 |
| 9:00 | 流量起 | — | 1,736 QPS 起爬，容量已 ≥2,008 | 2,008 |
| 9:05 | 排队 >64 | KEDA + prometheus | 预热池 377 卡补位（30 s） | 2,385 |
| 9:20 | 峰值 7,000 | — | 最后 127 卡由冷池补，接受 3 min 延迟 | 2,512 |
| 9:20 | 验收 | — | TTFT p95 = 610 ms，SLO 达成 | — |

**关键在 8:20 这一步**：预测式把 15 分钟的冷启动藏在了流量到来之前。
如果等到 9:00 才动，就是 §1 那个烧掉 30% 预算的时间轴。

### 8.5 异构池：能不能反应式，取决于模型多大

| 池 | 模型 | 权重 | 冷启动 | 可行策略 |
|---|---|---|---|---|
| prefill | 200B MoE | 400 GB | 8–15 min | **只能预测式** |
| decode | 200B MoE | 400 GB | 8–15 min | **只能预测式** |
| lite | 8B | 16 GB | 1–2 min | 反应式可用 |

**一条判据：冷启动 < 流量翻倍时间的 1/3，才可以考虑反应式。**

200B 的 10 分钟 > 5 分钟的 1/3，所以必须预测；
8B 的 2 分钟 < 5 分钟，反应式能跟上——**这也是第 6 章"lite 模型"的隐藏价值：
它不只是便宜，它还可以弹性。**

## 9. 失败模式

| 现象 | 根因 | 怎么发现 | 怎么修 |
|---|---|---|---|
| 每次高峰都慢半拍 | 用反应式扩容 | 扩容完成时间 > 流量到顶时间 | cron 提前 60 min |
| 整夜扩缩震荡 | 阈值无滞回 | 每小时伸缩次数 >6 | 扩 80 / 缩 40 |
| Pod 一直 Pending | 有 Pod 无节点 | `kubectl get pod` Pending | 补 Karpenter |
| 缩容后 500 错误率上升 | 没 drain | 缩容时间点错误率尖峰 | 摘流量后等 30 s |
| 长文档上线后 TTFT 爆 | P:D 漂移 | prefill 排队、decode 空闲 | 比例守卫 |
| 预热池常年占满 | 池子配小了 | 水位长期 >70% | 扩池或加 cron 提前量 |

第三条最隐蔽：KEDA 显示"已扩到 120 副本"，但全都 Pending，实际算力一张没加。

## 10. 验收

| 检查项 | 通过标准 |
|---|---|
| 预测覆盖 | ≥80% 的扩容由 cron 触发，而非反应式 |
| 就位时间 | 峰值到顶时容量已 ≥95% 就位 |
| 预热池水位 | 常态 30%–70%，从未击穿 |
| 滞回生效 | 日伸缩次数 ≤6 |
| 缩容排空 | 缩容期间错误率上升 <0.01% |
| PD 守卫 | P:D 偏离 ≤20% |
| 成本 | 预热成本 ≤ 总成本的 5% |

最后一条是关键：**弹性不是免费的**。377 卡短时预热 = ¥1,062 万/年，
占 ¥2.83 亿的 3.8%——这笔钱要能说清楚换回了什么。

## 11. 收口

> **HPA 假设"扩得快"，GPU 的物理假设"扩要 10 分钟"。
> 假设冲突时，赢的永远是物理——所以弹性只能靠预测，不能靠反应。**
