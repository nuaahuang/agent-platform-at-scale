# 第 33 章 · 扩缩容与弹性

> 读完你能回答：
> ① 为什么 HPA（Horizontal Pod Autoscaler，水平 Pod 伸缩器）在 GPU 平台上必然失效？
> ② 预热池该备多少张卡，一年花多少钱？
> ③ 缩容为什么比扩容更危险？
> ④ PD 分离后两个池怎么分别扩，比例漂了怎么办？

---

## 1. 问题：扩容要 10 分钟，流量爬坡只要 20 分钟

电商售后 Agent 的早高峰：

```
9:00   1,736 QPS  →  620 卡
9:05   指标越线，HPA 触发扩容
9:15   第一批实例可用（8–10 分钟）
9:20   流量到顶 7,000 QPS，需要 2,512 卡
       此刻只有约 1,400 卡 → 排队、TTFT 从 600 ms 涨到 4.2 s
9:35   终于补齐，但峰值已经过去 15 分钟
```

这一轮下来，SLO 错误预算烧掉 **30%**（全月只有 43.2 分钟）。

**根因不是扩容慢，是"扩容速度 < 流量变化速度"。**
弹性的目标从来不是"扩得快"，而是**"在需要之前就位"**。

---

## 2. 三个物理约束：为什么快不了

| 环节 | 耗时 | 能否优化 | 优化后 |
|---|---|---|---|
| 节点开机（云上） | 3–5 min | 预留节点池，常备空机 | 0 |
| 镜像拉取 | 8–15 GB，1–3 min | 本地缓存 + P2P 分发 | 20–30 s |
| **权重加载 400 GB** | 3–5 min | 本地 NVMe + P2P 分发 | 2–3 min |
| 预热（跑几个请求） | 30 s | 健康检查通过即可 | 10 s |
| **合计** | **8–15 min** | | **3–4 min** |

即使用尽所有优化手段，天花板也是 **3–4 分钟**。

对比：流量从 1,736 涨到 7,000 只要 **20 分钟**，翻倍只要 **5 分钟**。

> **物理约束决定：反应式扩容永远追不上快变流量。**
> 这不是工程能力问题，是加载 400 GB 权重所需时间的问题。

### 2.1 为什么"干脆多买 30% 卡"不是答案

一个直觉方案：峰值不是 7000 吗？按 1.3 倍备足，不就永远不用扩了？

| 方案 | 卡数 | 年成本 | 结果 |
|---|---|---|---|
| 多买 30% 常备 | +754 卡 | **+¥8,494 万** | 永远够用，但 20 小时在闲置 |
| 短时预热池 | +377 卡 × 6 h | **+¥1,062 万** | 峰值前就位 |

差 **8 倍**。原因很简单：**峰值每天只占 4 小时，但买卡是 24 小时付费。**

弹性要解决的不是"容量够不够"，是"容量在不在正确的时间点"。

---

## 3. 为什么 HPA 必然失效

HPA 的模型是"观察 → 决策 → 执行"，三段都有延迟：

| 延迟段 | 时长 | 来源 |
|---|---|---|
| **指标滞后** | 15–60 s | scrape 间隔 + 聚合窗口 |
| **决策滞后** | 60–300 s | 冷却期、连续 N 个窗口确认 |
| **执行滞后** | 480–900 s | 开机 + 拉镜像 + 加载权重 |
| **总滞后** | **9–20 min** | |

而流量翻倍只要 5 分钟——**总滞后 > 流量变化时间，闭环在数学上就不成立**。

### 3.1 第二个错误：指标选错了

| 指标 | 性质 | 提前量 | 说明 |
|---|---|---|---|
| GPU 利用率 | **滞后** | 0 | 饱和才到 100%，此时已经排队 |
| KV 水位 | 前导 | 60–120 s | 逼近上限说明要拒绝 |
| **排队数**（`num_requests_waiting`） | **前导** | 30–60 s | 饱和前先抬头 |
| TTFT p95 | 前导 | 30–60 s | 用户已经感受到 |

HPA 默认看 CPU，改配自定义指标又走同一套滞后链路。
**用 GPU 利用率做伸缩信号，等于看着后视镜开车。**

## 4. 先分清：反应式与预测式

这两种控制方式的区别只有一句话：**看现在，还是看未来。**

```
反应式（反馈控制，feedback）
   实测指标 ──▶ 与目标比较 ──▶ 调整 ──▶ 再实测
   滞后 = 检测 + 决策 + 执行

预测式（前馈控制，feedforward）
   预测未来需求 ──▶ 提前调整
   不依赖当前误差，依赖预判
```

放到时间轴上看得更清楚：

```
        9:00      9:10      9:20      9:30
需求    ─────────╱──────────█──────────╲────
                                    
反应式            ↑9:05发现  ↑9:15才动  ↑9:25才到
                  （永远慢 15 分钟）

预测式  ↑8:20就动
        （在需求上来之前就位）
```

| 维度 | 反应式 | 预测式 |
|---|---|---|
| **依据** | 当前实测指标 | 未来需求的估计 |
| **提前量** | 负的（滞后 9–20 min） | 正的（提前 30–60 min） |
| **准确度** | 高——看到的是事实 | 中——会猜错（±15%） |
| **失效模式** | 追不上快变流量 | 猜错：多备浪费，少备排队 |
| **成本** | 低（不提前占用） | 高（提前占卡） |
| **适合** | 慢变负载、小模型（8B 冷启 2 min） | 快变负载、大模型（10 min 冷启） |

**为什么 GPU 平台必须以预测式为主**：第 2 章算过，扩容的物理下限是 3–4 分钟，
HPA 全链路 9–20 分钟，而流量翻倍只要 5 分钟。**反应式的滞后大于变化时间，闭环不成立。**

但预测式也不是银弹——它会猜错，所以真实系统是**混合**的：

```
预测式：给 80% 的基线（cron，提前 60 min）
反应式：补 20% 的尾巴（KEDA，看到排队再补）
预热池：吸收那 ±15% 的预测误差
```

一句话记法：**预测式决定"备多少"，反应式决定"补多少"。**

## 5. 三种预测信号：在需要之前动手

| 信号 | 提前量 | 准确度 | 实现 | 适用场景 |
|---|---|---|---|---|
| **日周期（cron）** | 30–60 min | 高（±10%） | KEDA cron scaler / 定时任务 | 早高峰、晚高峰 |
| **斜率检测** | 5–10 min | 中 | 网关 QPS 斜率 > 2σ | 突发爬坡 |
| **业务日历** | 小时–天 | 最高 | 大促预案 + 人工确认 | 已知事件 |

三者是**叠加**关系，不是三选一：

```yaml
# 1) 日周期：每天 8:20 提前拉起
triggers:
- type: cron
  metadata:
    timezone: Asia/Shanghai
    start: "20 8 * * *"
    end: "30 23 * * *"
    desiredReplicas: "251"

# 2) 斜率/排队：兜底真实突发
- type: prometheus
  metadata:
    query: sum(vllm:num_requests_waiting{pool="decode"})
    threshold: "64"
```

**cron 负责"可预测的 80%"，prometheus 负责"不可预测的 20%"。**

## 6. 预热池：备多少，花多少钱

### 6.1 定义与公式

**预热池 = 已经加载好权重、随时可接流量的空实例。** 它不是"多买的卡"，
而是"把要用的卡提前推进到就绪态"。

```
预热池容量 = 峰值容量 × 预测误差 × 安全系数
```

| 参数 | 取值 | 依据 |
|---|---|---|
| 峰值容量 | 2,512 卡 | 第 13 章账本 |
| 预测误差 | ±15% | 历史 cron 预测的实际偏差 |
| 安全系数 | 1.0 | 已有 ×1.3 的容量余量 |
| **预热池** | **377 卡 ≈ 47 个 TP8 实例** | |

### 6.2 三档策略与成本

单卡年成本 = 2.83 亿 ÷ 2,512 = **¥112,660/卡·年**。

| 策略 | 池大小 | 存在时长 | 年成本 | 峰值表现 |
|---|---|---|---|---|
| **纯反应式** | 0 | — | 0 | 每次峰值烧 30% 预算 |
| **短时预热池** | 377 卡 | 6 h/天 | **¥1,062 万** | 峰值前就位 |
| **常驻预热池** | 377 卡 | 24 h | ¥4,247 万 | 全天就位 |

**选短时池**：6 小时覆盖早、晚两个高峰，成本是常驻的 1/4。

> 一个容易被忽略的点：如果这些卡本来就是为了峰值买的、夜里也要付折旧，
> 那么"常驻预热"的**边际成本只有电费**（约 ¥4,240/卡·年），不是 ¥112,660。
> 先算清楚你的卡是"自有"还是"弹性租用"，结论完全不同。

### 6.3 三级预热：热、温、冷

预热不是一个二元状态，而是三级，占用不同资源、对应不同提前量：

| 级别 | 状态 | 占用什么 | 就位时间 | 成本 |
|---|---|---|---|---|
| **热** | 进程跑着、KV 为空、健康检查通过 | GPU | 10–30 s | 全额 |
| **温** | 节点就绪、镜像与权重已在本地 NVMe、进程未起 | 磁盘 + 节点 | 2–3 min | 卡的折旧 |
| **冷** | 只有节点，什么都没拉 | 节点 | 8–10 min | 节点费 |

用法是分层覆盖时间轴：

```
峰值前 2 小时  → 温池就位（377 卡）
峰值前 30 分钟 → 温转热（30 s）
峰值中        → 冷池兜底（10 min，接受排队）
```

**热池只覆盖"最后一分钟"，温池覆盖"最后十分钟"。**
只做热池，成本最高；只做冷池，等于没做。

### 6.4 预热池也要管水位

| 水位 | 含义 | 动作 |
|---|---|---|
| < 30% 被占用 | 池子太大 | 缩减池子 |
| 30%–70% | 健康 | — |
| > 70% | 快用完 | 扩容池子或触发 cron 提前 |
| = 100% | 已击穿 | 只能靠 K8s 现开（10 min） |

## 7. 缩容：比扩容更危险

扩容失败只是慢，缩容失败是**直接掉服务**。

### 7.1 正确的缩容流程

```
摘流量（xDS 摘除端点）
   ↓  等待 ≥ 30 s（覆盖最长在飞请求 9 s + 排空余量）
等在飞请求清零
   ↓
丢弃 KV（或写入 swap）
   ↓
释放实例
```

### 7.2 四个坑

| 坑 | 后果 | 解法 |
|---|---|---|
| 立刻 kill | 在飞请求 500，用户看到失败 | drain ≥30 s |
| 缩完立刻又扩 | 整夜抖动 | **滞回**：扩容 80%、缩容 40% |
| 缩到 0 | 8 分钟后才能回来 | `minReplicaCount` = 预热池 |
| 一次缩太多 | 容量瞬间腰斩 | 每分钟最多缩 5% |

**一次误缩 10% = 251 卡 = 瞬间少 700 QPS 的处理能力**，而它要 8 分钟才能回来。

### 7.3 滞回参数

```
扩容阈值：排队 > 64  → 扩
缩容阈值：排队 < 16  → 缩（且持续 10 分钟）
冷却期：扩容后 5 min 内不缩，缩容后 10 min 内不扩
```

中间 48 个点的缓冲带，就是防震荡的全部秘密。

## 8. PD 分离后怎么分别扩

第 11 章把集群拆成 prefill 池（909 卡）与 decode 池（700 卡）。两池的瓶颈完全不同：

| 池 | 卡数 | 扩缩指标 | 谁在推高它 |
|---|---|---|---|
| **Prefill** | 909 | 排队数、输入 token/s | 输入长度变长 |
| **Decode** | 700 | KV 水位、TPOT p95 | 并发会话变多、输出变长 |

**风险：两池比例会漂移。**

```
输入长度 800 → 2,400 token（长文档功能上线）
prefill 工作量 ×3，decode 不变
P:D 从 1.3:1 漂到 3.9:1
→ prefill 排队，TTFT 从 600 ms 涨到 4,000 ms，decode 池却闲着
```

解法是**比例守卫**：每 5 分钟检查一次 P:D，偏离基线 ±20% 就触发重平衡。

```python
def guard_pd_ratio(current_pd, baseline=1.3, tol=0.2):
    drift = current_pd / baseline - 1
    if abs(drift) <= tol:
        return None
    if drift > 0:                       # prefill 不够
        return {"scale": "prefill", "delta": +int(909 * drift)}
    return {"scale": "decode", "delta": +int(700 * -drift)}
```

## 9. 实现：三层配置

### 9.1 第一层：KEDA 管副本数

```yaml
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: decode-pool
spec:
  scaleTargetRef:
    name: decode-deployment
  minReplicaCount: 12          # = 预热池，绝不为 0
  maxReplicaCount: 120
  pollingInterval: 30
  cooldownPeriod: 600
  advanced:
    horizontalPodAutoscalerConfig:
      behavior:
        scaleUp:
          stabilizationWindowSeconds: 0
        scaleDown:
          stabilizationWindowSeconds: 600   # 缩容慢，扩容快
  triggers:
  - type: prometheus
    metadata:
      query: sum(vllm:num_requests_waiting{pool="decode"})
      threshold: "64"
```

### 9.2 第二层：Karpenter 管节点

KEDA 只扩 Pod，不扩节点。节点不够时 Pod 会停在 `Pending`。

```yaml
apiVersion: karpenter.sh/v1
kind: NodePool
spec:
  limits:
    nvidia.com/gpu: "3000"
  template:
    spec:
      requirements:
      - key: node.kubernetes.io/instance-type
        operator: In
        values: ["p5.48xlarge"]        # 8×H800
```

### 9.3 第三层：预热池控制器

```go
func (r *WarmPoolReconciler) Reconcile(ctx context.Context, _ ctrl.Request) error {
    pool := r.currentWarmInstances()
    demand := r.predictedDemand(30 * time.Minute)   // cron + 斜率
    target := int(float64(demand) * 0.15)           // 15% 预热
    switch {
    case pool < target-2:
        return r.warmUp(target - pool)              // 提前加载
    case pool > target+5:
        return r.coolDown(pool - target)            // 缩容也走 drain
    }
    return nil
}
```

### 9.4 完整时序：8:20 到 9:20 谁在做什么

| 时间 | 触发 | 谁 | 动作 | 累计容量 |
|---|---|---|---|---|
| 8:20 | 日周期预测 | cron（KEDA） | 目标 251 副本 = 2,008 卡开始拉起 | 620 |
| 8:20–8:35 | 冷启动 | Karpenter + 节点池 | 补节点、拉镜像、加载权重 | 1,200 |
| 8:50 | — | — | 权重全部就位，进程转热 | 2,008 |
| 9:00 | 流量起 | — | 1,736 QPS 起爬，容量已 ≥2,008 | 2,008 |
| 9:05 | 排队 >64 | KEDA + prometheus | 预热池 377 卡补位（30 s） | 2,385 |
| 9:20 | 峰值 7,000 | — | 最后 127 卡由冷池补，接受 3 min 延迟 | 2,512 |
| 9:20 | 验收 | — | TTFT p95 = 610 ms，SLO 达成 | — |

**关键在 8:20 这一步**：预测式把 15 分钟的冷启动藏在了流量到来之前。
如果等到 9:00 才动，就是 §1 那个烧掉 30% 预算的时间轴。

### 9.5 异构池：能不能反应式，取决于模型多大

| 池 | 模型 | 权重 | 冷启动 | 可行策略 |
|---|---|---|---|---|
| prefill | 200B MoE | 400 GB | 8–15 min | **只能预测式** |
| decode | 200B MoE | 400 GB | 8–15 min | **只能预测式** |
| lite | 8B | 16 GB | 1–2 min | 反应式可用 |

**一条判据：冷启动 < 流量翻倍时间的 1/3，才可以考虑反应式。**

200B 的 10 分钟 > 5 分钟的 1/3，所以必须预测；
8B 的 2 分钟 < 5 分钟，反应式能跟上——**这也是第 6 章"lite 模型"的隐藏价值：
它不只是便宜，它还可以弹性。**

## 10. 实操：扩容的八个步骤

指标越线之后，到"新实例真的能接流量"，中间有八步。**每一步都有判据，缺一步就会扩了个寂寞。**

| 步 | 动作 | 谁做 | 命令 / 配置 | 判据 | 耗时 |
|---|---|---|---|---|---|
| 1 | 判定要扩 | KEDA | 排队 >64 连续 2 窗口 | `num_requests_waiting` 曲线 | 1 min |
| 2 | 算扩多少 | KEDA / 控制器 | `ceil(waiting/64)` 个副本 | 不超过 `maxReplicaCount` | 立即 |
| 3 | 改副本数 | KEDA → HPA | `kubectl get hpa -w` | `DESIRED` 变化 | 15 s |
| 4 | 等节点 | Karpenter | `kubectl get node` | 节点 Ready | 3–5 min |
| 5 | 等镜像 | kubelet | `kubectl describe pod` | 容器 Running | 20 s（有缓存） |
| 6 | 等权重 | 容器内 | `kubectl logs -f` | 日志出现 `model loaded` | 3–5 min |
| 7 | 探针通过 | kubelet | `kubectl get pod` | READY 1/1 | 20 s |
| 8 | 接流量 | Endpoint Controller | — | `Endpoints` 里出现新 IP | 5 s |

**第 6 步是最长的一步，也是唯一没法跳过的**——400 GB 权重必须真的进显存。

### 10.1 紧急扩容：怎么绕过自动决策

大促前发现预测失灵，要手工抢时间。但直接 `scale` 会和 KEDA 打架——它下一轮就把你的改动覆盖掉。

```bash
# 1) 先暂停 KEDA 的自动决策（只是暂停，不是删除）
kubectl annotate scaledobject decode-pool autoscaling.keda.sh/paused=true

# 2) 手工扩到目标值
kubectl scale deployment/decode --replicas=120

# 3) 盯住就绪进度
kubectl get pods -l app=decode -w | grep -v Running

# 4) 峰值过后恢复自动
kubectl annotate scaledobject decode-pool autoscaling.keda.sh/paused-
```

**顺序不能反**：先暂停再改，否则你改完 15 秒就被覆盖回去。

### 10.2 扩容后必须验证的三件事

| 验证 | 命令 | 不合格的表现 |
|---|---|---|
| 真的接了流量 | `kubectl get endpointslices` | 新 Pod 不在 endpoints 里 |
| 真的在算 | `vllm:num_requests_running` 上升 | 一直是 0（路由没打过来） |
| 真的有效 | TTFT p95 开始下降 | 扩完没变化（瓶颈不在容量） |

第三条最容易被忽略：**扩了 20 个副本，TTFT 没动，说明你扩错了方向**。

## 11. 实操：缩容的七个步骤

缩容比扩容难，因为它会**打断正在进行的请求**。核心是"先摘流、后停机"。

### 11.1 完整流程

```
① 选候选（负载最低、无长请求）
② 让 readiness 变红 → Endpoint 自动摘除
③ 轮询在飞请求数，等它归零（≤30 s）
④ preStop 兜底再等 20 s
⑤ 发 SIGTERM，引擎优雅退出
⑥ 等 terminationGracePeriodSeconds（60 s）
⑦ 释放 GPU，回池
```

### 11.2 摘流量：三条路径

"摘流量"不是一条命令，而是三条路径，按你的栈选，通常两两组合：

| 路径 | 机制 | 生效时间 | 适用 | 局限 |
|---|---|---|---|---|
| **K8s Endpoint** | readiness 变红 → EndpointSlice 摘除 | 1–5 s | 通用兜底 | **不断长连接**，旧连接继续复用 |
| **网关 / Envoy** | xDS 把权重设 0，或 health 置为 UNHEALTHY | <1 s | 有独立网关 | 只管经过网关的流量 |
| **协议层** | HTTP/2 发 `GOAWAY` | 立即 | gRPC 直连 | 需要客户端配合不新建流 |

**第一个局限是致命点**：把 Pod 从 Endpoints 摘了，已经建立的 HTTP/1.1 keep-alive
或 gRPC 长连接**不会断**，新请求照样从旧连接打进来。所以必须配 preStop 兜底。

三种做法的命令：

```bash
# 路径一：K8s Endpoint（改 readiness）
kubectl exec decode-xxx -- touch /tmp/drain
kubectl get endpointslice -l kubernetes.io/service-name=decode -w
# 看到该 Pod IP 消失即生效

# 路径二：Envoy 管理接口（本地 sidecar）
curl -s -X POST localhost:9901/healthcheck/fail     # 让健康检查失败 → 摘除
curl -s -X POST "localhost:9901/drain_listeners?graceful"  # 优雅关闭监听

# 路径三：gRPC 服务端主动 GOAWAY（应用内实现）
server.graceful_stop(grace=20)   # 停止接收新流，等在飞流结束
```

**推荐组合：路径二（快）+ 路径一（兜底）+ preStop（等连接自然关闭）。**

### 11.3 等在飞清零：观测什么、怎么等

**"在飞"不等于"连接数"**——一个长连接可能 0 个在飞，也可能 3 个在飞。要看的是引擎的运行请求数：

```bash
# 引擎侧（vLLM）
curl -s localhost:8000/metrics | grep '^vllm:num_requests_running'
```

preStop 里跑一个带超时的轮询（**必须有超时**，否则引擎卡住就永远等下去）：

```yaml
lifecycle:
  preStop:
    exec:
      command:
        - /bin/sh
        - -c
        - |
          touch /tmp/drain                      # 先摘流
          sleep 3                               # 等 Endpoint 生效
          for i in $(seq 1 25); do
            n=$(curl -s localhost:8000/metrics \
                | awk '/^vllm:num_requests_running/{print int($2)}')
            [ "$n" = "0" ] && break
            sleep 2
          done
terminationGracePeriodSeconds: 60
```

25 × 2 s = 50 s，加上前面的 3 s，正好卡在 60 s 的 grace 内。

三个坑：

| 坑 | 现象 | 解法 |
|---|---|---|
| 流式请求还在吐 token | `running=0` 但 SSE 连接未关 | 连接层也要等，别只看指标 |
| 长尾请求 30 s+ | 等不满 50 s 就超时 | 接受 0.00x% 失败，或提前拒绝新长任务 |
| 引擎 hang 住 | 指标不再更新，循环空转 | 超时后强制退出，别无限等 |

### 11.4 丢弃 KV：到底在丢什么

这是最容易误解的一步。**KV 不在磁盘上，"丢弃"不是删文件。**

| 场景 | 要做什么 | 为什么 |
|---|---|---|
| **纯本地引擎**（默认） | 什么都不用做 | 进程退出 → CUDA context 销毁 → 显存自动回收 |
| **前缀缓存索引在全局**（Redis / LMCache / 自研 KV 池） | **必须显式下线实例**，把它的 block 目录摘掉 | 否则新请求命中"指向已死实例"的条目 → 500 |
| **PD 分离** | 中止该实例上未完成的 KV 传输会话 | 否则 decode 侧等一个永远不来的 block |

代码上就是下线时的三个动作：

```python
def on_shutdown(instance_id):
    transfer.abort_all(instance_id)        # 1) 中止在传的 KV
    kv_index.remove_instance(instance_id)  # 2) 从全局目录摘除
    # 3) 显存交给进程退出自然回收，不需要手动 memset
```

**反例**：只做了 1、2 忘了 3 之外的东西没关系；真正的错误是**只关了进程，没清索引**——
运维看到的现象是"缩容后零星 500，重启才好"。

### 11.5 三个关键配置

**① 可被主动触发的 readiness 探针**

```yaml
readinessProbe:
  httpGet:
    path: /ready
    port: 8000
  periodSeconds: 5
  failureThreshold: 1
```

`/ready` 里检查一个文件：存在 `/tmp/drain` 就返回 503。
于是"摘流"变成一条命令：

```bash
kubectl exec decode-xxx -- touch /tmp/drain
# 5 秒内 Endpoint 摘除，新请求不再进来
```

**② preStop 兜底**

```yaml
lifecycle:
  preStop:
    exec:
      command: ["/bin/sh", "-c", "sleep 20"]
terminationGracePeriodSeconds: 60
```

为什么要 sleep 20？因为 **Endpoint 摘除是异步的**：kube-proxy / Envoy 更新规则需要 1–5 秒，
这期间仍可能有新请求打进来。preStop 给这段时间兜底。

**③ PDB 保住下限**

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: decode-pdb
spec:
  minAvailable: 90%
```

PDB 只管"自愿驱逐"（节点维护、缩容），不管崩溃。它是缩容时的最后一道闸。

### 11.6 一次性缩多少

```
每分钟最多缩 5%，且缩完等 10 分钟再看
```

按 2,512 卡 ≈ 314 个实例算，5% 就是 15 个实例。
一次缩 15 个 = 瞬间少 42 卡 ≈ 117 QPS 的处理能力，这个台阶还能接受；
一次缩 50 个，就是自由落体。

### 11.7 一个真实 bug：没配 preStop

某次发版滚动更新，每次滚动都有 **0.3% 的 500 错误**。

| 现象 | 根因 |
|---|---|
| 发版期间 500 占比 0.3% | Pod 收到 SIGTERM 立刻退出，在飞请求被掐断 |
| 只有发版时出现 | 平时不触发终止 |
| 日志里没有异常 | 进程是被 kill 的，来不及打日志 |

修法就是上面两条：**readiness 可主动摘流 + preStop sleep 20**。
修完 500 降到 0.00x%。

**这个 bug 的代价**：每次发版烧掉约 0.3% 的日请求，按 1.5 亿轮算就是 45 万次失败。

## 12. 失败模式

| 现象 | 根因 | 怎么发现 | 怎么修 |
|---|---|---|---|
| 每次高峰都慢半拍 | 用反应式扩容 | 扩容完成时间 > 流量到顶时间 | cron 提前 60 min |
| 整夜扩缩震荡 | 阈值无滞回 | 每小时伸缩次数 >6 | 扩 80 / 缩 40 |
| Pod 一直 Pending | 有 Pod 无节点 | `kubectl get pod` Pending | 补 Karpenter |
| 缩容后 500 错误率上升 | 没 drain | 缩容时间点错误率尖峰 | 摘流量后等 30 s |
| 长文档上线后 TTFT 爆 | P:D 漂移 | prefill 排队、decode 空闲 | 比例守卫 |
| 预热池常年占满 | 池子配小了 | 水位长期 >70% | 扩池或加 cron 提前量 |

第三条最隐蔽：KEDA 显示"已扩到 120 副本"，但全都 Pending，实际算力一张没加。

## 13. 验收

| 检查项 | 通过标准 |
|---|---|
| 预测覆盖 | ≥80% 的扩容由 cron 触发，而非反应式 |
| 就位时间 | 峰值到顶时容量已 ≥95% 就位 |
| 预热池水位 | 常态 30%–70%，从未击穿 |
| 滞回生效 | 日伸缩次数 ≤6 |
| 缩容排空 | 缩容期间错误率上升 <0.01% |
| PD 守卫 | P:D 偏离 ≤20% |
| 成本 | 预热成本 ≤ 总成本的 5% |

最后一条是关键：**弹性不是免费的**。377 卡短时预热 = ¥1,062 万/年，
占 ¥2.83 亿的 3.8%——这笔钱要能说清楚换回了什么。

## 14. 收口

> **HPA 假设"扩得快"，GPU 的物理假设"扩要 10 分钟"。
> 假设冲突时，赢的永远是物理——所以弹性只能靠预测，不能靠反应。**
