## 1. 问题：一次训练把容量模型打穿了

第 13 章算出的 2,512 卡，前提是"这些卡只做推理"。

现在产品要一版更强的模型，走 RL 训练，需要 800 卡跑 7 天。卡池一共 3,000 卡。冲突立刻出现：

| 用途 | 卡数 | 后果 |
|---|---|---|
| 训练 | 800 | 推理只剩 2,200 卡 |
| 推理 | 2,512 | 支撑峰值 7,000 QPS |
| 缺口 | 512 | 峰值时段 SLO（Service Level Objective，服务等级目标）必破 |

这不是"多买点卡"能一句话解决的事。按租用价 ¥30/卡时算，800 卡跑 7 天是 134,400 卡时，约 ¥403 万；如果为了这一次训练买卡，闲置期还要付折旧。

更麻烦的是，训练和推理对卡的要求不一样：训练要 NVLink 全互联做大并行，推理要的是高并发低延迟。同一批卡两种用法，切换一次要重新加载权重、重建通信组。

还有一个容易被忽略的差异：推理侧的账以 token 为单位，训练侧的账以卡时为单位。第 1 章的 0.517 分/轮，在训练场景里完全用不上——训练不产生 token，只消耗卡时。两套账混着算，容量模型一定错。

这一章只讲交界，不教怎么训模型。

## 2. Agentic RL 和 SFT 差在哪

SFT 的数据是静态的：一批（问题，答案）对，训练时反复读。RL 的数据是模型自己生成的：给定任务，让当前策略跑一遍，拿到轨迹和奖励，再更新策略。

这个差别决定了整个系统的形状：

| 维度 | SFT | Agentic RL |
|---|---|---|
| 数据来源 | 人工标注，固定 | 模型自己生成，每轮都变 |
| 单步耗时 | 30 秒（256 条样本） | 生成 80 秒 + 训练 30 秒 |
| 算力分布 | 训练占 90% | rollout 占 70%–90% |
| 稳定性 | 高，loss 单调降 | 低，奖励会震荡甚至崩 |
| 迭代周期 | 天 | 周 |
| 失败模式 | 过拟合 | 策略坍缩、奖励欺骗 |

最关键的一行是第三行：算力大部分花在"让模型生成"，不是"更新参数"。所以优化 RL Infra，八成力气应该花在 rollout 上。

还有一个结构性差别：SFT 的样本可以无限复用，RL 的样本用一次就旧了。训练一轮要重新采样，这意味着 rollout 的成本是每轮都要付的固定开销，不是一次性的数据准备。

## 3. Rollout 为什么是瓶颈

一条 Agent 轨迹不是一个回答，是一串动作：模型思考、调工具、看结果、再思考，最后给结论。

按售后场景估一条 20 步的轨迹：

```
每步平均生成 500 token（含思考）
20 步 = 10,000 token
200B 模型 rollout 吞吐约 1,000 token/s（单实例，含工具等待）
→ 单条轨迹约 10 秒
```

一个 batch 要 256 条轨迹：

```
单实例：256 × 10 = 2,560 秒 = 43 分钟
32 实例并行：80 秒
```

而训练一步（256 条 × 10K token，200B 全参）大约 30 秒。

所以 rollout 与训练的时间比在 3:1 到 10:1 之间。这个比值是本章所有结论的源头：优化 rollout 一秒，等于优化训练三到十秒。

四个手段，按收益排序：

| 手段 | 做法 | 收益 | 代价 |
|---|---|---|---|
| 前缀复用 | 系统提示和工具 schema 走 prefix cache | 首步 prefill 省 60% | 显存多占 10% |
| partial rollout | 轨迹没跑完先存，下一轮续 | 长尾轨迹不阻塞 batch | 状态序列化开销 |
| 引擎 sleep/wake | 训练时把 rollout 引擎的 KV 换出 | 同卡可混部 | 切换 60–90 秒 |
| 异步采样 | 训练不等全部 rollout 完成 | 吞吐翻倍 | off-policy 程度上升 |

前缀复用在 Agent 场景收益特别大，因为一条轨迹 20 步里，系统提示和工具定义每步都要重新过一遍。如果每步 3,000 token 的固定前缀都重新 prefill，20 步就是 60,000 token 的浪费，占总生成量的六成。

这也解释了为什么 Agent 场景对 prefix cache 的依赖比对话场景重得多：对话一般一两轮，Agent 是二十步。

## 4. 环境与沙箱：rollout 的地基

一条轨迹跑在环境里。模型说"调用 query_order"，环境真的执行，把结果回给模型。环境要同时满足三条：启动快、隔离强、结果可复现。

三种隔离方案，按隔离强度排：

| 方案 | 启动耗时 | 隔离强度 | 适用 |
|---|---|---|---|
| 容器 | 200–800 ms | 中，共享内核 | 可信工具、内部服务 |
| gVisor | 约 300 ms | 高，用户态内核 | 半可信代码 |
| Firecracker | 125 ms | 最高，独立内核 | 执行模型生成的代码 |

模型生成的代码必须跑在最强隔离里。这不是洁癖：一条被提示注入的轨迹，可以让模型写出删库的脚本，容器逃逸的代价是整台机器。

环境池要开多大，算一遍：

```
一个 batch 256 条轨迹，平均 20 步
每个环境同时只跑一条轨迹
一条轨迹 10 秒 → 每秒需要 256/10 = 25.6 个环境
加 1.5 倍冗余（等待、重建、长尾）→ 约 40 个并发环境
但如果 rollout 是 32 个实例 × 8 并发，就需要 256 个环境同时在线
```

实际配置按并发实例数乘每实例并发算，再乘 1.5 冗余。32 × 8 × 1.5 = 384 个环境。

启动耗时不是 125 ms 就够。Firecracker 启一个空 VM 是 125 ms，但镜像加载、依赖初始化、工具服务就绪要 1.5 秒。所以生产上用快照恢复：把已初始化好的内存快照存下来，恢复只要 30 ms，代价是快照本身占内存（每个约 512 MB）。

结果可复现是第三条，也是最难满足的。真实工具做不到——订单状态每分钟都在变。训练时必须用录制好的响应（第 4 章 §4.4 的 cassette），否则同一策略跑两次得到不同奖励，梯度就是噪声。

这条和评测共用同一套基础设施：录制回放的 cassette 既是评测的输入，也是 RL 的输入。

## 5. 显存账：训练侧和推理侧不是一个算法

推理侧的账很简单：权重 200 GB 加 KV 400 GB，切到 8 张卡上，每卡 75 GB。

训练侧完全是另一套算法。200B 全参 RL 的显存构成：

| 项 | 大小 | 说明 |
|---|---|---|
| 权重（bf16） | 400 GB | 训练不能用 FP8 主权重 |
| 梯度（bf16） | 400 GB | 与权重同尺寸 |
| 优化器状态（Adam m+v，fp32） | 1,600 GB | 权重的 4 倍，最大的一块 |
| 激活（batch 256，开重计算） | 约 600 GB | 与序列长度和 batch 成正比 |
| 合计 | 约 3,000 GB | 推理侧的 5 倍 |

切到 512 卡，每卡 5.9 GB，看着很宽裕。真正的瓶颈不是容量，是通信：ZeRO-3 每步要 all-gather 400 GB 权重，按 200 GB/s 的 IB 带宽算一次 2 秒；一个训练步有前向 all-gather、反向 all-gather、参数更新三次，合计 6 秒通信对 30 秒计算，通信占比 17%。

这也是为什么训练集群要 NVLink 加固态 IB，而推理集群对互联的要求低得多。

如果只训 LoRA，账会完全变样：

| 项 | 全参 | LoRA（r=16） |
|---|---|---|
| 可训练参数 | 200B | 约 2 亿 |
| 优化器状态 | 1,600 GB | 1.6 GB |
| 权重 | 400 GB（可训） | 400 GB（冻结，可用 FP8 存 200 GB） |
| 能否与推理混部 | 困难 | 可以 |

LoRA 的 RL 门槛低一个数量级，这意味着它能跑在推理池的空闲卡上。代价是可训练容量小，复杂策略学不动。

colocate 的显存冲突也在这里：训练要 3,000 GB，rollout 要 640 GB（TP8 实例），同卡放不下，只能靠 sleep 把 rollout 的 KV 和权重换出到 CPU。640 GB 按 PCIe 64 GB/s 算要 10 秒，加上重建，一次切换 60–90 秒。

## 6. 异步与 stale：省下的时间从哪来

同步模式下，32 个实例全部跑完 256 条轨迹才训练一步。只要有一条轨迹卡在工具超时，其余 31 个实例就空转。

异步模式不等：采到 192 条就开始训，剩下的下轮补。吞吐能翻倍，但样本来自稍旧的策略。

这个"旧"用 staleness 衡量：样本生成时的策略版本，与当前训练策略版本之间差了几版。

| staleness | 现象 | 处理 |
|---|---|---|
| 0 | 同步，无偏差 | 慢，GPU 空转 |
| 1 | 轻微 off-policy，通常可接受 | 主流做法 |
| 2 | 奖励开始抖动 | 需要重要性采样修正 |
| ≥3 | 策略退化，奖励掉 | 不可用 |

折中做法是按比例混：70% 新样本加 30% 旧样本，既填满 batch 又控制偏差。

staleness 的代价不是线性的。差 1 版时奖励曲线几乎无变化，差 2 版开始出现周期性抖动，差 3 版直接崩。所以阈值要卡在 1 到 2 之间，宁可让 GPU 空转 10%，也不要冒崩的风险。

## 7. 和线上推理的四个共用点

训练系统和线上系统看着是两套，其实共享四样东西。共享得不好，训出来的模型上线就变形。

| 共用 | 怎么共用 | 不同步的后果 |
|---|---|---|
| 权重精度 | 都用 FP8 | rollout 用 BF16 训、线上 FP8 跑，行为差 2–4 个点 |
| 推理引擎 | 同一版本 vLLM | kernel 实现不同，同一 Prompt 输出不同 |
| 前缀缓存 | 训练和线上都吃 KV | 显存账算漏，OOM |
| 指标口径 | 同一套 TTFT（Time To First Token）、TPOT（Time Per Output Token）、SLO（Service Level Objective） 定义 | 训练时测的"快"和线上不是一回事 |

第一条最容易被忽略。RL 训练时如果 rollout 引擎用 BF16，训出来的策略是"BF16 世界里的最优"，一上到 FP8 线上，量化误差会让它的决策路径漂移。正确做法是 rollout 一开始就用线上同款精度。

第四条也常出错：训练团队报"单请求 3 秒"，线上监控报"p95 12 秒"，一查是训练算的是纯生成时间，线上算的是端到端（第 8 章的 12 跳）。口径不统一，两边的数都不可信。

## 8. 轨迹数据：从线上到训练集要过四道

第 31A 章讲的是 badcase 怎么形成闭环，落到 RL 上还要更严一层——RL 需要可计算的奖励，而线上只有弱信号。

| 关卡 | 做什么 | 通过率 |
|---|---|---|
| 采集 | 按触发条件采样会话 | 100% 里约 3% 被采 |
| 脱敏 | 去手机号、地址、订单号明文 | 99%，1% 需人工复核 |
| 奖励可计算 | 能算出确定的 reward | 35% |
| 格式合法 | 轨迹结构完整、工具序列可解析 | 92% |

连乘下来，1 万条线上会话最终能进训练集的大约 190 条。这个转化率决定了 RL 的数据准备周期——不是"数据不够"，是"能算出奖励的数据不够"。

奖励有三种来源：

| 类型 | 例子 | 覆盖 | 成本 |
|---|---|---|---|
| 规则奖励 | 工具调用参数正确、JSON 合法、任务成功 | 35% | 几乎为零 |
| 模型奖励 | judge 按 rubric 打分 | 50% | 每条 ¥0.02 |
| 人工奖励 | 抽样标注 | 15% | 每条 ¥15 |

规则奖励最可靠也最便宜，所以 Agent 场景优先设计"可验证的任务"：能判断对错的（订单查到了没、退款金额算对了没），比"回答得好不好"更适合 RL。

这也是 RLVR（Reinforcement Learning with Verifiable Rewards，可验证奖励的强化学习）在数学和代码任务上先跑通的原因——答案对不对，机器能判。

奖励设计有三个陷阱，踩一个就白训：

| 陷阱 | 表现 | 后果 |
|---|---|---|
| 太稀疏 | 20 步只有终局一个分 | 19 步没有梯度信号，学不动 |
| 可欺骗 | 模型反复调同一个工具刷"调用正确率" | 奖励涨，任务完成率不涨 |
| 不可复现 | 奖励依赖外部状态（库存） | 同一轨迹两次跑分不同，梯度成噪声 |

第一个的解法是加过程奖励：每一步给一个轻量的格式分（JSON 合法、字段齐全），终局给任务分。两者加权，通常 0.2 比 0.8。

第二个只能靠约束：限制单条轨迹的工具调用次数上限，或把奖励定义成"首次调用是否正确"。

第三个就是上一节说的录制回放。

## 9. 容量怎么排：三种模式三笔钱

回到第 1 节的冲突。三种排法，各有各的账。

### 9.1 错峰：夜间训练，白天回缩

夜间流量是白天的 45%，推理只需 1,130 卡，能空出 1,870 卡给训练。做法是弹性训练：白天训练缩到 200 卡，夜间扩到 800 卡，每 30 分钟存一次 checkpoint。

| 项 | 值 |
|---|---|
| 额外卡成本 | 0，用闲置 |
| 训练周期 | 7 天拉长到 17 天 |
| 工程成本 | checkpoint 频繁存取，每卡每分钟 2 GB 写入 |
| 风险 | 白天回缩时训练进程被抢占，要能断点续训 |

账面上最省，代价是周期翻 2.4 倍。适合不着急的迭代。

### 9.2 混部：同卡分时，靠 sleep/wake 切换

训练和推理跑在同一批卡上，用引擎的 sleep 把 KV 换出到 CPU，腾出显存给训练。

| 项 | 值 |
|---|---|
| 额外卡成本 | 0 |
| 切换开销 | 每次 60–90 秒 |
| SLO 影响 | 切换期间该实例不可用，p99 抬高 200 ms |
| 适用 | 推理流量平稳、能容忍抖动的时段 |

切换太频繁会把收益吃光：一天切 20 次就是 30 分钟不可用。实践上按小时粒度切。

### 9.3 独立池：租一批卡，谁也不影响谁

| 项 | 值 |
|---|---|
| 成本 | 800 卡 × 168 小时 × ¥30 = ¥403 万 |
| 训练周期 | 7 天，不打折 |
| 推理影响 | 0 |
| 适用 | 大版本、有明确上线日期 |

### 9.4 怎么选

| 场景 | 选哪种 | 理由 |
|---|---|---|
| 日常小步迭代（改 reward、调超参） | 错峰 | 不急，省钱 |
| 中等规模（换数据配比） | 混部 | 周期和成本折中 |
| 大版本（要对外发布） | 独立池 | 时间比钱重要 |

多数团队是三者混用：日常错峰，季度大版本租独立池。

## 10. 权重回灌：训练完怎么上线

训练出一个新 checkpoint，不等于线上就能用。中间有四步，每步都可能出问题。

第一步是导出与转换。训练框架存的是分片 checkpoint（通常 bf16 或 fp32 master），线上引擎要的是 FP8 权重加 scaling factor。转换本身要重新校准，校准集用线上的真实输入分布。

第二步是验证。新权重先不上灰度，在离线环境跑第 4 章的 50 题加回放，确认没有退化。

第三步是灰度。按第 36 章的三层灰度：先 1% 租户，再 10%，再全量。每层看 goodput 和客诉。

第四步是 KV 作废。这一步最容易被忘。第 10B 章讲过，前缀缓存的唯一真实失效条件是权重版本变化。新权重上线时，旧 KV 全部作废，缓存命中率会从 85% 掉到 0，然后花 20 分钟爬回来。

| 步骤 | 耗时 | 出错的表现 |
|---|---|---|
| 导出与 FP8 校准 | 40 分钟 | 校准集不对，上线后精度掉点 |
| 离线验证 | 2 小时 | 漏跑通用集，只测了任务集 |
| 灰度 | 3 天 | 灰度量不足，覆盖不到周末流量 |
| KV 作废与预热 | 20 分钟 | 忘了作废，新模型读到旧 KV，输出错乱 |

全量替换 2,512 卡不是一次性推完。分批做，每批 128 卡，每批 12 分钟（含 200 GB 权重传输 2–3 分钟），20 批约 4 小时。

回滚比上线更重要。RL 训练的模型经常出现"训练时好、上线后差"，这时候要能在 30 分钟内切回旧版本。前提是旧的权重文件还在，且旧版的 KV 能被重建——这两条都要在训练开始前确认，不是出事时才找。

## 11. 一个最小可跑的循环

骨架只有三层：rollout、reward、train。真实系统复杂在并发和容错，结构就是这个。

```python
def rl_step(policy, envs, reward_fn, cfg):
    # 1) rollout：并行生成轨迹
    batch = []
    with ThreadPool(cfg.n_env) as pool:
        while len(batch) < cfg.batch_size:
            trajs = pool.map(lambda e: policy.rollout(e), envs[:cfg.n_env])
            for t in trajs:
                t.reward = reward_fn(t)          # 规则优先，模型兜底
            batch.extend(filter(lambda t: t.reward is not None, trajs))

    # 2) 组内归一化（GRPO 不需要 critic）
    for group in group_by_prompt(batch, size=cfg.group_size):
        mu = mean(t.reward for t in group)
        sd = std(t.reward for t in group) or 1.0
        for t in group:
            t.advantage = (t.reward - mu) / sd

    # 3) 更新：clip 加 KL 约束
    for epoch in range(cfg.ppo_epochs):
        loss = ppo_clip_loss(batch, policy, old_logprobs=policy.logprobs(batch),
                             clip=0.2, kl_coef=0.02)
        loss.backward()
        optimizer.step()
    return policy
```

三个参数决定这套东西能不能跑起来：

| 参数 | 典型值 | 调大的后果 |
|---|---|---|
| `batch_size` | 256 | 显存涨，staleness 涨 |
| `group_size` | 8 | 每个 prompt 采样多，方差小但慢 |
| `ppo_epochs` | 1–2 | off-policy 偏差放大，奖励崩 |

`ppo_epochs` 是最容易调错的。SFT 习惯跑 3 个 epoch，RL 里同一批数据训 3 遍会让策略偏离采样分布太远，奖励曲线先涨后崩。

## 12. 训练怎么知道自己在变好

训练指标和线上指标是两套，混淆这两套是 RL 项目最常见的失败。

先看训练侧该盯哪五个数：

| 指标 | 定义 | 健康区间 | 异常信号 |
|---|---|---|---|
| rollout 吞吐 | 每秒产出轨迹数 | 稳定 | 下降说明环境或工具变慢 |
| 平均轨迹步数 | 一条轨迹调用几次工具 | 稳定 | 上升说明模型在绕路 |
| 奖励均值 | batch 内的平均 reward | 缓慢上升 | 突然跳升多半是奖励被刷 |
| 奖励方差 | 组内 reward 的标准差 | 保持住 | 塌缩说明策略同质化 |
| KL 散度 | 与参考模型的偏离 | 0.01–0.04 | 超过 0.1 说明跑野了 |

第三个和第四个要一起看。奖励均值涨、方差塌缩，是策略坍缩的典型曲线：所有采样都走上同一条高分路径，探索没了，后面几轮涨不上去。健康的曲线是均值涨、方差稳住。

看训练侧不够，还要加两个联动的数：

- 每周用固定评测集（第 4 章的 50 题）跑一次，看通过率有没有跟着涨
- 每两周做一次线上 A/B，看 goodput 和客诉有没有跟着动

三条曲线（奖励、评测、线上）方向一致，才说明训练有效。方向不一致时，优先级是线上大于评测大于奖励——奖励是我们定义的代理指标，它错了也不会自己报警。

最典型的错位是：奖励涨了 30%，评测通过率没动。原因通常是模型学会了奖励函数偏好的表达，没学会完成任务。这时候该改 reward，不该加训练轮数。

## 13. 失败模式

| 现象 | 根因 | 怎么发现 | 怎么修 |
|---|---|---|---|
| 奖励涨但线上变差 | reward 与真实目标不一致，奖励欺骗 | 人工抽检奖励高的轨迹 | 加规则约束，缩短 reward 代理链 |
| 训练中途奖励崩到 0 | ppo_epochs 太大或 KL 系数太小 | 看 KL 散度曲线 | 降到 1 epoch，KL 调到 0.04 |
| rollout 卡在某条轨迹 | 工具超时没有 kill | 环境占用率长期 100% | 加超时，超时即判失败 |
| 训练完上线精度掉 3 点 | rollout 用 BF16，线上 FP8 | 同一 Prompt 两边对比 | rollout 精度对齐线上 |
| 缓存命中率长期上不去 | 权重频繁更新，KV 一直作废 | 命中率曲线呈锯齿状 | 降低发布频率，或做 KV 迁移 |
| 训练占了卡，线上 p99 抬高 | 混部没留缓冲 | 切流时 p99 尖峰 | 预留 15% 卡，或改错峰 |
| 环境池耗尽，rollout 排队 | 环境启动慢或长尾轨迹不退出 | 环境等待队列长度 | 加预热池，强制超时回收 |

第一条最危险：奖励涨、线上跌，而且不容易发现，因为所有训练指标都好看。

## 14. 什么情况下这些结论不成立

| 结论 | 推翻条件 |
|---|---|
| rollout 占 70%–90% 算力 | 轨迹很短（3–5 步）时，训练占比会升到 50% |
| 用 GRPO 不用 PPO | 奖励密集（每步都有分）时，critic 有价值 |
| 混部切换按小时粒度 | 推理有明确的波峰波谷时，可以按 15 分钟粒度切 |
| 独立池按周租 | 训练能在一夜跑完时，按小时租更划算 |
| 全参训练必须独立池 | 只训 LoRA 时，优化器状态降到 1.6 GB，可混部 |

## 15. 验收

1. 能算出你场景下 rollout 与训练的时间比，并指出瓶颈在哪。
2. 能算出环境池要开多少个，并说明冗余系数为什么是 1.5。
3. 能说出线上轨迹进训练集要过哪四道，转化率大概多少。
4. 给定卡池规模和训练需求，能排出错峰、混部、独立池三种方案的账。
5. 能说出权重回灌的四步，以及漏掉 KV 作废会发生什么。
