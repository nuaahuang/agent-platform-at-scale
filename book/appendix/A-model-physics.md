# 附录 A · 模型层的物理：显存、带宽、算力

> 迁移自 v1 `ch02-model-physics.md`。文中引用"第 N 章"为 **v1 旧编号**，与 v3 的对应关系见 [../MIGRATION.md](../MIGRATION.md)。


> **一句话结论**：所有容量数字都来自三个公式——**显存账本、KV 公式、Roofline**。
> 会推这三个，你就不需要背任何"经验值"。

---

## 1. 问题：为什么"加卡"不一定变快

新手的第一反应是"慢了就加卡"。但真实情况是：

- 加卡后 **TTFT 没降**——因为瓶颈在排队，不在算力；
- 加卡后 **吞吐没涨**——因为瓶颈在显存带宽，不在 FLOPs；
- 加卡后 **更慢了**——因为 TP 通信开销超过了收益。

要判断"该加什么"，必须先知道**当前卡在哪一种资源上**。这一章就是教你怎么判断。

## 2. 显存账本：640GB 里能装什么

以 8×H800（80GB/卡）为例：

| 项 | 大小 | 说明 |
|---|---|---|
| 模型权重 | **200GB** | 200B 参数 × 1 Byte（FP8） |
| KV Cache | ~300GB | 装会话的"记忆" |
| 激活 / 临时 | ~60GB | 中间结果、CUDA Graph |
| 碎片 / 预留 | ~80GB | 不能全用满 |
| **合计** | **640GB** | 正好一台 8 卡机 |

**关键认知**：**权重是固定的，KV 是弹性的。**
并发上不去，通常不是权重装不下，是 KV 装不下。

> 参数量 ≠ 显存。FP8 是 1 Byte/参数，FP16 是 2 Byte，INT4 是 0.5 Byte。
> "200B 模型要 400GB"只在 FP16 下成立。

---

### 2.1 什么是 HBM

**HBM（High Bandwidth Memory，高带宽存储器）**：把多层 DRAM 像盖楼一样 3D 堆叠，
通过 **TSV（硅通孔）**穿层连接，再用一块**硅中介层（interposer）和 GPU 封在同一个基板上**。

```
普通显存：GPU 芯片 —— PCB 走线 —— 显存颗粒（窄路）
HBM：    GPU 芯片 ══ 硅中介层（超宽马路）══ 5–8 摞 DRAM 楼（就在隔壁）
```

GPU 有上万个核心，数据喂不过来就全闲着。HBM 用"**超多引脚的超宽总线**"解决——
每个 stack 是 1024 位，5 个 stack 就是 5120 位（普通显卡显存总线只有 256–384 位）。

| | HBM | GDDR6（游戏卡） | DDR5（主机内存） |
|---|---|---|---|
| 带宽 | **3–8 TB/s** | 0.5–1 TB/s | 0.1–0.4 TB/s |
| 容量 | 80–192 GB | 12–24 GB | 数百 GB–TB |
| 位置 | 和 GPU 同封装 | 板卡旁边 | 主板上 |
| 价格 | 贵，受 CoWoS 封装产能限制 | 便宜 | 最便宜 |

**典型数字**：H800/H100 = 80GB HBM3、3.35 TB/s；H200 = 141GB HBM3e、4.8 TB/s；B200 = 192GB、8 TB/s。

**两个推论**：

1. **权重和 KV 必须放进 HBM**——PCIe 只有 64 GB/s，比 HBM 慢 50 倍，放外面 decode 立刻饿死；
2. **HBM 又贵又小**，所以才要 FP8、GQA/MLA、PagedAttention——这些技术都在回答
   同一个问题：**怎么在这 80GB 里塞下更多东西。**

## 3. KV 公式：一个 token 占多少

```
KV_bytes_per_token = 2 × L × H_kv × d × bytes_per_elem
```

- `2`：K 和 V 各一份
- `L`：层数
- `H_kv`：KV 头数（GQA 下远小于注意力头数）
- `d`：每头维度
- `bytes`：FP16 = 2，FP8 = 1

**代入本项目**（L=64，H_kv=4，d=128，FP16）：

```
2 × 64 × 4 × 128 × 2 = 131,072 B ≈ 128 KB/token
工程取值：120 KB/token
```

于是：

| 上下文 | 单会话 KV | 300GB 能装几条 |
|---|---|---|
| 2K | 0.24 GB | ~1,250 |
| 8K | **0.96 GB** | ~312 |
| 32K | 3.84 GB | ~78 |
| 128K | 15.4 GB | ~19 |

**这就是"长上下文很贵"的量化解释**：上下文翻 4 倍，能装的会话数掉到 1/4。

### 3.1 补充：MHA / MQA / GQA / MLA——KV 头数为什么能变小

注意力里有三种头：**Q 头**（查询）、**K 头**（键）、**V 头**（值）。
KV Cache 只存 K 和 V（Q 来自当前输入，不用存）。怎么分配这些头，直接决定 KV 大小：

```
MHA（多头注意力）：Q1 Q2 Q3 Q4 各自配  K1 K2 K3 K4 / V1..V4   ← 32 Q 头 = 32 份 KV
MQA（多查询注意力）：Q1..Q8 共享        K1 / V1               ← 8 个 Q 头共用 1 份
GQA（分组查询注意力）：Q1 Q2 用 K1V1；Q3 Q4 用 K2V2；……       ← 4 个 Q 头共用 1 份
MLA（DeepSeek）：低秩压缩 KV，比 GQA 再小 3–4 倍
```

以"32 个 Q 头"为例：

| 方案 | KV 头数 H_kv | KV/token | 8K 上下文 | 300GB 装几条 |
|---|---|---|---|---|
| MHA | 32 | ~1,024 KB | 8 GB | ~37 |
| **GQA（本项目假设）** | **4** | **~128 KB** | **~1 GB** | **~312** |
| MQA | 1 | ~32 KB | 0.25 GB | ~1,200 |
| MLA | 压缩后 | ~30–40 KB | 0.24–0.31 GB | ~1,000+ |

**为什么能共享**：注意力是"Q 去查 K、按权重取 V"。多个 Q 头查同一套 K/V，
仍然能从不同视角取信息，只是表达能力略降。Google 2023 的实验表明
**GQA 质量几乎追平 MHA，KV 却只剩 1/4–1/8**；MQA 省得更多，但部分模型掉 1–3 pt。

**注意**：GQA 不只省显存，还**省 decode 带宽**——每生成一个 token 要读的 KV 变小了，
所以 decode 直接变快。这是"改模型架构就能降推理成本"的典型例子。
现在主流模型几乎都用 GQA（Llama 3：32 Q / 8 KV），DeepSeek 用更激进的 MLA。

**MLA 为什么重要**：DeepSeek 的 MLA 把 KV 压到 GQA 的 1/3–1/4，
同样 300GB 能装的会话数直接翻 3–4 倍——**模型架构决定了推理成本的上限**。

## 4. 解码是带宽游戏

生成 1 个 token，要把"权重 + 所有在跑会话的 KV"从显存读一遍。

```
每步读取字节 ≈ 激活权重 + B × 单会话KV
每步耗时     ≈ 读取字节 / HBM带宽
```

H800 的 HBM 带宽是 **3.35 TB/s**，MoE 激活权重 30GB：

> **B 就是 batch size（批大小）：一个 step 里同时处理多少个序列。**
> GPU 几万个核心，一次只算一个用户根本喂不饱；把 B 个用户凑成一批，
> 权重读一次给 B 个人共用——这就是 batch 的意义。
> - 训练：一个 batch 是一组样本，算完一起更新权重（典型几百到几千条）；
> - 推理：一个 step 里**正在同时生成**的请求数（vLLM 动态变化，几十到几百）；
> - 每 step 每个序列各出 1 个 token → **每步共产出 B 个 token**；
> - B 越大越省（权重摊薄），但每步越慢（TPOT 变差）、KV 越占显存——上限由 KV 预算决定。

| Batch | 每步读取 | 每步耗时 | 聚合吞吐 |
|---|---|---|---|
| 1 | 30 GB | 9.0 ms | ~111 tok/s |
| 64 | 30 + 61 GB | 27 ms | ~2,370 tok/s |
| 256 | 30 + 246 GB | 82 ms | ~3,120 tok/s |
| ∞ | KV 主导 | — | **上限 ≈ 3,350 / 0.96 ≈ 3,490 tok/s** |

**一个 decode step 的五步**（以生成第 5,002 个 token 为例）：

| 步骤 | 做什么 | 数据量 |
|---|---|---|
| ① 投影 | 算新 token 自己的 K₅₀₀₂/V₅₀₀₂（只算 1 个） | 1 token |
| ② Q·K | 新 token 的 Q 乘**全部历史的 K**（1×5,002） | 读 5,002 个 K |
| ③ softmax·V | 对**全部历史 V** 加权求和 | 读 5,002 个 V |
| ④ 输出层 | output projection + FFN → 新 token | 2N FLOPs |
| ⑤ 追加 | K₅₀₀₂/V₅₀₀₂ 写进 Cache | **+120 KB** |

- **计算**只有 1 个 token 的量（恒定）；**读取**是全部历史（随上下文线性增长）；
- 历史 K/V **不重算**——自回归是因果的，旧 K/V 一旦算好永久有效。
- 每步**新增 120KB，却要读 0.96GB**（8K 时）：写一个人，读一整本书。

**三个结论**：

**表里的数字怎么来的（以 batch=1 为例）**：

```
第 1 步：每步读多少字节    = 激活权重 + B × 单会话 KV
                          = 30 GB + 1 × 0.96 GB ≈ 31 GB（表中忽略了小数）

第 2 步：每步耗时          = 字节 ÷ 带宽
                          = 30 GB ÷ 3.35 TB/s = 8.96 ms ≈ 9.0 ms

第 3 步：一个 step 里，batch 中每个序列各生成 1 个 token → 共产出 B 个 token
        聚合吞吐 = B ÷ 每步耗时 = 1 ÷ 0.009 s ≈ 111 tok/s
```

**关键区别：聚合吞吐 vs 单用户速度**

| Batch | 每步耗时 | 单用户速度 = 1/耗时 | 聚合吞吐 = B/耗时 |
|---|---|---|---|
| 1 | 9.0 ms | 111 tok/s | 111 tok/s |
| 64 | 27 ms | **37 tok/s** | **2,344 tok/s** |
| 256 | 82 ms | 12 tok/s | 3,122 tok/s |

- **聚合吞吐**：这块卡每秒总共吐出多少 token → 决定**成本**；
- **单用户速度**：某一个用户每 s 收到几个 token（= TPOT 的倒数）→ 决定**体验**。

batch 变大，聚合吞吐涨（权重被 64 个请求摊薄），但单用户速度反而掉——
**连续批处理就是在"成本"和"TPOT SLO"之间找最大 batch**。
batch→∞ 时，KV 主导：`3350 ÷ 0.96 ≈ 3,490 tok/s` 就是聚合上限。

> 注：这是数量级模型（把整台机器当一块卡，忽略了 TP 切分、kernel 效率），
> 真实值再乘 30–50%。**用它判断方向和上限，不用它定合同指标。**

1. **batch 变大，吞吐上升，但会饱和**——因为 KV 读取最终主导。
2. **吞吐上限 ≈ HBM 带宽 / 单会话 KV**。想让上限翻倍，要么换带宽更高的卡，要么把 KV 变小（MLA/量化）。
3. 上表是**理论上限**，真实要乘 **30–50%** 的效率系数（kernel、调度、通信开销）。

> 这也解释了为什么"decode 加卡"有效但线性度差：TP 会把 KV 和权重切开，
> 但每一步都要 all-reduce，通信会吃掉一部分收益。

## 5. Prefill 是算力游戏

### 5.0 Roofline：一张图判断谁是瓶颈

Roofline（Williams et al., 2009）把硬件的两个极限画成一个"屋顶"：

```
实际可达算力
(P)
 1.98 PF ┤___________________________  ← 平屋顶：算力顶（Tensor Core 极限）
         │                    ___───
         │               ___───
         │          ___───
         │     ___───                 ← 斜屋顶：带宽顶（P = 带宽 × AI）
         │__───
         └──────────────────────────── 算术强度 AI（FLOP/Byte）
         2          590           10,000
         ↑          ↑              ↑
       decode     拐点          prefill
```

**一个公式**：

```
P = min(峰值算力, 峰值带宽 × AI)          AI = FLOPs ÷ 读取字节数
```

- **斜屋顶**：AI 低时，每搬 1 Byte 只能做几次运算，GPU 在等数据——**带宽受限**；
- **平屋顶**：AI 高时，数据喂得够快，算力跑满——**算力受限**；
- **拐点（ridge point）= 峰值算力 ÷ 峰值带宽 = 1.98×10¹⁵ ÷ 3.35×10¹² = 590 FLOP/Byte**。

把两个阶段放上去：

| 阶段 | AI | 位置 | 可达算力 | 结论 |
|---|---|---|---|---|
| Decode（batch 小） | ≈ 2 | 斜屋顶 | 3.35T × 2 ≈ 6.7 TFLOPS | 算力只用了 0.3% |
| Prefill T=5,000 | ≈ 2T = 10,000 | 平屋顶 | 接近 1,980 TFLOPS | 算力受限 |

> 这里两个常数的出处：**2** 见 §5.2——每个参数对每个 token 做"1 次乘 + 1 次加 = 2 FLOP"；
> **3.35 TB/s** 见 §2.1——H800 HBM3 显存的硬件带宽规格。两者都是"记账约定/硬件参数"，不是推导值。

**这就是 PD 分离的数学根因**：两个工作负载在屋顶图上的位置相差 5,000 倍，
根本不可能用同一套资源配置同时优化。

类比：工厂的产能 = min(工人速度, 传送带速度)。AI 低时传送带是瓶颈（decode），
AI 高时工人忙不过来（prefill）。屋顶线就是那张"先瓶颈谁"的诊断图。

### 5.1 先分清四个单位

| 写法 | 含义 | 量级 | 例子 |
|---|---|---|---|
| **FLOP** | 一次浮点运算（一次乘或一次加） | 1 | 一个 MAC = 2 FLOP |
| **FLOPs** | 运算**总数**（复数，常被滥用） | 次数 | 一次 prefill 要做 300 TFLOP |
| **FLOPS** | 每秒运算次数（**速度**） | 次/秒 | H800 FP8：1.98 PFLOPS |
| **TFLOP / TFLOPS** | 10¹² 次 / 10¹² 次每秒 | 万亿 | 单卡 FP16 约 1 TFLOPS 的千倍 |
| **PFLOPS** | 10¹⁵ 次每秒 | 千万亿 | 1.98 PFLOPS = 1.98×10¹⁵ 次/秒 |

**最容易踩的坑**：

- **`TFLOP`（无 S）= 工作量**，`TFLOPS`（有 S）= 速度。差一个 S，差一个"每秒"。
- 厂商参数表写"1.98 PFLOPS"是**峰值速度**；你算出来的"300 TFLOP"是**工作量**。
  两者相除才得到时间：`300 TFLOP ÷ (1.98 PFLOPS × 35%) ≈ 0.43 秒`。
- FP8 的速度约是 FP16 的 **2 倍**；稀疏（2:4）还能再翻倍。看参数必须看精度。

### 5.1.1 「稀疏」有三种，说的不是一回事

| 稀疏 | 在哪一层 | 含义 | 影响什么 |
|---|---|---|---|
| **结构化稀疏（2:4）** | 硬件/权重 | 每 4 个权重里固定 2 个是 0，Tensor Core 跳过不算 | 峰值 FLOPS **×2**（参数表里的 "sparse" 指这个） |
| **MoE 条件计算** | 模型架构 | 每个 token 只激活少数专家（30B / 200B） | 单 token **FLOPs 变小**，但显存要装全部专家 |
| **稀疏注意力** | 算法 | 只算部分 token 对（滑窗/块稀疏） | 长上下文 **T² 项**变小 |

**买卡时看到的"稀疏"= 第一种**：H100/H800 参数表常写 "3,958 TFLOPS FP8 sparse"，
对应 dense 是 1,979 TFLOPS。要享受这个 2 倍，权重必须**剪枝成 2:4 模式**并微调，
不是"模型里有 0"就行。

**设计 MoE 时说的"稀疏"= 第二种**：它是**条件计算**——路由只让部分专家参与。
好处是单 token 算力低；代价是**显存装全部专家**、**专家并行要 all-to-all 通信**。

> 一句话：**2:4 稀疏省算力，MoE 稀疏省算力但费显存和网络。** 两者不能叠加着白拿。

### 5.2 为什么是 `2 × N_active × T`

一个线性层 `y = Wx`，`W` 有 `N` 个参数：

```
每个 token 经过每个参数：1 次乘法 + 1 次加法 = 2 FLOP（一个 MAC）
T 个 token            ：2 × N × T
```

**所以那个 2 不是"两个矩阵"，是"乘一次、加一次"。**

> 严格计数是 **2N−1**（N 次乘法 + N−1 次加法），N 以十亿计时约定记 2N；
> 硬件上 1 条 FMA 指令完成乘加，但厂商 FLOPS 按 2 FLOP 记账，两边口径一致。
> 训练时还要加反向传播：前向 2N + 对输入梯度 2N + 对权重梯度 2N = **6N/token（6ND）**。
> 为什么反向两遍：线性层 `Y=XW`，前向已知 X 求 Y=XW；反向时已知上游梯度 dY，
> 要算 **dX = dY·Wᵀ**（梯度传给上一层）和 **dW = Xᵀ·dY**（更新本层权重），
> 两个不同的矩阵乘，各约 2N FLOP。
> 推理时 dW/dX 都不需要，只留前向 2N——这也是为什么训练还要额外存激活（供反向用）。

**AI 不是恒等于 2**。一般式 `AI = 2N·B ÷ (N字节 + B × 单会话KV)`：
B=1、权重主导时 AI≈2；B=64 时 AI≈42；prefill 时 AI=2T（T=5000→10,000）；FP16 时减半。
2 只是"FP8 + decode + 小 batch + 权重主导"这一特例。

MoE 里每个 token 只走激活的专家，所以只用 `N_active`（30B），不是总参数 200B。

**注意：2N 不含注意力打分（它没有权重矩阵）。** 先分清"KV 的计算"有两种：

- ① 投影 K/V：`K=XW_K, V=XW_V`——带权重的线性层，**已含在 2N 内**；
- ② 打分取信：`QKᵀ` 和 `softmax·V`——**不带权重，不在 2N 内**。
- （把 K/V 存进 Cache 本身不耗 FLOPs，只耗显存和带宽。）

| | 注意力 FLOPs（L=64, d=7168） | 数值 | 占线性层比例 |
|---|---|---|---|
| Prefill（全部 T 个 token） | `4·L·T²·d` | T=5k：46 TF | 15%（不是 <1%，不可忽略） |
| | | T=32k：1,879 TF | **98%（长上下文注意力反超 FFN）** |
| Decode（每 token，只算新 Q 对历史） | `4·L·T·d` | T=8k：14.7 GF | 相对 2N=60 GF 约 **+24%** |

推论：长上下文 prefill 的 T² 项会主导算力，所以有 FlashAttention（**不减少 FLOPs，
只减少 HBM 读写**）和稀疏/滑动窗口注意力（真正减少 FLOPs）。
decode 即使多算 24% FLOPs，瓶颈仍是读 KV 的带宽，结论不变。

Prefill 要处理整个输入（5,000 token），计算量：

```
FLOPs ≈ 2 × N_active × T
```

- `N_active` = 30B（MoE 只激活一部分）
- `T` = 输入长度

### 5.3 算一遍

以 T=500 为例，把每一步的单位写出来：

```
FLOPs = 2 × N_active × T
      = 2 × 30×10⁹ × 500
      = 3.0×10¹³ 次运算
      = 30 TFLOP                  （÷10¹²）

时间  = FLOPs ÷ 峰值速度
      = 3.0×10¹³ ÷ 1.98×10¹⁵
      = 0.0152 秒                 （100% 利用率）

考虑 MFU 35%：
      = 0.0152 ÷ 0.35 = 0.043 秒
```

单位怎么消掉：`次 ÷ (次/秒) = 秒`。

| 输入 T | FLOPs | 折算 | 单卡 100% | 单卡 35% MFU |
|---|---|---|---|---|
| 500 | 3.0×10¹³ | 30 TFLOP | 0.015 s | 0.043 s |
| 5,000 | 3.0×10¹⁴ | 300 TFLOP | 0.152 s | **0.433 s** |
| 32,000 | 1.9×10¹⁵ | 1,920 TFLOP | 0.97 s | 2.77 s |

**单 token 成本 = 2N = 60 GFLOP**（30B 激活）。

> 第 01 章说 prefill 约 300ms，这里算出 433ms——差额来自 **70% 前缀命中**：
> 实际只算 1,500 token（约 130ms），再加固定开销。**数字对不上时，先查假设，不要怀疑公式。**

### 5.4 MFU：把"峰值"换成"实际"

```
MFU = 实际达到的 FLOP/s ÷ 硬件峰值 FLOP/s
```

上表的 "35%" 就是假设 MFU = 0.35。它回答一个问题：**买来的算力，真正用上了几成？**

**为什么到不了 100%**：

| 损耗来源 | 说明 |
|---|---|
| 显存等待 | 算得再快，数据没搬过来也要等 |
| 通信 | TP/EP 的 all-reduce / all-to-all 期间算力空转 |
| kernel 效率 | 小算子、非矩阵运算跑不满 Tensor Core |
| 调度 | batch 不满、长短请求混跑 |

**典型值**（工程经验，不是定律）：

| 场景 | MFU 大致范围 |
|---|---|
| 大模型训练 | 35–50% |
| Prefill（长输入、大 batch） | 30–50% |
| Decode（逐 token） | **MFU 很低，通常 <10%** |

**Decode 不要看 MFU**：它是**带宽受限**，算力闲置是正常的。
decode 该看 **MBU（Model Bandwidth Utilization）= 实际带宽 ÷ 峰值带宽**，
目标 60–80%，比 MFU 更有指导意义。

**怎么实测 MFU**：

```
MFU = (吞吐 tok/s × 2 × N_active) ÷ 峰值 FLOP/s
```

例：实测 1,200 tok/s、N_active=30B、峰值 1.98 PFLOPS：
`1200 × 6×10¹⁰ ÷ 1.98×10¹⁵ ≈ 3.6%`——这是 decode 的正常水平，不是故障。

**算术强度**（每读 1 Byte 能做多少次浮点运算）：

```
AI ≈ 2 × N_active × T / (N_active × 1 Byte) = 2T
```

H800 FP8 的 Roofline 拐点是：

```
1.98 PFLOPS / 3.35 TB/s ≈ 590 FLOP/Byte
```

于是：

- `2T > 590` → **T > 295** 时，prefill 进入**算力受限**；
- `2T < 590` → 短输入时，prefill 也是**带宽受限**。

**PD 分离的根本原因就在这里**：

| | Prefill | Decode |
|---|---|---|
| 瓶颈 | 算力（长输入） | 带宽（KV 读取） |
| 并行策略 | TP / EP，追求算力 | 大 batch，追求带宽利用率 |
| 扩缩容 | 秒级、突发 | 分钟级、平稳 |

**混在一起跑，就是在用同一个资源配置去满足两种相反的负载。**

### 5.5 全流程串讲：prefill 与 decode 怎么接力

一次请求（输入 5,000 token，输出 350 token）的内部时间线：

```
用户发来 prompt（5,000 token，一次到达）
        │
        ▼
┌─────────────── Prefill（一次性，约 300–600ms） ───────────────┐
│ ① 一次性算完 5,000 个 token 彼此的注意力（大矩阵乘法，并行度极高） │
│ ② 算出每个 token 的 K/V，写入 KV Cache                           │
│ ③ 输出第 1 个新 token（TTFT = 首 token 延迟）                    │
└───────────────────────────────┬────────────────────────────────┘
                                 │ KV Cache（5,001 个 token 的 K/V）
                                 ▼
┌─────────────── Decode（逐 token，350 步） ─────────────────────┐
│ 第 1 步：读 5,001 个 K/V → 生成 token 5,002 → 写入它的 K/V       │
│ 第 2 步：读 5,002 个 K/V → 生成 token 5,003 → 写入               │
│ ……                                                              │
│ 第 350 步：读 5,350 个 K/V → 生成结束 token                      │
└─────────────────────────────────────────────────────────────────┘
```

**两个阶段的本质区别**：

| | Prefill | Decode |
|---|---|---|
| 输入 | 5,000 token 一次到达 | 每步只新增 1 个 token |
| 每步算术强度 | 2T ≈ 10,000 FLOP/Byte | ≈ 2 FLOP/Byte |
| 相对 Roofline 拐点 590 | **远高于 → 算力受限** | **远低于 → 带宽受限** |
| 每步主要成本 | 矩阵乘法的 FLOPs | 读全部 KV 的 HBM 流量 |
| 跑满什么 | Tensor Core | HBM 带宽 |
| 典型耗时 | 300–600ms（一次） | 每步 20–30ms（×350 次） |
| KV Cache | **生产 KV** | **消费 KV + 追加 KV** |
| 负载特征 | 突发、秒级伸缩 | 平稳、长连接、分钟级 |

**串起来的三条工程结论**：

1. **PD 分离**：两种相反的负载必须拆——prefill 池配算力、decode 池配大显存带宽；
   两池之间传 KV（RDMA），传 0.96GB 只需 20ms，远小于重算的 300ms，所以值得。
2. **Chunked prefill**：不分离时，5,000 token 的 prefill 会独占 GPU 几十毫秒，
   decode 请求的 TPOT 会抖；把 prefill 切成小块和 decode 请求混批，平滑 TPOT。
3. **前缀缓存 / GQA / MLA**：全部作用在**让 KV 更少、更可复用**上——
   prefill 少算（命中率 70% 时只算 1,500 token），decode 少读（KV 压缩到 1/4）。

**一个反直觉点**：prefill 也要读 30GB 权重，但 5,000 token 摊下来
每 token 权重成本 = 30GB/5000 = 6MB；decode 每 token 读 30GB 权重 + 越来越长的 KV。
所以**同样一个 token，decode 比 prefill"贵"在访存，不在算力**。

## 7. 三个误区

**误区 1：参数量 × 2 = 显存。**
只在 FP16 成立。FP8 减半，INT4 再减半，MoE 还要加专家并行的副本开销。

**误区 2：batch 越大吞吐越高。**
到 KV 主导时饱和；再大只会把 p99 拉长、把显存挤爆。

**误区 3：TP 能线性加速。**
8 卡 TP 实测通常只有 3–5 倍，通信和效率会吃掉剩余部分。
