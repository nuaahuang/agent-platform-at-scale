011. 问题：成本要降 30%，四个手段摆上桌

第 13 章算出来，推理成本占 TCO 的 61%。老板要求降 30%。工程侧能动的只有四个地方：

手段省多少掉几个点实现难度
FP8 量化（权重与激活）45%1.5低，改启动参数
INT4 权重量化62%4中，要校准
FP8 KV 缓存不降单价，提并发0.8中，kernel 要支持
lite-8B 分流40% 流量成本降 73%分流错了更贵高，要训练分流器

四个手段不是并列的选项。前两个改的是"每个 token 多贵"，第三个改的是"一张卡能装多少请求"，第四个改的是"哪些请求不需要大模型"。

选错方向的典型：为了降单价去做 KV 量化，做完发现成本没变——因为单价由权重带宽决定，KV 量化提的是并发上限。

022. 先看瓶颈：一个 token 要读多少字节

decode 阶段每生成一个 token，GPU 要做两件事：读一遍权重，读这个请求的 KV。两者都走 HBM 带宽。

单 token 的带宽需求可以写成：

batch 越大，权重被摊得越薄。以 200B MoE、8K 上下文为例：

batch权重/批单请求 KV合计权重占比
643.1 GB1.0 GB4.1 GB76%
1281.6 GB1.0 GB2.6 GB61%
2560.78 GB1.0 GB1.78 GB44%
4160.48 GB1.0 GB1.48 GB32%

这张表决定了本章的结论：

  • batch 小（< 128）时，权重占七成带宽，权重量化收益大
  • batch 大（> 256）时，KV 占一半以上，KV 量化收益大
  • 两个都做，收益不是相加，要看当时的 batch 落在线性哪一段

所以"FP8 能省多少"这个问题没有统一答案，得先看你的实际 batch。线上 batch 通常由并发决定，而并发又由 SLO 决定——这是第 10 章的事。

033. FP8：几乎是免费的一档

FP8（8 位浮点）有两套格式，名字就是各位的分配：E 是 exponent（指数位），M 是 mantissa（尾数位）。

同样是 8 位，给指数多一位，范围就大、精度就差。

前面出现过 BF16 和 FP16，先把它们的位置放正。BF16（Brain Floating Point 16，Brain 浮点 16）是 Google Brain 提出的 16 位格式，位分配是 1 位符号 + 8 位指数 + 7 位尾数。

它的取法很特别：把 FP32 的 8 位指数原样搬过来，尾数从 23 位砍到 7 位。这样做的结果是范围和 FP32 一样大（3.4e38），精度掉到 0.4%。FP16 反过来，尾数留 10 位（精度 0.05%），指数只给 5 位，最大只能到 65,504。

训练用 BF16 不用 FP16，原因就是这一条：梯度值小且分布宽，FP16 会下溢成 0，得靠 loss scaling 补救；BF16 和 FP32 同范围，不用这层补丁。代价是精度差 8 倍——但训练对精度没那么敏感，对范围很敏感。

五种格式放一起看：

格式指数位尾数位最大值相对误差用在哪
FP328233.4e381e-7优化器状态
BF16873.4e380.4%训练权重
FP1651065,5040.05%旧版推理权重
FP8 E4M3434486%推理权重与激活
FP8 E5M25257,34412%梯度

两个关键差异：

E4M3 的范围只有 FP16 的 1/146（448 对 65,504）。所以用它之前必须做 scaling——把实际数值乘一个系数，压进 [−448, 448] 这个区间。权重和激活的分布集中，scaling 能做得很好，这就是它能用的原因。

E5M2 的指数位和 FP16 一样是 5 位，范围到 57,344，但尾数只剩 2 位，精度 12%。梯度用它是因为梯度需要的是范围不是精度：梯度值小而分布宽，范围不够会直接下溢成 0。

权重和激活用 E4M3，梯度回传用 E5M2——一句话，前向要精度，反向要范围。

MoE 模型特别适合 FP8，原因是它的计算以 GEMM 为主，数值分布集中，per-tensor scaling 就够用。稠密模型在注意力部分对精度更敏感，往往要 per-channel。

代价是 1.5 个百分点。我们实测的分布是：

题型BF16FP8差值
知识问答93.0%92.5%−0.5
工具调用94.0%93.2%−0.8
JSON 输出99.5%99.1%−0.4
数值推理86.0%82.5%−3.5
长上下文召回88.0%85.0%−3.0

掉点集中在数值推理和长上下文召回。前者因为 FP8 的尾数只有 3 位，累加误差在长计算链上放大；后者因为注意力分数对小扰动敏感。

这两类恰好是售后 Agent 的次要路径，所以能接受。如果业务主路径是算账或长文档比对，FP8 就得重新评估。

成本从 0.53 分/轮降到 0.294 分/轮。这个降幅不是线性的 50%，因为权重减半只影响了公式里的第一项，KV 那部分没变。

启动配置只有几行：

校准集要用线上的真实请求分布，512 条足够。用评测集校准会过拟合——评测集的问法比线上整齐得多。

校准集怎么挑，直接决定量化后掉在哪：

采样来源占比作用
线上随机采样60%覆盖真实分布
长上下文请求（>16K）20%注意力层对精度最敏感的地方
数值与金额类15%校准 scale 的极值区间
边界样本（拒答、异常）5%防止量化把极端值压平

漏掉第二行是常见的错：用短请求校准出来的 scale，跑长上下文会溢出或精度骤降，而评测集里恰好没有长请求。

校准完要看两个信号，不是直接上线：单层输出的相对误差（超过 1% 说明这一层 scale 不对），以及 KL 散度（量化前后输出分布的偏离，超过 0.05 说明模型行为已经变了）。

044. INT4：省得多，掉得也实在

INT4 只量化权重，激活仍是 FP16，所以叫 W4A16。两种主流做法：

方法原理校准成本精度
GPTQ逐层最小化重构误差，用 Hessian高，要几百条样本略好
AWQ找对精度敏感的通道，按通道缩放低，几十条样本略差但更稳

权重从 200 GB 降到 100 GB，成本降到 0.20 分/轮。但掉 4 个点，而且分布很不均匀：

题型FP8INT4差值
知识问答92.5%90.0%−2.5
工具调用93.2%88.0%−5.2
JSON 输出99.1%97.5%−1.6
数值推理82.5%74.0%−8.5
长上下文召回85.0%79.0%−6.0

MoE 还有一个额外问题：专家路由在低精度下更容易抖动。同一个 token，FP8 时路由到专家 12，INT4 时可能路由到 15。单次无所谓，但 batch 内的负载均衡会变差，最热的专家排队，最冷的闲着。

实测的专家利用率从 78% 掉到 61%，这直接吃掉了量化省下的一部分吞吐。

INT4 能用的场景要同时满足三条：

  • 任务窄，且能验证答案对不对（分类、抽取、格式转换）
  • 有 fallback：低置信度时升级到大模型
  • 掉点落在非关键题型上

三条缺一条，就别用 INT4。省下的 0.09 分/轮，抵不上一次批量答错带来的客诉成本。

055. KV 量化：提并发，不降单价

KV 缓存从 FP16 降到 FP8，容量减半：400 GB 变 200 GB，并发从 416 提到 832。

但单价几乎不变。原因在第 2 节的公式里：KV 那部分对应的是"单请求 KV 字节"，量化它只让每个请求占的空间变小，不让每个 token 的计算变少。收益体现在"同样卡数能装更多请求"，也就是摊薄了权重那部分。

4K–16K0.5–1.0

原因是 KV 里存的是历史 token 的键值向量，越长，误差累积越多。售后场景 80% 的请求在 4K 以内，所以整体掉 0.8 个点。如果业务以长文档为主，这个代价要重算。

工程上有个坑：per-token scaling 的计算开销。朴素做法是每个 token 算一次 scale，attention kernel 会被这个串行操作拖慢。生产实现一般用 per-head 或 per-block scaling，kernel 支持才开。

066. 精度-成本曲线：怎么判断停在哪一档

四个点画出来：

方案权重KV单轮成本通过率每掉 1 点省多少
BF16 基线400 GB400 GB0.530 分92.5%—
FP8200 GB400 GB0.294 分91.0%30%
FP8 + KV FP8200 GB200 GB0.260 分90.2%14%
INT4 + KV FP8100 GB200 GB0.190 分86.5%6%

最后一列是判断依据。它衡量的是"这笔交易划不划算"：

  • FP8 每掉 1 点换 30% 成本下降，几乎必上
  • KV 量化每掉 1 点换 14%，可以上，但要确认长上下文占比低
  • INT4 每掉 1 点只换 6%，边际收益降到三档里最差

停在哪一档，取决于两个业务参数：单点准确率值多少钱，以及长尾占比多少。

如果一条错误工单的赔付成本是 ¥20，处理 1.5 亿轮/日，掉 1 个点就是每天多 150 万次错误，代价远超省下的电费。这种情况下停在第 2 档。

反过来，如果是内部知识检索这种错了重问一次就行的场景，第 4 档也合理。

判定线可以量化：把"每掉 1 点的成本节省"和"每条错误的赔付成本 / 单轮成本"对比。前者大于后者，就往下走一档。

077. 四种推理形态，选错比量化选错更贵

压缩解决"多贵"，形态解决"怎么服务"。四种形态对应四类负载，混用会互相拖累。

形态适用负载关键参数代价
在线流式用户等着看（默认）stream=true，TTFT 优先不能批处理优化，吞吐低 30%
在线非流式结果要整体校验（表单填单）返回完整 JSON用户等待感差，要前端 loading
离线批处理批量分类、历史回刷batch 可到 512延迟以分钟计
长上下文合同比对、长文档问答32K 窗口，KV 量化单请求占满显存，并发掉到个位数

第一条和第二条的差别不只是 API：流式模式下，引擎要在 token 级做 flush，网关要支持 SSE，客户端要处理断线重连。整条链路都为"早一点看到第一个字"服务，代价是吞吐。

第三条是省钱的关键。离线任务不占在线资源，可以跑在夜间闲置卡上，按第 33 章的错峰策略，成本能压到在线的一半以下。售后系统的历史工单回刷、意图重新分类，都该走这条路。

第四条和量化直接冲突：长上下文请求的 KV 占比高，权重量化对它几乎没帮助，该做的是 KV 量化和上下文压缩。第 2 节的表已经说明，batch 越大 KV 越重要，而长上下文请求的"单请求 KV"本身就有 4 GB（32K），一个请求就顶四个普通请求。

形态选错的典型：把长文档问答做成在线流式。用户要等 30 秒才看到第一个字，因为 prefill 就要 30 秒（32K token × 0.09 ms），流式一点没用。这种场景该做的是先检索再生成，或者改成异步任务加通知。

088. 部署形态一：lite-8B 分流

8B 的成本是 0.078 分/轮，通过率 62%。单看通过率没法用，但它不是替代大模型，是筛掉一部分请求。

分流的判据不是"问题短"，而是"答案可验证"：

请求类型占比8B 通过率适合分流
意图分类40%88%是，输出是 12 个枚举值
订单状态查询20%85%是，有工具返回值兜底
简单政策问答15%61%否，容易答错条款
多步退款15%32%否
客诉与例外10%18%否

分流的账要算全，不能只算省下的：

分流器准确率要到 63% 才不亏，但 63% 意味着 37% 的请求要多跑一次，用户还要多等一轮。所以实际门槛定在 95%。

95% 的分流器不是靠 8B 自己判断，是用规则加小模型两层：先按意图分类（这个 8B 能到 88%），再用规则兜住高风险的（含金额、含投诉、含例外条款）。

099. 部署形态二：多 LoRA 隔离

一个基座加多个 adapter，每个业务方一个。adapter 很小：r=16 时约 2 亿参数，FP16 下 0.4 GB。

显存账：基座 200 GB，20 个 adapter 共 8 GB，可以忽略。真正的问题是批处理——同一个 batch 里混了不同 adapter 的请求，怎么算。

答案是分组 GEMM。把 batch 按 adapter 分组，每组做一次矩阵乘，再拼回去。Punica 提出的 SGMV 就是这个思路。

方案吞吐损失适用
每请求单独跑60%–80%不适用
按 adapter 分组批处理5%–15%主流
按 adapter 分实例0（但要独立显存）adapter 少、流量大

隔离要注意两点：

第一，KV 缓存必须按租户隔离。第 10B 章讲过前缀缓存的哈希要加 tenant salt，多 LoRA 场景更要严格——不同 adapter 的请求如果共享了 KV，会互相污染语义。

第二，adapter 数量有上限。超过 50 个时，SGMV 的分组开销和 kernel 切换开销会吃掉收益，实测吞吐降到 70% 以下。这时候该拆实例，不是一个实例挂 100 个 adapter。

1010. 四个手段叠起来，不是相加

单独看每个手段的收益，容易高估组合效果。它们作用在不同的项上：

组合作用项叠加后的成本说明
FP8权重0.294权重减半
FP8 + KV FP8权重 + KV0.260KV 减半只影响第二项
再加 lite-8B 分流流量结构0.17940% 流量走 0.078
再加多 LoRA不加成本—只影响隔离，不影响单价

第三行的算法要注意：分流不是简单乘 0.6，因为分错的请求要重跑。

分错的 5% 让总成本比理想值高 38%。这就是为什么分流器的准确率比省下的比例更重要。

四个手段全上，从 0.530 降到约 0.247，降幅 53%。但通过率从 92.5% 掉到 88% 左右——分流的错误和量化的掉点会叠加。

1111. 量化怎么验收：不是看平均分

量化上线前的验收要三件事，只看总分不够：

第一，逐题比对。同一批 50 题，BF16 和量化版各跑一遍，看哪些题翻转了。翻转的题要人工看，判断是"量化让答案变差了"还是"这题本来就在边界上"。

第二，KL 散度。在同一批输入上比较两个版本的输出分布，超过 0.05 说明行为变了，不只是精度掉了。这个指标能抓到总分看不出的漂移。

第三，按长度分桶。短请求和长请求分别看通过率。量化的问题经常只在长上下文暴露，混在一起看会被平均掉。

三件事都过，才允许灰度。灰度期间盯的是客诉率，不是模型指标——量化导致的退化，用户比指标先感知到。

1212. 失败模式

现象根因怎么发现怎么修
量化后吞吐没涨batch 太小，权重没摊薄看实际 batch 分布先提并发，再量化
量化后掉点集中在某类题该类对精度敏感分题型跑评测回退该类到 BF16，或改校准集
INT4 后专家利用率下降路由在低精度下抖动看专家负载直方图回退 FP8，或加路由平滑
KV 量化后长文崩了长上下文误差累积按长度分桶看通过率长请求走未量化的实例
分流后总成本上升分流器准确率不够统计重跑率加规则层，或提高阈值
多 LoRA 后 p99 变差adapter 太多，分组开销大看 kernel 时间占比拆实例

第一条最常见：团队先做量化，做完发现省得不多，因为线上 batch 只有 40，权重占了八成带宽但并发上不去，省的都被排队吃回去了。

1313. 什么情况下这些结论不成立

结论推翻条件
FP8 掉 1.5 点可以接受主路径是数值计算或长文比对时，3.5 点不可接受
INT4 只在窄任务用有强 fallback 且任务可验证时，可以放宽到主路径
KV 量化在高并发才值钱上下文超 32K 时，KV 本身就是瓶颈，低并发也值
分流器 95% 才划算单轮成本差距更大时（如 8B vs API），门槛可以降到 85%

1414. 验收

  1. 能算出你场景下权重和 KV 各占多少带宽，据此判断该量化哪个。
  2. 能画出自己模型的精度-成本曲线，并说出停在第几档、为什么。
  3. 能算出分流器的盈亏平衡点，并说明为什么实际门槛更高。
  4. 能估算多 LoRA 在多少 adapter 数量下开始亏。

1515. 复盘卡

我原来以为量化就是"少存点、快一点"，实际差在要看 batch——权重量化摊薄的是权重那部分，KV 量化摊薄的是并发，两者在不同 batch 下收益差三倍。

1616. 延伸

  • 第 2 章：roofline 与带宽受限，本章的公式来自那里
  • 第 10 章：batch 怎么被 SLO 限制住
  • 第 10B 章：KV 容量与并发上限的推导
