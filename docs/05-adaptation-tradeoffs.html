011. 同一句抱怨，三种病

运营那边反馈："它不懂我们售后业务。"

这句话本身没有信息量。把它拆开，至少是三种完全不同的病，对应四条不同的修复路径：

用户实际遇到的现象病在哪该走哪条路修复周期
问"我的订单到哪了"，模型答"请提供订单号"但不查不知道有这个工具Prompt 补工具说明半天
问"签收 9 天能退吗"，模型答"可以退"不知道政策是 7 天RAG 检索政策两周
每次回复都带"亲~"，不符合客诉场景行为不符合要求Prompt 改语气约束半天
输出的 JSON 少了 refund_amount 字段格式不稳定Prompt few-shot 或微调3 天到 2 个月
多步退款流程走到第三步就乱能力不足（不是知识）换更大模型，或拆步骤换模型

这张表是本章的地基。四件事修的从来不是同一个东西：

  • Prompt 改的是指令，模型权重和知识都没动
  • RAG 改的是这次请求的输入上下文，知识在系统外
  • 微调改的是权重，知识进模型了，但会忘
  • 蒸馏改的是模型规模，用一个小的去模仿大的

选错路径的代价不是白花钱，是花两个月得出"这条路不行"的结论，然后再花两个月。

022. 四种手段的账

先把账摆开，再谈怎么选。

改什么不改什么生效周期回滚成本单轮成本增量
Prompt指令与约束权重、知识分钟级回滚到旧版本+50 到 +300 token 输入
RAG输入上下文权重天到周关掉检索开关+1,500 到 +3,000 输入 token
微调权重系统架构周到月切回基础模型0（权重变，推理结构不变)
蒸馏模型规模教师模型月切回大模型降 3.8 倍（8B 替 200B）

回滚成本这一列最容易被忽略。微调把能力写进权重之后，"改回去"意味着重新拿基础模型再训一遍，中间那两周的评测和灰度要重走。Prompt 改坏了，一分钟就能退。

所以原则是按成本递增试：先 Prompt，不行再 RAG，都不够才微调，蒸馏是最后一步且只对高频窄任务做。

033. Prompt：最便宜，也最容易高估

Prompt 能解决的都是"模型本来就会，只是没被要求"的事：

  • 输出格式（JSON schema、字段顺序、必填项）
  • 语气与话术边界（不说"亲"、不承诺具体到账时间）
  • 流程约束（先查订单再给方案、退款金额必须复述）
  • 拒绝条件（超出权限时转人工）

它解决不了"模型根本不知道"的事。政策条款、这个用户的会员等级、昨天的系统故障——这些不在权重里。硬要用 Prompt 补，得到的不是正确答案，是更自信的编造。

一个具体的边界例子：给模型加一句"退款必须在签收 7 天内"，模型会照做，但它不知道"7 天"从哪天算。这个不知道会以两种方式暴露：一种是答错（用户说"我 8 天前签收的"它还说能退），一种是过度保守（把所有退款都转人工）。两种都比不加这句更糟。

Prompt 的成本要算进去。系统提示从 300 token 涨到 1,200 token，按 prefill 0.09 ms/token 算，TTFT（Time To First Token，首 token 延迟）多 81 ms。基线 610 ms 变成 691 ms，离 800 ms 的红线只剩 109 ms。这就是为什么系统提示不能无限加——它和 TTFT 抢的是同一份 SLO（Service Level Objective）预算。

Prompt 必须有版本号，而且要和评测报告绑定。用 p-2026-10-27.3 这种格式，改一次加一次，评测报告的 manifest 里记这个值（第 4 章 §4.8）。没有版本号的 Prompt，出了问题连"什么时候开始坏的"都查不出来。

044. RAG：解决"不知道"，但有三个天花板

RAG（Retrieval-Augmented Generation，检索增强生成）的做法很直接：用户提问 → 检索相关文档 → 把文档片段拼进上下文 → 模型基于上下文回答。

它把知识从权重里挪到了系统外，好处是政策改了只改文档，不用重训。但它有天花板，而且三个都在工程侧，不在模型侧。

4.1 第一个天花板：检索不到

用户问"我买的东西晚到了三天，能赔吗"，知识库里的条款写的是"配送超时补偿标准"。字面几乎没有重叠，向量检索能不能命中，取决于 embedding 的质量和分块方式。

分块是最常出错的地方。把一份 8,000 字的售后规则按 512 token 切，很可能把"7 天无理由"和它的例外条款切到两块里去。检索命中前半块，模型就按"可以退"回答，而例外条款说的是"拆封的电子产品除外"。

工程上的做法是三件事一起上：

手段配置解决什么
分块512 token，重叠 64避免条款被切断
混合检索向量 + BM25，各取 20 条字面不重叠时靠语义，术语精确时靠关键词
重排交叉编码器，取前 320 条里挑真正相关的 3 条

三件都做，召回率能从 60% 出头到 85% 左右。只做向量检索就上线，是第一大坑。

4.2 第二个天花板：检索到了，但模型没用上

这是更隐蔽的一种。检索结果正确，拼进上下文了，模型回答却绕开了它。

原因有两个。一是上下文太长，关键信息落在中间，模型对首尾更敏感——把最重要的那条放最前面，效果比排序优化更直接。二是上下文里有互相矛盾的条款（新旧政策同时被检索出来），模型会挑一个,挑哪个不确定。

解法是给检索结果加元数据：政策生效日期、适用范围、优先级。拼上下文时按生效日期过滤，冲突时明确告诉模型"以 2026-09 版为准"。这比调 Prompt 有效得多。

4.3 第三个天花板：上下文预算和 TTFT 抢资源

这是最硬的一个，也是容量规划里最容易被忽略的。

检索 2,000 token 上下文，prefill 多 180 ms（0.09 ms/token）。基线 TTFT 610 ms 变成 790 ms，而 SLO 是 800 ms——只剩 10 ms 余量，任何抖动都会破线。

所以 RAG 的上下文长度不是一个"效果越好越长"的参数，它有硬上限：

按 800 ms 目标和 610 ms 基线算，预算是 2,111 token。这决定了 top-k 取 3 还是 5，也决定了要不要做重排压缩。

如果业务确实需要更长的上下文，只有两条路：把 TTFT 目标放宽（用户感知会变差），或者把检索结果做摘要后再拼（多一次模型调用，但省上下文）。

4.4 什么时候不该用 RAG

两个判断：

知识总量很小，比如整个售后规则不到 50 页，约 3 万 token。这种情况下把它全塞进系统提示，比搭一套检索系统简单得多，也没有召回失败的风险。代价是每轮多付 3 万 token 的 prefill，按 0.09 ms/token 算 TTFT 要 2.7 秒——超过 SLO，所以只在低峰或离线场景可用。

另一个判断是任务性质：RAG 适合"查了就能答"，不适合"查了还要推"。用户问"我的情况和条款里第三条对不对得上"，这是推理任务，检索解决不了，得靠模型能力和 Prompt 引导。

055. 微调：三个门槛，缺一个就别做

微调的诱惑在于它看起来最"彻底"——直接改模型。但它是四条路里唯一会留下长期负债的一条。

5.1 门槛一：数据量

高质量样本 5,000 条起，且必须包含错例。

所谓错例，是"模型现在会答错、但正确答案明确"的样本。只用正确样本训，模型学到的是"这种问法该怎么答"，学不到"这种问法容易错在哪"。

数据的另一个要求是一致性。5,000 条样本如果由三个人标，标准不统一，训出来的模型会比基座更不稳定——它把三种标准都学了。

5.2 门槛二：任务窄且稳定

微调适合"同一个动作重复一万次"：把非结构化地址解析成省市区、把客诉文本分类到 12 个工单类型、把退款理由映射到标准码。

它不适合"什么都能答"——那是通用能力，微调只会让它在这件事上变差（灾难性遗忘）。判断方法很简单：能不能用一句话写清"这个模型只做这件事"。写不清就别微调。

5.3 门槛三：能承担版本管理成本

微调之后，你的发布单元从"Prompt 版本"变成了三件套：模型权重 + 训练数据 + 评测基线。

任何一件变了，都要重跑全量评测。这不是流程洁癖——只跑任务集会漏掉通用能力退化。常见做法是混合数据：80% 任务样本 + 20% 通用样本，训完两边都测。

一个 LoRA 微调的实测量级：8×H100，5,000 条样本，r=16、alpha=32、学习率 1e-4、3 个 epoch，约 6 小时，按 ¥30/卡时算约 ¥1,440。钱不多，贵的是后面的评测和灰度。

5.4 灾难性遗忘有多严重

按上面的混合比例训，通用能力通常掉 2 到 5 个百分点。掉在哪很关键：知识问答掉得多，指令遵循掉得少。

如果掉超过 5 个点，说明任务数据和通用数据的比例失衡，或者学习率太高。这两个参数是最常调的两个。

066. 蒸馏：只在高频窄任务上划算

蒸馏是让一个小模型学大模型的输出分布。它划算的条件有三个，同时满足才行：

条件判据不满足的后果
流量足够大该任务占比 ≥20%省下的钱不够训练和评测成本
任务足够窄一句话能说清学生学不全，掉点严重
老师足够强老师在该任务上 ≥90%学生只能学到老师的水平

售后场景里符合条件的是意图分类：占流量 40%，任务窄（12 个类），200B 老师在 50 题上 91%。

做法是拿 200B 标注 5 万条，其中 10% 人工校验，然后用它训 8B。结果通常是 8B 从 62% 提到 85% 到 88%，成本从 0.294 分/轮降到 0.078 分/轮，3.8 倍。

有一个风险要说清：老师答错的样本，学生会学得更自信。因为学生学的不是"正确答案"，是"老师的输出分布"。所以 10% 人工校验那一步不能省，尤其是边界样本。

另一个风险是分布漂移。意图分类的类别会变，加一个新类别就要重蒸一次，否则新类会被硬分到旧类里。

088. 组合起来长什么样

真实的系统不会只用一种。售后 Agent 的分层是这样：

层占比手段模型单轮成本
意图分类40%蒸馏到 8B + Prompt8B0.078 分
简单问答25%Prompt + 小 RAG8B0.11 分

加权下来约 0.30 分/轮，比全走 200B 的 0.294 分差不多，但复杂场景的成功率高 6 个百分点——这才是分层的目的，不是为了省钱，是为了把预算花在需要的地方。

第一条最反直觉：RAG 不是"有总比没有好"。检索系统引入了一个新的失败点，而这个失败点用户看得见——模型会引用一条过时条款，说得头头是道。

1111. 验收：四个问题答得出来才算懂

  1. 给定一条 badcase，能判断它属于"不知道"还是"不会"，并说出依据。
  2. 能算出加 2,000 token 上下文对 TTFT 的影响，并判断是否破线。
  3. 能说出微调之后发布单元变成了哪三件，为什么必须一起绑。
  4. 能判断一个任务该不该蒸馏，用哪三个条件。

1212. 复盘卡

我原来以为 RAG 是"接个向量库就行"，实际差在检索质量——分块、混合检索、重排三步少一步，召回率就掉 20 个点。
