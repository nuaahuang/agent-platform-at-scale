调度与 PD 分离

迁移自 v1 ch04-pd-disaggregation.md。文中引用"第 N 章"为 v1 旧编号，与 v3 的对应关系见 ../../MIGRATION.md。

一句话结论：prefill 和 decode 是两种相反的负载——一个突发吃算力，一个平稳吃带宽。

规模一大，唯一正确的做法是拆成两个资源池、两套调度信号、两个 SLO（Service Level Objective），

中间用一次 KV 传输完成交接。

011. 问题重述：为什么必须谈这件事

把前三章的结论并排放：

PrefillDecode
工作方式几千 token 一次并行1 token/步，走几百步
Roofline 位置平屋顶，算力受限斜屋顶，带宽受限
负载形态突发（7000 QPS 到达）平稳（每个会话持续几秒）
关心的 SLOTTFT（Time To First Token） < 800msTPOT（Time Per Output Token） p95 ≤ 50ms
扩容速度秒级响应突发分钟级，随在飞会话数变
容量模型里的卡数909（含前缀命中折扣）700

让它们共用一张卡，就像让急诊和住院部共用同一间手术室：住院（decode）本来按部就班，一来急诊（5000 token prefill）所有人暂停。

实验 pd_lab.py 把这一幕量化了（40 个在跑 decode，7 QPS 到达）：

模式TPOT p50TPOT p95TPOT max超 50ms 占比TTFT p95
混部（prefill 独占）25ms75ms224ms10.8%200ms
Chunked prefill36ms36ms36ms0%667ms
PD 分离25ms25ms25ms0%220ms

三种处理哲学：

  1. 混部独占：prefill 来了整卡归它，decode 全队停住 → 尖刺；
  2. Chunked：prefill 切碎混跑，人人有份 → 平滑但都变慢（TTFT 3.3 倍）；
  3. PD 分离：急诊住院物理分楼 → 两个 SLO 同时达标，代价是多一套资源 + 一次交接。

033. KV 传输：传什么、传多少、为什么比重算便宜

只传 K/V 张量，不传权重（权重每个实例本来就有一份）。

工程细节：

问题做法
传输时机prefill 结束立刻异步传，与首 token 流式返回并行，隐藏延迟
传哪里D 实例的空闲物理页（第 03 章的分页 pool），按页表写入，不复制第二遍
KV 量化用 FP8 KV 传输再反量化，流量减半（精度损失要评测）
拓扑要求GPUDirect RDMA + rail 对齐（附录 A.6），否则退回 TCP，20ms 变几百 ms
对齐要求P 和 D 必须同模型版本、同精度、同 KV 布局（MLA 压缩维度都要一致）
主流实现NIXL（NVIDIA）、Mooncake（Moonshot）、vLLM KV Connectors、SGLang PD disaggregation

什么时候传输反而不划算（不要教条分离）：

  • 集群太小：两个池各自凑不满 8 卡实例，碎片化浪费；
  • 没有 RDMA：TCP 传 KV 可能慢于重算；
  • 输入极短、输出极短：prefill 占大头，decode 池本身负载轻；
  • 前缀命中极高且 prefill 本就很轻时，chunked 混跑更简单。

经验阈值：日请求数十万级以上、平均输出 >150 token、有 IB/RoCE，分离才开始赚钱。

044. 两个池各自的调度器

4.1 Prefill 池：围绕 TTFT

  • 入队即排队：核心指标是 num_requests_waiting 和队列等待时间；
  • 调度策略：FCFS + 抢占式优先级（付费用户插队，被抢占请求只重算 prefill）；
  • Chunked prefill 仍在用：池内部把超长 prompt 切块，防止单请求饿死队列；
  • 基数树匹配是入队第一动作，决定"算多少"。

4.2 Decode 池：围绕 TPOT

  • 连续批处理（§第 03 章），每 25ms 重组 batch；
  • batch 上限由两条红线共同决定：TPOT p95 ≤ 50ms 和 KV 水位 < 85%；
  • 撞线时的动作有梯度：拒绝新加入 → 抢占低优先级请求（换出 KV 到 CPU，可换回）→ 丢弃重算；
  • 会话粘性：一个请求的 decode 中途不迁移实例（迁移 = 再传一次 KV）。

4.3 Router：第三个调度器

它做两个决定：

  1. 选 P：前缀亲和（同租户/同系统提示 → 同一实例的基数树）；
  2. 选 D：看 D 实例的实时 TPOT 与 KV 水位（KV-aware routing），

这正是 Gateway API Inference Extension 的 InferencePool 在标准化的接口。

我们部署目录里的 20-keda-decode.yaml已经是这套信号（waiting 数 + cache 水位双触发）；P 池再加一个队列长度触发器即可。

关键纪律：不要按 GPU 利用率扩缩容。decode 池 GPU 算力利用率常年 <10%（带宽受限！），按 GPU% 扩容会永远不弹。按队列和 SLO 扩。

5.1 分离后"闲置的另一半"怎么办

先纠正一个直觉：另一半资源本来就用不上，不是分离造成的。

P 跑 prefill T=5,000 时，AI≈10,000，远在屋顶拐点 590 之上：

D 池反过来：带宽跑满时算力只用 0.3%。这是 Roofline 的物理结论，混部也一样。

混部的真实账不是"互补填满"，而是互相踩：

混部（或 chunked）PD 分离
prefill kernel 在跑时decode 被推迟，TPOT 尖刺D 池照常每 25ms 出字
空闲出来的"另一半"无法利用（kernel 独占 SM、batch 形状冲突）不浪费——池大小各自按瓶颈资源定
总卡数按"尖刺叠加"超配按 P:D=1.3:1 分别配，总量更低

进一步省"另一半"的三个手段：

  1. 异构 SKU：P 池用算力强卡（H800），D 池用带宽/显存强卡（H200、甚至 H20——

互联满血、141GB 显存但算力被砍，恰好匹配 decode），每一分钱花在瓶颈资源上；

  1. 池内 chunked：P 池把长 prompt 切块提 MFU，D 池纯 decode 把带宽跑满，

互补优化发生在池内而不是混在一池；

  1. 独立伸缩：P 池按秒级突发弹，D 池按会话量缓变——这是混部永远做不到的弹性粒度。

一句话：分离不是"把浪费拆成两半"，而是承认算力和带宽在两种负载下本就不可兼得，让每种卡只对自己的瓶颈负责。

5.2 异构 SKU 的具体利用率：H800（P）vs H200（D）

口径：8 卡 TP=8 节点；200B MoE FP8 权重 200GB；KV 0.96GB/会话（8K，FP16）。

注意"利用率"必须说清是哪种资源——算力、带宽、容量三个数字完全不同。

推导（可以手算复核）：

看这张表的正确姿势：

  1. 不存在"一个利用率"：P 池算力 40%、带宽 2%、容量 40%；D 池算力 8%、带宽 65%、容量 80%——

每个池都有一项"主资源"被打满，这正是分离+异构的目的；

  1. H200 算力和 H800 完全相同（都是 Hopper），贵只贵在 HBM——

而 D 池恰好为 HBM 付费，P 池不为用不上的 HBM 多花钱；

  1. 中国区替代：P 池 H800，D 池可用 H20（96GB/卡、4TB/s、互联满血、算力被砍）——

decode 不缺算力，H20 当 D 池 SKU 是合规与成本的双优解；

  1. 拿"GPU 利用率"（nvidia-smi 的 SM%）考核两个池都会误判，

P 看 MFU、D 看 MBU 和 KV 水位。

5.3 异构后数据怎么搬：跨节点 KV 迁移

只搬 K/V 张量，权重不搬（权重每个节点本来就有一份 200GB）。

能搬的前提（一致性契约）：

必须一致不一致会怎样
模型版本/修订KV 语义不同 → 结果错乱（必须整池作废重建，见 §6.3 树的版本绑定）
权重精度与 KV 精度要加反量化转换，通常直接重算
注意力结构（GQA 头数/MLA 隐维）张量变不出对应维度
TP 切分方式P、D 都 TP=8 时张量分片天然对齐；TP 度数不同要 reshard（专门的重分片 kernel）
KV 布局/块大小由传输层做块级映射（NIXL registry 干这个），引擎侧不感知

H800 → H200 为什么能直接搬：同一 Hopper 架构、同样的 FP8 格式和张量核，KV 就是一串数字，换 HBM 更大的同代卡不改变 KV 内容——异构只异在"内存规格"，不在"计算语义"。

失败回退：D 池满、RDMA 超时 → 在目标节点重算 prefill（付 300–430ms）或换一台 D 重传，不能让请求挂死；传输层要有超时 + 重试 + 重算三级降级。

跨厂商（H800 → 昇腾）：KV 布局、kernel、页表全不同，不能直接搬——要么在目标栈重算 prefill，要么每个技术栈内部各自闭环 PD（呼应附录 A.8.2 的双栈策略）。

5.4 量化收益：四种架构的卡数、成本、SLO

同一负载（20M DAU、1.5 亿轮/日、7000 QPS、输入 5000、输出 350、命中 70%）：实验 pd_cost_lab.py，口径与 capacity_model.py 一致（冗余 1.3 × 双 AZ 1.2；H200 整机价按 +30%、H20 按 −15% 假设）。

收益拆成三笔（不要混着说）：

  1. PD 分离本身（A→B）：卡数 −16.7%、成本 −16.7%，

换来 TPOT p95 75ms → 25ms、SLO 未达率 10.8% → 0。 省的原因不是"卡跑得更快"，而是混部要压住尖刺必须超配 20%（1.20 争用系数）。

  1. 异构 SKU（B→C）：卡数再 −13.1%，成本 −6.0%。

D 池换成 H200 后单卡 decode 吞吐 ×1.43（带宽 4.8 vs 3.35），但整机贵 30%，所以钱只省 6%。 盈亏平衡点：H200 整机溢价 < 55% 时，异构仍比同构便宜；超过就该留在同构。

  1. 合规替代（B→D）：H20 单卡便宜且带宽 4.0TB/s 高于 H800，卡数 −7.0%、成本 −11.3%；

代价是算力被砍到 1/6——decode 不缺算力，所以几乎无感，但 prefill 绝不能放 H20 池。

必说的五个前提（否则这些百分比不成立）：

  • 规模：小集群两个池各自凑不满 8 卡实例，碎片化会把收益吃光；
  • 网络：无 RDMA/GPUDirect 时 KV 传输从 20ms 变几百 ms，PD 收益归零；
  • 命中率：前缀命中从 70% 掉到 40%，P 池要翻倍，比例失衡；
  • 上下文：32K 时 D 池变 KV 容量受限，H200（141GB）优势扩大，H20 优势缩小；
  • 价格：H200/H20 整机价必须用真实采购价替换后重跑，别抄假设值。

077. 落到我们的容量模型

  • 基准 2,512 卡中，raw 配比约 P 909 / D 700（其余为冗余），比例约 1.3 : 1；
  • 这个比例随业务漂移：输出越长、D 越重；长 prompt 越多、P 越重——所以池子要独立可调；
  • 8 个 cell 各自内部 PD 分离；cell 之间不传 KV（0.96GB × 跨城延迟不划算）；
  • 多轮对话的第二轮：前缀在 D 实例的基数树里 → Router 把请求路由回同一台 D，

由它直接做轻量 prefill 或交回 P——路由亲和把"分离成本"降到最低。

088. 四个误区

误区 0：P 池跑 prefill 时带宽闲置，是分离制造的浪费。不是——prefill 在平屋顶上，AI≈10,000 时只需 6% 的 HBM 带宽；同理 decode 池带宽跑满时算力闲置 99%+。这是 Roofline 的物理事实，混部时这些资源一样用不上（kernel 独占计算单元、batch 形状冲突），分离只是让每种资源"各归其主"。

误区 1：PD 分离 = 成本翻倍。两个池都在跑满自己擅长的负载，混部时的"prefill 尖刺期 decode 空转"消失，容量模型显示总量反而更省；翻倍的是资源碎片风险（小规模才疼）。

误区 2：有了 chunked prefill 就不用分离。Chunked 是"不分离时的最优解"（TPOT 从 224ms 尖刺变 36ms 平滑）；但它把 TTFT 拉长 3 倍，且两种负载仍互相稀释。高 QPS 生产形态两者都要：池内 chunked，池间分离。

误区 3：KV 传输就是 memcpy。它要解决选实例、建页表、RDMA 直写显存、版本一致性、失败回退（重算）五件事，所以才用 NIXL/Mooncake 这种专门组件，不在业务代码里手写。
