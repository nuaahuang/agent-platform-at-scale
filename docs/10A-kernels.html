011. 问题：同一张 H800，吞吐能差 3 倍

第 10 章讲了引擎的四种机制：连续批处理、PagedAttention、chunked prefill、前缀缓存。但机制只决定"谁先算"，不决定"算得多快"。

同样 8 张 H800、同样 200B MoE、同样 batch，attention 与 GEMM 的 kernel 写得好不好，端到端吞吐能差 2–3 倍。

写法H800 上的 attention 吞吐相对
朴素 PyTorch（eager，逐头循环）约 12% 峰值1×
通用 SDPA（cuDNN/flash 后端）约 45% 峰值3.7×
针对性 kernel（FlashMLA 级别）约 78% 峰值6.5×

这不是调参能补上的差距，是"谁来写这个循环"的差距。

022. 四个概念：层、算子、kernel、指令

概念是什么例子谁定义
层（layer）一组算子的组合一个 Transformer block模型结构
算子（operator）数学语义上的一个操作matmul、softmax、rmsnorm、topk框架（ATen 等）
kernel算子在某硬件上的具体实现cuBLAS gemm、flash_mla_with_kvcachekernel 作者
指令GPU 线程执行的机器指令HMMA（半精度矩阵乘加）、LDGSTS（全局→共享异步拷贝）、TMA（张量内存加速器）编译器/架构

关键区别：算子是不变的语义，kernel 是可变的实现。

同一个 matmul 算子，背后可能是三套完全不同的 kernel：

"融合"就发生在第三层：把 5 个算子映射成 1 个 kernel，省掉 4 次启动和 4 次中间结果的 HBM 往返。

033. 一次 decode step 有多少个 kernel

以 60 层模型、每层 12 个算子估算：

阶段每层 kernel 数
RMSNorm、RoPE2
QKV / O 投影3
Attention1
MoE gate + topk2
dispatch / grouped GEMM ×2 / SwiGLU / combine4–5
每层合计约 12–13

而 TPOT（Time Per Output Token） 预算是 25 ms——光下发就吃掉 12%，还没开始算。

这就是 CUDA Graph 存在的理由：把整条 kernel 序列录成一张图，一次提交，重复下发归零。代价是形状必须固定，所以变长 batch 要用 padding 或 masked 方案（DeepGEMM 的 masked grouped GEMM 就是为此而生）。

044. 一个 kernel 的内部结构

GPU 的执行层次：

CTA 是什么：Cooperative Thread Array，NVIDIA 对 thread block 的正式叫法（CUDA 里 blockIdx 指的就是它；OpenCL 叫 work-group，WebGPU 叫 workgroup）。

它是 GPU 上资源分配的单位——shared memory 按 CTA 分配，所以：

约束数值（H800/H100）后果
每 CTA 最多线程1024再大要拆
每 SM 最多线程2048（64 warp）一个 CTA 占满，其他进不来
每 SM shared memory228 KBCTA 要 200 KB → 单 SM 只能跑 1 个
SM 总数132决定并行上限

写 kernel 就是在回答四个问题：

问题典型答案（paged attention）
怎么切 grid？每个 (请求, 头) 一个 CTA
每个 CTA 搬什么进 shared memory？一个 KV block（16 token × 576 维）
怎么并行？warp 内按 16×16 分块做 QK^T
怎么处理长序列？online softmax：边算边更新 running max/sum

shared memory 是稀缺资源：H800/H100 每个 SM 只有 228 KB。一个 CTA 要 200 KB，那这个 SM 同时只能跑一个 CTA——占用率直接掉到下限。

访存合并是第二个坎：一个 warp 的 32 个线程如果读地址连续，一次事务搞定；如果散着读，就变成 32 次。PagedAttention 之所以用 16 token 一块，部分原因就是让这个 16×576 的块在内存里连续。

055. 用什么写：五种技术栈

技术栈代表门槛能达到的峰值可移植性
CUDA C++大多数生产 kernel极高90%+只 NVIDIA
CUTLASS / CuTeDeepGEMM 起点、cuBLAS 同源高90%+只 NVIDIA，按架构模板化
PTX / SASS 手写少量极致优化极高接近 100%绑死具体架构（PTX 是 NVIDIA 虚拟指令集，SASS 是 GPU 真正执行的机器码）
DSL：TritonPyTorch 生态、FlashInfer中70%–90%NVIDIA/AMD
DSL：TileLangDeepInfer、昇腾适配中70%–95%CUDA 与昇腾双后端
Ascend C昇腾原生算子中高依算子只昇腾

趋势是：新项目用 DSL 起步，遇到热点再下沉到 CUDA/CUTLASS。DeepInfer 就是这个组合——tilelang_ops 写通用部分，FlashMLA/DeepGEMM 写极致部分。

066. 融合的收益与代价

FlashMLA 把 Q-norm、Q-RoPE、attention、O-RoPE、转 FP8 五个算子融成一个 kernel：

收益不只是省 4 次启动，更重要的是省掉中间结果的 HBM 往返：每层少写读 2 次 [batch, heads, 512] 的 bf16 tensor——在 decode 这种带宽受限场景下就是净赚。

代价很硬：权重要提前重排。README 要求先调 permute_q_b_proj、permute_wv_proj把权重和 scale 改成 kernel 要求的布局。一旦换了 kernel，权重格式就得跟着变。

这是全书反复出现的模式：性能优化会把"数据布局"变成契约。

你优化的是 kernel，被锁定的是权重格式、checkpoint 格式、甚至训练侧。

077. 通信也是算子

MoE 的传统流程是四步、四次 kernel、两次跨卡：

DeepGEMM 的 Mega MoE 把它合成一个 kernel：dispatch、linear1、linear2、SwiGLU、combine全部融进去，用对称内存（symmetric memory）让 NVLink 通信与 tensor core 计算重叠。

意义在于：MoE 推理的瓶颈本来不是算力，是 all-to-all 的等待。把通信藏进 kernel，等于把"等"变成"顺便做"。

088. 硬件绑定：为什么换卡要重写

kernel 是按 SM 架构编译的，架构一换，指令集、tensor core 形状、shared memory 大小都可能变。

事实时间含义
FlashMLA 移除 Hopper 支持2026.09.30只留 SM100/SM103，KV 格式也变了
DeepInfer 只支持 SM100 与昇腾 9502026.10Hopper 不在列表
昇腾 950 稀疏注意力2026.09.30prefill 410 TFLOPS（峰值 95%）、decode 360（83%）

选硬件时先看 kernel 支持矩阵，再看纸面算力。一张算力更强但没有 kernel 的卡，实际吞吐可能不如一张"弱"卡。

1111. 失败模式：kernel 最常见的六个坑

现象根因怎么发现怎么修
正确但比预期慢 2 倍访存未合并 / bank conflictncu 看 DRAM 吞吐 <60%调整 tile 布局，shared memory 加 padding
跑到一半崩或变慢register spillncu 看 local memory 读写量减 tile、加 __launch_bounds__
结果偶发错误mask / 尾块边界错与参考实现对拍补 tail 分支
换 batch 组合结果就变浮点归约顺序不同固定 seed 仍复现用 batch-invariant kernel
首 token 卡 5 秒JIT 首次编译日志时间戳预热或 AOT 编译
升级驱动后变慢新架构 SASS 变了版本对比锁 toolchain 版本

第二条最隐蔽：寄存器溢出不会报错，只在某些 shape 下慢 30%，很容易被当成"正常波动"。

1211.5 这些 kernel 什么时候不值得

结论推翻条件
用 FlashMLA 而不是 FlashAttention序列短于 512 时，MLA 的额外元数据开销盖过收益
自研 GEMM 而不是 cuBLAS只有 FP8 且形状固定时才赚；FP16 下 cuBLAS 更成熟
手写融合 kernel融合后寄存器压力超限，occupancy 反而下降
SWA 限定窗口任务需要跨长距离回忆时，截断直接掉点

融合的收益上限可以先算出来：750 次 launch × 4 μs ≈ 3 ms，占 25 ms TPOT 的 12%；融合到 300 次能省 1.8 ms。省不到 1 ms 的融合不值得做，维护成本比收益高。

1312. 验收：用 ncu（Nsight Compute）看五个指标

ncu 指标期望说明
sm__throughput>60%SM 整体是否忙
gpu__dram_throughput按 roofline 判断是否撞带宽墙
sm__pipe_tensor_cycles_active>50%tensor core 是否真在用
launch__registers_per_thread<128过高会掉占用率
l1tex__data_bank_conflicts接近 0shared memory 冲突

判据：一个 kernel 优化完，这五个数里至少有两项改善超过 10 个百分点，且端到端吞吐提升可测。只看 kernel 时间不看端到端，容易优化了 5% 的算子、丢了 20% 的收益。

1413. 收口

**调度器决定"谁先算"，kernel 决定"算得多快"。

前者是你能改的，后者通常要等生态——所以选型时要把 kernel 的可获得性算进去。**
