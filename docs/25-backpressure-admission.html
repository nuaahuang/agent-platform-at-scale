011. 问题：90 秒从正常到雪崩

一个普通的工作日晚上，流量从 5,000 QPS 涨到 8,000。系统容量是 7,000。

按直觉，超了 14%，应该"慢一点"。实际发生的是这样：

时刻现象关键指标
T+0流量 8,000 QPS引擎 waiting 队列 500
T+10队列涨到 3,000TTFT（Time To First Token）p95 从 800 ms 到 1.5 s
T+20网关 9 秒超时开始触发超时率 3%
T+30客户端自动重试实际到达 9,600 QPS
T+45队列 12,000，内存告警TTFT p95 超过 9 s
T+60goodput 从 99% 掉到 40%所有请求都在超时
T+90人工限流到 6,000队列开始下降
T+10min恢复，但缓存全冷命中率 0，TTFT 仍然 1.9 s

超了 14%，结果不是"慢 14%"，是完全不可用。

三个原因叠在一起：

第一，队列没有上限。引擎的 waiting 队列默认无界，请求进来就排，排到内存耗尽。

第二，重试放大。客户端 9 秒超时后重试，重试的请求又进队列——实际到达量比真实需求高 20%，而系统的处理能力已经饱和。

第三，缓存被冲垮。过载时新请求不断挤占 KV 池，把热门前缀的块淘汰掉，命中率从 85% 掉到 20%，每次请求要多算 5 倍的 prefill，进一步恶化。

这一章讲的就是怎么在 T+10 秒的时候把这件事掐住。

022. 为什么单点限流救不了

最常见的做法是在网关配一个令牌桶：7,000 QPS，超过就 429。

它有两个盲区。

盲区一：QPS 不等于负载。 7,000 个短请求（200 token）和 7,000 个长请求（8K token）对 GPU 的压力差 40 倍。网关只看请求数，看不出来。

盲区二：压力产生在下游，网关不知道。 网关按 7,000 放行，但如果此刻引擎因为 KV 碎片只能跑到 5,000 的等效能力，网关仍然会放 7,000 进来——多出来的 2,000 全部堆在引擎队列里。

所以压力必须从产生的地方往回传，而不是在入口猜。

这就是背压（backpressure）和限流（rate limiting）的区别：

限流背压
依据预设的速率下游的实时状态
位置入口每一跳
反应固定随负载变化
缺点猜不准要协议支持

两者都要有，但只有限流一定会在过载时失效。

033. 压力信号：看五个数，不看 CPU

后端服务通常看 CPU 利用率做扩缩容。LLM 服务不行，因为 GPU 满载是正常状态——推理时 GPU 本来就该跑满。

五个真正有用的信号：

信号怎么取阈值说明
waiting 队列长度引擎内部计数> 目标等待 × 吞吐最直接
KV 块占用率已用块 ÷ 总块> 90%接近 OOM
TTFT p95滚动 1 分钟> 1.5 × SLO（Service Level Objective）用户体验开始崩
goodput达标请求 ÷ 总请求< 95%最终判据
拒绝率429 ÷ 总请求> 5%已经在丢了

第三个和第四个要一起看。TTFT 涨了但 goodput 没掉，说明只是慢了，还能撑；goodput 掉了，说明已经在丢请求。

第五个是结果，不是原因——它涨起来说明前面四道闸都已经在动作了。

为什么不看 GPU 利用率：它到 100% 是常态，没有区分度。真正有区分度的是"排队的人在等多久"。

044. goodput：降载的唯一判据

一个容易被忽略的定义问题：什么叫"过载"？

不是吞吐下降——吞吐可能还在涨，但每个请求都超时了，这种吞吐是无效的。

所以判据是 goodput：在 SLO 内完成的请求占比。

SLO 是 99.9%，所以 goodput 低于 99.9% 就该动作。但实际用 95% 作为降载触发线，因为 99.9% 太灵敏，一次抖动就触发。

过载时的目标不是"保住吞吐"，是"保住 goodput"。宁可服务 5,000 个都成功的请求，也不要服务 8,000 个里 4,000 个超时的。

055. 逐跳背压：三种机制

压力从下往上传，有三种做法。

机制一：队列水位信号。 每一跳暴露自己的队列长度和容量，上游按比例降速。

缺点是滞后：水位涨起来才知道，反应过来已经晚了几秒。

机制二：显式拒绝。 下游满了直接返回 503 带 Retry-After，上游收到就降速。

优点是准确（下游最清楚自己），缺点是拒绝本身有成本，而且上游如果重试，反而放大。

机制三：并发上限（连接数/在途请求数）。 上游对下游维持一个在途请求上限，满了就不发新的。

这是最有效的一种——它不依赖任何信号传递，靠"发不出去"自然形成背压。HTTP/2 的流控、gRPC 的 max_concurrent_streams 都是这个思路。

三者组合使用：

层用什么为什么
网关 → Harness并发上限简单可靠
Harness → LLM 网关并发上限 + 水位信号要提前量
LLM 网关 → 引擎引擎队列上限 + 显式 503引擎最清楚
引擎内部调度器 waiting 上限防 OOM

066. 五道闸

把上面的机制落到请求路径上，是五道闸，每道管一件事。

闸位置判据动作谁受损
① 配额闸网关入口租户配额（第 16 章）429超配额租户
② 限流闸网关入口全局限速 + 令牌桶429 + Retry-After超出部分
③ 排队闸网关队列长度 vs 上限等待 / 超时拒绝等不及的
④ 准入闸LLM 网关引擎 waiting 队列拒绝 / 降级低优先级
⑤ 执行闸引擎KV 水位抢占 / 截断长请求

五道闸的顺序不能乱。配额在最前（商务规则优先），执行闸在最后（最后一道防线）。

每道闸都要能独立回答三个问题：

  • 判据是什么数（可观测）
  • 超过多少就动作（阈值）
  • 动作是什么（拒绝 / 排队 / 降级 / 抢占）

答不出第三个的闸等于没有。

077. 限流按 QPS 还是 token

这是本章最常被问的问题，答案是两个都要，但用在不同层。

层按什么为什么
网关入口QPS便宜、快、防突发。此时还不知道 token 数
LLM 网关并发请求数能预估上下文长度，能区分长短请求
引擎token/秒 + KV 水位最准，但已经进来了

入口按 QPS 的合理性在于：它防的是"异常流量"（爬虫、攻击、配置错误），这些的特征是请求数异常，不是 token 数异常。

引擎按 token 的合理性在于：它防的是"容量打满"，而容量是被 token 消耗的。

它同时反映了请求数和请求时长，比单独的 QPS 准，又不需要预先知道 token 数。

088. 拒绝的四种语义

拒绝不是只有"返回 503"，语义不同，客户端的行为也不同。

语义状态码客户端该做什么用在哪
重试503 + Retry-After等 N 秒重试一次临时过载
降级200 + 降级标记展示降级内容质量可让
排队202 + 位置轮询或等待异步任务
永久拒绝429不要重试，改配额超配额

第一条要带 Retry-After 且必须是真的。写 Retry-After: 30 但实际 3 秒就好了，客户端会等 30 秒，白等；写 3 秒但实际要 30 秒，客户端重试还是失败，加重拥塞。

那个数字怎么来：

队列 12,000，速率 7,000/秒，就是 1.7 秒。这个数随队列实时变化，不能写死。

第二条容易被忽略。降级返回 200 比返回 503 对用户友好——用户看到的是"这个问题我需要确认后回复"，不是"服务不可用"。

099. 队列为什么是雪崩放大器

排队看起来温和（不拒绝用户），实际上在过载时是加速崩溃的。

用利特尔法则算：队列长度 = 到达率 × 等待时间。

队列 60,000 时，新来的请求要等 8.5 秒——已经超过 9 秒的端到端预算，意味着它们注定超时。但系统仍然在为它们消耗资源。

更糟的是重试：超时后客户端重试，到达率变成 9,600，净增 2,600/秒，队列翻倍速度从 60 秒变成 23 秒。

所以队列必须有上限，且上限由 SLO 反推：

超过 42 万，新请求的等待时间必然超过 60 秒，直接拒绝比排队好。

这条上限的作用不是"省资源"，是"止损"——它把系统的状态从"所有人都慢"变成"一部分人快、一部分人被拒"。后者从商业上更好看，从技术上更容易恢复。

1111. 失败模式

现象根因怎么发现怎么修
超了 20% 就全崩队列无上限队列长度无界增长设上限 + 超时
限流后仍然崩重试放大实际到达 > 真实需求关自动重试，或加大退避
拒绝率 5% 但 goodput 正常拒绝过于保守对比两者放宽阈值
恢复要十几分钟缓存被冲垮命中率曲线恢复期限流更严，先回填缓存
长请求拖垮整池无隔离按长度看 TPOT长请求独立池
网关 429 了但引擎还在满信号不同步对比两边速率统一信号源

第四个最容易被忽略：过载时缓存命中率会掉，恢复不是"流量回落就恢复"，而是"缓存重新热起来才恢复"。所以要给恢复期留缓冲——限流值比正常容量低 20%，跑 10 分钟再放开。

1212. 什么情况下这些结论不成立

结论推翻条件
队列要设上限离线批处理场景，等待时间无所谓，可以不设
拒绝比排队好有充足容量余量且请求可等待时，排队更友好
限流按 QPS请求长度方差极小（如全部是分类任务）时，QPS 就够准
五道闸单体服务、无多租户时，两道闸（限流 + 超时）就够

1313. 验收

  1. 能画出你系统的五道闸，每道说出判据、阈值、动作。
  2. 能算出队列上限，并说明为什么是这个数。
  3. 能说出 Retry-After 怎么算，为什么不能写死。
  4. 能解释为什么超 20% 会全崩，而不是慢 20%。

1414. 复盘卡

我原来以为过载就是"变慢"，实际差在队列和重试会把它加速成雪崩——慢是可以恢复的，雪崩要十几分钟。
