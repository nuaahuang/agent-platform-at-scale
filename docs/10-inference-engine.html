推理引擎：PagedAttention 与连续批处理

迁移自 v1 ch03-inference-engine.md。文中引用"第 N 章"为 v1 旧编号，与 v3 的对应关系见 ../../MIGRATION.md。

一句话结论：推理引擎不负责"算"（kernel 负责算），它负责一件操作系统做的事——

把有限的 HBM 安全、高效、不浪费地分配给成百上千个长短不一的会话。

三大技术：连续批处理、PagedAttention、前缀缓存。

011. 问题：没有引擎会怎样

回到第 02 章的约束：

  • 一块节点 300GB KV 预算，一个 8K 会话要 0.96GB；
  • 会话长短差异巨大（200–8000 token）；
  • 请求随机到达、随时结束；
  • decode 是带宽游戏，GPU 空转一秒就是钱烧掉一秒。

如果让每个请求独占一块显存、自己跑自己的，会出现两个浪费：

  1. padding 浪费：一个 batch 要等长，5000 token 的请求和 200 token 的请求凑一批，短的补 4800 个空位——算力浪费在空气上；
  2. 全队等最慢：batch 里 31 个请求生成完了，1 个还没结束，31 个位置全陪着等。

推理引擎就是来消灭这两个浪费的。

1.1 为什么"等长"是硬性要求

根本原因：GPU 只会算稠密矩形矩阵，不接受参差不齐的行。

一次矩阵乘 X·W，输入 X 必须是 [B, T, d] 的完整长方体：

三个技术原因：

  1. 显存是连续的矩形块：kernel 按固定步长寻址，第 2 行第 201 个位置必须存在，否则索引错乱；
  2. SIMT 并行要求整齐：上万个线程同拍执行同一条指令（SIMD），线程 1 算第 300 个 token、线程 2 却没有第 300 个 token，无法对齐执行；
  3. padding 不只是浪费算力：注意力里还要用 attention mask 屏蔽这些假 token，防止它们污染 softmax——多一步逻辑。

浪费有多大：5000 和 200 凑一批，有效算力利用率 = (5000+200) / (5000×2) = 52%，接近一半烧在空气上。

工程上的四种对策：

对策做法局限
Padding + mask补到本批最长长短混批时浪费
Bucketing（分桶）相近长度凑一批（256 桶、512 桶…）桶有碎片，prefill 常用
Varlen / FlashAttention拼成一维序列 + 偏移量，物理紧凑逻辑分条需要专用 kernel 支持
连续批处理（本章 §2）decode 每 step 重组，且每个请求每步只出 1 token——decode 阶段天然等长（都是 1），padding 问题消失引擎核心技术

注意区分：decode 每个请求每步都只处理 1 个 token，batch 内天然等长，不需要 padding；真正的等长难题在 prefill（输入长短不一），所以才有 bucketing、chunked prefill 和 varlen kernel。

022. 连续批处理（Continuous Batching）

规则只有一条：每个 decode step（约 25ms）结束后，重组一次 batch。

25ms 哪来的？ 它就是 TPOT（每 token 生成间隔），由第 02 章的带宽账决定：

```

每步耗时 = (激活权重 30GB + B × 单会话KV 0.96GB) ÷ 3.35 TB/s

B=32 → 60.7GB ÷ 3.35TB/s ≈ 18ms

B=64 → 91.4GB ÷ 3.35TB/s ≈ 27ms ← 我们的典型工作点

B=128 → 152.9GB ÷ 3.35TB/s ≈ 46ms

```

即"约 25ms"= B≈64、8K 上下文时的每步访存时间（理论值，真实乘效率系数）。

它不是常数，而是一个被选中的工作点：SLO（Service Level Objective） 定 TPOT ≤ 50ms，

调度器就把 batch 顶到满足该红线的最大值（约 120–130），25ms 是留了余量的典型值。

用户体验上：25ms/token ≈ 40 tok/s ≈ 每秒约 60 个汉字，快于人眼阅读。

batch 越大 step 越慢（字蹦得越慢），所以"聚合吞吐 vs TPOT"是调度器的核心权衡。

对比：

静态批处理连续批处理
新请求何时进整批结束后下一个 step（等 25ms）
完成的请求占着位置直到全队结束立刻释放，新人补位
GPU 利用率受最长请求拖累接近满载
谁实现老框架vLLM/SGLang/TGI 都这么做

直觉：静态批处理像"整团进出的旅行团"，连续批处理像"每站都上下客的公交车"。

注意：prefill 和 decode 的计算形状不同，能不能混在一个 step 里？能，但要切小块——

见第 5 节 Chunked Prefill。

为什么 B 只在纸上成立：

  • 显存是"一块连续空间"，会话一个挨一个放。会话结束留下空洞——外部碎片；
  • 会话变长，后面没空间，得整体搬移（memcpy），搬一次几 GB，线上直接卡顿；
  • 共享前缀（系统提示）要复制 KV，没法只存一份。

操作系统在 1960 年代就解决过这个问题：虚拟内存分页。vLLM 把它原封不动搬进来。

044. PagedAttention：给 KV 也装一套虚拟内存

4.1 核心结构

  • 每个物理 block 固定 16 个 token 的 KV（vLLM 默认 16，SGLang 类似）；
  • block table = 进程页表；KV 按需申请 block，写满一块才申请下一块；
  • 会话结束，block 归还池子，谁都能用——无外部碎片；
  • 浪费只有"最后一块没写满"，每会话 < 16 token，实测 0.4%（内部碎片）。

055. Chunked Prefill：让两种负载共乘一班车

问题：一个 5000 token 的 prefill 要独占 GPU 约 150–400ms，期间在 decode 的请求全部等住，TPOT 出现尖刺。

解法：把 prefill 切成 chunk（比如每块 512–2048 token），和 decode 请求混进同一个 step：

  • decode 请求每 step 都在推进，TPOT 平滑；
  • prefill 请求多花几个 step 完成，TTFT（Time To First Token） 略增——用 TTFT 换 TPOT 稳定；
  • 这个配比是调度参数（如 vLLM 的 --max-num-batched-tokens、SGLang 的 chunk 策略），

生产调优的核心旋钮之一。

PD 分离是另一个极端答案：干脆分池（第 04 章细讲）。Chunked prefill 是"不分离时的最优解"。

如果模型用的是滑动窗口注意力（SWA），还有第三种答案：不切 prefill，而是只重放最后一段。

见 §9 的 SWA bounded replay——它能把 prefill 计算量近乎砍半，但前提是注意力窗口有限。

6.1 RadixAttention 原理：把所有请求存成一棵前缀树

核心思想：每个请求的 token 序列是树上的一条路径；公共前缀只存一份 KV，节点可以按 token 粒度分叉（不是按 block）。

新请求进来，沿树找最长匹配前缀：命中的 token 跳过 prefill，只算后缀并把新枝挂上树。演示 radix_lab.py（3 用户 × 3 轮）：

和 vLLM block 哈希的区别：

block 哈希RadixAttention 基数树
复用粒度整个 block（16 token）单个 token（边可以任意长）
部分命中一个 token 不同，整块作废从分叉点精确复用
结构扁平哈希表树，天然表达前缀关系
淘汰块 LRU从叶子 LRU 回收（引用计数）
典型强项通用场景Agent 多轮、few-shot 模板、树搜索

代价：树结构在 CPU 侧维护，高 QPS 下锁竞争和树管理有开销；收益大小取决于前缀到底有多公共——零公共前缀的随机请求，两者都省不了。

和 PagedAttention 的关系（别混）：PagedAttention 管"KV 在显存里怎么摆"（分页），RadixAttention 管"哪段 KV 可以复用"（前缀树）；SGLang 两者都用——树决定复用关系，分页决定物理存放。

6.3 树的作用域：什么时候有几棵树

答案：一个引擎实例（一个模型）一棵逻辑树，不是全局一棵。

边界树的情况原因
不同模型各自独立的树权重不同，同一段 token 的 KV 也不同，复用无意义
同模型 TP=8一棵逻辑树（树在 CPU 侧的调度器里），KV 物理页分片在 8 张卡上匹配只看 token 序列，与卡无关；页表再把索引翻译到各卡分片
不同实例/Pod各有各的树，默认不共享树是进程内内存结构；这正是要做 KV-aware 路由的原因
多租户物理上一棵树，前缀在根处自然分叉；强隔离要求则按租户拆实例KV 不可变且需精确匹配，跨租户不会"误中"；但合规场景物理隔离
模型版本更新整棵树作废重建权重变了，全部旧 KV 失效（缓存版本号必须和模型版本绑定）

跨实例想共享怎么办（第 04/11 章展开）：

  1. 路由层亲和：同系统提示/同租户的请求固定路由到同一实例——把"共享"问题变成"路由"问题；
  2. 分布式 KV 传输：Mooncake / NIXL / LMCache 这类 connector 把前缀 KV 在实例间搬运，

SGLang 的 HiCache 还可以把被淘汰的前缀下沉到 CPU 内存/磁盘；

  1. PD 分离场景：prefill 实例树上的 KV 传给 decode 实例（两实例各有树，传的是 KV 数据本身）。

树节点只存 token 索引和引用关系（CPU 内存，几 MB 级），真正的 KV 在 GPU pool。

所以"多棵树"很便宜，跨机"共享树"很贵——这决定了业界选择"本地树 + 路由亲和 + 显式传输"，

而不是做一棵全局分布式树。

6.4 一个实例对应几张卡

1 个引擎实例 = 1 个并行组 = TP × PP 张卡；扩容靠多副本（数据并行），不靠做大单实例。

模型权重单实例卡数约束
8B FP1616GB1 卡（可一卡多实例/MIG）
70B FP16140GBTP=2–4
200B MoE FP8（本项目）200GBTP=8（一台 H800）≥3 卡装权重，NVLink 域 8 卡
DeepSeek 671B FP8670GB16–32 卡（TP=8 × EP 跨机 RDMA（Remote Direct Memory Access））MoE 专家并行必须跨机

卡数下限 = 权重装得下；上限 = 通信不拖后腿：H800 NVLink 域只有 8 卡（跨机退到 IB）；GB200 NVL72 才把域扩到 72 卡。

不做超大实例的三个原因：all-reduce ring 随卡数变长；故障域大（重载权重几分钟）；弹性粒度粗（闲 10% 就是几十张卡白烧）。所以线上是"几十个 8 卡副本 + 前缀亲和路由"，每副本各有自己的基数树——扩容 = 复制"8 卡 + 一棵树"。

088. 三个误区

误区 1：vLLM 的"连续批处理"靠 GPU 多线程。错。GPU 本身就是批量并行；连续批处理是调度器在 CPU 侧每步重组请求集合，是软件调度创新。

误区 2：PagedAttention 是一种新的注意力算法（数学不同）。错。注意力的数学完全不变，变的是 KV 的内存管理方式——访存地址从"连续读"变成"按 block table 读"。

误区 3：开了前缀缓存就不花钱。缓存只省 prefill 的算力；命中的 KV 照样占显存、decode 照样读。缓存命中率是容量和显存的权衡，不是免费午餐。

9.1 DSpark：把"猜几个"变成"猜几个值得验"

第 10 章我们在 §1 就说过 decode 是带宽受限。投机解码用"小模型猜、大模型验"换速度，但朴素做法有个隐形成本：猜得越多，验证越浪费——高并发下，验证 token 占的是本该给别人 decode 的 batch 容量。

DSpark 的两处改动（论文）：

  1. 半自回归草稿：并行骨干 + 轻量顺序模块，补上块内依赖，缓解"越往后接受率越低"的衰减；
  2. 置信度调度验证：按前缀存活概率 × 引擎吞吐画像，给每个请求动态决定验多长。

生产数据（DeepSeek 自述）：

指标结果
每步需验证的草稿 token−30%
生产负载吞吐+4%–7%
单用户生成速度（对齐吞吐，对比 MTP-1）+60%–85%

注意最后两行的区别：吞吐只涨了几个点，但用户体感快了 60% 以上。这是投机解码真正的价值——它买的不是总吞吐，是在同样吞吐下的交互性。这正好呼应第 1 章的 SLO 分层：TPOT 属于体验层，吞吐属于成本层，两者不是一回事。

9.2 SWA bounded replay：为什么它能砍掉一半 prefill

标准做法（§5）是把长 prefill 切片，和 decode 混跑。DeepInfer 走另一条路：

前提是模型用滑动窗口注意力：只有最后 W 个 token 参与注意力，更早的位置已经被窗口滑出。既然它们不影响结果，就没必要重算——只需保证保留的后缀覆盖"窗口 + 最大回溯长度"。

官方 README 的默认配置是 KEEP_TOKENS=140（compact 模式）；媒体报道写作"最后 128 个 token"，两者略有出入，以 README 为准。

这就是"模型结构决定引擎优化空间"的最好例子：同样的 prefill 问题，稠密全注意力只能切片，滑动窗口可以直接截断。第 06 章讲压缩时会再回到这一点。

它的最小高效部署是 64 GPU prefill + 64 GPU decode，P:D ≈ 1:1——和我们第 11 章算出来的 909:700 ≈ 1.3:1 同一个量级，这是相互印证的。

9.5 一句话

同一个问题（prefill 太贵、decode 太慢、batch 不可复现），

DeepSeek 的答案是"改模型结构 + 自研 kernel + 只在自家硬件上极致优化"；

本书的答案是"通用硬件 + 标准协议 + 可替换组件"。

两条路都对，取决于你有多少卡、多少人和多少时间。

1010. Kernel 层：本章只留结论

引擎的第五层是 kernel——算子在 GPU 上的具体实现。它不在引擎仓库里，而是以独立库（FlashMLA / DeepGEMM / DeepEP）的形式被依赖。

三个必须记住的结论：

  1. 一次 decode step 约 750 次 kernel 启动 ≈ 3 ms，占 TPOT 预算 25 ms 的 12%；
  2. 融合省的是 HBM 往返，代价是权重布局变成契约；
  3. kernel 78% 峰值 ≠ 模型 35% MFU，中间 43 个点丢在调度与通信里。

完整的解剖、五种技术栈、开源地图与调优方法，见 第 10A 章。

1110.5 失败模式与推翻条件

五种跑不顺的样子：

现象根因怎么发现怎么修
吞吐只有账面 70%max_num_seqs 配小了，batch 喂不满扫参数曲线找吞吐拐点按 §8 的表调
TTFT 抖动（p50 400 ms、p99 2 s）chunked prefill 切得太碎看 prefill 队列长度加大 chunk，或限并发
显存缓慢上涨、几小时后 OOM块没释放（引用计数泄漏）块总数只增不减查 release 路径（第 10B 章）
一个长请求拖垮整批长短请求混跑按长度分桶看 TPOT长请求走独立池
前缀命中率只有 40%系统提示里混了时间戳或订单号比对前缀哈希变量后置

显存涨有两个来源，判据不同：块总数（num_gpu_blocks_used）只增不减，是 KV 泄漏；块数稳定但显存仍涨，看 caching allocator 的 reserved 与 allocated 差值——差值扩大是碎片或句柄未释放，去查 request 生命周期，不是查 KV。

什么时候这套结论不成立：

前提推翻后
请求长度分布集中长短混杂时，统一 max_num_seqs 一定吃亏
前缀复用率 ≥85%复用率低时，前缀哈希的开销反而拖慢
单模型单实例多 LoRA 或一卡多模型时，显存账要重算
