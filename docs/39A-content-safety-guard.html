011. 问题：一句"根治"引发的下线

一个中医诊后管理助手，上线两个月，被投诉到监管。原因是给某个患者生成的建议里出现了"从根源改善体质"——这属于疗效承诺，违反广告法。

查日志才发现，这条不是模型自己编的，是患者的就诊记录里医生写了"从根源调理"，模型照抄进了输出。

三个问题同时暴露：

问题表现
提示词写了禁止项，但没兜住安全边界里明确写了"不使用根治、治愈"
没有输出侧校验模型输出了违规词，直接返回给用户
没有离线回溯同类问题已存在两个月，无人发现

这一章讲的就是怎么把这三件事补上：在线怎么拦、离线怎么发现、守卫模型怎么设计。

022. 守卫模型是什么

先说清概念。守卫模型（Guard Model）是一个独立的小模型，专门判断"这段输入或输出该不该放行"。

它和第 39 章的威胁模型不是一回事：

威胁模型（第 39 章）守卫模型（本章）
是什么一张分析表，列出谁会怎么攻击一个跑在推理链路上的分类器
产出攻击面与防御点放行 / 拦截 / 标记
运行方式人写，季度更新每请求调用，毫秒级
失败表现漏掉某个攻击面误杀或漏杀

守卫模型不是"内容审核 API"。商用审核 API 判的是通用违规（色情、暴力、政治），而你的业务违规是"疗效承诺""超范围诊疗""推荐药品"——这些通用 API 判不出来，必须自己训。

033. 三层防御

层手段延迟误杀率漏杀率覆盖
L1 规则正则、关键词、句式1 ms3%–8%40%–60%显性违规词
L2 小模型0.5B 分类器30 ms1%–3%15%–25%语义级违规
L3 大模型7B 生成式审核200 ms0.5%–1%5%–10%复杂判断
人工抽检分钟——兜底

三层不是串联，是并联后取最严：

为什么要三层而不是直接上 L3：延迟。L3 要 200 ms，而首 token 预算只有 800 ms，占了四分之一。所以 L3 只能用在"L2 标记可疑"的少数请求上（约 3%–5%），平均延迟增加约 10 ms。

3.1 每层的职责边界

层管什么不管什么
L1"根治""治愈""保证瘦"这类词"从根本上调理"这种变体
L2语义等价、意图判断、超范围需要专业知识才判的（如证型是否匹配）
L3复杂上下文、多轮累积违规实时性要求高的场景

L1 的边界最清楚：它只能抓显性词。"根治"能抓，"从根源改善"抓不到——后者要 L2。

044. 守卫模型怎么设计

4.1 先定任务形态

三种可选，成本差 10 倍：

形态输出模型延迟适用
二分类违规/正常0.5B30 ms单一违规类型
多分类违规类型0.5B–1B35 ms5–10 类违规
生成式判定 + 理由7B200 ms需要解释、需要引用条款

多数场景选第二种。生成式的价值在"能告诉你为什么违规、引用了哪条规则"，适合做 L3 复核和人工辅助，不适合做在线第一道。

4.2 训练数据从哪来

这是守卫模型最难的一步——你没有标注数据。

四个来源，按可用性排：

来源量质量怎么拿
规则命中的样本中高（正样本）L1 的命中记录
用户投诉/申诉低极高客服工单
人工构造的对抗样本低高安全团队红队
大模型标注 + 人工抽检高中用 L3 打标，人抽 10%

第三行最容易被忽略。红队构造的对抗样本是唯一能提前发现新攻击面的方式——等线上出事故再补，代价是下线。

一个可用的启动量：每类违规 2,000 条正样本 + 10,000 条负样本。少于这个量，0.5B 模型学不动。

4.3 评估指标不是准确率

守卫模型的评估和普通分类器不同，因为误杀和漏杀的代价不对称：

指标定义目标
误杀率正常内容被拦的比例< 2%
漏杀率违规内容被放行的比例< 5%
延迟 p99判定耗时< 50 ms

误杀率高会赶走正常用户（"怎么什么都拦"），漏杀率高会出事。两个都重要，但调节阈值时优先保误杀率——因为漏杀的后果是延迟的（可能几个月后才发现），误杀的后果是立刻的（用户当天就投诉）。

这也解释了为什么第一层用规则：规则误杀率 3%–8% 偏高，但它的命中可以只标记不拦截，交给 L2 判断。

4.4 多租户：一套模型还是多套

方案优点缺点
一套通用模型维护成本低不同行业规则冲突
每行业一套精准训练数据要按行业分
一套 + 租户规则层折中规则层要能配

推荐第三种：模型通用，规则租户可配。中医的"疗效承诺"和电商的"绝对化用语"是同一类问题（夸大宣传），模型能共用，只是关键词表不同。

055. 性能：30 ms 从哪来，怎么保住 TTFT

5.1 延迟分解

一条请求进网关后，防御的耗时：

步在哪耗时
字符粗估网关进程内0.001 ms
tokenize网关进程内（Rust）2 ms
结构化裁剪网关进程内0.01 ms
重复率 MinHash网关进程内2 ms
守卫模型独立 GPU 服务30 ms
拼接Harness0.001 ms

34 ms，其中守卫模型占 88%。

5.2 首 token 延迟预算

环节基线加防御
客户端到网关77
裁剪、检测、审核034
RAG 检索180180
排队5050
prefill（缓存命中）1518
合计258295

800 ms 预算用掉 37%，还剩 505 ms。

5.3 守卫模型不影响 TPOT（Time Per Output Token）

TPOT 是 decode 阶段每 token 的间隔，守卫模型在 prefill 之前就结束了。唯一例外是过载时的抢占，那是第 25 章的机制。

5.4 什么时候这套不够

换成 7B 生成式审核（200–500 ms）：

一次抖动就破线。三条出路：

出路做法代价
上调 SLOTTFT 从 800 提到 1,500 ms（SLO 同步放宽）体验变差
异步审核先返回，后台判，命中就撤回医疗场景不可撤回
只审 L2 可疑的5% 请求走 L3，平均只加 10 ms漏杀率略升

第三条是通用解：用 5% 的覆盖率换 90% 的延迟节省。

5.5 真正威胁 TTFT 的不是守卫

把命中率从 0 提到 85%，比砍掉全部防御划算 7 倍。所以优先级是：

优先级做什么收益
1提示词结构改对（静态前置）省 180 ms
2预热常见前缀（第 7 章）冷启动 270 → 15 ms
3削减守卫开销最多省 34 ms

不要为了省 30 ms 去掉守卫——那是拿 34 ms 换一次下线。

065.6 守卫服务怎么部署

守卫模型是独立服务，不是嵌在网关里的一个函数。三个理由：

理由说明
它是 GPU 推理0.5B 模型装不进网关的 CPU 进程
它要独立扩缩容拦截率升高时，守卫的负载先涨
它要独立灰度换模型版本不能带着主服务一起发

部署形态：

缓存很重要。 同一段输入在 60 秒内重复送审很常见（重试、多轮），判定结果缓存能把守卫的 QPS 降 30%–50%。

四个运行参数：

参数值说明
超时50 ms超过就走 fail-open/close
并发上限每副本 200超过就排队
降级规则兜底守卫全挂时只跑 L1
采样1% 全量存给离线训练用

第三行最关键：守卫服务挂了不能让主链路挂。降级策略是"只用规则层"，误杀率不变、漏杀率升到 40%，但服务可用。

这和第 25 章的分层是同一个思路：任何单点都允许失效，只要失效时是降级而不是崩。

076. 持续进化：守卫模型多久重训一次

守卫模型会衰减。攻击手法在变，新的违规变体每季度都会出现。三个机制保它不旧。

6.1 数据闭环

周期：数据每日入库，模型每月重训，规则每周更新。

为什么模型不能每周重训：训练本身几小时，但评估、灰度、回归要一周。而规则（L1）可以每周改，因为它没有训练成本。

6.2 漂移监控

守卫模型最危险的不是"判错"，是"悄悄失效"。三个监控指标：

指标正常异常说明
拦截率3%–5%突然降到 1% → 模型失效或被绕过
误杀率（人工抽检）< 2%升到 5% → 阈值太严
输入分布稳定长度/类型突变 → 业务变了，模型要重训

第二个靠人工抽检：每周抽 200 条被拦截的，人工判有多少是误杀。这个是唯一可信的误杀率来源。

6.3 红队常态化

等线上出事故再补，代价是下线。所以要有主动找问题的机制：

方式频率产出
内部红队每月20–50 条新对抗样本
外部众测每季度100+ 条
监管通报跟踪持续同类产品的处罚案例

第三行最实用：看同行被罚什么，就补什么规则。这是最便宜的威胁情报。

087. 一个完整的落地清单

项内容优先级

前三项不做完，不要上线。

098. 失败模式

现象根因怎么发现怎么修
违规内容上线两个月才发现没有离线审计事后才知道补 1% 采样
正常用户被批量拦截阈值太严误杀率监控降阈值，改由 L2 判
守卫模型拦截率从 4% 掉到 1%模型衰减或被绕过拦截率曲线重训 + 红队
加了守卫 TTFT 破线用了 7B 同步审TTFT p95改异步或只审可疑
同一内容 A 租户拦 B 租户放规则没隔离比对两个租户规则按租户配置
提示词说一套校验做一套两处维护全量失败从同一 schema 生成

第六行最常见：提示词写"缺失填 null"，校验却断言不能为 null——模型永远重试，永远失败，团队以为模型不听话。

109. 什么情况下这些结论不成立

结论推翻条件
守卫模型必须自训业务违规就是通用违规（色情/暴力）时，用商用 API 更划算
三层防御单一租户、单一场景时，规则 + 输出校验就够
L3 只审 5%监管要求全量审核时，只能同步全审并上调 SLO
每月重训业务规则极稳定（如只做格式转换）时，季度重训即可

1110. 验收

  1. 能画出你的三层防御，每层说出误杀率、漏杀率、延迟。
  2. 能说出守卫模型的训练数据从哪来，每类多少条。
  3. 能算出加守卫后的 TTFT，并说明是否在预算内。
  4. 能设计漂移监控的三个指标。

1211. 复盘卡

我原来以为提示词里写了禁止项就够了，实际差在没有输出侧校验——模型会照抄输入里的违规词，而提示词管不住这个。

1312. 延伸

  • 第 39 章：威胁模型，本章是它在内容维度的落地
  • 第 40 章：合规与数据治理，留存与审计
  • 第 7 章：提示词结构与缓存，本章的 30 ms 优化依赖它
  • 第 25 章：背压，守卫服务的可用性要求
  • 第 17 章：成本，守卫算力与离线审计的账

结论是：内容安全不是"加一个审核 API"，是三层分工——规则抓显性、小模型抓语义、大模型抓复杂，再加一条离线闭环把新发现的模式变成新规则。守卫模型吃 30 ms，但真正决定 TTFT 的是缓存命中率，不是它。
