011. 问题：按电商那套设计，三个月后被推翻

一个典型的重构事故，几乎每个团队都会走一遍：

团队按成熟电商架构设计了 Agent 平台：无状态服务 + 水平扩展 + Redis 缓存 + MQ 削峰 + 网关限流。

上线两周后，五个问题同时爆发。

设计预期实际根因
无状态 + 水平扩展加机器就扩容扩 10% 要 10 分钟，期间流量已经涨完GPU 扩容有加载成本
Redis 缓存回答命中率 60%+命中率 8%用户问题几乎不重复
MQ 削峰峰值排队，谷时消化堆了 10 万条，GPU 还是 7000 QPS算力不能"存起来"
网关限流保护后端短请求占满额度，长请求全排队瓶颈是 token 不是 QPS
失败重试 3 次提高成功率一次抖动变成雪崩重试成本是 prefill 全量

五个问题指向同一件事：AI 服务不是"另一种 Web 服务"，它是有状态的、按 token 计费的、排队不可缓冲的计算服务。

这一章不给结论，给判据——让你拿到任何一个经典模式，能自己判断它属于哪一档。

022. 一条判据：三问定性

拿到一个传统模式，先问三个问题：

问题如果答案是…结论
① 瓶颈是"并发连接"还是"计算/带宽"？计算/带宽传统扩容逻辑失效
② 状态能不能外置？不能（KV 在显存里）无状态假设失效
③ 计费单位是"请求"还是"token"？token限流/配额/成本模型全要改

三问全过，才能原样复用；中一个，就要变形；中两个以上，基本失效。

055. 从指标到自动动作：五层控制环

§4 的达标线不是拿来"看看"的——每一条都应该能被系统自己感知并处置。但"感知"和"自动处置"之间隔着四道关，任何一道没做对，自动化都会变成灾难。

5.1 一个指标要走完四道关

关卡要解决什么常见错误达标线
采集在哪打点、带什么标签只在网关打，引擎内部是黑盒每请求 ≥6 个标签；采集开销 <1%
聚合用什么窗口、什么分位只用平均值1 s / 10 s / 1 m / 5 m 四档；p50/p95/p99
判定阈值、趋势还是预算单点越线就动作连续 3 个窗口；滞回带 20%
执行选对动作 + 限速一律扩容动作预算：每小时 ≤6 次

采集这一关最重要：如果"亲和命中"这个数在路由层没有打点，它就只是一句口号，永远无法自动化。

5.2 关键：指标要分类，动作要匹配

这是整套自动化的核心洞察——不是所有指标都该用"扩容"来响应。

指标类型例子正确动作错误的动作为什么错
容量型队列深度、TTFT p95、KV 水位扩容 / 缩容降级降级只是掩盖，容量还是不够
正确性型亲和命中率、跨租户共享、对账差修配置 / 切流 / 回滚扩容命中率与卡数无关
成本型每轮 token、每秒成本降级 / 调参扩容越扩越贵
依赖型下游工具错误率、DB 延迟熔断 / 降级扩容问题不在你这边

举例：亲和命中率从 95% 掉到 60%，正确动作是检查路由表是否被重启清空、哈希键是否变了；此时扩容 100 张卡，命中率一点不会涨。

判断方法：问一句"这个指标变差，是因为资源不够吗？"

不是，就别用扩容解决。

5.3 五层架构

层职责组件达标线
L0 采集打点、统一 schemaSDK / sidecar / eBPF标签 ≤20 个防基数爆炸
L1 汇聚多分辨率聚合、原始事件留存流式聚合 + 列存1 s 粒度延迟 ≤3 s
L2 判定SLO（Service Level Objective） burn rate、规则、异常检测规则引擎误报率 <5%
L3 决策选动作、算预算、定优先级决策引擎决策延迟 ≤5 s
L4 执行调 K8s / 网关 / 配置Controller动作可回滚率 100%
L5 审计每次自动动作留痕事件日志可复原"当时为什么这么做"

L3 和 L4 必须分开：决策是"该怎么办"，执行是"怎么安全地办"。合并在一起，就会出现"决策说扩 50 台，执行一口气拉起 50 台把存储打爆"。

5.4 一个完整例子：TTFT p95 从 600 ms 涨到 1200 ms

时间层发生了什么
T+0L0网关与引擎同时上报 TTFT，标签含 tenant / model / cell
T+30 sL11 m 窗口 p95 = 1180 ms，越过 800 ms
T+90 sL2连续 3 个窗口越线，且错误预算燃烧率 3.2×（>2× 告警线）
T+95 sL3决策：先判别类型——查 token/s 是否超配额。发现长请求占比从 5%→22%，判定为"配额型过载"
T+100 sL4动作 1：对超配额租户限流（不动容量）；动作 2：预热池 +2 实例（3 min 后可用）
T+160 sL1复测 p95 = 820 ms，仍在临界
T+165 sL3动作 3：触发 L1 降级（关投机解码），单用户变慢但吞吐 +12%
T+220 sL2p95 = 640 ms，恢复；燃烧率回落到 0.4×
T+10 minL3稳定后自动撤销降级（这是最容易漏的一步）
全程L5记一条：原因=长请求激增 动作=限流+扩容+降级 结果=恢复@220s

这个例子里扩容只是三个动作之一。只会上扩的系统，遇到长请求激增会越扩越糟。

5.5 自动化的三条纪律

纪律内容违反的后果
先观察两周人工盯两周，确认规则不误报，再开自动执行规则一上线就震荡
每个动作可回滚扩容可缩、降级可撤、切流可切回出了错只能重启
动作预算每小时 ≤6 次，防震荡扩了缩、缩了扩，抖动放大

震荡是最常见的失败：扩容阈值 80%、缩容阈值 79%，系统会整夜开开关关。解法是滞回——扩容 80%、缩容 40%，中间 40 个点不动。

5.6 每层用什么组件，什么时候必须自研

层现成能力开源/商业组件什么时候必须自研
L0 采集指标 SDK、抓取OpenTelemetry、vLLM/SGLang 的 /metrics、eBPF（Pixie）需要引擎内部细粒度（每层 KV、每 block 命中）
L1 汇聚时序库、规则聚合Prometheus + Thanos/Mimir、VictoriaMetrics、ClickHouse高基数（按 session 维度）或跨年留存

L3 决策简单伸缩HPA（custom metrics）、KEDA（Kubernetes Event-driven Autoscaling）、Karpenter需要"先判类型再选动作"——必须自研

066. 三个必须自建的组件

6.1 路由层（Affinity Router）

项内容
为什么必须自建传统负载均衡按"连接数最少"分发，会打散会话，KV 全废
怎么做① 路由键 = hash(tenant_id + session_id)；② 路由表放 Redis，实例每 5 s 心跳续租；③ 目标实例不可达时回退到"冷实例"，同时触发事件重放重建上下文
达标线亲和命中 ≥95%；路由收敛 ≤5 s；单实例故障时迁移 ≤10 s；回退请求 TTFT ≤2 s
常见错误用随机或轮询 → 命中率趋近 0，等于每次都冷启动

6.2 配额中心（Quota Center）

项内容
为什么必须自建传统限流按 QPS，AI 的稀缺资源是 GPU 秒
怎么做① 三维配额：QPS / token-per-second / inflight；② 滑动窗口计数，本地预扣 + 中心校正（误差 <0.1%）；③ 支持租户间借调（空闲租户的额度可被借用，10 s 内生效）
达标线计数误差 <0.1%；配额变更 ≤10 s 全局生效；单点故障不影响放行
推翻条件当租户数 <10 时可退化为静态配置，不必上中心

6.3 版本矩阵（Release Matrix）

项内容
为什么必须自建传统发布只有"代码版本"，AI 有模型、Prompt、工具 schema 三套，且会互相不兼容
怎么做① 三套版本组成一个不可拆的 release set（如 m4.1-p7-t3）；② 每个 set 必须过 50 条黄金用例；③ 灰度时整个 set 一起切，不允许单独切其中一项
达标线每个 set 有用例覆盖率 100%；回滚 ≤1 min；非法组合在 CI 阶段就拒绝
反例只灰度模型不灰度 Prompt → 指标全绿，质量掉了（见 §6 第七条）

8.1 案例一：加机器为什么是阶梯不是滑杆

传统服务扩容：多起一个 Pod，容量 +1/N，秒级生效。

GPU 扩容的真实路径：

而且扩的不是"1 张卡"，是 TP8 = 8 卡一个实例——因为 200B 模型的权重切不开到单卡。

步骤耗时能优化吗
节点开机（云上）3–5 min用预留池

推论：容量是阶梯，不是滑杆。2512 卡扩 10% 是 251 卡 ≈ 31 个 TP8 实例，一次性要加载 31 × 200 GB = 6.2 TB——存储带宽会先成为瓶颈。

这就是第 33 章要讲"预热池"的原因：你不可能等它扩，只能提前准备好。

慢的物理原因不在这里，在下一层：为什么必须整卡 8 张、为什么镜像 8–15 GB、为什么驱动不能进容器——这些是 K8s 与 GPU 运行时决定的，展开见 第 32 章。本章只记结论：容量是阶梯。

8.2 案例二：一次重试有多贵

传统服务重试：CPU 空闲时成本接近 0。

LLM 重试：要把整段上下文重新 prefill 一遍。

现在算一笔账：

场景重试请求占比额外 GPU后果
健康0.1%2.8 张无感
轻微抖动1%28 张吃掉一个机柜
故障中（重试 3 次）全部重试 3 次+200%雪崩

1% 的重试 = 28 张卡。 这就是为什么第 24 章要把"重试预算"写进契约：重试不是免费的，它按 prefill 全价收费。

更进一步：重试会和降级打架。过载时你降级到小模型，客户端超时重试，重试打到已经降级的池子，池子更慢，超时更多——正反馈直到崩溃。

8.3 案例三：为什么限流放在网关会失效

网关看到的是 QPS，GPU 的瓶颈是 token/s。

假设 7000 QPS 里有 5% 是长文档：

请求类型占比每请求 token贡献 token/s
普通对话95%8005,320,000
长文档分析5%32,00011,200,000

5% 的请求贡献了 68% 的算力消耗。 但按 QPS 限流，它们只占 5% 的额度。

后果：

  1. 长请求"合法地"占用了 40 倍的算力；
  2. 短请求把额度吃满后，长请求开始排队，TTFT 从 800 ms 涨到 12 s；
  3. 你以为是"容量不够"，其实是"额度分配错了"。

三个维度缺一不可：QPS 管调度器，token 管 GPU，在飞数管显存。

8.4 案例四：多活为什么必须变成多 cell

传统多活：两个机房各接 50% 流量，挂一个切另一个，用户无感。

LLM 的会话是有状态的，KV 就在显存里：

而且不只是"慢"：会话一旦迁到另一个实例，前缀缓存全部失效，下一个请求要重新 prefill 32K token，TTFT 从 600 ms 变成 4 s。

方案代价
全局多活每次迁移 3.84 GB，p99 +3 s，缓存全废
多 cell每个 cell 独立闭环，会话不迁移；故障时该 cell 用户受影响

结论：放弃"全局多活"，改"多 cell + 单 cell 高可用"。可用性的说法也要改：不是"整体 99.9%"，而是"单 cell 99.9%，cell 间故障不扩散"。

顺序改什么为什么先改它不先改的后果

1010. 失败模式

现象根因怎么发现怎么修
扩容永远慢一步把 GPU 当无状态服务扩容耗时 vs 流量爬坡时间预热池 + 预测式（33 章）

削峰削不动算力不可存储MQ 堆积且 GPU 饱和准入控制替代排队（25 章）
长请求饿死短请求单一维度限流p99 与 p50 差距拉大token 维度限流

灰度后质量下降版本矩阵没维护只有主观反馈三套版本强绑定（36 章）
越重试越崩重试与降级互相激化重试率随错误率同步上升重试预算 + 降级期间禁重试

最后一条是个正反馈环：过载 → 降级 → 更慢 → 超时 → 重试 → 更过载。打破它只有一个办法：让重试本身也有预算，用完了就不再试。
