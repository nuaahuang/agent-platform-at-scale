011. 问题：按电商那套设计，三个月后被推翻

一个典型的重构事故，几乎每个团队都会走一遍：

团队按成熟电商架构设计了 Agent 平台：无状态服务 + 水平扩展 + Redis 缓存 + MQ 削峰 + 网关限流。

上线两周后，五个问题同时爆发。

设计预期实际根因
无状态 + 水平扩展加机器就扩容扩 10% 要 10 分钟，期间流量已经涨完GPU 扩容有加载成本
Redis 缓存回答命中率 60%+命中率 8%用户问题几乎不重复
MQ 削峰峰值排队，谷时消化堆了 10 万条，GPU 还是 7000 QPS算力不能"存起来"
网关限流保护后端短请求占满额度，长请求全排队瓶颈是 token 不是 QPS
失败重试 3 次提高成功率一次抖动变成雪崩重试成本是 prefill 全量

五个问题指向同一件事：AI 服务不是"另一种 Web 服务"，它是有状态的、按 token 计费的、排队不可缓冲的计算服务。

这一章不给结论，给判据——让你拿到任何一个经典模式，能自己判断它属于哪一档。

022. 一条判据：三问定性

拿到一个传统模式，先问三个问题：

问题如果答案是…结论
① 瓶颈是"并发连接"还是"计算/带宽"？计算/带宽传统扩容逻辑失效
② 状态能不能外置？不能（KV 在显存里）无状态假设失效
③ 计费单位是"请求"还是"token"？token限流/配额/成本模型全要改

三问全过，才能原样复用；中一个，就要变形；中两个以上，基本失效。

033. 判定表：13 个经典模式

经典模式判定为什么怎么改
无状态水平扩展变形GPU 有状态：KV、前缀树都在显存路由亲和 + 会话粘性
连接池复用到引擎的 gRPC 池仍然必要容量按 KV 显存算，不按连接数
多级缓存变形缓存的是 KV 不是响应前缀缓存，命中率 85% vs 8%
MQ 削峰失效算力不能"先存后算"只能准入控制 + 拒绝
限流变形瓶颈是 token/s，不是 QPS双维度：QPS + token/s
熔断复用语义没变阈值按 token 与在飞数设
降级变形降级目标是"更小的模型/规则"L0–L5 阶梯（第 35 章）
多活 / 单元化变形KV 不跨区传输多 cell，会话内闭环
分库分表复用数据模型没变按 tenant 分片 + 时间分区
幂等复用+工具调用有副作用，比写接口更关键幂等键 + 副作用日志
灰度发布扩展变成三套版本：模型 / Prompt / 工具版本矩阵（第 36 章）
压测变形必须按长度分布打开环 + 生产分布（第 12 章）
重试慎用重试要重跑 prefill重试预算 + 只重试可重试错误

判定为"复用"的只有 4 个（连接池、熔断、分库分表、幂等）。剩下 9 个全部要改——这个比例本身就是结论：传统经验能直接用的部分不到三分之一。

044. 三个深挖：为什么失效

4.1 案例一：加机器为什么是阶梯不是滑杆

传统服务扩容：多起一个 Pod，容量 +1/N，秒级生效。

步骤耗时能优化吗
节点开机（云上）3–5 min用预留池

权重加载 400 GB3–5 minP2P 分发、本地 NVMe 缓存

推论：容量是阶梯，不是滑杆。2512 卡扩 10% 是 251 卡 ≈ 31 个 TP8 实例，一次性要加载 31 × 400 GB = 12.4 TB——存储带宽会先成为瓶颈。

这就是第 33 章要讲"预热池"的原因：你不可能等它扩，只能提前准备好。

4.2 案例二：一次重试有多贵

传统服务重试：CPU 空闲时成本接近 0。

LLM 重试：要把整段上下文重新 prefill 一遍。

现在算一笔账：

场景重试请求占比额外 GPU后果
健康0.1%2.8 张无感
轻微抖动1%28 张吃掉一个机柜
故障中（重试 3 次）全部重试 3 次+200%雪崩

1% 的重试 = 28 张卡。 这就是为什么第 24 章要把"重试预算"写进契约：重试不是免费的，它按 prefill 全价收费。

更进一步：重试会和降级打架。过载时你降级到小模型，客户端超时重试，重试打到已经降级的池子，池子更慢，超时更多——正反馈直到崩溃。

4.3 案例三：为什么限流放在网关会失效

网关看到的是 QPS，GPU 的瓶颈是 token/s。

假设 7000 QPS 里有 5% 是长文档：

请求类型占比每请求 token贡献 token/s
普通对话95%8005,320,000
长文档分析5%32,00011,200,000

5% 的请求贡献了 68% 的算力消耗。 但按 QPS 限流，它们只占 5% 的额度。

后果：

  1. 长请求"合法地"占用了 40 倍的算力；
  2. 短请求把额度吃满后，长请求开始排队，TTFT 从 800 ms 涨到 12 s；
  3. 你以为是"容量不够"，其实是"额度分配错了"。

正确做法是双维度限流：

三个维度缺一不可：QPS 管调度器，token 管 GPU，在飞数管显存。

4.4 案例四：多活为什么必须变成多 cell

传统多活：两个机房各接 50% 流量，挂一个切另一个，用户无感。

LLM 的会话是有状态的，KV 就在显存里：

而且不只是"慢"：会话一旦迁到另一个实例，前缀缓存全部失效，下一个请求要重新 prefill 32K token，TTFT 从 600 ms 变成 4 s。

方案代价
全局多活每次迁移 3.84 GB，p99 +3 s，缓存全废
多 cell每个 cell 独立闭环，会话不迁移；故障时该 cell 用户受影响

结论：放弃"全局多活"，改"多 cell + 单 cell 高可用"。可用性的说法也要改：不是"整体 99.9%"，而是"单 cell 99.9%，cell 间故障不扩散"。

055. 照抄会死的七件事

照抄的做法什么时候死死法
Redis 缓存回答上线第一天命中率 8%，白占内存
MQ 削峰第一次大促堆 10 万条，内存爆，GPU 空转
只按 QPS 限流长文档功能上线5% 请求吃掉 68% 算力
无状态扩容流量突增新实例冷 KV，TTFT 4 s
全局多活跨区部署KV 跨区传输，p99 爆炸
失败重试 3 次一次抖动放大 3.6 倍，雪崩
灰度按 5% 用户切三套版本错配指标全绿，质量掉了

第七条最隐蔽：模型灰度了，Prompt 没灰度，评测集又没覆盖这个组合——监控上看不出任何异常，只有用户投诉"最近变笨了"。

5.1 改造顺序：先动哪个

顺序改什么为什么先改它不先改的后果
1限流加 token 维度成本最低，收益立刻可见后面所有优化都在给长请求打工
2缓存对象换成 KV/前缀命中率从 8% 到 85%加多少卡都不够
3重试加预算一次抖动就会暴露故障时放大 3 倍
4扩容改预热池周期最长，要提前排期每次大促都靠人肉扛
5多活改多 cell架构级，动一次管三年晚改要还技术债

066. 失败模式

现象根因怎么发现怎么修
扩容永远慢一步把 GPU 当无状态服务扩容耗时 vs 流量爬坡时间预热池 + 预测式（33 章）
缓存不命中还占内存缓存对象选错命中率 <20%缓存 KV 不缓存响应
削峰削不动算力不可存储MQ 堆积且 GPU 饱和准入控制替代排队（25 章）
长请求饿死短请求单一维度限流p99 与 p50 差距拉大token 维度限流
抖动变雪崩重试放大重试率突增重试预算 + 熔断
灰度后质量下降版本矩阵没维护只有主观反馈三套版本强绑定（36 章）
越重试越崩重试与降级互相激化重试率随错误率同步上升重试预算 + 降级期间禁重试

最后一条是个正反馈环：过载 → 降级 → 更慢 → 超时 → 重试 → 更过载。打破它只有一个办法：让重试本身也有预算，用完了就不再试。

077. 验收：怎么证明这张判定表用对了

检查项通过标准
每个传统组件都有判定13 个模式逐个标注了复用/变形/失效
变形项写了"怎么改"不是只写"要改"
失效项有替代方案例如"MQ 削峰 → 准入控制"
重试有预算有 max_retries + 预算上限 + 可重试错误白名单
限流有 token 维度不只是 QPS
缓存对象正确明确缓存 KV / 前缀，不是完整响应

099. 收口

**传统互联网的每一件工具都还在，但它们的假设变了：

从"无状态、可按请求计费、排队可以缓冲"，

变成"有状态、按 token 计费、排队等于烧钱"。**
