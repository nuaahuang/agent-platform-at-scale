011. 问题：先写 loop 的人，第五周会推翻重来

需求方说："做个能查订单、能退款、能回答政策的助手。"

最自然的做法是打开编辑器写循环：调模型 → 解析工具调用 → 执行 → 回灌 → 再调。一天能跑通 demo。

第五周会撞上四个墙：

撞墙症状
状态没处放用户断线重连，上下文没了
上下文爆炸第 8 步开始 token 超限
工具权限乱一个工具被所有 agent 共用，出了事查不出谁调的
多场景无法复用客服要 5 步、审批要 12 步，写了两套 loop

四堵墙都不是"代码写得不好"，是架构没画。loop 只是执行引擎，它上面要挂状态、上下文、工具、编排四层。

所以这一章不写 loop 的细节，先给全景——五个板块、它们的关系、以及一次请求怎么穿过它们。后面四章逐个展开。

022. Harness 在哪

先定位。一条请求的完整链路：

Harness 是编排层。它自己不做推理，它组织推理：

层回答什么问题不负责什么
网关这个请求能不能进进来之后干什么
Harness进来之后，下一步做什么这一步该怎么措辞
模型这一步输出什么下一步做什么
引擎怎么把这个 token 算出来算出来的东西对不对

第二行和第三行的分工是全书最重要的边界之一：模型管"这一步说什么"，Harness 管"下一步做什么"。

033. 五个板块

板块职责一句话章节
Loop驱动多步决定"还要不要下一步、做什么"本章 §5.1
State记住进度断了能续、错了能回放第 19 章
Context组织输入这一步该给模型看什么第 20 章
Tools执行动作调什么、怎么调、谁有权调第 21 章
Orchestration多 Agent 协作谁交给谁、怎么汇总第 22 章

五个板块不是五个服务，多数系统是一个进程里的五个模块。区分它们是为了划清职责，不是为了拆微服务。

044. 一次请求的完整路径

用户说："我要退第 3 件商品，钱退到哪张卡？"

步板块做什么耗时
1Context组装 system + 历史 + 检索到的退款政策180 ms
2Loop调模型，模型决定"先查订单"600 ms
3Tools调 query_order，带用户身份45 ms
4State记一步：query_order 已执行，结果 X2 ms
5Context把工具结果裁剪后回灌3 ms
6Loop再调模型，模型决定"查退款方式"600 ms
7Tools调 query_refund_method40 ms
8State记一步2 ms
9Loop模型决定输出最终答案600 ms
—合计3 轮，7 个子步骤2.1 s

这个路径说明三件事：

① 时间几乎全花在模型调用上（1.8 s / 2.1 s = 86%）。所以优化 Harness 的性能，重点是减少轮次，不是优化代码。

② 每轮都要重新组装 Context。 第 1、5、9 步都在拼输入，而拼法直接决定 token 数和缓存命中率（第 7 章）。

③ State 的写入很小但很关键。 2 ms 的写，换来的是断线能续——这是最划算的一笔开销。

055. 板块分解

5.1 Loop：七件事

Loop 是执行引擎。它要处理七件事，少了任何一件都跑不到生产：

#事管什么不管会怎样
1计划下一步做什么模型乱调工具、绕圈
2调用怎么执行工具重复执行、参数错
3观察结果怎么回灌上下文爆炸、注入
4状态中间结果存哪重启失忆
5预算花多少无限烧钱
6超时等多久挂死
7恢复断了怎么办重来或重复

第 4、5、6、7 是工程问题，第 1、2、3 是语义问题。demo 通常只做了后三件。

三个最关键的设计点：

计划的约束。 不是让模型自由规划，是给它受限的选择空间。最有效的约束是这一句：

实测能把平均步数从 11 降到 6。

恢复的顺序。 先记意图，再执行——这是正确性的全部：

重启后看到"第 15 步 pending"，就去查 idempotency_key 有没有生效，而不是直接重发。

预算是三维的。 32K token / 20 步 / 300 秒，先到先停，且必须返回进度。

状态机七个状态，其中 WAITING_HUMAN 不能省——多数系统把"转人工"当 final 输出，人工处理完用户追问一句，上下文就断了。

5.2 State：第 19 章

Loop 每一步都要落状态。核心问题是存什么、存哪、能不能重放。

方案存什么能回答的问题
无状态不存什么都不能
快照最新状态"现在做到哪了"
事件溯源全量事件"三个月前那个请求为什么失败"

多数系统停在快照层。事件溯源多花的成本，换来的是可回放、可审计、可归因（第 41 章）。

5.3 Context：第 20 章

每轮都要拼输入。拼法决定三件事：token 成本、缓存命中、模型能不能抓住重点。

第 4 节的路径里，Context 被调用了三次（初始、回灌、最终），每次的内容都不同。这是 Harness 里最容易被写成一坨字符串拼接的地方，也是优化空间最大的地方。

5.4 Tools：第 21 章

工具层不只是"调接口"。它要处理：权限（谁有权调）、幂等（重复调不重复执行）、限流（一分钟几次）、超时与重试、结果裁剪。

第 39 章讲过工具越权的后果——如果工具用服务身份调用，agent 就是个权限放大器。

5.5 Orchestration：第 22 章

单 Agent 走不通的时候才需要它：任务太长、需要并行、需要不同专长。

四种形态（handoff / supervisor / DAG / HITL）差别很大，但共同点是状态在 Agent 之间怎么传——这又回到 §5.2。

065.6 板块之间怎么连：四个接口

五个板块画出来容易，连起来难。连法决定了"改一处会不会动全身"。

四个接口，每个都是一份契约：

接口谁调用谁传什么关键约束
plan(state) -> ActionLoop → 模型组装好的上下文必须是纯函数，不能有副作用
execute(action) -> ResultLoop → Tools动作 + 身份上下文必须幂等
append(event)Loop → State一个事件只追加，不改历史
render(state) -> PromptLoop → Context状态与检索结果输出 token 数可预测

第二行的"必须幂等"和第四行的"可预测"是两个最容易违反的。

工具不幂等的后果第 1 节讲过——重复退款。

render 不可预测的后果更隐蔽：同一个状态，两次渲染出不同长度的 prompt（比如检索结果顺序不固定），缓存命中率就会抖。第 7 章算过，命中率从 85% 掉到 0，成本涨 5 倍。

所以渲染也要确定化：检索结果的排序、字段的顺序、空值的处理，都固定。

四个接口定清楚之后，五个板块就能独立演进——换模型不用改工具层，换工具不用改上下文层。

076. 自研还是用框架

方案覆盖哪些板块缺什么
LangGraphLoop + StateContext 工程、工具权限、多租户
Dify / CozeLoop + 可视化编排深度定制、私有化程度
AutoGen / CrewAIOrchestration生产级状态与恢复
全自研全部工作量大（15–20 人月）

判断标准还是那条：承载业务概念（租户、SLO、钱、权限）的部分必须自研。

框架通常把 Loop 和 Orchestration 做得很好，把 Context 和 Tools 做得很浅——因为前两者通用，后两者和业务强绑定。

所以常见组合是：框架跑 Loop，自研 Context/Tools/State。

087. 演进路径

不要一次建完五个板块。三个阶段：

阶段建什么能支撑典型时长
一 MVPLoop + 内存状态单场景 demo2 周
二 生产+ State 持久化 + Tools 层单场景上线6 周
三 规模化+ Context 工程 + Orchestration多场景、多租户3 个月

第一阶段的状态放内存，是为了快；第二阶段必须换掉，因为一重启就丢。

多数团队的坑是跳过第二阶段直接做第三阶段——多场景铺开了，状态和权限还是 demo 水平，出一次事故就全线回滚。

098. 失败模式

现象根因怎么发现怎么修
断线后从头重来只有 Loop 没有 State看日志重复调用加检查点
第 8 步 token 超限没有 Context 工程看单请求 token 曲线裁剪观察
一个工具出事查不出谁调的没有 Tools 层看调用日志加身份透传
客服和审批写了两套 loop没有 Orchestration 抽象代码重复抽公共 loop
五块都有但改一处动全身板块间没有边界改动影响面定接口

最后一行是架构问题里最贵的：五个板块都在，但互相直接调用，改 Context 会踩到 Tools。边界要靠接口而不是靠自觉。

109. 什么情况下这些结论不成立

结论推翻条件
五个板块都要有单步任务（一问一答调一个工具）时，Loop 就够
状态必须持久化纯查询类 agent（不产生副作用）时，丢了重来代价低
自研 Context 层场景极单一（只有一种 prompt 模板）时，硬编码更快
三阶段演进有明确上线日期时，可以二三阶段合并，但要接受返工

1110. 验收

  1. 能画出五个板块和它们的数据流。
  2. 能说出你的系统里，一次 5 步请求在哪几个点写状态。
  3. 能判断你的框架覆盖了哪几个板块，缺的那几个打算怎么办。
  4. 能说出你现在处在第几阶段，下一个阶段加什么。

1211. 复盘卡

我原来以为 agent 就是一个 while 循环，实际差在循环外面还有四层——状态、上下文、工具、编排，每一层不管都会在第五周变成返工。
