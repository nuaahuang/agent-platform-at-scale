022. dsh 的架构，其实只回答三个问题

把上面的例子放大到整个系统，dsh 只是在回答三个问题：

问题答案对应的东西
发生的事记在哪？一本只能往后写的账本会话日志
模型这次该看到什么？从账本里算出来提示词组装
想加新能力，改哪？加一个插件，不改主干Cordis

三个问题答完，架构就清楚了。剩下的名词都是这三件事的零件。

关键在第二个答案："算出来"。

多数系统把"模型该看到什么"存在内存里（一个 history 数组），边跑边改。dsh 不存这个数组——它每次从账本重新算一遍。

这一个选择改了下面四件事：

如果存 history如果从账本算
进程挂了 history 就没了账本在磁盘，重启接着算
想回放三个月前的请求做不到，history 早被覆盖账本还在，能重放
想 fork 一条分支要深拷贝数组复制账本前缀即可
内存和磁盘两份状态可能不一致只有一份真相

033. 一次请求的流水账

用户说："我要退第 3 件商品。"

dsh 依次做下面这八件事，每一步结束后都会往账本追加至少一条记录，下面是完整顺序：

#谁做做什么写进账本
1循环领到这句话，开一个"轮次"turn/start
2循环问插件：这一步该用哪个模型（快照保存，不写）
3提示词组装拼出"系统规则 + 最近对话 + 工具说明"无（拼出来的）
4循环把拼好的东西发给模型request/header
5模型回："先查订单，参数是 order_123"assistant/message
6工具层执行 query_order，拿到"已签收"tool/call + tool/result
7循环还有工具调用欠着，进下一步step/end，然后回到第 3 步
8循环模型这次回了最终答案，没有工具调用turn/end

一个 5 步的请求，这样的记录大约 47 条，占 47 KB 左右。

注意第 3 步：模型看到的内容不是存着的，是现拼的。拼的原料是账本里的记录（第 4、5、6 步写进去的那些）。

"唯一真源"落到操作层，就是账本是原料、其他都是成品，成品可以随时重做。

3.1 账本真的长这样

上面那张表是抽象说法。真实的记录是这样一行行追加的：

四个字段值得注意：

字段作用
seq严格递增的序号，并发写入时靠它定序
turn / step定位这条记录属于哪一轮哪一步
ts毫秒时间戳，用于算耗时和超时
bytes / tokens这条记录占多大，用于算成本和截断

seq 连续且递增，意味着任何两条记录之间不会插进第三条。这是"日志即真相"能成立的基础——如果顺序会乱，重放出来的历史就是错的。

一次 5 步的请求，seq 大约从 100 走到 147，共 47 条。第 120 行那条 step/end 里的 usage 告诉我们：这一步输入 3,184 token，其中 2,902 命中缓存（91%），输出 96 token，耗时 1,153 ms。

这三个数直接对应成本：命中部分按 ¥0.05/百万算，未命中的 282 token 按 ¥10.24/百万算，输出 96 token 按 ¥6.42/百万算。加起来约 0.0012 元。

日志不只是审计，它就是计费的数据源。 这是"只记一份"的另一个好处。

044. 那些名词，一句话一个

名词一句话为什么需要它
Cordis让"挂插件"这件事成立的框架提供"注册/撤销"的机制
ctx插件之间互相找人的通讯录ctx.llm 就是"谁能聊天"
事件广播：谁想听谁听，发的人不需要知道谁在听加功能不用改发的人
插件树谁依附于谁的层级卸载一个，下面的一起卸
profile一套插件清单web / headless / sdk 就是三份清单
seam一个"岗位说明书"：接口 + 实现 + 使用方换实现不影响使用方
patch按 id 改某个插件配置不改源码就能定制

七个名词里，只有 ctx 和 事件 是真正需要理解的，其余五个都是它们的衍生物。下面这张表说明每个名词分别由谁衍生出来。

  • 有 ctx，才有"换零件不改循环"
  • 有事件，才有"加功能不改主干"
  • seam 是 ctx 的用法规范（接口要单独立出来）
  • profile / patch 是启动时怎么组装这棵树的配置格式
  • Cordis 是上面这些机制的总称

055. 这样设计换来了四件"换掉不改主干"

换什么改哪主干代码
换模型启动配置里换一个适配器插件不动
加工具写一个工具插件注册到 ctx.tools不动
换沙箱换文件系统/进程的 provider不动，Bash/PTY/LSP 一起搬走
加行为（比如"危险操作先确认"）监听 tools/pre-execute 事件不动

第四行最能说明价值。"危险操作先确认"这个需求，在写死的循环里要加 if；在 dsh 里是挂一个监听器——需求变了加监听器，不是改循环。

上面四行都是"换东西"。还有一种更常见的需求是"加东西"，下一节用加一个工具走一遍。

5.1 加一个工具，具体改哪

"加工具"这句话太抽象。具体到文件层面是这样：

步骤做什么代码量
1写一个文件，声明名称、参数 schema、执行函数约 60 行
2在插件里注册到 ctx.tools1 行
3在启动配置里加上这个插件1 行
4重启，模型看到新工具0 行

第 1 步的 60 行里，真正有逻辑的约 20 行，其余是参数声明和错误处理。第 4 步是 0 行——提示词里列哪些工具，是从注册表算出来的，不是手写的清单。

这一点经常被忽略：如果工具清单是手写的，加工具就要同时改注册代码和提示词字符串，两处容易不一致——模型被告知有一个叫 query_order 的工具，实际注册的是 queryOrder，于是永远调不对。

清单从注册表算出来，"不一致"这个 bug 类别就消失了。

066. 它是 ReAct 吗

形态上是。默认的循环实现里，一个类就叫 ReactLoopInbox，干的正是 ReAct 那件事：请求 → 调工具 → 看结果 → 再请求。

但两点要说清：

第一，循环是可替换的。 agent-loop 只是一个默认实现，插件依赖的是 agent 接口。换一个循环不用改其他任何东西。

第二，ReAct 里的"Thought"不在循环里。 论文里的 Thought 是提示词结构（让模型输出"思考：… 行动：…"）；在 dsh 里，思考发生在模型内部，循环拿到的只有结构化的工具调用。

所以准确定位是：默认实现是 ReAct 形态，架构本身是"轮次 + 步骤"的状态机。

077. 代价

不能只讲好处。这套设计有四笔账：

代价表现
概念多要理解 ctx、事件、scope、realm 才能改代码
调试绕一个行为跨 3–5 个插件，看调用栈看不出全貌
启动慢插件初始化 200–500 ms，比单体慢 3–5 倍
需要文档改之前得先查"这个行为归谁"，不能靠读代码猜

它适合要被外部扩展、生命周期以年计的平台。自己团队做一个固定流程的 agent，200 行循环更好维护。

判断标准：你的 harness 会不会被第三方扩展？

088. 我们能借的四条

不做插件架构，也能借这四条：

原则怎么用
只记事实，不记成品存事件，不存拼好的上下文，重启能重算
接口单独立出来模型、工具、沙箱都先定义接口再实现
用事件代替 if加需求时先想"能不能挂个钩子"
配置分层可 dumpbase → 应用 → 用户 patch，能打印出最终配置

第一条最实用：把 messages 数组换成"事件 + 启动时重放"，进程崩溃后能从最后一条 seq 接着算，不用回滚到请求起点。

8.5.1 上下文管理：四道工序

上下文由四道工序依次产出，触发条件和落盘位置各不相同：

工序何时触发做什么数据落在哪

关键在于第三、四道工序都只"遮蔽"，不"删除"。 下面这条记录就是遮蔽的载体。

注意最后一个：人和模型看到的不是同一份历史。 人看 transcript（完整），模型看 surface（压缩后）。这不是 bug，是有意设计——审计要全，推理要省。

8.5.2 缓存命中：三条规则

前缀缓存按 token 前缀匹配，所以命中的前提是"前缀一个 token 都不变"。dsh 用三条规则保证这一点：

规则做法
顺序稳定段落按 order 数值排序（固定开场白 −1000、persona 前缀 0、persona 后缀 10200）
动态内容不进系统提示词日期、目录、平台信息作为 user 角色快照追加，不进 system
工具 schema 集合与顺序稳定用 toolOrder 显式固定，重排会从第一个变化的 token 起失效

第二条最容易被忽略。把"今天是 2026-11-23"写进 system prompt 的做法，代价是日期每天变一次，整个系统提示词前缀每天失效一次。dsh 把它放进 user 角色的运行时快照，system prompt 一个字不变。

第一条的收益可以算：系统提示词约 3,000 token、工具 schema 约 4,000 token，这 7,000 token 稳定，就意味着每轮请求的这 7,000 token 全部命中缓存。按 ¥10.24 vs ¥0.05 的价差，这 7,000 token 的成本从 0.0717 元降到 0.00035 元，差 200 倍。

8.5.3 工具流水线：瀑布 + 守卫

一次工具调用要过五道，顺序固定：

顺序环节能做什么能不能放行被拒的调用
1tools/pre-execute改参数、拒绝、接管能（瀑布式，监听器可改）
2ToolGuard只能收紧不能
3审批问用户不能
4tools/execute实际执行、包装超时—
5tools/post-execute改结果、标记失败—

第 2 道的"只能收紧"是安全边界的关键：前面任何监听器放宽的权限，守卫都能收回来；守卫自己拒绝的，后面谁也放不回来。

这是单调性（monotonic）设计——权限只能沿流水线变小，不能变大。

8.5.4 检索与索引：为什么不用向量

代码检索用的是 grep 和 glob，不是向量索引。这是个刻意的取舍：

维度grep/glob向量索引
精确匹配（函数名、错误串）有常漏
增量成本0（现扫）要建索引、要维护
新鲜度永远最新索引落后于代码
语义模糊查询弱强

代码场景里，开发者给的是精确线索（"找 ReactLoopInbox"），grep 直接命中；向量检索反而会返回"看起来相关"的错误结果。索引的维护成本还随仓库变化线性增长。

所以 dsh 的检索是：glob 找文件、grep 找内容、LSP 找符号、skills 目录按需注入说明。四样都是"用时才算"，没有后台索引。

向量检索在另一种场景才值：业务知识库（售后政策、商品文档），因为那里的查询是自然语言、答案不在字面里。我们的平台两种都要——代码/配置用 grep，售后知识用向量。

8.5.5 子 agent：持久会话 + 任务 DAG

一个子 agent 对应一个完整的持久会话，六项特性如下：

特性实现
身份独立 Session id，持久化
在线数最多一个 activation（同时只能跑一份）
fork用父日志的前缀做种子（从 seq 0 连续的一段）
命名树形路径，根叫 lead，子叫 lead/reviewer
结果结构化输出，提交后关闭输入
空闲可冷恢复（历史全在日志里）

并行的协调不靠调度器，靠共享任务板，三个字段决定它能不能用：

字段作用
revision每次修改 +1，compare-and-set 防并发覆盖
blockedBy依赖边，必须无环
writeScopes路径前缀提示，不是锁

注意最后一行：写作用域只是提示，不是互斥锁。多个 agent 写同一片区域仍可能冲突，靠的是任务设计时切分边界，而不是运行时加锁。这条很反直觉，但省掉了分布式锁的全部复杂度。

汇总时，父 agent 读子 agent 的结果——文本或结构化对象。没有额外的聚合层，聚合就是父 agent 自己的下一步。

8.5.6 六条主线的共同点

六条看起来各不相同，实现上都在做同一件事：把"当前状态"表示成"日志的投影"，然后让每个机制只负责一段投影规则。

  • 上下文是投影（surface）
  • 状态是投影（deriveMessages）
  • 客户端看到的是投影（session-projection）
  • 计费是投影（token-meter 从事件算）

所以加一个新机制，往往是"注册一个投影单元"，不是"改主干"。这是整套架构能长期演进的原因。

109. 失败模式

现象根因怎么发现怎么修
循环里 if 越来越多把变化写进了不变的地方数循环里的分支数抽接口，改由配置决定
重启后行为不一致内存里存了第二份状态重启前后对比只留日志为真源
换模型要改五处没定义接口搜模型名出现次数抽适配器
插件卸了还留副作用注册没返回撤销函数卸载后看指标注册即返回 disposer
配置改了不生效patch 层优先级搞错dump 配置对比按层排查

1110. 验收

  1. 能用代码说清"加一个模型"在写死循环和插件架构下各要改什么。
  2. 能说出"只记事实不记成品"带来的三个好处。
  3. 能判断你的系统该不该做插件化。

1211. 复盘卡

我原来以为 harness 就是一个循环加几个工具，实际差在"循环里该写什么"——写死的部分越少，这个系统活得越久。

复盘卡里那句"写死的部分越少，这个系统活得越久"，落到工程上就是四件可执行的事：日志只追加、接口先定、需求先想钩子、配置能 dump。
