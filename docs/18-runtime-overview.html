011. 问题：第 14 步断了

一个退单请求，Agent 走了 14 步：查订单、查物流、看政策、算金额、校验用户资格、准备退款单……第 15 步准备提交时，进程被重启（滚动发布）。

重启之后，用户的对话还在，但 Agent 忘了自己刚才干了什么。它重新从第 1 步开始：又查了一次订单、又算了一次金额、又准备了一次退款单。

这一次，退款提交了两次。 因为第 15 步的动作在重启前已经发出去，重启后又发了一次。

复盘时发现四个问题：

问题后果
没有持久化中间状态重启即失忆，只能重来
工具调用不幂等重放导致重复退款
没有步数上限某些请求会走 200 步，烧掉 3 块钱
没有整体超时挂住的请求一直占着连接

这一章讲的就是把这四件事补上——它们构成了 agent loop 的七件事。

033. 七件事

#事管什么不管会怎样
1计划下一步做什么模型乱调工具、绕圈
2调用怎么执行工具重复执行、参数错
3观察结果怎么回灌上下文爆炸、注入
4状态中间结果存哪重启失忆
5预算花多少无限烧钱
6超时等多久挂死
7恢复断了怎么办重来或重复

七件事里，第 4、5、6、7 是工程问题，第 1、2、3 是语义问题。多数团队的 demo 只做了后三件，生产化要补前三件。

七件事有三套常见实现方案，选哪个决定了后面的工程量：

方案状态存哪恢复能力适用
无状态函数不存不能恢复，重来demo、单步任务
快照式Redis 存最新状态恢复到最后一步多数生产系统
事件溯源Kafka 存全量事件可重放到任意时刻需要审计、回放

第二行是本章的写法，第三行是第 19 章的内容。差别在"能不能回答三个月前那个请求为什么失败"——快照式不能，事件溯源能。

要求做法
幂等同一 idempotency_key 重复调用只生效一次

066. 观察：结果怎么进上下文

工具返回可能是 100 KB 的 JSON。直接塞进上下文有三个后果：token 爆掉、注入风险、模型抓不住重点。

三件事要做：

动作做法
裁剪只取需要的字段（50 → 5，第 39 章）
结构化用固定模板，不要裸 JSON
截断单条观察上限 2,000 token

OBSERVE_SCHEMA 是配置，不是代码——新增工具只加配置。这一点很重要：观察格式是最容易变的东西（接口改字段），做成配置才能不发版。

截断到 2,000 token 的理由：20 步 × 2,000 = 40K，已经超过 32K 预算。所以实际要靠"只保留最近 5 步的完整观察 + 更早的摘要"来控制。

077. 状态：每步一个检查点

状态分两层：

层存什么存哪频率
会话状态消息历史、当前步、预算余额Redis每步
事件日志每步的输入输出、工具结果Kafka → 对象存储每步

Redis 存的是"最新快照"（约 50 KB），对象存储存的是"完整历史"（约 200 KB/请求）。

为什么要两层：恢复时要快（Redis），审计和回放要全（对象存储）。

TTL 设 1 小时：超过 1 小时的会话，用户基本不会再回来，恢复也没意义。

088. 预算：三维，先到先停

预算不是一个数，是三个：

维度值依据
token32,00020 步 × 1,500 + 初始 2,000
步数20P95 是 20，P99 是 35（超了转人工）
时间300 秒端到端 9 秒是单轮，多步要放宽

任一超限就停，返回"已尽力"，带上当前进度。不要静默停止——用户需要知道为什么没做完。

三个数的关系：20 步 × 平均 1,500 token = 30,000，接近 32K。所以 token 和步数大致同步耗尽。如果某个请求 5 步就烧了 32K，说明它每步观察太长——要查 OBSERVE_SCHEMA。

099. 超时：三层，各管一段

层值超了怎么办
单步（工具调用）30 秒该步失败，进重试或跳过
单轮（一次 LLM 调用）60 秒同上
整体（整个 loop）300 秒终止，返回已完成的进度

三层不是简单的包含关系：单步 30 秒 × 20 步 = 600 秒 > 整体 300 秒。所以整体超时会先触发。

这意味着长尾请求不是被单步超时杀死的，是被整体预算杀死的。所以整体超时给的返回值要包含"做到哪一步了"，让用户知道进度。

1010. 恢复：三种断法，三种处理

断法状态恢复方式
进程重启Redis 有快照从最后一步继续
工具超时该步失败重试读操作 / 查询确认写操作
用户断线会话还在重连后继续推流

第一种依赖检查点，第二种依赖幂等，第三种依赖流式会话的续传（第 23 章）。

最危险的是"状态存了但工具执行了两次"。前面那个退款事故就是这个：Redis 存的是第 14 步完成后的状态，但第 15 步的退款请求已经发出去了，重启后又发一次。

1111. 状态机

七个状态：

状态含义出口
INIT请求已创建PLANNING
PLANNING模型决定下一步ACTING / ASKING_USER / DONE
ACTING工具执行中OBSERVING / RECOVERING
OBSERVING处理工具结果PLANNING
ASKING_USER需要用户补充信息PLANNING（用户回复后）
RECOVERING单步失败，重试或降级ACTING / FAILED
WAITING_HUMAN转人工DONE（人工处理后）

WAITING_HUMAN 这个状态必须有。多数系统把"转人工"当成一种 final 输出，结果人工处理完之后无法回到 loop——用户追问一句，整个上下文就断了。

1313. 失败模式

现象根因怎么发现怎么修
重启后重复退款先执行后记账对账时发现两笔改成先记意图
请求走 200 步没有步数上限看步数分布加预算 + 步数上限
断开后从第 1 步重来没存检查点看日志重复调用每步 checkpoint
上下文超长报错观察没裁剪看单请求 token裁剪到 2,000/步
转人工后对话断了转人工当成终态用户追问无响应加 WAITING_HUMAN 状态
某工具一天被调 10 万次模型绕圈工具调用分布加"必须引用上一步观察"约束

第一行是最贵的：一次重复退款就是真金白银，而且很难在测试环境复现（要正好在第 15 步重启）。

1413.5 备选方案：用工作流引擎代替自研 loop

前面这套状态机可以用 Temporal、Argo Workflows 这类引擎实现，省掉检查点和恢复的代码。

方案优点代价
自研 loop轻、可控、延迟低要自己写检查点与恢复
工作流引擎恢复、重试、可视化都有多一跳 RPC（5–10 ms），状态存引擎
函数编排（Step Functions）托管，按次计费与推理服务的延迟不匹配

第二个方案的延迟值得算：loop 里每步都要和引擎通信，20 步 × 8 ms = 160 ms。相比 300 秒的整体预算可以忽略，但相比单轮的 9 秒就有感了。

小团队建议直接用引擎（Temporal），大团队自研——因为 loop 里的很多优化（比如批量观察、并行工具调用）引擎不支持。

1514. 什么情况下这些结论不成立

结论推翻条件
每步都要检查点单步 agent（只调一次工具）时，存一次就够
步数上限 20任务本身是长周期（如批量处理 100 个订单）时，要单独设计
工具超时 30 秒有慢工具（如人工审核接口 5 分钟）时，要分级
状态存 Redis请求量小、可接受重来时，存数据库就够

1615. 验收

  1. 能画出你的状态机，说出每个状态的出口。
  2. 能指出你的系统在哪一步做检查点，重启后从哪恢复。
  3. 能说出预算的三个维度，以及哪个先触发。
  4. 能解释"先记意图后执行"为什么能防重复。

1716. 复盘卡

我原来以为 agent loop 就是个 while 循环，实际差在它不是循环——是状态机，因为有预算、有超时、要能断点续跑。
