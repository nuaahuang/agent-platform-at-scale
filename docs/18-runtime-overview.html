011. 问题：不要设想一个 demo，去读一个真系统

教科书式的拆法是"循环、状态、上下文、工具、编排"五块。这个拆法没错，但是推演出来的——真实的系统未必这么长。

DeepSeek Harness（下称 dsh）是开源的，TypeScript 写的，架构文档齐全。用它当样板，能看清一个跑在生产里的 harness 到底怎么分层，以及哪些设计是被真实约束逼出来的。

这个仓库有 2.6 万个文件、6 个核心包、5 个随附 profile。这一章只讲全景：它的第一原则、它的组成、一个轮次怎么走。后面四章逐个拆它的核心子系统。

022. 第一原则：一切皆插件

dsh 建在 Cordis 上。Cordis 提供三样东西：

机制含义
共享上下文（ctx）插件把服务挂到 ctx.xxx 上，别人按名字取用
类型化事件插件发事件，别的插件监听，不需要互相 import
可逆副作用插件的每一次注册都是副作用，卸载时自动撤销

关键在第三行。没有特权内核——模型适配器、工具注册表、会话日志，甚至 agent loop 本身，全都是插件。所以每一个都能从配置里换掉。

这和"写一个 while 循环"的根本差别是：循环里每加一个能力（比如"支持新模型"），代码就要改一次，第三个模型时循环里已经有 3 个 if；而插件架构里，加能力是"旁边再挂一个插件"，循环一行不用动。

代价也明显：概念多、调试难、启动慢。后面 §9 会算这笔账。

033. 组合：profile、bundle、patch

插件树不是硬编码的，是拼出来的。三层概念、四种叠加来源：

层是什么例子
profile一套具名组装web、headless、sdk、acp
bundle（组合包）配置项 + 挂载代码的发行格式dsh-base、dsh-web-app
patch按 id 定位条目、替换其 config 或插入新条目cordis.patch.yml

叠加顺序是固定的：profile 里的 bundle（有序）→ 该 profile 的 cordis.patch.yml → home patch → --patch overlay。后一层覆盖前一层。

dsh-base 是 web/headless/sdk/acp 四个 profile 共享的第一层，装的是模型适配器、工具、持久化、沙箱与审批策略、设置、凭据、遥测。dsh-web-app 在上面加浏览器应用，dsh-headless 加一次性运行器。

044. 六个核心包

不管挂多少插件，主干是这六个：

包职责ctx 键
core/session仅追加的会话事件日志与内存存储，唯一真源ctx.sessions
core/system-prompt提示词片段与工具 schema 的组装ctx.systemPrompt
core/tools作用域化的工具注册表 + 带把关的执行流水线ctx.tools
core/agentAgent 接口、活跃注册表、agent/* 事件ctx.agents
core/agent-loop实现该接口的默认驱动器ctx.agentLoop
core/scope按 agent 划分作用域的注册原语（纯库）无

两个设计点值得注意。

agent 和 agent-loop 是分开的。 前者是接口，后者是默认实现。扩展插件只依赖 agent（要发起 agent 时也是），绝不直接依赖 agent-loop。所以循环是可替换的——这是插件架构落到具体模块上的体现。

scope 是纯库，没有 ctx 键。 它在模块图里位于 session 和 system-prompt 之下，正是为了让这两个消费它而不形成循环依赖。依赖方向是被精心安排过的。

055. 三个事件域

事件不都在一个池子里。dsh 分三个域，判断标准很实用：

域例子什么时候用存在哪
会话事件turn/start、step/end、tool/result重载后还要存在的事实持久日志
Agent 事件agent/pre-step、agent/request观察或拦截进行中的工作内存
能力事件fs/、tools/、telemetry/*给某个 seam 挂策略或适配器由 seam 定义

一条判据：这个事实在重载后还必须存在吗？ 是，就进会话日志；不是，就走 agent 事件。

这条判据直接决定了恢复能力。会话日志是"模型可见即已记录"——每个模型请求都必须能从日志重建。所以断线、重启、fork 全都从日志派生，不需要额外的状态机。

066. 一个轮次里发生了什么

先定两个词，多数人混：

词定义
步骤（step）一次模型请求 + 它调用的工具
轮次（turn）零或多个步骤；在领取首条输入前打开，在不再欠任何工作时关闭

三个细节体现了真实系统的复杂度：

① agent/pre-step 是"瀑布式"事件。 监听器必须调 next() 才往下传——所以它能改、能拒、能完全接管这一步。这是"在不改循环的前提下改变行为"的关键机制。

② 取消的语义是精确的。 在任一异步阶段取消，系统候选与已接纳的用户消息都不提交。所以"用户点了停止"不会留下半条脏数据。

③ 每次尝试都刷新运行时事实并派生历史。 重试会复用组装结果，但历史重新从日志派生——所以日志永远是唯一真源，内存里没有第二份真相。

6.1 一次轮次的开销，可以用事件数估

这套架构的每个动作都会落事件。数一下就知道成本在哪：

事件每步数量5 步合计
step/start / step/end210
request/header15
user/message15
assistant/message15
tool/call + tool/result2×工具数约 20
turn/start / turn/end各 12

一个 5 步、每步 2 次工具调用的轮次，约产生 47 个持久事件。按每事件平均 1 KB 算，单轮日志约 47 KB。

对比一下：完整上下文（含 8K token 的观察）是 200 KB 量级。所以日志比上下文小 4 倍——这是"事件溯源"能落地的关键，它存的是增量，不是全量快照。

如果改成每步存全量快照，5 步就是 5 × 200 KB = 1 MB，膨胀 20 倍。这也是为什么 dsh 选择"只追加事件 + 从日志派生"，而不是存快照。

077. 它是 ReAct 吗

形态上是。默认驱动器的 inbox 类叫 ReactLoopInbox，干的正是 ReAct 那件事：请求 → 调工具 → 看结果 → 再请求。

但有三点要说清：

说法准确性
"dsh 是 ReAct"形态上是，默认 driver 就是 ReAct 循环
"dsh 硬编码了 ReAct"不对，loop 是可替换插件（ctx.agentLoop）
"ReAct 的 Thought 是一个独立阶段"不对，思考在模型内部（reasoning token），循环只看到"请求"和"工具调用"

第三行值得展开。ReAct 论文里的 Thought 是提示词结构，让模型输出"思考：…… 行动：……"。而在 dsh 里，思考发生在模型内部，循环拿到的只有结构化的 tool call。所以同一套循环既能跑 ReAct 式的提示，也能跑纯 function calling——差别在提示词，不在循环。

一句话：形态是 ReAct，架构是可替换的 turn/step 状态机。

088. 能力 seam：换一个 provider 就换了整个产品

seam 是一组三角：

角色做什么
Service Definition声明接口
Service Provider实现它
Consumer用它（通常是面向模型的工具）

一个包可以兼任多个角色，但单一角色本身不是 seam——加一项能力要把三者一起设计。

seam 的威力在文件系统那个例子里：文件系统与进程提供方共享同一个"执行世界"，所以把它们指向远程沙箱，Bash、PTY、LSP 会一起搬过去，不需要为沙箱做专门的 fork。

换一个 provider 的连锁效应，就是从这个共用执行世界来的。

099. 这套架构的代价

不能只讲好处。插件化有四笔账：

代价表现
学习曲线Cordis 的服务、事件、realm、scope 四组概念，比 while 循环多约 10 倍的概念量
调试难一个行为要跨 3–5 个插件才看得全，调用栈不直观
性能每次注册要走事件分发，插件初始化约 200–500 ms，冷启动比单体慢 3–5 倍
认知负担"改这里会不会影响那里"要靠架构文档，不能靠读代码

所以它适合要长期演进、要给别人扩展的平台。如果只是给自己团队做一个固定流程的 agent，这套架构是负债——一个 200 行的循环更好维护。

判断标准：你的 harness 会不会被第三方扩展？ 会，插件化值得；不会，别学。

1010. 对我们的启示：四条能借的原则

即使不做插件架构，dsh 有四个设计原则可以直接借：

原则怎么用
单一真源会话日志是唯一真相，内存里的状态都是投影，可随时重建
事件分区用"重载后是否还需要"判断该不该持久化
seam 化模型、工具、沙箱都定义接口，实现可替换
配置分层base → 应用 → 用户 patch，三层覆盖，能 dump

第二条最实用：有的系统把"这一步用了多少 token"也持久化了，导致日志膨胀；按这条判据它应该走内存事件。

1111. 失败模式

现象根因怎么发现怎么修
加了功能后循环越来越乱直接改 loop，没走事件看 loop 文件的 if 分支数改成 waterfall 事件
重启后行为不一致内存里存了第二份状态重启前后对比只保留日志为真源
换模型要改五处没做 seam搜模型名字出现次数抽适配器接口
插件卸载后残留行为注册没做可逆卸载后看指标所有注册返回 disposer
配置改了不生效patch 层优先级搞错dump-config 对比按层序排查

第一条最常见：一开始循环很干净，三个月后里面塞了 20 个 if。dsh 的解法是把这些 if 变成事件监听器——加功能不改循环，挂插件。

1211.5 一个真实的数字：dsh 仓库的规模

如果要照着做一个，先知道量级：

项数值
仓库文件26,160
TypeScript 为主是
核心包6 个
随附 profile5 个（web/headless/sdk/sdk-minimal/acp）
架构文档179 行，覆盖从启动到扩展点
桌面应用体积210 MB（asar 包，含渲染进程）

6 个核心包对应的代码量，官方文档没给，但从职责推：session 最重（日志、迁移、投影），tools 次之（注册表、执行流水线、把关），agent-loop 最轻（driver 逻辑）。

这也解释了为什么"照着写一个"很难：不是代码量的问题，是每个包都要处理迁移——session 有 v0/v1 到 vN 的格式迁移，配置有 patch 层序，事件有版本兼容。这些都不产生功能，但少了就没法演进。

1312. 什么情况下这些结论不成立

结论推翻条件
一切皆插件单团队、单产品、不做扩展时，直接写更省
日志是唯一真源请求量大到日志写不动时，要分级（热状态存 Redis）
loop 可替换只有一个模型适配器时，抽象是浪费

1413. 验收

  1. 能说出 profile、bundle、patch 三者的关系，以及叠加顺序。
  2. 能说出六个核心包各自管什么，agent 和 agent-loop 为什么分开。
  3. 能用"重载后是否还需要"判断一个事实该进哪个事件域。
  4. 能解释"形态是 ReAct，架构不是硬编码 ReAct"。

1514. 复盘卡

我原来以为 harness 就是一个循环加上几个工具，实际差在循环外面还有一层——事件、seam、配置分层，这些东西不产生功能，但决定了这个系统能不能被别人扩展。
