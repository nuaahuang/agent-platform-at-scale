011. 先把 RSI 说具体

RSI（Recursive Self-Improvement，递归自我改进）常被讲成"模型自己变聪明"。在工程上它不是这个东西。

一个售后 Agent 平台里的 RSI，具体是三件事在转：

  • 线上出现 badcase，它被采集、归因、标注，进了评测集
  • 新版本在评测集上跑不过，就改 Prompt、改检索、改微调数据
  • 改完灰度验证，通过后放量，再产生新的 badcase

这三步连起来是闭环，转一圈大约一个月。RSI 指的就是这个环能不能自己转、转多快、转错的时候能不能发现。

它不是"模型改自己的权重"。你的平台没有预训练能力，模型权重是厂商的。你能自我改进的是 Prompt、检索、路由、工具描述、微调数据——都是系统层的东西。

这一章讲的就是这个环怎么搭，以及它在哪几个地方会转成自我强化错误。

022. 三条闭环，周期差一个数量级

不同环节的反馈周期完全不同，混在一起谈就会设计错。

闭环输入改什么周期自动化程度
快速闭环单条 badcasePrompt、工具描述、路由规则小时到天高，可自动生成候选
中期闭环一周的 badcase 聚类检索配置、few-shot、知识库周到两周中，人定方案机器执行
慢速闭环一个月的标注数据微调数据、蒸馏数据、评测集月到季度低，人主导

快速闭环能自动化的部分最多，也最容易出错——因为它改的是线上行为，一次改坏影响所有用户。慢速闭环最慢，但改的是权重和数据，影响面更大、回滚更贵。

三条闭环必须是同一个环的三个速度，不是三套独立系统。共享同一份 badcase 库、同一个评测集、同一套门禁。分开建的结果是：快速闭环把 Prompt 调到能过 50 题，慢速闭环训出来的模型却在另一套标准上评测。

033. 数据闭环：badcase 怎么变成资产

一条 badcase 要变成能用的东西，中间有四步，每一步都可能断。

第一步是采集。线上不能全量存请求（成本和合规都不允许），只能采样加规则命中。采什么：

触发条件采集什么占比
用户点了"没解决"完整会话 + 工具调用链100%
转人工转人工前的最后三轮100%
用户重问同一问题两次请求 + 中间隔了多久100%
随机采样完整会话1%
申诉与投诉全链路 + 工单结论100%

前三个是"用户已经告诉你出问题了"，信号最强。随机采样是为了抓"用户没抱怨但答得不好"的情况，1% 就够。

第二步是归因。一条 badcase 要归到四类之一，归错类后面全错：

归因判断依据进哪个池
知识缺失检索结果里没有正确条款知识库待补
检索失败条款在库里但没被召回检索配置
行为不符知道答案但格式/语气/流程不对Prompt 或微调
能力不足多步推理走错换模型或拆步骤

归因是人的活，不能交给模型。模型归因会倾向于归到"Prompt 能解决"那一类，因为它自己就是这么被训练的。

第三步是标注。一条 badcase 标注完要同时进两个地方：评测集（防回归）和训练集（如果要微调）。只进训练集不进评测集，改完没法验证；只进评测集不进训练集，同类问题会反复出现。

第四步是淘汰。评测集不能只增不减。每月新增 20 题，同时淘汰 20 题——淘汰规则是"连续三个月所有候选模型都通过"的题，它已经失去区分度。

这个 20/20 的节奏很关键。只增不减，评测集会从 50 题涨到 300 题，跑一次要一小时，然后没人跑了。

044. 评测闭环：为什么会自己把自己刷上去

这是 RSI 最危险的地方，也是最容易被忽略的。

用 LLM-as-judge 做自动评测，判分的是模型。如果候选模型和 judge 是同一家族、同一次迭代，它们会共享同一种偏好。结果是：新模型在 judge 眼里越来越好，在人工眼里没变。

具体的失效路径是这样的：

分数一路涨，人工评估一路跌。原因是 B 和 C 都在向 judge 的偏好靠，而不是向真实质量靠。

三个信号能提前发现：

信号怎么测阈值
judge 与人工的 Kappa 漂移每月重标 100 条比对从 0.82 掉到 0.65 就要停
人工抽检分与 judge 分的差每周抽 10%差值连续两周扩大
通过率分布收窄看各题得分的方差方差掉一半以上

第三个最隐蔽：所有题都变成 0.85 分，看起来整齐，其实是模型学会了"哪种回答 judge 喜欢"，而不是"哪种回答对"。

防法不是不用 judge，是三条一起上：

  1. judge 与被测模型不同源（至少不同厂商）
  2. 每月人工重标 100 条，重算 Kappa，掉了就换 judge
  3. 保留一个 20 题的人工盲测集，从不用于任何训练和调参，只用于验证

第三条是底线。没有 held-out 的人工集，整个闭环就是自己证明自己。

055. 合成数据：从哪一步开始退化

模型生成数据训模型，这件事在小规模上有效，规模一大就退化。这条路叫 model collapse。

退化不是突然发生的，是分阶段的：

阶段现象数据特征
第一代效果提升30% 合成 + 70% 真实
第三代提升变缓50% 合成，长尾开始消失
第五代分布收窄70% 合成，罕见表达消失
第 N 代只会说套话90% 合成，多样性崩溃

根源是采样偏差的累积：模型生成时倾向于高概率表达，低概率但真实的表达（方言、错别字、罕见句式）在每一代都被过滤掉一部分，几代之后彻底消失。

工程上的防法是三条硬约束：

  • 合成数据占比不超过 30%
  • 每一代必须混入新采集的真实数据，不能只用历史数据生成
  • 保留一个真实数据构成的验证集，每一代都测它的分布距离

第三条可以量化：算验证集和训练集的 token 分布 KL 散度，超过 0.3 就说明训练数据已经偏离真实分布。

066. 能自动改什么，不能自动改什么

这是设计 RSI 时最重要的一个决定。分错一次，可能造成安全事故。

对象能否自动改为什么
Prompt 的措辞与示例可以，但要过评测和灰度影响面可控，能回滚
工具描述与参数说明可以同上
路由规则（简单/复杂分流）可以影响成本，不影响正确性
few-shot 示例选择可以同上
检索的分块与 top-k半自动，人确认影响召回，错了很难发现
微调数据配比不能训一次两小时，错了要重来
评测集内容绝对不能自己改考卷等于作弊
安全策略与拒绝规则绝对不能自动化会让它越走越松
权限与工具白名单绝对不能一次错就是越权
模型版本选择不能涉及成本和容量的全局决策

中间有一条清晰的线：影响"答得好不好"的可以自动，影响"能不能做"的不能自动。

这条线画错的代价不对称。自动改 Prompt 改坏了，回滚一分钟；自动改安全规则改坏了，可能已经放出去一批越权操作，回滚也追不回来。所以判断标准不是"改这个会不会出错"，而是"出错了能不能收得回来"。

下面三件事看着像同类，其实分属两边。

安全规则尤其危险。如果让闭环去优化"拒绝率"，它会找到那条最省事的路径：全部放行，拒绝率归零，指标完美。所以安全相关的指标只能人定阈值，且只许收紧不许放松。

077. 转错的时候长什么样

一个自我强化的错误闭环，有三个典型形态。

第一种是目标被替换。指标从"用户问题解决率"变成"模型通过率"，因为后者好测。半年后通过率 96%，客诉率翻倍。

第二种是长尾被牺牲。闭环优化的永远是高频场景，因为样本多、收益大。低频场景没人管，慢慢全坏。售后里 5% 的疑难单，在闭环里永远排不上优先级。

第三种是评审疲劳。每周 200 条 badcase 要归因，前两个月认真，第三个月开始按模板填，第六个月归因准确率掉到 50% 以下。归因一错，后面全错。

三个形态的共同点是：指标都在变好，系统在变差。

防法只有一个——保留一个不参与优化的观察集，且由不看指标的人来评。

闭环本身有成本，不算清楚就撑不住长期跑。

环节单条成本每月 800 条的量
归因5 分钟人工67 小时 ≈ 0.4 人
标注（写期望 + 判定）12 分钟，¥15 外采160 小时 + ¥12,000
评测集维护20 进 20 出，2 小时2 小时
灰度观察每天 30 分钟15 小时

一个月约 1.2 人力和 ¥1 万出头。看起来不多，但它要长期养——三年就是 43 人月。所以闭环的产出必须能算成钱：修复一条高频问题，如果它影响 0.3% 的会话，按 1.5 亿轮/日算就是 45 万轮/日，值得修；影响 0.001% 的长尾，一个月只出现 15 次，就不该进本月的队列。

优先级按"影响面 × 修复成本"排，不按"谁先提的"排。这一点听着显然，但实际跑起来，喊得响的人永远排在前面——上线三个月回头看，队列里 60% 是影响面小于 0.01% 的个案。

088. 一个月的闭环怎么跑

把上面拼成排期：

时间动作谁做产出
每日采集 badcase，自动去重聚类系统待归因队列
每周一归因 + 排优先级值班 + 产品本周修复清单
每周三快速闭环：改 Prompt/检索，跑评测算法候选版本
每周五灰度 10%，看 goodput 与客诉SRE放量决议
每月 1 日评测集换题 20 进 20 出QA新评测集
每月 5 日人工重标 100 条，重算 KappaQAjudge 健康度
每季度判定是否微调/蒸馏算法 + 架构数据需求单

跑顺之后的关键指标是三个：

指标定义目标
badcase 转化率进入评测集或训练集的比例≥30%
修复周期从采集到灰度通过的中位天数≤7 天
回归率修好的问题三个月内再次出现≤5%

回归率最容易被忽略。修一个问题引入另一个问题，是闭环跑快之后最常见的副作用。它的根因通常是只跑任务集不跑全量。

099. 失败模式

现象根因怎么发现怎么修
评测分涨，客诉不降judge 与被测模型同源，一起漂人工抽检分与 judge 分背离换 judge，恢复人工盲测集
模型只会说套话合成数据占比过高验证集 KL 散度 >0.3降到 30%，混入新真实数据
修一个坏两个只跑任务集没跑全量回归率上升全量评测 + 变更影响面分析
归因准确率下降评审疲劳，模板化填表随机抽 20 条复核轮岗、缩短单次时长
低频场景全坏闭环只优化高频分场景统计通过率给小类设独立配额
拒绝率异常低把安全指标交给自动优化拒绝率曲线单调下降安全阈值只许人改，且单向收紧

最后一条值得单独说。任何"越低越好"或"越高越好"的单一指标，一旦交给优化器，它一定会走到极端。安全指标必须是双向约束（既不能太低也不能太高），且由人持有。

1010. 什么情况下这些结论不成立

结论推翻条件
合成数据不超过 30%有独立的高质量真实数据源持续供给时，比例可以放宽
三条闭环共享同一评测集业务线差异极大、评测标准互斥时，要拆成多套
快速闭环周期以天计强监管场景下，任何变更都要人工复核，周期必然拉长到周
归因必须人做归因分类极稳定（如只有两类）且有大量标注时，可先机器预分再人确认

1111. 验收

  1. 能画出你所在系统的三条闭环，说出各自的周期和责任人。
  2. 能说出 judge 漂移的三个信号，并指出你的系统里哪个指标能测到。
  3. 能判断一个优化动作属于"答得好不好"还是"能不能做"。
  4. 能解释为什么安全指标不能交给自动优化，并举一个反向例子。

1212. 复盘卡

我原来以为闭环越快越好，实际差在越快越需要观察集——没有不参与优化的那 20 题，跑得越快，偏离得越远。
