011. 问题：最贵的那个反而最便宜

售后 Agent 上线前，团队把四个候选都跑了一遍：

模型激活参数推理成本50 题通过率结论
8B 稠密8B0.078 分/轮62%❌ 工具调用经常错参
30B 稠密30B0.294 分/轮74%❌ 多步任务掉链子
70B 稠密70B0.686 分/轮78%❌ 贵且不够好
200B MoE（30B 激活）30B0.294 分/轮91%✅

最反直觉的一行是最后一行：200B 的总参数是 70B 的 2.9 倍，但成本只有它的 43%。

因为推理成本由激活参数决定，不由总参数决定。

这一条是本章的前提：能力看总参数，算力成本看激活参数。

但带宽成本要看"专家并集"——§3.0.3 会把它拆开讲。

033. 为什么是 200B MoE / 30B 激活

3.0 四个词先分清：稠密、稀疏、总参数、激活参数

它们不是同一个维度上的四种东西，而是两组正交的概念：

组概念回答什么
结构稠密（dense） / 稀疏（sparse, MoE）算一个 token 时，是否用到全部参数
数量总参数（total） / 激活参数（active）权重一共多大 / 单 token 实际用多少

两者的关系是一句话：

所以"稠密"是"激活等于总量"的特例，不是另一种参数。

我们的 200B MoE：总参数 200B，激活 30B，稀疏度 85%。

3.0.1 能力为什么看总参数

这一条我一开始写成了定律，后来改成"经验规律"。

参数越多、知识类任务越好，这个趋势在稠密模型上拟合得很准——缩放定律（loss ∝ N^(−α)）就是这么来的。但把它直接搬到 MoE 上会出问题：同样是 30B 激活，200B 的 MoE 在知识问答上能领先十几分，换到多步推理和数学，差距缩到两三分。

为什么会有这个差异，我没有证据解释，只能说实测如此。我的猜测是专家结构更擅长"记住"，而推理链要求激活路径本身连贯，被路由打断就会掉——但这只是猜测，没验证过。

所以 91% 和 74% 这两个数，是 50 道题跑出来的，不是从"参数大"推出来的。如果换一套更偏推理的题，差距大概率会缩小 5 个点以上。这一点我一直想补测，还没做。

3.0.2 为什么成本看激活参数

算力这一侧是严格的：

这就是"200B 比 70B 便宜"的全部原因：算力只认激活，不认总量。

但带宽这一侧有个坑，必须讲清。

3.0.3 带宽侧：专家并集会随 batch 放大

decode 每步要把权重读一遍。稠密模型读全部；MoE 只读被路由到的专家。

问题在于：一个 batch 里有 B 个 token，它们激活的专家可能不同，要读的是并集：

按 E=64、k=8 算：

batch并集专家数占全集含义
1812.5%只读 1/8 权重，很省
84266%省一半
165688%基本读全了
6464100%和稠密模型一样读全量

结论要修正一句：

成本看激活——在算力受限时严格成立；在带宽受限时，要看"有效激活"（专家并集）。

对实践的指导：

场景瓶颈MoE 收益
Prefill（算力受限）FLOPs完全按激活算，收益最大
Decode 小 batch带宽收益大（只读 1/8）
Decode 大 batch（≥32）带宽收益缩小（读全量，但摊到更多 token）

单 token 的带宽成本 = 并集字节 ÷ B，所以 batch 越大越便宜——这也是为什么吞吐要靠大 batch，而不是靠堆卡。

3.1 一条经验规律

把这两条画在一起，MoE 的价值就出来了：

方案总参数激活相对算力能力（通过率）
30B 稠密30B30B1.0×74%
70B 稠密70B70B2.33×78%
200B MoE200B30B1.0×91%

同样算力下，MoE 用 6.7 倍的参数换来了 17 个点的通过率。

3.2 MoE 的代价必须说清

代价数值影响
显存权重 200 GB（FP8），TP8 每卡 25 GB单卡装不下，必须 8 卡起
通信专家并行 all-to-all跨机走 IB 50 GB/s，是瓶颈（第 9 章）
负载不均热门专家排队需要 EPLB 均衡（第 10A 章）
显存换 KV640 GB 里 200 GB 给权重，KV 只剩 400 GB并发上限被压缩

推翻条件：如果目标硬件只有 40 GB 显存（如部分国产卡），200 GB 权重装不进 8 卡，MoE 方案直接不成立——这时只能退到 30B 稠密或更激进的量化。

044. 评测集：50 道题怎么出

4.1 分布必须等于生产分布

评测集最容易犯的错不是"题太少"，而是题和生产不像。

类型数量考什么判分方式
单轮意图识别10分类准不准精确匹配
多步工具调用15参数对不对、步数对不对调用序列比对
长上下文检索832K 里的事实召回关键字段匹配
拒答与安全7该拒的拒、不该拒的不拒规则 + 人工
结构化输出10JSON 合法率schema 校验

五类加起来 50 道。权重不是平均的——多步工具调用占 30%，因为它是售后 Agent 的主路径。

4.2 题目从哪来

来源占比说明
生产日志采样60%脱敏后取真实分布
人工构造25%覆盖长尾与边界
对抗样本15%提示注入、错别字、方言

对抗样本是唯一能提前发现安全事故的类别，不要省。

4.3 判分：三种手段，按可靠性排序

手段适用可靠性
规则/精确匹配分类、JSON、字段最高（无歧义）
调用序列比对工具调用高（可精确到参数）
LLM-as-judge开放式回答中（需校准）

用 judge 有前提：与人工标注的一致率 Kappa ≥0.8 才能用，否则就是自欺欺人。

055. 通过标准：不是"准确率 90%"

绝对阈值没有意义——模型会升级，题目会变难。正确做法是对标现网基线：

指标现网基线通过线一票否决
总通过率91%≥89%（−2 pt）<85%
工具调用参数正确率94%≥92%<88%
安全拒答率97%≥95%<90%
JSON 合法率99.5%≥99%<97%
TTFT p95610 ms≤800 ms>1,000 ms

三条规则：

  1. 总分允许 −2 pt，因为新版本常在边缘题上波动；
  2. 任何单项跌破一票否决线，整体不通过——85% 总分里工具调用 0 分也是废的；
  3. 安全项只许升不许降，没有"−2 pt"的余地。

066. 三个陷阱

陷阱表现防法
过拟合评测集每次调 Prompt 都涨分，上线不涨留出 20% 从不参与调优的"盲测集"，每月换题
Judge 偏见偏爱长回答、偏爱第一个选项交换 A/B 顺序、双 judge 交叉
分布漂移评测集是三个月前的，生产已经变了每月按生产日志重采样

第一条最隐蔽：团队反复在 50 题上调 Prompt，分数从 78% 刷到 93%，上线后真实通过率只有 79%——刷的是题，不是能力。

6.1 多久跑一次

触发跑什么耗时
模型版本上线全量 50 题 + 盲测 20 题25 s
Prompt 变更全量 50 题20 s
工具 schema 变更工具类 15 题8 s
每日巡检盲测 20 题10 s
每月按生产日志重采样换题半天

每次变更都跑，但只在"晋级"时跑盲测集——盲测集见得多就失效了。

099. 失败模式

现象根因怎么发现怎么修
评测 93%，上线 79%刷题过拟合盲测集分数低换题 + 盲测
总分 89% 但工具调用 0 分平均掩盖单类分组报告一票否决

Judge 分数虚高长度偏好A/B 交换后不一致双 judge
换模型后成本翻倍只看通过率不看 token统计 output_tokens加成本维度

1010. 验收

检查项通过标准
题量与覆盖≥50 题，5 类齐全，工具调用占比 ≥25%
分布一致与生产分布 KL 散度 <0.1
盲测集存在且从不参与调优，20 题以上
Judge 校准与人工 Kappa ≥0.8
一票否决安全/JSON/延迟三项独立判定
分组报告每类单独出分，不只有总分
可复现固定 temperature=0、固定评测集版本

1111. 备选方案

方案何时选代价
全用外部 API日调用 <10 万成本 12×，数据出境
只用 8B + 规则任务高度确定复杂售后走不通
蒸馏 200B → 30B已有 6 个月以上真实轨迹需要 3–6 个月，效果天花板低于教师
微调 30B领域非常窄泛化差，版本管理复杂（第 5 章）

顺序建议：先用 MoE 大模型跑通业务，收集 6 个月真实轨迹，再考虑蒸馏小模型降本。

1212. 收口

**选型不是选最强，是选"在成本与延迟约束下，能力刚好够用"的那个。

MoE 之所以成为默认答案，是因为它把"更大"和"更便宜"从对立变成了同向。**
