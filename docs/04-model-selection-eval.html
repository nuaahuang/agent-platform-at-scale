011. 问题：最贵的那个反而最便宜

售后 Agent 上线前，团队把四个候选都跑了一遍：

模型激活参数推理成本50 题通过率结论
8B 稠密8B0.078 分/轮62%❌ 工具调用经常错参
30B 稠密30B0.294 分/轮74%❌ 多步任务掉链子
70B 稠密70B0.686 分/轮78%❌ 贵且不够好
200B MoE（30B 激活）30B0.294 分/轮91%✅

最反直觉的一行是最后一行：200B 的总参数是 70B 的 2.9 倍，但成本只有它的 43%。

因为推理成本由激活参数决定，不由总参数决定。

这一条是本章的前提：能力看总参数，算力成本看激活参数。

但带宽成本要看"专家并集"——§3.0.3 会把它拆开讲。

033. 为什么是 200B MoE / 30B 激活

3.0 四个词先分清：稠密、稀疏、总参数、激活参数

它们不是同一个维度上的四种东西，而是两组正交的概念：

组概念回答什么
结构稠密（dense） / 稀疏（sparse, MoE）算一个 token 时，是否用到全部参数
数量总参数（total） / 激活参数（active）权重一共多大 / 单 token 实际用多少

两者的关系是一句话：

所以"稠密"是"激活等于总量"的特例，不是另一种参数。

我们的 200B MoE：总参数 200B，激活 30B，稀疏度 85%。

3.0.1 能力为什么看总参数

能力随总参数增长，但这是经验规律，不是定律。

参数越多、知识类任务越好，这个趋势在稠密模型上拟合得很准——缩放定律（loss ∝ N^(−α)）就是这么来的。但把它直接搬到 MoE 上会出问题：同样是 30B 激活，200B 的 MoE 在知识问答上能领先十几分，换到多步推理和数学，差距缩到两三分。

差异的来源通常这样解释：专家结构擅长"记住"，而推理链要求激活路径本身连贯，被路由打断就会掉。

所以 91% 和 74% 这两个数，是 50 道题跑出来的，不是从"参数大"推出来的。换一套更偏推理的题，差距会缩到 5 个点以内。

3.0.2 为什么成本看激活参数

算力这一侧是严格的：

这就是"200B 比 70B 便宜"的全部原因：算力只认激活，不认总量。

但带宽这一侧有个坑，得说清楚。

3.0.3 带宽侧：专家并集会随 batch 放大

decode 每步要把权重读一遍。稠密模型读全部；MoE 只读被路由到的专家。

问题在于：一个 batch 里有 B 个 token，它们激活的专家可能不同，要读的是并集：

按 E=64、k=8 算：

batch并集专家数占全集含义
1812.5%只读 1/8 权重，很省
84266%省一半
165688%基本读全了
6464100%和稠密模型一样读全量

结论要修正一句：

成本看激活——在算力受限时严格成立；在带宽受限时，要看"有效激活"（专家并集）。

对实践的指导：

场景瓶颈MoE 收益
Prefill（算力受限）FLOPs完全按激活算，收益最大
Decode 小 batch带宽收益大（只读 1/8）
Decode 大 batch（≥32）带宽收益缩小（读全量，但摊到更多 token）

单 token 的带宽成本 = 并集字节 ÷ B，所以 batch 越大越便宜——这也是为什么吞吐要靠大 batch，而不是靠堆卡。

3.1 一条经验规律

把这两条画在一起，MoE 的价值就出来了：

方案总参数激活相对算力能力（通过率）
30B 稠密30B30B1.0×74%
70B 稠密70B70B2.33×78%
200B MoE200B30B1.0×91%

同样算力下，MoE 用 6.7 倍的参数换来了 17 个点的通过率。

3.2 MoE 的三项代价

代价数值影响
显存权重 200 GB（FP8），TP8 每卡 25 GB单卡装不下，必须 8 卡起
通信专家并行 all-to-all跨机走 IB 50 GB/s，是瓶颈（第 9 章）
负载不均热门专家排队需要 EPLB（Expert Parallel Load Balancer） 均衡（第 10A 章）
显存换 KV640 GB 里 200 GB 给权重，KV 只剩 400 GB并发上限被压缩

推翻条件：如果目标硬件只有 40 GB 显存（如部分国产卡），200 GB 权重装不进 8 卡，MoE 方案直接不成立——这时只能退到 30B 稠密或更激进的量化。

044. 评测集：50 道题怎么出

4.1 分布要对齐生产

评测集最容易犯的错不是"题太少"，而是题和生产不像。

类型数量考什么判分方式
单轮意图识别10分类准不准精确匹配
多步工具调用15参数对不对、步数对不对调用序列比对
长上下文检索832K 里的事实召回关键字段匹配
拒答与安全7该拒的拒、不该拒的不拒规则 + 人工
结构化输出10JSON 合法率schema 校验

五类加起来 50 道。权重不是平均的——多步工具调用占 30%，因为它是售后 Agent 的主路径。

4.2 题目从哪来

来源占比说明
生产日志采样60%脱敏后取真实长度与意图分布
人工构造25%覆盖长尾与边界
对抗样本15%提示注入、错别字、方言

对抗样本是唯一能提前发现安全事故的类别，不要省。

4.3 题目的准确性：出题、审题、判分分三个人

一道题能不能用，取决于它的期望值可不可信。最常见的失效不是模型答错，而是题目本身就错。

举个例子。业务规定"签收 7 天内可退"，出题人写了期望答案"只能退不能换"，但政策原文是"可退可换"。模型答"可退可换"被判为错，这一题从上线起就在扣分，而且没人去看它为什么错。

三个角色分开，是唯一有效的防法：

角色干什么不能是谁
出题人写输入 + 期望 + 依据条款不能同时是写 Prompt 的人
审题人（QA）逐题核对依据、判分可执行性不能是出题人的直属下级
判分实现把期望写成判定函数不能改期望，只能提"不可判"

写 Prompt 的人出题，会不自觉地把"当前模型能做到的"当成标准，评测就失去意义。

每道题落盘六个字段，缺一不可：

basis 这一栏最容易被省，但它决定了政策变更时的响应速度：政策改了，用它反查命中哪些题，一次改完。没有它，只能等线上出了偏差再回头猜。

判分方式按可判性分三级，比例要控制：

级别判什么判法目标占比
L1意图、JSON 结构、工具调用序列、拒答代码精确比对≥50%
L2数值区间、枚举、必含字段、正则规则判定约 30%
L3语气、完整性、解释是否合理人工或 judge≤20%

L3 超过 20% 的评测集不可信——它意味着大部分分数来自主观判断，换个 judge 就变一批结果。

双人标注是保底手段：两人独立标注同一批，一致率（Cohen's Kappa）低于 0.8 就回去改判定规则，而不是改分数。分歧集中在哪类题，说明那类题的判定标准还没写清楚。

4.4 全流程评测：模型对了不等于应用对了

50 道题全部通过，上线仍然可能不可用，因为题目只测了模型，没测模型外面那一圈。真实链路是：

每一段都可能改变结果，所以评测要分五层：

层测什么手段通过线
L0 模型单次调用输出质量50 题离线见 §5
L1 契约请求/响应字段、错误码、流式分片schema 校验 + 契约测试0 字段丢失
L2 编排多轮状态、工具调用、RAG 命中录制回放（replay）工具序列一致率 ≥98%
L3 端到端用户最终看到的内容真实请求回放 + 结果比对与基线差异可解释
L4 线上goodput、SLO（Service Level Objective）达成、人工抽检灰度 + 影子流量SLO ≥99.9%

L0 通过只是入场券。三个最常见的断裂点都在 L1–L3：

  • 工具 schema 变了：模型按旧参数调，工具返回 400，Harness 重试三次后降级成兜底话术。L0 看不出来，用户看到的是"抱歉我暂时无法处理"。
  • RAG 检索不到：模型本身答得对，但 Harness 塞给它的上下文是空的。L0 用的是自己准备的标准上下文，永远命中。
  • 流式被截断：网关 buffer 或超时把最后几个分片丢了，JSON 少了收尾括号。L0 拿的是完整响应。

所以 L2 和 L3 要用录制回放：把线上真实请求（含工具返回值、检索结果）存下来，重放时逐段比对。录制文件要带版本号，和模型版本、Prompt 版本一起绑定。

4.5 参数一致性：应用层和模型接入层怎么保证一样

这一节解决一个很具体的问题：应用层传了 max_tokens=2048，模型接入层却按默认 512 截断，两边都认为自己是对的。

不一致的八种典型来源：

字段应用层常见值接入层默认不一致的后果
max_tokens2048512输出被截断，JSON 不完整
temperature0.7（线上）0（评测）评测通过率虚高 5–7 个点
tools12 个字段服务端过滤后 9 个模型看不到必填项，参数乱填
system应用拼的 A 版接入层再注入 B 版两段指令冲突，行为漂移
stop["\n\n"]未设置多输出一段，前端渲染错位
streamtrue不支持时静默降级前端等到超时
单位token字符截断位置差 3 倍
seed固定未透传同一题两次结果不同，无法回归

最后一行常被忽略：没有 seed，评测就不是可复现的，回归测试等于没做。

五个手段，按成本从低到高：

① 单一契约源。 请求体用 proto 或 OpenAPI 定义，两侧 SDK 都由它生成，禁止手写结构体。字段增删只改契约，改完重新生成。

② 未知字段报错，不许静默丢弃。 这是最关键的语义约定。接入层收到不认识的字段要返回 400，而不是忽略——静默丢弃会让"应用以为生效了"这种错误一直活到线上。

③ 默认值只在契约里定义一次。 两侧都不许各写一份默认值。应用不传就用契约默认，接入层不传也不许自己补——补了就等于有两个真相。

④ 契约测试（consumer-driven）。 应用侧录真实请求快照，接入层跑同一批快照，断言"收到什么就生效什么"。每加一个字段，补三类用例：最小请求、完整请求、非法请求。

⑤ 运行时可观测。 接入层每次请求记录 effective_params（实际生效值），按模型版本 + 契约版本聚合。评测和线上用同一套埋点，直接对比两组分布：

这三条一起用才闭环：契约管定义，契约测试管行为，埋点管漂移。少一条就会出现"配置看起来一样、行为不一样"。

最后一条纪律：评测走和线上完全相同的调用栈——同一个 SDK、同一个网关、同一份默认值。用 SDK 直连模型做评测，测的是另一个系统。如果线上有网关做限流、改写、注入，评测也必须经过它。

4.6 判分：三种手段，按可靠性排序

手段适用可靠性
规则/精确匹配分类、JSON、字段最高（无歧义）
调用序列比对工具调用高（可精确到参数）
LLM-as-judge开放式回答中（需校准）

judge 能用有前提：与人工标注的一致率 Kappa ≥0.8。达不到就说明判定标准没写清楚，先改标准，别调 judge 的 prompt。

4.7 选型流程：从"想换模型"到"全量上线"

七步，每步写清输入、执行人、产出和门禁。门禁不过就停在这一步，不许带着问题上台阶。

步做什么谁做产出耗时门禁
1定能力清单与硬约束PM + 算法能力项、延迟/成本/合规红线0.5 天每条约束可量化
2收集候选算法3–5 个候选及部署规格1 天每个候选有可跑形态
3能力探针（初筛）算法20 题探针结果0.5 天通过率 ≥ 基线 −5pt
4全量评测QA + 算法50 题 + 盲测 20 题报告1 天见 §5，含单项否决
5成本与延迟实测SRE分/轮、TTFT/TPOT p951 天成本 ≤ +20%，TTFT ≤ 800 ms
6灰度SRE + 算法5% 流量 3 天数据3 天错误率不升、goodput 不降
7放量与归档平台release manifest + 评测归档0.5 天回滚演练通过

表中的 SRE 指 Site Reliability Engineer（站点可靠性工程师），负责容量测算、灰度推进、告警配置和回滚演练。和传统运维的区别在考核方式：SRE 用 SLO 和错误预算衡量，不是用"有没有出事"衡量。

一周左右能走完一轮。真正拖时间的是第 6 步，三天不能压——一天的灰度量不足以覆盖工作日和周末两种流量形态。

第 3 步的"探针"是这套流程省时间的关键。20 道题按区分度选出来（正负样本各半，覆盖五类），30 分钟内能跑完 5 个候选，用来快速淘汰差 10 个点以上的模型，避免每个候选都跑全量。

门禁不过时的处理方式，比门禁本身更重要：

卡在哪先改什么不要做什么
探针不过换候选调 Prompt 硬拉——拉上来也撑不住长尾
全量总分不够看单类，补 few-shot 或改 Prompt改评测题
全量单项跌破否决线单类专项优化；仍不过就放弃这个候选用总分把单项平均掉
成本超标量化、压 max_tokens、把简单请求分流到小模型先上线再优化
灰度指标变差回滚，拉 trace 定位加大流量"再看看"

4.8 评测流程：四个触发点

评测不是上线前跑一次，它挂在四个位置上。

触发谁跑跑什么出结果阻断什么

每次评测落一个 report.json，字段固定，便于跨版本对比：

manifest 里那三个值是绑定关系：模型换了、Prompt 换了、契约换了，任何一个变了都要重跑。只记 run_id 不记 manifest，三个月后没人说得清那次 91.2% 是哪个组合跑出来的。

055. 通过标准：不是"准确率 90%"

绝对阈值没有意义——模型会升级，题目会变难。正确做法是对标现网基线：

指标现网基线通过线一票否决
总通过率91%≥89%（−2 pt）<85%
工具调用参数正确率94%≥92%<88%
安全拒答率97%≥95%<90%
JSON 合法率99.5%≥99%<97%
TTFT p95610 ms≤800 ms>1,000 ms
TPOT p9542 ms≤50 ms>58 ms
端到端 p957.6 s≤9 s>11 s

表里三条时延不能合成一条看。TTFT 管"多久看到第一个字"，TPOT 管"吐字快不快"，端到端管"整轮什么时候结束"。任一组合都可能出现：TTFT 200 ms 但 TPOT 200 ms，350 token 的回答要 70 秒；反过来 TPOT 25 ms，但排队排了 30 秒，用户根本没等到第一个字。

三条之间还有一个隐含的长度上限。端到端 9 s、TTFT 800 ms、TPOT 50 ms，能装下的输出是 (9000−800)/50 = 164 token。超过 164 token 的回答，"9 s 达标"这件事就不再发生在 p95 上：350 token 的长回答落在 p99，它的预算是 0.8 + 350×0.05 = 18.3 s。对单个确定长度的请求，端到端就是 TTFT + N × TPOT——不能相加的是分位数，不是这两个量（第 1 章 §2.3）。

所以评测报告里三个数要一起出现。只报 TTFT 的评测，等于只测了"开头"，长回答退化成什么样完全看不见。

三条规则：

  1. 总分允许 −2 pt，因为新版本常在边缘题上波动；
  2. 任何单项跌破一票否决线，整体不通过——85% 总分里工具调用 0 分也是废的；
  3. 安全项只许升不许降，没有"−2 pt"的余地。

066. 三个陷阱

陷阱表现防法
过拟合评测集每次调 Prompt 都涨分，上线不涨留出 20% 从不参与调优的"盲测集"，每月换题
Judge 偏见偏爱长回答、偏爱第一个选项交换 A/B 顺序、双 judge 交叉
分布漂移评测集是三个月前的，生产已经变了每月按生产日志重采样

第一条最隐蔽：团队反复在 50 题上调 Prompt，分数从 78% 刷到 93%，上线后真实通过率只有 79%——刷的是题，不是能力。

099. 失败模式

现象根因怎么发现怎么修
评测 93%，上线 79%刷题过拟合盲测集分数低换题 + 盲测

1010. 验收

检查项通过标准
题量与覆盖≥50 题，5 类齐全，工具调用占比 ≥25%
分布一致与生产分布 KL 散度 <0.1
盲测集存在且从不参与调优，20 题以上
Judge 校准与人工 Kappa ≥0.8
一票否决安全/JSON/延迟三项独立判定
分组报告每类单独出分，不只有总分
可复现固定 temperature=0、固定评测集版本

1111. 备选方案

方案何时选代价
全用外部 API日调用 <10 万成本 12×，数据出境
只用 8B + 规则任务高度确定复杂售后走不通
蒸馏 200B → 30B已有 6 个月以上真实轨迹需要 3–6 个月，效果天花板低于教师
微调 30B领域非常窄泛化差，版本管理复杂（第 5 章）

顺序建议：先用 MoE 大模型跑通业务，收集 6 个月真实轨迹，再考虑蒸馏小模型降本。

1212. 收口

**选型不是选最强，是选"在成本与延迟约束下，能力刚好够用"的那个。

MoE 之所以成为默认答案，是因为它把"更大"和"更便宜"从对立变成了同向。**
