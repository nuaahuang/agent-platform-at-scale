011. 问题：两个变更撞在同一天

10 月 27 日，两件事排进了同一周：

  • 算法组要把模型从 FP8 换成 FP8 加 KV 量化，说能再省 12% 成本
  • 产品组要上线新版 Prompt，改退款话术，说客诉能降 8%

两个变更单独看都没问题。一起上，出了问题就分不清是谁的。

更麻烦的是它们互相影响：新 Prompt 更长，prefill 变慢，KV 量化又在长上下文掉点更多。上线后 TTFT（Time To First Token，首 token 延迟）涨了 90 ms、长文通过率掉 2 个点，两个指标都在报警，但没人能说清哪个变更导致的。

这一章解决的就是这件事：把版本拆成可独立发布的层，定清楚谁和谁必须绑、谁变了要重跑什么、谁变了要让什么失效。

022. 四层版本

一个 Agent 平台同时存在四种版本，变更频率差两个数量级：

层命名示例变更频率影响面谁改
代码gw-v3.2.1每天全链路工程
Promptp-2026-10-27.3每周行为与格式产品 + 算法
模型权重w-2026-11-02每月能力与知识算法
精度格式fp8-e4m3季度性能与精度算法 + 平台

这四层的差别不只是频率。前两层可以回滚得很快，后两层回滚要动权重和显存。

关键区别在于：代码和 Prompt 是"可以按请求生效"的，模型权重和精度格式是"按实例生效"的。因为一个推理实例只装得下一份权重，不可能同一个实例对 A 用户跑旧模型、对 B 用户跑新模型。

这个物理约束决定了本章的核心结论：灰度方式被版本类型限制，不是你想怎么切就怎么切。

033. 版本矩阵：什么组合是合法的

四层任意组合有 16 种，但只有一部分能跑。下面是实际会遇到的组合：

变更必须重跑必须失效能独立发布吗
代码（业务层）契约测试无能
代码（引擎 / kernel 层）回放 + 压测无能，但要重测性能
Prompt50 题 + 盲测前缀缓存（Prompt 是前缀时）能
模型权重50 题 + 回放 + 通用集全部 KV能，但要按实例
精度格式50 题 + 逐题 diff + KL全部 KV + 量化校准能，但要按实例
Tokenizer全部重测全部 KV + 重新校准 + 重算成本不能，要整体换

最后一行是特例。Tokenizer 换了，token id 的映射全变，历史 KV 的哈希、量化的 scale、成本核算的 token 计数全部失效。这种变更不该"灰度"，只能整体切换，而且要提前一周通知所有下游。

三种组合最容易出事：

第一种，新权重配旧 KV。权重变了但缓存没清，新模型读到旧模型算出来的 KV，注意力结果错乱。症状是输出不通顺、答非所问，但不会报错，很难定位。第 10B 章讲过，权重版本是 KV 唯一的真实失效条件，这种事得由发布流程强制保证，不能靠人记得。

第二种，新 tokenizer 配旧量化 scale。Tokenizer 换了之后，激活的数值分布变了，原来的 per-tensor scale 就压不住了，要么溢出被 clamp，要么精度骤降。表现是准确率掉 5 个点以上，但量化配置看起来没变。

第三种，新 Prompt 配旧评测基线。Prompt 改了，通过率从 91% 掉到 89%，团队以为是模型退化，实际是新 Prompt 让模型更保守。基线要和版本绑定，不绑就没法归因。

044. 一个串标识完整组合

版本散落在四个地方，发布时必然对不上。解决办法是打成一个 manifest：

六个字段缺一个，出问题就查不清。第 4 章的评测报告用同一套 manifest，评测结果和线上运行的是同一个组合——这一点是排查的前提。

manifest 要落到两个地方：镜像的 label（运行时能查到），和发布记录表（历史能查）。只放镜像 label，回滚时找不到旧版本是什么组合；只放记录表，容器里查不到自己跑的是哪个版本。

055. 评测门禁：哪几项不过就不许发

门禁不是"跑一遍评测"，是"不过就拦住"。四项硬门禁，来自第 4 章的通过线：

门禁通过线一票否决谁看
总通过率≥89%（基线 −2pt）<85%自动
工具调用参数正确率≥92%<88%自动
安全拒答率≥95%<90%自动
JSON 合法率≥99%<97%自动

四项之外还有三条软门禁，需要人签核：

  • 通用能力退化不超过 5 个点（防止微调把模型训窄）
  • 长上下文（>16K）通过率不低于基线 2 个点
  • 成本变化在 ±20% 以内，超出要说明原因

软门禁的意义在于拦住"任务指标变好、整体变差"的发布。这种情况在微调和量化里都常见。

门禁的判定要绑定 manifest。同一份 Prompt、同一个权重、同一套评测集，跑出来的结果才有可比性。换了评测集再比，比的是两件事。

066. 灰度：模型层只能按实例切

这是本章最容易做错的地方。

业务代码的灰度是按请求切的：给 5% 的请求打标，走新版本，其余走旧版本。同一个实例可以同时服务两个版本。

模型不行。一个实例的显存里只装得下一份 200 GB 权重，要同时跑两个版本就得两份显存，等于两倍的卡。所以模型灰度只有一种做法：换实例。

具体做法是双池：

比例从 5% 开始，按租户切而不是按请求切——同一个用户在一次会话里不能一会儿新模型一会儿旧模型，否则上下文对不上。

阶段卡数占比观察时长放量条件
金丝雀5%（128 卡）1 天错误率不升，客诉不升
小流量20%（512 卡）2 天goodput 不降，成本符合预期
半量50%2 天以上全部满足
全量100%—回滚演练通过

每个阶段都要跨一个完整的流量周期。只在工作日灰度，周末的流量形态（占比 30%，但客诉集中）根本没覆盖到。

双池期间的成本要额外算：新池 128 卡没有前缀缓存，命中率从 85% 掉到 0，TTFT 会短暂破线。所以所以切流前要先预热（下一节）。

077. KV 作废与预热

7.1 缓存里存的到底是什么

先把这件事说清楚，后面才谈得上预热。

前缀缓存存的不是请求，也不是回答文本，是 KV 块——每个块 16 个 token 的 K 和 V 张量，1.92 MB，躺在显存里（第 10B 章）。

索引也不是请求 id，是 token 序列的哈希。而且是链式的：

链式的作用是：要命中第 3 块，必须前 3 块完全相同。这就是为什么只有"从第 0 个 token 开始的前缀"能复用——RoPE 的位置编码使得中间截一段的 KV 不能直接拼。

一个新请求进来，引擎做的事是：

步动作结果
1tokenize 成 ids拿到 3,200 个整数 id
2每 16 个切一块，逐块算链式哈希200 个哈希
3拿哈希去块池查前 187 块命中，后 13 块未命中
4只对未命中的 13 块做 prefill算 208 个 token，不是 3,200
5新算出的块写回池子，登记哈希池子变大

表里第 1 步的 id 是什么，值得停一下。Tokenizer 把文本切成 token——不是词，是子词片段——每个 token 在词表里有一个下标，这个下标就是 id。现代模型的词表在 12 万到 15 万之间，所以 id 是一个 0 到 15 万之间的整数。

文本切分id（示意）
退货退 / 货45,102 / 8,733
我的订单我 / 的 / 订单1,024 / 13 / 88,301

中文大约 1 个 token 对 1.5 个汉字，所以 3,200 个 id 约等于 2,100 个汉字——正是"系统提示 + 工具定义"的量级。

用 id 而不是文本，是因为模型只认 id。同一句话用不同 tokenizer 切，id 完全不同，算出来的 KV 也不同。这是第 3 节那条规则的根源：换 tokenizer 等于换了一套坐标系，历史 KV 的哈希、量化的 scale、计费的 token 数全部对不上，只能整体切换。

所以"缓存"是引擎在第一次处理某个前缀时顺手写下的，不需要任何配置。命中率 85% 这个数，就是长期运行后自然形成的。

7.2 那预热是在做什么

预热看清楚了：它是主动把还没人用过的那段前缀，提前算一遍写进池子。

不是"把旧请求搬回来"，也不是"重放"——旧 KV 已经随权重版本作废了，搬不回来。是拿同样的文本，用新权重重新算一遍 prefill，得到新 KV，写进池子。

一个具体的例子。售后 Agent 的系统提示加工具定义是 3,000 token，用户问题平均 200 token，这个前缀每天出现 50 万次。两种情况并排放：

指标没预热预热后变化
每请求要算的 prefill3,200 token200 token−94%
单请求 prefill 耗时267 ms15 ms−94%
单请求 TTFT（含排队 100 ms、网络 50 ms）417 ms165 ms−60%
日 prefill 总量（50 万次）16 亿 token1 亿 token−94%
折合单实例工作时间37.5 实例·小时2.5 实例·小时−93%
p95 TTFT（实测，0% 命中 vs 85% 命中）1,900 ms610 ms−68%

这张表要横着读。前三行是单请求，中间两行是按 50 万次放大，最后一行是线上实测。

有两个数字值得注意。

第一，prefill 耗时降了 94%，但 TTFT 只降 60%。差额是排队和网络——这两项不随预热变化，它们在分母里把百分比稀释了。所以"省了多少计算"和"用户快了多少"是两个数，不能混着说。

第二，日计算量从 37.5 实例·小时降到 2.5，意思是这一个前缀每天省下 35 个实例·小时的 GPU 时间，约等于 1.5 张卡一直在算。而且这是一个前缀的账，Top 100 加起来更多。

再看最后一行：实测的 p95 是 1,900 ms 对 610 ms，降 68%，和单请求模型的 60% 接近，说明模型没有算错方向。它的绝对值对不上，是因为 p95 里包含排队——高负载时排队那项会从 100 ms 涨到 600 ms 以上。

这就是为什么值得花 3 分钟做预热：用 3 分钟换每天 35 个实例·小时。

那"Top 100"是怎么来的？这里最容易误解成"挑 100 条代表性请求"。不是。

一个请求的结构是这样的：

用户问题各不一样，但前面的 system 和 tools 是模板，全平台只有几百种组合（业务线 × Prompt 版本 × 工具集）。所以统计的对象是前缀，不是请求：

环节数量级
一天的请求1.5 亿条
去掉用户问题、只留 system + tools150 万条
按前缀哈希去重约 200 种
按出现次数排序取前 100100 种（覆盖 78%）

真实分布通常更集中：前 5 种前缀就可能覆盖 70%，前 100 种覆盖 78%，后面是长尾。如果业务简单，可能总共只有 8 种前缀，那"Top 100"实际就是 8 条。

反过来说，如果统计出来有几万种前缀，通常不是业务复杂，是有人在系统提示里拼了时间戳、用户名或订单号——变量前置了。这种写法会让缓存命中率长期为零，是设计问题，不是预热能救的（第 20 章讲上下文工程时会再提）。

拿到这 100 个前缀的文本之后，才轮到渲染和重算。完整流程七步：

步动作产出
1日志取最近 7 天，抽 1%150 万条记录
2每条取 system + tools，canonical JSON 算 SHA1前缀指纹
3按指纹计数，降序取前 100100 种前缀的文本
4用线上同款 tokenizer + 模板渲染成 token ids每条的真实 id 序列
5按 id 长度累加，估算 KV 占用，超预算就截断实际预热的条数与总 token
6逐条 engine.generate(max_tokens=1)引擎切块、算哈希、prefill、写回池子
7读 num_cached_tokens 断言确认写入成功

第 5 步最容易被跳过，但它是唯一能防止"预热把显存吃满"的环节。做法不是"100 条乘平均长度"，而是先渲染、按实际长度累加——前缀长度分布很偏，一条 8,000 token 的长前缀顶三条 2,600 的。

算例：

前缀档位条数单条 token小计 tokenKV 占用
短（<1K）5580044,0005.3 GB
中（1–3K）302,00060,0007.2 GB
长（3–8K）155,00075,0009.0 GB
合计100—179,00021.5 GB

179,000 token 乘 120 KB 约 21.5 GB，占 400 GB 池子的 5.4%，安全。

如果统计出来是 60 万 token（比如长前缀占比高），就是 72 GB、18%，仍然能跑但接近警戒线。这时候按"每 GB 省多少毫秒"排序，砍掉短前缀——短前缀 prefill 本来就快，预热收益低。

预算公式和警戒水位在 §8.4.2，这里只强调顺序：先估再算，不是算完再看显存。

第 6 步是关键：它不是"把文本存进去"，是让引擎真的算一遍。算出来的块进了池子，后面真实请求才可能命中。

然后对这 100 条文本，各发一次只跑 prefill 的请求，让引擎按正常路径算出 KV 写进池子。之后真实请求带着同样的 token ids 进来，链式哈希一致，直接命中。

为什么不用"把 KV 存到磁盘再读回来"？因为重算更快也更简单：300K token 的 prefill 只要 27 秒计算，而 36 GB 的 KV 落盘再加载要处理序列化、块布局对齐、版本校验，出一次错就是脏缓存。

7.3 权重一变，为什么全废

权重版本变了，KV 就全部作废。这不是缓存策略的问题，是数学上的必然：KV 是旧权重的中间结果，新权重的注意力分布不同，旧 KV 拿来用就是错的。

失效的代价：

时点命中率TTFT p95现象
切换前85%610 ms正常
刚切换0%1,900 ms超时告警集中爆发
预热 5 分钟后40%1,100 ms仍破线
预热 20 分钟后85%620 ms恢复

预热不是等自然流量填满，那要几个小时。做法是主动重算：取线上 Top 100 的前缀（覆盖 78% 的请求），在新实例上各跑一遍 prefill，把新 KV 写进池子。

重算不是简单发一百个请求，中间有三个坑会让命中率停在 20% 上不去。具体做法见 §8.4。

100 条提示的 prefill 计算量是 300K token × 0.09 ms ≈ 27 秒，加上模板渲染、调度和并发度限制，实际 1–3 分钟。之后靠自然流量把长尾补到 85%。

预热要在切流之前做。切完再预热，前 20 分钟的请求全部承受 1.9 秒的 TTFT。

088. 滚动替换：把一批卡换掉的完整时序

上一节说模型灰度按实例切，这里补最关键的一段：一个实例从"跑旧模型"变成"跑新模型"，中间到底发生什么。

先纠正一个常见误解。版本切换不做原地换权重，做销毁重建。原因是显存碎片——不重启进程、只卸载权重再加载新权重，第二次加载大概率 OOM。vLLM 的 sleep/wake 是给"同版本内腾显存"用的，不是给换版本用的。

所以一次替换是六步，不是"下载新权重然后热加载"：

步动作耗时判据
1摘流（从服务发现移除）0 秒新请求不再进来
2等待在途请求跑完≤30 秒active_requests == 0
3进程退出，KV 随显存释放5 秒显存回落
4拉新镜像与新权重2–3 分钟权重 checksum 匹配
5模型 warmup2 分钟首 token 延迟回到基线
6KV 预热3 分钟命中率回到 60% 以上

单批约 14 分钟，其中 7 分钟是纯等待。下面拆开说每一步的细节。

8.1 摘流量：软摘，不是硬断

摘流的意思是把实例从服务发现里移除，让它不再接新请求，但它身上还有正在跑的请求，不能立刻杀。

做法是在 readiness 探针上做文章：

/drain 做三件事：把 draining 置真、对新请求返回 503 加 Retry-After、等 active_requests 归零。探针失败后 k8s 把它从 Endpoints 摘掉，网关不再路由过来。

30 秒这个数不是拍的。端到端 p99.9 是 15 秒（第 1 章），等两倍覆盖长尾。超过 30 秒还没跑完的，是流式长输出，需要特殊处理：在下一个 token 边界发 [DONE] 收尾，前端显示"回答已停止"，而不是报错——用户看到半句话，比看到"网络错误"好得多。

摘流期间的三类请求要分别处理：

请求类型处理用户感知
未开始的503 + Retry-After，网关重试到别的实例延迟 +200 ms，无感
正在跑的非流式等它跑完，最多 30 秒正常
正在跑的流式到下一个 token 边界收尾"回答已停止"

网关那边要配合：摘流瞬间会有几十个 in-flight 请求同时 503，重试预算要够，否则会把重试风暴变成故障。

8.2 清 KV：靠进程退出，不靠"记得清"

KV 在显存里，进程一死操作系统就回收了，不需要单独清。这也是为什么用销毁重建而不是热加载——它把"清 KV"这个容易忘的步骤，变成了物理必然。

如果非要在进程内换（比如只想换 LoRA adapter），必须显式清理，而且要检查两个数：

只看 memory_allocated 降下来不够，memory_reserved 才是真正占着卡的量。reserved 没降就加载新权重，会 OOM——而且报的错是"显存不足"，看起来像权重太大，实际是碎片。

8.3 加载权重：先落盘，再并行进显存

200 GB 权重不是从对象存储直接进显存的。路径是三段：

8.4 预热分三层，顺序不能反

大多数人只做第一层，结果前几分钟的请求全在踩坑。

层做什么耗时不做的后果
权重 warmup跑 dummy 请求触发 kernel autotune2 分钟首个真实请求慢 3–5 秒
KV 预热Top 100 提示回填前缀缓存3 分钟命中率 0，TTFT 1.9 秒
调度预热低流量跑 5 分钟看队列与 TPOT（Time Per Output Token）5 分钟配置错误要等放量才发现

第一层最容易被跳过。GPU 的 kernel 首次调用要编译和选优，vLLM 在启动时可以用 profile run 提前触发。不做的话，第一个真实请求会吃到 3–5 秒的额外延迟，而灰度阶段偏偏最容易把这个当成"新模型更慢"。

第三层是观察，不是技术动作：新实例接 1% 流量跑 5 分钟，看队列长度、TPOT 分布、显存水位是否和旧实例一致。不一致就停下来查，别急着放量。

8.4.1 Top 100 怎么重算

重算的难点不在"发请求"，在"让引擎算出来的前缀和线上那条逐 token 相同"。

三个坑，每一个都能让命中率停在 20%：

第一个坑是模板。用 messages 数组发送，引擎会用服务端自己的 chat template 渲染；预热脚本如果你自己拼字符串，两边的 token 序列差一个空格，block hash 就不同，命中不了。正确做法是预热脚本加载同一个 tokenizer 和模板，直接渲染成 token ids 再发。

第二个坑是工具定义的序列化。tools 里的 key 顺序、空格、是否转义，只要变一处，前缀就变了。必须固定成 canonical JSON（sort_keys=True），而且这个序列化函数要和线上网关用同一份代码，不能各写一遍。

第三个坑是只预热了一半。前缀是"系统提示 + 工具定义"这段公共部分，如果预热时漏了 tools，实际请求的前缀比预热的长，照样不命中。

脚本里要包含"先估再算"这一步：渲染完拿到 id 长度，累加超过预算就截断，然后再进循环。

显存代价要提前算：100 条 × 3,000 token = 300K token，按每 token 121 KB 算约 36 GB，占 400 GB KV 池的 9%。如果显存本来就紧张，预热会触发淘汰，把刚写进去的又挤出来，命中率卡在 40% 上不去。这种情况要么降数量到 50 条，要么等扩容。

8.4.2 预热会不会把显存占满

会，而且这是预热最现实的失败方式。

先算账。每个 token 的 KV 约 120 KB（1.92 MB ÷ 16），所以：

场景前缀数每前缀 token总 KV占 400 GB 池
售后主流程1003,00036 GB9%
长文档问答2032,00077 GB19%
极端（全量长前缀）10032,000384 GB96%

前两行安全，第三行会爆。爆的表现不是报错，是新请求拿不到块，触发淘汰，把刚预热的又挤出去——命中率从 60% 掉回 30%，而且越预热越低。

三个机制让这件事可控。

第一，预热块不带引用，随时会被淘汰。

块池是共享的，空闲块按 LRU 排队。预热写进去的块引用计数是 0，一旦有新请求要块，它们就是第一批候选。所以预热是"尽力而为"，不是"钉住"。

这也解释了一个反直觉现象：预热完立刻测命中率是 60%，跑 5 分钟掉到 40%。不是预热没生效，是被真实流量挤掉了。

要让高频前缀留住，得靠"周期性重算"而不是"一次性预热"——每 10 分钟补一次 Top 20，让它们在 LRU 队列里保持新鲜。

第二，预热前先算预算。

脚本里加一个累计判断，超预算就截断，只预热前 N 条。宁少不炸。

第三，健康标准是预热后剩余空闲块不低于 20%。

预热完立刻查两个数：

低于 20% 就把预热条数砍半重来。这个阈值不是拍的：真实流量的并发峰值需要足够块才能接住，池子被预热吃到 80% 以上时，一次流量突增就会触发大面积淘汰。

还有一个取巧办法：只预热长前缀。原因不是"短前缀不值得算"，是单位显存的收益随长度上升：

前缀长度prefill 耗时KV 占用每 GB 省
800 token60 ms0.09 GB655 ms/GB
2,000 token159 ms0.23 GB693 ms/GB
5,000 token450 ms0.57 GB786 ms/GB
8,000 token806 ms0.92 GB880 ms/GB

如果 prefill 严格按 0.09 ms/token 线性，这一列会是常数（786 ms/GB）——因为时间和显存都正比于长度，比值自然不变。实际上它随长度上升，因为 prefill 里有两部分：

线性层（QKV、MLP、专家）按 token 走，注意力按 token 的平方走。5,000 token 时注意力只占 20%，32,000 token 时占到 62%。所以长前缀的每 token 成本更高，它省下的时间也就更多。

这也提醒一件事：0.09 ms/token 是 5,000 token 这个点的平均值，不是常数。用它估算 800 token 会多算 20%，估算 32K 会少算一倍。

不过截断的时候，频次仍然是第一位的。一条出现 50 万次的前缀和一条出现 100 次的，单条收益相同，总收益差 5,000 倍；而长短带来的单位差异只有 34%。排序按"频次 × 单条节省时间"，长度只作为同频次时的次序。

099. 回滚：30 分钟的前提是三个

回滚的目标是 30 分钟内恢复到旧版本。这个数字能不能达到，取决于三件事在发布前有没有准备好。

前提不满足会怎样怎么准备
旧权重文件还在要重新导出和校准，2 小时起保留最近 3 个版本，冷存储
旧版 KV 能重建缓存无法恢复，TTFT 长期破线预热脚本支持指定版本
数据库 schema 兼容降级后读不了新写入的字段变更前后各保留一个兼容版本

第三条最容易忽略。模型版本回滚通常不涉及 schema，但如果同一批发布里带了新字段（比如工具调用记录新增了 refund_reason_code），回滚后旧代码读到这个字段会报错，或者直接忽略导致数据丢失。

30 分钟的构成：

这个账要提前算，不能出事时才算。而且每季度要真做一次回滚演练——演练不做，第一次真回滚一定会超时。

1010. 版本保留策略：留多了占地方，留少了回不去

权重文件很大，200 GB 一个，攒一年就是 2.4 TB。保留策略要在"回得去"和"存得起"之间定。

版本保留时长存哪一个月成本
当前线上常驻，每实例一份GPU 显存已含在推理成本里
前一个版本30 天对象存储 + 预热好的实例池¥120
再往前一个90 天对象存储冷层¥30
更早删除—0

存得起，是因为对象存储便宜：200 GB 乘 ¥0.15/GB/月，一个版本一个月三十块。真正贵的是"保留可随时切换的实例池"——要真做到 30 分钟回滚，前几天得留一批空卡或者能快速腾出的池子。

所以策略分两档：有明确上线日期的发布，前 7 天留一个 128 卡的空池；日常小版本只保留冷存储里的权重，回滚需要 25 分钟重建。
