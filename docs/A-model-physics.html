# 附录 A · 模型层的物理：显存、带宽、算力

迁移自 v1 ch02-model-physics.md。文中引用"第 N 章"为 v1 旧编号，与 v3 的对应关系见 ../MIGRATION.md。

一句话结论：所有容量数字都来自三个公式——显存账本、KV 公式、Roofline。

会推这三个，你就不需要背任何"经验值"。

011. 问题：为什么"加卡"不一定变快

新手的第一反应是"慢了就加卡"。但真实情况是：

  • 加卡后 TTFT（Time To First Token） 没降——因为瓶颈在排队，不在算力；
  • 加卡后 吞吐没涨——因为瓶颈在显存带宽，不在 FLOPs；
  • 加卡后 更慢了——因为 TP 通信开销超过了收益。

要判断"该加什么"，必须先知道当前卡在哪一种资源上。这一章就是教你怎么判断。

022. 显存账本：640GB 里能装什么

以 8×H800（80GB/卡）为例：

项大小说明
模型权重200GB200B 参数 × 1 Byte（FP8）
KV Cache~300GB装会话的"记忆"
激活 / 临时~60GB中间结果、CUDA Graph

关键认知：权重是固定的，KV 是弹性的。并发上不去，通常不是权重装不下，是 KV 装不下。

参数量 ≠ 显存。FP8 是 1 Byte/参数，FP16 是 2 Byte，INT4 是 0.5 Byte。

"200B 模型要 400GB"只在 FP16 下成立。

2.1 什么是 HBM

HBM（High Bandwidth Memory，高带宽存储器）：把多层 DRAM 像盖楼一样 3D 堆叠，通过 TSV（硅通孔）穿层连接，再用一块硅中介层（interposer）和 GPU 封在同一个基板上。

GPU 有上万个核心，数据喂不过来就全闲着。HBM 用"超多引脚的超宽总线"解决——每个 stack 是 1024 位，5 个 stack 就是 5120 位（普通显卡显存总线只有 256–384 位）。

HBMGDDR6（游戏卡）DDR5（主机内存）
带宽3–8 TB/s0.5–1 TB/s0.1–0.4 TB/s
容量80–192 GB12–24 GB数百 GB–TB
位置和 GPU 同封装板卡旁边主板上
价格贵，受 CoWoS 封装产能限制便宜最便宜

典型数字：H800/H100 = 80GB HBM3、3.35 TB/s；H200 = 141GB HBM3e、4.8 TB/s；B200 = 192GB、8 TB/s。

两个推论：

  1. 权重和 KV 必须放进 HBM——PCIe 只有 64 GB/s，比 HBM 慢 50 倍，放外面 decode 立刻饿死；
  2. HBM 又贵又小，所以才要 FP8、GQA/MLA、PagedAttention——这些技术都在回答

同一个问题：怎么在这 80GB 里塞下更多东西。

3.1 补充：MHA / MQA / GQA / MLA——KV 头数为什么能变小

注意力里有三种头：Q 头（查询）、K 头（键）、V 头（值）。KV Cache 只存 K 和 V（Q 来自当前输入，不用存）。怎么分配这些头，直接决定 KV 大小：

以"32 个 Q 头"为例：

方案KV 头数 H_kvKV/token8K 上下文300GB 装几条
MHA32~1,024 KB8 GB~37
GQA（本项目假设）4~128 KB~1 GB~312
MQA1~32 KB0.25 GB~1,200
MLA压缩后~30–40 KB0.24–0.31 GB~1,000+

为什么能共享：注意力是"Q 去查 K、按权重取 V"。多个 Q 头查同一套 K/V，仍然能从不同视角取信息，只是表达能力略降。Google 2023 的实验表明GQA 质量几乎追平 MHA，KV 却只剩 1/4–1/8；MQA 省得更多，但部分模型掉 1–3 pt。

注意：GQA 不只省显存，还省 decode 带宽——每生成一个 token 要读的 KV 变小了，所以 decode 直接变快。这是"改模型架构就能降推理成本"的典型例子。现在主流模型几乎都用 GQA（Llama 3：32 Q / 8 KV），DeepSeek 用更激进的 MLA。

MLA 为什么重要：DeepSeek 的 MLA 把 KV 压到 GQA 的 1/3–1/4，同样 300GB 能装的会话数直接翻 3–4 倍——模型架构决定了推理成本的上限。

044. 解码是带宽游戏

生成 1 个 token，要把"权重 + 所有在跑会话的 KV"从显存读一遍。

H800 的 HBM 带宽是 3.35 TB/s，MoE 激活权重 30GB：

B 就是 batch size（批大小）：一个 step 里同时处理多少个序列。

GPU 几万个核心，一次只算一个用户根本喂不饱；把 B 个用户凑成一批，

权重读一次给 B 个人共用——这就是 batch 的意义。

- 训练：一个 batch 是一组样本，算完一起更新权重（典型几百到几千条）；

- 推理：一个 step 里正在同时生成的请求数（vLLM 动态变化，几十到几百）；

- 每 step 每个序列各出 1 个 token → 每步共产出 B 个 token；

- B 越大越省（权重摊薄），但每步越慢（TPOT（Time Per Output Token） 变差）、KV 越占显存——上限由 KV 预算决定。

一个 decode step 的五步（以生成第 5,002 个 token 为例）：

步骤做什么数据量
① 投影算新 token 自己的 K₅₀₀₂/V₅₀₀₂（只算 1 个）1 token
② Q·K新 token 的 Q 乘全部历史的 K（1×5,002）读 5,002 个 K
③ softmax·V对全部历史 V 加权求和读 5,002 个 V

  • 计算只有 1 个 token 的量（恒定）；读取是全部历史（随上下文线性增长）；
  • 历史 K/V 不重算——自回归是因果的，旧 K/V 一旦算好永久有效。
  • 每步新增 120KB，却要读 0.96GB（8K 时）：写一个人，读一整本书。

  • 单用户速度：某一个用户每 s 收到几个 token（= TPOT 的倒数）→ 决定体验。

batch 变大，聚合吞吐涨（权重被 64 个请求摊薄），但单用户速度反而掉——连续批处理就是在"成本"和"TPOT SLO（Service Level Objective）"之间找最大 batch。batch→∞ 时，KV 主导：3350 ÷ 0.96 ≈ 3,490 tok/s 就是聚合上限。

注：这是数量级模型（把整台机器当一块卡，忽略了 TP 切分、kernel 效率），

真实值再乘 30–50%。用它判断方向和上限，不用它定合同指标。

  1. batch 变大，吞吐上升，但会饱和——因为 KV 读取最终主导。
  2. 吞吐上限 ≈ HBM 带宽 / 单会话 KV。想让上限翻倍，要么换带宽更高的卡，要么把 KV 变小（MLA/量化）。
  3. 上表是理论上限，真实要乘 30–50% 的效率系数（kernel、调度、通信开销）。

这也解释了为什么"decode 加卡"有效但线性度差：TP 会把 KV 和权重切开，

但每一步都要 all-reduce，通信会吃掉一部分收益。

055. Prefill 是算力游戏

5.0 Roofline：一张图判断谁是瓶颈

Roofline（Williams et al., 2009）把硬件的两个极限画成一个"屋顶"：

一个公式：

  • 斜屋顶：AI 低时，每搬 1 Byte 只能做几次运算，GPU 在等数据——带宽受限；
  • 平屋顶：AI 高时，数据喂得够快，算力跑满——算力受限；
  • 拐点（ridge point）= 峰值算力 ÷ 峰值带宽 = 1.98×10¹⁵ ÷ 3.35×10¹² = 590 FLOP/Byte。

把两个阶段放上去：

阶段AI位置可达算力结论
Decode（batch 小）≈ 2斜屋顶3.35T × 2 ≈ 6.7 TFLOPS算力只用了 0.3%
Prefill T=5,000≈ 2T = 10,000平屋顶接近 1,980 TFLOPS算力受限

这里两个常数的出处：2 见 §5.2——每个参数对每个 token 做"1 次乘 + 1 次加 = 2 FLOP"；

3.35 TB/s 见 §2.1——H800 HBM3 显存的硬件带宽规格。两者都是"记账约定/硬件参数"，不是推导值。

这就是 PD 分离的数学根因：两个工作负载在屋顶图上的位置相差 5,000 倍，根本不可能用同一套资源配置同时优化。

类比：工厂的产能 = min(工人速度, 传送带速度)。AI 低时传送带是瓶颈（decode），AI 高时工人忙不过来（prefill）。屋顶线就是那张"先瓶颈谁"的诊断图。

5.1 先分清四个单位

写法含义量级例子
FLOP一次浮点运算（一次乘或一次加）1一个 MAC = 2 FLOP
FLOPs运算总数（复数，常被滥用）次数一次 prefill 要做 300 TFLOP
FLOPS每秒运算次数（速度）次/秒H800 FP8：1.98 PFLOPS
TFLOP / TFLOPS10¹² 次 / 10¹² 次每秒万亿单卡 FP16 约 1 TFLOPS 的千倍
PFLOPS10¹⁵ 次每秒千万亿1.98 PFLOPS = 1.98×10¹⁵ 次/秒

最容易踩的坑：

  • TFLOP（无 S）= 工作量，TFLOPS（有 S）= 速度。差一个 S，差一个"每秒"。
  • 厂商参数表写"1.98 PFLOPS"是峰值速度；你算出来的"300 TFLOP"是工作量。

两者相除才得到时间：300 TFLOP ÷ (1.98 PFLOPS × 35%) ≈ 0.43 秒。

  • FP8 的速度约是 FP16 的 2 倍；稀疏（2:4）还能再翻倍。看参数必须看精度。

5.1.1 「稀疏」有三种，说的不是一回事

稀疏在哪一层含义影响什么
结构化稀疏（2:4）硬件/权重每 4 个权重里固定 2 个是 0，Tensor Core 跳过不算峰值 FLOPS ×2（参数表里的 "sparse" 指这个）
MoE 条件计算模型架构每个 token 只激活少数专家（30B / 200B）单 token FLOPs 变小，但显存要装全部专家
稀疏注意力算法只算部分 token 对（滑窗/块稀疏）长上下文 T² 项变小

买卡时看到的"稀疏"= 第一种：H100/H800 参数表常写 "3,958 TFLOPS FP8 sparse"，对应 dense 是 1,979 TFLOPS。要享受这个 2 倍，权重必须剪枝成 2:4 模式并微调，不是"模型里有 0"就行。

设计 MoE 时说的"稀疏"= 第二种：它是条件计算——路由只让部分专家参与。好处是单 token 算力低；代价是显存装全部专家、专家并行要 all-to-all 通信。

一句话：2:4 稀疏省算力，MoE 稀疏省算力但费显存和网络。 两者不能叠加着白拿。

5.2 为什么是 2 × N_active × T

一个线性层 y = Wx，W 有 N 个参数：

所以那个 2 不是"两个矩阵"，是"乘一次、加一次"。

严格计数是 2N−1（N 次乘法 + N−1 次加法），N 以十亿计时约定记 2N；

硬件上 1 条 FMA 指令完成乘加，但厂商 FLOPS 按 2 FLOP 记账，两边口径一致。

训练时还要加反向传播：前向 2N + 对输入梯度 2N + 对权重梯度 2N = 6N/token（6ND）。

为什么反向两遍：线性层 Y=XW，前向已知 X 求 Y=XW；反向时已知上游梯度 dY，

要算 dX = dY·Wᵀ（梯度传给上一层）和 dW = Xᵀ·dY（更新本层权重），

两个不同的矩阵乘，各约 2N FLOP。

推理时 dW/dX 都不需要，只留前向 2N——这也是为什么训练还要额外存激活（供反向用）。

AI 不是恒等于 2。一般式 AI = 2N·B ÷ (N字节 + B × 单会话KV)：B=1、权重主导时 AI≈2；B=64 时 AI≈42；prefill 时 AI=2T（T=5000→10,000）；FP16 时减半。2 只是"FP8 + decode + 小 batch + 权重主导"这一特例。

MoE 里每个 token 只走激活的专家，所以只用 N_active（30B），不是总参数 200B。

注意：2N 不含注意力打分（它没有权重矩阵）。 先分清"KV 的计算"有两种：

  • ① 投影 K/V：K=XW_K, V=XW_V——带权重的线性层，已含在 2N 内；
  • ② 打分取信：QKᵀ 和 softmax·V——不带权重，不在 2N 内。
  • （把 K/V 存进 Cache 本身不耗 FLOPs，只耗显存和带宽。）
注意力 FLOPs（L=64, d=7168）数值占线性层比例
Prefill（全部 T 个 token）4·L·T²·dT=5k：46 TF15%（不是 <1%，不可忽略）
T=32k：1,879 TF98%（长上下文注意力反超 FFN）

推论：长上下文 prefill 的 T² 项会主导算力，所以有 FlashAttention（不减少 FLOPs，只减少 HBM 读写）和稀疏/滑动窗口注意力（真正减少 FLOPs）。decode 即使多算 24% FLOPs，瓶颈仍是读 KV 的带宽，结论不变。

串起来的三条工程结论：

  1. PD 分离：两种相反的负载必须拆——prefill 池配算力、decode 池配大显存带宽；

两池之间传 KV（RDMA（Remote Direct Memory Access）），传 0.96GB 只需 20ms，远小于重算的 300ms，所以值得。

  1. Chunked prefill：不分离时，5,000 token 的 prefill 会独占 GPU 几十毫秒，

decode 请求的 TPOT 会抖；把 prefill 切成小块和 decode 请求混批，平滑 TPOT。

  1. 前缀缓存 / GQA / MLA：全部作用在让 KV 更少、更可复用上——

prefill 少算（命中率 70% 时只算 1,500 token），decode 少读（KV 压缩到 1/4）。

一个反直觉点：prefill 也要读 30GB 权重，但 5,000 token 摊下来每 token 权重成本 = 30GB/5000 = 6MB；decode 每 token 读 30GB 权重 + 越来越长的 KV。所以同样一个 token，decode 比 prefill"贵"在访存，不在算力。

077. 三个误区

误区 1：参数量 × 2 = 显存。只在 FP16 成立。FP8 减半，INT4 再减半，MoE 还要加专家并行的副本开销。

误区 2：batch 越大吞吐越高。到 KV 主导时饱和；再大只会把 p99 拉长、把显存挤爆。

误区 3：TP 能线性加速。8 卡 TP 实测通常只有 3–5 倍，通信和效率会吃掉剩余部分。

087.5 失败模式：五个算错的地方

下面五个错误都能让容量算错 2 倍以上，而且都不报错，只是数字不对。

现象根因怎么发现怎么修
算出的显存总比实测小 15%只算了权重和 KV，漏了激活、workspace、显存碎片nvidia-smi 对比公式结果预留 15%–20%，别算到 100%
KV 少算一半忘了 K 和 V 是两份，且每层各有一份拿引擎日志里 kv_cache_size 核对公式里显式写 ×2×层数
按算力推的吞吐达不到实际卡在带宽上（decode 小 batch）ncu 看 HBM 利用率是否接近 100%用 roofline 判断，别只看 TFLOPS
单卡能跑，8 卡 OOM忘了通信 buffer 与 NCCL 缓冲逐卡看显存曲线每卡留 2–4 GB
理论 FLOPs 与实测差 3 倍拿峰值算 MFU，不是拿可达值用实测 TFLOPS 反推MFU 按 35%–45% 估

最后一条最容易被忽略：卡上标的 1,979 TFLOPS 是稠密 FP16 峰值，注意力与 GEMM 混跑能到 35%–45% 就算不错（第 10 章 §10）。按峰值算出来的卡数，落地必然不够。
