并行策略与集合通信（读懂 TP/EP 与 all-reduce/all-to-all）

迁移自 v1 ch02a-parallelism.md。文中引用"第 N 章"为 v1 旧编号，与 v3 的对应关系见 ../../MIGRATION.md。

这是第 02 章的必备前置。读不懂 all-to-all，就不可能真正理解 MoE 推理为什么贵。

01A.0 问题：单卡为什么不够

200B 模型 FP8 权重 = 200 GB，H800 单卡 80 GB，装都装不下——这是并行的第一条理由。第二条是算力：prefill 一个 5K token 请求需要 2 × 30B × 5000 = 3.0e14 FLOP，单卡 1.98 PFLOPS 下要 0.43 s（还没算 MFU），乘上 7000 QPS 的峰值直接不可行。

约束单卡数字后果对应并行
显存80 GB vs 200 GB 权重放不下TP / PP / EP
算力1.98 PFLOPSprefill 太慢TP / EP
带宽3.35 TB/sdecode 每步读 30 GB → 8.96 ms并行解决不了，只能加卡

结论先行：TP 解决"放不下"和"单步太慢"，EP 解决"专家太多放不下"，PP 解决"跨机放得下但延迟高"。并行不是越多越好——每加一级，就多一次通信，通信是这条路上最贵的税。

02A.1 稠密 vs 稀疏：一张表

稠密（Dense）稀疏（MoE）
每 token 算力2 × N_total2 × N_active
显存占用N_totalN_total（全部专家都要装）
通信TP 的 all-reduceTP + EP 的 all-to-all
延迟可预测性高低（路由不均、专家倾斜）
小 batch 表现好差（专家利用率低）
大 batch 表现线性变贵摊薄后更便宜
工程复杂度低高（路由、均衡、通信）
典型用途延迟敏感、小模型大模型、追求"每 FLOP 的质量"

一句话：稀疏是用显存和通信换算力；稠密是用算力换简单和稳定。

什么时候稀疏不划算：

  • batch 很小（每个专家只分到几个 token，算力省了但通信没省）；
  • 网络差（all-to-all 打满，GPU 等网络）；
  • 延迟敏感（路由 + 通信让 p99 抖动）。

03A.2 四种并行：DP / TP / PP / EP

并行切什么通信典型范围
DP 数据并行切 batch，每卡一份完整模型梯度 all-reduce（训练）多机
TP 张量并行切一层内的矩阵（按列/行）每层 all-reduce机内 ≤8 卡（NVLink）
PP 流水并行切层（前几层在 A 卡，后几层在 B 卡）点对点 send/recv多机
EP 专家并行切 MoE 专家（e1–e8 放不同卡）all-to-all多机（IB/RDMA（Remote Direct Memory Access））

04A.3 五种集合通信（用 4 张卡举例）

设 4 张卡各自持有一个向量：

all-reduce：所有人得到"总和"

用途：TP 每层合并部分和；DP 同步梯度。代价：约 2 × (N-1)/N × 数据量，N 越大越接近 2 倍数据量。

all-gather：所有人拿到"全部片段"

用途：TP 的输出拼接、ZeRO 推理取权重。

reduce-scatter：先求和，再各拿一片

用途：ZeRO 梯度分片。all-reduce = reduce-scatter + all-gather，所以能省一半流量。

all-to-all：每个人给每个人发"不同的东西"

这是"转置"：把 [卡][数据块] 变成 [数据块][卡]。用途：EP 的 dispatch/combine；序列并行。

broadcast / send-recv

  • broadcast：一个人发给所有人（配置下发）；
  • send/recv：点对点（PP 的层间传递）。

如果每卡 100ms 出一个 step，光通信就要 17.6 GB/s，还没算拥塞和抖动。所以 MoE 推理只有 RDMA 才跑得动；rail-optimized 网络是为了让一组专家落在同一台交换机下，把跨 leaf 的流量砍掉。

对比 TP 的 all-reduce：每层通信量约等于激活值大小（512×7168×2B≈7.3MB），量级相近，但 TP 在机内走 NVLink（400GB/s），EP 跨机走 IB（400Gb/s=50GB/s）——同样的数据量，跨机贵 8 倍。

06A.5 2:4 结构化稀疏：怎么剪、怎么微调

规则

每 4 个连续权重为一组，只能保留 2 个，另 2 个置零：

硬件（Ampere 之后的稀疏 Tensor Core）读到元数据就跳过零，理论算力 ×2。

三步落地

  1. 选保留谁：按绝对值大小（magnitude）或 SparseGPT 之类的方法，逐组选 2 个；
  2. 固定 mask 继续训练（微调）：被剪掉的权重不再更新，其余权重用较小学习率再训一段，

把掉下去的效果拉回来——这一步就是"并微调"；

  1. 导出稀疏格式：cuSPARSELt / TensorRT-LLM 的 sparse 权重，推理引擎要支持。

为什么生产里很少用

问题说明
精度损失LLM 权重存在离群通道（部分层 >10σ），强行 2:4 精度掉 2–5 pt，微调也只补回一半
引擎支持vLLM/SGLang 对 2:4 稀疏算子支持有限，主流还是 dense
收益打折decode 是带宽受限，算力翻倍不代表速度翻倍（可能只快 1.2–1.5×）
维护成本每换一版模型都要重新剪枝 + 微调 + 验证

结论：2:4 稀疏适合"算力卡脖子、模型固定、愿意做精度补偿"的场景；通用推理平台默认用 dense，把钱花在 KV 压缩和批处理上更划算。

07A.6 RDMA 与 rail-optimized

A.6.1 RDMA：让网卡直接写对方内存

普通 TCP 发数据要经过：用户态 → 内核 socket → 协议栈 → 网卡 → 对方内核 → 用户态，每一跳都有 CPU 拷贝和中断。RDMA 把这套全绕过：

TCPRDMA
延迟20–100 µs2–5 µs
CPU 占用每包都要处理≈0
拷贝次数2–4 次0（零拷贝）
带宽受 CPU 限制100–400 Gb/s 轻松跑满

三种实现：

类型说明现状
InfiniBand原生 RDMA，专用网络性能最好，交换机贵
RoCEv2以太网上的 RDMA便宜，但要配无损网络（PFC/ECN）
iWARP老方案少用

GPUDirect RDMA：网卡直接读写 GPU 显存（走 PCIe/NVLink），不经过主机内存中转——多机推理的 all-to-all 必须开这个，否则多一次拷贝。

代价：RDMA 要求网络无损（丢包重传代价极高），要配 PFC、ECN、DCQCN，运维门槛比普通以太网高一个档次。

A.6.2 rail-optimized：一台机器 8 张卡，8 条独立的"车道"

普通做法：一个节点插 1–2 张网卡，8 张 GPU 共享 → all-to-all 时 8 卡抢一条车道。

rail-optimized：每张 GPU 配一张网卡，各自接到独立的 leaf 交换机（一条 rail）。

关键性质：节点 A 的 GPU3 和节点 B 的 GPU3 通信，只经过 Leaf3 一跳，不经过 spine，不和其他 rail 抢带宽 → 同号 GPU 之间是"非阻塞"的。

为什么这对 EP 特别重要：all-to-all 里，每张 GPU 要和"其他所有卡的对应专家"交换数据。如果拓扑是 rail 对齐的，集合通信库（NCCL）可以把通信组织成"同号 GPU 之间"，把大部分流量关在 leaf 内，避免 spine 拥塞。

代价：8 张网卡 + 8 台 leaf 交换机，布线和成本都上去了；跨 rail 的流量仍要过 spine，所以专家放置策略要尽量"同号优先"。

同一个 14.7MB 的 all-to-all，走 NVLink 是 0.04ms，走 IB 是 0.3ms，走 TCP 可能 1ms+。这就是为什么"跨机贵 8 倍"不是形容词，是算出来的。

A.6.4 PFC / ECN / DCQCN：无损网络的三件套

RoCEv2 跑在以太网上，而以太网默认会丢包。RDMA 最怕丢包，所以要把网络改造成"无损"：

机制全称干什么类比
PFCPriority Flow Control（802.1Qbb）交换机队列快满时，向上游发 PAUSE 帧，让它暂停发送某个优先级的流量路口红灯，整条路停下
ECNExplicit Congestion Notification（RFC 3168）队列超过阈值时，交换机在包头打拥塞标记，接收方通知发送方减速在车上贴"前方拥堵"标签
DCQCNDatacenter QCNRoCE 网卡收到拥塞通知后降速，再逐步恢复的完整算法看到标签后松油门的规则

为什么要两个一起用：ECN 是"提前减速"（治本），PFC 是"马上刹停"（兜底）。只靠 PFC 会有两个严重问题：

  • 拥塞传播：一台交换机 PAUSE 上游，上游又 PAUSE 它的上游，一路传回去；
  • PFC 死锁：缓冲区形成循环等待，整个网络卡死，要手动恢复。

所以好的无损网络是"ECN/DCQCN 把速度调平滑，PFC 尽量不触发，只在极端情况兜底"。

A.6.5 丢包为什么对 RDMA 是灾难

TCP 是为"会丢包的网络"设计的（SACK、快重传），RDMA 不是。丢一个包会发生：

  1. RDMA 可靠连接要重传整个窗口（go-back-N），不是只补一个包；
  2. 集合通信有 barrier：all-reduce 必须等所有 GPU 都到齐——

一张卡等重传，其余几十张卡全部空转；

  1. 显存里为这次通信准备的 buffer 不能释放，后续步骤全堵住；
  2. 延迟从微秒跳到毫秒，NCCL 超时（训练任务默认十几分钟无进展会直接崩溃重启）。

类比：32 个人抬一根长木头，一个人绊倒，全部人停住；

如果木头掉了（超时），整趟重来。TCP 像各自跑步，摔一个不影响别人。

0.1% 的丢包率在普通 Web 服务里毫无感觉，在 RDMA 集群里等于事故。

A.6.6 rail 与 NCCL

rail（轨道）：一张物理网卡 + 它直连的那组 leaf 交换机构成一个网络平面。一张 GPU 对应一条 rail，8 张 GPU 的节点就有 8 条互不共享的 rail。"多 rail"就是多条并行的独立平面，同号 GPU 之间永远在同一条 rail 上一跳直达。

NCCL（NVIDIA Collective Communications Library）：GPU 集合通信库，PyTorch 里的 all_reduce / all_to_all 最终都是调它。它做两件事：

  1. 拓扑发现：启动时探测 NVLink、PCIe、网卡怎么连，给每张 GPU 编号；
  2. 选算法和路由：ring 还是 tree、走哪张网卡、是否 rail 对齐——

发现 GPU i 都在 rail i 上，就把通信组织成"同号通信"，流量不进 spine。

类比：NCCL 是物流调度系统，NVLink/IB 是高速公路，rail 是专用车道。路修得再好，调度系统不按拓扑发货也会堵。

A.6.7 采购/上云时那句话怎么理解

"跨节点是否 IB 或无损 RoCE？"

网络含义能不能跑 EP/PD
InfiniBand原生 RDMA，信用机制天然无损✅ 最佳
无损 RoCEv2以太网 + RDMA + PFC/ECN/DCQCN 全套配置✅ 可以
普通 VPC 以太网多租户、有损、没有无损配置❌ 退回 TCP，慢 8 倍

要追问的四件事：

  1. 网卡型号与带宽（如 ConnectX-7、每 GPU 400Gb/s）；
  2. 是否 rail 对齐（8 卡 8 网，还是 8 卡共享 2 网）；
  3. 是否支持 GPUDirect RDMA（网卡直读写显存）；
  4. 实例能否强制放置在同一 RoCE 子网 / 集群放置组里。

08A.8 NVLink 域：TP 的天然边界

NVLink 是 NVIDIA 的 GPU 间专有互联（不是 PCIe，也不是网络）。H800 一机 8 卡通过板上的 NVSwitch 芯片两两全互联：任意两张卡之间都有400 GB/s 的直连带宽（H100 是 900 GB/s，H800 出口受限版降到 400）。

NVLink 域 = 被这张 NVSwitch 全互联网络覆盖、通信不出机的 GPU 集合：

三层带宽对比：

路径带宽延迟谁走这里
GPU ↔ HBM3.35 TB/sns权重/KV 读取
GPU ↔ GPU（NVLink 域内）400 GB/sµsTP 的 all-reduce
GPU ↔ 跨节点 GPU（IB/RDMA）50 GB/s几 µs–几十 µsEP 的 all-to-all、PD 传 KV

为什么 TP 不出域：TP 每层都要 all-reduce，一次推理 60 层 ×2（attention/FFN）= 上百次。域内走 NVLink 总开销可接受；跨域走 IB，每层通信时间 ×8，TP 的加速比会被吃光。域的大小 = TP 的实际上限：H800/H100 是 8；GB200 NVL72 用机柜级 NVLink Switch把 72 张卡接成一张网，域才扩大到 72。

怎么查自己机器的域：

NCCL 启动时做的"拓扑发现"，本质就是找到这个域，把 TP 通信排在域内、EP 通信走网卡。

K8s 调度含义：一个 TP=8 的 Pod 必须被调度到同一台 8 卡机（单 NUMA 节点），所以资源申请写 nvidia.com/gpu: 8；跨机的 EP 组则要配合放置组 + rail 对齐的网络。

11A.8.4 推翻条件：这个并行策略什么时候不成立

TP=8 是机内 NVLink 下的最优解，但它有明确边界：

前提不成立时换成什么
单机放得下 8 卡且 NVLink 全互联卡间只有 PCIeTP 降到 2，靠 PP 补
权重能切进 8 张卡权重 > 8×80 GB加 PP，接受跨机
跨机带宽 ≥ 50 GB/s只有 25 Gbps 以太放弃跨机 EP，改机内 TP + 跨机 PP

下面三条就是它的推翻条件，最容易被踩到的是第三条。EP 的 all-to-all 对带宽极敏感，带宽不够时通信会把收益吃光，不如老老实实 TP+PP。账可以自己算：25 Gbps 以太传 8 MB 的 all-to-all 消息约 2.7 ms，EP 每步两次就是 5.4 ms，占 25 ms TPOT 的 21%——带宽再低一半，通信就吃掉四成 decode 时间。

12A.9 自测

  1. TP=8 时，一个线性层要做几次 all-reduce？为什么 TP 一般不跨机？
  2. EP 的 all-to-all 传的是什么？为什么它是 MoE 推理的瓶颈？
  3. all-reduce 和 all-to-all 的区别，用一句话说清。
  4. 2:4 稀疏的"2 倍"为什么在 decode 上拿不到？
  5. 什么情况下 MoE 反而不如稠密模型划算？
参考答案
  1. 每层 1 次（前向），因为要把各卡的部分和加起来；跨机 all-reduce 走 IB，带宽只有 NVLink 的 1/8，延迟高，所以 TP 限制在机内。
  2. 传 token 的隐藏状态（dispatch 送去专家，combine 送回结果）；量大、突发、跨机，且专家分布不均会加剧拥塞。
  3. all-reduce 是"大家求和后人人都有全量结果"；all-to-all 是"人人把不同的数据发给不同的人"，本质是转置。
  4. decode 受显存带宽限制，算力闲置率本就 >80%（MFU <10%）；稀疏只省算力、不省带宽，所以加速有限。
  5. batch 小、网络差、延迟敏感、专家负载严重不均时，MoE 的通信和调度开销会吃掉算力优势。
