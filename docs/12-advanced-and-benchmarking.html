011. 问题：压测过的配置，上线三小时就崩

三种最常见的翻车：

现场压测时看到的上线后
A并发 1，TTFT 120 ms7000 QPS 时 TTFT 4.2 s，超时雪崩
B固定 512 token 输入，吞吐 3200 tok/s/GPU真实输入 p95 4800 token，吞吐掉到 1100
C闭环 200 并发，QPS 稳定 6500开环到达率 7000 时排队爆炸，p99 到 30 s

根因只有一个：压测测的是"系统最快能跑多快"，而生产要的是"在 SLO 下最多能接多少"。

这两个数字能差 2–3 倍。本章讲的就是怎么测后面那个。

033. 投机解码：什么时候是赚的

3.1 三个符号，先定义清楚

投机解码的做法是：小模型先"猜"几个 token，大模型一次前向把它们全验一遍。

符号含义怎么得到典型值
k每步草稿模型猜几个 token你配的参数（如 USE_NEXTN_DECODE=5）2–8
α单个草稿 token 被接受的概率实测：接受数 ÷ 草稿总数0.4–0.9
c每多验一个草稿，耗时涨多少（无量纲，相对一次普通 step）实测：step 耗时增量 ÷ 基准 step 耗时0.05–1.0

c 的单位是"没有单位"——它是两个时间的比：

```

c = 每多一个草稿 token 增加的耗时（ms/token） ÷ 基准 step 耗时（ms）

= 1.25 ms/token ÷ 25 ms = 0.05 /token

```

所以 1 + k·c 算出来的是耗时倍数（1.2 倍），不是钱。

要换成钱，还得乘一步的成本——那是第 14、17 章的事。

α 是最关键的未知数，它取决于草稿模型和主模型有多像。同一个草稿模型，在"续写代码"上 α 可能 0.85，在"复杂推理"上只有 0.35。

3.2 一条时间轴看懂在干什么

所以问题变成两句话：

  1. 一个 step 平均能出几个 token？ → 记为 E
  2. 一个 step 变贵了多少？ → 记为 1 + k·c

加速比就是这两个数的比。

3.3 E 怎么来的：把"平均"拆成"每个位置的概率"

第 i 个草稿要被接受，必须前面 i 个全对（第 3 个被接受，意味着第 1、2 个也对）。假设每个位置独立、接受率都是 α：

位置被接受的条件概率对期望的贡献
第 1 个草稿d1 对αα
第 2 个草稿d1、d2 都对α²α²
第 3 个草稿前 3 个都对α³α³
第 4 个草稿前 4 个都对α⁴α⁴
修正位目标模型必出 1 个11
E = 1 + α + α² + α³ + α⁴

这就是那个等比数列的来历——它不是凑出来的，是"第 i 个位置要求前 i 个都对"的直接结果。

意思是：每一步平均产出 3.36 个 token，而不是 1 个。

3.4 c 为什么是 0.05 而不是 1

直觉上"验 5 个位置应该贵 5 倍"，但 decode 阶段不是这样算的：

  • 低并发：权重读取占 90% 以上，多算 4 个位置几乎不增加时间 → c ≈ 0.05

（一步 25 ms，多一个草稿只多 1.25 ms）；

  • 高并发：batch 已经塞满，多 4 个位置就是实打实的算力 → c 会一路涨到接近 1。

c 不是常数，它是"GPU 有多忙"的度量。 这一点决定了下一节。

3.5 合起来：S = E / (1 + k·c)

α = 0.8、k = 4、c = 0.05：

对照一下：如果不做投机，一步出 1 个 token、成本 1，S = 1。收益全部来自"一个 step 出多个 token"摊薄了权重读取。

3.6 α 和 k 怎么配：不是越大越好

固定 c = 0.05，扫一遍 α × k：

看 α = 0.4 那一行：k 从 2 加到 6，收益反而下降。因为第 5、6 个草稿的接受概率只有 α⁵ ≈ 1%、α⁶ ≈ 0.4%，但每一个都要付 c = 5% 的成本——赚的比花的多。

判据：只要 α^k > c 就继续加，否则停。

这就是 DeepInfer 默认 k = 5 的原因：α 在 0.6–0.7 时，5 刚好在拐点附近。

044. 压测方法论：五个必须钉死的变量

变量为什么重要怎么固定
输入长度分布固定长度会高估吞吐 2–3 倍用生产采样，或对数正态（p50 800 / p95 4800）
输出长度分布决定 decode 步数记录真实 EOS 分布，别用 max_tokens
并发模型闭环会掩盖排队开环 Poisson 到达
缓存状态冷启动和热缓存差 30%冷/热各测一轮，分开报
是否含网关引擎内 TTFT ≠ 用户 TTFT端到端压测，至少含网关与网络

4.1 闭环 vs 开环：最容易被忽略的一条

这就是 coordinated omission：闭环压测里，系统越慢，压测工具发的越少，于是你永远测不到真实的 p99。生产是开环的，所以压测也必须是开环。

4.2 一个 30 行的开环压测脚本

三个坑：limit=0 不设连接上限、客户端要多核、时钟要 NTP 同步。

4.3 长度分布为什么值 3 倍

同一套硬件，只换输入分布：

负载平均输入平均输出单卡吞吐
固定 512 / 2565122563,200 tok/s
均匀 100–2,0001,0502561,900 tok/s
生产分布（p50 800 / p95 4,800）1,2503001,100 tok/s

原因有两个：attention 的计算随长度平方增长；长请求的 KV 常驻，挤掉并发。用固定长度压测，等于给系统开了一张 3 倍的假支票。

055. 三个必测场景

场景怎么打通过标准
稳态容量阶梯加压 500→8000 QPS，每档 5 分钟找到 TTFT p95 = 800 ms 的拐点
尖峰0→3× 峰值，持续 30 s不雪崩；恢复时间 <60 s
长稳24 小时，70% 负载KV 碎片不涨、内存无泄漏、p95 不漂移

尖峰测试的关键不是"扛住"，是"扛不住时怎么退化"：是拒绝新请求（好），还是所有请求一起变慢（坏）。这就是第 24 章背压要解决的问题。

长上下文还要单测一层：在 32K 上下文里埋 10 个事实（needle-in-a-haystack），看召回率。吞吐达标但召回掉 3 个点，等于这个配置不能用——性能达标不等于能力达标。

077. 五个常见误判

现象根因正确做法
压到 5000 QPS 很稳，上线 3000 就崩闭环压测掩盖排队改开环 Poisson
引擎 TTFT 200 ms，用户看到 1500 ms没算网关、排队、网络端到端压测

第二条最普遍：引擎内指标和用户体感之间，隔着 3–4 跳（第 8 章的 12 跳链路里，网关 + 排队 + 网络约占 300–800 ms）。只压引擎，等于只测了一半。

099. 没有同规模环境怎么压

2512 卡的集群，测试环境不可能也是 2512 卡。这是所有大规模系统的共同处境。

9.1 换问题：不复制规模，测单位产出

把"集群能扛多少 QPS"拆成两个独立的问题：

第一个问题 8 张卡就能回答，第二个是采购数字，第三个是经验系数。整条链里，只有"规模折扣"需要大规模才能测准——而它可以靠分段验证逼近。

9.2 四层测试：每层只需要很少的卡

层规模测什么能发现发现不了
L1 单机1–8 卡单卡吞吐-延迟曲线、SLO 拐点引擎调优、batch 上限任何跨机问题
L2 小集群32–64 卡PD 比例、路由、前缀缓存命中组间干扰、负载不均网络拥塞
L3 影子512 卡 + 5% 真实流量端到端 SLO、真实分布网关、排队、长尾全量故障叠加
L4 生产2512 卡只做混沌与故障演练，不做压测重调度风暴、级联失败—

关键认知：L4 不是用来压的，是用来"打坏"的。压测找边界，混沌找塌陷。

9.3 外推三步，加三个折扣

步骤做法我们的数
① 测单卡L1 上找 TTFT p95 = 800 ms 的拐点2.8 QPS/卡（7000 ÷ 2512）
② 乘卡数线性放大7000 QPS
③ 打折扣见下表见下
折扣典型值来源
网络与调度损耗8%–15%L2 上对比"单机组"与"跨机组"
故障预留10%一台挂掉后的重调度窗口
碎片与预热5%冷启动、KV 未命中
合计约 1.25×与第 1 章的 ×1.3 余量对应

注意：单卡测的是"混合口径"（prefill + decode 一起），不能拿去和 decode 单卡的3,500 tok/s 比较——两者不是同一个指标。

9.4 没有真实流量，用三种替代

方式成本真实度适用层
合成负载（Poisson + 生产长度分布）极低中L1、L2
录制回放（生产请求脱敏后重放）中高L2、L3
分流灰度（5% 真实用户）低（但要有用户）最高L3

回放有个坑：工具调用要 mock，否则测试集群会真的去查订单、发短信。

9.5 只有真实规模才暴露的五件事

诚实地说，下面这些在小集群上永远测不出来，只能靠分批上线逼近：

问题什么时候炸怎么防
spine 层网络拥塞跨 POD 的 all-to-all 占比升高时分批扩，每批不超过一个 spine
调度器与元数据压力节点数 > 500 后线性变差压测 etcd/调度器本身
模型加载带宽一次发布拉起 2512 个副本限制并发拉取，用 P2P 分发
故障叠加一台挂 → 重调度 → 雪崩混沌演练，故意杀节点
冷缓存击穿全量重启后前缀缓存全空灰度重启，控制冷启动比例

分批上线的节奏：64 → 256 → 512 → 1024 → 全量，每批至少观察 24 小时。

9.6 仿真器：唯一能"免费"跑 2512 卡的办法

把 L1 测到的服务时间分布（不是均值）作为输入，用离散事件仿真跑 2512 卡的排队。

能回答不能回答
P:D 比例取多少最省网络拥塞
路由策略 A/B 谁更好硬件故障
峰值时排队多长缓存命中率

工具不复杂：SimPy 或自己写 200 行事件循环。仿真不能替代压测，但能把"试错成本"从 2512 卡降到 0 卡。

9.7 仿真器的三个要素与一条可信判据

它跑得快的真正原因不是"算得省"，是时间可以快进：不执行模型，只按事件推进时钟。

要素建模什么数据从哪来
到达过程请求何时来生产日志（Poisson 或实测轨迹）
服务时间prefill / 一个 decode step 多久L1 实测的分布，不是均值
调度规则batching、抢占、KV 上限引擎源码里的真实逻辑

开源参考：Vidur（MIT，微软）——LLM 推理仿真器，支持连续批处理与多种并行策略，可作为自研的对照基线。

可信判据：拿 L2 小集群的一次真实实验做回放，仿真出的 p95 误差 < 15% 才敢用于决策。达不到，就只是漂亮的数字。

1010. 过载怎么测：测的不是"扛住"，是"退化曲线"

设计容量 7000 QPS，那 10,500 QPS 打进来会发生什么？这才是生产最关心的问题。

过载测试的产出不是"最大 QPS"，是三条曲线：

10.1 好形状 vs 坏形状

10.2 五级降级阶梯（先设计，再测）

顺序不能反：先牺牲"锦上添花"（投机、长度），最后才牺牲可用性（拒绝）。这也呼应第 1 章的优先级：可用性 > 体验 > 成本。

拒绝发生的位置入口快速拒绝（<50 ms）排队 30 s 后超时
拒绝的语义429 + Retry-After + 可重试标记500 或直接断连
公平性按租户配额，小客户不被饿死先到先得，大客户挤爆
降级是否自动阈值触发、可观测靠人手动切
GPU 保护KV 水位不超 90%，不 OOM打满后 OOM 重启
恢复撤压后 5 min 内回到 SLO越等越糟
级联无重试风暴客户端重试把负载放大 2×

10.5 小集群怎么测这个

好消息：过载行为主要由控制面决定，与集群规模弱相关。

限流阈值、队列长度、降级触发点都是"按设计容量比例"配置的。在 64 卡的小集群上把阈值等比缩到 1/40，压到 1.5× 设计容量，看到的退化曲线和生产是同一形状。

参数生产（2512 卡）测试（64 卡）
设计容量7000 QPS175 QPS
限流阈值7200 QPS180 QPS
队列上限2.5 万在飞625 在飞
降级触发排队 > 2 s排队 > 2 s（不变）

只有"排队时间"这类时间量纲的阈值不用缩放——这也是为什么过载测试在小集群上特别可信。

10.6 观测：判断"优雅"需要的六个指标

指标看什么
goodput（达标请求/秒）核心，别的都是解释它
丢弃率与丢弃位置入口拒绝比队列超时好
队列深度是否无界增长
KV 水位是否逼近 OOM
降级命中计数哪一级被触发
客户端重试率是否在放大故障

1111. 验收：怎么证明压测是可信的

检查项通过标准
是否开环到达过程是 Poisson，不是固定并发
客户端不是瓶颈压测机 CPU <60%，无连接池上限
长度分布来自生产有采样依据，不是拍脑袋
冷/热缓存分别报两个数都给了
端到端覆盖至少含网关与网络
配置指纹完整六项齐全
长稳 ≥24h有 p95 漂移曲线

七条里缺任何一条，这份报告只能当"参考"，不能进容量模型。

1212. 收口

**压测不是找系统的极限，是找 SLO 的边界。

极限告诉你"还能撑多久"，边界告诉你"该在哪里停"。**
