011. 问题：每秒 58 万次块分配

一个 2,000 万 DAU 的平台，每天 1.5 亿轮对话、平均 5,350 token：

每秒 58 万次 KV 块分配与释放。 每一次都要回答三个问题：

  1. 有没有空闲块？（分配）
  2. 没有的话，能不能挤掉部分缓存？（淘汰）
  3. 还不能的话，牺牲哪个正在跑的请求？（抢占）

三个问题对应三套机制，混在一起讲必然讲糊。

022. 三种回收不是一回事

类型触发时机影响负责模块用户感知
① 空闲块回收请求正常结束无BlockAllocator无
② 前缀缓存淘汰要腾空间给新请求下次命中率下降LRU / 基数树变慢一点
③ 抢占 preemption正在跑的请求被夺走 KV该请求回炉Scheduler可见卡顿（1.6 s）

日常说的"淘汰"是 ②，但生产事故多来自 ③——因为它直接让用户看到一个正在输出的回答突然停住。

最危险的默认值是"队列无上限"：流量翻倍时队列长到 5,000，TTFT 变成 30 分钟，所有请求都在等一个永远不会释放的块——成功率 100%，体验归零。

3.2 队列会不会满：上限怎么定，满了怎么办

先分清三种"放不下"，它们的行为完全不同：

位置默认上限满了的表现
网关熔断器1,024503，快速返回
引擎 waiting 队列无上限不报错，延迟无限涨
KV 块池208,000 块请求卡在 waiting

关键：引擎队列不会"满"，它只会一直涨。

涨到进程 OOM 被 kill，所有在飞请求一起丢——这比"满了直接拒绝"糟糕一个量级。

所以队列必须由我们自己设上限。定法是一条除法：

配 5,000 的队列，等于向用户承诺"最多等 30 分钟"。

3.3 满了之后：四种策略

策略做法评价
拒绝新请求429 + Retry-After: 5默认选择，保护已接受的
丢最老的踢掉队头绝对不要——它最接近完成，丢掉最亏
降级切小模型 / 缩短 max_tokens体验降级，但保住可用性
带超时排队等 30 s 仍未开始就 503推荐，与拒绝组合

实现位置有四种，选一种或叠加：

位置手段优点
应用侧有界 Semaphore / 计数器精确到实例，最可控
网关Envoy max_pending_requests: 84挡在最外层，省资源
令牌桶按 QPS 与 token 双维度限速防长请求偷额度
引擎调小 max_num_seqs间接减少排队，不精确

拒绝必须满足三个条件，否则会把过载放大成雪崩：

  1. 快：<50 ms 返回，不要先排队再超时；
  2. 可重试：429 + Retry-After，明确告诉客户端多久后再来；
  3. 有预算：客户端重试要有上限——1.2 倍过载能被无脑重试放大成 2.4 倍（第 2 章 §8.2）。

3.4 三个必须观测的数

排队时长比队列深度更重要：队列 200 但每秒消化 300，用户等 0.7 秒；队列 50 但每秒只消化 5，用户等 10 秒。

背压与准入的完整设计见第 25 章。

关键：block table 是间接层，所以物理块可以不连续——这正是 PagedAttention 的全部意义（第 10 章 §4）。

044. 前缀缓存淘汰：叶子 LRU + 引用计数

4.1 为什么是树，为什么从叶子删

前缀缓存的结构天然是树（RadixAttention）：

两条硬约束：

约束原因
从叶子开始删父节点被子节点引用，先删父会让子悬空
ref > 0 不能删正在被请求使用，删了就是读写已释放内存

vLLM 是扁平版：块有内容哈希和引用计数，空闲块进 LRU 队列，分配时从队尾取。SGLang 是树版：同上，但粒度到 token，且多一层 HiCache 下沉。

4.2 没有 TTL：为什么 KV 不需要时间过期

这是最容易被问住的一点：KV 缓存不设过期时间。

同一段 token、同一个权重，算出来的 KV 永远一样。既然结果恒定，"过期"就不成立。

所以主流引擎里没有时间过期逻辑，只有两种回收：引用归零、容量压力。

情况算过期吗说明
请求结束❌块回 free list，但内容还在，下次能命中
权重版本变了✅ 真失效旧 KV 用旧权重算的，必须整批作废
显存压力❌被挤掉，不是过期
租户隔离❌逻辑隔离，与时间无关

唯一的真失效是权重版本——所以第 36 章讲灰度时，第一件事就是"KV 不跨版本共享"。

4.3 位置依赖：只有"从 0 开始的前缀"能复用

这条约束常被忽略。假设公共文本放中间：

因为 RoPE 把位置偏移编进了 K/V：同一段文本在第 0 位和第 12 位算出的 KV 不同。

结论：稳定内容必须放最前面。 这不是编码习惯，是数学要求。

055. 抢占：recompute 还是 swap

5.1 两种做法的代价

做法操作代价公式
recompute丢掉 KV，稍后重跑 prefillL ÷ 20000（prefill 吞吐）
swap搬到 CPU 内存，需要时搬回2 × KV_bytes ÷ 64 GB/s

代入实际数字：

上下文KV 大小recomputeswap 往返谁赢
2K240 MB0.10 s7.5 msswap
8K0.96 GB0.40 s30 msswap
32K3.84 GB1.60 s120 msswap

纸面上 swap 快 13 倍，但 vLLM 默认用 recompute。三个原因：

原因说明
CPU 内存贵3.84 GB/请求 × 数十个被抢占请求 = 几百 GB 主机内存
PCIe 是共享资源多个 swap 并发会互相拖慢，延迟从 30 ms 涨到数百 ms
批处理摊薄10 个被抢占请求一起重跑 prefill，单请求代价降到 1/5 以下

5.2 怎么选

场景选择
单序列、短上下文（< 8K）recompute（默认）
单序列、超长上下文（> 32K）且主机内存充裕swap
beam search / 多序列组swap（要保住多个分支的 KV）
抢占频繁（每秒 >1 次）先降 max_num_seqs，别急着改抢占策略

066. 卸载：把 KV 搬到显存之外

6.1 谁来做：三种组件形态

"卸载"不是一个开关，而是三种不同的部署形态，复杂度递增：

形态组件谁负责搬运典型实现适用
① 引擎内置block manager 自带两级池引擎自己--cpu-offload-gb、vLLM swap space单机，快速试水
② 外挂连接器KV Connector 接口 + 外部存储客户端引擎调接口，外部服务存LMCache connector希望复用已有存储
③ 独立服务独立的 KV Store 集群专门的传输层（RDMA）Mooncake Store跨机共享、全球复用

对应的角色分工：

角色职责
Scheduler决定"这个请求值不值得去远端取"（取比算快才取）
Block manager执行 evict → 发起 offload 写、发起 fetch 读
Connector / Store client序列化、传输、重试、校验
KV Store 服务存块、按哈希索引、自己再做一层 LRU
平台 SRE配容量、配租户配额、配保留策略

6.2 一次卸载的完整动作序列

第 ② 步是最容易被跳过的一步：如果不筛选就全量下沉，等于把显存压力原封不动转移成网络压力。

6.3 什么时候值得：一笔除法

传输路径带宽0.96 GB（8K 请求）耗时
NVLink900 GB/s1 ms
PCIe 4.0 x1664 GB/s15 ms
RDMA 400 Gbps50 GB/s19 ms

对比重算：8K prefill ≈ 400 ms。

只要命中率超过 10%，下沉就是赚的。 但前提是"这些前缀真的会被再次用到"——纯随机单轮问答，命中率接近 0，下沉等于白搬。

场景前缀复用率值得吗
Agent 多轮（同一会话反复带历史）高✅ 非常值得
客服（同一套系统提示 + 工具 schema）很高✅ 值得
一次性文档问答低❌ 不如重算
代码补全（同一文件反复改）高✅ 值得

6.4 还有哪些手段：不一定要搬

卸载只是"扩容"的一种，同一目标还有四条路：

手段做法等效收益代价
KV 量化FP16 → FP8/FP4容量 ×2 或 ×4精度掉点（第 6 章）
稀疏注意力只保留滑动窗口内 KV容量 ×N依赖模型结构（第 10 章 §9）
只下沉高频前缀按访问计数筛选传输量 −80%需要计数与阈值
KV 预计算快照离线算好公共提示的 KV，启动时分发冷启动 TTFT −60%版本必须严格对齐

最后一条特别实用：把"系统提示 + 工具 schema"这 2.5K token 的 KV 离线算好，新实例启动时直接加载，冷启动的首个请求不用再 prefill。

077. 多租户：朴素 LRU 会闯祸

7.1 不公平从哪来

前缀缓存是全局共享的（否则复用率为零），但 LRU 只看"最近访问"，不看"谁在用"：

这不是容量问题，是分配问题。 扩容治不了，只会让 A 占得更多。

7.2 四种解法对比

方案做法优点缺点
硬分区每租户独立缓存，互不可见隔离彻底、实现简单碎片浪费，小租户吃不满
软配额 + 加权淘汰超配额者优先被淘汰利用率高需要配额中心
SLA 分级金牌租户保底池商业上可解释配置复杂
租户哈希命名空间缓存键带租户盐安全（防串号）减少跨租户复用

实践组合：命名空间（安全）+ 软配额（公平）+ 金牌保底（商业）。

7.3 安全性：跨租户命中 = 数据泄露

这一条比公平性更严重。如果两个租户的提示词恰好相同，哈希就会碰撞到同一个缓存条目——用户在响应里可能看到别人的上下文。

088. 指标与调参

8.1 四个必看指标

8.2 max_num_seqs 怎么定

它决定"一个 batch 最多装几个请求"，直接影响会不会频繁抢占：

max_num_seqs单实例并发抢占频率吞吐TTFT
64低几乎为 0低（-35%）好
128中低中好
256高偶发高一般
512很高频繁反而下降差

我们的账：400 GB KV ÷ 0.96 GB（8K 请求）= 416 个上限。

配 256 时有 40% 余量，但长请求会吃掉它：一个 32K 请求占 3.84 GB = 4 个 8K 请求的额度。峰值时长请求占比升高，等效并发就会突破 416，于是开始抢占。

建议配 256，并把 32K 以上请求路由到独立池（第 11 章）。

1010. 验收：七条怎么测

10.1 逐条测法

检查项怎么测通过标准
抢占率压测 30 min，读 num_preemptions_total ÷ 总请求<0.1%
前缀命中率跑生产分布流量，读 prefix_cache_hit_rate≥85%

前六条都能靠跑和看指标完成，第七条必须专门设计测试，而且它一旦出错是静默的。

1111. 备选方案：如果不这么做会怎样

备选做法代价为什么没成主流
预分配最大长度（PagedAttention 之前）按 32K 预留 → 实际用 2K 时浪费 94% 显存并发上不去
连续分配 + 搬移每次扩容要拷贝整段 KV拷贝成本随长度平方增长
固定块但不共享无前缀复用命中率 0，等于没有缓存
全量下沉 CPU每次 decode 都过 PCIe带宽被打爆，TPOT 从 25 ms 涨到 200 ms+
不分页 + 大页（2 MB）内部碎片短请求浪费，长请求仍不连续

PagedAttention 赢在"间接层"：物理可以不连续，逻辑连续由 block table 保证。这个思路和操作系统的虚拟内存完全同构——只是页大小从 4 KB 变成了 1.92 MB。

替代路线里唯一有竞争力的是 vAttention（动态显存 + CUDA VMM API 直接映射），它省掉了 block table 的软件开销，但要求驱动与硬件支持，可移植性差。

1212. 收口

**KV 的生命周期里没有"过期"，只有"不够用"。

淘汰是容量问题，抢占是并发问题——把两者混在一起调，永远调不对。**
